22.1 CLR 寄宿（CLR Hosting）

核心问题：Windows 只认 PE 文件，不认托管代码。那 CLR 自己又是怎么"挂"进一个 Windows 进程里去的？
关键事实：
  • ••
    CLR 被实现为一个 COM 服务器（DLL），有标准 COM 接口和 GUID，安装 .NET Framework 时在 Windows 注册表里注册
  • ••
    任何 Windows 应用程序都可以寄宿（host）CLR，步骤大致是：
    1. 1.1.
      Windows 检查 EXE 头，决定创建 32 位 / 64 位 / WoW64 进程
    2. 2.2.
      把对应版本的 MSCorEE.dll（垫片 shim）加载进进程
    3. 3.3.
      主线程调用 CLRCreateInstance → 拿到 ICLRMetaHost → GetRuntime 拿到 ICLRRuntimeInfo → GetInterface 拿到 ICLRRuntimeHost
  • ••
    通过 ICLRRuntimeHost，宿主可以做五件事：设置宿主管理器、获取 CLR 管理器、初始化并启动 CLR、加载程序集并执行代码、停止 CLR
几个必须记住的细节：
💡 CLR 一旦加载进进程，永远不能卸载——唯一能把它从进程里去掉的办法是终止整个进程
💡 .NET Framework 4 之前，一个进程只能加载一个版本的 CLR（v1.0 / v1.1 / v2.0 三选一）；.NET Framework 4 开始支持 v2.0 和 v4.0 并存于同一进程
宿主通过"宿主管理器"可以深度参与 CLR 的决策：内存分配、线程调度与同步、程序集加载、垃圾回收启停通知、超时通知；通过"CLR 管理器"可以禁止某些类/成员被使用，还能指定当 AppDomain 卸载、CLR 停止、堆栈溢出等事件发生时调用哪个方法

22.2 AppDomain

一句话定义：AppDomain 是一组程序集的逻辑容器，它的唯一作用就是隔离。
CLR COM 服务器初始化时会自动创建一个 AppDomain，称为默认 AppDomain——它只有在 Windows 进程终止时才会被销毁。宿主也可以通过非托管 COM 接口或托管 API 要求 CLR 创建额外的 AppDomain。
AppDomain 提供的四大隔离能力：
能力
说明
代码隔离​
一个 AppDomain 中的代码不能直接访问另一个 AppDomain 创建的对象
可卸载​
AppDomain 可以整体卸载（但不能只卸载其中某个程序集）
可保护​
创建时可施加一个权限集
可配置​
创建后关联一组配置：搜索路径、版本绑定重定向、卷影复制、加载器优化
关于 Loader 堆的重要细节（这是 Richter 讲得最透的部分）：
  • ••
    每个 AppDomain 有自己的 Loader 堆，记录自创建以来访问过的类型
  • ••
    即使两个 AppDomain 都加载了 System.dll，类型对象的内存也不共享，JIT 编译出的本机代码也各自关联
  • ••
    这种"看似浪费"的设计是为了保证：卸载某个 AppDomain 时不会影响其他 AppDomain
  • ••
    例外：MSCorLib.dll（含 System.Object、System.Int32 等核心类型）以 AppDomain 中立方式加载，所有 AppDomain 共享其类型对象，CLR 为它维护一个特殊的 Loader 堆
⚠️ 这是 .NET Framework 的概念。在 .NET Core / .NET 5+ 中，AppDomain 的隔离功能主要由 AssemblyLoadContext 替代

跨越 AppDomain 边界访问对象

既然 AppDomain 之间不能直接访问对象，那跨域调用怎么办？答案是两种"封送（marshaling）"语义：
1. 按引用封送（Marshal-by-Reference）
  • ••
    对象必须派生自 System.MarshalByRefObject
  • ••
    通过 CreateInstanceAndUnwrap 把一个 AppDomain 中的对象按引用封送到另一个 AppDomain，返回的是代理对象
  • ••
    代价：跨边界调用性能较差
2. 按值封送（Marshal-by-Value）
  • ••
    对象未派生自 MarshalByRefObject 但可序列化时采用
  • ••
    CLR 把对象序列化成字节数组，从源 AppDomain 复制到目标 AppDomain 后反序列化，并在目标 AppDomain 加载相应程序集、实例化出新对象（书里称为"精准复制"）
简单说：想跨域传引用就用 MarshalByRefObject，想跨域传副本就让对象可序列化。

卸载 AppDomain

调用 AppDomain.Unload 静态方法即可，但这个方法会阻塞调用线程，CLR 在背后做了一整套动作：
  1. 1.1.
    挂起进程中所有曾执行过托管代码的线程
  2. 2.2.
    检查所有线程栈，找出哪些线程正在被卸载的 AppDomain 中执行，或将来可能返回到该 AppDomain
  3. 3.3.
    强制这些线程抛出 ThreadAbortException，让它们展开调用栈、执行 finally 块做清理
  4. 4.4.
    对正在执行 finally 块、catch 块、类构造函数、临界执行区或非托管代码的线程，不立即中止，等这些代码块执行完再抛异常
  5. 5.5.
    所有相关线程离开 AppDomain 后，CLR 遍历堆，给所有指向该 AppDomain 对象的代理对象打上失效标记——之后再调用这些代理的方法会抛 AppDomainUnloadedException
  6. 6.6.
    强制执行一次垃圾回收，调用待回收对象的 Finalize 方法
  7. 7.7.
    恢复其余线程，AppDomain.Unload 的调用者继续运行
⚠️ 这里有个反常细节：普通未处理异常会让 CLR 杀掉进程，但 ThreadAbortException 如果不被捕获，线程死掉而进程继续运行

监视 AppDomain

CLR 提供了一套应用程序域资源监视（ARM）机制，宿主可以监控每个 AppDomain 的 CPU 时间和内存使用量。
启用方式很简单——设置静态属性：
csharp
AppDomain.MonitoringIsEnabled = true;
书上给出了一个工具类 AppDomainMonitorDelta（实现 IDisposable），它在静态构造函数里打开监视，然后用三个字段跟踪：
  • ••
    m_thisADCpu：TimeSpan 类型，CPU 时间
  • ••
    m_thisADMemoryInUse：当前使用的内存
  • ••
    m_thisADMemoryAllocated：累计分配的内存
通过这个工具类可以在一段代码执行前后对比 AppDomain 的资源消耗增量。

先建立一个核心认知：CLR 本质上是个 DLL

你可能以为 ".NET 程序一运行，CLR 就自动出现了"——其实不是。
真相是：CLR 只是一段 C++ 代码编译出来的 DLL 文件（在 .NET Framework 里叫 clr.dll）。它自己不会自己跑起来，必须有一个 Windows 进程把它加载进去，它才能在那个进程里工作。
💡 "寄宿（Hosting）"这个词的意思就是：让 CLR 寄居在某个 Windows 进程里
谁来当这个"房东"？最常见的房东就是 dotnet.exe 或者 xxx.vshost.exe——也就是你运行 C# 程序时，Windows 真正启动的那个原生 EXE。但这个 EXE 本身是用 C/C++ 写的，它不懂托管代码，它只负责一件事：把 CLR 这个 DLL 请进自己的进程空间。
除了 dotnet.exe，IIS（ASP.NET）、SQL Server、PowerShell​ 等都是 CLR 的房东——它们把自己的进程"借"一块给 CLR 住着，这样就能在自己的进程里跑 C# 代码。这就是"寄宿"这个概念的存在意义。

加载 CLR 的完整链路（重点理解这 4 步）

Windows 启动一个托管程序时，发生的事其实是一条接力赛：
纯文本
Windows 内核
   ↓ ① 创建进程，发现是 .NET 程序
   ↓    于是加载 MSCorEE.dll（垫片）
MSCorEE.dll（垫片 / Shim）
   ↓ ② 根据程序的目标框架版本，找到对应的 clr.dll
   ↓    调用 COM 接口把 CLR 请进来
CLR（clr.dll）
   ↓ ③ 创建默认 AppDomain
   ↓ ④ 加载入口程序集，JIT 开始编译 Main 方法
你的 Main 方法终于跑起来了
逐站解释：

① 垫片 MSCorEE.dll 是什么？

MSCorEE = Microsoft Component Object Runtime Execution Engine。它是 .NET Framework 安装时放到 `C:\Windows\System32` 下的一个很小的 DLL。
为什么需要它？因为一个机器上可能装了多个版本的 CLR（v2.0、v4.0……）。Windows 加载 EXE 时还不知道这个程序到底需要哪个版本的 CLR，所以先统一加载 MSCorEE.dll 这个"中间人"，由它去判断："哦，这个程序是 .NET 4.8 的，那我去加载 v4.0 的 clr.dll"。
📌 你可以把 MSCorEE.dll 理解成CLR 的"前台接待"——你（EXE）来了先找它，它帮你转接到正确的 CLR 版本

② COM 接口是什么鬼？

COM（Component Object Model）​ 是 Windows 上古时期就定下的一种"二进制接口标准"——它规定了：一个 DLL 暴露出来的函数，别人怎么调用它。
CLR 是以 COM 服务器的形式实现的，也就是说它向外暴露了一组标准的 COM 接口。房东进程通过这些接口"遥控"CLR。
Richter 书里提到的那串接口调用：
cpp
CLRCreateInstance()        // 拿到 IMetaHost 工厂
  → GetRuntime()           // 指定版本（如 "v4.0.30319"），拿到 ICLRRuntimeInfo
    → GetInterface()       // 拿到 ICLRRuntimeHost（这才是真正控制 CLR 的把手）
翻译成人话就是：
  • ••
    CLRCreateInstance：跟系统说"我要找个 CLR"
  • ••
    GetRuntime("v4.0.30319")：明确"我要 4.0 这个版本"
  • ••
    GetInterface(ICLRRuntimeHost)：拿到控制 CLR 的遥控器

③ ICLRRuntimeHost 这个"遥控器"能干什么？

拿到这个接口后，宿主就能对 CLR 发号施令了，主要是 5 件事：
能力
通俗解释
设置宿主管理器​
告诉 CLR："内存分配你别全权管，遇到 XX 情况要先问我"
获取 CLR 管理器​
反过来，宿主也可以限制 CLR：比如"不允许加载某某程序集"
初始化并启动 CLR​
按下开机键
加载程序集并执行​
让 CLR 开始干活
停止 CLR​
关机（但其实 CLR 不支持真正卸载，只能随进程死）

④ 为什么"CLR 不能卸载"是个大事？

这是个反直觉的点：DLL 不是可以 FreeLibrary 卸掉的吗？
CLR 特殊。因为它一旦启动，就会在进程里创建一堆内部状态（线程池、GC 堆、类型系统、JIT 缓存……）。这些状态深度交织，微软觉得做"部分卸载"风险太大，干脆不支持。
所以规则是：CLR 加载后，除非整个进程退出，否则它永远在那。这也是为什么：
  • ••
    IIS 里你改了 web.config，想让 CLR 重新加载？不行，必须重启整个 w3wp.exe 进程
  • ••
    想在一个进程里切换 CLR 版本？.NET Framework 4 之前完全不行，4.0 开始才允许 v2.0 + v4.0 两个 CLR 并存（注意是并存，不是替换）

宿主管理器和 CLR 管理器：谁说了算？

这是本节最容易懵的地方。简单说就是双向控制：
纯文本
┌─────────────┐
        │   宿主进程   │
        └──────┬──────┘
    设置宿主管理器│
    （宿主→CLR）│
               ↓
        ┌─────────────┐
        │     CLR     │
        └──────▲──────┘
               │
    获取CLR管理器│
    （CLR→宿主）│
        ┌──────┴──────┐
        │   宿主回调   │
        └─────────────┘
  • ••
    宿主管理器（Host Manager）：宿主主动设置给 CLR 的一组"政策"。比如宿主可以说："内存紧张时先通知我"、"线程调度你要听我的"、"程序集加载要经过我批准"
  • ••
    CLR 管理器：宿主通过它反向限制 CLR。比如："System.IO.File 的 Delete 方法不准用"、"AppDomain 卸载时要回调我的 XX 方法"
💡 为什么要这么复杂？因为像 SQL Server 这种宿主，它本身就是个庞大的 C++ 程序，CLR 只是它的一个"插件"。宿主必须能压制 CLR，否则 CLR 乱分配内存、乱开线程，SQL Server 就崩了

把整个流程串成一句话

当你双击一个 .exe 文件：
  1. 1.1.
    Windows 创建一个原生进程
  2. 2.2.
    发现这是 .NET 程序，加载 MSCorEE.dll 这个垫片
  3. 3.3.
    垫片根据程序版本，找到对应的 clr.dll 并加载
  4. 4.4.
    宿主通过 COM 接口 ICLRRuntimeHost，启动 CLR
  5. 5.5.
    CLR 创建默认 AppDomain，加载你的程序集，JIT 编译 Main 方法
  6. 6.6.
    你的 C# 代码终于开始执行

这节你只需要记住 3 件事

🎯 第一：CLR 是个 DLL，不是什么魔法。它必须被某个 Windows 进程"请"进去才能工作，这个过程叫寄宿
🎯 第二：MSCorEE.dll 是垫片（前台），clr.dll 才是真正的 CLR（后台）。宿主通过 COM 接口 ICLRRuntimeHost 遥控 CLR

一、先回答最核心的问题：运行 C# 程序前，要不要装"dotnet 环境"？

要的。​ 但更准确的说法是：要在机器上运行 C# 程序，这台机器必须有对应的 .NET 运行时（Runtime）。
为什么？因为 C# 代码编译后不是 CPU 能直接执行的机器码，而是一种叫 CIL（通用中间语言）​ 的东西。CPU 不认识 CIL，必须有个"翻译官"在程序运行的时候把 CIL 一句句翻译成机器码——这个翻译官就是 CLR（公共语言运行时），而 CLR 就包含在 .NET 运行时里。
📌 所以"装 dotnet 环境"的本质 = 在机器上安装 CLR + 基础类库，让这台机器具备"执行 CIL"的能力

  • ••

  • ••

  • ••

二、AppDomain 到底是什么？

定义：AppDomain 是 CLR 提供的一种逻辑容器，用来装一组程序集（Assembly）。它是隔离的单元、卸载的单元、权限的单元、配置的单元。
CLR 启动时，会自动创建一个 AppDomain，叫默认 AppDomain（Default AppDomain）。你的 Main 方法就跑在这个默认 AppDomain 里。
但你完全可以自己再创建更多的 AppDomain：
csharp
// 在当前进程里再建一个 AppDomain
AppDomain newDomain = AppDomain.CreateDomain("MyPluginDomain");

// 在新 AppDomain 里加载一个程序集并执行
newDomain.ExecuteAssembly("Plugin.dll");

// 用完就扔——整个 AppDomain 被卸载，里面的所有代码、对象、内存全部回收
AppDomain.Unload(newDomain);
📌 关键点：AppDomain 可以卸载，但进程不能。一个进程里可以有多个 AppDomain，卸载其中一个，其他的不受影响，进程本身也不受影响。

三、AppDomain 提供的四大能力

书里总结了 AppDomain 的四个核心特性，我一个个讲：

1. 代码隔离（Isolation）

不同 AppDomain 里的代码不能直接互相访问对象。
csharp
// 在默认 AppDomain 里
var obj = new MyClass();  // MyClass 在默认 AppDomain

// 在另一个 AppDomain 里
// 无法直接拿到上面那个 obj！
为什么？因为 AppDomain 是"逻辑进程"，跨 AppDomain 访问对象就像跨进程——必须经过封送（Marshaling）。这就引出了下面的重点。

2. 可卸载（Unloadable）

AppDomain.Unload(domain) 可以把整个 domain 卸掉，里面所有的：
  • ••
    程序集
  • ••
    类型对象
  • ••
    已创建的对象实例
  • ••
    分配的堆内存
……全部被 GC 回收。这是 AppDomain 最有价值的能力——你可以动态加载插件，用完即弃，不污染主程序。

3. 可保护（Configurable Security）

创建 AppDomain 时可以给它指定一个权限集（Permission Set）。比如你可以创建一个"受限 AppDomain"，里面的代码：
  • ••
    ❌ 不能访问文件系统
  • ••
    ❌ 不能访问网络
  • ••
    ❌ 不能调用 P/Invoke
这就实现了沙箱（Sandbox）——用来跑不可信的第三方代码。

4. 可配置（Configurable）

每个 AppDomain 可以有不同的配置：
  • ••
    搜索路径：去哪里找程序集
  • ••
    版本绑定重定向：程序集版本冲突时怎么处理
  • ••
    卷影复制（Shadow Copy）：允许更新正在被使用的 DLL
  • ••
    加载器优化：性能调优
这就是为什么 IIS 上每个站点可以有自己独立的 web.config 和 bin 目录——它们各自跑在各自的 AppDomain 里。

四、跨 AppDomain 访问：封送（Marshaling）

这是 22.2 节最难懂的部分。既然 AppDomain 之间不能直接访问对象，那如果我想从主程序调用插件里的一个对象的方法，怎么办？
CLR 提供了两种封送方式：

方式一：按引用封送（Marshal-by-Reference）

对象必须继承 MarshalByRefObject：
csharp
// 在插件程序集里
public class Plugin : MarshalByRefObject
{
    public string DoWork() => "插件干活中...";
}

// 在主程序里
AppDomain pluginDomain = AppDomain.CreateDomain("Plugin");
Plugin proxy = (Plugin)pluginDomain.CreateInstanceAndUnwrap(
    "PluginAssembly", 
    "Plugin");
    
string result = proxy.DoWork();  // 跨 AppDomain 调用
proxy 不是真正的 Plugin 对象，而是一个代理（Proxy）。当你调用 proxy.DoWork() 时：
  1. 1.1.
    CLR 拦截这次调用
  2. 2.2.
    把调用参数封送到 pluginDomain
  3. 3.3.
    在 pluginDomain 里执行真正的 DoWork()
  4. 4.4.
    把返回值封送回主 AppDomain
  5. 5.5.
    你拿到结果
⚠️ 代价：每次跨边界调用都有性能开销（序列化/反序列化 + 上下文切换）

方式二：按值封送（Marshal-by-Value）

对象不继承 MarshalByRefObject，但标记为 [Serializable]：
csharp
[Serializable]
public class Data
{
    public int Value { get; set; }
}

// 主程序里
AppDomain pluginDomain = AppDomain.CreateDomain("Plugin");
Data data = new Data { Value = 42 };

// 跨 AppDomain 传递 data 时，CLR 会：
// 1. 把 data 序列化成字节流
// 2. 在目标 AppDomain 里反序列化
// 3. 创建 data 的一个"精准复制"对象
// 4. 把这个副本交给你
这种方式下，目标 AppDomain 拿到的是数据的副本，不是引用。之后两边各改各的，互不影响。

怎么选？

场景
选择
对象有行为（方法），想远程调用
按引用（MarshalByRefObject）
对象只是数据，想传过去自己用

对象很大，不想复制

五、Loader 堆：AppDomain 的"记忆"

这是 Richter 讲得最深的部分，但理解了会很通透。
每个 AppDomain 都有自己的 Loader 堆。Loader 堆里存的是：这个 AppDomain 自创建以来访问过的所有类型的类型对象（Type Object）。
什么意思？看这个例子：
纯文本
进程里有两个 AppDomain：DomainA 和 DomainB

DomainA 里第一次用到 string → CLR 在 DomainA 的 Loader 堆里
                                  创建 System.String 的类型对象
                                  
DomainB 里第一次用到 string → CLR 在 DomainB 的 Loader 堆里
                                  也创建 System.String 的类型对象
两个 AppDomain 里的 System.String 类型对象，在内存里是两份！​ JIT 编译出的本地代码也是两套。
为什么这么"浪费"？为了隔离性——这样卸载 DomainA 时，可以直接把 DomainA 的 Loader 堆整个清掉，不用担心影响到 DomainB。
💡 唯一的例外：MSCorLib.dll（含 System.Object、System.Int32、System.String 等最基础的类型）以 AppDomain 中立（AppDomain-neutral）方式加载——所有 AppDomain 共享同一份类型对象和 JIT 代码。CLR 为它维护一个特殊的 Loader 堆。
这是为了性能优化：这些基础类型被所有 AppDomain 频繁使用，如果每域一份就太浪费了。

六、卸载 AppDomain：背后发生了什么？

调用 AppDomain.Unload(domain) 时，CLR 做了一连串动作（这部分书里讲得很细）：
纯文本
① 挂起进程中所有曾执行过托管代码的线程
② 检查所有线程栈，找出哪些线程：
   - 正在该 AppDomain 中执行，或
   - 将来可能返回到该 AppDomain
③ 对这些线程强制抛出 ThreadAbortException
   → 线程展开调用栈，执行 finally 块做清理
   → 但如果在执行 finally/catch/类构造函数/非托管代码，
     则等这些代码块执行完再抛
④ 所有相关线程离开该 AppDomain 后：
   → 给所有指向该 AppDomain 对象的代理打上"失效"标记
   → 之后再调用这些代理的方法会抛 AppDomainUnloadedException
⑤ 强制执行一次 GC，调用待回收对象的 Finalize 方法
⑥ 恢复其余线程
⚠️ 注意：AppDomain.Unload 是个阻塞调用，它会等所有清理工作做完才返回。

七、监视 AppDomain 的资源使用

CLR 提供了应用程序域资源监视（ARM）机制，可以监控每个 AppDomain 消耗了多少 CPU 时间和内存：
csharp
// 打开全局监视开关
AppDomain.MonitoringIsEnabled = true;

// 读取当前 AppDomain 的资源使用

long memoryUsed = AppDomain.CurrentDomain.MonitoringSurvivedMemorySize;
long memoryAllocated = AppDomain.CurrentDomain.MonitoringTotalAllocatedMemorySize;
Richter 在书里写了一个 AppDomainMonitorDelta 工具类（实现 IDisposable），可以方便地测量某段代码执行前后​ AppDomain 的资源增量。这是诊断内存泄漏、性能瓶颈的好工具。

这是 Richter 书里讲 Loader 堆时提到的重点。同一个程序集（比如 System.dll）被两个 AppDomain 加载：
默认情况（非域中立加载）：
  • ••
    每个 AppDomain 里各有一份该程序的类型对象和 JIT 编译代码
  • ••
    好处：卸载 AppDomain A 时，A 里的 System.dll 可以跟着一起被回收
  • ••
    代价：内存里有多份副本，费内存
域中立加载（Domain-Neutral）：
  • ••
    所有 AppDomain 共享同一份​ JIT 编译代码
  • ••
    好处：省内存
  • ••
    代价：这个程序集永远不能从进程里卸载，除非整个进程退出

二、为什么微软要"砍掉"AppDomain？

这不是拍脑袋决定的，有三个深层原因：

1. AppDomain 依赖"远程处理（Remoting）"，而 Remoting 被砍了

AppDomain 之间跨域访问对象，底层靠的是 Remoting​ 技术（也就是 MarshalByRefObject 那一套）。.NET Core 重构时，Remoting 因为"性能开销大、复杂、难以维护"被列入了裁剪清单。
💡 没有 Remoting 支持，AppDomain 就无法实现跨域对象访问——那 AppDomain 作为"隔离容器"的核心价值就没了
Stack Overflow 上 .NET 团队的人解释："You can't run code in an app domain without remoting support"（没有远程处理支持，就无法在应用程序域中运行代码）——所以 AppDomain 也被一并放到了裁剪清单上。

2. AppDomain 的资源开销大，不符合现代 .NET 的定位

.NET Core 的目标是小巧、跨平台、高性能。AppDomain 需要 CLR 深度支持（独立的 Loader 堆、独立的 GC 视角、跨域代理……），这些机制让运行时变得沉重。
微软的原话："AppDomains require runtime support and are generally quite expensive"（AppDomain 需要运行时支持，且通常相当昂贵）。

3. 现代架构更喜欢"进程/容器隔离"

云计算时代，隔离的最佳实践已经变成了：
  • ••
    Docker 容器（强隔离，资源可控）
  • ••
    独立进程（操作系统级隔离，崩溃互不影响）
相比之下，AppDomain 这种"进程内逻辑隔离"显得尴尬——隔离性不如容器/进程，灵活性又不够轻量。

三、替代品：AssemblyLoadContext（ALC）

微软给出的现代解决方案是 AssemblyLoadContext（.NET Core 引入，.NET Framework 中没有）。

ALC 是什么？

微软文档定义："AssemblyLoadContext 提供查找、加载和缓存托管程序集及其他依赖项的服务。为了支持动态代码的加载和卸载，它会创建隔离上下文，在自身的 AssemblyLoadContext 实例中加载代码及其依赖项。"
简单说：ALC 是"程序集加载的上下文"——它决定了"当代码说'我要加载 XXX.dll'时，去哪里找、加载哪个版本"。

ALC 的核心能力

每个 .NET 5+ 应用程序都隐含使用 ALC。它的关键特性：
1. 版本隔离
一个 ALC 实例对同一个程序集（按简单名称）只能加载一个版本。所以当你需要让不同版本的 Newtonsoft.Json.dll 共存时，就把它们放进不同的 ALC：
纯文本
默认 ALC
└── Newtonsoft.Json v13.0.1
└── PluginA.dll（依赖 Json v13）

插件 ALC
└── Newtonsoft.Json v12.0.3
└── PluginB.dll（依赖 Json v12）
这是 AppDomain 时代很难优雅解决的问题——现在 ALC 天然支持。
2. 可卸载（Collectible）
创建 ALC 时可以指定 isCollectible: true，之后调用 Unload() 可以卸载整个上下文里的所有程序集：
csharp
var context = new AssemblyLoadContext("PluginContext", isCollectible: true);
Assembly plugin = context.LoadFromAssemblyPath("PluginB.dll");
// ... 使用插件 ...
context.Unload();  // 卸载
但要注意：ALC 的卸载不像 AppDomain.Unload 那么彻底。它依赖 GC——你必须确保所有对插件对象、类型的引用都被释放，ALC 才能在下次 GC 时被回收。这比 AppDomain 的"整体卸载"更容易内存泄漏。

using System.Runtime.Loader;

// 1. 定义一个可收集的 ALC
class PluginLoadContext : AssemblyLoadContext
{
    public PluginLoadContext() : base(isCollectible: true) { }
    
    // 自定义程序集解析逻辑
    protected override Assembly? Load(AssemblyName name)
    {
        // 从插件目录加载依赖
        return null;  // 交给默认逻辑
    }
}

// 2. 使用
var alc = new PluginLoadContext();
Assembly plugin = alc.LoadFromAssemblyPath(@"plugins\PluginB.dll");

// 3. 通过共享接口创建实例（主程序和插件都引用同一个接口程序集）
Type pluginType = plugin.GetType("PluginB.Plugin");
var instance = (IPlugin)Activator.CreateInstance(pluginType);

instance.Execute();

// 4. 卸载
alc.Unload();
// 注意：还要确保所有对 instance、pluginType、plugin 的引用都被释放
// 否则 ALC 不会被 GC 回收
