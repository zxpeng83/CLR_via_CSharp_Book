这句说的是 JIT 对数组访问里的越界检查（bounds check）做的一个经典优化，叫 "循环不变提升 + 范围检查消除"。书里那个脚注①想表达的也是：你写代码以为每次 arr[i] 都要查一次 i < arr.Length，但实际上 JIT 够聪明的话，能把它压到一次甚至零次。

先看"直觉上"发生了什么

C# 里每次访问数组元素，CLR 都要保证 0 <= index < arr.Length，否则抛 IndexOutOfRangeException。所以你直觉觉得这段代码的成本是：
csharp
int Sum(int[] arr)
{
    int s = 0;
    for (int i = 0; i < arr.Length; i++)
    {
        s += arr[i];   // ← 这里"每次"都要做一次 i < arr.Length 的检查？
    }
    return s;
}
如果真的每次迭代都插一条判断 + 分支，对 tight loop 是有开销的。

JIT 实际做了什么

RyuJIT 在看到这个循环时，会做几步推理：
  1. 1.1.
    arr 在循环里没被重新赋值 → arr.Length 是循环不变量
  2. 2.2.
    i 从 0 开始，每次 +1，终止条件是 i < arr.Length
  3. 3.3.
    所以 arr[i] 的每一次访问，i 必然落在 [0, arr.Length-1]
→ 所有 arr[i] 的越界检查都可以消掉，只剩循环头那个 i < arr.Length 本身就够了（而那个判断本来就是你 for 语句里写的，不算"额外"开销）。
换句话说，JIT 把"数组访问自带的边界检查"和"你循环条件里的判断"合并成一份了。

用反例更能体会"通常"二字

下面这种 JIT 就消不掉，每次还得查：
csharp
// 情况1：下标不是简单 i++
for (int i = 0; i < arr.Length; i += 2)
{
    s += arr[i];      // 还能消
    s += arr[i + 1];  // ❌ 这里 i+1 不一定在界内（万一 Length 是奇数？），消不掉
}

// 情况2：循环里数组引用被动过
for (int i = 0; i < arr.Length; i++)
{
    if (i == 10) arr = GetAnotherArray(); // arr 变了，Length 可能变
    s += arr[i];      // ❌ 不敢消
}

// 情况3：foreach 走 IEnumerator 非数组特化路径、或多维数组、或非 0 基
// 也可能消得不彻底
所以书里说"通常微乎其微"——常见的一维 0 基 for-i 遍历，JIT 基本都能把这个开销压到接近零；但一旦模式稍微复杂点，那些检查就回来了。

一、Buffer.BlockCopy：纯内存搬运工（极速，但很“笨”）

核心思想

不关心元素是什么类型，只把一块连续内存原样拷贝过去
它做的是 字节级拷贝，类似 C/C++ 里的 memcpy。

关键特点

  1. 1.1.
    参数是“字节偏移”，不是“元素索引”
  2. 2.2.
    不做任何类型转换
  3. 3.3.
    只适用于“按位兼容（blittable）”的数据
  4. 4.4.
    非常快

例子：byte[] → char[] 

csharp
byte[] bytes = { 0x41, 0x00, 0x42, 0x00 }; // 'A', 'B' (UTF-16 LE)
char[] chars = new char[2];

Buffer.BlockCopy(
    src: bytes,
    srcOffset: 0,
    dst: chars,
    dstOffset: 0,
    count: bytes.Length   // ⚠️ 字节数！
);

Console.WriteLine(chars); // AB

这里发生了什么？

  • ••
    char 在 .NET 中是 2 字节
  • ••
    BlockCopy 根本不知道什么是 char
  • ••
    它只是把 4 个字节从 bytes 原样搬到 chars
  • ••
    因为 byte 和 char 在内存中都是“裸数据”，按位兼容（blittable），所以合法
⚠️ 如果你写成这样，就错了：
csharp
Buffer.BlockCopy(bytes, 0, chars, 0, 2); // ❌ 只拷 2 字节，char[2] 会残缺
因为 dstOffset 和 count 都是 字节数，不是元素个数。

为什么它比 Array.Copy 快？

方法
行为
Array.Copy
逐个元素检查类型、必要时装箱/拆箱/转型
Buffer.BlockCopy
直接 memcpy，一条 CPU 指令批量搬
所以：性能敏感 + 确定类型安全 → 用 BlockCopy

什么是“按位兼容（blittable）”？

书中译注提到的 blittable，本质就是一句话：
这种类型在托管内存和非托管内存里的二进制表示完全一致
典型 blittable 类型：
  • ••
    byte, sbyte
  • ••
    short, ushort
  • ••
    int, uint
  • ••
    long, ulong
  • ••
    float, double
  • ••
    char（UTF-16）
  • ••
    由 blittable 类型组成的结构体
❌ 非 blittable：
  • ••
    string（内部有引用）
  • ••
    bool（大小不固定）
  • ••
    含引用字段的结构体
  • ••
    任意对象数组
👉 BlockCopy 只信任 blittable 数据

二、Array.Copy：智能搬运工（慢一点，但很聪明）

核心思想

知道你在拷贝“元素”，会自动做类型转换

它能干什么？ 

csharp
int[] ints = { 1, 2, 3 };
long[] longs = new long[3];

Array.Copy(ints, longs, ints.Length);
// ✅ int → long 自动加宽
csharp
object[] objs = new object[3];
string[] strs = { "a", "b", "c" };

Array.Copy(strs, objs, 2);
// ✅ string → object（协变）
但它也有代价：
  • ••
    运行时类型检查
  • ••
    装箱 / 拆箱
  • ••
    数值类型转换
👉 这就是它比 BlockCopy 慢的原因

三、Array.ConstrainedCopy：事务型搬运工（最安全）

核心思想

要么全部成功，要么目标数组完全不动
这是为 关键系统代码 / CER（约束执行区域）​ 准备的。

例子：对比 Array.Copy 

csharp
object[] src = { 1, "two", 3.0 };
object[] dst = new object[3];

try
{
    Array.Copy(src, dst, src.Length);
}
catch
{
    // dst 可能已经被部分修改
}
csharp
try
{
    Array.ConstrainedCopy(src, 0, dst, 0, src.Length);
}
catch
{
    // dst 一定保持原状
}

它的严格限制（书中重点）

✅ 允许：
  • ••
    源类型和目标类型 相同
  • ••
    源类型 派生自​ 目标类型
❌ 不允许：
  • ••
    装箱 / 拆箱
  • ••
    数值类型转换
  • ••
    向下转型
csharp
object[] src = { "hello" };
string[] dst = new string[1];

Array.ConstrainedCopy(src, 0, dst, 0, 1); // ✅ string → object 的基类方向
csharp
string[] src = { "hello" };
object[] dst = new object[1];

Array.ConstrainedCopy(src, 0, dst, 0, 1); // ❌ 不允许

1. 词源：Blit 是什么意思？

这个词源自计算机图形学里的 Bit BLT​ (Bit Block Transfer)，读作 "blit"。
  • ••
    BLT​ = Block Transfer（块传输）
  • ••
    Bit​ = 按位
在早期的图形处理中，"blitting" 就是把显存里的一块二进制数据直接搬到另一块显存，不做任何解析，速度极快。
.NET 借用了这个概念：Blittable = 可以直接按位复制的类型。

2. 核心定义：托管与非托管的“共识”

Blittable​ 类型的核心特征是：
它在 .NET 托管堆里的二进制模样，和在原生（Native/C++）内存里的二进制模样，是一模一样的。
CLR 不需要做任何转换（比如调整指针、转换格式），就可以直接把这块内存丢给 Windows API 或者 C++ 代码使用。

3. 最直观的例子：为什么 int 是 Blittable，而 string 不是？

场景：跨语言调用

假设我们要把数据从 C# 传给 C++。
Case 1: int (Blittable)
C# 里的 int 是 4 字节，struct Layout 就是连续的 4 个字节：[01 00 00 00]。
C++ 里的 int 也是 4 字节，布局也是 [01 00 00 00]。
结论：CLR 直接把那 4 个字节的内存地址扔给 C++，双方都能看懂。这就是 Blit。
Case 2: string (Non-Blittable)
C# 里的 string 是一个对象。在内存里，它包含：
  1. 1.1.
    对象头（Sync Block Index 等）
  2. 2.2.
    长度字段
  3. 3.3.
    指向实际字符数组的指针（引用）
  4. 4.4.
    字符数据本身（UTF-16）
而 C++ 里的 char*（假设是 ANSI）只是一个指向单字节字符序列的指针，且没有长度前缀。
结论：如果你把 C# string 的内存地址直接扔给 C++，C++ 拿到的第一个 4/8 字节是 C# 的对象头，而不是字符串内容。程序立刻崩溃。
所以 string 不是​ blittable。CLR 必须进行复杂的封送（Marshaling）：分配新的非托管内存，把字符一个个复制过去，转换编码，然后把新地址传给 C++。

4. 回到书中的 Buffer.BlockCopy

书中说：
“该方法一定程度上弥补了不能将数组当作任意类型的内存块来处理的不足。”
Buffer.BlockCopy 之所以快，就是因为它假定你传入的数据是 Blittable​ 的。
它不管你传的是 byte[] 还是 char[]，它只认字节。只要数据的二进制表示是连续的、固定的，它就能拷。
这就是为什么 BlockCopy 的参数必须是字节偏移量：
因为它跳过了 C# 的类型系统，直接操作内存地址。

6. 一个“格式化的值类型”的例子

书中提到：“格式化的值类型如果包含 blittable 类型，该值类型也是 blittable 类型。”

    public int X; // int 是 blittable
    public int Y; // int 是 blittable

// 这是一个 Non-Blittable 的结构体
struct BadPoint
{
    public string Name; // string 不是 blittable
    public int X;
}
当你创建一个 Point[] 数组时，数组在内存中是连续的 X, Y, X, Y...。你可以安全地使用 Buffer.BlockCopy 在这个数组和 byte[] 之间拷贝数据，因为它们都是“按位兼容”的。

总结

Blittable = 内存布局的通用语。
  • ••
    是 Blittable：可以直接 memcpy，速度快，适合 Buffer.BlockCopy。
  • ••
    不是 Blittable：必须经过 CLR 翻译（Marshaling），速度慢，只能用 Array.Copy。

一句话先给结论

一、C# 源码层面：你看不到继承 

csharp
// 你写的

// class int[] : System.Array { ... }   // ❌ 根本不允许这么写
C# 语法里 int[] 是"数组类型"，不是 class，你不能手动让它继承任何东西，也不能写 class Foo : int[]。

二、CLR 层面：数组类型是"捏出来的"

编译 int[]，C# 编译器在 IL 里生成的是 int32[]（IL 类型名），但并没有一个 Int32Array 的元数据类定义躺在程序集里。
真正发生的事是：
  1. 1.1.
    C# 编译器​ → 在 IL 里用 newarr / ldelem / stelem 这一系列专用指令操作 int32[]
  2. 2.2.
    CLR 加载时​ → 发现"哦，这里有一个 int32[] 被用到了"，于是当场在托管堆的类型表里造一个类型：
    • ••
      名字：System.Int32[]（运行时可见名）
    • ••
      父类：System.Array
    • ••
      内部布局：对象头 + Length + 元素[0..n-1]
  3. 3.3.
    以后每次用到 int[]，都复用这个 CLR 造出来的类型
所以：
csharp
int[] a = new int[3];
Console.WriteLine(a.GetType().BaseType);   // System.Array
Console.WriteLine(a is Array);              // True
int[] 能调 Array.Length、Array.Rank、Array.Copy(...) 这些实例/静态方法，根本原因就是它的"爹"在 CLR 眼里就是 System.Array。

三、对比"显式派生"，你就明白"隐式"在哪了

数组在语法上不像个子类，但在类型系统 / 运行时里，它就是 Array 的子类，享有 Array 的所有虚方法、所有静态方法、所有接口实现。

  • ••

  • ••

    • ••
      改变布局
    • ••
      插入额外字段
    • ••
      破坏 GC 扫描逻辑
👉 这会让整个运行时崩溃

2️⃣ 数组有专门的 IL 指令

C# 里你写：

一、先搞懂 newarr / ldelem / stelem：CLR给数组开的「专用VIP通道」

1. 先铺垫：IL是什么？

C#代码编译后不会直接变成机器码，而是变成IL，交给CLR的JIT编译器再转成机器码。IL是CLR的“通用指令集”，比如ldc.i4.5是把整数5压到计算栈，call是调用方法，这些都是所有类型通用的。
但newarr/ldelem/stelem是数组专属特权指令——就像高速公路的ETC通道，只有装了ETC的车（数组）能走，普通车（class）只能走人工通道。

newarr     [System.Runtime]System.Int32  // 🔴 创建int[]数组，大小10，返回数组引用
stloc.0                 // 把数组引用存到局部变量arr

// 2. 存元素：stelem.i4
ldloc.0                 // 加载arr引用到栈顶
ldc.i4.0                // 加载索引0到栈顶
ldc.i4.5                // 加载值5到栈顶
stelem.i4               // 🔴 把5存入arr[0]。.i4后缀代表操作4字节整数（对应int）

// 3. 取元素：ldelem.i4
ldloc.0                 // 加载arr引用
ldc.i4.0                // 加载索引0
ldelem.i4               // 🔴 把arr[0]的值加载到栈顶
stloc.1                 // 存到局部变量x

3. 为什么要有这三个专用指令？

为了极致性能：
  • ••
    stelem.i4不需要调用方法，JIT直接把它翻译成「基地址 + 索引×4字节」的CPU地址计算指令，一步到位写内存。
  • ••
    对比普通集合List<int>的索引器赋值：list[0] = 5，编译出的IL是call instance void System.Collections.Generic.List1::set_Item(int32, !T)`，要走方法调用流程（压参数、找方法表、跳转执行），开销比专用指令大得多。

4. 关键限制：这三个指令只认CLR生成的数组类型

你自定义的任何class，哪怕是模仿数组的结构，也没法用这三个指令。IL规范里明确写了：newarr的操作数必须是「数组类型」，而数组类型只能是CLR动态生成的，不能是用户定义的class。

二、为什么Array是abstract，却不能手动继承？

你问的这个点非常关键：你自己写的abstract类当然可以继承，但Array不是“普通abstract类”，它是CLR的「特殊内建类型」，abstract只是它的一个表面属性，不是不能继承的原因。
我们分三层拆解：

1. 先澄清一个误区：abstract≠可继承

abstract的作用仅仅是「不能实例化」，和「能不能被继承」没有必然联系：
  • ••
    你自己写的abstract class A {}：可以继承，因为你是这个类的作者，知道它的所有实现细节。
  • ••
    string是sealed class：不能继承，因为特殊。
  • ••
    Array是abstract class：也不能继承，同样因为特殊。
    它们的共性都是：属于CLR的基础设施，不是普通托管类型。

2. 你自己写的abstract类，为什么能继承？

比如你写：
csharp
abstract class MyAbstract
{
    protected abstract void Foo();
}

class Derived : MyAbstract
{
    protected override void Foo() { /* 你的实现 */ }
}
这个过程是完全可控的：
  1. 1.1.
    你写的MyAbstract有完整的元数据：编译器知道它有哪些成员、抽象方法签名是什么。
  2. 2.2.
    你写Derived的时候，编译器知道要把Foo的实现地址填到方法表里，也知道Derived的内存布局（对象头+父类字段+自己的字段）。
  3. 3.3.
    调用Foo的时候，JIT知道怎么从Derived的方法表里找到你的实现。
    一切都在托管代码的规则范围内，没有任何黑盒。

3. Array为什么不能继承？三个硬限制，每一个都绕不开

Array是CLI（.NET底层公共语言基础设施规范）明确定义的特殊类型（Special Type），从规范到实现都锁死了不能继承：

限制1：Array的实现是CLR的“黑盒”

你翻Array的源码会发现，它的核心方法全是extern（外部实现）：
csharp
public abstract class Array
{
    public extern int Length { get; }
    public extern int Rank { get; }
    public extern object GetValue(int index);
    // ... 其他方法全是extern
}
这些方法的实现不在托管代码里，而是CLR用C++写的，入口点不对外暴露。你如果继承Array，overrideLength的时候，根本没法写base.Length——因为你找不到CLR里Length的实现在哪，CLR也不会给你开后门访问。

限制2：数组的内存布局是CLR硬编码的，容不得一点改动

一个一维0基数组在托管堆的布局是CLR强制规定的（简化版）：
纯文本
[对象头(SyncBlock+类型指针)][Length字段][元素0][元素1]...[元素n-1]
这个布局是GC、JIT、类型系统的“共同约定”：
  • ••
    GC扫描数组的时候，知道跳过开头的对象头和Length，直接扫后面的元素区。
  • ••
    JIT执行ldelem.i4的时候，知道用「数组起始地址 + 4×索引 + 偏移量」计算元素地址。
    如果你继承Array，加了一个自己的字段int MyField，布局就变成了：
纯文本
[对象头][Length][MyField][元素0]...
这时候GC扫到MyField会以为是对象引用，直接崩溃；JIT算地址的时候也会错位，读到错误的数据。
CLR绝对不可能允许这种破坏布局的行为发生。

限制3：IL指令的硬限制，哪怕你绕开C#也没用

就算你不用C#，直接用IL汇编（ILASM）写代码继承Array：
il
.class public MyArray extends System.Array
{
    // ...
}
CLR在加载这个类型的时候，会直接触发类型验证错误，拒绝加载。因为CLI规范明确规定：
数组类型是运行时动态构造的类型，不得作为任何其他类型的基类。
这不是C#编译器的限制，是CLR底层的规则——三个专用指令newarr/ldelem/stelem只认CLR动态生成的数组类型，不认任何自定义派生类。就算你强行继承了，你也用不了[]语法，也用不了new int[10]创建你的派生类，因为这些语法都会编译成上述专用指令，CLR执行时直接抛异常。

三、把两个问题串起来，你就通透了

为什么CLR要给数组搞三个专用指令，又禁止继承Array？
本质是为了性能和安全性的平衡：
  1. 1.1.
    为了极致性能，CLR给数组开了newarr/ldelem/stelem这三个专用通道，省去了方法调用的开销。
  2. 2.2.
    为了保证这三个通道能正常工作，CLR必须完全掌控数组的所有细节：类型必须由CLR动态生成、布局必须硬编码、方法必须由CLR内部实现。
  3. 3.3.
    因此，绝对不能允许用户自定义类继承Array——否则专用通道的逻辑会全面崩塌。

一、newarr 的 operand 不是 Int32[]，是 Int32

看 IL 就很清楚了。C# 写：
csharp
int[] a = new int[5];
编译出的 IL 是：
il

newarr [mscorlib]System.Int32   // ⚠️ operand 是 System.Int32，不是 System.Int32[]
stloc.0
注意 newarr 后面跟的 token 是 元素类型 System.Int32 的元数据 token，不是数组类型本身的 token
。
ECMA-335 对 newarr 的定义就一句话：
Create a new zero-based, one-dimensional array whose elements are of type etype.
所以 newarr 的语义是："给我造一个一维 0 基数组，元素类型是 XX，长度是栈顶那个数"。

二、newarr 执行时，CLR 内部发生了什么？

JIT 看到 newarr [System.Int32] 后，不是去查"有没有一个叫 Int32[] 的 class 定义"，而是直接调 CLR 的内部 helper：
asm
mov  edx, 5            ; 元素个数
mov  ecx, <typeof(int)> ; 元素类型句柄（MethodTable* of System.Int32）
call JIT_NewArr1       ; CLR 内部函数
JIT_NewArr1 里干的事（简化）：
  1. 1.1.
    拿着元素类型 System.Int32，去"数组类型缓存"里查：有没有人已经造过 Int32[] 这个类型？
    • ••
      有 → 拿来用
    • ••
      没有 → 当场造一个
  2. 2.2.
    造 Int32[] 类型时，CLR 做的事：
    • ••
      类型名：System.Int32[]（运行时可见）
    • ••
      父类：填 System.Array
    • ••
      元素类型：挂 Int32
    • ••
      秩=1，下界=0
    • ••
      布局：对象头 + Length + 4 字节/元素 的连续区
    • ••
      把自己注册为"SZ 数组"，享受 ldelem.i4 / stelem.i4 这种类型专用指令的快捷路径
  3. 3.3.
    用这个刚拿到/查到的 Int32[] 的 MethodTable，算对象大小 = 对象头 + 4 + 5×4 = 28 字节（64 位下更大），从 GC 堆 alloc
  4. 4.4.
    初始化 Length=5，元素区清零
  5. 5.5.
    把对象引用推回 IL 栈
👉 System.Int32[] 这个"类"不是编译期存在的，是 newarr 第一次被执行时，CLR 才给你造出来的。

三、那 ldelem / stelem 又是怎么消费 Int32[] 的？

这块最关键，能解释"为什么 Int32[] 不需要一个源码 class 也能被访问"。
看 C# a[0] = 5 编译出的 IL：
il
ldloc.0      // 压 a（Int32[] 引用）
ldc.i4.0     // 压索引 0
ldc.i4.5     // 压值 5
stelem.i4    // ⚠️ 注意后缀 .i4，不是 .ref
stelem.i4 的语义（ECMA-335）：
从栈上弹出 array、index、value；把 4 字节整数 value 写入 array[index]；顺便做越界检查。
重点来了：stelem.i4 根本不查 Int32[] 的方法表，也不调任何 Array 的虚方法。它只认三件事：
  1. 1.1.
    这是不是一个数组对象（对象头里有个标志位）
  2. 2.2.
    长度够不够 index（越界检查）
  3. 3.3.
    元素宽度 = 4 字节（.i4 后缀已经硬编码了）
然后 JIT 直接生成一条地址计算：
asm
lea  target, [array_base + 0x10 + index*4]   ; 0x10 = 跳过对象头+Length
mov  [target], 5
ldelem.i4 同理，反向读。
👉 ldelem/stelem 消费的不是 Int32[] 这个"类"的 API，而是 Int32[] 实例在内存里的"布局约定"——而这个布局是 CLR 造 Int32[] 类型时硬编码的，跟有没有 class 源码无关。

二、真相：这是 CLR 的“隐式实现”（Runtime Magic）

1. 源码层面：根本没有这些接口

你去翻 .NET 源码，找不到任何地方定义：
csharp
class Int32[] : Array, IEnumerable<int>, IList<int> ... // ❌ 不存在
正如我们上一轮聊的：int[] 是 CLR 动态合成的类型，不是 C# 编译器生成的。

2. CLR 在“造”数组类型时偷偷加了接口

当 CLR 第一次碰到 int[] 时，它生成的类型信息里包含：
  • ••
    父类：System.Array
  • ••
    附加接口列表：
    • ••
      IEnumerable<int>
    • ••
      ICollection<int>
    • ••
      IList<int>
    • ••
      （以及非泛型版本 IEnumerable, ICollection, IList）
但是，CLR 并没有生成这些接口方法的实际代码（比如 Add, Remove）。

3. 调用接口方法时发生了什么？

当你调用：
csharp
il.Add(4); // IList<int>.Add
CLR 并不是去查 int[] 的方法表找 Add 方法，而是：
  1. 1.1.
    识别到这是 SZ 数组（一维零基）​ 的接口调用。
  2. 2.2.
    直接抛出 NotSupportedException。
    • ••
      因为数组长度是固定的，不能 Add。
csharp
int[] arr = {1, 2, 3};
IList<int> list = arr;
list[0] = 10;     // ✅ 允许（修改现有元素）
list.Add(4);      // ❌ 运行时异常：Collection was of a fixed size.
结论：数组对这些接口的支持是“只读/只修改”的，凡是涉及改变长度的（Add, Remove, Clear），统统不支持。

三、核心难点：int[] 和 IEnumerable<object> 的爱恨情仇

这是这一节最难懂、也是面试最爱考的点。

1. 引用类型的数组（没问题） 

csharp
string[] strs = { "hello" };
IEnumerable<object> objects = strs; // ✅ OK
这是因为 数组协变（Covariance）：
  • ••
    string 派生自 object
  • ••
    CLR 允许 string[] 转换为 object[]（及其泛型接口变体）

2. 值类型的数组（大问题） 

csharp
int[] ints = { 1, 2, 3 };
IEnumerable<object> objects = ints; // ❌ 编译错误！
为什么不行？

原因一：装箱的成本

如果允许 int[] → IEnumerable<object>，意味着遍历的时候：
csharp
foreach (object o in ints) // o 应该是 object
{
    // 每遍历一个元素，都需要把 int 装箱成 object
}
CLR 不想在底层偷偷帮你做大量的隐式装箱操作（性能杀手）。

原因二：CLR 的硬性规定

值类型数组，不实现其元素基类型的泛型接口。
  • ••
    int[] 实现：IEnumerable<int>
  • ••
    int[] 不实现：IEnumerable<object>
  • ••
    int[] 不实现：IEnumerable<IComparable>（即使 int 实现了这个接口）
反射验证：
csharp
int[] ints = { 1, 2, 3 };
Console.WriteLine(ints.GetType().GetInterfaces().Contains(typeof(IEnumerable<int>)));      // True
Console.WriteLine(ints.GetType().GetInterfaces().Contains(typeof(IEnumerable<object>)));  // False

四、结合 IL 和 foreach 看本质

1. 为什么 foreach 对数组这么快？

当你写：
csharp
foreach (int i in intArray)
{
    // ...
}
编译器不会把它编译成调用 IEnumerable<int> 的 GetEnumerator()。
它会直接编译成：
csharp
for (int i = 0; i < intArray.Length; i++)
{
    int v = intArray[i]; // 直接使用 ldelem.i4
}
这就是为什么书里前面说数组遍历快——foreach 对数组有特殊优化，绕过了接口调用。

2. 什么时候才会走接口？

只有当你强制把数组当成接口时：
csharp
IEnumerable<int> ie = intArray; // 强制转换
foreach (int i in ie)           // 这时才会调用接口方法 GetEnumerator()
{
}
这种情况下，CLR 会返回一个特殊的枚举器（不是 IEnumerator<int> 的普通实现，而是针对数组的优化版本），但性能依然不如直接的 for 循环或特化的 foreach。

五、多维数组的“低人一等”

书中还提到了多维数组（如 int[,]）：
csharp
int[,] matrix = new int[2, 2];
IList<int> list = matrix; // ❌ 编译错误
原因很简单：
  • ••
    只有一维零基数组（SZ Array）​ 才隐式实现泛型接口。
  • ••
    多维数组、非 0 基数组只实现非泛型的 IList（而且大部分方法抛异常）。
这是为了性能考虑，因为多维数组的索引计算（row * cols + col）比一维数组复杂，CLR 不愿意为它们维护一套复杂的泛型接口映射。

六、总结：一句话记住这一节

数组在 CLR 层面被“开小灶”：一维零基数组会被偷偷加上泛型接口（IEnumerable<T>等），但这只是为了让你能把它传给期望接口的 API；实际上数组并不包含这些接口的真正实现（Add/Remove 会报错），且值类型数组绝不会实现“装箱后的接口”（如 IEnumerable<object>）。

首先讲【传递】，这里Richter主要讲了两个点：1. 数组作为参数，修改元素会影响原数组；2. 数组协变带来的类型安全问题；3. 要不要做防御性拷贝。
先举个最基础的例子，先讲“传引用拷贝”这个点，很多人会混淆“引用传递”和“传引用的拷贝”：
比如：
void ChangeArray(int[] arr) {
arr[0] = 100; // 改元素，原数组变
arr = new int[5]; // 改引用指向，原数组不变
}
然后调用的时候：
int[] a = new int[]{1,2,3};
ChangeArray(a);
Console.WriteLine(a[0]); // 100，因为改了元素
Console.WriteLine(a.Length); // 3，因为改的是形参的引用，不影响实参a
这里要强调：C#里默认是「值传递」，数组的变量是引用，所以传的是“引用的值”——也就是把a存的那个堆地址拷贝了一份给arr，所以arr和a指向同一个数组，改元素当然同步，但arr重新指向新数组，只是改了拷贝的地址，a还是指向原来的。
然后讲Richter提到的「数组协变的坑」，这个是传递时的大问题，之前提过但这里是应用场景：
比如有个方法接收object[]：

foreach(var o in arr) Console.WriteLine(o);
}
然后你传string[]：
string[] strs = {"a", "b"};
PrintObjects(strs); // 编译通过，因为数组协变
这看起来没问题，但如果方法里偷偷改元素呢？
void AddObject(object[] arr) {
arr[0] = new object(); // 编译通过，但运行时炸
}
AddObject(strs); // ❌ ArrayTypeMismatchException，因为strs里只能放string，不能放object
这就是Richter说的“数组协变不保证类型安全”，传递的时候很容易踩这个坑，所以现在推荐用泛型集合，比如IEnumerable<string>，就不会有这个问题。
然后讲【返回数组】，这是16.5里最绕的，也是Richter重点强调的：方法返回数组的时候，千万不要直接返回内部数组的引用，不然会泄露内部状态，外部可以随意修改你的内部数据。
举个典型的坏例子：
class BadClass {
private int[] _data = new int[]{1,2,3};
public int[] GetData() {
return _data; // ❌ 直接返回内部数组引用
}
}
调用的时候：
BadClass b = new BadClass();

data[0] = 100; // 直接修改了b的内部_data！
Console.WriteLine(b._data[0]); // 100，内部状态被篡改了
这就是Richter说的“返回数组的危险性”——因为数组是引用类型，返回后外部拿到的是内部数组的引用，可以直接改内部数据，破坏了封装性。
那Richter给出的解决方案是什么？三个，要结合例子讲，还要和用户之前学的性能知识联动：
  1. 1.1.
    防御性拷贝（最常用，但有性能成本）
    就是返回数组的副本，而不是直接返回原数组：
    class GoodClass1 {
    private int[] _data = new int[]{1,2,3};
    public int[] GetData() {
    return (int[])_data.Clone(); // Clone()返回浅拷贝，值类型数组没问题
    // 或者用Array.Copy新建一个数组
    }
    }
    这样外部修改的是副本，不影响内部_data。但这里要提一下：Clone()对于值类型数组是完美的，对于引用类型数组是浅拷贝（只拷贝引用，元素本身还是同一个），如果要深拷贝得自己处理。还有性能问题：拷贝数组要O(n)时间，大数组有开销，这也是为什么后来有了Span/Memory之类的方案。
  2. 2.2.
    返回只读包装（.NET Framework 4.5之后的方案，性能好）
    用Array.AsReadOnly()，返回一个ReadOnlyCollection<T>，这个包装不允许修改元素：
    class GoodClass2 {
    private int[] _data = new int[]{1,2,3};
    public ReadOnlyCollection<int> GetData() {
    return Array.AsReadOnly(_data); // 返回只读包装，不拷贝数组
    }
    }
    这样外部不能修改元素（调用Add/Remove/setter都会抛异常），而且没有拷贝开销，性能很好。但要注意：这个包装是“浅只读”，如果数组元素是引用类型，你还是可以修改元素内部的属性，比如：
    class Person { public int Age; }
    class Test {
    private Person[] _people = new Person[]{new Person{Age=10}};
    public ReadOnlyCollection<Person> GetPeople() => Array.AsReadOnly(_people);
    }
    var people = new Test().GetPeople();
    // people[0] = new Person(); // ❌ 不允许，只读
    people[0].Age = 20; // ✅ 允许！因为元素本身是引用，只读包装管不了元素内部的状态
    这点Richter可能没细讲，但很重要，要提一下。
  3. 3.3.
    返回接口，让调用方决定（最灵活，推荐）
    比如返回IEnumerable<T>，这样调用方只能遍历，不能修改（除非强转成数组，但那是调用方自己的责任）：
    class GoodClass3 {
    private int[] _data = new int[]{1,2,3};
    public IEnumerable<int> GetData() {
    return _data; // 返回IEnumerable<int>，不暴露修改能力
    }
    }
    调用方如果想修改，可以自己ToList()或者ToArray()，但那是调用方的选择，类的内部状态不会被意外修改。而且之前讲过，foreach遍历数组的时候，编译器会优化成for循环，性能几乎没有损失。
    然后还要讲Richter提到的「传递数组时的另一个坑：长度可变？不对，数组长度不可变，但方法可能会假设数组长度足够」，比如有个方法要填充数组：

    for(int i=0;i<arr.Length;i++) {
    arr[i] = i;
    }
    }
    调用的时候如果传的数组长度不够？不对，arr.Length就是数组的长度，所以没问题，但如果方法是这样：
    void FillFirstThree(int[] arr) {
    arr[0] = 1;
    arr[1] = 2;
    arr[2] = 3; // 如果arr长度<3，直接IndexOutOfRangeException
    }
    这时候Richter建议什么？哦对，他建议如果方法需要填充数组，最好让调用方传入数组，并且明确说明需要的数组长度，或者方法自己创建数组返回，避免长度不够的问题。还有，.NET里的很多API（比如Stream.Read(byte[] buffer, int offset, int count)）都是这么设计的：调用方提供缓冲区，方法填充，count是最大填充长度，offset是起始位置，这样既避免了方法内部分配数组，又保证了安全性。
    还要和用户之前学的知识联动：比如之前讲的Array.Copy和Buffer.BlockCopy，在防御性拷贝的时候用哪个？如果数组是blittable的，用Buffer.BlockCopy更快，但Array.Copy更安全，支持类型转换。
    还有之前讲的“特判拦截”：比如返回IEnumerable<int>的时候，编译器会把foreach优化成for循环，所以性能很好，不用怕返回接口有开销。

数组是引用类型，但C#默认是值传递——也就是说，你传数组的时候，传的是「引用的一份拷贝」，不是引用本身：
csharp
void ChangeArray(int[] arr) {
    arr[0] = 100;       // 改的是拷贝的引用指向的数组元素 → 原数组同步变

int[] a = new int[]{1,2,3};
ChangeArray(a);

Console.WriteLine(a[0]);   // 100（元素被改了）
Console.WriteLine(a.Length); // 3（引用指向没变）
这是理解整节的基础：数组的“可变性”只体现在元素上，数组本身的引用指向是可以被方法覆盖但不影响外部的。

一、数组的传递：三个坑，Richter挨个点了

1. 第一个坑：修改元素会“污染”原数组

这是引用类型的天性，但数组的特殊之处在于：你没法阻止别人改元素（除非用只读包装）。
比如你写一个工具方法：
csharp
void ResetFirstElement(int[] arr) {
    arr[0] = 0; // 完全合法，没有任何语法限制
}

int[] myArray = new int[]{1,2,3};
ResetFirstElement(myArray);
Console.WriteLine(myArray[0]); // 0，原数组被改了
Richter在这里想提醒你：如果方法的语义是“只读处理数组”，一定要在文档里写清楚，或者在方法内部做防御性拷贝——否则调用方可能无意中改了你的数组。

2. 第二个坑：数组协变的类型安全隐患（之前学过，这里是应用场景）

之前我们聊过数组协变：string[]可以隐式转成object[]，但这是“假安全”：
csharp
void AddObject(object[] arr) {
    arr[0] = new object(); // 编译通过，因为object[]允许放object
}

string[] strs = new string[2];
AddObject(strs); // 编译通过，但运行时直接炸：ArrayTypeMismatchException
原因我们之前讲过：CLR在给数组赋值时，会加一层特判拦截，检查元素类型是否匹配——strs里只能放string，放object直接抛异常。
Richter在这里的结论很明确：不要用数组协变来传递参数，优先用泛型接口IEnumerable<T>/IList<T>，从根源上避免类型安全问题。

3. 第三个坑：方法假设数组长度足够（常见API设计问题）

有些方法会要求调用方传入数组，然后往里面填数据，比如.NET的Stream.Read：
csharp
// Stream.Read的经典设计：调用方提供缓冲区，方法填充数据
public int Read(byte[] buffer, int offset, int count);
如果调用方传的数组长度不够，比如buffer.Length < offset + count，直接抛IndexOutOfRangeException。
Richter的建议是：
  • ••

二、数组的返回：这节最绕、也是最重要的部分

Richter在这部分的警告是：永远不要直接返回内部数组的引用——这是90%数组相关bug的来源。
我们先看反例，你就懂为什么他这么说了：

反例：返回内部数组，直接泄露封装性 

csharp
class User {
    private int[] _scores = new int[]{90, 85, 95}; // 内部状态
    public int[] GetScores() {
        return _scores; // ❌ 致命错误：直接返回内部数组的引用
    }
}

User u = new User();
int[] scores = u.GetScores();
scores[0] = 0; // 直接修改了User内部的_scores！
Console.WriteLine(u.GetScores()[0]); // 0，内部状态被篡改了
这就是Richter说的“返回数组的危险性”：数组是引用类型，返回后外部拿到的是内部数组的“钥匙”，可以随意修改你的私有数据，完全破坏了面向对象的封装性。

那什么时候可以直接返回数组？

只有一种情况：返回的是方法内部新创建的数组，不是内部字段的引用：
csharp
public int[] GetNewScores() {
    return new int[]{90, 85, 95}; // ✅ 安全：数组是新创建的，没有内部状态泄露
}
比如String.Split()就是这么做的：它返回的是新分配的string[]，调用方怎么改都不会影响原string（况且string本身是不可变的），所以完全没问题。

Richter给出的三个解决方案（按推荐程度排序）

方案1：返回接口，把控制权留在调用方（最推荐）

返回IEnumerable<T>，只暴露遍历能力，不暴露修改能力：
csharp
class User {
    private int[] _scores = new int[]{90, 85, 95};
    public IEnumerable<int> GetScores() {
        return _scores; // ✅ 安全：调用方只能遍历，不能修改
    }
}
这里要联动你之前学的“foreach特判拦截”：编译器看到遍历的是数组，会直接把foreach优化成for循环，性能几乎没有损失。如果调用方确实需要修改，可以自己调用ToArray()/ToList()，这是调用方的选择，不是你的责任。
这也是现在.NET API最推荐的写法：用泛型接口作为参数/返回值，既安全又灵活，性能损失极小。

方案2：返回只读包装（性能好，无拷贝）

.NET 4.5之后提供了Array.AsReadOnly()，返回一个ReadOnlyCollection<T>包装，完全禁止修改元素：
csharp
class User {
    private int[] _scores = new int[]{90, 85, 95};
    public ReadOnlyCollection<int> GetScores() {
        return Array.AsReadOnly(_scores); // ✅ 安全：不拷贝数组，零额外开销
    }
}

var scores = new User().GetScores();
// scores[0] = 0; // ❌ 编译通过，运行时抛NotSupportedException
⚠️ 注意：这是“浅只读”——如果数组元素是引用类型，你还是可以修改元素内部的属性：
csharp
class Person { public int Age; }
class Team {
    private Person[] _members = new Person[]{new Person{Age=20}};
    public ReadOnlyCollection<Person> GetMembers() => Array.AsReadOnly(_members);
}

var members = new Team().GetMembers();
// members[0] = new Person(); // ❌ 不允许
members[0].Age = 30; // ✅ 允许！只读包装管不了元素内部的状态

方案3：防御性拷贝（最安全，但有性能成本）

返回数组的副本，而不是直接返回原数组：
csharp
class User {
    private int[] _scores = new int[]{90, 85, 95};
    public int[] GetScores() {
        return (int[])_scores.Clone(); // ✅ 安全：返回的是副本，修改不影响内部
        // 等价于：int[] copy = new int[_scores.Length]; Array.Copy(_scores, copy, _scores.Length); return copy;
    }
}
  • ••
    对于值类型数组（比如int[]），Clone()是完美的浅拷贝，没有额外问题。
  • ••
    对于引用类型数组，Clone()是浅拷贝：拷贝的是元素引用，不是元素本身——如果需要深拷贝，得自己遍历拷贝每个元素。
  • ••
    缺点是要O(n)的时间和空间开销，大数组会有性能损耗。
    这里可以联动之前学的Array.Copy和Buffer.BlockCopy：如果数组是blittable类型，用Buffer.BlockCopy做拷贝会比Array.Copy快，因为少了类型检查。

一、为什么要“不安全访问”？—— 痛点引入

在此之前，访问数组元素 arr[i]，JIT 会生成：
  1. 1.1.
    边界检查（i是否在范围内）
  2. 2.2.
    计算地址（arr地址 + i * sizeof(T)）
在普通业务代码中，这没问题。但在以下场景，这就是累赘：
  1. 1.1.
    高频循环：比如图形处理，每一帧都要遍历百万级像素。
  2. 2.2.
    P/Invoke：调用C/C++函数，C++不认 int[]，它只认 int*。
  3. 3.3.
    与非托管代码共享内存。
C#提供了 unsafe、fixed、stackalloc 这几个关键字来关掉安全检查，换取速度。

二、Fixed（固定）：防止GC“捣乱”

1. 问题：GC会“搬家”

你之前学过，数组是在托管堆上的。
GC在整理内存（压缩堆）时，会把对象挪来挪去，更新所有的引用指针。
如果你拿到了数组的内存地址（指针），GC一挪对象，这个地址就失效了（指向垃圾数据）。

2. 解决：fixed 语句

fixed 的作用是：告诉GC，“在这个代码块里，别动这个对象，把它钉（Pin）在原地”。

例子：用指针遍历数组 

csharp
using System;

class Program
{
    unsafe static void Main()
    {
        int[] arr = { 1, 2, 3, 4, 5 };
        
        // fixed 块：把 arr 钉住，获取指向第一个元素的指针 p
        fixed (int* p = arr)
        {
            // 现在可以用指针算术访问数组了
            for (int i = 0; i < arr.Length; i++)
            {
                Console.WriteLine(*(p + i)); // 等价于 arr[i]
            }
        } // 出了 fixed 块，arr 解锁，GC 可以继续移动它
    }
}
编译时必须开启 /unsafe（在项目属性 -> 生成 -> 允许不安全代码）。

发生了什么？

  1. 1.1.
    fixed (int* p = arr)：CLR 找到 arr 在堆上的起始地址，把它“钉”住。
  2. 2.2.
    *(p + i)：这是纯指针运算。没有边界检查，没有方法调用，直接读写内存。
  3. 3.3.
    性能：这比 arr[i] 理论上更快（虽然现代 JIT 已经优化了边界检查，但在复杂循环中差距明显）。

危险之处 

csharp
fixed (int* p = arr)
{
    *(p + 100) = 999; // 编译通过！运行时直接炸（写入了不属于数组的内存）
}
这就是“不安全”的含义：你把安全责任从CLR手里抢过来了，写错了没人兜底。

三、Stackalloc：在栈上分配数组

这是本节另一个重磅知识点。之前的数组都在堆上，stackalloc 允许你在栈（Stack）上分配内存。

1. 语法与例子 

csharp
using System;

class Program
{
    unsafe static void Main()
    {
        // 在栈上分配 5 个 int 的空间
        int* p = stackalloc int[5];
        
        // 赋值
        for (int i = 0; i < 5; i++)
        {
            p[i] = i * i; // 注意：这里可以用 p[i]，编译器会转成指针运算
        }

        // 读取
        for (int i = 0; i < 5; i++)
        {
            Console.WriteLine(p[i]);
        }
    }
}

四、固定大小的缓冲区（Fixed-size Buffers）—— 结构体里的数组

这是 16.8 节里最晦涩的一块，主要用于 与非托管结构体互操作。

1. 问题：结构体里不能定义数组

普通的 C# 结构体里不能直接定义数组：
csharp
struct BadStruct {
    public int[] Arr; // 实际上存的是“引用”，不是数组本身
}
在内存中，BadStruct 只占一个指针的大小（8字节），数组在别处。

2. 解决：fixed 关键字（在 struct 内）

如果你想定义一个 内存连续的​ 结构体，比如 C 语言里的：
c
struct MyStruct {
    int Arr[5]; // 直接在结构体里占 20 字节
};
C# 必须这样写：
csharp
using System.Runtime.InteropServices;

[StructLayout(LayoutKind.Sequential)]
unsafe struct GoodStruct
{
    // 固定大小的缓冲区
    public fixed int Arr[5]; // 直接在结构体里占 20 字节
    public int Value;
}

class Program
{
    unsafe static void Main()
    {
        GoodStruct s;
        s.Arr[0] = 10; // 直接访问
        s.Value = 20;

        Console.WriteLine(sizeof(GoodStruct)); // 输出 24 (20 + 4)
    }
}

3. 这是什么？

  • ••
    fixed int Arr[5] 告诉 CLR：在 GoodStruct 的内存布局里，预留 5 个 int 的连续空间。
  • ••
    这完全模拟了 C/C++ 的结构体内嵌数组。
  • ••
    必须用 unsafe，因为它打破了 .NET 内存安全的常规（比如越界访问会破坏后面的 Value 字段）。

4. 典型应用场景：P/Invoke

当你调用 Win32 API 或 C 库函数，对方定义了一个包含数组的结构体时，你必须用 fixed 缓冲区来匹配内存布局，否则数据会错位。
