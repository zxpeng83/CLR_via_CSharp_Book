23.1 程序集加载

JIT 编译器把 IL 编译成本地代码时，会查看 IL 引用的类型，然后借助程序集的 TypeRef 和 AssemblyRef 元数据表来判断"哪个程序集定义了这个类型"。CLR 内部通过 System.Reflection.Assembly 的静态方法 Load​ 来完成加载——它是 CLR 版的 LoadLibrary
。
常用的加载方法：
  • ••
    Assembly.Load(assemblyRef)：传入 AssemblyName 或程序集字符串。CLR 会应用版本绑定重定向策略，先查 GAC，再到应用基目录、私有路径子目录、codebase 位置查找。这是动态可扩展应用加载程序集的首选方式​
    。
  • ••
    Assembly.LoadFrom(path)：加载指定路径（甚至可以是 URL）的程序集。内部流程是先调用 AssemblyName.GetAssemblyName 拿到程序集标识，再调用 Assembly.Load；若按标识找不到，则按实参路径加载
    。
  • ••
    Assembly.LoadFile：可从任意路径加载，且允许把"相同标识"的程序集多次加载到同一个 AppDomain
    。
  • ••
    Assembly.ReflectionOnlyLoad / ReflectionOnlyLoadFrom：只加载程序集用于分析元数据，禁止其中任何代码执行​
    。
  • ••
    弱命名程序集调用 Load 时，不会走版本绑定重定向，也不会查 GAC
    。
💡 关于依赖 DLL：可以把依赖的 DLL 作为"嵌入资源"打进 EXE，部署时只需分发一个文件；运行时在 AppDomain.CurrentDomain.AssemblyResolve 事件中登记回调，从资源流中读出字节数组再调用 Assembly.Load(byte[]) 加载
。

23.2 使用反射构建动态可扩展应用程序

元数据本质上是一系列表（类型定义表、字段定义表、方法定义表等）。利用 System.Reflection 命名空间下的类型，可以在运行时"解析"这些元数据表，从而发现并使用编译时完全不了解的类型
。
这种机制的经典场景是宿主应用程序 + 加载项（add-in）：宿主方在编译时并不知道插件的具体类型，需要在运行时动态发现并调用。
⚠️ 注意：要求反射查找名为 int 的类型会通过编译，但运行时返回 null，因为 CLR 只认 System.Int32，不认 int 这个 C# 关键字别名 。

23.3 反射的性能

反射有两个核心缺点：编译时无法保证类型安全​ + 速度慢​
。
慢在哪里：
  1. 1.1.
    类型、成员都用字符串标识，运行时要在元数据表里做大量字符串搜索（通常还不区分大小写）
  2. 2.2.
    用反射调用方法时，实参要先打包成数组 → 内部解包到线程栈 → CLR 检查实参类型 → 检查调用者安全权限
书中给出绕开反射调用的两条推荐路径
：
  • ••
    让类型从编译时已知的基类型派生​ → 运行时构造实例，引用放到基类变量中，调用基类虚方法
  • ••
    让类型实现编译时已知的接口​ → 运行时构造实例，引用放到接口变量中，调用接口方法
📌 作者个人更偏好接口方案，因为基类方案会限制开发人员选择最合适的基类；但涉及版本控制时基类方案更好——往基类加成员，派生类自动继承，而接口加成员则要求所有实现者改代码重编译。强烈建议把接口/基类放到独立的程序集中，以缓解版本控制问题（详见 23.4）。

23.4 设计支持加载项的应用程序

这一节讲如何把"宿主 + 插件"的架构落地。关键思想：把公共接口（或基类）放到一个独立的、版本稳定的程序集中，宿主和加载项都引用它。这样加载项可以独立于宿主发布，宿主在运行时通过 Assembly.LoadFrom 加载插件程序集、通过接口/基类多态调用。

23.5 使用反射发现类型的成员

这里是反射操作最细粒度的部分。

23.5.1 发现类型成员

通过 Type.GetMembers() 等方法获取 MemberInfo 派生对象（如 FieldInfo、MethodInfo、PropertyInfo 等）。

23.5.2 BindingFlags：筛选返回的成员种类

用 BindingFlags 枚举来控制要返回哪些成员（public/private、static/instance、declared only 等）
。

23.5.3 发现类型的接口

通过 Type.GetInterfaces() 获取类型实现的接口列表。

23.5.4 调用类型的成员

调用成员的几种方式，性能从低到高
：
  1. 1.1.
    Type.InvokeMember​ – 最慢，每次都要重新绑定
  2. 2.2.
    FieldInfo / MethodInfo / PropertyInfo 等​ – 一次绑定，多次调用，性能更好
  3. 3.3.
    创建委托引用成员​ – 比方式 2 更快
  4. 4.4.
    C# 的 dynamic 基元类型​ – 简化语法

23.5.5 一次绑定，多次调用

强调用 MethodInfo/FieldInfo 等做"一次绑定、多次调用"，避免每次调用都重复绑定开销。

23.5.6 使用绑定句柄来减少进程的内存耗用

使用 运行时句柄​ RuntimeTypeHandle、RuntimeFieldHandle、RuntimeMethodHandle 来减少进程的内存开销
。当需要在内存中缓存大量类型/成员信息时，存句柄比存 Type/MemberInfo 对象更省内存。

元数据是什么

简单来说，元数据就是描述数据的数据——在这里，它是描述程序集中"有哪些类型、每个类型有哪些成员、这些方法参数是什么、引用了哪些其他程序集"等信息的二进制数据。
打个比方：
  • ••
    你写了一份 Word 文档（= 程序集）
  • ••
    文档里有正文内容（= IL 中间语言代码，真正干活的指令）
  • ••
    但 Word 文档还有一份隐藏的属性信息：作者是谁、创建时间、字数多少、用了哪些样式……（= 元数据）
元数据就是程序集的"自描述说明书"，它告诉 CLR：
  • ••
    这个程序集里定义了哪些类型（类、接口、结构体、枚举、委托）
  • ••
    每个类型里有哪些字段、方法、属性、事件
  • ••
    这些成员的访问修饰符、返回类型、参数类型
  • ••
    这个程序集依赖/引用了哪些其他程序集

元数据的物理形态：表

在 PE 文件格式里，元数据不是杂乱存放的，而是组织成一系列表（table）：
表名
存的内容

FieldDef​

...
共几十张表
每张表由若干记录（row）组成，每条记录有固定的列。比如 TypeDef 表的每一行描述一个类型：它的名称、命名空间、基类、标志位等 。

元数据 vs. 程序集：包含关系

这是关键，记住这句话：
程序集（Assembly）= 清单（Manifest）+ 元数据（Metadata）+ IL 代码 + 资源（Resources）
也就是说，元数据是程序集的内部组成部分之一，二者是"整体与局部"的关系 ：
纯文本
程序集 (.dll / .exe)
├── 清单 (Manifest)        ← 程序集的"身份证"：名称、版本、文化、公钥、入口点
├── 元数据 (Metadata)      ← 类型的详细描述（一堆表）
├── IL 代码                ← 方法体里的实际指令
└── 资源 (Resources)       ← 图片、字符串表等嵌入资源
  • ••
    清单告诉你"我是谁、我依赖谁"
  • ••
    元数据告诉你"我里面有什么类型、这些类型长什么样"
  • ••
    IL​ 才是真正被 CPU 执行的代码（经 JIT 编译后）

元数据在 23 章里扮演的角色

回到你正在学的第 23 章，所有反射操作本质上都是在"读元数据表"：
1. 程序集加载时，CLR 读元数据
当你写 Assembly.Load("SomeLib") 时，CLR 找到 SomeLib.dll，读取它的 AssemblyRef 元数据表，看它依赖哪些程序集，然后递归加载那些依赖项 。这就是 23.1 节讲的程序集加载机制的数据基础。
2. 反射就是遍历元数据表
Type.GetMembers() 本质是扫描 TypeDef 表 + MethodDef / FieldDef 等表，把每行记录包装成 MemberInfo 对象返回给你。这就是为什么 23.3 节说"反射慢"——它要做大量的字符串匹配去查这些表。
3. JIT 编译时，CLR 读 TypeRef + AssemblyRef
上一轮我们提到：JIT 编译 IL 时遇到一个类型引用，会查 IL 的 TypeRef 表和 AssemblyRef 表，判断"这个类型定义在哪个程序集里"，然后触发那个程序集的加载 。这条链路全靠元数据驱动。

用一段 IL 直观感受

用 ildasm 或 dotnet-ildasm 打开任何一个 DLL，你会看到类似：
il
// 元数据里的 TypeDef 表（节选）
.class public auto ansi beforefieldinit MyApp.Person
    extends [mscorlib]System.Object
{
    // 字段（FieldDef 表的记录）
    .field private string '<Name>k__BackingField'

    // 方法（MethodDef 表的记录）
    .method public hidebysig specialname instance string
        get_Name() cil managed { ... }
}
上面这段不是代码，而是元数据的人可读形式——它描述了 Person 类的结构。而 get_Name() 方法 { ... } 花括号里那堆才是 IL 代码。

为什么元数据这么重要

  1. 1.1.
    语言互操作：C# 写的类，VB.NET 能直接用，因为元数据是语言中立的——任何 .NET 语言编译后都生成统一的元数据格式
  2. 2.2.
    无需头文件/IDL：传统 C++ 要 #include 头文件才知道别人定义了什么；.NET 里直接读程序集的元数据就行，所以不需要头文件
  3. 3.3.
    反射的基础：运行时动态发现类型全靠它
  4. 4.4.
    GC 的根基：GC 要判断一个对象是否可回收，需要知道"哪些字段是引用类型"——这信息就在元数据里
  5. 5.5.
    序列化、IDE 智能提示、调试器……全都依赖元数据
一句话串起来：程序集是 .NET 的部署单元，元数据是程序集里的"类型说明书"（一系列二进制表），IL 是真正干活的代码，而反射就是运行时去读这份"说明书"的过程。23 章讲的"程序集加载"和"反射"，本质都是围绕元数据转——加载是为了让 CLR 读到元数据，反射是为了让你在代码里读到元数据。

第 22 章核心回顾（3 个关键概念）

1. CLR 寄宿（CLR Hosting）

CLR 本身是一个 COM 服务器（DLL），任何 Windows 进程都可以把它加载进来当"运行时管家"。宿主通过 ICLRRuntimeHost 接口做五件事 ：
  • ••
    设置宿主管理器（内存、程序集加载、安全、线程同步）
  • ••
    初始化并启动 CLR
  • ••
    加载程序集并执行代码
  • ••
    管理运行时生命周期
  • ••
    停止 CLR
典型宿主：ASP.NET（每个虚拟目录一个 AppDomain）、SQL Server（执行托管存储过程）、以及你自己写的宿主 。

2. AppDomain：程序集的逻辑容器

CLR 启动时自动创建一个默认 AppDomain，它随进程死亡而销毁。除此之外，宿主可以通过托管 API 或 COM 接口让 CLR 创建更多 AppDomain 。
AppDomain 的四大特性 ：
特性
说明
隔离​
一个 AppDomain 里的代码不能直接访问另一个 AppDomain 创建的对象
可卸载​
可以整体卸载一个 AppDomain（但不能单独卸载某个程序集）
可单独保护​
创建时可施加权限集，限制其中代码的权限
可单独配置​
搜索路径、版本绑定重定向、卷影复制、加载器优化等都按 AppDomain 配置
💡 关键限制：CLR 不支持从 AppDomain 中单独卸载一个程序集。要回收程序集占用的内存，唯一的办法是卸载整个 AppDomain 。这条限制直接决定了第 23 章插件架构的设计思路。

3. 跨越 AppDomain 边界

两个 AppDomain 中的对象不能直接互相引用，必须通过：
  • ••
    按引用封送（Marshal-by-Reference）：类型继承 MarshalByRefObject，跨域拿到的是代理对象
  • ••
    按值封送（Marshal-by-Value）：对象可序列化，复制一份到目标 AppDomain

23.1 程序集加载 → 加载进哪个 AppDomain？

Assembly.Load 的文档明确说：JIT 编译器根据 IL 的 TypeRef 和 AssemblyRef 元数据表确定类型所属的程序集，然后把该程序集加载到当前 AppDomain 中​ 。
也就是说：
  • ••
    Assembly.Load("Plugin.dll") 是把 Plugin.dll 加载到调用这段代码所在的 AppDomain
  • ••
    如果你想加载到别的 AppDomain，要用 AppDomain 实例的 Load 方法——但 23 章明确指出这个方法设计上是给非托管宿主调用的，托管代码开发人员应优先用 Assembly.Load​
⚠️ 23 章特别提醒：不要随便调 AppDomain.Load。因为它返回 Assembly 对象时，Assembly 类不继承 MarshalByRefObject，必须按值封送回调用方的 AppDomain，这会导致 CLR 用调用方 AppDomain 的策略去重新定位程序集，很可能抛出 FileNotFoundException 。
所以正确的插件加载姿势是（结合两章）：
  1. 1.1.
    用 22 章的方式创建新的 AppDomain：AppDomain.CreateDomain("PluginDomain", null, setup)
  2. 2.2.
    在新 AppDomain 中创建宿主自己的 MarshalByRefObject 派生类型实例
  3. 3.3.
    通过这个代理对象，在新 AppDomain 内部调用 Assembly.LoadFrom 加载插件程序集
  4. 4.4.
    插件类型构造实例后，转型为编译时已知的接口，通过代理暴露给默认 AppDomain

23.2 动态可扩展应用 → 为什么需要 AppDomain 隔离？

23 章构建插件系统时，如果只是用 Assembly.Load 把插件加载到默认 AppDomain，会遇到一个致命问题：插件程序集永远无法从内存中卸载（只有卸载 AppDomain 才能卸载程序集）。
这正是 22 章 AppDomain 的价值所在——为每个插件创建独立的 AppDomain，不用了就 AppDomain.Unload 整体卸掉，干净利落 。

23.3 反射的性能 → 接口/基类方案与跨域通信衔接

23.3 节强调：用反射直接调用成员很慢，应该把对象转型为编译时已知的接口或基类，通过多态调用 。
这个建议在跨 AppDomain 场景下更重要：
  • ••
    如果你的插件类型实现了宿主已知的接口，那么跨域通信时可以直接把接口引用返回
  • ••
    如果插件类型是 MarshalByRefObject 的派生类，那么跨域拿到的是透明代理，调用接口方法性能尚可
  • ••
    反之，如果只能用反射调用，每次跨域调用都要走封送 + 反射双重开销

微软开发 VS Code 的时候，根本不知道你将来会装什么插件——可能是有人写个"彩虹猫"插件，也可能是微软自己后来开发的 C# 扩展。所以：
  • ••
    编译时（开发 VS Code 时）：微软的程序员写代码，他们不可能引用"彩虹猫插件"的类型，因为这个插件当时还不存在
  • ••
    运行时（你启动 VS Code 后）：VS Code 扫描 extensions 文件夹，发现了你装的插件 DLL，动态加载进来，然后调用插件里实现好的功能
这就是"宿主方在编译时并不知道插件的具体类型，需要在运行时动态发现并调用"。

拆解"编译时不知道"是什么意思

假设没有插件机制，硬编码写死：
csharp
// ❌ 假设 VS Code 团队在代码里直接调用插件
var rainbowCat = new RainbowCatPlugin();  // 编译错误！RainbowCatPlugin 类根本不存在
rainbowCat.Activate();
这行代码编译不过，因为 RainbowCatPlugin 这个类在 VS Code 开发时还没被发明出来。
所以宿主必须换一种方式——不依赖具体类型，只依赖一个"契约"（接口）：
csharp
// ✅ 宿主定义一个接口（契约）
public interface IPlugin
{
    void Activate();   // 所有插件都必须实现这个方法
    string Name { get; }
}

// ✅ 宿主加载插件时，只认 IPlugin 接口，不认具体类型
public class PluginHost
{
    public void LoadAllPlugins(string pluginsFolder)
    {
        foreach (var dllPath in Directory.GetFiles(pluginsFolder, "*.dll"))
        {
            // 1. 动态加载程序集（23.1 节的内容）
            Assembly asm = Assembly.LoadFrom(dllPath);
            
            // 2. 在程序集中查找实现了 IPlugin 接口的类型（23.2 节的内容）
            foreach (var type in asm.ExportedTypes)
            {
                if (typeof(IPlugin).IsAssignableFrom(type))
                {
                    // 3. 动态创建实例（23.3.4 节的内容）
                    IPlugin plugin = (IPlugin)Activator.CreateInstance(type);
                    
                    // 4. 通过接口调用，无需知道具体类型
                    Console.WriteLine($"加载插件: {plugin.Name}");
                    plugin.Activate();
                }
            }
        }
    }
}
注意第 4 步：宿主拿到的变量类型是 IPlugin——这是一个编译时已知的接口，宿主代码可以放心地调用 .Activate()、.Name。至于背后是哪个具体类（RainbowCatPlugin、CSharpExtension、GitLens），宿主完全不关心。

为什么必须这么做？三个核心理由

1. 宿主团队无法预知未来

VS Code 团队 2015 年发布 1.0 版本时，怎么可能知道 2024 年有人会写一个"用 AI 自动补全代码"的插件？所以他们必须把系统设计成对未知插件开放。

2. 插件团队无法修改宿主源码

彩虹猫插件的开发者，不可能去改 VS Code 的源代码把 new RainbowCatPlugin() 加进去——他只能按宿主规定的"契约"（接口）来写插件，然后让宿主在运行时发现它。

3. 热插拔需求

你安装一个新插件后，不想重启 VS Code​ 就能用。这就要求宿主能在运行时动态加载 DLL、动态创建实例、动态调用——这正是 23 章讲的全部内容。

先构造场景

宿主定义了一个"契约"，第三方写了插件。问题是：宿主编译时不知道插件的具体类名，怎么高效调用插件的方法？

方式一：基类派生方案

第 1 步：宿主定义一个基类（编译时已知） 

csharp
// 宿主程序集里定义
public abstract class PluginBase
{
    public abstract void Activate();
    
    // 基类可以提供默认实现，派生类可选覆盖
    public virtual void Deactivate()
    {
        Console.WriteLine("默认卸载逻辑");
    }
    
    public string Name { get; protected set; }
}

第 2 步：插件继承这个基类 

csharp
// 插件程序集里写（第三方开发者）
public class RainbowCatPlugin : PluginBase
{
    public override void Activate()
    {
        Name = "彩虹猫";
        Console.WriteLine("🌈🐱 激活！");
    }
    
    // Deactivate 不重写，用基类的默认实现
}

第 3 步：宿主运行时构造并调用 

csharp
public class PluginHost
{
    public void LoadPlugin(string dllPath)
    {
        Assembly asm = Assembly.LoadFrom(dllPath);
        
        // 找到继承自 PluginBase 的类型
        var pluginType = asm.GetTypes()
            .First(t => t.IsSubclassOf(typeof(PluginBase)));
        
        // 关键：引用放在【基类变量】中
        PluginBase plugin = (PluginBase)Activator.CreateInstance(pluginType);
        
        // 调用【基类虚方法】—— 这里是编译时已知的调用，很快！
        plugin.Activate();      // CLR 多态派发到 RainbowCatPlugin.Activate
        plugin.Deactivate();    // 调用基类默认实现
    }
}
为什么快？​ 因为 plugin 变量的类型是 PluginBase——这是编译时已知的类型。C# 编译器在编译 plugin.Activate() 这行时，就已经知道要调用 PluginBase.Activate 这个虚方法，JIT 生成的是标准的虚方法调用指令（callvirt）。没有运行时字符串查找，没有反射开销。

第 1 步：宿主定义一个接口（编译时已知）

23.3.2 类型对象的准确含义

先搞懂：什么是"类型对象"？

你写的每一个类（比如 Person），在程序运行起来之后，CLR 都会在内存里为它创建一个专门的数据结构，用来存储这个类的所有信息：它叫什么名字、有什么字段、有什么方法、父类是谁、实现了哪些接口……
这个数据结构，就是 类型对象（Type Object）。我们在 C# 代码里通过 typeof(Person) 拿到的那个 System.Type 对象，就是对这个内部数据结构的"托管包装"。

核心规则：每种类型只有一个 Type 对象

不管你在程序的哪个角落、用哪种方式去获取同一个类型的 Type 对象，拿到的永远是同一个引用。
用一个生活例子比喻：
户籍系统里，张三这个人只有一条档案记录。你去派出所查（用身份证号查）、去居委会查（用户口本查）、网上查（用姓名+身份证号查），查出来的都是同一条档案，而不是复印了三份。

代码验证 

csharp
using System;

class Person { }

class Program
{
    static void Main()
    {
        Person p1 = new Person();
        Person p2 = new Person();

        // 方式1：用 typeof 运算符
        Type t1 = typeof(Person);

        // 方式2：用实例的 GetType() 方法
        Type t2 = p1.GetType();
        Type t3 = p2.GetType();

        // 方式3：用字符串全名（包含命名空间）
        Type t4 = Type.GetType("Person");

        Console.WriteLine($"t1 == t2 : {t1 == t2}");   // True
        Console.WriteLine($"t2 == t3 : {t2 == t3}");   // True
        Console.WriteLine($"t1 == t4 : {t1 == t4}");   // True（如果命名空间匹配）

        // 最严格的引用比较
        Console.WriteLine($"引用完全相同: {object.ReferenceEquals(t1, t2)}"); // True
        Console.WriteLine($"t1 的 HashCode: {t1.GetHashCode()}");
        Console.WriteLine($"t2 的 HashCode: {t2.GetHashCode()}"); // 一模一样

23.3.3 构建 Exception 派生类型的一个层次结构

这节到底在干什么？

.NET 基础类库（mscorlib / System.Private.CoreLib）里定义了上百种异常类型，它们之间有着复杂的继承关系：
纯文本
Exception
 ├── SystemException
 │    ├── ArgumentException
 │    │    ├── ArgumentNullException
 │    │    └── ArgumentOutOfRangeException
 │    ├── InvalidOperationException
 │    └── NullReferenceException
 └── ApplicationException
      └── YourCustomException
23.3.3 节的目的就是：写一段代码，自动扫描程序集，把这棵"异常家族树"挖出来，构建成结构化的数据。这在写日志框架、IDE 工具、或者动态异常处理中间件时非常有用。

核心思路

  1. 1.1.
    拿到包含 Exception 类的程序集（typeof(Exception).Assembly）
  2. 2.2.
    遍历里面所有的类型
  3. 3.3.
    筛选出所有继承自 Exception 的类型
  4. 4.4.
    利用 Type.BaseType 属性理清父子关系，构建成一棵树

完整示例代码 

csharp
using System;
using System.Collections.Generic;
using System.Linq;

class Program
{
    static void Main()
    {
        // 第1步：拿到 Exception 所在的程序集
        Assembly coreAssembly = typeof(Exception).Assembly;

        // 第2步：找出所有具体的（非抽象）Exception 派生类
        var allExceptions = coreAssembly.GetTypes()
            .Where(t => t.IsClass 
                     && !t.IsAbstract 
                     && typeof(Exception).IsAssignableFrom(t))
            .ToList();

        Console.WriteLine($"共找到 {allExceptions.Count} 种异常类型\n");

        // 第3步：构建父子关系字典（层次结构）
        // Key = 父类型, Value = 直接子类列表
        Dictionary<Type, List<Type>> hierarchy = new Dictionary<Type, List<Type>>();

        foreach (var exType in allExceptions)
        {
            Type parent = exType.BaseType;
            if (parent == null) continue;

            if (!hierarchy.ContainsKey(parent))
                hierarchy[parent] = new List<Type>();
            
            hierarchy[parent].Add(exType);
        }

        // 第4步：从 Exception 开始，递归打印整棵树
        PrintTree(typeof(Exception), hierarchy, 0);

        // 额外演示：打印某个具体类型的完整继承链
        Console.WriteLine("\n===== 单个类型的继承链 =====");
        PrintInheritanceChain(typeof(ArgumentNullException));
    }

    /// <summary>
    /// 递归打印异常层次树
    /// </summary>
    static void PrintTree(Type parent, Dictionary<Type, List<Type>> tree, int depth)
    {
        Console.WriteLine($"{new string(' ', depth * 2)}{parent.Name}");

        if (tree.ContainsKey(parent))
        {
            foreach (var child in tree[parent].OrderBy(t => t.Name))
            {
                PrintTree(child, tree, depth + 1);
            }
        }
    }

    /// <summary>
    /// 打印某个类型的完整继承链（从自身一直到 object）
    /// </summary>
    static void PrintInheritanceChain(Type type)
    {
        Type current = type;
        while (current != null)
        {
            Console.WriteLine(current.FullName);
            Console.WriteLine("  ↑ 继承自");
            current = current.BaseType;
        }
        Console.WriteLine("System.Object");
    }
}

23.5.4 调用类型的成员

问题背景

假设你有一个类型，需要通过反射来调用它的方法。有几种做法，性能差别巨大。
先准备一个测试用的类：
csharp
public class Calculator
{
    public int Add(int a, int b) => a + b;
    
    public string Name { get; set; } = "MyCalculator";
    
    public void PrintSum(int x, int y)
    {
        Console.WriteLine($"{x} + {y} = {x + y}");
    }
}

方式一：Type.InvokeMember（最慢） 

csharp
Type type = typeof(Calculator);
object instance = Activator.CreateInstance(type);

// 用 InvokeMember 调用 Add 方法
object result = type.InvokeMember(
    "Add",                                              // 方法名（字符串）
    BindingFlags.InvokeMethod | BindingFlags.Public | BindingFlags.Instance,
    null,                                               // Binder（用默认）
    instance,                                           // 目标对象
    new object[] { 1, 2 }                               // 实参数组
);

Console.WriteLine(result); // 3
为什么最慢？
InvokeMember 相当于"一站式服务"——它内部要依次做这些事：
  1. 1.1.
    根据方法名 "Add" 在元数据表里搜索匹配的方法（字符串比对）
  2. 2.2.
    根据 BindingFlags 筛选出正确的方法
  3. 3.3.
    如果找到了多个重载（比如 Add(int, int) 和 Add(double, double)），还要做重载决议（选最匹配的）
  4. 4.4.
    把实参数组里的元素逐个类型检查
  5. 5.5.
    最后才调用
而且每次调用都要重复以上全部步骤。如果你在一个循环里调用 10000 次，搜索就做了 10000 次。

方式二：MethodInfo.Invoke（中等） 

csharp
Type type = typeof(Calculator);
object instance = Activator.CreateInstance(type);

// 先"绑定"一次：找到 MethodInfo
MethodInfo addMethod = type.GetMethod("Add");

// 然后多次调用
for (int i = 0; i < 10000; i++)
{
    object result = addMethod.Invoke(instance, new object[] { i, i + 1 });
}
为什么比方式一快？
关键在于 "一次绑定，多次调用"：
  • ••
    type.GetMethod("Add") —— 这一步做了搜索、筛选、重载决议，拿到了一个 MethodInfo 对象
  • ••
    之后每次 addMethod.Invoke(...) —— 不需要再搜索了，直接调用
搜索只做一次，所以比 InvokeMember 快。但 Invoke 本身仍然有开销：实参要打包成数组、CLR 要检查类型安全、要检查调用权限。

方式三：创建委托（更快） 

csharp
Type type = typeof(Calculator);
object instance = Activator.CreateInstance(type);

// 先获取 MethodInfo（绑定一次）
MethodInfo addMethod = type.GetMethod("Add");

// 把 MethodInfo 包装成强类型委托
var addDelegate = (Func<int, int, int>)Delegate.CreateDelegate(
    typeof(Func<int, int, int>),  // 委托类型
    instance,                      // 目标对象
    addMethod                      // 方法信息
);

// 调用委托 —— 几乎没有反射开销
for (int i = 0; i < 10000; i++)
{
    int result = addDelegate(i, i + 1);  // 直接调用，像普通方法一样快
}
为什么更快？
委托是 CLR 的一等公民。创建委托后，CLR 内部生成一个"跳板"（thunk），直接把调用转发到目标方法。调用委托时：
  • ••
    不需要再查元数据表
  • ••
    不需要打包实参数组
  • ••
    不需要做类型安全检查（编译时已经检查过了）
  • ••
    JIT 甚至可以内联这个小调用
性能接近直接写 calculator.Add(1, 2)。

方式四：dynamic（C# 4.0+，语法最简） 

csharp
using System.Dynamic;

Type type = typeof(Calculator);
object instance = Activator.CreateInstance(type);

// 转为 dynamic
dynamic calc = instance;

// 像普通对象一样调用
calc.PrintSum(1, 2);  // DLR 在运行时解析成员
原理：dynamic 背后是 DLR（Dynamic Language Runtime）。第一次调用 calc.PrintSum 时，DLR 会：
  1. 1.1.
    缓存调用站点（Call Site）
  2. 2.2.
    做一次成员查找和方法绑定
  3. 3.3.
    后续调用直接从缓存中取，不再重复绑定
所以性能和 MethodInfo.Invoke（方式二）接近，但代码写起来最简洁。

23.5.6 使用绑定句柄来减少进程的内存耗用

问题背景

假设你正在写一个工具，需要扫描程序集里所有类型、所有方法，并缓存它们的信息以便后续使用。
直觉写法：
csharp
// 缓存所有方法的 MethodInfo 对象
Dictionary<string, MethodInfo> methodCache = new Dictionary<string, MethodInfo>();

foreach (Type type in Assembly.Load("MyLib").GetTypes())
{
    foreach (MethodInfo method in type.GetMethods())
    {
        methodCache[$"{type.Name}.{method.Name}"] = method;
    }
}
问题：MethodInfo 是个"胖对象"。

为什么 MethodInfo 占用内存大？

一个 MethodInfo 对象内部引用了一整条对象链：
纯文本
MethodInfo
 ├── Name (string)           ← 字符串对象
 ├── DeclaringType (Type)    ← 指向类型对象
 │    ├── FullName (string)
 │    ├── Assembly (Assembly) ← 指向程序集对象
 │    ├── BaseType (Type)
 │    └── ...
 ├── ReturnType (Type)       ← 又是一个 Type 对象
 ├── Parameters (ParameterInfo[]) ← 参数数组
 │    ├── ParameterInfo[0]
 │    │    ├── Name (string)
 │    │    ├── ParameterType (Type)
 │    │    └── ...
 │    └── ParameterInfo[1]
 │         └── ...
 ├── CustomAttributes (object[]) ← 自定义特性
 └── ...
扫描一个大型程序集（比如 System.Private.CoreLib），可能有上万种类型、几十万个方法。如果每个 MethodInfo 连带它引用的整个对象图都常驻内存，内存占用会非常可观。

解决方案：用"绑定句柄"代替"MemberInfo 对象"

CLR 提供了三种轻量级句柄类型：
句柄类型
对应信息
获取方式
RuntimeTypeHandle
类型信息
typeof(T).TypeHandle 或 type.TypeHandle
RuntimeMethodHandle
方法信息
method.MethodHandle
RuntimeFieldHandle
字段信息
field.FieldHandle
句柄本质上是一个轻量级的值类型（内部就是一个指针/令牌），占用内存极小（通常 4~8 字节），而且不持有对 Type、Assembly 等大对象的引用。

代码示例 

csharp
using System;
using System.Reflection;

public class Person
{
    public string Name { get; set; }
    public int Age { get; set; }
    
    public void SayHello() => Console.WriteLine($"Hello, I'm {Name}");
    
    public int GetBirthYear(int currentYear) => currentYear - Age;
}

class Program
{
    static void Main()
    {
        Type type = typeof(Person);
        
        // ===== 获取句柄 =====
        
        // 类型句柄
        RuntimeTypeHandle typeHandle = type.TypeHandle;
        Console.WriteLine($"TypeHandle: {typeHandle}");
        
        // 方法句柄
        MethodInfo sayHelloMethod = type.GetMethod("SayHello");
        RuntimeMethodHandle methodHandle = sayHelloMethod.MethodHandle;
        
        // 属性句柄（通过属性的 getter/setter 方法获取）
        PropertyInfo nameProperty = type.GetProperty("Name");
        RuntimeMethodHandle getterHandle = nameProperty.GetGetMethod().MethodHandle;
        
        // ===== 从句柄还原 =====
        
        // 从句柄还原回 Type 对象
        Type restoredType = Type.GetTypeFromHandle(typeHandle);
        Console.WriteLine($"还原的类型名: {restoredType.Name}"); // Person
        Console.WriteLine($"类型相同: {restoredType == type}");   // True
        
        // 从句柄还原回 MethodInfo 对象
        MethodInfo restoredMethod = (MethodInfo)MethodInfo.GetMethodFromHandle(methodHandle);
        Console.WriteLine($"还原的方法名: {restoredMethod.Name}"); // SayHello
        
        // ===== 实际使用：用句柄做缓存 =====
        
        // 用句柄做 Dictionary 的 Key（比用 Type/MethodInfo 更省内存）
        Dictionary<RuntimeMethodHandle, string> methodCache = 
            new Dictionary<RuntimeMethodHandle, string>();
        
        foreach (MethodInfo method in type.GetMethods(BindingFlags.Public | BindingFlags.Instance | BindingFlags.DeclaredOnly))
        {
            methodCache[method.MethodHandle] = method.Name;
        }
        
        Console.WriteLine($"\n缓存了 {methodCache.Count} 个方法句柄");
        
        // 需要时再还原
        foreach (var kvp in methodCache)
        {
            MethodInfo m = (MethodInfo)MethodInfo.GetMethodFromHandle(kvp.Key);
            Console.WriteLine($"  {m.Name}");
        }
    }
}

需要精确化的一点："加载整个程序集"到底加载了什么？

你说"首先得加载整个程序集"，这里的"加载"需要区分两层含义，不然容易误以为"加载程序集 = 把所有代码都执行了一遍"：

第一层：元数据 + IL 被映射到内存（确实加载了"整个"）

当你调用 Assembly.Load("MyLib") 时，CLR 会：
  • ••
    找到 MyLib.dll 文件
  • ••
    把 PE 文件头、清单、所有元数据表、所有 IL 代码​ 都映射到进程内存中
  • ••
    如果有依赖项（比如 MyLib 引用了 Newtonsoft.Json），CLR 会递归加载依赖项的元数据（这也是为什么有时候你只反射了一个类型，却看到一堆相关程序集被加载进来）
到这一步为止，程序集里的 代码一行都没执行，只是"说明书"被翻开了。

第二层：类型和方法不一定被"初始化"

  • ••
    类型对象（Type Object）：通常在第一次用到该类型时才创建（比如第一次 typeof(T) 或 new T()），不是 Assembly.Load 瞬间就创建好所有类型的 Type 对象
  • ••
    静态构造函数：在类型第一次被访问时触发，不是程序集加载时
  • ••
    JIT 编译：方法的 IL 代码在第一次被调用时才被 JIT 编译成本地机器码，不是加载时就编译
所以更准确的说法是：
"反射一个类型，必须先让包含它的程序集的元数据进入内存。但这只是把'说明书'翻开，不代表把书里所有的'动作'都做了一遍。"

一个关键认知

CLR 的自动加载解决的是"已知依赖"的问题，23 章的 Assembly.Load 解决的是"未知/动态"的问题。
  • ••
    已知依赖：你在 Visual Studio 里"添加引用" → 编译进 AssemblyRef 表 → CLR 启动时自动加载
  • ••
    未知/动态：插件、延迟加载、条件加载 → 必须显式调用 Assembly.Load
这就是为什么普通的 WinForms/WPF/Console 程序里你从来没写过 Assembly.Load——因为所有依赖都是编译时已知的，CLR 自动搞定。只有当你要做"插件系统"、"热更新"、"动态扩展"这类高级架构时，才需要显式调用 23 章的那些 API。
