18.1 这一节在讲什么

核心一句话：定制特性就是“给代码元素贴元数据标签”，编译器把这些标签序列化进 PE 文件的元数据里，运行期靠反射读出来驱动行为。这一节沿着这条线铺了几件事：
1）FCL 里现成的特性先认一遍
Richter 举了几个你肯定眼熟的例子，让你感知“特性不是魔法，是 CLR/编译器/库已经大量在用”的东西：
  • ••
    [DllImport("Kernel32")] → 告诉 CLR 方法体在非托管 DLL 里
  • ••
    [Serializable] → 告诉序列化格式化器“这个类型的字段可以序列化”
  • ••
    [AssemblyVersion("1.0.0")] → 钉程序集版本号
  • ••
    [Flags] → 枚举变成位标志集合
2）特性能贴在哪
C# 允许几乎任何元数据可表示的东西：assembly / module / type / field / method / param / return / property / event，还可以用前缀显式指定目标，比如：
csharp
[assembly: SomeAttr]      // 贴到整个程序集
[return: MarshalAs(...)]  // 贴到方法返回值
[param: In, Out]          // 贴到参数
多数情况编译器能推断，但有些模糊场合（比如泛型参数、返回值）得手写前缀。
3）特性的本质：Attribute 派生类的实例
符合 CLS 规范要求 → 必须直接或间接从 System.Attribute 派生，C# 也只认这种。
应用特性的语法看起来像调用构造器，其实就是在描述“将来反射时要怎么 new 这个实例”：
csharp
[DllImport("Kernel32", CharSet = CharSet.Auto, SetLastError = true)]
  • ••
    "Kernel32" → 构造器实参，叫定位参数（positional），必填
  • ••
    CharSet = ... → 设公共字段/属性，叫命名参数（named），可选
4）几种等价写法（这一节的小彩蛋）
csharp
[Serializable][Flags]
[Serializable, Flags]
[FlagsAttribute, SerializableAttribute]
[FlagsAttribute()][Serializable()]
这四种完全一样。推导：每个特性可单开方括号，也可逗号塞同一对；构造器无参时圆括号可省；Attribute 后缀可省。

为什么 Attribute 后缀可以省

这是 C# 编译器层的语法糖，不是 CLR 层的。System.Attribute 派生类的命名惯例是 XxxAttribute，但应用的时候写 [Xxx] 还是 [XxxAttribute] 都行——规范 17.2 原文：
按照约定，属性类的命名带有 Attribute 后缀。attribute_name 可以包含或省略此后缀。
编译器解析 [Xxx] 时的实际动作是：同时去查 Xxx 和 XxxAttribute 两个类型，找到哪个用哪个。

⚠️ 但这里有个坑：歧义编译错误

如果两个都存在——既有类 Xxx 又有类 XxxAttribute——编译器不给你“二选一”，直接 CS0104 歧义报错
。这时候用逐字标识符 @ 化解：
csharp
[@Foo]       // 只匹配 Foo，不匹配 FooAttribute
[@FooAttribute] // 匹配 FooAttribute（逐字不影响后缀查找）
顺便说：[Serializable] 真实类名其实是 SerializableAttribute，[DllImport] 真实类名是 DllImportAttribute——你在元数据里看到的、MSDN 里点进去的，都是带 Attribute 后缀的那个；源码里写短的那个，是 C# 编译器帮你补全的。
设计动机就是 Richter 说的“减少击键、提升可读性”——方括号里本来就已经是特性语境了，再写一遍 Attribute 纯属视觉噪音。
18.1 读下来其实就建立一个心智模型：特性 = Attribute 派生类实例 + 编译期序列化进元数据 + 运行期反射反序列化。后面 18.2 开始让你自己写 class FooAttribute : Attribute，18.4 才讲 IsDefined / GetCustomAttribute 怎么把元数据里的字节真的变回对象——这条链路顺下来这一章就通了。

  1. 1.1.
    首先点破核心：[Serializable]本身只是个元数据标记，它的类里没有任何"序列化逻辑"，你去看SerializableAttribute源码就知道，它就是个空壳子，继承Attribute、啥逻辑都没有。

  3. 3.3.
    延伸到一般规律：几乎所有特性都是这个模式——Attribute只是"声明/标注"，逻辑在读取这个特性的框架代码里。DllImport→CLR的Interop层；Obsolete→C#编译器；Conditional→编译器裁剪；ASP.NET的[Authorize]→MVC过滤器管道；NUnit的[Test]→测试 runner。
  4. 4.4.
    顺手区分一下"编译期特性"（Obsolete、Conditional，编译器直接消费，元数据都可能不留下）vs"运行期特性"（Serializable、DllImport，进元数据，反射消费），这个维度Richter 18章后面也会带到（CustomAttributeData那段其实偏安全/运行时）。

很好的问题——这正好戳到"特性"这个概念最容易让人迷糊的地方：特性本身不实现功能，它只是个"标签"，真正干活的是"读这个标签的代码"。

以 [Serializable] 为例拆开看

SerializableAttribute 这个类长这样（简化）：
csharp
namespace System
{
    [AttributeUsage(AttributeTargets.Class | AttributeTargets.Struct | AttributeTargets.Enum | AttributeTargets.Delegate)]
    public sealed class SerializableAttribute : Attribute
    {
        // 注意：构造器是空的，没有任何逻辑
        public SerializableAttribute() { }
    }
}
你贴 [Serializable]，编译器做的事就只是在类型的元数据里写一条记录："这个 Type 被 SerializableAttribute 标记过"。这个类本身一行业务逻辑都没有。
那"允许序列化"在哪实现的？——在序列化器（Formatter）里。
比如老牌的 BinaryFormatter（虽然现在不推荐用了，但逻辑最清楚）：
csharp
// BinaryFormatter.Serialize 内部大致逻辑
internal static void CheckSerializable(Type t)
{
    if (!t.IsSerializable)   // 本质就是去查元数据里有没有 [Serializable]
        throw new SerializationException(
            $"Type '{t}' is not marked as serializable.");
}
t.IsSerializable 底层走的其实就是 Attribute.IsDefined(t, typeof(SerializableAttribute))。发现你贴了 → 继续走序列化流程；没贴 → 抛异常。
所以链条是：
你贴 [Serializable] → 编译器写元数据 → BinaryFormatter 反射查元数据 → 发现标记 → 放行序列化
"允许"这两个字不是 SerializableAttribute 做的，是序列化器看到这个标记后决定放行。

这就引出一个重要视角

特性 = 编译期写入的声明性元数据​ + 某种框架在合适时机读取它并执行对应逻辑
所以你写自己的 [MyAttribute] 贴在某方法上，它本身啥也不会做——除非你自己（或某个框架）在某个地方写 GetCustomAttribute 去读它，然后 decide 做什么。这也是为什么 Richter 18.5 专门讲 IsDefined / GetCustomAttribute / CustomAttributeData——那是"消费者侧"的 API，没有这部分，特性就是死数据。
举个自制小例子把这条链闭环：
csharp
// 1. 定义（纯数据，无逻辑）
[AttributeUsage(AttributeTargets.Method)]
public class AutoRunAttribute : Attribute { }

// 2. 贴标签
class Program
{
    [AutoRun]
    static void Hello() => Console.WriteLine("跑了");
    
    static void Main()
    {
        // 3. 消费者：启动时任扫一遍，找到就 Invoke
        var methods = typeof(Program).GetMethods(BindingFlags.Static | BindingFlags.NonPublic);
        foreach (var m in methods)
        {
            if (m.IsDefined(typeof(AutoRunAttribute), false))
                m.Invoke(null, null);
        }
    }
}
[AutoRun] 本身啥也不干，Main 里那段扫描代码才是"功能"所在。这跟 [Serializable] + BinaryFormatter 是同一个故事，只是规模小。
所以回到你的问题："允许序列化"不在 SerializableAttribute 里，在 BinaryFormatter（或任何序列化器）的实现里——它约定"见到这标签我才序列化"。​ 理解到这一层，特性的整个设计哲学就通了：它是声明式编程的载体，把"做什么"和"怎么做"解耦——你只管贴标签声明意图，框架负责读标签执行逻辑。

Richter这节其实在讲一个核心矛盾：特性要能在编译期写入元数据，又要能在运行期还原成对象。元数据格式决定了能存什么，CLR又规定了能还原什么。可以用对比表格把允许类型和禁止类型列出来，再举几个典型例子说明为什么某些类型不行。

一、核心结论先记住

特性构造器的实参 + 命名字段/属性的值，必须在编译期就能确定，并且必须是“元数据兼容类型”。
换句话说：[ ] 里写的不是普通 C# 表达式，而是元数据字面量。

二、CLR 允许哪些“写进元数据”的类型？

Richter 列了一个白名单，你完全可以把它当成“特性专用类型表”：
分类
允许的具体类型
简单类型
bool, byte, char, double, float, int, long, short, string
枚举
任意 enum（本质是整型）
Type
typeof(Foo)（写入的是 TypeRef/TypeDef Token）
数组
上述类型的数组（如 int[], string[]）
⚠️ 注意：这是闭集，不在表里的一律不行。

三、为什么会有这些限制？（关键）

1️⃣ 元数据里不存“对象”，只存“值”

特性信息存在 Metadata Table​ 里，不是 GC 堆里。
比如你写：
csharp
[MyAttr(10, "hello")]
编译器做的是：
  • ••
    把 10 写成一个 Int32 常量
  • ••
    把 "hello" 写成一个 #US (User String) 堆偏移
  • ••
    在 CustomAttribute 表里记一条记录
不会 new 一个对象，也不会执行任何代码。
👉 所以下面这种写法是非法的：
csharp
[MyAttr(DateTime.Now)]   // ❌ DateTime 不是常量
[MyAttr(new object())]   // ❌ new 表达式
[MyAttr(GetValue())]     // ❌ 方法调用
因为这些只能在运行期算出来，而特性必须在编译期定死。

2️⃣ Type 是个特例（非常重要）

这是本节最容易晕的点。
✅ 允许：
csharp
[MyAttr(typeof(FileStream))]
原因是：
  • ••
    typeof(FileStream) 在编译期就能解析
  • ••
    编译器写入的是 TypeRef / TypeDef 元数据 token
  • ••
    运行期 GetCustomAttribute 时，CLR 再用这个 token 解析出 Type 对象
❌ 不允许：
csharp
[MyAttr(fileStream.GetType())] // ❌ 运行期才能知道

四、数组为什么可以？（Richter 特意讲的）

CLR 支持 一维 0 下标数组（SZArray）​ 作为特性参数。
csharp
[AttributeUsage(AttributeTargets.Class)]
public class MyAttr : Attribute
{
    public int[] Values { get; }

    public MyAttr(int[] values)
    {
        Values = values;
    }
}

[MyAttr(new int[] { 1, 2, 3 })]
class Test { }
这里发生了什么？
  • ••
    {1,2,3} 被编译成一个静态只读数组
  • ••
    元数据里保存的是数组元素的引用
  • ••
    运行期反序列化回来
⚠️ 但注意：数组里的元素仍然必须遵守上面的白名单。

五、枚举为什么可以？（这是个坑） 

csharp
enum Color { Red, Blue }

[MyAttr(Color.Red)]
原因是：枚举底层是整型常量，编译期完全确定。
但 Richtere 提醒一点：
如果你改了枚举的定义（比如插入一个新值），已编译好的特性不会自动更新。
这是元数据绑定带来的副作用。

七、为什么字段 / 属性也要遵守同样规则？

Richter 强调：命名参数 = 构造完成后赋值。

等价于（概念上）：

所以：

  • ••

贴完 [Serializable] 编译完，元数据 CustomAttribute 表里有一条记录，长这样（概念上）：
纯文本
Parent: TypeDef → MyClass
Type: TypeRef → SerializableAttribute
Constructor Args: (empty)
Named Args: (empty)
它只是一个"配方"——new SerializableAttribute() 需要的参数都记着，但对象还没 new。
"检测特性" = 按配方把对象造出来（或者至少确认配方存在）。

二、三套 API，Richter 按"从轻到重"给的

1️⃣ IsDefined —— 最轻，只"看一眼有没有" 

csharp
bool Attribute.IsDefined(MemberInfo element, Type attributeType)
bool Attribute.IsDefined(MemberInfo element, Type attributeType, bool inherit)
行为：只查元数据表，不构造 Attribute 对象。
csharp
// 判断 MyClass 有没有 [Serializable]
bool ok = Attribute.IsDefined(typeof(MyClass), typeof(SerializableAttribute));
适合场景：你只关心"有没有"，不关心参数值。比如 BinaryFormatter 里那个 CheckSerializable，用 IsDefined 就够了，没必要 new 一个空对象的 SerializableAttribute 出来浪费。
💡 Richter 特意点了这个性能点：频繁扫特性（比如 MVC 启动扫全程序集 Controller），IsDefined 比 GetCustomAttribute 便宜，因为后者要真的 invoke 构造器、设命名字段。

2️⃣ GetCustomAttribute(s) —— 反序列化，造对象 

csharp
Attribute Attribute.GetCustomAttribute(MemberInfo, Type)
Attribute[] Attribute.GetCustomAttributes(MemberInfo, Type, bool inherit)
行为：
  1. 1.1.
    查元数据里有没有这条 CustomAttribute 记录
  2. 2.2.
    有 → 按记录的构造器参数 new 实例
  3. 3.3.
    再按命名字段/属性赋值
  4. 4.4.
    返回你这个 Attribute 对象
csharp
class AuthorAttribute : Attribute
{
    public string Name { get; }
    public AuthorAttribute(string name) => Name = name;
}

[Author("Jeffrey")]
class Book {}

var attr = (AuthorAttribute)Attribute.GetCustomAttribute(
    typeof(Book), typeof(AuthorAttribute));
Console.WriteLine(attr.Name); // "Jeffrey"
这一步你就明白 18.3 的限制为啥那么严了——这里要真的调构造器，new AuthorAttribute("Jeffrey")，所以构造器参数必须是元数据能表示的常量，否则反序列化不了。

3️⃣ MemberInfo.GetCustomAttribute(s) —— 实例方法版 

csharp
var attrs = typeof(Book).GetCustomAttributes(typeof(AuthorAttribute), false);
Richter 提了一句：System.Attribute 的静态方法内部其实也是调 MemberInfo 的实例方法，两套等价，看你顺手。

三、那个 inherit 参数（本节最容易踩的坑）

三个 API 都有个 bool inherit，默认 false。Richter 用不小篇幅讲这个。

规则一句话

类/方法/属性/事件​ 上，inherit: true 会让 CLR 沿着继承链往上追查基类有没有贴这个特性。
csharp
[Author("Base")]
class Base {}

class Derived : Base {}   // 自己没贴

// inherit = false → 找不到
Attribute.GetCustomAttribute(typeof(Derived), typeof(AuthorAttribute), false); // null

// inherit = true → 追到 Base，找到了
Attribute.GetCustomAttribute(typeof(Derived), typeof(AuthorAttribute), true);  // Base 那个

但有三个坑 Richter 点名了

坑 1：[AttributeUsage(Inherited = false)] 会阻断
csharp
[AttributeUsage(AttributeTargets.Class, Inherited = false)]
class AuthorAttribute : Attribute { ... }

[Author("Base")]
class Base {}
class Derived : Base {}

Attribute.GetCustomAttribute(typeof(Derived), typeof(AuthorAttribute), true); // null！
虽然 inherit=true 说"往上追"，但特性类自己声明了 Inherited=false → 这条特性拒绝被继承。
坑 2：不是所有目标都能"继承"
  • ••
    能追：Type（类继承）、Method（virtual/override）、Property、Event
  • ••
    不能追：Field（CLR 里字段不参与继承语义）、Assembly、Module、ReturnValue、Param
对 Field 传 inherit:true 也没用，CLR 直接忽略。
坑 3：方法 override 场景的"覆盖"语义
csharp
class Base
{
    [Obsolete]
    virtual void M() { }
}

class Derived : Base
{
    [Obsolete("new msg")]   // AllowMultiple=false，默认覆盖基类那份
    override void M() { }
}
inherit=true 在 Derived.M 上查，拿到的是 Derived 自己贴的那份（新 msg），基类的被"盖掉"——因为 Obsolete 的 AllowMultiple = false。如果 AllowMultiple=true（比如某些框架自己定义的），那基类的 + 派生类的会叠加返回数组。

四、CustomAttributeData —— 本节收尾的安全 API

Richter 这一节最后讲这个，动机是"反序列化特性可能触发代码执行 + 加载依赖类型"。

问题在哪？

GetCustomAttribute 内部要做：
  1. 1.1.
    解析构造器参数里的 typeof(X) → 得加载 X 这个 Type（可能触发程序集加载）
  2. 2.2.
    new AttributeXXX(args) → 执行构造器代码（特性作者可以在构造器里写任意逻辑，包括抛异常、访问文件、调非托管…）
在沙箱 / 只加载元数据不加载执行代码的场景下（比如工具、反编译、部分信任），这不行。

CustomAttributeData 的解法 

csharp
IList<CustomAttributeData> data = CustomAttributeData.GetCustomAttributes(typeof(Book));
foreach (var d in data)
{
    Console.WriteLine(d.AttributeType.FullName);        // 特性类名
    Console.WriteLine(d.ConstructorArguments[0]);       // 构造器参数（原始值）
    foreach (var na in d.NamedArguments)
        Console.WriteLine(na.MemberName + "=" + na.TypedValue.Value);
}
关键区别：
GetCustomAttribute
CustomAttributeData
new 实例？
✅ 是，调构造器
❌ 否，只给"配方"
加载依赖 Type？
✅ 会（typeof 参数要解析）
❌ 不会，Type 以 TypeHandle 形式懒表示
执行特性作者代码？
✅ 会
❌ 不会
所以 Richter 说：只关心"贴了什么、参数是什么"，不打算真用这个 Attribute 对象 → 用 CustomAttributeData 更安全更轻。

五、把 18.3 + 18.4 串成一句完整的话

18.3 你写 [Foo(1, typeof(Bar))] → 编译器把 1 和 Bar 的 TypeRef 序列化进元数据 CustomAttribute 表；
18.4 你调 GetCustomAttribute → CLR 按表里的配方 反序列化：加载 Bar、new Foo(1)、赋值命名字段 → 返回一个活对象。
IsDefined 是"只查表不配方"，CustomAttributeData 是"只给配方不动手"。
