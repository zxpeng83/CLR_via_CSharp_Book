用户在啃《CLR via C#》第9章，看到9.6常量性那一节，然后抛出这个问题——'C#明明有const关键字啊，Jeffrey Richter为什么说CLR不支持常量性？'这是这章一个非常经典的认知冲突点，得把两层拆开讲清楚。第一层：C#的const只能修饰primitive/built-in类型+string，编译期直接把字面量塞进调用方的metadata，运行时根本不存在那个symbol，所以叫'编译期常量'，而且必须是编译能算出的值。第二层：CLR确实在字段层面有Literal和InitOnly（readonly）两种标记，但Literal就是C# const的那套（只限built-in），InitOnly是readonly——运行时常量但可以改（构造函数里能赋值，反射也能改）。Richter说的'CLR不支持const对象'，指的是你不能写一个class Foo { public const SomeClass x = new SomeClass(); }这种——引用类型的const除了string被特例化外，别的都不行，因为new要在运行时算。然后顺手补一下readonly和const的差异（runtime vs compile-time、mutable inside ctor、数组readonly只是引用不可变元素可变这个坑），这样用户就能明白Richter那句'CLR不支持常量性'指的是对象级别的immutability，不是C# const关键字不存在。不用搜，这是书内概念辨析。
好问题，这里有个"语法层面"和"CLR 层面"的区分，Richter 说的"CLR 不支持常量性"指的不是 C# 没有 const 关键字，而是另一回事。

C# 的 const 是什么

C# 的 const 只能用在编译期能确定值的 primitive / built-in 类型 + string：
csharp
public const int Max = 100;              // ✅
public const string Name = "hello";       // ✅（string 是特例）
public const DateTime T = new DateTime(); // ❌ 编译错
它的本质是：
  • ••
    编译期把值直接内联到调用方的 IL 里（ldc.i4.s 100），原程序集里那个 Max 字段本身其实带的是 Literal 元数据标志
  • ••
    带有 System.Runtime.CompilerServices.CompilerGenerated + Literal 属性，运行时根本没有"读取这个字段"这一步
  • ••
    所以跨程序集时，A 引用 B 的 const，B 改了重编、A 不重编 → A 还拿着旧值，这是这章前面 9.1 也提到的坑

那 Richter 说"CLR 不支持常量性"指什么

他指的是 "对象级别的 immutability（不可变性）"，也就是你能不能声明一个"对象一旦构造完，所有字段都不能再改"的语义，像 C++ 的 const MyClass& 那种。
CLR 层面缺的东西：
  1. 1.1.
    没有 per-instance 或 per-field 的"写保护"机制——字段要么靠 readonly（C# 层，只限制"非构造器内不能赋值"，但 CLR 不阻止反射 SetValue 去改），要么靠 initonly 标志，但同样是弱约束。
  2. 2.2.
    没有"这个方法不修改对象"的契约——C# 连 const 成员方法都没有（C++ 有），你没法在 CLR 层面保证"调这个方法不会动字段"。
  3. 3.3.
    引用类型 const 基本不可用——除了 string 被 JIT/CLR 特例化了，const SomeClass x = new SomeClass() 这种写法 C# 直接拒绝，因为 new 是运行时行为，塞不进 metadata 字面量。
所以 Richter 那句的意思是：
C# 的 const ≠ CLR 有常量性支持。const 只是编译器+metadata 的把戏（Literal），管不了"对象不可变"这件事；而 CLR 本身没有 Verifier 层面的"这个对象/字段不能再写"的强制机制，要 immutable 只能靠类设计者自己（比如 String 那种返回新实例的写法，或者所有字段 readonly + 深层不可变）。

一句话定义

内联（Inline），就是把一个“被调用的函数/常量”的代码，直接复制粘贴到调用它的地方，从而省去“调用”这个过程。

1. 生活中的比喻

想象你去餐厅点餐：
  • ••
    普通调用：你对服务员说“我要一份鱼香肉丝”。服务员跑去厨房告诉厨师，厨师做好后端出来。这中间有沟通成本（调用开销）。
  • ••
    内联：菜单背面直接印着鱼香肉丝的菜谱。你自己看一眼就会做了，根本不用喊服务员。这就省去了沟通成本。

2. 针对你刚才问的 const（常量内联）

这是你现在最需要理解的场景。
看这段代码：
csharp
// Assembly A
public class Utils {
    public const int MaxCount = 100;
}

// Assembly B (调用方)
int x = Utils.MaxCount;
Console.WriteLine(x);
如果没有内联（假设它只是一个普通静态只读字段）：
编译后的 IL 会是：“去加载 Utils 类的 MaxCount 字段的值”。运行时要去 A.dll 的内存里把这个数值找出来。
C# 编译器实际做的（内联）：
编译器发现 MaxCount 是 const，它在编译 B 的时候，根本不会记录“我要去 A 那里拿数据”，而是直接把数字 100 写死在 B 的 IL 代码里。
编译后 B 的 IL 实际上变成了：
il
ldc.i4.s 100   // 把整数 100 推入堆栈
这就叫常量内联。
带来的后果（这章提到的坑）：
如果有一天你把 A 里的 MaxCount 改成了 200 并重新编译，但 B 没有重新编译。
运行 B 时，它依然输出 100。因为 B 的代码里根本没有去查 A，它只认识那个被“内联”进来的 100。

3. 另一个常见场景：方法内联（JIT优化）

虽然第9章没细讲，但为了让你体系化理解，必须提一下 Method Inlining。
这是 JIT（即时编译器）干的事，不是 C# 编译器干的。
看代码：
csharp
int Add(int a, int b) => a + b;

int result = Add(3, 5);
Console.WriteLine(result);
如果没有内联：
程序需要先跳转到 Add 方法的地址，执行加法，再跳回来。这涉及压栈、出栈（开销很小，但高频调用累积起来就大了）。
JIT 做了内联优化后：
JIT 发现 Add 方法很简单，它会直接在调用处把代码展开：
csharp
int result = 3 + 5; // 甚至直接优化成 int result = 8;
Console.WriteLine(result);
Add 方法在运行时甚至可能根本不存在独立的机器码。
为什么 C# 不让你控制这个？
因为 C# 有 CLR。在 C++ 里你需要手动写 inline 关键字建议编译器内联，但在 .NET 里，JIT 比人类更懂什么时候该内联（它知道CPU型号、运行时压力等），所以我们不需要（也不能）像 C++ 那样精确控制。

4. 总结：内联的利与弊

方面
说明
优点​
速度极快：消除了函数调用开销（压栈/跳转）。
更好的优化：内联后，编译器可以做更深度的优化（比如常量折叠）。
缺点​
代码膨胀：代码被复制了多次，程序体积变大。
维护性问题（特指 const）：正如刚才说的，旧值被固化在调用方，修改原始值可能引发隐蔽 Bug。

10.1 无参属性（Property）

  • ••
    本质：编译器生成 get_Xxx / set_Xxx 两个方法 + 元数据里的 PropertyDef 记录项。CLR 运行时只认方法，不认元数据，元数据是给编译器和 Reflection 用的。
  • ••
    AIP 自动实现属性的槽点（Richter 自己不用）：
    • ••
      不能在声明处初始化（得在每个 ctor 里写）
    • ••
      序列化坑：编译器生成的支持字段名不定，重编译可能变，反序列化炸
    • ••
      调试不能在 get/set 上打断点
    • ••
      必须同时 get+set，不能只自动实现一个
  • ••
    10.1.2 属性和字段的 7 条差异（这节是灵魂）：
    1. 1.1.
      属性可只读/只写，字段不行（readonly 也只是 ctor 外不可写）
    2. 2.2.
      属性可能抛异常，字段不会
    3. 3.3.
      属性不能当 out/ref 参数
    4. 4.4.
      属性可能慢（线程同步、MarshalByRefObject 远程调用巨慢）
    5. 5.5.
      连续调用属性可能每次返回值不同（DateTime.Now 被点名是设计错误）
    6. 6.6.
      属性可能有 side effect（调试器监视窗口自动求值那个坑）
    7. 7.7.
      属性可能返回拷贝，改了不作用到原对象

    对象/集合初始化器：new Employee { Name = "Jeff", Age = 45 } 纯语法糖，编译器展开成一堆赋值。
  • ••

这句话是理解这一章的命门。Jeffrey Richter 在这一章反复强调的就是：CLR 其实并不知道“属性”的存在，它只认方法。
我们可以把这个过程拆开来看，你就彻底通透了：

1. C# 编译器干了什么？

当你写下这段 C# 代码时：
csharp
public class Person {
    public string Name { get; set; }
}
C# 编译器（Roslyn）在生成 IL 的时候，会偷偷做两件事：
  1. 1.1.
    生成一个私有字段（如果是自动属性）：private string <Name>k__BackingField
  2. 2.2.
    生成两个方法：
    • ••
      get_Name() : string
    • ••
      set_Name(string value) : void

2. CLR 看到了什么？

CLR 加载程序集后，它看到的只有：
  • ••
    一个私有字段。
  • ••
    两个普通的方法 (get_Name, set_Name)。
  • ••
    一段额外的元数据（Metadata），记录了“这两个方法和那个叫 Name 的属性是关联的”。
关键点：​ CLR 在运行代码时，完全不看那段元数据，它只执行那两个方法。元数据是给编译器、Visual Studio 智能感知和反射（Reflection）用的。

3. 证据：IL 代码

当你写 p.Name = "Jeff"; 时，编译器把它翻译成了对 set_Name 的调用。
当你写 var n = p.Name; 时，编译器把它翻译成了对 get_Name 的调用。
这就是为什么 Richter 说“属性是方法”。

但是，为什么 C# 要造这个“糖”？

既然本质是方法，为什么不直接让我写 p.set_Name("Jeff")？
这涉及到了设计规范（Design Guidelines）：
  1. 1.1.
    自然语言映射：person.Age 读起来像是在询问一个“特征”，而 person.GetAge() 读起来像是在请求一个“动作”。属性适合表示名词性的状态，方法适合表示动词性的行为。
  2. 2.2.
    数据绑定（Data Binding）：UI 框架（WPF/WinForms）通常只认 Property，不认 Method。因为它们需要的是“数据源的特征”，而不是“命令”。
  3. 3.3.
    统一访问：你可以把 public string Name; 改成属性，而不用修改调用方的代码（二进制兼容）。

一个重要的补充：索引器也是糖

不仅是普通属性，索引器（Indexer）也是糖。
csharp
public string this[int index] { ... }
编译器生成的其实是：
csharp
string get_Item(int index) { ... }
void set_Item(int index, string value) { ... }
这就是为什么这章后面会提到 IndexerName 特性——因为默认生成的方法名就叫 get_Item。

唯一的“例外”（冷知识）

虽然我们说它是语法糖，但有一个地方它比普通方法“高级”一点点：
属性支持 init 访问器（C# 9+）。
csharp
public string Name { get; init; }
编译器生成的 set 方法会被标记为 IsInitOnly，这让 CLR 在对象初始化阶段允许写入，之后禁止。这是极少数 CLR 专门为属性（或者说为了 init）提供的特殊支持，普通的 void SetName(string name) 方法是做不到这一点的（除非你自己写一堆检查逻辑）。
总结：
你现在的直觉非常准。属性 = 方法 + 元数据 + 语法糖。理解了这一点，第10章里 Richter 对属性的那些吐槽（比如“属性可能很慢”、“属性有副作用”）就全都能对应上了——因为你调用的本质上就是一个方法，方法能干的所有坏事（抛异常、耗时、改状态），属性都能干。

1. 什么是“支持字段”（Backing Field）？

这是最常见的情况，但不是唯一情况。
csharp
public class Person {
    // 这就是“支持字段”
    private string _name; 

    public string Name {
        get { return _name; }      // 访问支持字段
        set { _name = value; }     // 修改支持字段
    }
}
在这种“最无聊”的情况下，_name 负责在内存里存数据，Name 属性只是提供了一个受控的访问入口。这也是自动属性（AIP）背后的真相。

2. 情况一：没有字段，直接和系统打交道（Thread.Priority）

System.Threading.Thread.Priority 就是一个典型例子。
你可能以为 Thread 类内部是这样的：
csharp
class Thread {
    private int _priority; // 你以为有这个字段？
    public int Priority { get; set; }
}
事实并非如此。
线程的优先级并不保存在 .NET 对象的内存里，而是保存在 Windows 操作系统内核（Kernel）​ 的数据结构中。
当你写：
csharp
Thread.CurrentThread.Priority = ThreadPriority.High;
实际上发生的是：
  1. 1.1.
    set_Priority 方法被调用。
  2. 2.2.
    这个方法内部调用了 Windows 的 Win32 API（比如 SetThreadPriority）。
  3. 3.3.
    CPU 去修改操作系统内核里记录该线程优先级的那个值。
反过来读的时候：
csharp
var p = Thread.CurrentThread.Priority;
get_Priority 并不是去读 _priority 字段，而是再次调用系统 API，问操作系统：“嘿，这个线程现在的优先级是多少？”
结论：​ 这时候属性就像一个代理（Proxy），它背后没有自己的仓库（字段），而是去问别的系统（操作系统）要数据。

3. 情况二：没有字段，实时计算（数组长度、矩形面积）

这种情况更直观，数据不需要存，算一下就有了。
例子1：数组的 Length
csharp
int[] arr = new int[10];
int len = arr.Length; // Length 是属性
CLR 在管理数组时，确实在内存里记录了数组的长度（为了边界检查），但这个值不是通过一个 public int length; 字段暴露给你的。
Length 属性在 get 的时候，是去读取数组对象头部的那个“长度信息”。
为什么不做成字段？因为字段可以被反射随便改，如果有人把 arr.length 改了，整个 CLR 的内存安全就崩塌了。做成属性，只读，安全。
例子2：矩形的面积
csharp
public class Rectangle {
    public double Width { get; set; }
    public double Height { get; set; }

    // 没有 backing field 的只读属性
    public double Area {
        get { return Width * Height; } // 实时计算
    }
}
这里 Area 就没有自己的私有字段 _area。
  • ••
    如果你存一个 _area 字段，当用户修改 Width 时，你必须记得同步更新 _area，这非常容易出 Bug。
  • ••
    如果不存，每次访问 Area 时现算，虽然慢一点点，但保证了数据的绝对一致性。

  • ••

  • ••

先翻译一下这段话在说什么

作者想表达三个核心点：
  1. 1.1.
    AIP 默认是可读可写的（除非你用 private set 或 C# 6.0+ 的 { get; }）。
  2. 2.2.
    AIP 是一个整体：编译器要么全帮你干，要么全不帮你干。
  3. 3.3.
    只要你碰了其中一个访问器（get 或 set），编译器就罢工了，剩下的那个也不会再自动生成。

1. 为什么 AIP 必须同时生成 get 和 set？（旧版 C# 语境）

这是 Richter 写这本书时的 C# 版本（大概是 C# 3.0/4.0）的限制。那时候还没有 C# 6.0 的只读自动属性。
作者的逻辑是：
AIP 的核心是编译器帮你生成一个隐藏的后台字段（backing field）。
  • ••
    如果你只有 get，编译器不知道你是不是打算自己写 set。
  • ••
    如果你只有 set，编译器不知道你是不是打算自己写 get。
为了确保这个隐藏字段能被正确初始化且不出乱子，早期的编译器设计决定：只要用 AIP，就默认你是想要一个普通的读写属性。
注意：现在的 C#（6.0+）已经支持 { get; } 只读自动属性了，编译器会在构造函数结束后锁定这个字段。但书中讲的是当时的设计逻辑。

2. 关键难点：“只写字段的支持字段到底是什么名字”

这句话有点绕，我们换个说法：
假设你这样写：
csharp
public class User {
    // 假设这是合法的：只想自动实现 set，get 我自己写
    public string Name {
        get { /* 我手写逻辑 */ }
        set; // 我想让编译器自动实现
    }
}
编译器会崩溃：
  1. 1.1.
    编译器为了自动实现 set，必须生成一个后台字段，比如 <Name>k__BackingField。
  2. 2.2.
    但是，你的手写 get 方法需要返回这个值。
  3. 3.3.
    问题来了：你的手写代码怎么知道编译器生成的那个字段叫什么名字？
    • ••
      你不能在代码里写 return <Name>k__BackingField;（这是非法标识符）。
    • ••
      编译器也不能强行把你手写的 get 方法改成去读那个字段（因为那是你的代码，编译器不能随意篡改）。
结论：只要有一个访问器是你手写的，你就必须亲手掌控那个后台字段。既然你都要掌控字段了，那就没必要用 AIP 了。

3. “不能显式实现一个，让另一个自动实现”

这就是所谓的 “全有或全无”。
❌ 错误示范（书中想表达的）：
csharp
public class Test {
    // 错误：不能混合
    public int MyProp {
        get { return 10; } // 我显式实现了 get
        set;               // 却想让编译器自动实现 set？不行！
    }
}
✅ 正确姿势 1：全部自动（AIP）
csharp
public class Test {
    // 编译器全包了：生成字段 + get + set
    public int MyProp { get; set; }
}
✅ 正确姿势 2：全部显式（传统写法）
csharp
public class Test {
    private int _myProp; // 我自己声明字段
    public int MyProp {
        get { return 10; }         // 我手写 get
        set { _myProp = value; }   // 我手写 set
    }
}

4. 现代 C# 的补丁（了解即可，不影响看书）

现在的 C# 其实放宽了一些限制，但底层逻辑没变：
  1. 1.1.
    只读自动属性：
    csharp
    public int MyProp { get; } // 合法
    原理：编译器生成一个 readonly 的 backing field，只能在构造函数里赋值。
  2. 2.2.
    访问级别不同：
    csharp
    public int MyProp { get; private set; } // 合法
    原理：编译器依然全权负责生成字段和两个方法，只是给 set 方法加了 private 标记。这不属于“混合实现”，因为两个访问器都是编译器自动生成的，只是权限不同。

总结

这段话其实是在揭示 C# 编译器的“懒人逻辑”：
要么我（编译器）从头到尾帮你把属性、字段、方法全生成了（AIP）；要么你就自己从头到尾全写了（显式属性）。我不接受半吊子的合作。
因为一旦你介入了（手写 get 或 set），你就打破了编译器对“支持字段”的封装，它就没法安全地替你生成剩下的部分了。

1. 序列化到底存了什么？

当你把一个对象序列化（比如保存成一个二进制文件或通过网络发送）时，序列化引擎（如 BinaryFormatter）的核心任务是：把对象的状态保存下来，以便将来能还原（反序列化）。
它保存的是什么？是字段（Fields），而不是属性（Properties）。
看这个例子：
csharp
[Serializable]
public class Person {
    private int _age = 30; // 字段
    public int Age { get; set; } // 属性（AIP）
}
当你序列化 Person 对象时，流（Stream）里存的内容大概是这样的逻辑结构：
纯文本
[类型信息: Person]
[字段名: "_age"] [值: 30]
[字段名: "<Age>k__BackingField"] [值: ???] // 假设Age也有值
关键点：序列化引擎会忠实地把字段的名字和字段的值一起写进去。

2. AIP 的字段名是怎么来的？

当你写 public int Age { get; set; } 时，编译器自动生成了一个私有字段。
在 C# 编译器眼里，它生成的字段名大概是这样的（这是简化版，实际更复杂）：
<Age>k__BackingField
重点来了：这个字段名是 C# 编译器自己起的。
  • ••
    今天你用的是 Visual Studio 2022，编译器版本是 v4.8，它生成叫 <Age>k__BackingField。
  • ••
    明天微软发布了新版本，为了修复某个 Bug，编译器小组改了一下命名规则，新版本生成叫 <Age>z__BackingField。
  • ••
    或者你换了一款编译器（比如 Mono 的某个版本），它可能生成叫 $Age$BackingField。
Richter 的警告是：编译器保留随时更改这个名字的权利。

如果你显式声明字段，情况就完全不同：
csharp
[Serializable]
public class Person {
    private int _age; // 字段名是你定的，编译器不敢改
    public int Age {
        get { return _age; }
        set { _age = value; }
    }
}
无论你如何升级编译器，无论你重新编译多少次，_age 这个名字永远不会改变。
反序列化时，引擎一看：“哦，文件里有 _age，我这个类里也有 _age，完美匹配！”于是数据成功恢复。

先想清楚：为什么"纯 get 只读属性"默认反序列化不了？

回顾上一轮说的：现代序列化器（System.Text.Json）走的是调 set 访问器这条路。
csharp
public class Person {
    public string Name { get; set; }  // 序列化器：反序列化时调 set_Name("Jeff")
}
那如果写成这样呢？
csharp
public class Person {
    public string Name { get; }  // 只有 get，没有 set
}
序列化器傻了："我没 set_Name 可调，那 JSON 里的 "Name":"Jeff" 往哪塞？"​ → 默认行为是直接忽略这个属性，反序列化完 Name 还是 null/默认值。
这就是用户常遇到的那个坑：{ get; } 或 { get; init; } 的属性，反序列化后数据"丢"了。

解法一：private set + [JsonInclude]（最常用，.NET 8 前就能用） 

csharp
using System.Text.Json.Serialization;

public class Person {
    [JsonInclude]
    public string Name { get; private set; }  // 属性对外只读，但对 Json 开放
    
    [JsonInclude]
    public int Age { get; private set; }

    // 必须有一个 public 无参ctor（System.Text.Json 默认要走这个）
    public Person() { }
}
原理：
  • ••
    private set 仍然是 set 方法，CLR 层面 set_Name 这个方法存在，只是访问权限是 private
  • ••
    [JsonInclude] 告诉 System.Text.Json："别管访问修饰符，这个属性的访问器（包括 private 的）都纳入序列化契约"
  • ••
    反序列化时，Json 引擎用反射去调 set_Name("Jeff")，private 挡不住反射
💡 这是 C# 9 之前最主流的解法，"对外只读 + 对内（含序列化器）可写"。

解法二：.NET 8+ 真·无 set（连 private set 都没有）→ Populate 模式

这是你问的"黑科技"本体。Richter 那本书写的时候还没这功能，.NET 8 才加的。
csharp
using System.Text.Json;
using System.Text.Json.Serialization;

[JsonObjectCreationHandling(JsonObjectCreationHandling.Populate)]
public class Order {
    public List<string> Tags { get; } = new() { "default" };  // 真·只读，连 private set 都没有
    public string Id { get; } = Guid.NewGuid().ToString();
}
JSON 进来：{ "Tags": ["a","b"], "Id": "xxx" }
反序列化后发生了什么？
  • ••
    Tags → 不替换实例，而是在已有的 List<string> 上 Add("a")、Add("b")，最终 Tags = ["default", "a", "b"]
  • ••
    Id → 字符串是不可变类型，"xxx" 没法"填进"原来的 Id 实例里（string 没有 Add/Modify 这种 mutable 操作），所以 Id 还是原来的 Guid，JSON 里的 "xxx" 直接丢了
原理要讲透，这是关键：
Populate 模式的本质是：不 new 一个新对象替换掉属性引用的实例，而是复用已有实例，去"填"它内部的可变状态。
所以它能工作的前提是：属性类型本身是可变的（mutable）——
  • ••
    ✅ List<T>、Dictionary<TKey,TValue>、自定义 class（有可写字段/属性）→ 能填
  • ••
    ❌ string、int、record struct、以及你自己写的 fully immutable class → 填不动，JSON 值会被静默丢弃
这就是为什么微软文档特意强调："structure 属性仍然需要 setter"
，因为 struct 是值类型，Populate 只能改副本再重新赋值，没 setter 塞不回去。

解法三：record 主构造函数 / [JsonConstructor]（不可变类型的正统姿势）

csharp
// record：System.Text.Json 自动认主构造函数，不需要 [JsonConstructor]
public record Person(string Name, int Age);

var json = """{"Name":"Jeff","Age":30}""";
var p = JsonSerializer.Deserialize<Person>(json);  // ✅ 自动调主构 Person("Jeff", 30)
非 record 的类也能玩：
csharp
public class Person {
    public string Name { get; }
    public int Age { get; }
    
    [JsonConstructor]  // 告诉 Json：反序列化走这个ctor
    public Person(string name, int age) {
        Name = name;
        Age = age;
    }
}
规则：构造函数参数名必须和 JSON 的 key 对上（忽略大小写），或者参数上加 [JsonPropertyName("xxx")] 显式映射

1. 场景设定：为什么编译器要“全有或全无”？

假设 C# 编译器允许你这样做（这正是 Richter 在脑补的一种非法情况）：
csharp
// 假设这是合法的（但实际上 C# 不允许）
public class Person {
    // 我想手写 get，让编译器自动 set
    public string Name {
        get { 
            // 我手写逻辑：比如返回大写
            return _name.ToUpper(); 
        }
        set; // 我想让编译器自动生成 set
    }
}
问题来了：
  • ••
    编译器为了自动生成 set，必须创建一个私有字段来存储值。比如它起名叫：private string <Name>k__BackingField;
  • ••
    你在手写的 get 方法里，写了 return _name.ToUpper();。
编译器立刻懵了：
“等等，你代码里的这个 _name 是什么鬼？我生成的字段名叫 <Name>k__BackingField，不是 _name 啊！难道你要我猜你指的是哪个变量？”
结论 1：只要你在代码里显式写了 get 或 set，你就引入了手写代码。手写代码必须明确地知道字段叫什么名字才能操作它。而 AIP 的字段名是编译器随机生成的（对程序员不可见）。两者无法沟通。

我们再换个角度。如果规则是“可以混合”：
  • ••
    情况 A：你写了 get，编译器自动 set。
    • ••
      编译器生成了字段 <Name>k__BackingField。
    • ••
      你的 get 怎么读这个字段？你写不了代码去读它，因为你不知道它叫 <Name>k__BackingField。
  • ••
    情况 B：你写了 set，编译器自动 get。
    • ••
      编译器生成了字段 <Name>k__BackingField。
    • ••
      你的 set 怎么写这个字段？同样，你不知道名字。
所以 Richter 说“代码只能用属性名访问属性”。意思就是：在你的 C# 源代码里，你根本看不到那个支持字段的名字，你只能通过 Name 这个属性去间接访问。
如果编译器允许你手写其中一个访问器，你就被迫要去操作那个“没有名字”的字段，这是不可能的。因此，编译器干脆一刀切：要么我全包（AIP），要么你全包（显式属性）。

  1. 1.1.

1. 为什么属性可能很慢？（与字段对比）

字段（Field）：
  • ••
    本质：一块内存地址。
  • ••
    访问：int x = obj._count;
  • ••
    过程：CPU 直接去内存地址拿数据。这是纳秒级的操作，几乎不消耗时间。
属性（Property）：
  • ••
    本质：get_X() / set_X() 方法。
  • ••
    访问：int x = obj.Count;
  • ••
    过程：
    1. 1.1.
      调用方法（压栈、跳转）。
    2. 2.2.
      执行方法体内的代码（哪怕只是 return _count;，也得执行）。
    3. 3.3.
      返回结果。
关键差异：
  • ••
    Release 模式：JIT 编译器非常聪明，它会把简单的 get/set 内联（Inline）。也就是说，它会把 get 方法的代码直接复制到调用处，就像没有调用方法一样快。所以平时你感觉不到差别。
  • ••
    Debug 模式/JIT 未优化：没有内联，每次访问属性都是一次实实在在的方法调用，比字段慢。
  • ••
    复杂的 Getter：如果 get 里有一行 Thread.Sleep(5000);，那访问这个属性就要卡 5 秒。

2. 为什么线程同步不要用属性？（死锁风险）

这是 Richter 最担心的一点。
场景：你写了一个属性来加锁。
csharp
private object _lock = new object();
private int _counter;

// 危险的属性设计
public int Counter {
    get {
        lock (_lock) {
            return _counter;
        }
    }
    set {
        lock (_lock) {
            _counter = value;
        }
    }
}
问题在哪？
属性伪装成了字段。调用者会把它当成普通数据访问，而不是一个耗时的操作。
灾难现场：
csharp
lock (someOtherLock) {
    // 调用者以为这只是读个数据，很快
    int temp = obj.Counter; 
    // ... 做一些其他事
}
如果 Counter 的 get 访问器内部也在等待 someOtherLock（哪怕是通过其他调用路径），就会发生死锁（Deadlock）。
Richter 的建议：
如果访问一个数据需要加锁，或者需要线程同步，一定要把它写成方法。
csharp
// 清晰的意图：这是一个操作，可能很慢，可能有锁
public int GetCounter() { ... }
这样调用者看到 GetCounter()，心理预期就是“这是一个方法调用，内部可能有逻辑，我得小心处理锁”。这就是代码可读性和行为规范的问题。

3. 最狠的坑：MarshalByRefObject（远程调用）

这是这段话里最技术化、也是最容易被现代 Web 开发者忽略的一块。这涉及到 .NET Remoting（一种古老的分布式技术，现在基本被 Web API 取代了，但原理很重要）。
什么是 MarshalByRefObject？
通常我们创建对象，对象在内存里。但如果类继承自 MarshalByRefObject，它就可以跨应用程序域（AppDomain）甚至跨进程存在。
  • ••
    本地：你有一个“代理（Proxy）”。
  • ••
    远程：真正的对象在另一个服务器进程里。
属性调用的代价：
当你调用 obj.Counter 时：
  1. 1.1.
    如果是普通对象：调用本地的 get_Counter() 方法。
  2. 2.2.
    如果是 MarshalByRefObject：这会触发一次远程调用（RPC）。
    • ••
      你的进程暂停。
    • ••
      参数打包（序列化）。
    • ••
      通过网络/IPC 发送到远程服务器。
    • ••
      服务器执行 get_Counter()。
    • ••
      结果打包发回来。
    • ••
      你的进程继续。
这有多慢？
  • ••
    字段访问：~1 纳秒。
  • ••
    本地方法调用：~10 纳秒。
  • ••
    远程属性调用：毫秒级甚至秒级（取决于网络）。
Richter 为什么说“永远不要用”？
因为属性看起来太像字段了！如果你在一个循环里访问这个属性：
csharp
for (int i = 0; i < 1000; i++) {
    Console.WriteLine(obj.Counter); // 如果是 MBRO，这里发生了 1000 次远程调用！
}
程序会慢到令人发指。而如果把它写成方法 obj.GetCounter()，程序员看到方法名，就会本能地意识到“这是远程调用，我应该缓存结果”，比如：
csharp
int counter = obj.GetCounter(); // 调用一次
for (int i = 0; i < 1000; i++) {
    Console.WriteLine(counter); // 使用本地缓存
}

我们拆成两个半句讲。

半句 1：「属性方法可能需要额外的内存」

字段访问是直接读那块内存，零额外开销。
属性访问因为是方法调用，有可能在方法内部new 一个对象返回，也可能因为值类型拷贝产生临时空间。
举个最经典的例子：
csharp
public class Person {
    private DateTime _birth;  // DateTime 是 struct（值类型）

    public DateTime Birth {
        get { return _birth; }   // 返回的是 _birth 的一份拷贝
        set { _birth = value; }
    }
}
DateTime 是 struct，struct 传值是拷贝语义。get_Birth() 返回时，CLR 会把 _birth 整个拷一份放到调用者的栈上。
对比字段：
csharp
public class Person {
    public DateTime Birth;  // 字段
}

var p = new Person { Birth = new DateTime(1990, 1, 1) };
p.Birth = p.Birth.AddYears(1);  // ✅ 没问题，字段赋值，改完就存回去了
换成属性就炸了：
csharp
p.Birth.AddYears(1);  
// ❌ 看起来改了，其实改的是 get 返回的那个临时拷贝，p.Birth 还是 1990/1/1
因为 get_Birth() 返回的是拷贝，你调 AddYears(1) 改的是那个拷贝，原始 _birth 纹丝不动。这就是 Richter 说的"对返回对象的修改作用不到原始对象身上"。

半句 2：「返回的引用并非指向对象状态一部分」

这句话绕，但意思很清楚——字段返回的引用（或值）就是对象自己那块内存；属性返回的东西可能是"加工过的 / 新造的"，跟原对象状态没关系了。
三种典型场景：

场景 A：值类型属性（struct）→ 拷贝

上面 DateTime 就是。Birth 返回的是 _birth 的拷贝，不在对象状态里。

场景 B：引用类型属性返回 new 出来的对象 

csharp
public class Order {
    private List<string> _tags = new() { "vip" };

    // 坑：每次 get 都 new 一个返回
    public List<string> Tags {
        get { return new List<string>(_tags); }  // 返回副本
    }
}

var o = new Order();
o.Tags.Add("new");  
// 你以为给订单加了 tag，其实加的是那个 new 出来的副本，_tags 里还是只有 "vip"
字段就没这问题：字段直接返回 _tags 的引用，改的就是原对象。

场景 C：数组 / 集合防御性拷贝（最经典） 

csharp
public class User {
    private string[] _roles = { "User" };

    public string[] Roles {
        get { return (string[])_roles.Clone(); }  // 防御性拷贝，防外部改
    }
}

var u = new User();
u.Roles[0] = "Admin";  // 看起来想篡权，其实改的是 Clone 出来的数组，原 _roles 还是 "User"
设计者故意这么干（安全），但调用方如果不知道，就会一脸懵："我明明改了啊，怎么没生效？"

「文档也经常没有专门说明」为什么是坑

这就是 Richter 吐槽的点——属性披着字段的语法外衣，调用方心理上以为是"直接访问数据"：
csharp

p.Birth = p.Birth.AddYears(1); // 这才是对的写法，但直觉上不容易想到
字段不会有这问题（struct 字段也是拷贝，但你拿到的是变量本身，赋值回去语法上更自然）；属性因为语法 = 字段，调用方会默认"它就是字段"，于是踩坑。
Richter 自己在书里点名过 DateTime——DateTime.Now 是属性（设计错误，因为违反"属性应快速无副作用"），而 Point.X / Point.Y 这种 struct 属性也是高频踩坑点。

  1. 1.1.

1. 为什么方法不能接受匿名类型参数？

你的困惑点：既然匿名类型也是 object，我为什么不能写 void M(object o) 传进去？
答案：你能传进去，但传进去后你什么都做不了。
场景复现：
csharp
// 方法1：创建匿名类型
var person = new { Name = "Jeff", Age = 30 };
Process(person);

// 方法2：接收
void Process(object o) {
    // 完了，我现在拿到了 o，但我怎么访问 Name？
    // o.Name? 不行，编译错，object 没有 Name 属性。
    // 转型？(???)? 不行，我不知道类型名怎么写。
}
根本原因：
匿名类型在编译后，确实有一个名字，比如 <>f__AnonymousType0<string,int>。
但是！​ 这个名字是编译器随机生成的，并且被标记为 internal（仅限当前程序集可见）。你在 C# 代码里根本拼不出这个名字。
所以，虽然 CLR 知道它是什么类型，但你和编译器在写代码时不知道。这就好比你手里拿着一把钥匙（对象实例），但你不知道这把钥匙对应的锁叫什么名字（类型名），所以你打不开它（无法访问其属性）。

2. 为什么不能返回匿名类型？

这和参数是一样的道理。
csharp
// 错误：无法在方法签名中写出返回类型
public ??? GetPerson() {
    return new { Name = "Jeff", Age = 30 };
}
你没法写 ??? 这个地方。你不能写 object，因为返回 object 后，调用者又回到了上一个问题——拿到了却用不了。

3. 为什么不能转型回匿名类型？

这是最让人抓狂的一点。
csharp
var person = new { Name = "Jeff", Age = 30 };
object o = person; // 向上转型（装箱/引用转换）

// 想转回来？
var p2 = (???)o; // 错误：你不知道写什么类型名
虽然 o 内部确实藏着那个匿名类型的实例，但 C# 语法规定，转型操作 (TypeName) 必须写一个明确的类型名。因为匿名类型没有名字，所以你无法完成这个操作。
对比一下：
如果是普通类：
csharp
object o = new Person("Jeff");
var p = (Person)o; // 成功，因为我知道类型名叫 Person。

把匿名类型想象成一次性便签纸：
  1. 1.1.
    内部使用：你在办公室（一个方法）里写了一张便签：{ Name: Jeff, Age: 30 }。你自己看着很方便。
  2. 2.2.
    传递出去：你想把这张纸传给隔壁同事（另一个方法）。
    • ••
      如果你只是把纸揉成一团扔过去（object），同事捡起来一看，不知道这纸是干嘛的，也不敢乱写（无法访问属性）。
    • ••
      如果你想正式交接，需要填写一张标准表格（比如 Person 类）。表格有名字，大家都能看懂。
  3. 3.3.
    无法复刻：这张便签纸没有标准的“表格名”。你想让同事照着画一张一模一样的，他不知道这表格官方叫什么（编译时名称），所以画不出来（无法声明变量类型）。

5. Tuple 为什么能解决这个问题？

Richter 提到 System.Tuple 就是为了应对这个场景。
Tuple 是有名有姓的类型。
csharp
// 返回 Tuple

    return Tuple.Create("Jeff", 30);
}

// 调用

Console.WriteLine(data.Item1); // 我知道属性叫 Item1
虽然 Item1 这个名字很难听，但它是确定的、可写的。编译器认识 Tuple<string, int>，所以你可以在方法间传递它。
现代 C# 的改进：
现在大家都用 ValueTuple（语法糖是圆括号）：
csharp
// 返回 ValueTuple

    return ("Jeff", 30);
}

// 调用
var p = GetPerson();
Console.WriteLine(p.Name); // 语义化命名，完美！
这就是 Richter 当年梦想的“既能匿名传递，又有名字”的理想形态。

6. 匿名类型的正确用法

既然不能泄露出去，那它有什么用？
主要用于 LINQ 查询的内部投影。
csharp

            where p.Age > 25
            select new { p.Name, p.Age }; // 只在 LINQ 语句内部使用

    Console.WriteLine($"{item.Name}: {item.Age}"); // 在循环内部（同一方法上下文）使用

已深度思考(用时12秒)
用户现在在啃CLR via C#第10章索引器（有参属性）这块，这段讲的是C#里索引器和CLR/元数据的关系，核心是「C#的索引器语法糖怎么映射到CLR的底层规则」，还有「为什么C#只能有一个索引器」。首先得把用户最懵的几个概念先拎出来：有参属性、DefaultMemberAttribute、IndexerName、C#的单索引器限制，这几个串起来。
首先，得先对齐基础认知：之前讲的无参属性是getter/setter，有参属性就是带参数的属性，C#里叫「索引器」，比如list[0]这种。首先要区分「C#语法层的索引器」和「CLR层的有参属性」，这是Richter一贯的套路：C#是语法糖，CLR不管你叫啥，只看元数据和方法。
然后，用户不懂的第一个点：「为什么要有默认属性？」「多个有参属性怎么办？」首先得说，CLR本身是支持一个类型有多个有参属性的，比如VB.NET就可以写Default Property和另一个带名字的有参属性。但C#语法不支持啊！C#里索引器只能写this[int i]，没有名字，那别的语言（比如VB）调用的时候怎么知道你这个this[int i]是哪个？所以需要一个「默认有参属性」的标记，这就是DefaultMemberAttribute的作用——相当于给类型贴个标签：「我这个类型默认的、没有名字的那个有参属性，叫XXX」。
接下来是IndexerName的问题。C#里索引器默认生成的方法名叫get_Item/set_Item，对吧？那如果我用[IndexerName("Bit")]修饰索引器，生成的方法名就变成get_Bit/set_Bit了。那DefaultMemberAttribute里存的名字，就会跟着变：没加IndexerName就是Item，加了就是Bit。这个要举例子，比如String的Chars索引器，就是加了[IndexerName("Chars")]，所以元数据里DefaultMember是Chars，方法名是get_Chars，对吧？刚好可以拿用户熟悉的String.Char[int]举例子，一下子就通了。
然后是C#的限制：「多个名称不一样的有参属性无法编译」。为什么？因为C#的索引器语法没有名字啊！你写this[int i]和this[string s]，这两个参数不一样，C#允许重载索引器（按参数区分），但如果你写两个不同名字的？比如你想写一个是this[int i]，另一个是Foo[int i]，C#语法根本不支持给索引器起名字啊！所以C#里所有的索引器都是「默认有参属性」，只能有一个默认，所以不能有多个不同名字的。而VB可以，因为VB的有参属性可以有名字，比如Public Property Item(i As Int) As T和Public Property Foo(i As Int) As T是两个不同的有参属性，然后VB会选一个标DefaultMember，剩下那个不是默认的，调用的时候要写obj.Foo(1)而不是obj(1)。
然后后面的「不支持有参属性的语言怎么调用」：比如C++/CLI，或者有些脚本语言，不知道C#的this语法，那它就直接调用get_Item或者get_Bit这些方法，对吧？因为CLR只认方法，不认属性，所以有参属性本质上就是带参数的get/set方法，不管什么语言，最终都是调这些方法。
还有最后那句「CLR不区分无参和有参属性，都用PropertyInfo」：对的，因为CLR眼里，属性就是元数据里的一个记录，关联两个方法，不管方法带不带参数，都是PropertyDef表里的条目，所以用PropertyInfo都能拿到，比如你反射拿String的Chars属性，拿到的PropertyInfo，然后Invoke它的get方法，传个index参数，就对了。
还要把之前的AIP、匿名类型、属性是方法的逻辑串起来：这里又一次体现「C#语法糖 vs CLR底层」：C#的索引器是语法糖，编译后变成带名字的get_XXX/set_XXX方法，然后用DefaultMemberAttribute告诉其他语言「这个XXX就是默认的索引器」。CLR不管你叫索引器还是属性，只认方法和元数据里的PropertyDef记录。
还要举具体的代码例子，比如：
  1. 1.1.
    普通索引器，看元数据的DefaultMember是Item，方法有get_Item。
  2. 2.2.
    加了[IndexerName("Bit")]的索引器，DefaultMember是Bit，方法get_Bit。
  3. 3.3.
    VB的多有参属性例子，对比C#的限制。
  4. 4.4.
    String.Chars的例子，用户天天用，一下子就懂了。
  5. 5.5.
    反射调用的例子，比如不用[]语法，直接调get_Chars方法，证明CLR只认方法。
还要澄清一个常见的误解：很多人以为索引器是C#特有的，其实不是，是CLR的有参属性，C#只是选了一种语法来表达，而且是「只能表达默认有参属性」的语法。
最后把这段的逻辑串起来，Richter这段其实讲了三层：
  1. 1.1.
    CLR层：支持任意多有参属性，每个都是带参数的getter/setter方法，元数据里每个有参属性一条记录。
  2. 2.2.
    跨语言互通：为了让没名字的C#索引器能被其他语言识别，需要DefaultMemberAttribute标记默认的有参属性名。
  3. 3.3.
    C#语法限制：因为C#的索引器没有名字，只能对应默认有参属性，所以C#不允许定义多个不同名字的有参属性（只能重载参数，不能起不同名字）。
对了，还要提到C#里为什么不能写static索引器？因为CLR支持static有参属性，但C#的语法里this只能指代实例，所以没法给静态索引器语法，这也是C#语法糖的限制，不是CLR的，刚好呼应Richter一贯的「C#语法vsCLR能力」的主题。
还要避免太学术，用大白话，比如把DefaultMemberAttribute比作「门牌号贴纸」：你家（类型）有好几个门（有参属性），但只有一个是正门（默认），你贴个贴纸说「正门叫Item」，快递员（其他语言）就知道走哪个门了。C#的人自己知道正门是this[]，但外人不知道，所以要贴贴纸。
哦对，还有用户之前问过AIP的字段名是编译器生成的，这里索引器的方法名也是编译器生成的，除非你用IndexerName改，和AIP的逻辑一致：编译器生成的东西，你可以通过Attribute干预，但不能直接在代码里写名字。
还有，之前讲属性的时候说CLR不用属性元数据，只用方法，这里又说反射用PropertyInfo，这不矛盾：运行时执行代码不用，反射是元数据查询，所以要用PropertyInfo，和之前的逻辑一致。

C#里的this[int index]索引器，本质是CLR层的「有参属性」，但C#语法不允许给索引器起名字，所以必须给类型贴一个DefaultMemberAttribute的标签，告诉其他语言：「我这唯一没名字的索引器，底层对应的方法名叫XXX」。

第一层：CLR根本不认识「索引器」，只认识「有参属性」

之前讲无参属性的时候说过：CLR眼里没有「属性」这个概念，只有「方法+元数据记录」。有参属性（Parameterized Property）本质也一样：
  • ••
    编译后会生成两个带参数的方法：get_XXX()和set_XXX(T value)
  • ••
    元数据里会有一条PropertyDef记录，把XXX这个属性名和这两个方法关联起来
CLR本身完全支持一个类型有多个有参属性，比如VB.NET就可以这么写：
vbnet
' VB支持多个有参属性，每个都有自己的名字
Public Class MyCollection
    ' 第一个有参属性，叫Item，标为默认
    Default Public Property Item(index As Integer) As String
        Get
            Return ""
        End Get
        Set(value As String)
        End Set
    End Property

    ' 第二个有参属性，叫Foo，不是默认的
    Public Property Foo(key As String) As String
        Get
            Return ""
        End Get
        Set(value As String)
        End Set
    End Property
End Class

  • ••

  • ••

第二层：C#的语法糖限制 → 必须搞「默认属性」

但C#的语法设计是：索引器没有名字，统一用this[]表示。比如你写：
csharp
public class MyCollection {
    public string this[int index] {
        get => "";
        set {}
    }
}
这里根本没有「索引器叫什么」的语法位置。那问题来了：
其他语言（比如VB、C++/CLI）调用这个C#类型的时候，怎么知道this[int]对应的底层方法叫什么？
为了解决这个问题，C#编译器做了一个约定：给类型自动贴DefaultMemberAttribute标签，相当于对外喊一嗓子：「我这唯一的索引器，底层名字叫XXX」。

规则1：没加IndexerName，默认叫Item

上面的C#代码编译后，元数据里会给MyCollection贴这个标签：
csharp
[System.Reflection.DefaultMember("Item")]
public class MyCollection {
    // 编译器自动生成的方法名：get_Item/set_Item
    public string get_Item(int index) => "";
    public void set_Item(int index, string value) {}
}
这就是为什么你反编译C#索引器，永远能看到get_Item/set_Item方法。

规则2：加了IndexerName，就用你指定的名字

如果你不想叫Item，可以用[IndexerName]特性改：
csharp
[IndexerName("Bit")]
public class BitArray {
    public bool this[int index] {
        get => false;
        set {}
    }
}
编译后元数据里的标签会变成：
csharp
[System.Reflection.DefaultMember("Bit")]
public class BitArray {
    // 方法名变成了get_Bit/set_Bit
    public bool get_Bit(int index) => false;
    public void set_Bit(int index, bool value) {}
}

最经典的现网例子：String.Chars

你天天用的string[index]，就是改了索引器名的：
csharp
// String类型的实际定义（简化）
[IndexerName("Chars")]
public sealed class String {
    // 索引器
    public char this[int index] { get; }
}
所以：
  • ••
    元数据里DefaultMember是Chars
  • ••
    底层方法名是get_Chars
  • ••
    你用反射拿索引器的时候，属性名是Chars，不是Item，也不是this

第三层：C#为什么不允许定义多个有参属性？

Richter说「如果代码中含有多个名称不一样的有参属性，C#将无法编译」，原因很简单：
C#的索引器语法没有「给索引器起名字」的位置。
你只能写this[int i]、this[string s]这种按参数重载的索引器，但没法写两个不同名字的索引器——因为C#语法里根本没给「索引器名字」留地方。
比如你想在C#里写两个索引器：
csharp
// ❌ C#编译报错：索引器不能有名字
public string this[int index] { get {} set {} }
public string Foo[int index] { get {} set {} } // 语法就不支持
而VB支持，因为VB的有参属性可以显式写名字（比如上面的Foo属性）。
所以C#的限制本质是：C#语法只能表达「默认有参属性」，无法表达其他有名字的有参属性。

剩下的零散点串讲

1. 「不支持有参属性的语言怎么调用？」

比如有些老旧的语言、或者C++/CLI，不认识C#的obj[1]语法，那它们就直接调用底层方法：
csharp
// 不用[]语法，直接调用get_Item方法，效果完全一样

这也再次验证了：CLR只认方法，不认属性语法。

2. 「CLR不区分无参和有参属性，都用PropertyInfo」

你用反射的时候，不管是Length这种无参属性，还是Chars这种有参属性，拿到的都是PropertyInfo：
csharp
// 拿String的Chars有参属性
PropertyInfo charsProp = typeof(string).GetProperty("Chars");
// 调用get访问器，传index参数
char c = (char)charsProp.GetValue("abc", new object[]{0});
因为CLR眼里，它们都是PropertyDef元数据表里的条目，只是关联的get方法参数个数不同而已。

3. 为什么C#不支持静态索引器？

CLR是支持静态有参属性的，但C#的索引器语法是this[]，this只能指代实例，没法写static this[]，所以C#语法限制了静态索引器——这又是一次「C#语法糖 vs CLR能力」的典型差异。
