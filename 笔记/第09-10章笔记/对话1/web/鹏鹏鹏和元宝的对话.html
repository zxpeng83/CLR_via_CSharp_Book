  1. 1.1.
    编译时（假设默认值为 "Untitled"）：
    • ••
      您编写了一个库，其中包含方法 MakePath(string filename = "Untitled")。
    • ••
      其他程序员（调用方）引用您的库，并写代码调用 MakePath()。
    • ••
      关键点：C#编译器在编译调用方的代码时，发现filename参数缺失，它会直接将默认值"Untitled"作为字面量，嵌入到调用方的程序集（DLL/EXE）中。生成的代码等价于 MakePath("Untitled")。这个“调用地方”就是文档中提到的 call site。
  2. 2.2.
    发布新版本时（您将默认值改为 "Default.txt"）：
    • ••
      您更新了库，将方法改为 MakePath(string filename = "Default.txt")，并发布新版本的DLL。
    • ••
      调用方没有重新编译他们的程序，只是替换了您的新版DLL。
    • ••
      问题发生：当调用方程序运行时，它执行的代码仍然是当初编译时嵌入的 MakePath("Untitled")。它不会自动去读取您新DLL中定义的 "Default.txt"。因此，即使您更改了源码中的默认值，旧版本的调用方代码依然传递着旧的默认值。
这就导致了潜在的危险性：您看似修改了默认行为，但实际上，所有未重新编译的现有客户端程序的行为都没有改变，造成了版本间的行为不一致。

文档建议的解决方案是避免将“有业务意义的默认值”直接写在参数默认值里，而是用一个无意义的“哨兵值”（如 null, 0, Guid.Empty 等）作为参数默认，然后在方法内部实现真正的默认逻辑。

2. 可选/命名参数的调用规则

规则一：命名实参必须放在位置实参之后 

csharp
void Print(string name, int age = 20, string city = "Unknown") { ... }

规则二：必须传递所有必需的参数 

csharp
void Calculate(int required1, int required2, int optional = 0) { ... }

// ✅ 正确：通过位置传递必需参数
Calculate(1, 2);

// ✅ 正确：通过命名传递必需参数
Calculate(required1: 1, required2: 2);

// ❌ 错误：缺少必需参数
Calculate(required2: 2);  // 缺少 required1

规则三：不能用空逗号跳过参数 

csharp
void M(int a = 1, int b = 2, int c = 3) { ... }

// ❌ 错误：试图跳过中间参数
M(1, , 3);  // 编译错误！程序员需要数逗号位置，容易出错

// ✅ 正确：用命名参数跳过中间参数
M(1, c: 3);  // a=1, b=2(默认), c=3

我们注意到用户的问题是关于C#中为什么要求在调用方法时指定out或ref关键字。文档中提到，虽然编译器知道被调用方法需要的是out还是ref，但C#语言设计者要求调用者显式指定，是为了让调用者明确知道传递的变量可能会被修改。
我们来详细解释一下：
在C#中，当你传递参数给方法时，默认是传递值（对于值类型）或传递引用的值（对于引用类型）。但是，使用out和ref时，你传递的是变量的引用（即变量的内存地址），这样方法就可以改变这个变量的值。
为什么要求调用者显式写上out或ref呢？主要有以下几个原因：
  1. 1.1.
    代码清晰性：在调用点，你一眼就能看出这个方法可能会修改你传入的变量。如果你看到方法调用中有一个out或ref，你就会知道这个变量的值可能会被方法改变。这相当于一种警告，让你在阅读代码时更加小心。
  2. 2.2.
    设计意图明确：方法声明时使用out或ref，表示这个方法可能会修改传入的变量（对于ref）或者必须为传入的变量赋值（对于out）。调用者必须显式地表明他们同意这样做，即他们愿意让方法修改他们的变量。这避免了由于疏忽而将变量传递给可能会修改它的方法。
  3. 3.3.
    避免错误：如果没有这个要求，开发者可能会无意中将一个变量传递给一个会修改它的方法，而他们本意可能只是想传递值。这可能导致难以发现的bug。
  4. 4.4.
    与CLR保持一致：在CLR层面，out和ref都是通过传递引用来实现的，但C#通过不同的关键字来区分它们，以便在编译时进行不同的规则检查（例如，out参数必须在方法内赋值，而ref参数必须在传入前赋值）。在调用点，通过要求指定out或ref，使得调用者必须考虑变量的初始化状态。
文档中提到，C#编译器确实知道被调用的方法需要的是out还是ref，所以理论上它可以自动处理。但是，语言设计者认为，调用者应该明确知道他们的变量是否可能被修改，因此要求调用者显式指定。
举个例子：
假设有一个方法：

调用时，你必须写：

Modify(ref a);
这样，任何阅读代码的人都能看到，a可能会被Modify方法修改。
相反，如果你可以这样写：

那么阅读代码的人可能不会意识到a可能会被修改，除非他们去看Modify方法的签名。这增加了代码的理解难度，特别是当方法名没有明确提示它会修改参数时。
因此，虽然编译器可以自动推断，但为了代码的清晰性和安全性，C#要求调用者显式使用ref或out关键字。

1. C++ 的 const 是如何工作的？（以及它如何“撒谎”）

在 C++ 中，你可以：
  1. 1.1.
    将方法声明为 const，承诺该方法不会修改对象的成员。
  2. 2.2.
    将参数声明为 const &，承诺不会通过这个引用修改传入的对象。
C++ 示例：
cpp
class MyObject {
private:
    int value;
public:
    // 一个 const 方法，承诺不修改对象
    int getValue() const {
        return value; // 正确：只是读取
        // value = 10; // 错误：在 const 方法中不能修改成员
    }
    
    void mutate() {
        value = 20; // 正确：非 const 方法可以修改
    }
};

// 一个接收常量引用的函数，承诺不修改传入对象
void printValue(const MyObject& obj) {
    cout << obj.getValue(); // 可以调用 const 方法
    // obj.mutate(); // 错误：不能通过 const 引用调用非 const 方法
}
但是，C++ 的“常量性”是可以被绕过的：
cpp
class Deceptive {
private:
    int secret = 0;
public:
    int getSecret() const {
        // 通过“强制类型转换去掉常量性”来修改！
        const_cast<Deceptive*>(this)->secret = 42; // 🚨 编译通过，运行时会修改！
        return secret;
    }
};
文档所说的“撒谎”：
  • ••
    C++ 的 const 是一个编译时承诺，而非运行时强制保护。
  • ••
    编译器会阻止“常规代码”的修改，但开发者可以通过 const_cast 或获取地址后写入等“非常规”手段，在 const 方法内部或通过 const 引用修改对象。
  • ••
    因此，C++ 让程序员“以为”对象不能被修改，但实际上技术上仍然可以，这降低了其保证的可信度。

2. 为什么 CLR 不提供这个功能？

如果 CLR 要实现真正可靠的常量性，就需要解决以下难题，而文档认为这些代价太高：
a) 性能开销巨大
如果 CLR 要确保一个被声明为常量的对象在运行时不被修改，它必须：
  • ••
    在每一次可能写入内存的操作（如设置字段、调用可能修改对象的方法）前进行检查。
  • ••
    跟踪整个对象图（比如对象内部的嵌套对象）的常量状态。
    这种持续的运行时检查会严重拖慢程序执行速度。
b) 实现极其复杂
  • ••
    如何定义“常量”的边界？一个常量对象的字段如果引用另一个对象，那个对象是否也是常量？
  • ••
    如何处理反射？const 对象通过反射还能修改吗？
  • ••
    如何处理与非托管代码的互操作？非托管代码可不管 CLR 的常量性。
c) 对类型设计的限制过强
如果支持真正的常量性，那么一个“不可变类型”必须满足：
  • ••
    所有字段都必须是只读的。
  • ••
    字段的类型本身也必须是不可变的。
    这在实际编程中限制太大，很多有用的模式无法实现。

3. C# 如何应对？——“不可变性”代替“常量性”

既然 CLR 不提供底层支持，C# 采取了另一条路：通过类型设计和语言特性，在源码层面鼓励和实现“不可变性”，而不是依赖一个可能被绕过的 const 修饰符。
文档中的例子：String 类
String 是“不可变”的经典例子。它没有提供任何可以修改当前实例内容的方法。所有看似修改的方法（如 Replace, ToUpper）都返回一个全新的字符串对象。
csharp
string s1 = "Hello";
string s2 = s1.ToUpper(); // s1 仍然是 "Hello"，s2 是新的 "HELLO" 对象
// s1[0] = 'h'; // 错误：不允许。索引器只有 get 访问器。
这种不可变性是由类的设计者（Microsoft）在编写 String 类时主动保证的，而不是由 CLR 通过 const 关键字强制保证的。
C# 中实现不可变性的现代工具：
  1. 1.1.
    readonly 字段：确保字段只能在构造函数中赋值。
  2. 2.2.
    Init-only 属性（init 访问器）：对象初始化后属性就不能再变。
  3. 3.3.
    记录类型（record）：默认就是不可变的。
  4. 4.4.
    不可变集合（System.Collections.Immutable 命名空间）。
示例：在 C# 中创建一个不可变类型
csharp
public class Person
{
    // 1. 字段设置为 readonly
    public readonly string Name;
    public readonly int Age;
    
    // 2. 通过构造函数提供初始值
    public Person(string name, int age)
    {
        this.Name = name;
        this.Age = age;
    }
    
    // 3. 任何“修改”操作都返回一个新实例
    public Person WithAge(int newAge)
    {
        return new Person(this.Name, newAge);
    }
}

// 使用
var person = new Person("Alice", 30);
var olderPerson = person.WithAge(31); // person 保持不变，得到一个新对象

1. 可选参数与命名参数​
允许为参数设置默认值，调用时可省略或按名称指定。
- 默认值必须是编译时常量。
- 版本控制风险：默认值在调用点编译时被固化，修改默认值后，未重新编译的调用方仍使用旧值。
- 建议用 null/0 作“哨兵值”，在方法内部实现默认逻辑，以保持二进制兼容性。
2. 隐式类型局部变量（var）​
编译器根据初始化表达式推断局部变量类型。
- 只能用于局部变量，不能用于字段、参数或返回类型。
- 常用于匿名类型、复杂泛型实例（如 Dictionary<string, int>），简化代码。
- 区别于 dynamic：var 是编译时静态类型推断，dynamic 是运行时动态类型。
3. 引用传递（ref/out）​
通过引用传递变量，允许方法直接修改调用方的变量。
- ref：调用前必须初始化，方法内部可读可写。
- out：调用前无需初始化，方法内部必须赋值。
- 设计意图：C# 强制在调用点显式写 ref/out，是为了明确表达“该方法可能修改变量”，提高代码可读性和安全性。
- 引用类型使用 ref/out 通常用于“换引用”（让参数指向新对象）。
4. 可变数量参数（params）​
使用 params 关键字定义接受可变数量参数的方法。
- 必须是方法的最后一个参数，且为一维数组。
- 编译器自动将实参包装成数组。
- 性能考虑：频繁调用可能因数组分配影响性能，可为常见参数数量提供重载版本（如 String.Concat 的做法）。
5. 参数与返回类型设计规范​
设计良好的API时应遵循的强弱类型原则。
- 参数类型尽量“弱”：使用接口（如 IEnumerable<T>）或基类（如 Stream），提高方法通用性。
- 返回类型尽量“强”：返回具体类型（如 FileStream），给予调用方更多操作自由，但若考虑未来变更，可返回较弱类型（如 IList<T>）。
6. 常量性​
解释为何 CLR 不提供类似 C++ const 的语言级常量性支持。
- C++ 的 const 仅为编译时承诺，可通过强制转型绕过，非真正不可变。
- 实现真正的运行时常量性验证会带来巨大性能开销和复杂性。
- C# 通过不可变类型设计（如 String、readonly 字段、record 类型）在语言层面鼓励不可变性，而非依赖运行时强制约束。
