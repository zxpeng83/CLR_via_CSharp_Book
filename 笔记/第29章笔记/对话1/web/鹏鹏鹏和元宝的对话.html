🎯 章节总纲：线程同步的本质与代价

线程同步解决的唯一问题是——多个线程同时访问共享数据时防止数据损坏。注意"同时"二字：如果多线程不可能在同一时刻碰到同一份数据，根本不需要同步。
但线程同步本身有三重代价，这是全章的基调：
  1. 1.1.
    繁琐且极易出错：必须找出所有可能被多线程同时访问的数据，并用锁包裹。漏掉一处，数据就坏；而且没有任何办法能证明你加锁加对了，只能靠压力测试去撞。
  2. 2.2.
    损害性能：加锁/放锁涉及额外的方法调用，且 CPU 之间要互相协调谁先拿到锁，这种核间通信本身就拖慢性能。
  3. 3.3.
    一次只允许一个线程访问资源：资源利用率下降。
💡 作者的核心建议：在设计层面尽量避免线程同步。具体做法：避免静态字段这类共享数据；多用值类型（每次都是副本）；多个线程只读访问共享数据完全没问题（比如 String 是不可变的，可被多线程同时读）。

29.1 类库和线程安全

这一节讲 FCL（Framework Class Library）的设计约定，你写类库时也应该参照：
  • ••
    FCL 保证所有静态方法是线程安全的——两个线程同时调同一个静态方法，数据不会坏。
  • ••
    FCL 不保证实例方法是线程安全的——如果对每个实例方法都加锁，性能损失太大。
📌 这条约定是你设计自己类库时的标杆：静态方法默认线程安全，实例方法由调用者决定是否同步。

优先用用户模式，因为它显著快于内核模式。但用户模式有个致命缺点：如果拥有构造的线程一直不释放，等待线程会一直在 CPU 上自旋，这叫"活锁（livelock）"——既浪费 CPU 又浪费内存（线程栈）。
⚠️ 活锁比死锁更糟：死锁只浪费内存，活锁还搭上 CPU 时间。
内核模式构造虽然慢（每次调用都要从托管代码 → 原生用户模式 → 原生内核模式走一圈），但它能在发生竞争时把败者线程阻塞掉，不让它在 CPU 上空转。此外内核构造还支持：跨进程同步、可设安全描述符、可指定超时、可等待一组构造中的任意一个或全部可用。

29.3 用户模式构造

CLR 保证对这些数据类型的读写是原子的：Boolean、Char、(S)Byte、(U)Int16、(U)Int32、(U)IntPtr、Single、引用类型。意思是变量里所有字节一次性读完/写完。
但原子性不保证时序——编译器和 CPU 的优化可能重排指令，导致其他线程看到错误的中间状态。用户模式构造就是用来约束这些原子读写的时序的，并且还能强制 (U)Int64 和 Double 也变成原子+时序受控的访问。
用户模式构造又分两种：易失（Volatile）构造​ 和 互锁（Interlocked）构造。

29.4 易失构造（Volatile Constructs）

要解决什么问题

看这段经典代码：
csharp
class ThreadsSharingData {
    private Int32 m_flag = 0;
    private Int32 m_value = 0;
    public void Thread1() {        // 线程1执行
        m_value = 5;
        m_flag = 1;
    }
    public void Thread2() {        // 线程2执行
        if (m_flag == 1)
            Console.WriteLine(m_value);
    }
}
直觉上 Thread2 打印的一定是 5，但实际可能打印 0。原因有二：
  1. 1.1.
    JIT 可能重排 Thread1 里的两行——先写 m_flag 再写 m_value。
  2. 2.2.
    即使没重排，Thread2 从内存读 m_flag 和 m_value 时，可能先读到旧的 m_value（值为 0），然后 Thread1 才执行并把 m_value 改成 5，但 Thread2 的寄存器里已经是 0 了。
这类问题在 Release 构建下比 Debug 下更容易出现，特别难查。

解决方案：System.Threading.Volatile 类

提供静态方法 Write 和 Read：
  • ••
    Volatile.Write(ref location, value)：强制在调用点把值写入 location，且在程序顺序上，这次写之前的所有加载/存储都必须先发生。
  • ••
    Volatile.Read(ref location)：强制在调用点从 location 读取值，且在程序顺序上，这次读之后的所有加载/存储都必须后发生。
修正上面的代码：
csharp
public void Thread1() {
    m_value = 5;
    Volatile.Write(ref m_flag, 1);   // 保证 m_value=5 先发生
}
public void Thread2() {
    if (Volatile.Read(ref m_flag) == 1)
        Console.WriteLine(m_value);   // 保证读到的是最新 m_value
}
此外还有 Volatile.MemoryBarrier()——不强加内存访问，只强制前后的加载/存储在它之前/之后完成。

C# 的 volatile 关键字

手写 Volatile.Read/Write 太累，C# 提供 volatile 关键字，可作用于 Boolean、(S)Byte、(U)Int16、(U)Int32、(U)IntPtr、Single、Char、引用类型和底层类型为前述整型的枚举。
JIT 编译器保证：对 volatile 字段的所有访问都以 volatile 读/写方式执行；同时告诉编译器和 JIT 不要把字段缓存在 CPU 寄存器中，确保每次读写都真的落到内存。
💡 volatile 关键字 = 自动调用 Volatile.Read/Write，省心但只支持上述类型。

29.5 互锁构造（Interlocked Constructs）

Volatile 的 Read/Write 只做单次原子读或写。而 System.Threading.Interlocked 类的每个方法都做一次原子读+写操作，并且全是完整内存屏障（full memory fence）——即调用前的所有写操作都先于它发生，调用后的所有读操作都后于它发生。
常用方法：Increment、Decrement、Add、Exchange、CompareExchange 等。

核心模式：Interlocked Anything Pattern

Interlocked.CompareExchange 是实现任意复杂原子操作的关键。思路是循环尝试：
csharp
delegate Int32 Morpher(Int32 startValue, TArgument argument, out TResult morphResult);

static TResult Morph(ref Int32 target, TArgument argument, Morpher morpher) {
    TResult morphResult;
    Int32 currentVal = target, startVal, desiredVal;
    do {
        startVal = currentVal;
        desiredVal = morpher(startVal, argument, out morphResult);
        // 如果 target 没被别的线程改过，就换成 desiredVal
        currentVal = Interlocked.CompareExchange(ref target, desiredVal, startVal);
    } while (startVal != currentVal);  // 被改过就重来
    return morphResult;
}
工作原理：
  • ••
    CompareExchange 检查 target 是否还等于 startVal（我们操作时认为的值）。
  • ••
    是 → 换成 desiredVal，返回 startVal，循环退出。
  • ••
    否 → target 已被别的线程改了，返回新值，循环重来。
这套模式让你可以把任意复杂的计算包装成原子操作，是 Interlocked 构造的精髓。

29.6 实现一个简单的自旋锁（Simple Spin Lock）

基于 Interlocked 构造，可以自己撸一个简单的自旋锁：
  • ••
    用 Interlocked.CompareExchange 抢锁，抢到就进入临界区，退出时用 Volatile.Write 释放。
  • ••
    没抢到的线程在原地自旋等待。
这是用户模式锁的最小实现，帮助理解锁的本质——其实就是对一个标志位的原子抢占。但这种纯自旋锁在竞争激烈时很浪费 CPU，所以生产环境要用第30章讲的"混合构造"。

29.7 内核模式构造

Windows 提供的内核模式同步构造，虽然慢，但优势明显：
  • ••
    发生竞争时阻塞败者线程，不在 CPU 上空转
  • ••
    可同步原生线程与托管线程
  • ••
    可同步同一机器上不同进程的线程
  • ••
    可施加安全描述符
  • ••
    可等待一组构造中的任意一个或全部
  • ••
    可指定超时
内核模式构造主要有三类：事件（Event）、信号量（Semaphore）、互斥体（Mutex）。

Event Constructs（事件构造）

分两种：
  • ••
    AutoResetEvent（自动重置事件）：多个线程等待时，调用 Set() 只唤醒一个线程，然后事件自动重置为未触发状态。
  • ••
    ManualResetEvent（手动重置事件）：多个线程等待时，调用 Set() 唤醒所有等待线程，事件保持触发状态直到显式调用 Reset()。
📌 行为差异：AutoResetEvent 像一个"单次通行证"，ManualResetEvent 像一个"开门信号"。

Semaphore Constructs（信号量构造）

信号量是内核维护的一个 Int32 变量：
  • ••
    计数为 0 时，等待的线程阻塞
  • ••
    计数 > 0 时，一个等待线程被唤醒，内核自动把计数减 1
  • ••
    有一个最大计数值，当前计数不允许超过它
Release() 方法让计数加 1；如果连续 Release 太多导致超过最大值，抛 SemaphoreFullException。
💡 AutoResetEvent 其实等价于最大计数为 1 的信号量。区别在于：对 AutoResetEvent 连续多次 Set()，仍然只唤醒一个线程；而对信号量连续多次 Release()，计数会累加，可能唤醒多个线程。

Mutex Constructs（互斥体构造）

Mutex 代表互斥锁，行为类似最大计数为 1 的 AutoResetEvent 或 Semaphore。
但它多了个所有权概念：
  • ••
    内核记录是哪个线程拿到了 Mutex（通过查询调用线程的 Int32 ID）
  • ••
    调用 ReleaseMutex() 时，Mutex 会检查调用线程是否是当初获取的线程
  • ••
    如果不是，Mutex 状态不变，并抛出 System.ApplicationException
这意味着 Mutex 是可重入的——只有拿锁的线程才能放锁，避免了"别的线程误放锁"的问题。代价是它比 Event 和 Semaphore 更复杂。

  3. 3.3.
    对比一下"真正需要同步"的场景（比如多个线程并行循环访问同一个字段），让用户感受到区别。

  1. 1.1.
    数据是共享的（多线程都能碰到）
  2. 2.2.
    这些线程同时在访问这份数据
  3. 3.3.
    其中至少有一个是写操作
只要缺一个，就不需要同步。而异步函数的特殊之处，恰恰让它打破了第 2 条——虽然不同线程参与了同一个函数的执行，但它们访问数据的时间并不重叠。

假设有这样一个异步方法：

async Task ProcessOrderAsync(Order order)
{

    order.Validate();
    var price = order.CalculatePrice();   // 写 order.TotalPrice
    
    await db.SaveAsync(order);            // ← await 点，发生"交接"
    
    // 第二部分：可能在线程 B 上执行
    order.TotalPrice = price;             // 写 order.TotalPrice
    await notification.SendAsync(order);  // 读 order 数据

当我们调用 ProcessOrderAsync(order) 时，实际发生的是：
  • ••
    线程 A​ 执行到 await db.SaveAsync(order) 之前的所有代码：校验订单、计算价格。这部分完全跑在线程 A 上。
  • ••
    遇到 await，线程 A 把执行权交出去，自己去线程池接别的活儿了。此时 order 对象暂时没有被任何线程访问。
  • ••

线程池的基本工作原理

线程池维护着一个工作队列和一组线程：
  • ••
    你把任务丢进队列（Task.Run、ThreadPool.QueueUserWorkItem 等）
  • ••
    线程池里的线程从队列里取任务执行
  • ••
    一个线程同一时刻只执行一个任务，执行完再去取下一个
CLR 的线程池会根据 CPU 核心数、任务数量等动态调节线程数量——任务多、现有线程忙不过来时，就创建新线程；线程长期闲置时，就回收。

关键问题：被阻塞的线程 = 死掉的线程

当一个线程池线程被锁阻塞时（比如 lock(obj) 拿不到锁），它处于 WaitSleepJoin 状态，什么事都干不了——不能处理队列里的下一个任务，就是在那里干等。
线程池不知道这个线程是"真的在干活"还是"被锁卡住了"，它只看到一个事实：这个线程不来处理新任务。

连锁反应：阻塞 → 新线程 → 再阻塞

一、"静态方法线程安全"到底是谁保证的？

是 Microsoft 的 FCL（Framework Class Library）设计团队按约定实现的，不是 CLR 运行时自动强制的。
CLR 本身对静态方法和实例方法的对待方式是完全一样的——它不会因为你写的是 static 方法就自动加锁、自动做原子操作。CLR 只提供 lock、Monitor、Interlocked 等原语让你自己去用
。
"静态方法线程安全"是一条类库设计准则，由微软提出并落实到 FCL 的每一个类中：
Static state must be thread safe. Instance state does not need to be thread safe. By default, class libraries should not be thread safe. Adding locks to create thread-safe code decreases performance, increases lock contention, and creates the possibility for deadlock bugs to occur.
翻译过来就是：静态状态必须线程安全；实例状态不需要线程安全；默认情况下类库不应该线程安全，因为加锁会降低性能、增加锁竞争、引入死锁风险。
所以更准确的说法是：FCL 的设计者承诺并实现了"所有静态方法线程安全"，这是人保证的，不是 CLR 机器保证的。

二、FCL 是怎么实现"静态方法线程安全"的？

这里有个反直觉的关键点——线程安全 ≠ 内部一定加了锁。
Richter 在原书中明确说："使一个方法线程安全，并不是说它一定要在内部获取一个线程同步锁。线程安全的方法意味着在两个线程试图同时访问数据时，数据不会被破坏。"
FCL 实现静态方法线程安全，主要靠三种手段：

手段 1：只用值类型参数，不碰共享状态（最常见、最优雅）

以 System.Math.Max 为例
：
csharp
public static Int32 Max(Int32 val1, Int32 val2)
{
    return (val1 < val2) ? val2 : val1;
}
Int32 是值类型，调用时两个参数会被复制到方法的栈帧里。两个线程同时调 Max，每个线程都有自己独立的 val1、val2 副本，线程之间根本不共享任何数据——自然就不会有数据竞争，不需要任何锁。
这就是为什么 Richter 说"即使它没有获取任何锁"，它依然是线程安全的。

手段 2：内部对静态字段加锁

有些静态方法不得不操作静态字段，这时 FCL 会在内部加锁。典型例子是 Console 类
：
Console 类包含了一个静态字段，类的许多方法都要获取和释放这个字段上的锁，确保一次只有一个线程访问控制台。
伪代码逻辑类似：
csharp
private static readonly object _lock = new object();

public static void WriteLine(string value)
{
    lock (_lock)
    {
        // 操作控制台这个共享资源
    }
}

手段 3：使用 Interlocked 等原子操作

对于简单的自增、赋值等，用 Interlocked.Increment、Interlocked.Exchange 等，一条 CPU 指令搞定，比 lock 轻量得多。微软设计指南里也明确推荐：对于必须是原子的更新，Interlocked 类比 lock 语句更优
。
💡 所以"静态方法线程安全"的实现策略是因方法而异的：能避免共享就不共享，能免锁就免锁，实在避不开才用锁或原子操作。

三、为什么实例方法就不是线程安全的？

这是一个设计权衡问题，不是技术限制问题。原因有三：

原因 1：实例通常由单个线程独占，默认没必要同步

Richter 的解释很直白
：
线程构造对象时，只有这个线程才拥有对象引用，其他线程都不能访问那个对象，所以在调用实例方法时无需线程同步。
典型的用法是：
csharp
var list = new List<int>();  // 线程 A 创建
list.Add(1);                 // 线程 A 使用
list.Add(2);                 // 仍然是线程 A
// list 从未离开线程 A，不存在并发访问
在这种"一个线程从头用到尾"的场景下，实例方法根本没有并发问题，加锁纯粹是浪费。

原因 2：如果每个实例方法都加锁，性能灾难 + 实际上退化为单线程

Richter 算了一笔账
：
假如全部添加锁定，会造成性能的巨 大损失。另外，假如每个实例方法都需要获取和释放一个锁，事实上会造成最终在任何给定的时刻，你的应用程序只有一个线程在运行，这对性能的影响是显而易见的。
如果 List<T>.Add 内部每次都 lock，那么：
  • ••
    性能下降（加锁/放锁有开销，且引发 CPU 核间协调）
  • ••
    更严重的是：整个 AppDomain 里所有线程调用任何 List 实例的 Add 都会串行化——因为锁通常锁在 this 或静态对象上，结果就是"任何给定时刻只有一个线程在运行"
这直接违背了多线程编程的初衷。

原因 3：实例的并发边界应该由调用方决定，而不是类型自己决定

这是最深层的设计哲学。微软指南说
：
默认情况下，类库不应该线程安全。在想要提供线程安全版本的情况时，请提供静态 Synchronized 方法，返回类型的线程安全实例。
什么意思？看 ArrayList 的设计：
csharp
// 普通实例 —— 不保证线程安全，由调用方负责同步
var list = new ArrayList();

// 线程安全包装 —— 调用方显式选择要线程安全的版本
var safeList = ArrayList.Synchronized(new ArrayList());
把选择权交给调用方。如果调用方知道这个实例只在一个线程里用，就用普通版本，零开销；如果调用方要在多线程间共享，就主动用 Synchronized 包装，或者自己加锁。
为什么这么做？因为只有调用方才知道同步的真实边界。比如调用方要做"检查 + 添加"这两个操作的原子组合：
csharp
// 即使 List.Add 内部是线程安全的，这两行组合起来仍然不是原子的
if (!list.Contains(item))   // 线程 A 检查完，还没添加
{                           // 线程 B 也检查，也没包含
    list.Add(item);         // 两个线程都添加 → 重复项！
}
类型内部的锁无法保护调用方的复合操作，所以这个责任必须由调用方承担——既然如此，不如让实例方法本身就不加锁，把同步责任完全交给调用方。

二、用户模式构造：自旋的"轻量级锁"

生活类比

想象公司只有一个会议室（共享资源）。用户模式的做法是：你想用会议室，门上锁了，你就站在门口不停敲门问"好了没？好了没？好了没？"——你占着走廊（CPU）不停重试，别人过不去，你自己也干不了别的。

C# 代码示例 

csharp
private int lockFlag = 0;  // 0 = 无人，1 = 有人

public void UserModeLock()
{
    // 尝试把 lockFlag 从 0 改成 1，如果改成功说明抢到锁
    while (Interlocked.CompareExchange(ref lockFlag, 1, 0) != 0)
    {
        // 没抢到！自旋——空转等待
        // 这里的"空转"就是用户模式的本质
        Thread.SpinWait(1);  // 或者干脆 while 循环什么都不做
    }
    
    // === 临界区：访问共享数据 ===
    sharedData.DoSomething();
    
    // 释放锁
    Volatile.Write(ref lockFlag, 0);
}
关键就在 while 循环里——抢不到锁的线程在这里疯狂重试，这就是"自旋"。它跑在 CPU 上，消耗 CPU 时间片。

用户模式的"活锁"问题

如果持有锁的线程要占用锁很久（比如 10 秒），那其他 10 个等待线程就会在 CPU 上自旋 10 秒——这就是 Richter 说的"活锁（livelock）"：
  • ••
    这 10 个线程不干正事，纯浪费 CPU
  • ••
    持有锁的线程想释放锁，但 CPU 被这 10 个自旋线程霸占，反而更难释放
  • ••
    结果：CPU 100%，但有效工作接近 0

用户模式适合什么场景

锁持有时间非常短（几微秒内）——比如只是做一个 count++ 这样的原子操作。这种场景下：
  • ••
    自旋几次就能拿到锁
  • ••
    自旋的总 CPU 消耗 < 切换到内核模式的开销
  • ••
    所以用户模式更快

三、内核模式构造：阻塞的"重量级锁"

生活类比

还是会议室。内核模式的做法是：门上锁了，你去休息室睡觉（阻塞），前台（操作系统）记下你的名字。等会议室空出来，前台叫你进来。​ 你睡觉时不占走廊（不耗 CPU），但前台叫你、你走到会议室，这个过程有点慢（上下文切换开销）。

C# 代码示例 

csharp
private readonly ManualResetEventSlim gate = new ManualResetEventSlim(false);

public void KernelModeWait()
{
    // 尝试进入临界区，如果资源不可用，线程在此 BLOCK（挂起）
    gate.Wait();  // ← 关键：这里线程被挂起，不占 CPU
    
    // === 临界区 ===
    sharedData.DoSomething();
    
    // 释放资源，唤醒一个等待线程
    gate.Set();
}
当 gate.Wait() 发现资源不可用时，CLR 通过 P/Invoke 调用 Windows 内核的 WaitForSingleObject，操作系统把这个线程从运行态改为等待态，从 CPU 调度队列里移走。这个线程完全不消耗 CPU，直到 gate.Set() 被调用，操作系统才把它重新调度回 CPU。

内核模式的代价

每次调用 gate.Wait() 或 gate.Set()，执行路径是：
纯文本
C# 代码 → CLR 托管层 → 原生用户模式层 → 原生内核模式层（Ring 3 → Ring 0）
要穿越整个操作系统栈，大约 1-2 微秒（相比之下用户模式的 Interlocked 操作只要 10-20 纳秒）。所以单次操作慢约 100 倍。

内核模式的优势

  1. 1.1.
    不浪费 CPU：等待线程被挂起，CPU 可以去干别的
  2. 2.2.
    跨进程：内核对象在整个系统可见，所以可以用来做进程间同步
  3. 3.3.
    支持超时：WaitOne(timeout) 可以指定最多等多久
  4. 4.4.
    支持 WaitAll/WaitAny：可以同时等多个内核对象

用户模式（自旋锁）：

五、为什么会有这两种模式？本质是什么？

根本原因：自旋和阻塞各有适用场景，没有一种"完美方案"。
  • ••
    如果锁总是很快释放（纳秒~微秒级），自旋等几次就拿到，自旋的总开销 < 内核切换的开销​ → 用户模式赢
  • ••
    如果锁可能持有较长时间（毫秒级以上），自旋就是纯浪费 → 内核模式赢

💡 混合构造的思路：先用用户模式自旋一小会儿（比如几十个 CPU 周期），如果还拿不到锁，就"升级"到内核模式阻塞。这样短竞争走快速路径，长竞争走阻塞路径，兼得两者优点。
C# 里的 Monitor（也就是 lock 关键字）、SemaphoreSlim、ReaderWriterLockSlim 等都是混合构造。

一、"同步构造"是什么？

同步构造 = 多线程世界里用来"协调多个线程"的工具。
想象一个场景：有一个卫生间（共享资源），多个人（多个线程）要用。如果没有任何规则，两个人同时进去就乱套了。
"同步构造"就是用来制定规则的工具，比如：
  • ••
    门锁（一次只让一个人进）
  • ••
    排队叫号器（按先后顺序进）
  • ••
    信号灯（红灯停绿灯行）
在 C# 里，lock 关键字、Interlocked 类、AutoResetEvent、Semaphore、Mutex 等等——这些全是"同步构造"。它们的共同使命只有一个：让多个线程安全地访问共享数据，不出错。
所以"同步构造"不是什么高深概念，它就是"多线程协调工具"的统称。

二、"基元"是什么意思？

"基元"= Primitive = 最基础、不可再分的原子级工具。
还是用卫生间比喻。"同步构造"是所有协调工具的统称，而"基元同步构造"是其中最底层、最简单的那一批——就像化学里的"元素"（氢、氧、碳），它们是构成一切复杂物质的基础，自己不能再拆了。
对比一下：
  • ••
    基元同步构造（元素）：Interlocked 类、Volatile、SpinLock、内核的 Event/Semaphore/Mutex
  • ••
    混合同步构造（化合物，由基元组合而成）：Monitor（lock 关键字就是这个）、SemaphoreSlim、ReaderWriterLockSlim
混合构造之所以叫"混合"，是因为它们内部就是用基元构造组装出来的。比如 lock 关键字底层用了 Interlocked 操作 + 内核 Event——先尝试用极快的用户模式自旋抢锁，抢不到再 fallback 到内核模式阻塞。

三、为什么 Richter 要把基元构造分成"用户模式"和"内核模式"？

因为这两种基元的实现层级不同：

用户模式基元：在 CPU 和 CLR 层面实现

这些工具不经过操作系统内核，直接在 CPU 指令层面完成：
  • ••
    Interlocked.Increment → 编译成 CPU 的 LOCK XADD 指令（硬件级原子操作）
  • ••
    Volatile.Read/Write → 编译成带内存屏障的 CPU 指令
  • ••
    SpinLock → 用 Interlocked 抢锁 + 自旋
特点：极快（纳秒级），但不跨进程，抢不到锁时线程原地空转（活锁）。

内核模式基元：在 Windows 操作系统内核层面实现

这些工具调用 Windows 内核的 API（如 WaitForSingleObject、SetEvent），由操作系统管理：
  • ••
    AutoResetEvent、ManualResetEvent
  • ••
    Semaphore
  • ••
    Mutex
特点：较慢（微秒~毫秒级），但可以跨进程、抢不到锁时线程被挂起（不浪费 CPU）、支持超时。

这个过程大约需要 1000-2000 个 CPU 时钟周期。如果 CPU 主频是 3GHz，那就是约 0.3-0.6 微秒。听起来很短，但比起用户模式的一条指令（约 1-2 纳秒），慢了几百倍。

一、为什么需要用户模式构造？从一个 bug 说起

假设我们有一个简单的计数器，多个线程同时自增：
csharp
class Counter
{
    public int count = 0;
    
    public void Increment()
    {
        count++;  // 这行代码看起来是"一步"，其实分三步
    }
}
你以为 count++ 是一行代码就安全了？错。在 CPU 层面，count++ 实际分解为三条指令：
纯文本
1. 从内存读取 count 到寄存器：  mov eax, [count]
2. 寄存器加 1：                 add eax, 1
3. 写回内存：                   mov [count], eax
如果两个线程同时执行，会发生这种情况：
纯文本
线程A: 读 count=0 到寄存器
线程B: 读 count=0 到寄存器
线程A: 寄存器 0+1=1
线程B: 寄存器 0+1=1
线程A: 写回 count=1
线程B: 写回 count=1
结果：count=1（应该是2！）
这就是数据竞争（Race Condition）——多个线程交错执行导致结果错误。
用户模式构造就是用来解决这类问题的工具集。

二、Volatile 构造：解决"看到旧数据"的问题

问题场景：编译器和 CPU 的"聪明"优化 

csharp
class FlagExample
{
    private int flag = 0;
    private int data = 0;
    
    // 线程1执行
    public void Producer()
    {
        data = 42;          // 步骤1：写数据
        flag = 1;           // 步骤2：置标志位
    }
    
    // 线程2执行
    public void Consumer()
    {
        if (flag == 1)              // 步骤3：检查标志
            Console.WriteLine(data); // 步骤4：读数据
    }
}
直觉上：如果 flag==1，那 data 一定是 42。但实际可能打印 0！原因：
  1. 1.1.
    编译器/JIT 可能重排步骤1和步骤2：因为编译器觉得这两行没依赖关系，为了提高性能，可能先执行 flag=1，再执行 data=42。这样线程2看到 flag==1 时，data 还没被赋值，读到的还是 0。
  2. 2.2.
    CPU 缓存问题：现代 CPU 每个核心有自己的缓存。flag 和 data 可能在不同的缓存行里，线程1写完后，线程2的某个核心可能还没看到最新的 data 值。

Volatile 的解决方案

用 Volatile.Write 和 Volatile.Read 明确告诉编译器和 CPU："这里不能重排，必须按顺序来"：
csharp
class FlagExampleFixed
{
    private int flag = 0;
    private int data = 0;
    
    public void Producer()
    {
        data = 42;
        Volatile.Write(ref flag, 1);   // 保证这一行之前的所有写操作都已"提交"
    }
    
    public void Consumer()
    {
        if (Volatile.Read(ref flag) == 1)  // 保证这一行之后的所有读操作都看到最新值
            Console.WriteLine(data);       // 一定能读到 42
    }
}
Volatile.Write 的作用：在写 flag=1 之前，强制把 data=42 的写入操作"刷新"到主内存，让其他 CPU 核心能看到。
Volatile.Read 的作用：在读 flag 之后，强制从主内存重新加载后续要读的数据，确保看到最新值。

volatile 关键字：语法糖版本

C# 还提供了一个更简单的关键字写法：
csharp
class FlagExampleKeyword
{
    private volatile int flag = 0;   // 加 volatile 关键字
    private int data = 0;
    
    public void Producer()
    {
        data = 42;
        flag = 1;   // 自动按 Volatile.Write 处理
    }
    
    public void Consumer()
    {
        if (flag == 1)               // 自动按 Volatile.Read 处理
            Console.WriteLine(data);
    }
}
💡 Volatile 构造的本质：控制内存访问的顺序和可见性，确保一个线程的写入能被其他线程及时、正确地看到。

三、Interlocked 构造：解决"读-改-写"的原子性问题

回到开头的计数器问题

count++ 不是原子的，所以多线程下会出错。怎么修？
错误做法：用 volatile
csharp
private volatile int count = 0;
public void Increment()
{
    count++;  // 还是错的！volatile 不保证 count++ 这三步的原子性
}
volatile 只能保证单次读或单次写的顺序和可见性，不能保证 count++ 这一整组"读-改-写"操作的原子性。
正确做法：用 Interlocked
csharp
private int count = 0;
public void Increment()
{
    Interlocked.Increment(ref count);  // 一条 CPU 原子指令完成 读-改-写
}
Interlocked.Increment 编译成 CPU 的 LOCK XADD 指令——这是硬件级别的原子操作，在指令执行期间，内存总线被锁住，其他 CPU 核心无法同时访问这块内存，从根本上杜绝了数据竞争。

Interlocked 家族常用方法 

csharp
int value = 0;

// 原子自增：value++
Interlocked.Increment(ref value);

// 原子自减：value--
Interlocked.Decrement(ref value);

// 原子加法：value += 10
Interlocked.Add(ref value, 10);

// 原子交换：把 value 改成 99，返回旧值
int oldValue = Interlocked.Exchange(ref value, 99);

// 原子比较并交换（CAS）：如果 value == 0，就改成 1，返回 value 的旧值
int original = Interlocked.CompareExchange(ref value, 1, 0);
// 如果 original == 0，说明修改成功（之前确实是0）
// 如果 original != 0，说明 value 已经被别的线程改了，本次修改未发生

最强大的 CompareExchange：实现任意原子操作

CompareExchange 是用户模式构造里的"瑞士军刀"，可以用它实现任意复杂的原子操作。Richter 在书里介绍了 Interlocked Anything Pattern：
csharp
// 通用模式：对 target 做一个复杂的原子操作
delegate int Morpher(int startValue, out int result);

static int Morph(ref int target, Morpher morpher, out int result)
{
    int currentVal = target;
    int startVal, desiredVal;
    
    do
    {
        startVal = currentVal;
        desiredVal = morpher(startVal, out result);
        
        // 如果 target 在此期间没被改过，就换成 desiredVal
        currentVal = Interlocked.CompareExchange(ref target, desiredVal, startVal);
        
    } while (startVal != currentVal);  // 被改过就重试
    
    return result;
}
这个模式的妙处：即使你的计算逻辑很复杂（比如 target = target * 2 + 1），也能用这个模板包成原子操作。

四、基于 Interlocked 构建自旋锁

有了 Interlocked，我们就可以自己造一把最简单的锁（这就是用户模式构造的实际应用）：
csharp
class SimpleSpinLock
{
    private int lockFlag = 0;  // 0=空闲, 1=被占用
    
    public void Enter()
    {
        // 自旋等待，直到成功把 lockFlag 从 0 改成 1
        while (Interlocked.CompareExchange(ref lockFlag, 1, 0) != 0)
        {
            // 抢不到，空转等
            Thread.SpinWait(1);
        }
        // 抢到了，进入临界区
    }
    
    public void Exit()
    {
        // 释放锁
        Volatile.Write(ref lockFlag, 0);
    }
}

// 使用示例
var spinLock = new SimpleSpinLock();
spinLock.Enter();
try
{
    // 临界区：安全地访问共享数据
    sharedData.Modify();
}
finally
{
    spinLock.Exit();
}
这就是用户模式锁的完整实现——核心就是 Interlocked.CompareExchange + 自旋。没有进内核，纯粹在 CPU 上完成。

五、用户模式构造的"能力边界"

用户模式构造虽快，但有硬伤：

1. 抢不到锁只能自旋（活锁） 

csharp
// 如果持有锁的线程要占用锁 10 秒
// 其他 10 个等待线程就会在 CPU 上自旋 10 秒
// 这就是"活锁"——CPU 100% 但没干正事
while (Interlocked.CompareExchange(ref lockFlag, 1, 0) != 0)
{
    Thread.SpinWait(1);  // 10 秒内这里被循环了几十亿次
}

2. 只适用于极短暂的临界区

因为自旋浪费 CPU，用户模式锁只适合保护"执行时间极短"的临界区（比如只是改一个整数、改一个引用）。如果要保护的代码要执行几毫秒以上，自旋的 CPU 浪费就超过了它的速度优势。

3. 不能跨进程

用户模式构造用的都是进程内的内存变量，无法在不同进程之间协调。

一、CLR 保证的"原子性"到底指什么？

CLR 说这些数据类型的读写是原子的：
Boolean、Char、(S)Byte、(U)Int16、(U)Int32、(U)IntPtr、Single、引用类型
"原子"这个词来自希腊语"atomos"，意思是"不可分割"。在这里的含义是：
对这些类型的单次读或单次写操作，要么完全完成，要么完全没做，不会出现"做了一半被别的线程看到"的情况。

举个"非原子"的反例：Int64

在 32 位系统上，Int64（long）占 8 字节。对它的一次写入其实是两条 32 位指令：
纯文本
写低 32 位  →  mov [address], eax
写高 32 位  →  mov [address+4], edx
如果在两条指令之间，另一个线程来读这个 Int64，它可能读到"新低 32 位 + 高高 32 位"的组合——一个根本不存在的撕裂值。这就是"非原子"的灾难。
但对 Int32（4 字节），单次写入就是一条 32 位指令，要么写入完成，要么没写入，不存在"写了一半"的中间状态。所以 CLR 保证 Int32 的读写是原子的。

一句话理解

CLR 的原子性保证 = 单次读/写操作不会被"撕裂"，其他线程要么看到旧值，要么看到新值，不会看到半成品。

二、但这个"原子性"是非常有限的

很多人误以为"CLR 保证了原子性，那多线程读写就安全了"——大错特错。CLR 的原子性保证只覆盖了非常窄的范围：
操作类型
CLR 是否保证原子性
说明
单次读 x
✅ 是
不会读到撕裂值
单次写 x = 5
✅ 是
不会写出撕裂值
读-改-写​ x++
❌ 否​
这是"读 + 改 + 写"三步，CLR 不保证这三步整体原子
多变量组合​ flag=1; data=42;
❌ 否​
CLR 不保证这两条语句的执行顺序
跨线程可见性​
❌ 否​
线程 A 写了 x=5，线程 B 可能还在自己的 CPU 缓存里看到旧的 x=0
关键点：CLR 的"原子性"只保证单次读或单次写这一个动作不可分割。它不保证：
  1. 1.1.
    复杂操作（如 x++）的原子性
  2. 2.2.
    多个操作之间的顺序（指令重排）
  3. 3.3.
    写入对其他线程的及时可见性（CPU 缓存）

三、用户模式构造就是来补这三个坑的

这正是 29.3 节的核心——用户模式构造就是为了解决 CLR 原子性保证的不足：

坑 1：复杂操作不是原子的 → 用 Interlocked

x++ 不是原子的，但 Interlocked.Increment(ref x) 是原子的。后者在硬件层面用 LOCK XADD 指令，把"读-改-写"三步打包成一条不可分割的 CPU 指令。
csharp
// 不安全的写法（x++ 不是原子操作）
x++;  // 多线程下会丢更新

// 安全的写法（Interlocked 保证整体原子性）
Interlocked.Increment(ref x);  // 硬件级原子

坑 2：指令重排 → 用 Volatile

即使 flag=1 和 data=42 都是原子的单次写，编译器和 CPU 仍可能重排它们的执行顺序，导致其他线程看到不一致的状态。
csharp
// 可能出错的写法
data = 42;      // 原子写
flag = 1;       // 原子写，但可能被重排到上一行之前执行

// 安全的写法
data = 42;
Volatile.Write(ref flag, 1);  // 强制：这一行之前的写入必须先完成
Volatile.Write/Read 插入了内存屏障，禁止编译器和 CPU 跨越屏障重排指令。

坑 3：可见性问题 → 还是用 Volatile

线程 A 写了 x=5，但由于 CPU 缓存，线程 B 可能还在自己的缓存里看到 x=0。Volatile.Read 强制从主内存重新加载，Volatile.Write 强制把写入刷到主内存。
csharp
// 线程A
Volatile.Write(ref x, 5);  // 强制刷到主内存

// 线程B
int val = Volatile.Read(ref x);  // 强制从主内存读，看到 5

三、Semaphore（信号量）：限制同时进入的人数

生活类比

想象一个停车场，只有 3 个车位。来一辆车，如果还有空位就进去；如果满了，后来的车就得在外面排队等。有车开出来腾出车位，外面的车才能进去。

代码示例 

csharp
// 初始有 3 个空位，最多 3 个

void Worker(int id)
{
    Console.WriteLine($"工人{id}：想进停车场...");
    semaphore.WaitOne();  // 还有空位吗？没有就睡觉等
    
    try
    {
        Console.WriteLine($"工人{id}：进来了，干活中...");
        Thread.Sleep(2000);  // 模拟干活
    }
    finally
    {
        Console.WriteLine($"工人{id}：干完了，离开");
        semaphore.Release();  // 腾出一个车位
    }
}
执行流程：
  1. 1.1.
    工人1、2、3 调用 WaitOne() → 车位够 → 直接进（信号量计数：3→2→1→0）
  2. 2.2.
    工人4 调用 WaitOne() → 计数为 0 → 睡觉等
  3. 3.3.
    工人1 干完活，Release() → 计数变回 1 → 操作系统唤醒工人4
  4. 4.4.
    工人4 进去，计数又变 0

Semaphore vs AutoResetEvent

你可能觉得："Semaphore 初始计数设为 1，不就跟 AutoResetEvent 一样了吗？"
几乎一样，但有一个关键区别：
csharp
// AutoResetEvent：连续 Set 两次，仍然只放一个

auto.Set();  // 再放一个？不，多余的 Set 无效（内部计数最大就是1）
auto.WaitOne();  // 一个人进
auto.WaitOne();  // 第二个人？睡觉去

// Semaphore(初始1, 最大3)：连续 Release 两次，计数累加
var sem = new Semaphore(1, 3);
sem.Release();  // 计数变2
sem.Release();  // 计数变3（累加！）
sem.WaitOne();  // 一个人进，计数变2
sem.WaitOne();  // 第二个人直接进，计数变1（不用等 Release）
💡 AutoResetEvent 的"库存"永远是 0 或 1，不会累加；Semaphore 的"库存"可以累加。

四、Mutex（互斥体）：带所有权的锁

生活类比

Mutex 就像一个带名字的钥匙：谁拿到钥匙谁才能开门，而且只有拿到钥匙的人才能把钥匙还回去。别人不能替你还。

代码示例 

csharp

{

    mutex.WaitOne();  // 拿钥匙，拿不到就睡觉等
    
    try
    {
        Console.WriteLine($"线程{threadId}：拿到钥匙，进屋干活");
        Thread.Sleep(1000);  // 模拟干活
    }
    finally
    {
        Console.WriteLine($"线程{threadId}：干完了，还钥匙");
        mutex.ReleaseMutex();  // 只有拿钥匙的人才能还
    }
}

Mutex 的独特之处：所有权

这是 Mutex 和其他内核构造最大的区别：
csharp

// 线程B

csharp

💡 Mutex 是"谁拿谁还"；Event/Semaphore 是"谁都能放"。

一、先把"最大计数为 1 的信号量"长什么样写出来 

csharp
// 初始计数=1，最大计数=3
var sem = new Semaphore(1, 3);
这意味着：一开始就有 1 个"许可"，最多允许累积到 3 个"许可"。

二、关键场景：没有人等待时，连续调用两次

AutoResetEvent 的行为 

csharp
var gate = new AutoResetEvent(false);  // 初始关闭

// 此时没有任何线程在 WaitOne()
gate.Set();    // ① 门开了（变为 signal 状态）
gate.Set();    // ② 门已经是开的，再 Set 没有额外效果

// 现在线程 A 来了
gate.WaitOne();  // 门是开的，A 直接进，进门后门自动关上
// 现在门又关了

// 线程 B 来了
gate.WaitOne();  // 门关着 → B 阻塞！睡觉去
结果：两次 Set()，只让 1 个线程通过了。
为什么？因为 AutoResetEvent 内部只有两种状态：开（signal）或 关（nonsignal）。你调用 Set() 只是把状态翻成"开"，再调用一次 Set()，它已经是开的了，翻不翻都一样。它不会因为被 Set 了两次就变成"超级开"或者"存了两个许可"。

Semaphore 的行为（最大计数=1 的版本）

等等，为了公平对比，我们把 Semaphore 也设成初始计数=1，但最大计数设大一点（比如 3）：
csharp
var sem = new Semaphore(1, 3);  // 初始1个许可，最多3个

// 此时没有任何线程在 WaitOne()
sem.Release();  // ① 计数 +1 → 变成 2
sem.Release();  // ② 计数 +1 → 变成 3（累加！）

// 现在线程 A 来了
sem.WaitOne();  // 拿到1个许可，计数变 2

// 线程 B 来了
sem.WaitOne();  // 拿到1个许可，计数变 1

// 线程 C 来了
sem.WaitOne();  // 拿到1个许可，计数变 0

// 线程 D 来了
sem.WaitOne();  // 没许可了 → D 阻塞！
结果：两次 Release()，让 3 个线程通过了（A、B、C 都拿到了许可）。
因为 Semaphore 内部是一个计数器，Release() 就是往计数器里加数字，加几次就加几。它不像 AutoResetEvent 那样只有"开/关"两种状态，它可以存"多个许可"。

gate.Set();  // 唤醒线程A，然后门自动关上
gate.Set();  // 唤醒线程B，然后门自动关上
这里看起来好像"两次 Set 唤醒了两个线程"，跟 Semaphore 一样？是的，在这个特定场景下效果一样。但区别在于：
  • ••
    如果你在没有线程等待时连续 Set 两次，AutoResetEvent 只存了"开"这一个状态，只能放一个人
  • ••
    Semaphore 在没有线程等待时连续 Release 两次，存了两个许可，能放两个人

五、为什么这个区别很重要？

假设你写一个生产者-消费者系统：
csharp
// 生产者线程
void Produce()
{
    // 生产了数据
    gate.Set();   // 通知消费者
    gate.Set();   // 又生产了一条，再通知
}
  • ••
    如果用 AutoResetEvent：第二次 Set() 是无效的（如果没有消费者在等），第二条数据生产出来却没有通知到消费者 → 数据丢了！
  • ••
    如果用 Semaphore（初始0，最大不限）：第二次 Release() 会让计数变成 2，消费者调用两次 WaitOne() 都能通过 → 每条数据都有对应的通知
⚠️ 这就是为什么生产者-消费者模型通常用 SemaphoreSlim 或 Channel 而不是 AutoResetEvent——因为你需要计数，而不是"开关"。

🎯 一句话总结

三、为什么 await 不阻塞线程？

因为 await 的本质是注册回调，不是让线程傻等。
编译器把你的代码：
csharp
await DownloadFileAsync();
ProcessFile();
改写成类似这样的逻辑（简化版）：
csharp
var awaiter = DownloadFileAsync().GetAwaiter();
awaiter.OnCompleted(() =>
{
    // 下载完成后，线程池派线程来执行这段回调
    ProcessFile();
});
// 当前方法到这里就返回了，线程回到线程池
下载文件是 IO 操作（网卡在干活），不需要 CPU 参与。所以 await 说："我先走了，下载完了你叫我"，然后线程就回线程池了。下载完成后，网卡通过中断通知操作系统，操作系统通知 .NET 的 IO 完成端口（IOCP），IOCP 从线程池捞一个线程来执行回调。

二、WaitAsync 底层到底做了什么？

SemaphoreSlim.WaitAsync() 的内部逻辑大致是：
csharp
public async Task WaitAsync()
{
    // 第一步：尝试快速拿许可（用户模式自旋）
    if (TryTakeImmediate())
        return;  // 拿到了，直接返回，不 await
    
    // 第二步：没拿到，创建一个 TaskCompletionSource
    var tcs = new TaskCompletionSource<bool>();
    
    // 把自己加入等待队列
    _waiters.Enqueue(tcs);
    
    // 第三步：返回一个 Task，调用者 await 这个 Task
    await tcs.Task;
    // 当别的线程 Release() 时，会从队列里取出 tcs 并调用 tcs.SetResult(true)
    // 这里的 await 就会完成，调用者继续执行
}
关键点：
  1. 1.1.
    没有进内核：SemaphoreSlim 是"轻量级"的，它用 .NET 的 TaskCompletionSource + 链表队列实现，完全在托管代码层面完成
  2. 2.2.
    没有阻塞线程：await tcs.Task 是标准的 async 等待——线程立即撤退
  3. 3.3.
    当有许可释放时：Release() 从队列头部取出一个 TaskCompletionSource，调用 SetResult(true)，那个等待的 Task 就完成了，线程池派线程回来接着跑

WaitAsync 还支持 CancellationToken，这是传统内核信号量做不到的优雅写法：
