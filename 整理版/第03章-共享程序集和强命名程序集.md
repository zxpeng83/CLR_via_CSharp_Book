<a id="c03-overview"></a>
## 私有部署之后为什么还要共享

[第2章](第02章-生成、打包、部署和管理应用程序及类型.md#c02-private-deploy)用每应用一个`Cool.dll`副本减少共享覆盖影响。原总览接着问：既然副本隔离方便，为什么还要共享？

在原书Framework环境中，`mscorlib.dll`、`System.dll`等基础程序集会被许多应用使用。如果每个应用都携带同样的Framework基础组件，可能增加磁盘和维护负担；本机受管理的共享部署允许多个应用使用公共组件。共享需要能区分组件的身份和版本，不能重新回到“任何人装一个同文件名DLL就覆盖大家依赖”的做法。

这并不意味着任何第三方库都应该装到共享位置。是否私有或共享取决于部署和维护需要；强名称程序集也可以私有部署，强名称不是“必须进入GAC”的标签。

<a id="c03-strong-name"></a>
## 弱名称与强名称

弱命名（未强命名）程序集没有相应强名称公钥和签名。它仍可以有程序集名称、版本、文化和清单等信息，不是“没有元数据或身份资料”。在本章Framework的通常部署模型中，它不具备进入GAC的条件，通常使用应用私有部署。

强名称包含程序集身份信息，以及公钥和用对应私钥产生的数字签名。简单名称、版本、文化及公钥相关身份信息帮助区分程序集；引用通常用较短的公钥标记（PublicKeyToken）表示相应公钥身份部分。这里的简单名称通常与文件基名相近，却不是“完整路径加.dll后缀”；程序集身份和磁盘文件路径必须分开看。

| 项目 | 用途 | 不能由它推出什么 |
| --- | --- | --- |
| 简单名称 | 标识程序集名称 | 同文件名一定同程序集身份 |
| 版本/文化 | 表达身份和适用的相关资料 | 运行时无条件忽略配置、只加载该数字对应文件 |
| 公钥 | 强名称身份的一部分，供签名相关机制使用 | 公钥天然证明真实公司的可信度 |
| 公钥标记 | 公钥的短表示，便于引用身份资料 | 标记绝对不可能碰撞，或等于完整公钥 |
| 数字签名 | 在适用的验证中检查签名与内容的一致性 | 程序代码已被加密，或签名程序一定安全 |

原回答把强名称比作“数字身份证”。这个类比可用于理解同名称之外还要带身份资料，但不能把“身份证”误解成可信证书颁发机构已经确认了公司的现实身份。强名称的意义主要是程序集身份；Microsoft明确提醒[不能依赖强名称建立安全信任](https://learn.microsoft.com/en-us/dotnet/standard/assembly/create-use-strong-named)。

<a id="c03-dataaccess"></a>
## DataAccess.dll：同文件名不等于同身份

原例中的公司A和公司B都发布`DataAccess.dll`。仅看文件名，调用方无法理解“我要的是哪一家、哪一个版本”。把两个弱命名DLL都放入GAC并不成立，因为未强命名程序集本来就不能这样安装；原答这段假设应当用于说明文件名冲突问题，而不是一个可执行的GAC部署步骤。

在符合条件的Framework强名称场景中，公司A的1.0版`DataAccess`和公司B的2.0版`DataAccess`可具有不同的程序集身份。应用通过名称、版本、文化和公钥相关信息描述所引用的组件，再由绑定规则选择实际程序集，因而不必仅靠“DataAccess.dll”这一个字符串辨认。

```text
同样的文件名线索：DataAccess.dll

身份A：DataAccess + 版本1.0 + 相应文化 + 公司A所用公钥身份
身份B：DataAccess + 版本2.0 + 相应文化 + 公司B所用公钥身份

应用引用的是相应身份；实际加载还受绑定/配置规则影响。
```

原答把两家公司的公钥标记写成“绝对不同”和“全球唯一”，过于确定。不同私钥/公钥通常提供不同的身份资料，但厂商也可能使用相同密钥，短标记也不是数学上的无碰撞承诺。正确教学点是：**强名称增加了身份区分信息，而非对任意两个文件作绝对唯一性的证明**。

<a id="c03-gac"></a>
## GAC是本机目录，还是互联网公共目录

GAC是Global Assembly Cache，全局程序集缓存。在本书Framework语境中，它是**本机的受管理共享位置**。这里的global是“机器范围内共享”，不是“地球上所有电脑共同访问一个互联网文件夹”。

本机范围也不是应用的安全沙箱或代码信任边界。GAC本身是本机缓存，程序集的来源、部署或绑定却可能涉及网络；“缓存位于本机”不能推出应用没有网络传输，也不能替代发布者及代码信任判断。

原答给出的路径线索包括旧环境常见的`C:\Windows\assembly`，以及Framework4相关的`%SystemRoot%\Microsoft.NET\Assembly`。`%SystemRoot%`代表Windows安装位置，通常为`C:\Windows`。具体目录和内部组织是实现细节，不应把某个路径当成跨运行时、跨平台不变的规范。

| 原问题中的判断点 | 正确理解 |
| --- | --- |
| “部署到自己电脑的公共目录” | 是本机受管理的共享位置 |
| “所有电脑都访问的公共目录” | GAC本身不提供这样的公网服务 |
| “全局共享” | 本机Framework应用可按规则引用公共组件，不代表每个应用自动加载每个GAC程序集 |
| “谁可以安装” | 安装到GAC通常需要管理员等相应权限；这是本机系统级部署 |
| “任何DLL都能放进去吗” | GAC只接纳满足要求的强名称程序集；文件复制不等同受支持的安装 |

原笔记提到`GACUtil.exe`和管理员权限，是为了进一步确认操作发生在本机。GACUtil是相关开发工具；部署时还应区分受支持的安装器及其管理职责，不能把手工复制文件当作完整GAC安装。[Framework GAC说明](https://learn.microsoft.com/en-us/dotnet/framework/app-domains/gac)给出了它的机器共享范围和强名称要求。

<a id="c03-gac-analogies"></a>
### 公共图书馆、小区健身房与公司通讯录

原正式答把GAC比作本机“公共图书馆”。应用无需每家都藏一份相同共享组件，可以按相应身份资料找到所需版本。强名称与签名在这里好比书的标识和可验证印记，帮助区分与检查内容；它们不自动证明作者可信或书里每句话都正确。

前三章总览还用了“市政公共图书馆、ISBN及出版社防伪印章”的完整类比：私人家中的书对应私有部署，受管理公共馆藏对应共享位置，目录中的身份资料帮助选书。该类比中的“市民”表示本机应用；“出版社印章”只表示签名/完整性机制，不能替代可信发布者认证。

思考区另给了两个不同的本地范围类比。小区公共健身房是本小区的共享设施，并非全市任何人都直接共用；公司全局通讯录的“全局”是公司范围，不是全世界。它们都帮助区分**一个环境内部的共享**与**互联网公开服务**，不应因为与图书馆表达相似就删掉这些不同场景。

<a id="c03-signing"></a>
## 签名、完整性与可信度的边界

强名称签名使用私钥生成，公钥供相应验证。签名不是把整个程序集内容秘密加密起来；IL和元数据仍可被工具查看。知道一个公钥也不等于知道其持有者是现实中的哪家可信公司。

原总览说安装到GAC时检查签名，文件被修改会影响签名的有效性。这个机制可解释完整性检查的用途。但它接着把结论扩大为“CLR在所有情形都拒绝任何篡改程序集，因此能保证安全”，需要修正：验证是否进行及其作用范围必须按运行时和加载环境判断。

在Framework3.5 SP1以后的相应全信任条件下，存在强名称验签旁路，例如从ApplicationBase下加载到全信任AppDomain、满足相关条件且非延迟签名的程序集；不能写成每次加载都做同一套强名称验证。GAC安装阶段的验证也不能简单等同所有运行阶段的行为。[微软强名称说明](https://learn.microsoft.com/en-us/dotnet/standard/assembly/create-use-strong-named)明确说明了这个例外。

因此应区分三个问题：程序集声称什么身份、相应内容与签名是否匹配、是否信任这个发布者及其代码。强名称帮助前两个问题的相关机制，不能单独解决第三个，也不是应用程序的安全隔离边界。

<a id="c03-binding"></a>
## 引用、版本策略和指定位置

原六章总览提到“引用强命名程序集”“运行时解析类型引用”和“高级管理控制配置”。其联系是：引用记录描述需要的身份，绑定和配置决定实际去找哪些候选文件，加载后再按类型/成员资料解析使用。

Framework通常按其规则考虑引用身份及适用的应用、发布者和机器配置，检查已加载程序集，按条件查询GAC，再使用指定位置或探测规则。强名称和弱名称不能套用同一套无条件版本检查，配置也可能改变原始版本选择。原答“每个应用各取所需版本”是这套机制的设计目的，不是随便放两份文件就一定能正确加载的保证。[Framework程序集查找流程](https://learn.microsoft.com/en-us/dotnet/framework/deployment/how-the-runtime-locates-assemblies)说明了相关条件。

### `codeBase`网络地址为什么不等于互联网GAC

用户在追问GAC的公共目录性质时，原答补充了`codeBase`。在相关Framework场景中，配置可以指定程序集的位置，包括适用的网络URL，再按加载和安全规则获取、缓存或使用组件。指定或下载一个网络文件，与本机GAC的机器级公共缓存是两种机制。

思考区把网络部署比作“快递送货上门”：东西通过网络送到使用环境，不能据此说小区内部的公共健身房已经变成全球健身房。相应地，组件有网络来源，不表示所有机器同时在远程“公共GAC”里执行它。具体能否加载还取决于Framework版本、配置、位置和安全规则；本章没有实际执行任何URL程序集加载。

<a id="c03-delay-sign"></a>
## 延迟签名与私有/共享选择

原总览列了“延迟签名技术”。它在强名称流程中表示先放入公钥身份资料并为签名留出相应位置，后来取得对应私钥条件后完成正式签名。它帮助组织开发、测试和最终签名流程，不能把“预留签名位置”当作已经通过完整签名验证的证据。相关操作需要结合Framework工具和验证设置判断。[延迟签名说明](https://learn.microsoft.com/en-us/dotnet/standard/assembly/delay-sign)区分了开发阶段与最终签名。

引用和友元声明对公钥资料的要求也不完全一样。例如第6章的`InternalsVisibleTo`强名称场景要求完整`PublicKey`，不能拿短`PublicKeyToken`代替；这个具体`Wintellect`场景见[第6章](README.md#chapter-06)。这也帮助避免把“身份里的公钥”“短标记”“签名数据”当成同一个值。

私有部署与强名称是两个维度：私有副本解决某些文件覆盖边界，强名称解决相关程序集身份表达，GAC是Framework的一种共享部署设施。不要用“程序集有强名称”代替实际部署、版本或信任方案。

<a id="c03-corrections"></a>
## 现代差异与重要纠错

GAC和这里的Framework绑定配置属于原书的历史运行环境。现代.NET没有照搬这套GAC部署模型；它也支持读取强名称程序集的身份资料，但不能据此假设完全采用旧Framework的签名强制验证和绑定策略。

| 编号 | 原误解、过度概括或容易产生的误读 | 原因与正确结论 | 一手依据 |
| --- | --- | --- | --- |
| C03-F03 | GAC是互联网所有电脑访问的公共目录 | GAC是本机Framework的受管理共享位置；网络下载是另一机制 | [Framework GAC](https://learn.microsoft.com/en-us/dotnet/framework/app-domains/gac) |
| C03-F02 | 只要同名DLL，CLR就只能看文件名 | 程序集引用和绑定还使用相应身份资料；路径与身份不同 | [强名称身份](https://learn.microsoft.com/en-us/dotnet/standard/assembly/strong-named) |
| C03-F02 | 任意两个公司的公钥标记都绝对不同 | 不同身份资料能帮助区分，短标记不是绝对无碰撞证明，也可能共享密钥 | [身份中的公钥与标记](https://learn.microsoft.com/en-us/dotnet/standard/assembly/create-use-strong-named)，短表示不构成数学无碰撞保证 |
| C03-F04 | 未强命名DLL可以都装GAC，才产生重名覆盖 | 它们本来不满足GAC安装要求；该假设只能用于说明文件名不足 | [GAC安装要求](https://learn.microsoft.com/en-us/dotnet/framework/app-domains/gac) |
| C03-F01 | 原问答把弱命名程序集概括为“只有名称和版本” | 未强命名缺少相应强名称身份/签名，但不等于没有其他程序集结构与身份信息 | [程序集清单](https://learn.microsoft.com/en-us/dotnet/standard/assembly/manifest) |
| C03-F05 | 强名称意味着来自可信公司、代码安全 | 身份、签名完整性、发布者信任是不同判断 | [强名称信任范围](https://learn.microsoft.com/en-us/dotnet/standard/assembly/create-use-strong-named) |
| C03-F06 | 把“公私钥加密技术”误读成加密整个程序集 | 强名称签名不使IL/元数据成为秘密密文 | [强名称生成内容](https://learn.microsoft.com/en-us/dotnet/standard/assembly/strong-named) |
| C03-F05 | 每次CLR加载都验签，修改后一定不能加载 | Framework存在指定全信任条件的验签旁路；不能跨场景泛化 | [Framework3.5SP1旁路条件](https://learn.microsoft.com/en-us/dotnet/standard/assembly/create-use-strong-named) |
| C03-F07 | 强名称程序集必须共享部署 | 它也可以私有部署；身份与部署位置是两个维度 | [GAC共享选择](https://learn.microsoft.com/en-us/dotnet/framework/app-domains/gac) |
| C03-F08 | 版本记录就保证总按原数字加载 | 实际选择还要考虑Framework绑定和配置策略 | [Framework绑定流程](https://learn.microsoft.com/en-us/dotnet/framework/deployment/how-the-runtime-locates-assemblies) |

“公共图书馆”“健身房”“通讯录”“快递”分别强调身份查找、本地共享范围和网络送达过程。把类比对应的机制分清楚，就能避免将本机缓存、网络服务、程序集身份和代码信任混在一起。
