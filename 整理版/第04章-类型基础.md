## 本章的主线

类型基础连接了三个层次：源码中如何表达和使用一个类型，编译器怎样把这种使用解析为具体类型及成员，运行时怎样根据编译后的表示创建对象和执行逻辑。原前六章导读还提到了类型转换、运行时类型、对象、线程栈与托管堆的关系；这些概念在具体问题中分别发挥作用，不能只由一句“所有东西都是Object”替代。

`System.Object`是普通托管类层次的根，未指定其他基类的普通C#类会隐式从它派生；这不等于接口、指针等所有类型都把Object作为元数据基类。结构/枚举的特殊基类和装箱关系在第5章解释。类型关系、变量的静态类型、对象的运行时类型及其实际存储是不同概念。

例如，克隆返回的是对新对象的引用，强制转换把该引用表达为已知的`Person`类型；这个新对象和其引用字段所指的`Address`又是不同对象。对值/引用语义、存储及隐式基类的后续追问见[第5章](README.md#chapter-05)，本章先把身份、名字、引用和对象内容分开。

<a id="c04-memberwiseclone"></a>
## MemberwiseClone复制了什么

<a id="c04-shallow-clone"></a>
### 返回的新对象有源对象的字段值吗

有。`System.Object.MemberwiseClone`创建一个**与源对象具有相同运行时类型**的新对象，并复制原对象的实例字段，是**浅拷贝**。它不复制静态字段，也不会自动为每个引用字段指向的对象创建一个新的对象。

| 实例字段 | 复制的内容 | 新旧对象之间的关系 |
| --- | --- | --- |
| `int Age`等值字段 | 字段中的值 | 两个`Person`分别有自己的字段状态 |
| `Address`等引用字段 | 对同一对象的引用 | 初始时两者仍指向同一个`Address` |
| 包含引用字段的结构 | 结构值及其中的引用 | 结构值被复制，引用指向的对象不因此深复制 |

源答中的`Person`例有`Age=30`和`Address.City="Beijing"`。克隆后`cloned.Age`仍是30，`cloned.Address`与原对象的`Address`引用同一个地址对象；把克隆中的城市改成`"Shanghai"`，原对象看到的城市也改变。这不是两个Person变成同一个对象，而是它们共享一个子对象。

<a id="c04-clone-program"></a>
### 原示例的protected调用怎样修正

`MemberwiseClone`是`protected`，原答在任意外部代码中写`original.MemberwiseClone()`不能直接编译。可在`Person`内包装为一个公开操作，然后从外部调用。

完整程序E04-01，保留原输入及共享地址场景，并用独立修改Age说明字段副本：

```csharp
using System;

class Address
{
    public string City;
}

class Person
{
    public int Age;
    public Address Address;

    public Person Clone()
    {
        return (Person)MemberwiseClone();
    }
}

class Program
{
    static void Main()
    {
        Person original = new Person
        {
            Age = 30,
            Address = new Address { City = "Beijing" }
        };
        Person cloned = original.Clone();

        cloned.Age = 31;
        cloned.Address.City = "Shanghai";

        Console.WriteLine(original.Age + "/" + cloned.Age);
        Console.WriteLine(original.Address.City);
        Console.WriteLine(Object.ReferenceEquals(original.Address, cloned.Address));
    }
}
```

实际输出：

```text
30/31
Shanghai
True
```

浅拷贝复制的是实例字段的值；一个引用本身也是字段值，但其指向的对象不会自动复制。若业务需要独立的`Address`，必须按对象结构定义相应深拷贝逻辑，不能把浅拷贝后的“所有字段值相同”读成“所有子对象也都是新对象”。[MemberwiseClone API](https://learn.microsoft.com/en-us/dotnet/api/system.object.memberwiseclone?view=netstandard-1.6)明确规定了浅拷贝行为与可访问性。

## 程序集引用与依赖链

<a id="c04-reference-inputs"></a>
### “引用的程序集”是什么

编译当前项目时，需要告诉编译器哪些外部程序集可作为类型/成员的参考。原书通过`/reference`说明这种输入；Visual Studio项目引用、项目文件及构建工具也会形成相应输入。原问题中“当前程序集引用的程序集”首先可以理解为当前代码所依赖、编译时引用的其他程序集，不能仅凭这句话强推为“编译器必然自动沿所有间接引用递归搜索”。

原答用`MyApp`说明依赖层次：

```text
MyApp
 ├─ 直接使用 Newtonsoft.Json.dll（JsonConvert）
 └─ 直接使用 MyCompany.Utilities.dll
                         └─ 该工具库自身使用 System.Data.dll
                                      （例如方法返回DataSet）
```

`Newtonsoft.Json.dll`和`MyCompany.Utilities.dll`是这个例子的直接依赖，`System.Data.dll`是工具库自身的依赖。若MyApp使用的API暴露`DataSet`等外部类型，编译器还需要取得它的相应定义，才能进行类型检查。

这里要区分**依赖关系存在**和**编译器输入已经具备**。直接调用`csc`时，它不会因为B的元数据里提到C，就无条件把所有C文件自动加入参考集合；缺少所需的参考程序集可能报CS0012等错误，需补充引用。SDK/NuGet/项目构建可以解析传递依赖并给编译器提供相应参考，这属于构建输入管理，不是`using`或`csc`无限递归找DLL的规则。[引用缺失诊断](https://learn.microsoft.com/en-us/dotnet/csharp/misc/cs0400)说明了这类错误。

原思考区还用了另一套包依赖场景：项目A使用NuGet包B，包B又依赖包C。这时B是项目的直接包依赖，C是传递包依赖；还原和构建可以把相应参考交给编译器。它解释包关系，不能证明csc看到一个名字就自动扫描并加入任意包C。这个包场景与下面显式命令行输入的小型程序集实验分别保留。

作者的小型验证使用相同层次的A/B/C：B的公开方法返回C，调用方只给`/reference:B.dll`时编译失败CS0012，给B和C后运行得到C中的值7。它验证“缺少参考不能靠间接引用自动补齐”，不声称已下载或运行例中的真实Newtonsoft包。

<a id="c04-compile-reference-result"></a>
### 编译器何时记录解析结果

编译器依据当前源声明、作用域和已提供参考的元数据进行绑定，再把相应类型/成员引用编码到输出模块中。不是先读取一个尚未生成的`MyApp.exe`清单，才知道应该怎么编译它。

编译成功也不保证部署机器一定具有相容的实现和完整文件；运行时仍可能发生绑定或解析失败。记录引用资料提供了继续解析的依据，不是对任意目标环境的一次永久验证。

例如，使用`JsonConvert.SerializeObject(...)`需要能找到相应类型及方法。找到后，生成的元数据和IL记录相应引用，供运行时进一步解析；`MyCompany.Utilities`返回`DataSet`的情形还需要检查这个返回类型的参考。定义信息、引用信息和具体操作分层，见[第1章](第01章-CLR的执行模型.md#c01-metadata-il)。

原书Framework默认参考核心库`mscorlib.dll`，其中有`Object`、`Int32`、`String`等类型；编译器选项可以改变默认参考，不能把“通常自动具备”写成不可关闭的永久特例。现代SDK还广泛使用参考程序集，并不等于C#编译器总是直接把运行时`System.Private.CoreLib.dll`作为用户编译输入。[参考程序集说明](https://learn.microsoft.com/en-us/dotnet/standard/assembly/reference-assemblies)区分了编译API描述与运行实现。

<a id="c04-using"></a>
## using和程序集引用是两个维度

<a id="c04-using-lookup"></a>
### 是先找引用，再到using里面找吗

程序集引用回答“哪些外部类型定义可用于本次编译”，`using`及当前作用域等规则参与回答“源码中的简短名字表示什么”。`using System.IO;`不是加载一个名叫System.IO的DLL，也不是向运行时注册一条搜索路径。

类型片段E04-02，两个简短名字分别对应两个命名空间中的类型：

```csharp
using System.IO;
using System.Text;

class Names
{
    FileStream stream;       // System.IO.FileStream
    StringBuilder builder;  // System.Text.StringBuilder
}
```

可用的参考仍需要存在。反过来，即使没有这两个`using`，也可以在适当参考下写出完整限定名字。`using`提供便利，不是引用外部程序集的唯一必要方式。

原答把它称作“类型名称拼图”：编译器有两份线索清单，参考告诉它哪些定义可参与本次编译，using等名称规则帮助解释候选名字。这是“去哪里找”与“可能叫什么”两份线索配合，不是两条按书写次序竞速的搜索路线。

原答用两个图书馆解释这件事：参考程序集像你可以查询的A馆、B馆；`using`像《基础教程》可能所属的系列名称，帮助把短名字解释成更完整的名称。它说明两个维度配合使用，不是说编译器一定按“先全库逐个找短名字，再按using书写顺序加前缀”的固定算法运行。

原答还写了`FileStream fs = new FileStream();`。这个类型没有这样适用的公有无参构造器，不能作为可运行示例照抄；上面的类型片段只演示名字解析。如果真要创建FileStream，还应按需要选择有适当路径、模式等参数的构造器。

<a id="c04-using-ambiguity"></a>
### using的先后顺序会选择哪个同名类型吗

不会用“先写的using赢”来消除这种歧义。C#按作用域和名字解析规则处理名称；多个导入命名空间提供相同类型名字时，简短引用可能不明确。可以写完整限定名或使用别名，不能依赖调整两行using顺序来任选一个类型。

反例E04-03，完整类型片段，故意保留歧义，不能编译：

```csharp
using N1;
using N2;

namespace N1 { public class Widget { } }
namespace N2 { public class Widget { } }

class Test
{
    Widget item; // CS0104：无法从这两个同名导入类型中唯一确定
}
```

把两个using的顺序调换，仍报CS0104。这里两个`Widget`来自不同命名空间；下一节`ABC.BuyProduct`来自两个程序集且完全限定名相同，是另一种冲突，不能混成同一个错误码。[C#命名空间规范](https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/language-specification/namespaces)规定了导入歧义及别名作用。

<a id="c04-runtime-identity"></a>
## CLR“不知道命名空间”该怎样理解

<a id="c04-namespace-not-assembly"></a>
### 编译器使用名字，运行时使用已编码的引用

原书的提示强调：运行时不会重新执行源码里的`using`，替你猜`FileStream`的简短名字是哪个类型。编译器已经按作用域、名字规则和参考集合解析了这次使用，输出中的类型/成员引用告诉运行时需要解析哪个实体。

但“CLR对命名空间一无所知”不能解释为“元数据完全没有namespace信息”或“运行时只有一串不可分的完整名字”。CLI的`TypeDef`和`TypeRef`等实际保留类型名称及namespace等相应资料；引用还关联其解析范围。命名空间是名字组织维度，不是一个自动对应程序集的运行时容器。[CLI元数据规范](https://www.ecma-international.org/wp-content/uploads/ECMA-335_6th_edition_june_2012.pdf)与反射可直接核对这些信息。

以`System.IO.FileStream`为例，源码using帮助使用短名字，编译输出编码相应类型引用。运行时按引用及加载规则寻找实现，不按源文件中using的书写顺序查库。原答把它直接固定为“CLR加载System.IO.dll再找FileStream”不够准确：Framework及现代.NET的定义程序集、参考程序集和类型转发关系不同，不能把命名空间名字直接变成实现DLL的名字。

现代差异：编译用的参考程序集描述API，实际实现可能在其他程序集，经相应类型转发和运行时机制解析。`mscorlib`的历史说明不能简单把名字替换成`System.Private.CoreLib`后宣称其他规则全相同。

<a id="c04-identity-analogies"></a>
### 寄信、图书管理员和仓库管理员

原正式答用了寄信的完整例子：写信时知道张三在北京市海淀区XYZ公司技术部，把足够完整的地址写在信封上；邮递员按信封资料送达，不重新猜测你脑中“张三”“技术部”这两个简称。这里using帮助源码解释名字，编译输出提供运行时可使用的引用资料。它说明职责分工，不表示一个类型身份只是一条地址字符串。

思考区另用了图书管理员和仓库管理员：图书管理员依据允许查询的目录和名称线索找到具体书；仓库管理员据明确编号及位置取物，而不重新沿用你最初的书名猜测。它与寄信的场景不同，仍保留其“编译时绑定与运行时解析分工”的用途。实际引用不只是缓存一个路径，运行时仍有加载、绑定和解析工作。

<a id="c04-extern-alias"></a>
## extern alias：两家ABC公司的BuyProduct

<a id="c04-same-type-name"></a>
### 命名空间相同还不够区分程序集

原书的两家公司是Australian Boomerang Company（澳大利亚回旋镖公司）与Alaskan Boat Corporation（阿拉斯加船业公司）。它们都使用命名空间`ABC`，并各定义`BuyProduct`。

```text
AustralianBoomerangCompany.dll ── ABC.BuyProduct（回旋镖）
AlaskanBoatCorporation.dll     ── ABC.BuyProduct（船）
```

若两DLL都进入通常的global引用范围，只写`ABC.BuyProduct`仍无法唯一选择。同完整类型名来自两个程序集时，通常报CS0433；换`using ABC;`不能解决，因为冲突根本不只在命名空间前缀。

`extern alias`为程序集引用引入额外的根级别别名，让源码能通过别名限定所需的类型。它与普通using类型别名有联系，但首先必须有相应的程序集参考别名定义。

<a id="c04-alias-setup"></a>
### 先给参考别名，再在源码声明

原答给出了Visual Studio操作和命令行操作两条路径。

1. 在解决方案资源管理器选择`AustralianBoomerangCompany.dll`的引用，打开属性。
2. 找到Aliases（别名）。通常的默认值`global`让该参考参与全局范围。
3. 将其设为`CompanyA`；对`AlaskanBoatCorporation.dll`设为`CompanyB`。
4. 在使用这些别名的源码文件或适当命名空间范围声明`extern alias CompanyA;`及`extern alias CompanyB;`。

命令行编译参数示意：

```text
/reference:CompanyA=AustralianBoomerangCompany.dll
/reference:CompanyB=AlaskanBoatCorporation.dll
```

别名是参考及源码名字解析资料，不是自动给DLL改文件名，也不是把整个程序集复制为另一个程序集。IDE具体入口依版本和项目形式可能不同，命令行参考别名的核心意义不变。

<a id="c04-alias-code"></a>
### 原源码示例中的using别名不能放在Main里

原答在Main方法体内写`using CompanyAProduct = ...;`，这是非法位置。using别名指令需要在相应文件或命名空间位置，不是方法体中的资源释放using语句。

多文件示例E04-04：先分别把下面两个类型片段编为对应DLL。为便于观察，它们的Order方法分别返回一个说明来源的字符串；两个类的完全限定名仍相同。

`AustralianBoomerangCompany.dll`类型片段：

```csharp
namespace ABC
{
    public class BuyProduct
    {
        public string Order() { return "boomerang"; }
    }
}
```

`AlaskanBoatCorporation.dll`类型片段：

```csharp
namespace ABC
{
    public class BuyProduct
    {
        public string Order() { return "boat"; }
    }
}
```

调用方完整程序，使用前面的参考别名参数编译：

```csharp
extern alias CompanyA;
extern alias CompanyB;

using System;
using CompanyAProduct = CompanyA::ABC.BuyProduct;
using CompanyBProduct = CompanyB::ABC.BuyProduct;

class Program
{
    static void Main()
    {
        CompanyA::ABC.BuyProduct boomerang = new CompanyA::ABC.BuyProduct();
        CompanyB::ABC.BuyProduct boat = new CompanyB::ABC.BuyProduct();
        Console.WriteLine(boomerang.Order());
        Console.WriteLine(boat.Order());

        CompanyAProduct anotherBoomerang = new CompanyAProduct();
        CompanyBProduct anotherBoat = new CompanyBProduct();
        Console.WriteLine(anotherBoomerang.Order());
        Console.WriteLine(anotherBoat.Order());
    }
}
```

期望且实测的输出：

```text
boomerang
boat
boomerang
boat
```

第一种写法通过`CompanyA::ABC.BuyProduct`与`CompanyB::ABC.BuyProduct`直接指定根别名；第二种先用文件级using别名简化同一类型的引用。两种语法用途都保留，不能只留下一个“加别名”结论。

`extern alias`声明也可以出现在规范允许的命名空间范围，不能把“通常放文件顶部”改成唯一合法位置。别名需要外部参考定义，否则声明并不会凭空加载一个程序集。[extern alias参考](https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/keywords/extern-alias)说明了参考与声明的配合。

<a id="c04-alias-version"></a>
## 两个版本与运行时边界

原答还给了不同版本的场景：库X需要`CommonLib.dll`1.0，库Y需要2.0。编译时可以为相应参考指定`V1`和`V2`，然后用`V1::CommonLib.SomeType`及`V2::CommonLib.SomeType`表达要使用哪个参考中的类型。

这有编译前提：两份参考必须能够按程序集身份区分并被编译器接受。在原书Framework场景中，强名称等相关身份机制可参与区分版本；两个同简单名称的未强命名库，即使用不同alias，也可能在导入参考阶段报CS1704，不能由“类型名字已经写V1/V2”就断定编译成功。alias解决名字指认，不解决同程序集身份导入冲突。[程序集参考诊断](https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/compiler-messages/assembly-references)说明了CS1703/CS1704等条件。

这些名称让编译器可以区分源码符号，不自动保证运行时一定能在同一加载环境里同时使用两个实现。Framework的强名称身份和绑定、现代.NET加载上下文及依赖策略，还会决定实际可加载范围。现代默认加载上下文通常只能按同一简单程序集名称缓存一个版本；需要不同版本时要考虑相应加载上下文设计，而不是只改两行extern alias。[AssemblyLoadContext说明](https://learn.microsoft.com/en-us/dotnet/core/dependency-loading/understanding-assemblyloadcontext)明确区分版本解析和加载范围。

原最后的“仓库标签”类比可以保留：多个仓库里都可能有同名物品，给参考贴上标签，源码用“标签::类型全名”指明来自哪个仓库。标签解决源码指认，不负责运输、版本兼容或运行时隔离。GAC/强名称的历史背景见[第3章](第03章-共享程序集和强命名程序集.md#c03-binding)，加载范围的后续主题见[第22章](README.md#chapter-22)。
