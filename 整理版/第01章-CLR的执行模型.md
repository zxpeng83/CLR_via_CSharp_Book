<a id="c01-overview"></a>
## 本章的主线

第一章回答“程序如何跑起来”，第二章回答“怎样生成、打包和部署”，第三章回答“怎样识别和共享程序集”。它们联系紧密，但概念不在同一层：C#是语言，IL是编译结果的一种指令形式，程序集是交付和引用的逻辑单元，CLR是执行和管理程序的运行时。

原问答中的工厂类比可以按生产流程理解：`.cs`源代码是设计方案，编译器生成产品的操作说明与结构资料，清单把要交付的文件组成一个完整包裹，运行时再按目标机器的条件执行。

```mermaid
flowchart LR
    A[源代码：C#、VB等] --> B[面向CLI的编译器]
    B --> C[托管模块：头信息、元数据、IL]
    C --> D[程序集：清单组织模块与资源]
    D --> E[加载运行时和依赖]
    E --> F[JIT把所需IL编成本机代码]
    F --> G[CPU执行；运行时提供GC等服务]
```

这是本书采用的普通Framework执行模型。C#编译器通常一步就生成带清单的单文件程序集，并不要求开发者总是另跑一次“打包”。NGen、现代预编译或Unity IL2CPP会改变其中生成本机代码的环节，后文分别说明。

<a id="c01-clr-csharp"></a>
## CLR和C#：执行者与表达工具

CLR是Common Language Runtime，公共语言运行时。它负责加载程序集、了解和检查类型、执行托管代码，并提供垃圾回收、异常处理、线程和同步支持等服务。原书还讨论Framework时代的安全检查；这不意味着只要交给CLR，任意程序就自动成为可信程序。

C#是程序员表达逻辑的高级语言。面向CLI的C#编译器把源码转换为IL和元数据；运行时利用这些产物执行程序。VB.NET、F#等语言也能产生兼容的中间表示，因此运行时并不要求知道程序员最初使用哪一种语言。语言编译器仍需保证它生成的类型和成员满足相应的类型系统规则。

原回答给了两个互补的类比。把CLR称作“发动机和大管家”，强调它一面让程序执行，一面管理内存和其他运行服务。把C#源码称作“设计图”、CLR称作“施工队和质检环节”，强调写下逻辑与执行、检查逻辑的职责不同；设计图仍须符合施工系统支持的规则。这两个类比都不能理解成“CLR逐行阅读C#文本”。CLR处理的是编译后的表示。

若进一步问“CLR和.NET是什么关系”，思考区的“发动机与整辆车”比喻很有用：CLR是执行引擎，.NET平台还包括类库、工具及应用开发体系，不能把整个平台等同于一个执行引擎。[CLR概述](https://learn.microsoft.com/dotnet/standard/clr)说明了运行时提供的基本服务。

<a id="c01-managed-module"></a>
## 托管模块、程序集与文件后缀

<a id="c01-module-parts"></a>
### 托管模块的四个组成部分

本书语境中的托管模块是面向CLR的编译器生成的标准化文件，其重要组成部分如下。

| 部分 | 保存什么 | 帮助解决什么问题 |
| --- | --- | --- |
| PE32或PE32+头 | 可执行文件格式、平台等信息 | 操作系统怎样识别和处理这个文件 |
| CLR头 | 托管运行所需信息，如相关版本和入口信息 | 怎样进入托管执行过程 |
| 元数据 | 类型、成员、签名、关系及引用等结构信息 | 模块定义了什么、需要什么 |
| IL | 方法等的中间指令及方法体相关结构 | 具体逻辑怎样执行 |

PE格式和CLR头主要对应本书的Windows/Framework背景。IL通常与具体CPU指令集无关，但一个程序集可能依赖特定平台的原生库，包含混合代码，或带有目标平台限制，不能由“有IL”推出“在任意机器都能运行”。

<a id="c01-assembly-module"></a>
### `.dll`或`.exe`就是托管模块吗

在常见的单文件C#程序集里，同一个`.dll`或`.exe`既是托管模块，又是带程序集清单的程序集主文件。模块是物理组成部分，程序集是由清单组织起来的逻辑部署、引用和版本单元。“程序集清单”是元数据的一部分，记录程序集标识、组成文件、资源和程序集引用等信息。

多文件程序集可以用`MyApp.exe`保存清单，并把`Logic.netmodule`、`Graphic.netmodule`和图片资源组成同一个逻辑程序集。后两个模块不含程序集清单，不能各自当独立程序集使用。程序集也可引用另一个程序集，和“这个程序集内部包含多个模块”是两种关系。

原回答用“砖块与房子”区分模块和程序集：模块是组成材料，清单说明怎样组织交付，程序集是完整交付单元。另一组“混凝土和钢筋、建筑图纸、毛坯房或精装房”的比喻强调组件内容、组织说明与最终文件的关系；图纸在这里只是帮助理解清单，不表示IL和元数据是无法运行的原材料。

后缀只能提供线索，不能证明文件的内容：原生C/C++也会生成`.dll`和`.exe`；C#还可生成`.netmodule`。现代.NET应用的`.exe`还可能只是本机启动宿主，真正的托管程序集在旁边的`.dll`。判断一个文件是否托管，应检查其实际结构。部署和多文件组织见[第2章](README.md#chapter-02)。

原总览还使用了完整的出版类比：开发者用中文写小说，编译器把它转换成通用的“世界语”（IL），同时附上目录和人物介绍（元数据）；清单好比本书身份和组成说明，读者使用能理解这些表示的阅读器（运行时），把需要执行的内容转成目标机器的指令。它说明编译后的统一表示和运行时的角色；“ISBN”只是身份类比，不能据此认定普通程序集天然具有全球唯一身份或经过可信出版者认证。

<a id="c01-metadata-il"></a>
## 元数据和IL究竟分别保存什么

<a id="c01-metadata-definitions-references"></a>
### “定义和引用”与“实际指令”

元数据是一组结构化的表和相关数据。定义信息告诉工具和运行时“这里有一个什么类型或成员”；引用信息告诉它们“这里使用了哪个程序集、类型或成员”。例如，`Employee`的`public string Name`属性和`public void CalculateSalary()`方法需要结构记录；调用`System.Console.WriteLine`则涉及对外部类型和方法的引用。

原回答还把元数据比作“程序集的数据库”或“蓝图”：数据库式的表记录结构，蓝图式的说明标出组成与关系；它们都不等于每个运行中对象当前字段值的快照。IL则承载具体操作步骤。这组结构数据库/蓝图类比与下面书目录/正文的类比各有侧重，前者着重结构记录，后者着重信息种类的区分。

常见表包括`TypeDef`、`MethodDef`、`Field`、`Property`、`AssemblyRef`、`TypeRef`和`MemberRef`。原笔记用“FieldDef”“PropertyDef”泛称定义信息；CLI标准表的准确名称是`Field`和`Property`。属性本身有属性元数据，它的访问器则是方法；自动属性还可能有编译器生成的存储字段，不能把这几部分混为一项。

| 对比项 | 元数据 | IL及方法体 |
| --- | --- | --- |
| 主要问题 | 是什么、叫什么、和谁有关 | 做什么、按什么步骤做 |
| 典型内容 | 类型与成员名称、签名、标志、继承及引用 | 加载、算术、跳转、调用等指令 |
| 使用者 | 编译器、加载器、反射和开发工具等 | JIT或其他执行/编译实现 |
| 原类比 | 一本书的目录、索引和术语表 | 对应章节的正文 |

元数据使程序集自描述，编译器和工具无需再依赖C/C++式头文件了解托管类型的公开形状；它也供CLR进行类型解析、检查及反射。自描述和依赖记录有助于部署，但它们不会自动保证任意依赖版本都兼容，也不会自动部署所有原生依赖。

书中用`ILDasm.exe`观察这些结构。例如，可以看到定义`Program`类型的`TypeDef`记录，以及引用`System.Console`类型的`TypeRef`记录。工具显示的类型/成员结构与指令分别回答前面两类问题，不能把其中的类型名称直接当成方法体代码。

<a id="c01-method-name-body"></a>
### 方法名在元数据，方法体逻辑在IL，这样理解对吗

对于通常由C#编写并具有实现的方法，这个概括是对的，但元数据远不止一个名字。`MethodDef`及签名记录能够表示方法名称、可访问性、是否静态或虚方法、参数和返回类型，以及关联方法体的位置等。普通IL方法的RVA指向模块内的方法体，不能把RVA当作跨进程通用的运行时函数指针。

类型片段E01-01，方法名和参数/返回类型是结构信息；相加并返回是实现逻辑：

```csharp
public class Calculator
{
    public static int Add(int a, int b)
    {
        return a + b;
    }
}
```

对应方法体IL示意，省略方法声明及其他容器：

```il
ldarg.0     // 静态方法的第一个实参a
ldarg.1     // 第二个实参b
add
ret
```

IL使用求值栈表达运算：上例加载两个实参，把它们作为操作数放到求值栈，`add`取出两个数并留下相加结果，`ret`返回结果。这个抽象求值栈不等于承诺运行机器必须为每条IL都在物理线程栈上存取数据，JIT可以使用寄存器等实现。

原回答还给了不同的算术表达式`int a = b + 5`。方法片段E01-03保留常数`5`这个操作数：

```csharp
public static int AddFive(int b)
{
    int a = b + 5;
    return a;
}
```

在此方法的优化IL中，可以用`ldarg.0`、`ldc.i4.5`、`add`、`ret`表达相同结果；编译器不必为仅用于返回的局部变量`a`保留单独存储步骤。两例分别是“两个实参相加”与“实参加固定常数”，不能因为都使用`add`就删除其中一个。

加载实参、相加、返回是指令；方法叫什么、接收两个`int`并返回`int`则由元数据描述。原思考区还提醒，实际方法体不只有这些指令：含异常处理的方法还会有相关异常处理区域和方法体信息，局部变量类型也会通过相应签名关联。不能把“方法体”机械缩成源码的一段文本或只列算术指令。

原答把方法的元数据比作“身份证和简历”，把IL比作“工作手册”：前者说明身份、权限、形状和位置，后者说明执行步骤。这与前一张表中的书目录/正文比喻用途不同，两组都可以帮助建立分层认识。

第6章“为各种成员生成元数据和IL”的表达是整体编译职责的概括，不能推成**每种成员都有一个独立IL方法体**。字段和常量需要结构记录，不各自有方法体；属性和事件通过访问器方法实现相关行为；抽象方法没有该类型中的实现体，`extern`方法的实现在别处。详见[第6章](README.md#chapter-06)。

<a id="c01-field-initializer"></a>
### `int a = 1`中的`1`是在元数据里吗

用户讨论的是普通类的实例字段初始化，不是`const`声明。

类型片段E01-02：

```csharp
public class Example
{
    public int a = 1;
}
```

这里至少要分三层。字段名称、类型和访问标志等进入字段元数据；给字段写入`1`的初始化行为由编译器生成进实例构造器的IL；创建对象后，实际值保存在该对象的字段状态中。构造器IL可以包含加载常数和存储字段的指令，不需要把这个普通字段当前的值作为元数据中的“对象状态”保存。

静态字段初始化通常由类型初始化逻辑处理；常量则有编译期取值和使用点替换等不同规则。所以正确结论是“**这条普通实例字段初始化不是靠元数据保存每个对象的当前值**”，而不是“元数据绝对不能保存任何常数”。常量和字段的差别见[第7章](README.md#chapter-07)，构造器顺序见[第8章](第08章-方法.md#c08-initialization-order)。

<a id="c01-compilation"></a>
## 本机编译、JIT与NGen

<a id="c01-native-compiler"></a>
### 本机代码编译器是什么

在原书与面向CLR编译器的对比中，“本机代码编译器”指生成特定CPU架构机器码的编译器，例如通常的原生C/C++编译工具链。它的输出直接面向目标操作系统及指令集，不要求像普通C# IL程序集那样先交给CLR的JIT。

| 编译方式 | 典型输出 | 后续执行条件 |
| --- | --- | --- |
| 原生C/C++编译 | 特定目标的机器码 | 目标操作系统、CPU及所依赖的原生运行库 |
| 普通面向CLI的C#/VB编译 | IL和元数据 | 兼容的运行时及依赖，通常还要生成本机代码 |

Microsoft C++编译器的特殊之处是能支持两种路线：通常生成原生代码，使用`/clr`等选项可以产生托管代码，也能在相应模式下把托管与非托管部分放入一个混合模块。它不是“C++语言只能选择其中一种”的结论。

“本机代码”说明代码已面向目标CPU，“非托管”说明其执行和管理模型，不能把两个词无条件当作同义词。CLR的JIT本身也生成本机代码，而这些代码继续接受运行时的GC等服务；AOT同样可能保留托管服务。原生程序也会依靠自己的运行库，并不表示全部内存和同步功能只能手工逐字节实现。

<a id="c01-jit-ngen"></a>
### 先生成IL，再JIT，为什么不是直接执行IL

普通Framework模型中，C#编译器负责把语言表达转换为中间表示；JIT在运行时把需要执行的方法编译为目标CPU指令。原书用“第一次调用编译，后续调用使用已生成代码”说明这一过程，目的在于区分源码编译和运行时编译，避免把每次调用都想成重新翻译源码。

在本书描述的Windows启动路径中，普通Framework托管可执行文件通过CLR相关启动入口及`MSCorEE.dll`等启动桥接组件接入运行时，再按托管入口信息进入程序；CLR也可以由其他应用宿主加载。`MSCorEE.dll`这一名称属于该Windows/Framework背景，不能写成所有现代.NET、Mono及所有操作系统统一使用的加载入口。

运行时在生成和执行代码时利用类型信息与检查机制，并维护GC所需信息。JIT优化会考虑目标机器和运行条件，但“支持检查”不等于任意IL、原生互操作或unsafe代码都由同一种验证自动证明安全。

本书还介绍Framework的`NGen.exe`：它提前为程序集生成特定CPU的本机映像，运行时在条件合适时可使用本机映像缓存，减少启动时的编译工作，并可能改善工作集或共享。映像与程序集、依赖及运行环境有关，更新后可能失效；不适用时仍可能回到JIT。它不是“提前编译就永远更快”，也不是把Framework依赖全部删除。[NGen官方说明](https://learn.microsoft.com/en-us/dotnet/framework/tools/ngen-exe-native-image-generator)明确限定该工具面向.NET Framework。

现代差异：现代.NET可能采用分层编译、预生成代码、动态重新优化或AOT，不能把历史流程图中的“一次JIT”当作所有现代方法一生只编译一次的保证。Unity IL2CPP也属于预先生成本机程序的路线，但它不是NGen的另一名称。

<a id="c01-platform"></a>
## 32位、64位、x86、x64和AnyCPU

<a id="c01-bit-architecture"></a>
### 原问题的对应关系写反了

在常见Windows/.NET平台目标语境里，`x86`表示32位目标，`x64`表示64位的x86扩展目标，后者也称x86-64或AMD64。不是“32位=x64、64位=x86”。更广义的x86名称有历史沿革，最初的8086是16位架构；32位和64位也不只有x86家族，例如ARM64同样是64位目标。

位数与寄存器、指针及地址空间模型有关，不能仅说成“能装多少物理内存”。32位线性地址的理论数量是2³²，按字节寻址即4GiB；这不等于每个32位进程都能使用全部4GiB，更不等于任意32位系统最多只能管理4GiB物理RAM。64位地址模型的理论范围也不表示CPU或操作系统真的实现并开放了全部2⁶⁴字节。

原对照表纠正后保留四组术语：

| 术语 | 本质 | 通俗理解 | 原书编译场景 |
| --- | --- | --- | --- |
| x86 | 此处为32位x86目标 | 旧式目标模式 | `/platform:x86`，通常是PE32且要求32位执行 |
| x64 | x86指令集的64位扩展目标 | 同一家族的增强模式 | `/platform:x64`，PE32+和64位目标 |
| 32位 | 指针/地址模型等使用32位表示 | 较窄的地址通道 | 32位进程的地址空间；可用范围受系统安排限制 |
| 64位 | 相应的64位执行和地址模型 | 较宽的地址通道 | 64位进程；实际地址范围由平台实现决定 |

原回答把CPU处理中心比作道路：x86目标的车在32位道路运行，x64目标的车需要64位道路。64位Windows提供WoW64兼容支持时，可以给32位程序保留一条适合它的旧道路；这不是把它自动变成64位程序。x64程序则不能直接在32位Windows运行。车道类比只表达执行模型和兼容条件，不表示“车道数翻倍，所有程序速度也翻倍”。

<a id="c01-anycpu"></a>
### PE32、AnyCPU和实际进程位数

`/platform:x86`通常生成要求32位执行的PE32映像；`/platform:x64`生成x64的PE32+映像。普通AnyCPU托管程序集也可用PE32封装，因此**看见PE32不能直接断定最终进程一定32位**。

在没有32位优先等额外条件的普通Framework AnyCPU可执行程序模型里，32位Windows按32位执行，64位Windows通常按64位执行。这是原书说明AnyCPU时的主要思路。实际判断还要区分以下情况。

| 情况 | 决定位数时要看什么 |
| --- | --- |
| x86可执行程序 | 要求32位进程；64位Windows需兼容支持 |
| x64可执行程序 | 要求对应的64位环境 |
| Framework AnyCPU可执行程序 | 系统和运行条件；还要检查32位优先标志 |
| `anycpu32bitpreferred`可执行程序 | 在支持的Framework环境中优先作为32位进程；不是普通AnyCPU的无条件64位规则 |
| 加载到现有进程的AnyCPU库 | 不能自行把宿主进程改成另一位数；要与宿主及依赖兼容 |
| 现代.NET应用 | 还要看实际选用的dotnet/apphost、运行时及发布目标 |

Visual Studio项目中的“首选32位”会改变相关平台设置，不能仅根据编辑器里看到“AnyCPU”四个字作判断。[Visual Studio平台目标说明](https://learn.microsoft.com/en-us/visualstudio/ide/how-to-configure-projects-to-target-platforms?view=visualstudio)给出了配置入口。排查问题时应确认运行中进程位数以及原生依赖的架构，而非只检查源码语言。

<a id="c01-fcl-cts-cls"></a>
## FCL、CTS与CLS

这三个概念解释为什么不同语言能在同一套平台上协作。

| 名称 | 作用 | 与前面概念的联系 |
| --- | --- | --- |
| FCL，Framework Class Library | 提供大量现成类型和功能 | 文件、文本、网络、界面等程序可重用其类型；命名空间帮助组织API |
| CTS，Common Type System | 定义类型、成员及其行为的通用规则 | 编译器按共同模型生成元数据，运行时据此理解类型 |
| CLS，Common Language Specification | 约束需要跨语言使用的公开特性 | 不同语言支持的功能并不完全相同，公开API可选择共同可用的部分 |

原书列举了Web服务、Web窗体、桌面和控制台等Framework应用场景，`System`、`System.IO`等命名空间帮助查找相应类型。命名空间不是程序集文件夹，也不意味着一个命名空间只能来自一个程序集。

CTS中的类采用单基类继承，但可实现多个接口。普通托管类的根是`System.Object`，结构和枚举也有相应类型关系；不能把“所有类型都派生Object”扩张到指针类型或把接口的元数据基类说成Object。值类型的特殊关系见[第5章](README.md#chapter-05)。

CLS主要影响对其他程序集公开、希望被多种语言使用的API，不能说每个内部实现都必须只用CLS的最小特性集合。语言互操作也依赖共同的类型、签名及调用约定，不只是“最后都有IL”这一个条件。

<a id="c01-runtime-family"></a>
## CLR、.NET、Mono与IL2CPP

<a id="c01-framework-coreclr-mono"></a>
### 运行时与平台实现的关系

原问题把CLR、.NET、.NET Core、Mono和IL2CPP放到一起。先区分平台实现、执行引擎和编译后端，关系就清楚了。

| 技术 | 与原书CLR的关系 | 主要执行特点 | 场景与范围 |
| --- | --- | --- | --- |
| .NET Framework及其CLR | 原书的主要微软Windows背景 | 托管运行时，通常使用JIT，也可使用NGen映像 | 传统Windows桌面及服务器技术体系 |
| .NET Core / 后续.NET及CoreCLR | 现代跨平台.NET的一条运行时实现路线 | JIT及现代优化/预编译等；不是只支持一种生成模式 | 跨平台服务、桌面及其他受支持应用 |
| Mono | 另一条CLI/.NET实现路线，历史早于.NET Core | 在具体平台和产品中可用JIT、解释或AOT等路线 | 历史跨平台应用及Unity等产品的相关后端 |
| Unity IL2CPP | Unity的AOT脚本后端和相关运行支持 | 托管IL转换为C++，再由目标平台原生编译器生成本机代码 | Unity选择的受支持发布平台，尤其有JIT限制的环境 |

.NET Framework包含CLR和Framework类库等部分，不能说CLR就是全部.NET。原问答的“乐高城市套装”比喻表示完整开发平台，里面的电动马达和控制系统表示运行时。

.NET Core及后续.NET使用跨平台设计；把它类比为可在不同桌面搭建的模块化电动系统，有助于理解环境范围扩大。**.NET5并未把.NET Framework的全部技术合为同一个新运行时，也没有使所有旧应用自动兼容**。[.NET5官方说明](https://learn.microsoft.com/en-us/dotnet/core/whats-new/dotnet-5)明确区分它与.NET Framework。

Mono的历史类比是另一家厂商按兼容接口标准实现自己的马达和底盘：来源不同，但试图支持共同的CLI类型及执行模型。这个比喻说明历史实现关系，不表示Mono永远是与微软或现代.NET毫无关系的孤立第三方产品。Unity使用哪种后端还受平台和项目配置影响，不能简单写成“旧Unity只有Mono，新Unity全部IL2CPP”。

思考区另把CoreCLR与Mono比作承担共同引擎职责的不同实现型号。这能帮助理解“都在执行和管理.NET程序”与“内部实现相同”不是同一件事；不同型号仍可能采用不同的执行策略、GC和平台支持。这里保留型号类比的教学目的，修正“必定是同一个发动机设计”的暗示。

<a id="c01-il2cpp"></a>
### IL2CPP改变了哪个环节

Unity的IL2CPP路线仍先编译C#脚本，再把相关托管程序集的IL转换为C++，最后由目标平台的原生C++编译工具链生成可执行代码。根据构建设置还可能有裁剪等步骤，不能把“相关程序集”说成永远逐字保留全部类库。

它不同于本书普通CLR在运行时JIT编译IL的流程，但不能由“已经是本机代码”推出“没有任何运行时支持”。IL2CPP程序仍需类型、对象、GC、异常及互操作等相关支持。是否更快、更小或更适合某个工作负载，需要具体条件和测量；AOT是执行路线，不是性能保证。[Unity2019.4 IL2CPP概述](https://docs.unity3d.com/2019.4/Documentation/Manual/IL2CPP.html)说明了其AOT构建过程及平台限制。

原回答的“出厂翻译官”比喻保留了另一种理解方式：普通JIT阅读器在执行需要时把通用说明转为目标指令；IL2CPP更像在出厂前完成相应转换。最终产品减少运行时翻译工作，但仍带着执行和管理产品所需的支持设施。因此“无需现场翻译”与“无需任何运行服务”是两句话。

## 如何结合本书做练习

原问题询问官方配套习题集。原答用“搜索没有找到”作出“没有官方习题集”的确定判断，证据不足。出版方明确介绍了本书的代码示例及Framework4.5/VS2012定位；本整理未核实独立的官方习题集，因此保留这个不确定性，不把社区文章标作官方配套教材。[Microsoft Press第4版页面](https://www.microsoftpressstore.com/store/clr-via-c-sharp-9780735668751)可用于确认版本定位。

原回答中有价值的学习做法可以实际执行：

1. **精读并改动代码**：先预测结果，再运行、调试和修改一处条件。对于元数据/IL主题，比较源码、元数据签名、IL以及实际输出，区分语言规则和具体实现。
2. **用问题自测**：社区“带着问题读CLR via C#”一类文章可以帮助整理阅读问题，但它们是读者材料。回答存在争议时，应回到原书语境及对应规范/API依据，不能因为有问答就视为已证明正确。
3. **做部署实验**：读完程序集、强名称和GAC后，可以在合适的Framework实验环境中创建、签名和部署小程序集，观察私有副本与共享身份的作用；不必把这些旧机制直接搬到所有现代.NET/Unity项目中。
4. **结合官方文档**：查相应版本的API、C#规则及CLI说明。原笔记提到的旧MSDN名称如今通常可从Microsoft Learn进入；API文档说明类型和成员契约，语言/CLI规范用于进一步判断底层规则。

第1—3章建立执行、打包和部署的模型，第4—6章进一步学习类型、值/引用语义及成员设计，再进入常量和字段。这个阅读路线帮助把后面的具体追问放回整体模型，而不是用背诵术语替代运行和解释代码。
