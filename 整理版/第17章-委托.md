## 从回调到委托

回调把“什么时候需要某个动作”和“具体做什么”分开。算法或组件在适当时机调用你提供的方法。Windows 的窗口过程 `WndProc`、钩子 `HookProc`、APC，以及 .NET 的未处理异常通知、窗口状态变化、菜单选择、文件系统变化、窗体控件事件、异步完成通知，都有这种角色分工；它们的具体线程与生命周期规则各自不同。

开场问答还提到泛型委托的协变/逆变。它们允许符合引用类型转换方向的签名复用；不是所有参数类型都能随意替换，值类型实例化也不能靠变型转换。已有细节见[第12章泛型](第12章-泛型.md)。`Action`、`Func` 是常用类型，不存在普遍“微软禁止或不建议自定义delegate”的规则；本章后面的特殊签名就是合理需求。

<a id="c17-qsort"></a>
### qsort 怎样把比较规则交给调用者

`qsort` 是 C 标准库 `<stdlib.h>` 的通用排序函数。原问答把它直接称为“快速排序函数”：微软 CRT 文档确实这样描述其实现，但 C 标准只规定排序结果与比较合同，不保证所有实现都采用快速排序。下面是原型形状；`base` 是数组起点，`nmemb` 是元素个数，`size` 是每项字节数。

```c
void qsort(
    void *base,           // 要排序的数组起始地址
    size_t nmemb,         // 元素个数
    size_t size,          // 每个元素的大小（字节）
    int (*compar)(const void *, const void *)  // 比较函数指针
);
```

比较函数返回负数、零或正数表示小于、等于或大于。排序代码不必知道数组元素是整数、double、结构体还是字符串，也不必固定按年龄、姓名、升序或降序；调用者通过比较规则决定。原 C 示例保留如下，输入四个小整数的相减不会溢出；程序本身没有打印语句。

```c
#include <stdlib.h>
#include <stdio.h>

int compare_ints(const void *a, const void *b) {
    int ia = *(int *)a;
    int ib = *(int *)b;
    return ia - ib;  // 此输入安全；不能推广为任意 int 的通用比较器
}

int main() {
    int arr[] = {4, 2, 9, 1};
    qsort(arr, 4, sizeof(int), compare_ints);
}
```

排序后的元素顺序为 `1, 2, 4, 9`。`qsort` 在排序过程中反过来调用 `compare_ints`，这就是回调；调用次数和顺序属于排序实现，不能依赖固定次数。**补充修正**：通用 C 比较器可返回 `(ia > ib) - (ia < ib)`，避免有符号相减超范围的未定义行为。

<a id="c17-qsort-table"></a>
原问答的四维对照表保留，边界修正为“普通 C 函数指针”而非所有 C++ 回调：

| C / C++ 中的普通 C 函数指针 | .NET / C# 委托 |
| --- | --- |
| qsort 的 `int (*)(const void*, const void*)` | 声明有参数/返回类型的 `delegate` |
| qsort 接收比较函数 | `Array.Sort` 可接收 `Comparison<T>` |
| 指针签名可检查，但 `void*` 不表达元素的实际类型 | 委托签名表达 `T`，编译器检查绑定和调用 |
| 普通 C 函数指针本身不储存捕获环境；C++另有函数对象/lambda | lambda 转为委托时可以捕获外部变量 |

<a id="c17-sort-examples"></a>
两个 C# 原写法分别保留。第一种通过lambda中的比较操作表达顺序：

```csharp
int[] arr = {4, 2, 9, 1};
Array.Sort(arr, (x, y) => x.CompareTo(y));
```

第二种原来显式构造 `Comparison<int>`，教学目的是看见委托对象；它没有比第一种“更底层”的不同算法。原相减写法保留为有范围限制的对照：

```csharp
// 原写法：仅适用于比较差不会溢出的值域。
Array.Sort(arr, new Comparison<int>((x, y) => x - y));
// 修正后的通用比较，同样保留显式构造的教学目的。
Array.Sort(arr, new Comparison<int>((x, y) => x.CompareTo(y)));
```

在 unchecked `int` 运算中，`int.MinValue - int.MaxValue` 得到 `1`，方向错误；checked 则会抛异常。`CompareTo` 正确给出负数。本章探针在两运行时都确认此边界，没有把输出提升为排序实现保证。

## Feedback：同一计数器，三个不同回调

`Counter` 负责数数，`Feedback` 接住每个值并决定打印、弹窗或写文件。用户贴出的完整原例保留；它依赖 Windows Forms，运行时会弹出多次模态窗口，并向当前工作目录的 `Status` 文件追加内容。

```csharp
using System;
using System.Windows.Forms;
using System.IO;

// 声明一个委托类型，它的实例引用一个方法，
// 该方法获取一个 Int32 参数，返回 void
internal delegate void Feedback(Int32 value);
public sealed class Program {
    public static void Main() {
        StaticDelegateDemo();
        InstanceDelegateDemo();
        ChainDelegateDemo1(new Program());
        ChainDelegateDemo2(new Program());
    }

    private static void StaticDelegateDemo() {
        Console.WriteLine("----- Static Delegate Demo -----");
        Counter(1, 3, null);
        Counter(1, 3, new Feedback(Program.FeedbackToConsole));
        Counter(1, 3, new Feedback(FeedbackToMsgBox));          // 前缀 "Program." 可选
        Console.WriteLine();
    }

    private static void InstanceDelegateDemo() {
        Console.WriteLine("----- Instance Delegate Demo -----");
        Program p = new Program();
        Counter(1, 3, new Feedback(p.FeedbackToFile));
        Console.WriteLine();
    }

    private static void ChainDelegateDemo1(Program p) {
        Console.WriteLine("----- Chain Delegate Demo 1 -----");
        Feedback fb1 = new Feedback(FeedbackToConsole);
        Feedback fb2 = new Feedback(FeedbackToMsgBox);
        Feedback fb3 = new Feedback(p.FeedbackToFile);

        Feedback fbChain = null;
        fbChain = (Feedback) Delegate.Combine(fbChain, fb1);
        fbChain = (Feedback) Delegate.Combine(fbChain, fb2);
        fbChain = (Feedback) Delegate.Combine(fbChain, fb3);
        Counter(1, 2, fbChain);

        Console.WriteLine();
        fbChain = (Feedback)
            Delegate.Remove(fbChain, new Feedback(FeedbackToMsgBox));
        Counter(1, 2, fbChain);
    }

    private static void ChainDelegateDemo2(Program p) {
        Console.WriteLine("----- Chain Delegate Demo 2 -----");
        Feedback fb1 = new Feedback(FeedbackToConsole);
        Feedback fb2 = new Feedback(FeedbackToMsgBox);
        Feedback fb3 = new Feedback(p.FeedbackToFile);

        Feedback fbChain = null;
        fbChain += fb1;
        fbChain += fb2;
        fbChain += fb3;
        Counter(1, 2, fbChain);

        Console.WriteLine();
        fbChain -= new Feedback(FeedbackToMsgBox);
        Counter(1, 2, fbChain);
    }

    private static void Counter(Int32 from, Int32 to, Feedback fb) {
        for (Int32 val = from; val <= to; val++) {
            // 如果指定了任何回调，就调用它们
            if (fb != null)
                fb(val);
        }
    }

    private static void FeedbackToConsole(Int32 value) {
        Console.WriteLine("Item=" + value);
    }

    private static void FeedbackToMsgBox(Int32 value) {
        MessageBox.Show("Item=" + value);
    }

    private void FeedbackToFile(Int32 value) {
        using (StreamWriter sw = new StreamWriter("Status", true)) {
            sw.WriteLine("Item=" + value);
        }
    }
}
```

<a id="c17-counter"></a>
### Counter 只依赖委托签名

`internal delegate void Feedback(Int32 value);` 定义新的委托类型。`fb(val)` 在语言语义上调用其 `Invoke`，把当前整数交给对应方法。`Counter` 不需要知道回调属于哪个类、静态还是实例、输出目的地是哪一种。`Counter(1, 3, null)` 仍走完循环，但 `if (fb != null)` 使它不调用任何回调，并非程序停住。

三个方法的签名都与 `Feedback` 兼容。`FeedbackToConsole` 和 `FeedbackToMsgBox` 是静态方法；`FeedbackToFile` 是实例方法，需要具体 `Program p`。`sw.WriteLine` 的接收者是方法中新建的 `StreamWriter sw`，并不是委托的目标 `p`；绑定 `p` 使实例方法有 `this`，不会把所有被调用对象都变成委托目标。

<a id="c17-feedback-results"></a>
### 四个演示的步骤与结果

`StaticDelegateDemo` 先打印标题，然后空回调不输出；控制台回调依序输出 `Item=1`、`Item=2`、`Item=3`，弹窗回调依序显示同三条字符串。在同一类内，`new Feedback(Program.FeedbackToConsole)` 与 `new Feedback(FeedbackToConsole)` 可绑定同一静态方法。

`InstanceDelegateDemo` 建立 `p`，把 `p.FeedbackToFile` 绑定为回调。控制台除标题/空行外没有 Item 行，`Status` 追加 `Item=1`、`Item=2`、`Item=3`；多次运行不会自动清空旧文件。

`ChainDelegateDemo1` 以 Combine 依次加控制台、弹窗、文件回调。对值1先打印、再弹窗、再写文件，然后对值2重复。移除弹窗回调后再次计数1—2，只剩打印和写文件。`ChainDelegateDemo2` 用 `+=` / `-=` 做相同的两阶段过程；它是独立执行的另一演示，仍须保留。两链分别各追加两轮 `Item=1`、`Item=2`；一次 Main 共向原文件追加11行。

作者实际将原完整 WinForms 程序编译为 Framework 程序，未启动真实弹窗。另用明确标注的 `MessageBox.Show` 记录替身，在 Framework 和 .NET10运行原 Counter/四Demo/文件代码；仅替身把弹窗改为日志，不改变回调顺序，11文件行已核对。这不是实际 GUI 或所有文件异常行为的测试。

## 委托类型、构造和目标对象

委托类型是引用类型。C# 编译器生成与 `MulticastDelegate` 关联的密封类型及相应元数据，运行时支持其调用；不是运行中把普通用户代码随意改成某个类。问答的简化形状可以用来认识构造器和 `Invoke`，但以下是**元数据教学形状，不能作为可编译C#类**；用户不能按这个形状手写继承 `MulticastDelegate` 的普通类。

```text
sealed Feedback : MulticastDelegate
    .ctor(Object target, IntPtr methodPtr)
    Invoke(Int32 value) -> void
    BeginInvoke / EndInvoke（Framework时期异步委托入口）
```

<a id="c17-fields-table"></a>
原三个内部字段表保留，并修正解释：

| 字段示意 | 含义与限制 |
| --- | --- |
| `_target` | 教学上表示绑定对象；本例普通静态方法的公共 `Target` 为null，封闭实例方法的公共 `Target` 为p。私有字段布局不能直接用这条规则概括。 |
| `_methodPtr` | 运行时调用入口相关指针，可能指向适配跳板；不是“方法IL入口”。 |
| `_invocationList` | 多播实现中的调用列表存储；不是纯方法名数组，通常要保存各条委托及其目标。 |

固定 [.NET10 Delegate实现](https://raw.githubusercontent.com/dotnet/runtime/v10.0.0/src/coreclr/System.Private.CoreLib/src/System/Delegate.CoreCLR.cs)还含 `_methodPtrAux`，静态调用可能通过 thunk 适配。方法元数据、方法句柄、IL字节和实际调用入口是不同对象，不能仅检查三个私有字段就定义所有委托行为。

<a id="c17-target-lowering"></a>
### 为什么 new Feedback(p.FeedbackToFile) 只有一个源码参数

`p.FeedbackToFile` 是带有接收对象表达式的方法组，不是先执行该方法。编译器解析方法、评估 `p`，再构造委托。典型 IL 教学过程是把 `p` 压栈，用 `ldftn` 取得方法入口，再 `newobj Feedback::.ctor(object, native int)`；虚方法绑定还有 `ldvirtftn` 等情形。源码方法组语法与元数据构造器参数不是同一层。

原回答声称它会翻译为下面这句，**这是假代码且不是实际编译过程**：

```text
new Feedback(p, typeof(Program).GetMethod("FeedbackToFile"))
```

普通绑定不必做反射；这里 `GetMethod` 也返回 MethodInfo 而不是该构造器需要的 IntPtr，默认查找还看不到 private 方法。正确可写的源码就是 `new Feedback(p.FeedbackToFile)`，或者 `Feedback fb = p.FeedbackToFile;`。

<a id="c17-target-boundary"></a>
原问答“静态总null、实例总非null”只能用于当前两类绑定。反射还可创建开放实例委托：每次调用时用首参数传入实例；也能创建封闭静态委托：提前绑定静态方法的首参数。它们并非新语法把静态方法变成实例方法。[CreateDelegate合同](https://learn.microsoft.com/en-us/dotnet/api/system.delegate.createdelegate?view=net-10.0)明确这些形态，不能用Target为空与否一概判定Method.IsStatic。

<a id="c17-async-history"></a>
历史委托有 `BeginInvoke` / `EndInvoke`，应按Framework异步委托语境理解。在 .NET Core 和现代 .NET，这些委托异步入口不受支持，运行会出现 `PlatformNotSupportedException`，不是一句“现在obsolete”就说明全部问题；普通同步Invoke仍可用，也不能据此宣布所有APM API都不支持。现代迁移可另考虑Task，但不把Task例替换历史原机制。[微软迁移说明](https://devblogs.microsoft.com/dotnet/migrating-delegate-begininvoke-calls-for-net-core/)

<a id="c17-chain"></a>
## 调用列表、不可变性与匹配

对本例，合并后的逻辑顺序为：

```text
[ FeedbackToConsole,
  FeedbackToMsgBox,
  p.FeedbackToFile ]
```

`fbChain(1)` 会同步依序做如下三个动作，而不是并行广播：

```csharp
FeedbackToConsole(1);
FeedbackToMsgBox(1);
p.FeedbackToFile(1);
```

调用列表中每项不仅有方法，还可能带不同对象。原链不可变：Combine/Remove 的结果必须放回变量；原来保存旧链的别处仍看到旧内容。`fbChain += fb1` 的委托变量语义是 Combine并赋回；事件表达式则调用add访问器，访问器内部的存储策略可以不同。

原“每次Combine/Remove都创建不同的新对象”过强：`Combine(null, fb1)` 可直接返回 `fb1`；没有匹配的 Remove 可返回原对象；最后一项被删可得到null。不可变性指逻辑调用列表不被原地改写，不保证每次必分配、不意味着整个 `+=` 读改写自然线程安全。[Combine](https://learn.microsoft.com/en-us/dotnet/api/system.delegate.combine?view=net-10.0)、[Remove](https://learn.microsoft.com/en-us/dotnet/api/system.delegate.remove?view=net-10.0)

<a id="c17-remove"></a>
### 为什么 Remove 能用新构造的委托

可以直接将已有 `fb2` 传给Remove，并不必须重新new。原程序用 `new Feedback(FeedbackToMsgBox)`，是为了说明新构造的等值实例也能匹配；它和原 `fb2` 不必是同一引用，但可有相同委托类型、同一目标/方法及相同调用列表。Remove按列表相等匹配，从原列表中删除**最后一个匹配的连续子列表**；若被移除的委托只有一个条目，就是最后一个匹配项。原“只按方法签名”不正确：两个不同方法能有相同签名，两个对象上的同一实例方法也不是同一绑定。单靠原始 `_methodPtr` 值比较还可能漏掉运行时入口状态差异。

仅写 `Delegate.Remove(fbChain, ...)` 而忽略返回值，不会改变 `fbChain`；原完整程序已正确赋回。`+=` / `-=` 是方便的C#写法，并不取消委托类型匹配要求。

<a id="c17-chain-exception"></a>
### 异常与返回值

若某回调抛出且未在该回调内捕获，普通多播调用立即向调用方传播，后面的回调不会执行。没有“每项自动try/catch”。开场与思考区提到的 `GetInvocationList` 用途是手动管理这一策略。**补充片段**如下，每项捕获后继续只是一种明确选择：

```csharp
foreach (Feedback callback in fbChain.GetInvocationList()) {
    try { callback(1); }
    catch (Exception error) { Console.WriteLine(error.Message); }
}
```

本源没有展开逐项返回数组的程序。应保留其知识：带返回值的普通委托链在所有条目均正常完成后返回最后一项的返回值，而不是收集全部结果；若任何条目向外抛异常，整个调用没有正常返回值，不能把异常前最后一次成功的值当作结果。要收集全部正常结果必须自己遍历调用列表。两环境探针确认A→B抛异常后C不执行，手动捕获则A/B/C都到达；返回10、20的链正常完成后最终返回20。[C#委托调用规范](https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/language-specification/delegates#216-delegate-invocation)

<a id="c17-equality-cas"></a>
委托 `==` 比较调用列表意义上的相等，`ReferenceEquals` 比较对象身份。已有[委托CAS实证](整理记录/核验与验收/共享-委托CAS引用身份实测.md)以显式构造的相同静态方法委托a0/a1证明：`==` 为true而身份不同；引用CompareExchange失败返回a1时，不能用委托==误判成功。身份判断重试才安装第二条回调。该实验是确定顺序模拟交错，不是竞争线程或所有调度证明，亦不替换本章原多播程序。

<a id="c17-remote-analogy"></a>
原“遥控器按钮”类比：Feedback像规定“按下接收一个整数”的按钮接口，控制台、弹窗、文件方法是不同电器功能；Counter只负责按按钮，`+=`把多个动作接到同一按钮。这里的“接口”是类比，Feedback并非C# interface。

<a id="c17-event"></a>
## 事件是成员，add/remove 才是方法

用户问“事件是方法，委托是类，这样理解对吗？”后半句可用来描述委托类型；事件本身是类/结构/接口中的成员，不等于某一个方法。原三概念表保留：

| 概念 | 本质 |
| --- | --- |
| 委托 delegate | 声明新的委托类型；其实例表示可调用绑定/调用列表 |
| 事件 event | 允许订阅/退订的成员，封装对回调机制的访问 |
| add / remove | 事件访问器方法，类似属性访问器但合同不同 |

<a id="c17-event-lowering"></a>
原 NewMail 场景：

```csharp
public event EventHandler<NewMailEventArgs> NewMail;
```

这是字段式事件。典型编译器形状包括私有委托字段、add和remove方法，以及事件元数据。原展开片段保留为**教学形状**，不要求把同名字段和事件再手写成同一份合法C#声明：

```text
private EventHandler<NewMailEventArgs> NewMail = null;
public void add_NewMail(EventHandler<NewMailEventArgs> value) { ... }
public void remove_NewMail(EventHandler<NewMailEventArgs> value) { ... }
```

从普通外部C#代码只能对可访问事件使用 `+=` / `-=`，不能当字段整体赋值、读取并Invoke。此访问控制不是安全沙箱，不能把反射访问或所有类内部访问条件都说成“永远拿不到”。**自定义add/remove事件不必有对应私有字段**，可能转存EventSet/字典或转发到别处。详见[第11章字段式及自定义事件](第11章-事件.md#c11-custom-events)；原问答把所有事件统一成“一个私有字段+两个公共方法”遗漏了自定义事件与访问级别条件。

<a id="c17-event-target-table"></a>
原事件关联字段表在普通方法组绑定的模型中保留：

| 字段示意 | 本例关联 |
| --- | --- |
| 目标对象 | `p.FeedbackToFile` 绑定p；普通静态FeedbackToConsole无需接收对象 |
| 方法指针 | 关联要调用的方法，具体适配入口由运行时实现 |

原 `mm.NewMail += FaxMsg;` 示例假设FaxMsg是faxObject的实例方法，可写成 `mm.NewMail += faxObject.FaxMsg;`。典型 lowering 是建立 `EventHandler<NewMailEventArgs>` 绑定，再调用 `add_NewMail`。原下句仅是意图示意，**不是C#可调用的事件访问器/委托构造源码**：

```text
mm.add_NewMail(new EventHandler<NewMailEventArgs>(faxObject, FaxMsg));
```

正常订阅使访问器把新回调并入内部存储；compiler生成字段式访问器可用原子循环保证订阅修改，但事件一般合同不自动承诺所有业务逻辑线程安全。事件是否`protected virtual`引发、为何用EventHandler<T>、EventSet稀疏存储已有[第11章主位置](第11章-事件.md#c11-contract)；这里源只提出后续方向，不扩写整段新教材。

<a id="c17-event-permissions"></a>
对照原裸字段 `public EventHandler<NewMailEventArgs> NewMail;`：外部可以设null清空别人回调、覆盖整链或Invoke。改成 `public event ... NewMail;` 就限制外部普通源码只订阅/退订；一般由声明类型内部按设计引发。

原“遥控器安全外壳”类比和前面按钮类比用途不同：委托是可按的遥控器，目标是被控制电器，方法是按钮功能，链是一排电器；事件外壳只开放加/删连接，调用按钮留给厂商实现。它说明API权限，不能据此推导线程安全或不可被任何反射接触。

<a id="c17-wrapper"></a>
## wrapper 是委托实例，不是方法复制品

“包装器”在这里指包着可调用绑定的委托**对象**，类型由delegate声明定义；类的声明本身不是已装入某个方法的那份对象。它让方法可以通过对象变量传递。**补充说明**：包装对象不复制方法的IL，也不要求每次调用都反射查找。

原简化类形状为了突出对象/指针/多播三部分，保留为**概念图，字段实际位于基类/运行时实现，不能按此手写继承**：

```text
sealed Feedback : MulticastDelegate
    object _target                 // 目标绑定示意
    IntPtr _methodPtr               // 入口/适配示意
    object[] _invocationList        // 多播存储示意，不保证实际字段类型/布局
    Invoke(Int32 value)             // 运行时支持的调用
```

<a id="c17-wrapper-table"></a>
原包装内容表保留，针对 `new Feedback(p.FeedbackToFile)`：

| 包装内容示意 | 本例值/边界 |
| --- | --- |
| 绑定对象 | p这个Program实例，可用公共Target观察 |
| 方法入口关联 | FeedbackToFile的运行时调用入口，不是IL入口 |
| 调用列表 | 逻辑上一个绑定；私有_invocationList常用于多播，不以其null定义全部单播形态 |

<a id="c17-wrapper-path"></a>
两条原调用路径的用途不同，应分别理解：

```csharp
p.FeedbackToFile(1);  // 直接选择这个实例方法
Feedback fb = new Feedback(p.FeedbackToFile);
fb(1);               // 通过委托调用，语言上等于fb.Invoke(1)
```

```text
fb(1)
 ↓ Invoke
 ↓ 使用绑定对象p与FeedbackToFile的调用入口
 ↓ p.FeedbackToFile(1)
```

普通静态绑定“包方法”，封闭实例绑定“包p及其方法”，`Feedback fb = fb1 + fb2 + fb3;` 则“包一串回调绑定”。原T独有的“信封”类比也保留：把调用动作装进信封，在信封上记录接收者及动作；信封不是把收件人的代码复制进去。

<a id="c17-pointer-boundary"></a>
### 与普通 C 函数指针的区别

原 C式声明不属于C#语法：

```text
void (*callback)(int) = Program.FeedbackToConsole;
```

第四版C#5语境没有现代函数指针语法。现代C#9以后在unsafe中另有 `delegate*`，所以不能永久断言“C#不允许函数指针”。`delegate*`也不是带目标对象和多播列表的普通托管委托。[现代函数指针](https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/unsafe-code#function-pointers)

原qsort指针片段把返回值误写为void，应修正为：

```c
int (*compar)(const void*, const void*);
```

这种指针本身只指向函数，不额外存实例接收者。排序比较器仍会获得两个元素地址；若另需上下文，标准qsort没有独立的context参数，可用约定的全局状态或选具有context参数的扩展API等设计。不能误说结构体数组的成员都只能靠全局变量传。委托的对象绑定使Counter不必自行拼接目标和函数地址；“方法不是变量”意指不能在普通源码中把未转换方法组当任意方法对象，方法组可转换为合适委托。

<a id="c17-generic"></a>
## Action/Func 的边界来自委托声明

`Action<int>` 表示接收int返回void，`Func<int,string>` 接收int返回string，`Predicate<int>` 接收int返回bool；它们都是实在的委托类型，不是“语法糖工厂”。它们的声明参数没有你要的任意 `params` 标记、默认值或自选类型参数约束。普通通用签名用它们方便；要求这些元数据/源码调用特征时，应声明自己的委托。

<a id="c17-params"></a>
### params 改变调用语法，不阻止绑定数组参数

原自定义Logger完整例保留：

```csharp
delegate void MyLogger(params string[] messages);

class Program {
    static void Log(params string[] messages) {
        Console.WriteLine(string.Join(", ", messages));
    }
    static void Main() {
        MyLogger log = Log;
        log("a", "b", "c");  // a, b, c
    }
}
```

`params` 在委托声明上，编译器可将三个字符串打包成一个数组传给Invoke。**补充对照**：`Action<string[]> a = Log;` 合法，`a(new[] {"a","b","c"})` 也输出同结果；但 `a("a","b","c")` 编译失败，因为Action的Invoke只有一个数组参数，不带params展开。这不是Log绑定失败。

原 `Action<string[]> a = Console.WriteLine;` 被错误标作“编译错误”，实际能绑定 `Console.WriteLine(object)`，调用会打印数组类型名 `System.String[]`，不会自动拼接a/b/c，也不是WriteLine的params重载被绑定。[方法组转换规范](https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/language-specification/conversions#108-method-group-conversions)

<a id="c17-defaults"></a>
### 默认值属于调用端看到的委托参数

原例完整保留：

```csharp
delegate void MyDelegate(int x = 10);

class Program {
    static void Foo(int x = 10) {
        Console.WriteLine(x);
    }
    static void Main() {
        MyDelegate d = Foo;
        d();       // 10
        d(20);     // 20
    }
}
```

`Foo(int x=10)` 可合法绑定 `Action<int> a = Foo;`。`a(20)` 可调用，但`a()`失败；委托Invoke不是从Foo取得默认值。若补充声明 `delegate void DifferentDefault(int x=30);` 并另写 `DifferentDefault different = Foo;`，则`different()`传入30；上面原MyDelegate变量d的`d()`仍传入10。原A误把绑定标非法、原T说“委托定义本身不能包含默认值”，均须纠正；原小标题“默认值写在方法上”也应改为“委托调用看委托声明”。

原lambda形状 `Action<int> a = (x = 10) => { };` 是失败示例，不是有效默认参数写法。**现代差异补充**：C#12支持显式参数类型的默认参数/params lambda，例如 `var a = (int x=10) => Console.WriteLine(x);` 可`a()`；compiler会合成适当委托类型，这不使Action/Func自身的Invoke变成可选/params。[现代lambda参数说明](https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/operators/lambda-expressions)

<a id="c17-constraints"></a>
### 泛型约束要表达实际类型条件

原约束声明保留：

```csharp
delegate string MyFormatter<T>(T value)
    where T : class, new();
```

它要求引用类型并有public无参构造器。原“`MyFormatter<string>`合法”不成立：string没有这种构造器；`MyFormatter<int>`也失败，因为int不满足class。原两类型反例分别保留：

```csharp
// 故意失败的声明片段，分别编译核验：
MyFormatter<string> f1 = null; // string不满足new()
MyFormatter<int> f2 = null;    // int不满足class
```

**补充正确正例**是自有public无参构造器的Item，`MyFormatter<Item>`可绑定格式方法。Func的类型参数本身不声明你的class/new()/接口约束，不过外围泛型方法可以约束T并接受 `Func<T,string>`；不能夸大为用了Func就再也无法限制外围T。[泛型约束说明](https://learn.microsoft.com/en-us/dotnet/csharp/programming-guide/generics/constraints-on-type-parameters)

<a id="c17-feedback-signatures"></a>
两个不同的原Feedback扩展形状分别保留：

```csharp
internal delegate void Feedback(
    Int32 start = 0,
    params Int32[] values
);
```

第二个原来用了未声明TResult，下面仅补上缺少的类型参数，保留“参数T需要IComparable<T>、返回类型另选”的目的：

```csharp
internal delegate TResult Feedback<T, TResult>(T value)
    where T : IComparable<T>;
```

这些是独立声明片段，不能把同名同签名的第一种和前面原Feedback(Int32)不加判断塞入一个重复声明环境。`Action<int>` / `Func<int,int>`不自动具有上述params/default/约束声明。

<a id="c17-generic-design"></a>
原“最小公分母/兼容不同语言”“工厂产品与手工打造”的类比，适合表达复用通用签名与自定义合同的区别；这些类型还受所在框架版本/可用重载族限制。原断言“加这些功能必然爆炸成几十上百重载、破坏ABI、80%/20%且为Richter引文”没有本源的可靠设计证据，保留为需纠正的原解释，不能当实际比例或经核实作者原话。当前可确认的是既有类型声明的合同和语言调用规则，不能把推测当设计史。

<a id="c17-lambda"></a>
## lambda 的代码在哪里，怎样避免难读

Richter的“超过三行就写命名方法”是个人风格，不是语言限制。其提醒是让小回调清楚、复杂流程有名字与可单独测试边界；不是“lambda只能表达做什么，不能表达怎么做”。可读性还取决于状态捕获、副作用、异常与业务含义。

<a id="c17-lambda-lowering"></a>
原命名方法与对应lambda分别保留：

```csharp
private static void FeedbackToConsole(Int32 value) {
    Console.WriteLine("Item=" + value);
}
// 在拥有Counter的调用上下文中：
Counter(1, 3, val => Console.WriteLine("Item=" + val));
```

命名方法的名字、调用栈与复用入口清楚；lambda在此转换为Feedback，回调体通常编译到生成的方法中，而非在建立委托那一刻执行输出。原 `<>c` / `<Main>b__0_0` 示例保留为**生成形状示意**，不是可写C#标识符/固定compiler承诺：

```text
[CompilerGenerated]
<>c 或其他编译器生成位置
    <Main>b__0_0(Int32 val)
        Console.WriteLine("Item=" + val)
```

无捕获lambda不必为每次调用新建闭包类；编译器可以采用静态方法或共享辅助实例并缓存委托。转换为表达式树的lambda又是另一种表示，不能将所有lambda都定义成“闭包类+方法+委托包装器”。生成类名、IL降级和JIT内联位置都是实现细节；“实际不在这个方法里”指常见编译结构，源码调试器仍可通过调试信息映射到原lambda，不能说你已不再调试自己写的逻辑。

<a id="c17-lambda-exception"></a>
原除零示例保留：

```csharp
Counter(1, 3, val => {
    int x = 10;
    int y = x / (val - 2); // val=2 时抛异常
    Console.WriteLine(y);
});
```

val1打印-10；val2除零，若外层没有catch，整个调用向外传播，val3不会到达。原调用栈示意是：

```text
at Program.<Main>b__0_0(Int32 val)
at Program.Counter(Int32 from, Int32 to, Feedback fb)
at Program.Main()
```

具体名字、是否带行号和栈帧是否内联都可变。Visual Studio能单步进入lambda；调试信息、构建优化和异步状态机会影响显示，源未展开的异步lambda例不另编造。

<a id="c17-capture"></a>
原factor捕获场景和输出保留：

```csharp
int factor = 10;
Counter(1, 3, val => {
    Console.WriteLine(val * factor);
});
```

输出10、20、30。普通compiler会把捕获变量移到某个生成环境，例如原示意 `<>c__DisplayClass1.factor`；调试器可能以提升后的字段显示，不应保证所有配置中“factor必不在当前帧”。捕获的是变量而不是创建时数值快照；补充探针保存委托、改factor为20、再用val1调用得到20。委托继续存活可能使捕获对象/环境保持可达，形成意外延寿；不是任何闭包都等于内存泄漏。[lambda捕获说明](https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/operators/lambda-expressions)

<a id="c17-lambda-resource"></a>
### 五行日志回调与命名方法

原例包含C#6字符串插值，晚于第四版C#5；保留其现代写法与问题：

```csharp
Counter(1, 3, val => {
    var sw = new StreamWriter("log.txt", true);
    sw.WriteLine($"Processing {val}");
    sw.Flush();
    sw.Dispose();
    Console.WriteLine(val);
});
```

原来将此代码作为难读、异常处理不明显的反例，并没有声称它保证异常清理。**补充具体边界**：它将IO、清理和控制台混进匿名回调，若WriteLine或Flush抛出，后面的手动Dispose不会执行；行数只是提示，资源异常路径才是具体问题。正常执行会追加Processing1/2/3并打印1/2/3，实际字符串是`Processing 1`等。

原命名方法版本使用 **C#8 using声明**，也晚于第四版：

```csharp
private static void LogAndPrint(int val) {
    using var sw = new StreamWriter("log.txt", true);
    sw.WriteLine($"Processing {val}");
    Console.WriteLine(val);
}
// 调用片段：
Counter(1, 3, new Feedback(LogAndPrint));
```

命名方法表达用途，能复用、单测和定位。using声明保证离开作用域时Dispose，包括异常路径；其清理发生在Console.WriteLine之后，而原手动版在之前。**第四版语境补充等价修订**可用传统using块和 `"Processing " + val`，在块后打印，以保留原手动例正常路径的顺序。没有声称同一源码可在C#5编译；作者未把原log.txt业务实跑当必要验证。

<a id="c17-lambda-natural"></a>
短小明确的原LINQ/排序/计数例各自保留：

```csharp
var list = new List<int> { 1, 2, 3 };
var even = list.Where(x => x % 2 == 0);
Array.Sort(arr, (x, y) => x.CompareTo(y));
Counter(1, 3, val => Console.WriteLine(val));
```

需要 `System.Collections.Generic`、`System.Linq` 及前文Counter/arr上下文。`Where`查询遍历得到2，排序将原4/2/9/1变为1/2/4/9，最后打印1/2/3。原来“无副作用、纯逻辑”指此处的整数Where谓词和CompareTo比较lambda体，它们本身只做计算，该描述在此范围成立。**补充边界**：整个Array.Sort操作会修改数组，另一个Console.WriteLine回调会输出，不能将比较lambda体的性质移到整个操作或另一回调上。

原自查三问保留为风格提醒：是否超过三行、是否捕获外部变量、别人一周后是否能看懂。出现复杂状态/难懂控制流时可拆命名方法；捕获变量本身不是错误，清楚的长lambda也不会因行数被语言拒绝。

<a id="c17-reflection"></a>
## 根据字符串建立委托：反射程序

此例用两个预先声明的委托类型和四个现有方法，运行时由命令行选择，不是运行前连所有候选签名都“不知道”。反射查方法，CreateDelegate建立符合签名的绑定，DynamicInvoke用object[]调用。在已知菜单中，switch/委托字典同样能做分发；开放的插件、脚本、规则引擎或框架发现需求才常使反射有价值。MVC路由/过滤器、Unity、Autofac可以涉及这类机制，不宣称它们的全部实现都等于本程序。

<a id="c17-reflection-original-errors"></a>
用户原程序和原解释有四类实质问题：usage含{1}而只传换行一个格式参数，少参路径抛FormatException；整数循环从0开始，先把"TwoInt32s"当整数解析并失败（正常原输入实际打印Parameters must be integers.）；GetDeclaredMethod可能返回null，随后CreateDelegate会空引用；Int32.Parse超范围另抛OverflowException。帮助文本的Subtracr拼写也要修正，args[1]是方法名，不是回调的第一业务参数。

<a id="c17-reflection-corrected"></a>
下面是**在原完整程序上做必要修正的版本**：保留Type.GetType/GetTypeInfo/GetDeclaredMethod/CreateDelegate/参数数组/DynamicInvoke与四方法，只限制原菜单、补null与整数溢出处理、改循环起点和帮助参数。不是用全新方案替掉原例。

```csharp
using System;
using System.Reflection;
using System.IO;
using System.Linq;

// 下面是一些不同的委托定义
internal delegate Object TwoInt32s(Int32 n1, Int32 n2);
internal delegate Object OneString(String s1);

public static class DelegateReflection {
    public static void Main(String[] args) {
        if (args.Length < 2) {
            String usage =
                @"Usage:" +
                "{0} delType methodName [Arg1] [Arg2]" +
                "{0}    where delType must be TwoInt32s or OneString" +
                "{0}    if delType is TwoInt32s, methodName must be Add or Subtract" +
                "{0}    if delType is OneString, methodName must be NumChars or Reverse" +
                "{0}" +
                "{0}Examples:" +
                "{0}    {1} TwoInt32s Add 123 321" +
                "{0}    {1} TwoInt32s Subtract 123 321" +
                "{0}    {1} OneString NumChars \"Hello there\"" +
                "{0}    {1} OneString Reverse \"Hello there\"";
            Console.WriteLine(usage, Environment.NewLine, "DelegateReflection.exe");
            return;
        }

        // 将 delType 实参转换为委托类型
        Type delType = Type.GetType(args[0]);
        if (delType != typeof(TwoInt32s) && delType != typeof(OneString)) {
            Console.WriteLine("Invalid delType argument: " + args[0]);
            return;
        }

        Delegate d;
        try {
            // 将 Arg1 实参转换为方法
            MethodInfo mi = typeof(DelegateReflection).GetTypeInfo().GetDeclaredMethod(args[1]);

            // 创建包装了静态方法的委托对象
            if (mi == null) { Console.WriteLine("Invalid methodName argument: " + args[1]); return; }
            d = mi.CreateDelegate(delType);
        }
        catch (ArgumentException) {
            Console.WriteLine("Invalid methodName argument: " + args[1]);
            return;
        }

        // 创建一个数组，其中只包含要通过委托对象传给方法的参数
        Object[] callbackArgs = new Object[args.Length - 2];

        if (d.GetType() == typeof(TwoInt32s)) {
            try {
                // 将 String 类型的参数转换为 Int32 类型的参数
                for (Int32 a = 2; a < args.Length; a++)
                    callbackArgs[a - 2] = Int32.Parse(args[a]);
            }
            catch (OverflowException) { Console.WriteLine("Parameters must be integers within Int32 range."); return; }
            catch (FormatException) {
                Console.WriteLine("Parameters must be integers.");
                return;
            }
        }

        if (d.GetType() == typeof(OneString)) {
            // 只复制 String 参数
            Array.Copy(args, 2, callbackArgs, 0, callbackArgs.Length);
        }

        try {
            // 调用委托并显示结果
            Object result = d.DynamicInvoke(callbackArgs);
            Console.WriteLine("Result = " + result);
        }
        catch (TargetParameterCountException) {
            Console.WriteLine("Incorrect number of parameters specified.");
        }
    }

    // 这个回调方法获取 2 个 Int32 参数
    private static Object Add(Int32 n1, Int32 n2) {
        return n1 + n2;
    }

    // 这个回调方法获取 2 个 Int32 参数
    private static Object Subtract(Int32 n1, Int32 n2) {
        return n1 - n2;
    }

    // 这个回调方法获取 1 个 String 参数
    private static Object NumChars(String s1) {
        return s1.Length;
    }

    // 这个回调方法获取 1 个 String 参数
    private static Object Reverse(String s1) {
        return new String(s1.Reverse().ToArray());
    }
}
```

<a id="c17-reflection-args"></a>
`args[0]`委托类型名、`args[1]`方法名，`args[2]`起为业务参数。原ASCII位置图保留：

<a id="c17-reflection-path"></a>
原流程图保留，但两条字符串查找支路不能误读成“委托Type负责查业务方法”：

```text
args[0]字符串 ── Type.GetType ── 委托Type
args[1]字符串 ── typeof(DelegateReflection).GetTypeInfo().GetDeclaredMethod
                                  ↓ MethodInfo
委托Type + MethodInfo ── CreateDelegate ── 委托对象
业务字符串 ── Parse / Array.Copy ── object[]
委托对象 + object[] ── DynamicInvoke ── 真正的方法执行
```

CreateDelegate绑定一个方法，并非把整个MethodInfo当一个“包含所有IL的新包装副本”直接复制进去。返回值是object，是因为两个委托都这样声明；Add/Subtract返回int时会装箱。

<a id="c17-dynamic-limits"></a>
### DynamicInvoke 的适用边界

变量d的静态类型是 `Delegate`，不能直接写 `d(123,321)`；可在知道实际类型时转为TwoInt32s再强类型调用。DynamicInvoke允许用object[]晚绑定，它检查数量和参数匹配，进行API允许的转换，并返回object；不支持任意自定义格式字符串自动转换。数量错是TargetParameterCountException，元素类型不匹配可为ArgumentException，回调自身抛出的异常通常包装在TargetInvocationException，其InnerException是实际错误。[DynamicInvoke合同](https://learn.microsoft.com/en-us/dotnet/api/system.delegate.dynamicinvoke?view=net-10.0)

原程序只catch参数数量；修正Parse和mi=null不意味着它已处理所有反射/回调异常。两环境补充探针确证传"123"/"321"给int委托出现ArgumentException，回调抛InvalidOperationException则外层TargetInvocationException携带它。CreateDelegate也要求类型与方法签名兼容；OneString绑定Add在创建阶段拒绝。

与强类型委托直接调用相比，DynamicInvoke通常有额外检查/反射成本；没有本章速度基准支持“绝对最慢”。应按动态需求选用，而不是一律“日常业务禁用、只有框架才能用”。委托本身是CLR支持的类型与调用机制，C#的省略new、+=、lambda等是相应便利语法，二者不冲突。
