## 线程基础的知识地图

第26章先解释 Windows 为什么支持线程，再列出线程的空间与时间成本，提醒开发者停止无节制创建线程；随后讨论 CPU 发展、CLR与Windows线程、专用线程、线程的使用理由、调度优先级、前台/后台线程。线程是对处理器执行机会的虚拟化：多个执行流能交替取得处理器，而多个逻辑处理器可以真正同时运行不同线程。

线程不是免费的资源。创建、销毁、保存执行状态、调度以及访问重新变冷的数据都可能产生成本；下一章的线程池通过复用线程摊薄部分成本。可响应性和吞吐量也不是同一个目标，增加线程是否有帮助取决于任务是否计算密集、是否阻塞、是否需要独立生命周期。

<a id="c26-responsive"></a>
## 线程为何能改善响应

### 进程隔离与抢占调度承担不同职责

原书26.1以早期16位Windows打印或死循环使机器失去响应为背景。Windows NT把每个应用实例的资源放入进程，给它独立的虚拟地址空间，限制普通应用直接修改别的进程或内核数据；这改善安全与故障隔离。但只有内存隔离，还不能防止某段代码占住CPU。线程配合抢占式调度，让其他可运行线程取得执行机会，失去响应的应用之外仍能运行其他应用。

这里的“隔离”描述通常的受保护进程模型；合法共享内存、调试权限或系统级故障另有条件，不能把“普通应用出错通常不会破坏其他进程”理解为系统绝对不会出故障。

### 银行柜台与10秒按钮例

银行只有一个柜台时，前面的客户办理“大额转账+理财咨询”花20分钟，后面的人只能等待；多个柜台可让一个柜台办耗时业务，其他柜台继续服务。这说明拆分执行职责能改善响应。单逻辑处理器上的柜台需要轮流工作，多核才可能真正同时工作；类比不表示加柜台必然提高总吞吐量。

问答用两个事件处理器版本对比。它们应分别放在UI应用中，不是在同一类型里定义两次同签名方法；这里仅展示片段。

```csharp
// 版本A：在UI线程里等待10秒，阻塞该线程的消息处理。
private void Button_Click(object sender, EventArgs e)
{
    Thread.Sleep(10000);
}
```

```csharp
// 版本B：让工作线程等待，UI事件处理器很快返回。
private void Button_Click(object sender, EventArgs e)
{
    Thread t = new Thread(() =>
    {
        Thread.Sleep(10000);
    });
    t.IsBackground = true;
    t.Start();
}
```

版本A模拟耗时操作，窗口不能及时处理拖动、点击等消息；版本B保留10秒输入，由工作线程睡眠，UI线程可以返回消息循环。`Sleep`没有做计算，例子只说明等待发生在哪个线程；实际计算、结果交回UI、异常和取消要另设计。`IsBackground`控制正常退出时是否维持进程，不是保证UI流畅的开关。此处不运行实际GUI。

### 从外部结束冻结进程

原问答保留的流程是：打开任务管理器→找到失去响应的应用→选择“结束任务”。任务管理器有自己的进程和线程，抢占调度让它能继续获得CPU，系统可终止目标进程及其线程并回收该进程资源。这不依赖“任务管理器一定比目标线程优先级更高”这一前提。

终止失控进程也可能丢失它尚未保存的数据，强制终止不保证执行托管`finally`或原生DLL清理。这里说明进程隔离与调度的用途；本章不实际终止应用或制造死循环。

## 五项线程成本

### 空间成本表和reserve/commit区别

原书26.2列的是历史Windows线程模型。以下表保留问答的各项关系，纠正把近似尺度当成跨版本固定值的说法。

| 要素 | 原书/问答尺度 | 保存什么、为什么有成本 |
| --- | --- | --- |
| 线程内核对象 | 不能把整个对象概括为“几百字节” | 内核的线程描述、调度属性与执行状态；书列的x86约700、x64约1240、ARM约350字节是上下文的历史尺度，不能冒充整个KTHREAD/ETHREAD的大小 |
| TEB | 书中约一个内存页、4KB | 用户态的线程环境信息、TLS相关信息以及GDI/OpenGL等状态；当前结构和大小可随Windows/架构变化 |
| 用户模式栈 | Windows链接器通常默认reserve 1MB | 为调用帧、局部变量、实参、返回地址等提供存储；寄存器分配、优化和调用约定使这些内容不一定全部位于栈 |
| 内核模式栈 | 书中的32位12KB、64位24KB | 线程执行内核代码时的调用栈；不是现代所有Windows平台的固定API保证 |

reserve是在虚拟地址空间中预留范围；commit消耗系统提交额度；页面是否当前驻留物理内存又是另一层。初始提交和后续增长受配置、可执行文件头、线程创建参数及运行时实现影响。Windows的线程栈契约见[Thread Stack Size](https://learn.microsoft.com/en-us/windows/win32/procthread/thread-stack-size)。

原例的数量关系应这样读：若每个线程reserve 1MB，100个线程预留约100MB、1000个约1GB、10000个约10GB**虚拟地址范围**，不等于立即占用等量RAM。地址空间、提交量、实际栈深度和其他线程数据结构仍会限制可创建的线程数；不能据此实施无限线程或递归实验。

### 内核对象：档案与存档点

把线程内核对象类比成“人事档案+游戏存档点”：它帮助内核描述和调度线程，并保留继续执行所需的信息。书中的寄存器上下文模型便于理解保存/恢复；实现中有关状态可能分布在内核线程结构、内核栈和架构专用保存区，不把示意图当作当前KTHREAD的精确公开布局。

指令指针IP/RIP标识执行位置，栈指针SP/RSP标识当前栈位置，通用寄存器保存计算中间状态。优先级、状态、运行时间统计和关联TEB/栈等也属于线程管理信息，但问答把这些全列成同一个结构的具体字段并无对应版本源码证明。

### TEB：私人办公桌抽屉

TEB位于用户模式，便于线程取得自身的环境信息；与只有内核可直接访问的线程内核结构相比，可类比成“自己随时拉开的办公桌抽屉”。它有TLS相关字段，但不是托管字段布局的公开合同。[TEB文档](https://learn.microsoft.com/en-us/windows/win32/api/winternl/ns-winternl-teb)明确允许结构随版本变化，并建议通过相应API访问。

原书/问答说“每进入一个`try`块就在异常链插节点”适合解释传统x86基于栈的SEH，不能覆盖所有C#、x64或ARM实现。x64用函数表与展开信息描述异常处理，JIT也须提供相应信息；见[x64 exception handling](https://learn.microsoft.com/en-us/cpp/build/exception-handling-x64)。

`[ThreadStatic]`使静态字段具有每线程独立的值，是CLR管理的TLS功能；不能由此断言字段的值就直接存在TEB固定位置。`AsyncLocal<T>`关联异步执行上下文，可以随异步流程跨线程传播，也不能简单等同于TEB的线程槽。这里保留原追问所指的关联，详细托管TLS见第28章；[托管TLS说明](https://learn.microsoft.com/en-us/dotnet/standard/threading/thread-local-storage-thread-relative-static-fields-and-data-slots)说明的是托管语义。

### 两种栈：工作台与安全传输带

用户栈可类比成放图纸和返回位置指示的工作台。每个线程有自己的常规调用栈，但同一进程内地址空间共享，其他线程若持有合法指针仍可能访问它，不能把“线程自己的栈”理解成进程内内存安全隔离。

内核栈供内核代码保存自身调用帧、局部状态与返回位置。原问答用“进入机要室的安全传输带”解释把必要用户参数捕获到内核私有存储，以避免验证后被外部篡改；此安全目的有价值，但“任何系统调用的所有实参都从用户栈复制到内核栈”过于绝对。寄存器传参、指针指向的缓冲区以及buffered/direct/neither I/O处理不同，内核必须按接口验证、捕获或锁定所需数据，目的地也可以是内核池。见[用户地址访问错误](https://learn.microsoft.com/en-us/windows-hardware/drivers/kernel/errors-in-referencing-user-space-addresses)与[驱动安全检查](https://learn.microsoft.com/en-us/windows-hardware/drivers/driversecurity/driver-security-checklist)。

### DLL线程通知：时间成本

原生DLL可用`DllMain`的`DLL_THREAD_ATTACH`和`DLL_THREAD_DETACH`通知做每线程初始化与清理；CRT线程本地状态是原书的示例。普通C#生成的托管DLL不因此各自获得原生`DllMain`通知。原生DLL还可以在合适条件下用`DisableThreadLibraryCalls`关闭线程通知；静态TLS、CRT等条件要按API要求处理。

原补充例假设50个需要通知的DLL：创建线程可能触发50次入口调用；某段入口代码若已被换出，还可能需要换入，即使其线程分支没有实质工作，也有调用成本。原书的Visual Studio例记录约470个加载模块，用来放大说明通知开销；不能由总加载模块数直接推出每次必有470个有效入口被通知，更不是现代VS的固定模块数。

正常线程退出与进程整体退出不同；进程退出时不向每个线程逐一发送`DLL_THREAD_DETACH`，强制终止线程/进程也有通知缺失边界。[DllMain契约](https://learn.microsoft.com/en-us/windows/win32/dlls/dllmain)说明这些情形。通知开销取决于实际DLL及其工作，不保证它永远是创建线程成本的最大项。

保留原生命周期示意，数字为历史尺度，顺序为概念整理：

```text
new Thread(callback)       创建托管包装对象，尚未创建新的OS线程
    ↓ Start(...)
内核线程管理状态 + 用户态TEB
用户栈reserve（历史例1MB）及必要commit
内核栈（历史例32位12KB / 64位24KB）
适用原生DLL收到THREAD_ATTACH，执行线程初始化
    ↓
运行线程回调
    ↓ 正常回调返回/正常线程退出
适用DLL收到THREAD_DETACH，线程执行资源得到释放
内核对象自身还可能受句柄/引用寿命影响
```

原ASCII归属图也保留：

```text
内核模式：线程管理结构、执行状态、内核模式栈
-------------------------------------------------
用户模式（线程所属进程地址空间）：TEB、用户模式栈
-------------------------------------------------
DLL attach/detach：适用的创建/退出通知，不是另一块栈
```

原图中的`Abort`不能等价于原生强制结束且总能正常清理。Framework中的`Thread.Abort`有异步异常与状态风险，现代.NET不支持；本章不执行。线程池复用已存在线程，减少反复创建/退出与通知成本，但不会让管理、调度和所有资源成本都“几乎归零”。

### 10000个任务：原场景与闭包修正

下面保留原输入“10000个独立任务”、两种投递方式和比较目的，代码仅作静态展示；不实际创建10000个线程。

```csharp
// 方案A：每任务创建专用线程。ProcessTask为应用自定义方法。
for (int i = 0; i < 10000; i++)
{
    int taskId = i; // 复制本轮输入，避免延迟执行的闭包共享for变量i。
    new Thread(() => ProcessTask(taskId)).Start();
}

// 方案B：向线程池投递10000个任务，线程由池管理和复用。
for (int i = 0; i < 10000; i++)
{
    int taskId = i;
    ThreadPool.QueueUserWorkItem(_ => ProcessTask(taskId));
}
```

方案A在每线程reserve 1MB的假设下可能预留约10GB地址空间，还增加创建、通知与调度成本。方案B避免为每个任务都创建线程；线程池工作线程数会动态调整，队列和任务仍占资源，阻塞任务也可能造成等待。它不是“固定数量线程所以任何负载都可控”的保证。原例若直接捕获`i`，回调拿到的值取决于执行时机，不能保证是各自的0—9999；修正明确保存了原本要处理的任务编号。

## 上下文切换的三步

### quantum不是固定30ms闹钟

Windows在逻辑处理器上调度就绪线程。每个逻辑处理器同一时刻执行一个被调度的软件线程；一个物理核若支持SMT可承载多个逻辑处理器，不能把“逻辑处理器”与“物理核”混为一谈。单处理器上的并发体现为交替执行，多逻辑处理器上的线程可以并行；它们仍共享缓存、带宽等资源，并非完全互不影响。

书用约30ms说明时间片尺度。时间片受系统版本、配置与处理器等影响；线程等待I/O、睡眠或同步对象时可在时间片用完前阻塞，更高优先级线程变成就绪也可能触发抢占；时间片到期后若没有合适的其他就绪线程，当前线程可继续运行。见[Context Switches](https://learn.microsoft.com/en-us/windows/win32/procthread/context-switches)。

保留原时间线的A/B/A/C输入，其中30ms只是原书的教学示意，不是固定预测：

```text
时间 →
逻辑CPU0: [A约30ms][B约30ms][A约30ms][C约30ms]...
其他可能：A提前等待 → B；A片结束但没有合适其他线程 → A继续
```

线程写了无限循环也可能被抢占，但不能由此保证所有系统负载、优先级与资源条件下UI都永远流畅。此处不运行无限循环。

### 保存、选择、恢复

1. 保存旧线程继续执行所需的处理器状态。教学模型中包含IP/RIP、SP/RSP和通用寄存器等，不是把线程的所有内存全拷走；具体状态保存方式属于对应架构与内核实现。
2. 选择可运行的新线程。等待输入、同步对象或被挂起的线程不因优先级高就取得CPU。若新线程属于另一个进程，还须建立正确的进程地址空间上下文。
3. 恢复新线程的状态，使其从暂停位置继续。新线程第一次运行则使用初始化的状态。寄存器恢复提供继续执行所需的状态，但墙上时间、共享内存等可能已经变化，所以不能说线程绝对无法感知自己曾暂停。

```text
时间片到期/当前线程等待/更高优先级线程就绪
                    ↓ 确实需要换线程时
┌ 保存：旧线程的寄存器、执行位置、栈位置等状态
├ 选择：新就绪线程；跨进程时切换进程地址空间上下文
└ 恢复：新线程的执行状态 → 继续执行
```

原书26.2已经说明同一线程可继续运行、等待时提前放弃等条件，调度优先级的正式小节就在26.8；问答说“第29章细讲Windows线程调度”需更正，第29章主题是基元线程同步构造。

### 同一个虚拟地址为什么会指向不同数据

原例让进程A与B都使用`0x10000000`。这个数字相同，不表示指向同一份存储；两个进程的映射可能不同，也可能有共享映射，甚至某个进程没有映射该地址。CPU须使用当前进程的翻译与访问权限。

在传统x86/x64示意中可写“CR3换成新进程页表的根”；它用于说明CPU必须看见正确地址空间，不是所有架构与现代Windows切换路径的完整指令表。如果错误地用A的映射访问B的虚拟地址，可能取到错误数据或发生访问故障，不能断言每次都会立即使整个系统崩溃。

同一进程中的线程共享地址空间，切换通常不需要更换进程地址空间。跨进程可能多出地址翻译等成本，但不能据此保证每次“跨进程切换耗时一定大于同进程切换”。PCID/带标签TLB、全局映射和缓存工作集等条件会改变成本；普通切换也不意味着所有TLB或CPU缓存内容必然全部清空。

### 厨师交接的比喻与性能边界

把CPU看成厨师、寄存器看成菜做到了哪一步、地址空间看成当前食谱/食材区。经理决定换菜时，厨师把状态写在纸条上；同一桌可继续使用同一食材区，换另一桌就切换对应食谱与食材区；拿到新菜的纸条，按记录继续做。交接本身没有做完一道新菜，所以对业务有管理成本，但它换来了调度与响应能力。

这里的“清工作台”表示改变当前映射，不表示把旧进程内存删除。等待线程不进入就绪队列；线程总数多不等于同一时刻都争用CPU。对纯计算、长期就绪的工作，过度订阅容易增加切换与缓存竞争；阻塞/I/O/独立响应场景则可能有合理理由超过逻辑处理器数。线程池减轻生命周期成本，真正异步I/O配合`async/await`还能减少专门等待的线程；`async`关键字本身不保证I/O API一定异步。

原补充提到`Thread.Sleep(0)`和yield：[Sleep(0)](https://learn.microsoft.com/en-us/dotnet/api/system.threading.thread.sleep?view=net-10.0)给同优先级的就绪线程一个机会，没有相应线程时可以继续；[Thread.Yield()](https://learn.microsoft.com/en-us/dotnet/api/system.threading.thread.yield?view=net-10.0)请求当前处理器上的其他就绪线程运行，是否成功由返回值体现。它们不等同于某个确定顺序的线程切换。

<a id="c26-stack"></a>
## 保存现场是否要搬运栈

### 保存的是继续执行的位置与状态

追问“保存现场时是保存内核栈到内核空间吗？那用户栈呢？”混淆了保存处理器现场与复制整块栈。普通调度切换保存/恢复所需执行状态，管理线程对应的用户栈与内核栈信息；它不会为了每次换线程而把整块用户栈、整块内核栈另拷一遍。

用户栈位于所属进程的地址空间，内核栈用于内核执行。线程恢复时，正确的地址空间和栈位置让它继续使用已有调用帧。栈通常由线程持有，但不是“别的线程绝不能碰”；生命周期、访问合法性、页是否驻留又分别有条件。

原答的`ESP0`也需辨清：x86的TSS中有`SS0:ESP0`特权级0栈信息，`ESP0`不是像`RSP`那样一个可独立直接读写的通用CPU寄存器。不同架构的内核栈切换和保存区不同；不把这段补充误写成现代Windows一律通过硬件TSS任务切换。

### 保留A/a1到B/b1的完整场景

```text
场景：进程A线程a1 → 进程B线程b1

① 保存a1的必要处理器状态与栈相关信息
   a1的用户栈仍属于A；内核栈仍属于a1，不整体拷给b1
② 切换到B的地址空间上下文
   相同用户虚拟地址按B的映射解释；不会因此删除A的栈
③ 恢复b1的执行状态与正确的栈信息
   b1继续使用自己的用户/内核调用栈

a1再次就绪并被选中：建立A的地址空间 → 恢复a1状态 → 继续a1
```

保留原两进程归属图，同时移除“永远在同一物理位置”这样的过强承诺：

```text
系统管理的内核存储
  ┌ a1内核栈 + a1线程执行状态/关联信息
  └ b1内核栈 + b1线程执行状态/关联信息

进程A用户地址空间             进程B用户地址空间
  ┌ a1用户栈                   ┌ b1用户栈
  └ a1用户态环境信息           └ b1用户态环境信息

切换：保存a1 → 选择B/b1并建立正确映射 → 恢复b1
目的：保留各自调用帧，普通切换不整体搬运栈
```

“栈留在原地”的教学主旨是不用每次拷贝整块栈，不能保证页面永远驻留RAM或永远保持物理位置；内核栈在某些等待条件下也可能被换出。Windows文档还明确其大小与架构/版本相关，见[Using the Kernel Stack](https://learn.microsoft.com/en-us/windows-hardware/drivers/kernel/using-the-kernel-stack)。

### 为什么不搬栈，为什么仍有成本

原反问以1000个线程、每个reserve 1MB的用户栈说明：如果每次把整块栈搬走再搬回，会做大量与当前任务无关的工作。只保留恢复所需状态使成本不随栈中所有字节线性增长。这一解释不需要“99.9%栈数据不会访问”“固定微秒级”“只有几百字节所以极快”等无测量保证。

切换后新线程的代码或数据可能不在相应高速缓存、地址翻译也可能需要重新建立；这些是额外成本来源，但缓存/TLB不是一律全部失效，也不能在没有工作负载和平台条件时认定某一项永远最贵。原书26.2已经提醒无法给所有上下文切换统一耗时。

```text
单核示意：[Core]                         原例约3.8GHz
四核示意：[Core][Core][Core][Core]         原例每核约3GHz
四份独立、可均分的计算 → 理想情况下可同时处理
不意味着所有单线程代码永远不再变快，也不保证总性能恰为4倍
```

更多核数本身不会自动把一个顺序执行流拆开；但新CPU的指令级并行、缓存、架构、频率和编译优化仍可能提升单线程性能。线程还能在处理器之间迁移，只是在同一时刻不会被同时调度到两个逻辑处理器。其余3/7/15核不一定闲置，它们可运行别的进程、运行时或系统工作；“2005年3.8GHz与2024年4GHz单线程几乎一样”缺少可比较的架构、代码与测量，不能作为事实。

### 100000000次计算和并行骨架

原计算片段的输入与运算保持：

```csharp
// 成员片段：result为调用者管理的double累计值。
void Compute()
{
    for (int i = 0; i < 100_000_000; i++)
    {
        result += Math.Sqrt(i) * Math.Cos(i);
    }
}
```

原例假设1核3GHz耗时10秒，再比较4核3GHz仍10秒，意在说明顺序执行不会自动利用四核。它没有提供实测环境；相同GHz也不能保证相同每核性能，10秒是教学假设。

原并行片段是**未实现计算的骨架**，不能拿它与上面的求和比较时间或结果：

```csharp
void ComputeParallel()
{
    Parallel.For(0, 100_000_000, i =>
    {
        // 原骨架：这里还没有Math.Sqrt/Math.Cos和结果归并。
        // Parallel.For管理迭代调度，不保证每次迭代分配到不同核心。
    });
}
```

为了补全同一求和目的，以下**修正补充片段**保持100000000次输入，将四块结果独立写入数组，再串行归并。比较两版本次总和时，顺序版应在调用前把`result`设为0；修正版返回本次总和。若原场景是给已有`result`累加，调用者须再把返回值加到该原值，不能静默改变累计起点：

```csharp
double ComputeParallelCorrected()
{
    const int count = 100_000_000;
    double[] partial = new double[4];
    Parallel.For(0, 4, block =>
    {
        int from = block * (count / 4);
        int to = (block + 1) * (count / 4);
        double local = 0;
        for (int i = from; i < to; i++)
            local += Math.Sqrt(i) * Math.Cos(i);
        partial[block] = local;
    });
    return partial[0] + partial[1] + partial[2] + partial[3];
}
```

不同块写不同数组元素，不共享非原子`result +=`；浮点加法结合顺序改变，结果可能有舍入差异。四块不是保证四线程/四核同时执行，更不是所有计算的最优划分。原问答的2.5—3秒仅是接近四倍加速的设想，空骨架和本章有限验证都不能证明它。并行收益还受串行部分、调度、负载均衡、带宽、同步与分块大小影响；原100000000次版本仅编译/静态核验，不用于真实性能排名。

<a id="c26-cpu-hardware"></a>
### 三层硬件组织：多插槽、多核、SMT

这些技术增加系统可同时推进的执行流，但不是“真的CPU”和“假的CPU”的分类。

```text
主板
├ 物理处理器封装1
│ ├ 物理核心1 → 逻辑处理器0、1（若该核开启双路SMT）
│ └ 物理核心2 → 逻辑处理器2、3（若该核开启双路SMT）
├ 物理处理器封装2 → 它自己的物理核心/逻辑处理器
└ 物理处理器封装3 → 它自己的物理核心/逻辑处理器
   ↑ 多CPU/多插槽      ↑ 封装内多核      ↑ 核内SMT
```

多CPU通常指多个物理处理器封装安装在不同插槽；多核指一个封装里有多个核心，现代封装还可能包含多个芯粒，不必只有一块硅die。多CPU与多核可以叠加，不能说多核必然意味着主板只有一个插槽，或多核完全取代多插槽。更多插槽通常需要更多主板、电源与散热支持，但总功耗和价格不能脱离型号、总容量与负载作绝对比较。

多核有更多相对独立的执行资源；缓存与控制器的共享范围依微架构而定，不能普遍规定每核L2独立、所有核共享同一L3/同一内存控制器。多个封装通常有各自缓存，也通过互连保持需要的缓存一致性；不是多CPU天然“缓存不一致”，更不是只要同芯片就没有一致性维护成本。

Hyper-Threading是Intel的SMT实现/名称。原书与问答正确指出：双路SMT复制两份架构状态、共享物理执行资源，不等于增加一个完整物理核。但把它说成“同一时刻只能执行一个线程、只有线程A停住才切到B”不准确：两个逻辑处理器的指令可同时在不同流水线阶段或执行单元中推进。原书纸本598页也确实有此说法；Intel[2002年架构论文](https://www.intel.com/content/dam/www/public/us/en/documents/research/2002-vol06-iss-1-intel-technology-journal.pdf)已明确说明同时执行，因此这不只是现代版本不同。

一个核通常有多个执行单元，不是问答说的恰好一个ALU、一个FPU。缓存未命中、分支预测或依赖可能降低某线程可发射的指令量，另一线程可利用空闲资源；硬件内部资源仲裁不同于Windows调度器做软件上下文切换。书中10%—30%是历史性能宣传尺度，不保证任意负载都有这个收益，两个争用相同资源的线程也可能更慢；同样不能把额外逻辑处理器固定折算成“0.x核”。

Windows能取得逻辑处理器之间的核、封装、缓存和NUMA关系，[GetLogicalProcessorInformationEx](https://learn.microsoft.com/en-us/windows/win32/api/sysinfoapi/nf-sysinfoapi-getlogicalprocessorinformationex)在Windows7/Server2008R2已经提供相应接口。原书说Windows完全不知道HT拓扑应修正；先分散到物理核再用兄弟逻辑处理器可解释调度动机，不能当成所有Windows版本、线程亲和性、优先级、负载下的固定次序。

保留原三组数量例，成立前提是每颗的核数相同、每核启用相同数量SMT、没有屏蔽或限制：

```text
1颗 × 4核 × 每核2逻辑处理器 = 8逻辑处理器（示例CPU0—CPU7）
2颗 × 4核 × 每核2逻辑处理器 = 16逻辑处理器、8物理核
2颗 × 16核 × 每核2逻辑处理器 = 64逻辑处理器、32物理核
```

第一例可对应某些四核八线程i7，而不是所有i7的定义。异构核、禁用SMT、虚拟机与可用处理器限制时，要按各核实际逻辑处理器数求和。Windows调度的执行实体是**线程**，执行位置是逻辑处理器；问答说“逻辑处理器是调度最小单位”混淆了对象与位置。

### 三种公司类比和硬件对照表

原问答的“多人各有办公桌”“同办公室里多个工人”与“公司—分公司—团队—设备”都保留，分别强调不同层级。

| 技术 | 原生活类比 | 类比的边界 |
| --- | --- | --- |
| 多CPU | 公司有多个分公司，或多雇几个人，每人一张桌 | 分公司有自己的资源，但仍通过互连协调；不能由分公司数直接推出加速比 |
| 多核 | 一个分公司有多个团队，或把多个工人放入同一个办公室 | 每人可干自己的工作，仍共享部分资源；共享咖啡机不能代表所有核必共享同一L3 |
| SMT | 团队有两名成员共享一套设备；原例也比作一人两工作台 | 共享设备的意象有用；“一双手只能交替工作”只是资源共享类比，不能用来否认真实同时指令推进；不到两完整核的资源不等于固定性能倍数 |

第8轮又用分公司打长途电话、同办公室团队近距离沟通来比较通信距离；保其解释角度，不把“近距离”升级为任何操作都快几个数量级。原两CPU各两核与单CPU四核对照图保持输入：

```text
多CPU示例：主板 [插槽A:核1/核2] [插槽B:核1/核2]
单CPU多核示例：主板 [插槽A:核1/核2/核3/核4]
两例都有4个物理核；区别是封装/插槽组织，不是多核只能单插槽。
```

| 对比维度 | 多CPU/多插槽 | 一个多核封装 |
| --- | --- | --- |
| 物理形态 | 多个处理器封装，各封装本身可多核 | 一个封装内多个核心，可能多芯粒 |
| 核心间通信 | 跨封装互连，成本受平台与访问路径影响 | 封装内互连，也可能跨芯粒；不能统一保证“延迟极低” |
| 共享什么 | 可共享系统内存，通过一致性机制协调各级缓存；有的平台内存分节点 | 缓存/控制器共享范围按设计，未必全核共用同一L3 |
| 功耗/发热 | 多插槽通常增加供电与散热规模 | 集成可改善效率，但要在可比型号、容量和负载下判断 |
| 成本 | 多插槽主板与平台较复杂 | 集成常降低平台成本，不保证任何配置性价比必胜 |
| 典型场景 | 服务器、工作站等需要大容量/扩展能力的系统 | 消费设备、手机、服务器都可有多核；两类不是互斥市场 |

<a id="c26-cpu-numa"></a>
### NUMA、ProcessorCount和线程池

NUMA表示内存访问代价随节点位置不同；多个插槽常有各自直连内存，访问远端内存可能更慢。性能敏感的数据库、Web服务等须结合线程与内存放置考虑局部性，线程亲和性只是工具之一，盲目固定线程也可能妨碍调度。

“多核系统不存在NUMA”错误。一个多核封装可划成多个NUMA节点，例如AMD[EPYC 9004调优指南](https://www.amd.com/content/dam/amd/en/documents/epyc-technical-docs/tuning-guides/58011-epyc-9004-tg-bios-and-workload.pdf)的NPS选项；同封装共享某些资源不消除所有访问距离。普通代码不必手写硬件调度，但性能分析仍可能依赖拓扑。

`Environment.ProcessorCount`不是物理核数。在Windows旧.NET中它通常反映机器逻辑处理器数；.NET6起考虑进程亲和性和CPU限额等限制，详见[版本变更说明](https://learn.microsoft.com/en-us/dotnet/core/compatibility/core-libraries/6.0/environment-processorcount-on-windows)。不要由这个整数倒推物理核/SMT/NUMA布局。

原问答举桌面/服务器16、32、64核、手机8核、云VM96vCPU，用来说明并行资源数量可以很大，不能当成所有平台的当前“主流”统计。96vCPU也不等于96物理核，例如[AWS的m5.24xlarge规格](https://docs.aws.amazon.com/ec2/latest/instancetypes/gp.html)列96vCPU、48核、每核2线程。

长期就绪的纯计算可从可用处理器数量附近试起，但SMT、串行部分、缓存、带宽与响应要求决定收益；不保证“线程数=物理核数必最优”。I/O阻塞可需要更多线程来覆盖等待，真正异步I/O又能减少专门等待的线程。线程池按实际运行时算法动态调节线程数，以吞吐与阻塞等信息作决策，不是只读一个核数固定建池。

### 第26—30章的正确路线

| 原书章 | 主要解决的问题 |
| --- | --- |
| 第26章 线程基础 | 响应、扩展性、线程成本、专用线程与生命周期；调度/优先级就在26.8 |
| 第27章 计算限制的异步操作 | 线程池、Task、并行计算等；通过复用减少线程创建开销 |

Task/Parallel帮助表达计算并发，`async/await`帮助编排异步流程；异步并不必然使用多个核，不能把它们统一说成“为多核加速而生”。原书强调有智能地使用线程，而不是要求每个程序必须创建更多线程。

## CLR线程、专用线程与优先级

### Windows线程与历史宿主抽象

第4版26.5以桌面Windows/.NET Framework为背景，托管线程通常由Windows线程承载。CLR有自己的托管线程ID，Windows又有OS线程ID；`Environment.CurrentManagedThreadId`与`ProcessThread.Id`属于两种视图，不要求数值相同。现代.NET还能运行在其他OS上，不能把“CLR线程等价于Windows线程”无条件推广到所有平台。

原书讲了早期逻辑线程抽象尝试与留下的线程亲和性API。第1轮把它转述成“把物理线程在不同OS线程间迁移”，混淆了任务与物理线程；`Thread.BeginThreadAffinity`的[Framework契约](https://learn.microsoft.com/en-us/dotnet/api/system.threading.thread.beginthreadaffinity?view=netframework-4.8.1)描述能自行管理线程的宿主（例为SQL Server 2005）可能在物理OS线程之间移动**执行中的任务**，依赖OS线程身份的代码需通知宿主。此API不是CPU核心亲和性的设置器，也不能据旧API存在宣称现代SQL Server配置必然使用这类迁移。本章不运行SQL、宿主或原生锁程序。

本地MD和同版纸本599页都写了`System.Thread`；实际类型名是`System.Threading.Thread`，这是原书/摘录的命名错误而非新版本重命名。书中关于Windows Store移除Thread相关API是当年应用模型的历史范围，不把它概括成所有现代Windows应用都禁止`Thread`。

### 为什么有时仍要专用线程

原书26.6有四条理由，第1轮把两条混为一条，保全后应区分：

1. 需要特定的非普通优先级。线程池默认普通优先级，不宜为单个工作项长期改池线程状态。
2. 需要前台线程来维持正常托管进程生存期，使主入口返回后仍等该线程完成。
3. 计算任务需要长时间运行，专用线程可避免长期占据池工作线程、干扰线程池调节；“长运行”与“前台”不是同一条件。
4. 书中历史理由是可能要用`Thread.Abort`提前中止。它属于Framework时代API，不能作为现代.NET的实践建议；.NETCore/5+不支持，.NET5起还发弃用警告。应设计协作取消，见[Abort版本说明](https://learn.microsoft.com/en-us/dotnet/core/compatibility/core-libraries/5.0/thread-abort-obsolete)。

这四条是书的历史选择依据，不是随便新建线程的通行证。现代线程池[官方说明](https://learn.microsoft.com/en-us/dotnet/standard/threading/the-managed-thread-pool)还列长期阻塞、STA或稳定线程身份等限制；这里作为必要边界补充。`Suspend`/`Resume`和异步中止会产生状态/锁等问题，本章只静态保其历史语境。

### Start(5)、Join和两种输出顺序

`Thread`可接受无参的`ThreadStart`或参数为`object`、返回`void`的`ParameterizedThreadStart`。构造托管包装对象不等同立即创建新OS线程，`Start`使新线程开始执行回调；`Start(5)`将装箱后的5传给参数回调。原书偏好参数委托是作者当时的设计观点，无参/闭包形式同样是合法API。

保留书26.6完整程序、输入5、两处1000毫秒等待、Join与Enter退出流程，修正纸本600页把主线程1000毫秒注为10秒的真实注释错误：

```csharp
using System;
using System.Threading;

public static class Program
{
    public static void Main()
    {
        Console.WriteLine("Main thread: starting a dedicated thread " +
                          "to do an asynchronous operation");
        Thread dedicatedThread = new Thread(ComputeBoundOp);
        dedicatedThread.Start(5);

        Console.WriteLine("Main thread: Doing other work here...");
        Thread.Sleep(1000); // 模拟其他工作1秒；不是10秒，也不是实际计算。
        dedicatedThread.Join(); // 等待该线程终止。
        Console.WriteLine("Hit <Enter> to end this program...");
        Console.ReadLine();
    }
    private static void ComputeBoundOp(object state)
    {
        Console.WriteLine("In ComputeBoundOp: state={0}", state);
        Thread.Sleep(1000); // 模拟其他任务1秒。
    }
}
```

原书列的两组输出是前3行的可能前缀，都保留：

```text
Main thread: starting a dedicated thread to do an asynchronous operation
Main thread: Doing other work here...
In ComputeBoundOp: state=5
```

```text
Main thread: starting a dedicated thread to do an asynchronous operation
In ComputeBoundOp: state=5
Main thread: Doing other work here...
```

主线程的第一行在`Start`前；随后主线程与工作线程的打印顺序由实际调度决定。`Join`等待目标线程终止，故最终`Hit <Enter>...`在工作线程完成后，书的两组前缀省略了它，不能当作完整程序输出。原本的两处Sleep没有建立第二/第三行打印次序；调用`Join`阻塞的是调用者。本章有限验证对ReadLine传入已知换行，不等待未知用户输入。

### 调度优先级

Windows调度线程，进程优先级类影响线程基础优先级。六个进程类与七个相对线程优先级的原书表26-1（纸本606页）如下，五个普通行是`ThreadPriority`通常提供的层级：

| 相对线程优先级 | Idle | BelowNormal | Normal | AboveNormal | High | Realtime |
| --- | --- | --- | --- | --- | --- | --- |
| Time-Critical | 15 | 15 | 15 | 15 | 15 | 31 |
| Highest | 6 | 8 | 10 | 12 | 15 | 26 |
| AboveNormal | 5 | 7 | 9 | 11 | 14 | 25 |
| Normal | 4 | 6 | 8 | 10 | 13 | 24 |
| BelowNormal | 3 | 5 | 7 | 9 | 12 | 23 |
| Lowest | 2 | 4 | 6 | 8 | 11 | 22 |
| Idle | 1 | 1 | 1 | 1 | 1 | 16 |

例如Normal进程中的Normal线程基础值8，High进程中的Normal线程13，将进程类改Idle则4；同名线程相对层级不变，但基础数值不同。`ThreadPriority`自身枚举值0—4（Lowest到Highest）不是Windows绝对优先级；不要把它的Highest=4理解成内核优先级4。

Windows还有动态优先级，调度使用动态值而不是始终使用表中基础值。低于实时范围的线程可因输入或I/O等获得临时提升，再逐步回到基础值；16—31基础级不使用这种普通提升。优先级0保留给系统零页线程，不是托管Lowest。[Scheduling Priorities](https://learn.microsoft.com/en-us/windows/win32/procthread/scheduling-priorities)与[Priority Boosts](https://learn.microsoft.com/en-us/windows/win32/procthread/priority-boosts)支持这一区分。

只有就绪线程参与竞争；同层可轮流，符合调度约束的高优先级就绪线程可能抢占低优先级者，长期高优先级工作会使低优先级工作饥饿。多处理器与亲和性等使“任何地方只要有31就永不运行0—30”不能直接推广成全机绝对规则。

书图26-3示例的线程在等待，基础优先级8、当前12，累计31768次切换；约25:30:52的存活时间与约0.781秒CPU时间不同。它说明执行时间、等待时间、基础和动态值可以分别观测，不是所有等待线程都没有用途的证明。书中建议降低长计算优先级、使高优先级响应线程很快返回等待；它不保证实时deadline。原“网络数据到达后1ms内必须运行”在普通Windows/CLR上不能由设为Realtime获得硬实时保证；JIT、GC、调度及系统组件都可能影响延迟。本章不提升进程至High/Realtime，不做调度性能实验。

## 前台与后台线程

### 正常托管退出规则与默认值

前台/后台决定线程是否维持正常托管进程生存期，不代表工作重要性或UI是否在屏幕前。所有前台线程终止后，剩余后台线程不再维持托管执行环境；正常关闭会停止它们，不在它们中抛出用于收尾的异常。[官方合同](https://learn.microsoft.com/en-us/dotnet/standard/threading/foreground-and-background-threads)也说明Framework的AppDomain卸载会在进入该域的前台/后台线程中抛`ThreadAbortException`，与正常进程关闭不同。现代.NET不支持创建/卸载额外AppDomain。

前台线程仍活着不保证程序永远不退出：强制终止、未处理异常、显式退出等不受该正常生存期规则保护。所有前台结束到系统关闭也不是一个硬时长为零的操作，更不保证后台任务已经清理完成。

在书的.NET Framework多AppDomain应用模型中，一个应用的前台线程结束后，其他应用的前台线程仍可维持同一进程；只有整个进程的前台线程都结束，才开始这种正常关闭。这是纸本608页的完整解释，本地摘录26.9的概括漏了中间条件，不能把某一个AppDomain的应用退出等同整个进程退出。

| 创建方式 | 默认属性 | 需要注意的条件 |
| --- | --- | --- |
| `new Thread(...)`并启动 | 前台 | 可用IsBackground改变正常生存期作用 |
| `ThreadPool.QueueUserWorkItem` | 后台 | 线程池管理的工作线程为后台 |
| `Task.Run`在线程池运行委托 | 后台线程执行该委托 | Task本身不是线程；调用者若等待/await它，可由调用者的生存期保证流程继续 |

主入口线程通常为前台；从原生代码进入托管环境的线程默认标后台。`IsBackground`与优先级独立；不能因为线程是后台就推出它必低优先级。

原属性演示中的`...`是占位，以下用空委托保持演示目的：

```csharp
var t1 = new Thread(() => { });
Console.WriteLine(t1.IsBackground); // False
t1.IsBackground = true;
Console.WriteLine(t1.IsBackground); // True
```

该例没有Start，打印的是已构造Thread的属性，不能据它声称工作线程已运行。

### 原10秒前台例

下面是独立程序的Main片段，配套`using System; using System.Threading;`及类型外壳：

```csharp
static void Main()
{
    var worker = new Thread(() =>
    {
        Console.WriteLine("工作线程开始");
        Thread.Sleep(10000);
        Console.WriteLine("工作线程结束");
    }); // 默认前台。
    worker.Start();
    Console.WriteLine("Main 结束");
}
```

保留原运行示意作为一种可能顺序：

```text
Main 结束
工作线程开始
（工作线程等待约10秒，可能还需等待调度）
工作线程结束
（所有前台完成后，正常关闭）
```

`工作线程开始`也可先于`Main 结束`。两行各自按所属线程的程序次序执行，Main返回后worker作为前台仍维持正常运行；Sleep10000不是保证整程序恰好10秒终止。

### 仅将工作线程改后台的原例

```csharp
static void Main()
{
    var worker = new Thread(() =>
    {
        Console.WriteLine("工作线程开始");
        Thread.Sleep(10000);
        Console.WriteLine("工作线程结束"); // 后台退出风险：不保证运行到这里。
    });
    worker.IsBackground = true;
    worker.Start();
    Console.WriteLine("Main 结束");
}
```

原问答给出的“Main结束→工作线程开始→进程立即终止”可以是常见观察的一种，但worker可能还没有开始就被关闭，也可能先打印开始。若Main或关闭过程受到长时间延迟，worker也可能已完成，不能断言结束行**永远**不会打印。能依赖的规则是：后台worker不会使正常关闭等它完成。

```text
常见可能输出之一：
Main 结束
工作线程开始
（正常关闭停止未完成的后台线程，结束行未出现）

另一种可能：只有 Main 结束，worker未得到打印机会
```

关机/进程关闭直接停止后台线程时，不应依赖该线程的`finally`完成收尾；这不等于后台线程平常执行时不会跑finally，也不等于系统替它正确提交数据。UI窗口关闭还须看应用框架的消息循环和宿主生命周期，不能无条件等同Main返回。前台线程导致“窗口已关进程仍存在”有实际风险，但不是因此“杀不掉”，也不是操作系统中已退出待回收的僵尸进程概念。

同版书26.9的原例用命名方法`Worker`，只在等待后打印，与上述“开始/结束”问答例分开保留；原参数和调用顺序不变，修注释的确定性：

```csharp
using System;
using System.Threading;
public static class ForegroundBackgroundBookExample
{
    public static void Main()
    {
        Thread t = new Thread(Worker); // 默认前台。
        t.IsBackground = true;        // 注释此行可比较前台版本。
        t.Start();
        Console.WriteLine("Returning from Main");
    }
    private static void Worker()
    {
        Thread.Sleep(10000);
        // Main很快返回且开始正常关闭时，后台通常不会运行到这里。
        Console.WriteLine("Returning from Worker");
    }
}
```

正常前台版本会等这个Worker完成；后台版本不保证最后一行出现。它不需要另一个“工作线程开始”输出，不能把两份不同代码的输出拼成一次运行。

### 有价值的持久化任务与协作收尾

原书26.9以把内存缓冲区flush到磁盘说明确实希望完成的工作；重新计算电子表格单元格、建立记录索引可在重启后继续，是后台任务例。第9轮补充了关键服务线程与数据保存例：它们都可能很重要，后台属性只表示本线程不维持正常托管生命周期，不能代替事务、持久化协议或服务宿主管理。

“前台会阻止正常退出”不等于保证刷盘一定成功；应用仍须处理错误、取消与超时。原书还有UI组件偷偷创建前台线程导致进程不退的咨询案例，改用线程池后解决，因此作者建议尽量避免无控制的前台线程；不是禁止所有前台工作。

保留原CancellationToken→工作结束/SaveState→Join→Main退出流程。`DoOneBoundedUnit`和`SaveState`是应用占位方法，不是本章调用磁盘的代码：

```csharp
static void Main()
{
    using (var cts = new CancellationTokenSource())
    {
        var worker = new Thread(() =>
        {
            while (!cts.Token.IsCancellationRequested)
            {
                DoOneBoundedUnit(cts.Token); // 原“干活...”的占位：须有限、可取消。
            }
            SaveState(); // 原保存状态目的保留，须自行处理失败/持久性。
            Console.WriteLine("工作线程优雅退出");
        });
        worker.Start(); // 这里仍为前台，也可以配合主线程等待使用后台。
        Console.WriteLine("准备退出，通知工作线程...");
        cts.Cancel();
        worker.Join();
        Console.WriteLine("Main 结束，进程退出");
    }
}
```

这段代码主动执行Cancel，没有安装Ctrl+C或关窗口事件处理器；不能把注释“用户按Ctrl+C”当作已实现的功能。取消是请求，不是立即杀线程；工作须检查请求并结束阻塞操作，保存过程也可能失败。无限等待的Join不适合没有可靠结束条件的线程，实际应用可用有界Join、超时处理与宿主退出协议。本章只运行有界内存替身，不执行无限循环、保存用户文件或GUI关闭。

### 三个线程的生命周期图与异步边界

保留A(Main)、B(显式Thread)、C(池任务)这一组不同输入：

```text
进程启动：A前台(Main)，B前台(new Thread默认)，C后台(池委托)
  ↓ A结束
B仍运行 → 正常托管进程继续
  ↓ B结束；没有其他前台线程
正常关闭 → C若未完成，不因其存在而延长生命周期
```

“前台撑住进程、后台随进程结束”是生存期类比，限正常托管退出。ASP.NET等请求也可在线程池后台线程上执行，但服务宿主负责请求与关闭流程，不能把这归成不重要的工作。

Task/async-await没有单一前台/后台属性：`Task.Run`委托在池线程上执行；`await`续体可回到UI线程或其他执行上下文；异步Main或主线程等待Task使入口流程尚未完成。后台线程上的关键工作，应在允许正常退出前由应用等待它并处理失败；外部事务/日志能改善恢复性，但不能无条件使任意线程操作“必完成”。
