### 完整的MailManager、Fax和Pager场景

邮件到来时，MailManager通知关注它的Fax和Pager，每个侦听对象按自己的方式处理。以下完整程序保留四步关系；模拟邮件只是内存中的数据，不发送真实邮件或传真。

```csharp
using System;
using System.Threading;
public sealed class NewMailEventArgs : EventArgs {
    private readonly string from, to, subject;
    public NewMailEventArgs(string from, string to, string subject) {
        this.from = from; this.to = to; this.subject = subject;
    }
    public string From { get { return from; } }
    public string To { get { return to; } }
    public string Subject { get { return subject; } }
}
public class MailManager {
    public event EventHandler<NewMailEventArgs> NewMail;
    protected virtual void OnNewMail(NewMailEventArgs e) {
        EventHandler<NewMailEventArgs> temp = Volatile.Read(ref NewMail);
        if (temp != null) temp(this, e);
    }
    public void SimulateNewMail(string from, string to, string subject) {
        OnNewMail(new NewMailEventArgs(from, to, subject));
    }
}
public sealed class Fax {
    public Fax(MailManager manager) { manager.NewMail += OnNewMail; }
    public void OnNewMail(object sender, NewMailEventArgs e) {
        Console.WriteLine("Fax: " + e.Subject);
    }
    public void Unregister(MailManager manager) { manager.NewMail -= OnNewMail; }
}
public sealed class Pager {
    public Pager(MailManager manager) { manager.NewMail += OnNewMail; }
    private void OnNewMail(object sender, NewMailEventArgs e) {
        Console.WriteLine("Pager: " + e.Subject);
    }
    public void Unregister(MailManager manager) { manager.NewMail -= OnNewMail; }
}
class Program {
    static void Main() {
        var manager = new MailManager();
        var fax = new Fax(manager); var pager = new Pager(manager);
        manager.SimulateNewMail("Alice", "Bob", "Hello");
        fax.Unregister(manager); pager.Unregister(manager);
    }
}
```

输出依订阅顺序为`Fax: Hello`、`Pager: Hello`。无附加数据的事件可用`EventArgs.Empty`；不必每次创建空参数对象。类未密封时，protected virtual OnXxx是常见扩展点；密封类可用private非虚方法。派生类调用OnXxx引发通知，不能仅因继承了公开事件就直接读取基类的委托存储。

<a id="c11-sender"></a>
## sender、e和返回值：模式不等于语言强制

原疑问是：只有MailManager引发NewMail，为何不用`MailManager sender`？标准`EventHandler<NewMailEventArgs>`的第一个参数是object，回调通常写成`void Handler(object sender, NewMailEventArgs e)`。如果直接把回调改成`void Handler(MailManager sender, NewMailEventArgs e)`，它不能绑定到这个委托：调用方有权传入任意object，方法却只能接受MailManager。

反过来，自定义委托把sender声明成MailManager时，SmtpMailManager对象本来就能作为MailManager参数传入，继承不造成必然类型错误。只有回调要使用派生类专有成员时，才需判型或转换；不能说“无论怎样都必须转型，所以object毫无代价”。object的实际好处是标准模式统一，也允许无共同MailManager基类的发布者复用相同委托与回调。

原思考区借“依赖抽象而非具体实现”帮助理解通用性：回调只依赖需要的通知协议可减少发布者类型耦合。但object本身不会自动提供某个业务接口，访问具体能力仍需合适的类型契约或检查。

<a id="c11-sender-examples"></a>
### Smtp、Pop与强类型委托的对照

以下完整程序保留原MailManager→SmtpMailManager、无继承PopMailManager和订阅Handler三个场景。

```csharp
using System;
class NewMailEventArgs : EventArgs { }
class MailManager {
    public event EventHandler<NewMailEventArgs> NewMail;
    public void Raise() { var h = NewMail; if (h != null) h(this, new NewMailEventArgs()); }
}
class SmtpMailManager : MailManager { public string Protocol { get { return "SMTP"; } } }
class PopMailManager {
    public event EventHandler<NewMailEventArgs> NewMail;
    public void Raise() { var h = NewMail; if (h != null) h(this, new NewMailEventArgs()); }
}
delegate void TypedMailHandler(MailManager sender, NewMailEventArgs e);
class Program {
    static void Handler(object sender, NewMailEventArgs e) {
        Console.WriteLine(sender.GetType().Name);
        var smtp = sender as SmtpMailManager;
        if (smtp != null) Console.WriteLine(smtp.Protocol);
    }
    static void TypedHandler(MailManager sender, NewMailEventArgs e) {
        Console.WriteLine(sender.GetType().Name);
    }
    static void Main() {
        var smtp = new SmtpMailManager(); smtp.NewMail += Handler; smtp.Raise();
        var pop = new PopMailManager(); pop.NewMail += Handler; pop.Raise();
        TypedMailHandler typed = TypedHandler; typed(smtp, new NewMailEventArgs());
        // smtp.NewMail += TypedHandler; // 反例：CS0123，标准委托sender是object
    }
}
```

依次输出`SmtpMailManager`、`SMTP`、`PopMailManager`、`SmtpMailManager`。若业务已保证类型，也可写原式`var smtp = (SmtpMailManager)sender;`，错误发布者则会抛出InvalidCastException；本例用`as`保留同一回调可处理Pop的条件。

Visual Studio在输入`+=`并接受生成回调时，常得到如下方法体片段；工具行为随版本和设置变化，参数名本身不是绑定依据。

```csharp
// 放在具有smtp字段的侦听类型内部：
void Subscribe() { smtp.NewMail += SmtpMailManager_NewMail; }
private void SmtpMailManager_NewMail(object sender, NewMailEventArgs e) { }
```

<a id="c11-event-return"></a>
### void、多播返回值与ResolveEventHandler

| 设计点 | 准确理由 |
| --- | --- |
| object sender | 统一模式，允许不同发布者复用；需具体成员时检查实际类型 |
| EventArgs类及参数名e | 附加信息和命名约定，工具容易识别；e不是语言强制名称 |
| void返回值 | 通知通常不需要挑选多个回调的结果；并非多播绝对不能获得多个返回值 |

普通多播委托调用非void方法时，返回最后一个实际执行方法的返回值；前面方法的结果不会自动汇总。原对话的foreach是这个概念的示意：取出`GetInvocationList()`，再逐个调用。以下完整程序把原伪代码补成类型正确的返回值收集，说明语言上做得到。

书中“事件处理程序”指事件处理方法，VB语境可指Sub过程，不是另一个独立运行的进程。

```csharp
using System;
class Program {
    static int First() { return 1; } static int Second() { return 2; }
    static void Main() {
        Func<int> handlers = First; handlers += Second;
        Console.WriteLine("normal: " + handlers());
        foreach (Func<int> handler in handlers.GetInvocationList())
            Console.WriteLine("individual: " + handler());
    }
}
```

输出`normal: 2`、`individual: 1`、`individual: 2`。若某处理程序抛出未捕获异常，后续处理程序通常不再执行，不是必定通知完所有对象。

`ResolveEventHandler`是原对话的非void例外，其历史签名返回Assembly；现代API的可空注解可显示为`Assembly?`，不表示原C# 5支持可空引用语法。

```text
public delegate System.Reflection.Assembly ResolveEventHandler(
    object sender, System.ResolveEventArgs args);
```

Framework的AssemblyResolve有专门协议：处理程序未能解析时返回null；多处理程序时按顺序询问，取得首个非null结果后停止。不能把它套成“正常多播自动返回最后一个，所以解析必选最后一个”。标准object/e/void模式是设计指导，事件语言语法也允许其他委托签名。[AssemblyResolve契约](https://learn.microsoft.com/en-us/dotnet/api/system.appdomain.assemblyresolve?view=netframework-4.8)

<a id="c11-type-member"></a>
## delegate是类型，event是成员

原疑问“event到底和delegate区别在哪里”需先分清三个东西：`delegate`声明委托类型；委托字段保存这个类型的对象；`event`声明提供登记/注销接口的成员。把delegate与event排成包含集合关系，或把event看成另一个委托类型，都会混淆层次。

| 概念 | 是什么 | 原类比的准确范围 |
| --- | --- | --- |
| delegate声明 | 定义一种委托类型 | 类似用class定义类型，但有专门语言与CLI规则 |
| event声明 | 类型中的事件成员 | 与字段、属性、方法一样属于成员类别 |
| EventHandler | 具体委托类型 | 可与List<T>等类型在“类型”层面比较 |
| `public event EventHandler NewMail` | 使用EventHandler类型的事件成员 | `public List<string> Names`也是使用某类型的成员，但它是字段，不是事件 |

<a id="c11-field-permissions"></a>
### 裸字段允许覆盖、清空和外部调用

以下类型与方法体片段保留原NewMail清空、调用、覆盖三例。这里只讨论公开字段暴露的权限，不表示所有“不写event”的设计都一定公开裸字段；也可以私有保存委托，另设AddCallback方法。

```csharp
public class MailManager {
    public EventHandler<NewMailEventArgs> NewMail;
}
// 调用方方法体内，mailManager、args和MyHandler已定义：
mailManager.NewMail = MyHandler;
mailManager.NewMail(mailManager, args); // 外部可直接调用，未订阅时需防null
mailManager.NewMail = null;            // 外部可清空所有订阅
```

换成field-like事件后，调用方能`+=`和`-=`，不能取得委托值、赋值或调用。

```csharp
public class MailManager {
    public event EventHandler<NewMailEventArgs> NewMail;
    public void Test(NewMailEventArgs args) {
        var h = NewMail; if (h != null) h(this, args); // 声明事件的类型内部
    }
}
// 调用方方法体内：
mailManager.NewMail += Handler;
mailManager.NewMail -= Handler;
// mailManager.NewMail = null;                // 反例：CS0070
// mailManager.NewMail(mailManager, args);    // 反例：CS0070
// mailManager.NewMail?.Invoke(mailManager, args); // C#6+也受同一权限约束
```

原对话两个权限表各有侧重点，分别保留。

| 外部操作 | 裸委托字段 | field-like或自定义访问器事件 |
| --- | --- | --- |
| += | 允许 | 相应事件可访问时允许 |
| -= | 允许 | 相应事件可访问时允许 |
| =赋值 | 允许 | 不允许 |
| 直接Invoke | 允许，须处理null | 不允许 |

| 操作范围 | 裸委托字段 | 事件 |
| --- | --- | --- |
| 外部+= | 允许 | 允许登记 |
| 外部-= | 允许 | 允许注销 |
| 外部= | 允许 | 不允许替换整条链 |
| 外部Invoke | 允许 | 不允许 |
| 内部Invoke | 读取字段后可调用 | field-like事件在声明类型内可读；自定义事件需从自己的后备存储取得委托 |

`public Action OnDead;`也有相同裸字段权限；加`event`后变为事件成员。event保护的是订阅接口，不能据此保证处理程序无异常、发布者没泄漏或所有对象状态线程安全。[C#事件规则](https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/language-specification/classes#158-events)

<a id="c11-property-analogy"></a>
### 字段与属性的类比

原例的两种Age声明是两个替代方案，不能在同一类型里同时声明同名成员。

```csharp
class FieldExample { public int Age; }
class PropertyExample { public int Age { get; set; } }
```

| 对比 | 字段/属性 | 委托字段/事件 |
| --- | --- | --- |
| 常见存储 | 字段 | 委托字段，也可存入EventSet |
| 对外暴露 | 属性可提供读取/写入接口 | 事件提供登记/注销接口 |
| 访问器 | get/set | add/remove |
| 封装逻辑 | 验证、计算等 | 同步、过滤、日志等 |
| 设计意图 | 管理状态访问 | 管理订阅访问 |

这是接口封装的类比：计算属性不必有后备字段，自定义事件也不必每个事件一个字段。事件没有隐含的public getter让外部拿到所有订阅者。

属性可只定义get或set；C#自定义事件需要add和remove两个访问器，field-like写法由编译器提供相应登记/注销机制。事件声明和委托类型不冗余：前者建立使用回调的成员契约，后者表示回调的类型与对象，不能只靠公开字段代替相同权限。

<a id="c11-lowering"></a>
## 编译器实现：对应关系不是可手写的普通类源码

原疑问“delegate像class、event像字段，为什么写法对不上”指出了类比的边界。C#为委托类型和事件成员提供专用声明语法。委托在CLI元数据中是特殊的密封引用类型，通常派生自MulticastDelegate；C#不允许开发者直接用普通class继承Delegate或MulticastDelegate。

```csharp
public delegate void MyDelegate(int x);
```

下面保留原构造器、Invoke、BeginInvoke和EndInvoke四个成员，但这是**元数据形状示意**，不是可编译C#类；省略号不代表能自行补普通方法体。

```text
.class sealed MyDelegate extends System.MulticastDelegate
  .ctor(object target, native int method)
  Invoke(int32 x) -> void
  BeginInvoke(int32 x, AsyncCallback callback, object state) -> IAsyncResult
  EndInvoke(IAsyncResult result) -> void
```

Framework历史上支持委托BeginInvoke/EndInvoke的异步调用。现代.NET仍能看到这些生成方法，但执行BeginInvoke会抛PlatformNotSupportedException；新代码选择Task等机制，不以“元数据有方法”推断运行时支持。

<a id="c11-lowering-tables"></a>
### AIP与事件的两张对应表

原正式答的两行表比较生成成员；思考区另有三行表包含调用动作，信息不完全重复，分别保留。

| 表层声明 | 典型生成结构 | 含义 |
| --- | --- | --- |
| `public int Age { get; set; }` | 私有自动属性后备字段、get_Age、set_Age | 属性及其访问器；后备字段不是可在相同源码再声明的同名Age |
| `public event MyDelegate MyEvent;` | 对普通具体类型的field-like实例事件：私有委托字段、add_MyEvent、remove_MyEvent | 事件元数据和访问器；自定义访问器事件可另选存储 |

| 表层语法 | 编译后对应 | 类比 |
| --- | --- | --- |
| `delegate void MyDel(int x);` | 特殊密封委托类型及Invoke等方法 | 类型定义，但不能用普通继承类完全替代 |
| `public event MyDel MyEvent;` | field-like事件的委托存储和add/remove | 类似属性封装存储 |
| `MyEvent += handler;` | 调用事件add访问器 | 类似Age赋值调用set_Age；并非每个自定义add都必定Combine |

`add_NewMail`、`remove_NewMail`是元数据方法名称。以下是**实现关系示意**，不能和同名事件一起原样作为C#源码，也不表示C#调用方可直接调用这些访问器。

```text
private EventHandler NewMail;             // 典型field-like事件存储
public void add_NewMail(EventHandler value) { /* Combine与同步 */ }
public void remove_NewMail(EventHandler value) { /* Remove与同步 */ }
```

原稿还把`public MyDelegate NewMail { add... remove... }`称为伪代码；真实C#的这个位置需要`event`，不是普通属性语法。可编译类型片段如下，**单线程教学版**，并发版本见CAS节。

```csharp
using System;
public delegate void MyDelegate(int x);
class MailManager {
    private MyDelegate _newMail;
    public event MyDelegate NewMail {
        add { _newMail = (MyDelegate)Delegate.Combine(_newMail, value); }
        remove { _newMail = (MyDelegate)Delegate.Remove(_newMail, value); }
    }
}
```

手写`_newMail += value`或Combine赋值不是自动等价于编译器field-like访问器的线程安全实现；具体编译器算法也不是所有CLI实现都必须采用同一CAS源码。

<a id="c11-method-group"></a>
### 方法组转换与“只订阅没有引发”

思考区说`MyDel del = Method`是委托重载赋值运算符，这是错误。C#不能用户定义重载普通赋值`=`；这里是方法组到委托的转换，创建或取得与目标/方法相绑定的委托对象。`string`与System.String的别名有助于理解语言专用表示，但委托包含独特规则，不能称它和普通class完全无区别。

```csharp
using System;
delegate void MyDel(int x);
class Program {
    static void Method(int x) { Console.WriteLine(x); }
    static void Main() { MyDel del = Method; del(7); }
}
```

输出7。原对话的另一个完整程序只登记打印Hi的lambda，没有引发事件，**没有输出**；不能以订阅动作替代通知动作。

原另一个语法类比是using语句的资源释放可降低为try/finally。它能说明语言写法与底层实现不必逐字相同，不能证明开发者可以手写普通class继承MulticastDelegate。

```csharp
using System;
public delegate void Del();
public class Test { public event Del MyEvent; }
class Program {
    static void Main() {
        Test t = new Test();
        t.MyEvent += () => Console.WriteLine("Hi");
    }
}
```

编译后订阅动作对应实例`t`的add_MyEvent访问器，参数是委托；不是静态`Test.add_MyEvent(t, ...)`的普通C#可调用API。编译器会对直接访问器调用报CS0571。[委托历史异步支持](https://learn.microsoft.com/en-us/dotnet/standard/asynchronous-programming-patterns/asynchronous-programming-using-delegates)

<a id="c11-snapshot"></a>
## 引发事件：先取得一次快照，再检查和调用同一值

原对话反复追问`EventHandler<NewMailEventArgs> temp = Volatile.Read(ref NewMail)`和局部变量会否被优化。先区分两个问题：同一次通知能否避免“检查到非null、调用时又读到null”的竞态；能否保证观察到最新订阅、同步全部对象状态。前者可用单次读取的快照解决，后者需要另行设计同步契约。

<a id="c11-three-versions"></a>
### 三个历史版本与一个现代写法

以下是**放在声明field-like NewMail事件类型内的方法片段**，NewMailEventArgs已定义。

```csharp
// 版本1：两次读取共享字段，存在check-invoke竞态
protected virtual void OnNewMail1(NewMailEventArgs e) {
    if (NewMail != null) NewMail(this, e);
}
// 版本2：普通局部快照，检查和调用同一委托值
protected virtual void OnNewMail2(NewMailEventArgs e) {
    EventHandler<NewMailEventArgs> temp = NewMail;
    if (temp != null) temp(this, e);
}
// 版本3：用volatile读取取得局部快照，附加读取排序语义
protected virtual void OnNewMail3(NewMailEventArgs e) {
    EventHandler<NewMailEventArgs> temp = Volatile.Read(ref NewMail);
    if (temp != null) temp(this, e);
}
```

现代C# 6+还可以写以下方法片段；`?.`仅求值一次接收者，等价于局部快照检查，避免在检查后另读共享字段。Microsoft官方将这种调用描述为线程安全的委托调用，其范围是这个竞态，不是所有处理程序线程安全。

```csharp
protected virtual void OnNewMail(NewMailEventArgs e) {
    NewMail?.Invoke(this, e);
}
```

引用读取是原子的，不会读到“写到一半的半个引用”。委托调用列表不可变；字段可以被换成另一条列表，但已经取得的委托对象不会原地变成null。处理程序所引用的目标对象仍可能可变；“委托不可变”不等于订阅者状态不可变。

<a id="c11-race-tables"></a>
### 原两张时序表：必须是退订使字段变null

原答两张表都把`+=`、正在构造委托链或没写完，描述成从非null变null并导致异常。只有不断添加合法处理程序，不会把一个非null链改成null。正确保留原教学目的，应换成**另一个线程移除最后一个订阅者**。

| 线程A：修改订阅 | 线程B：版本1引发 |
| --- | --- |
| NewMail当前含一个处理程序 | 读取NewMail，检查非null |
| `NewMail -= handler`移除最后一个，安装null | 已进入if，尚未执行调用 |
| 更新完成 | 第二次读到null，调用抛NullReferenceException |

下一张保留原“委托链更新与两次访问”的视角，不用“半成品对象”解释。

| 线程A：链的变化 | 线程B：读取动作 |
| --- | --- |
| 起初链为handler | `if (NewMail != null)`成立 |
| `Delegate.Remove`产生结果null，更新字段 | 检查与调用之间可被调度 |
| 字段现在为null | `NewMail(this,e)`再读字段并失败 |
| 若B早已取得非null局部快照 | 调用原handler，尽管它现在已退订 |

原另一个反例`if (NewMail != null) { var temp = NewMail; temp(this,e); }`仍两次读：先检查字段，再给temp赋值，未解决问题。必须先赋局部值，再检查这个局部值。

<a id="c11-volatile-check-only"></a>
### 仅检查时使用Volatile.Read仍然不够

下面**方法体反例**保持原场景：第一次是volatile读，调用又用普通字段读。最后一次退订仍可在二者之间发生。

```csharp
if (Volatile.Read(ref NewMail) != null) {
    NewMail(this, e); // 第二次读取；不是一次快照调用
}
```

正确的两种简写片段是`var temp = NewMail; temp?.Invoke(this,e);`和`var temp = Volatile.Read(ref NewMail); if(temp != null) temp(this,e);`。读取temp不会再读取NewMail：Volatile修饰的是取得快照这一次访问，不强制每次使用temp刷新共享字段。

<a id="c11-snapshot-results"></a>
### 受控验证及通知语义

验证工作区用两个有超时的线程控制顺序：引发线程先读，退订线程移除最后一个处理程序并确认完成，随后引发线程调用。Framework4.8和.NET10得到相同结果：版本1为`NullReferenceException，回调0次`；普通快照和Volatile快照均为`调用成功，回调1次`；共享字段最终均为null。这证明本例中的单次快照与两次读差别，不穷尽所有调度或证明“总是最新”。

原直播类比可这样保留：共享字段是不断换演员的舞台名单，读到的委托是当时拍下的名单照片。导演之后改名单，照片不随之改变；拿照片通知可以避免前后读到两个名单，却不能保证照片包含刚加入的人。原“导演收走相机”不能类比成Microsoft JIT会重新查看舞台，这是把去掉变量名与新增共享读取混淆。

订阅者可能在`-=`返回后仍被另一线程的旧快照调用。如果需要“退订完成后绝不再回调”，须添加生命周期、停止标志或等待正在执行的通知等协议，普通事件接口不自动给出该承诺。

<a id="c11-volatile"></a>
### Volatile.Read规定排序，不保证最新

Volatile读取具有获取（acquire）语义，限制后续相关内存操作移到读取之前；Volatile写具有释放（release）语义，限制之前的操作移到写之后。不能扩大为“所有操作都不可重排”“一定绕过CPU缓存”或“总能看到最新写入”。官方甚至说明：一个处理器volatile写后，另一个处理器后续volatile读仍可能读到旧值。需要哪种跨线程关系，应按完整读写协议判断。[Volatile契约](https://learn.microsoft.com/en-us/dotnet/api/system.threading.volatile?view=net-10.0)

`Volatile.Read(ref x)`针对这一次读取；对引用类型，普通引用读本来就原子，Volatile还增加相应排序语义。对某些64位数值，Volatile方法在32位处理器上也提供原子访问，因此也不能统一说“Volatile不是原子操作”。它不把“读取—判断—调用”整个序列变成一个不可分割的操作。

原volatile字段例是**私有委托字段**，不是加volatile修饰的event：

```csharp
private volatile EventHandler<NewMailEventArgs> NewMail;
```

| 对比维度 | volatile字段 | Volatile.Read |
| --- | --- | --- |
| 可读性 | 声明处说明整个字段的访问语义，访问处不逐次标注 | 调用处明确显示这一次volatile读取 |
| 控制粒度 | 字段的读写按volatile规则 | 选择特定读；配套写可用Volatile.Write等 |
| JIT/平台 | 语言规定语义，平台决定实现指令 | API规定语义，平台决定实现指令 |
| 选择依据 | 有类型限制，适合字段整体采用该规则 | 可用于数组元素等场景及单次访问；不是无条件比旧语法更优 |

锁通常更容易建立完整临界区。Volatile和CAS需要精确判断，不能从“读是原子”推出整个复合操作安全。

状态标志位是否采用volatile也取决于通信协议，还可使用lock或Interlocked等；不是见到一个状态字段就必须volatile。x86/x64与ARM可能采用不同指令实现规定语义，不据此声称每次Volatile.Read必插入某条固定硬件屏障指令。

原后续提示还提到`Interlocked.CompareExchange(ref NewMail, null, null)`读法：当字段非null时比较失败并返回原引用，字段为null时比较成功但仍写null，因此不清空非null订阅链；可将其返回值当快照使用。它具有Interlocked操作的同步语义，不是“返回值永远最新”或每次通知必须用它的要求。对于自定义事件，要对其实际后备字段使用该读法。

<a id="c11-jit-history"></a>
### 原书Microsoft JIT限定为何不能反着解读

原书先给出对局部变量被移除、新增堆读取的历史理论担忧，随后明确说Microsoft JIT尊重这一不变量、避免这种新增读取。对话正式答却把这句话解释成“普通temp只在单线程安全、JIT可能每次重读”，与用户引用的限定相反。应把两处连在一起读：不要截掉实现前提，不把担忧写成已经复现的Microsoft JIT行为；现代C#官方单次快照/`?.Invoke`说明也支持防check-invoke竞态的用法。

| 术语 | 在这个问题中的含义 |
| --- | --- |
| JIT编译器 | 把IL编译为机器码的实现 |
| 尊重 | 在这里避免改变单次观察共享值的关键行为 |
| 不变量invariant | 局部temp继续代表取得的那一委托引用，不是共享字段从此不变 |
| 堆内存 | MailManager引用类型实例中的NewMail字段；并非凡引用类型字段都永远在堆上这一泛化规则 |
| 新的读取动作 | 原来只读一次，却又从共享字段读取新的值 |

原寄存器例保留为**伪汇编**，不是实际委托Invoke反汇编。真实委托调用还涉及目标、方法指针、调用列表等，`call rax`只说明复用一个读到的值。

```asm
; 示意：读到的引用可以保留在寄存器中
mov rax, [NewMail]
test rax, rax
je done
call rax              ; 仅示意“使用同一观察值”，非真实委托调用机器码
done:
```

Volatile.Read返回后，temp也可以保留在寄存器中；这不违反volatile，因为不要求再次读取原字段。原微信群公告类比保留为“把公告记下来，后来按记下的内容办事”，刷新公告是另一次读取，不能把Volatile想成读一次后每次用记忆都会自动刷新。思考区的“共享白板与手边草稿纸”是另一类比：白板可被别人改，抄到纸上的快照仍代表当时内容；acquire只是对有关读写顺序的要求，不保证纸上绝对最新。

原书Microsoft .NET Framework JIT条件不是所有CLI实现的共同实现细节。现代.NET/CoreCLR、Unity Mono和IL2CPP要分别讨论；IL2CPP是AOT，不是另一个“IL2CPP JIT”。不制造随机压力实验来声称编译器必新增读取。

<a id="c11-callback-lock"></a>
### 锁内调用未知处理程序的边界

原方法体片段：

```csharp
lock (_lock) {
    NewMail?.Invoke(this, e); // C#6+；在锁内执行订阅者代码
}
```

若所有相关读写都使用同一个锁，可提供相应同步；只在引发时锁住，订阅修改却不遵循同一锁，不等于冻结了订阅链。Monitor允许同一线程重入，因此处理程序同线程再次获取同一锁不自动死锁。风险来自执行未知代码时持锁：回调可能等待另一线程，而那一线程正等待此锁，或两线程以相反顺序获取两个锁形成等待环。取快照后锁外调用能减少这类耦合，但需接受订阅快照和状态可能变化。

重入与进入/退出配对要求见[Monitor.Enter官方说明](https://learn.microsoft.com/en-us/dotnet/api/system.threading.monitor.enter?view=net-10.0)。

<a id="c11-cas"></a>
## 添加订阅的CAS循环：观察、派生、比较交换、重试

原问的`add_NewMail`片段有两处编译问题：外层已声明newMail，内层又声明同名局部变量；随后CAS使用未声明的newHandler。C#不仅禁止同一块重复声明，也限制嵌套局部作用域的同名声明。这里按变量职责修正，不把聊天摘录的错误归给原书作者。

<a id="c11-cas-names"></a>
### 两种命名和三个不同角色

| 原Q7两变量导读 | 准确含义 |
| --- | --- |
| preHandler | 本次尝试用作comparand的旧引用 |
| newMail | 初始读到的引用，之后接收CAS实际返回的旧引用；不保证始终是字段此刻的最新值 |

原Q8将第二个变量改为currentNewMail，不改变算法，名称区分更清楚。

| 三变量 | 含义 |
| --- | --- |
| preHandler | 本轮依据的旧值 |
| newHandler | 基于preHandler与value组合得到的候选值 |
| currentNewMail | 初始观察值或CAS返回的旧值，用于判断成功和下一轮重试 |

下面**完整类型片段**用实际C# event add/remove表达元数据`add_NewMail`的教学逻辑，补全原remove省略号；两者都按引用身份判断成功。NewMailEventArgs是事件附加参数。

```csharp
using System;
using System.Threading;
public class NewMailEventArgs : EventArgs { }
public class MailManager {
    private EventHandler<NewMailEventArgs> _newMail;
    public event EventHandler<NewMailEventArgs> NewMail {
        add {
            EventHandler<NewMailEventArgs> currentNewMail = _newMail;
            EventHandler<NewMailEventArgs> preHandler;
            do {
                preHandler = currentNewMail;
                EventHandler<NewMailEventArgs> newHandler =
                    (EventHandler<NewMailEventArgs>)Delegate.Combine(preHandler, value);
                currentNewMail = Interlocked.CompareExchange(
                    ref _newMail, newHandler, preHandler);
            } while (!ReferenceEquals(currentNewMail, preHandler));
        }
        remove {
            EventHandler<NewMailEventArgs> currentNewMail = _newMail;
            EventHandler<NewMailEventArgs> preHandler;
            do {
                preHandler = currentNewMail;
                var newHandler = (EventHandler<NewMailEventArgs>)Delegate.Remove(preHandler, value);
                currentNewMail = Interlocked.CompareExchange(ref _newMail, newHandler, preHandler);
            } while (!ReferenceEquals(currentNewMail, preHandler));
        }
    }
    protected virtual void OnNewMail(NewMailEventArgs e) {
        var temp = Volatile.Read(ref _newMail);
        if (temp != null) temp(this, e);
    }
    public void SimulateNewMail() { OnNewMail(new NewMailEventArgs()); }
}
```

算法五步：先读到当前链；保存到preHandler；根据它组合候选链；CAS在字段仍引用preHandler时安装候选链；失败时拿返回的实际旧值重新组合和尝试。初始普通引用读取可以参与这个CAS算法，正确性不要求每次初始读都必须Volatile.Read；关键是有条件安装及失败后重新派生候选值。这里CAS是原子比较交换，线程仍可在它前后被调度，不是整个线程永远不能中断。

Interlocked.CompareExchange还提供其同步内存排序语义，这是原思考区联系Volatile的前提；并非只有原子替换而没有同步作用。现代.NET实现规格将Interlocked方法列为full-fence操作，这是一手的当前.NET实现说明，不冒称所有CLI或Unity后端共同规则。这里它协调这条共享委托链的更新，完整对象状态和回调协议仍需另外满足相应同步条件，不能扩大成任意业务自动同步。与普通读取/acquire的区别见[Volatile说明](#c11-volatile)及[.NET内存模型规格](https://github.com/dotnet/runtime/blob/main/docs/design/specs/Memory-model.md)。

<a id="c11-cas-identity"></a>
### 为什么不能用delegate的==判断CAS成功

泛型引用CompareExchange按**引用身份**比较；返回交换前的引用。delegate的`==`比较委托类型、目标方法和调用列表等值，不是同一个对象才相等。两个不同委托实例完全可能值相等。原`while (newMail != preHandler)`以及`if (CAS(...) == pre)`会因此误判成功。[CompareExchange契约](https://learn.microsoft.com/en-us/dotnet/api/system.threading.interlocked.compareexchange?view=net-10.0)

| 本轮结果 | 判断与动作 |
| --- | --- |
| `ReferenceEquals(observed, preHandler)`为true | CAS比较成功，安装本轮候选值，退出 |
| 上式为false | CAS比较失败，observed是实际旧值，以它重新生成候选链 |

原思考区用普通if/else说明CAS，保留为**语义伪代码**；比较也改为identity。普通C# if、读、赋值三个动作不能提供同样原子性。

```text
原子地完成：
  old = 字段当前值
  如果 ReferenceEquals(old, preHandler)，字段 = newHandler
  返回 old
```

共享实测显式创建两个同方法、不同身份的委托a0和a1：先读a0，再受控将字段换成a1，CAS以a0为比较值失败并返回a1。Framework4.8和.NET10都得到`delegate_equality=True, reference_equality=False, handlers=1`；按身份重试后`handlers=2`。不是观察到值相等就说明“没人抢”，也不能宣称这里绝无任何ABA相关状态讨论。对本算法，字段回到同一引用后成功安装基于该引用的候选链未必构成错误；是否存在问题要看算法需要维护的状态，不能套一个无条件结论。

<a id="c11-cas-two-threads"></a>
### 两个订阅者从null开始的交错

保持原A/B场景：字段初始null，线程A准备安装A，线程B准备安装B。若A先CAS成功，B的comparand仍是null，B失败得到A，重新Combine为A+B，再CAS成功。最终两个订阅都在链中；A/B先后不固定，最终顺序可不同。

```text
初始：NewMail = null
线程A：pre=null，next=A
线程B：pre=null，next=B
A CAS(null -> A)成功
B CAS(null -> B)失败，返回A
B 重算next=A+B，CAS(A -> A+B)成功
```

反例是`newHandler = Delegate.Combine(field,value); field = newHandler;`整个读改写不原子。两个线程均以null构造后分别赋值，最终只剩A或B；若恰好串行执行也可能都保留，因此是“可能丢更新”，不是每次必丢。验证用Barrier确保两者在第一次观察null并构造候选后才继续：Framework和.NET10均为`naive:1`、`CAS:2`。Barrier只放第一次尝试，失败重试不会再次等待已经结束的另一个线程。

| 实现 | 优点 | 边界/代价 |
| --- | --- | --- |
| lock | 容易表达完整临界区 | 可阻塞；错误锁顺序/等待关系会死锁，同线程重入本身不会 |
| CAS重试 | 此更新路径不用互斥锁，失败时重算 | 代码复杂，高竞争时重试与分配增加；不保证每个线程无饥饿，也不保证任何负载下最快 |

“乐观修改”类比：先抄登记簿、写候选新名单，交回时确认登记簿仍是抄下的那一版本；变了就基于实际版本再写。这不是保证订阅通常高频、CAS一定性能最优的依据。

Combine/Remove保持委托调用列表对象的不可变性，但不必每次新分配：`Delegate.Combine(null,value)`可直接返回value；对null订阅也可能无变化。不可变列表可以支持引用快照，不代表引用的订阅者对象不可变。[Combine的null处理](https://learn.microsoft.com/en-us/dotnet/api/system.delegate.combine?view=net-10.0)

<a id="c11-stale-combine"></a>
### 不能把Combine只放在循环外

原反例试图省掉重试中的Combine。下面**类型内部方法反例**保留错误意图，但改用引用身份判断，让问题集中在候选值过期。

```csharp
void BadAdd(EventHandler<NewMailEventArgs> value) {
    var newHandler = (EventHandler<NewMailEventArgs>)Delegate.Combine(_newMail, value);
    while (true) {
        var pre = _newMail;
        if (ReferenceEquals(Interlocked.CompareExchange(ref _newMail, newHandler, pre), pre))
            break;
    }
}
```

从null构造候选B后，另一线程已安装A；本线程随后读pre=A，CAS比较成功，却用仍为B的候选覆盖A。受控验证为`CAS-success:True, handlers:1, A-preserved:False`。这里无需发生A→B→A的ABA，也无需任何失败重试就会丢更新。候选链必须在每轮基于本轮pre重新生成，原Q7的分段Combine/CAS/循环步骤因此不能任意移出。

<a id="c11-contract"></a>
## “公开”“侦听”与“显式实现事件”说的是不同视角

公开事件是发布者对相应消费者提供的订阅契约；public便于其他类型订阅，internal、protected等也可在各自可访问范围内提供事件。原private事件示例只在自身范围使用，不能因“事件公开模式”一词就推断语言只允许public事件。声明一个事件不要求业务上一定使用object/EventArgs/void模式。

公开后，事件名称、委托签名和附加数据类型成为消费者依赖的API；版本升级随意改变它们可能破坏调用方。保持对外声明和协议，可以在内部将单字段存储换成EventSet，而不改变消费者的`+=`/`-=`用法。

```csharp
using System;
class MailManager {
    private event EventHandler<NewMailEventArgs> NewMail;
}
```

这是独立类型片段；NewMailEventArgs使用前文类型。侦听者做的是原调用`mailManager.NewMail += fax.OnNewMail;`，注销时用相应`-=`。Fax中的OnNewMail是回调方法名；发布者OnNewMail是受保护的引发方法，同名不等于同一个职责。

```text
MailManager：输入 -> EventArgs -> OnNewMail -> NewMail通知契约
                                           |
                                  +=登记 / -=注销
                                           v
                                  Fax / Pager回调

很多事件的发布者：自定义add/remove -> EventSet -> 按key找到委托链
```

回调执行通常同步发生在引发线程。耗时回调会延迟后续通知；某回调抛出未处理异常可能终止当前调用链。需要异步、隔离异常、限速或分发到UI线程时，应建立明确协议，event本身不自动创建线程或异常隔离。

订阅一般使发布者的委托链强引用实例方法的目标对象。**发布者仍可被根引用且链未解除**时，订阅者可能因此被保活；如果整个发布者与订阅者都不可达，GC可回收它们，循环引用本身不构成永久泄漏。不必把所有`-=`遗漏都判成泄漏，长期服务与短寿命视图组合尤其需要设计注销。

订阅目标引用与注销模式参考[微软事件订阅/注销说明](https://learn.microsoft.com/en-us/dotnet/csharp/programming-guide/events/how-to-subscribe-to-and-unsubscribe-from-events)。

<a id="c11-custom-events"></a>
### 自定义add/remove仍然使用event

原“显式实现事件就是不用event关键字、自己维护委托吗”应回答：书中这里是**保留event，自定义add/remove及存储**。可以用字典、一个字段、框架存储或其它机制。没有event时，类型也能提供普通AddCallback/RemoveCallback方法，但这不是C#事件成员。

| 维度 | field-like事件 | 自定义访问器事件 |
| --- | --- | --- |
| 存储 | 典型具体类型声明由编译器维护对应委托字段 | 开发者选择字段、EventSet、转发等 |
| add/remove | 编译器生成 | 开发者编写 |
| 用途 | 少量简单事件方便 | 多事件稀疏存储或特殊登记逻辑；不是数量多才可用 |

“event是壳，add/remove是肉，显式实现是换肉不换壳”可作为记忆类比：壳代表订阅接口，肉代表存储与登记实现。外部权限不因换成EventSet而放宽。add/remove可做日志、权限判断、过滤、限流、订阅计数或转发；具体行为须作为契约说明，不能默认所有自定义事件都线程安全。

<a id="c11-component-example"></a>
### 原IComponent与object事件键片段的补全

原稿`MailManager : IComponent`只写了NewMail，没有实现Site、Disposed和Dispose，且object键版本的EventSet不能直接当成下节EventKey键版本。这里保留**组件发布者、object静态键、自管事件存储**的场景：继承Component取得IComponent实现，单独用ObjectEventSet适配object键；不声称下列存储是实际WinForms实现。

```csharp
using System;
using System.Collections.Generic;
using System.ComponentModel;
public sealed class ObjectEventSet {
    private readonly Dictionary<object, Delegate> events = new Dictionary<object, Delegate>();
    public void Add(object key, Delegate handler) {
        if (handler == null) return;
        lock (events) { Delegate old; events.TryGetValue(key, out old);
            events[key] = Delegate.Combine(old, handler); }
    }
    public void Remove(object key, Delegate handler) {
        if (handler == null) return;
        lock (events) { Delegate old; if (!events.TryGetValue(key, out old)) return;
            var next = Delegate.Remove(old, handler);
            if (next == null) events.Remove(key); else events[key] = next; }
    }
    public Delegate Get(object key) {
        lock (events) { Delegate value; events.TryGetValue(key, out value); return value; }
    }
}
public class MailManager : Component, IComponent {
    private readonly ObjectEventSet _events = new ObjectEventSet();
    private static readonly object _newMailKey = new object();
    public event EventHandler<NewMailEventArgs> NewMail {
        add { _events.Add(_newMailKey, value); }
        remove { _events.Remove(_newMailKey, value); }
    }
    protected virtual void OnNewMail(NewMailEventArgs e) {
        var h = (EventHandler<NewMailEventArgs>)_events.Get(_newMailKey);
        if (h != null) h(this, e);
    }
}
```

这是类型片段，使用前文NewMailEventArgs。继承Component不自动解除这里自定义的NewMail订阅；如业务需要，另定义Dispose清理策略。原例的目的在自定义存储，不在组件生命周期全部实现。

原餐厅类比有两层：发布者像用喇叭叫号，侦听者凭自己的小票关注座位；自定义存储像前台登记谁领取了震动器，只给有登记的人通知，而不是每个潜在顾客先配一个槽。它说明“同一对外通知接口可以换登记方式”，不能据此推断登记表无需固定成本。

<a id="c11-explicit-interface"></a>
### 自定义事件访问器与显式接口实现分开理解

自定义add/remove不是“显式接口实现”。后者指定接口成员，只能通过相应接口视图订阅。原正式答用IMailService，思考区用IMailManager，除名字外同一结构与教学点，合并下面完整类型片段；将接口名和限定成员名一起改为IMailManager即为原另一命名方案。

原名称类比还列了`IEnumerable.GetEnumerator`：它示意用接口名限定显式接口成员，与“亲手写add/remove”不是同一种规则；自定义访问器也可直接公开在类上。

```csharp
using System;
interface IMailService { event EventHandler<NewMailEventArgs> NewMail; }
class MailManager : IMailService {
    private EventHandler<NewMailEventArgs> handlers;
    event EventHandler<NewMailEventArgs> IMailService.NewMail {
        add { handlers += value; } remove { handlers -= value; }
    }
    public void Raise(NewMailEventArgs e) {
        var h = handlers; if (h != null) h(this, e);
    }
}
// 调用方方法体内：
MailManager manager = new MailManager();
IMailService service = manager;
service.NewMail += Handler;
manager.Raise(new NewMailEventArgs());
service.NewMail -= Handler;
```

NewMailEventArgs在此使用无参教学版本，Handler按标准签名定义。这个示例单线程；需要并发订阅时用CAS或共同锁。`manager.NewMail += Handler`不能访问这个显式接口成员。自定义事件即便在自己的类型里也没有可直接读/Invoke的事件值，Raise读取handlers；上一节CAS也是读取_newMail。原`public event EventHandler NewMail { add { _newMail += value; } remove { _newMail -= value; } }`表达同一手工字段存储，但`+=`与`-=`内部复合更新未自动原子化。

<a id="c11-sparse"></a>
## EventSet：为实际订阅的事件存储委托链

原书以一个有约70个事件的Control类说明空间问题，举Click、DoubleClick、MouseMove、KeyDown、DragDrop等。如果朴素地给每个field-like实例事件分配引用字段，每实例会有70个槽，即使应用只订阅2—3个；方法代码由类型共享，不会每实例复制add/remove方法机器码，但实例字段槽仍占空间。

<a id="c11-sparse-budget"></a>
### 三事件、70事件和1000实例三个层次

原最小三事件类型片段：

```csharp
using System;
class MyClass {
    public event EventHandler A;
    public event EventHandler B;
    public event EventHandler C;
}
```

三事件足以说明多个独立存储槽。扩展到70事件、1000实例有70000个引用槽；每实例只订阅Click时，69000个槽为空，而不是70000全空。只算引用槽，32位约70×4=280字节/实例，64位约70×8=560字节/实例；1000实例约273KiB/547KiB。原“几十KB每实例、几十MB总计”不是这些假设推出的结果。这里只是预算，不包括对象头、对齐、实际委托对象、字典桶及项，也不是实测Control布局。

思考区的MailManager如果有100个潜在事件、游戏里很多对象只订其中少数，也有同类设计问题；不表示所有MailManager/Unity类型本来就有100事件。稀疏方案保留一个EventSet引用、EventSet对象和可能的字典成本，仅实际有处理程序的key才有项；未订阅并不等于零总开销。事件少或订阅密集时，普通字段可能更简单、成本更低。不能因未订阅槽“浪费”就说普通事件不能实现多事件类型。

这种方案还增加维护key与委托类型对应关系、手写访问器和处理同步/异常的复杂度。本例DynamicInvoke路径可能有额外分发成本，但可选类型化调用；是否值得采用应由实际实例数量、订阅密度和调用频率决定，原“日常99%用不上”没有统计依据。Unity也不因自身框架而天然无需此类存储选择。

<a id="c11-event-key"></a>
### 空EventKey类使用对象身份，不使用唯一哈希码

```csharp
public sealed class EventKey { }
```

没有重写Equals时，两个不同实例作为键按对象身份区分。静态字段让某事件在所有实例上使用同一个标识对象；不是每个实例重新分配70个键，也不是保证每个键哈希码唯一。哈希冲突允许存在，Dictionary还按相等性判断。


<a id="c11-eventset-code"></a>
### 异常安全的完整EventSet类型

原Q12/Q13的核心Add、Remove、Raise逻辑相同，仅局部名、目标类型化new/out var等表层差别，合并为兼容C# 5的完整类型；保留Combine、Remove后删key、锁内取链/锁外通知三个职责。原Monitor.Enter/Exit未用finally，字典或Combine抛异常时会漏锁，这里修成lock。

```csharp
using System;
using System.Collections.Generic;
public sealed class EventKey { }
public sealed class EventSet {
    private readonly Dictionary<EventKey, Delegate> m_events =
        new Dictionary<EventKey, Delegate>();
    public void Add(EventKey key, Delegate handler) {
        if (key == null) throw new ArgumentNullException("key");
        if (handler == null) return;
        lock (m_events) {
            Delegate existing; m_events.TryGetValue(key, out existing);
            m_events[key] = Delegate.Combine(existing, handler);
        }
    }
    public void Remove(EventKey key, Delegate handler) {
        if (key == null) throw new ArgumentNullException("key");
        if (handler == null) return;
        lock (m_events) {
            Delegate existing;
            if (!m_events.TryGetValue(key, out existing)) return;
            var next = Delegate.Remove(existing, handler);
            if (next == null) m_events.Remove(key);
            else m_events[key] = next;
        }
    }
    public Delegate Get(EventKey key) {
        if (key == null) throw new ArgumentNullException("key");
        lock (m_events) {
            Delegate handler; m_events.TryGetValue(key, out handler);
            return handler;
        }
    }
    public void Raise(EventKey key, object sender, EventArgs e) {
        Delegate handler = Get(key); // 锁内读取一次，返回后已释放锁
        if (handler != null) handler.DynamicInvoke(new object[] { sender, e });
    }
}
```

这里规定null handler为不操作，移除最后一个处理程序就删key，避免`+= null`创建空项。每个key必须始终对应同一委托类型及参数协议；给同一key混入不同委托类型会在Combine等操作失败，锁仍应释放。Remove按委托相等性从调用列表移除匹配项；不同对象身份的等值委托可用于注销，与CAS成功判断的引用身份不同。

Get公开是为下文类型化Raise演示，原核心只需内部取链。返回的快照可在退订后继续调用，锁保护字典操作而非整个订阅者生命周期。回调在锁外执行，不把未知订阅者代码塞入字典锁。实际项目可隐藏Get、用专门方法限制每key协议；本教学类不是生产事件框架所有契约。

<a id="c11-foo-bar-data"></a>
### 第一套Foo/Bar：自定义EventArgs和protected EventSet

以下**类型片段**与上面的EventKey、EventSet同编译，补全原未定义的FooEventArgs、BarEventArgs。保留原非泛型EventHandler、两个事件、protected EventSet属性、On方法及Simulate方法；参数运行时仍可传派生EventArgs。

```csharp
using System;
public class FooEventArgs : EventArgs { }
public class BarEventArgs : EventArgs { }
public class TypeWithLotsOfEvents {
    private readonly EventSet m_eventSet = new EventSet();
    protected EventSet EventSet { get { return m_eventSet; } }
    protected static readonly EventKey s_fooEventKey = new EventKey();
    protected static readonly EventKey s_barEventKey = new EventKey();
    public event EventHandler Foo {
        add { m_eventSet.Add(s_fooEventKey, value); }
        remove { m_eventSet.Remove(s_fooEventKey, value); }
    }
    public event EventHandler Bar {
        add { m_eventSet.Add(s_barEventKey, value); }
        remove { m_eventSet.Remove(s_barEventKey, value); }
    }
    protected virtual void OnFoo(FooEventArgs e) { m_eventSet.Raise(s_fooEventKey, this, e); }
    protected virtual void OnBar(BarEventArgs e) { m_eventSet.Raise(s_barEventKey, this, e); }
    public void SimulateFoo() { OnFoo(new FooEventArgs()); }
    public void SimulateBar() { OnBar(new BarEventArgs()); }
}
```

给Foo和Bar分别登记回调，再SimulateFoo/SimulateBar，会调用各自链并收到相应参数对象；只订阅Foo不会创建Bar项。要让Foo回调在编译时得到FooEventArgs，可声明EventHandler<FooEventArgs>，这是下一节泛型签名方案，不能误称原非泛型代码已经是它。

原后续解释还给了OnFoo/OnBar接受EventArgs、Simulate传Empty的变体，条件不同，保留独立类型。将类型改名仅为允许与前例同编译；访问器改成C# 5括号形式不改变逻辑。

### 存储比较与前章知识对应

| 维度 | field-like事件的典型实现 | 本例EventSet自定义实现 |
| --- | --- | --- |
| 存储 | 每个实例事件一个委托引用槽 | 每实例一个EventSet，实际链按key入字典 |
| add/remove | 编译器生成 | 自定义访问器转发Add/Remove |

| 内存 | 70个字段槽，即使部分null | 一个存储及字典固定成本，加已订阅项；不是只算一根引用 |

| 前面知识 | 11.4中的位置 |
| --- | --- |
| 11.1四步法 | 两套TypeWithLotsOfEvents仍有事件、OnXxx及输入转通知，存储方案改变 |
| 11.2编译器实现 | 自己编写add/remove，避免按默认方式每事件一个实例槽 |
| Volatile.Read | 本EventSet用共同锁保护字典；并非锁和volatile能任意互换，保护范围不同 |
| WinForms/WPF Control | 框架也有集中存储思路，但数据结构、同步和调用实现不必与本例相同 |

原房东钥匙类比：事件是可能出租的房间，EventKey是对应房间标识，委托链是领取钥匙的租户名单，EventSet是钥匙柜；只给已登记的房间存记录，房东按对应标识找名单。钥匙柜本身占空间，不能把未租房间省下的记录成本当成整套存储免费。

原自检三问应这样回答：Control**可以**使用普通field-like事件，集中存储是成本选择；本异构集合用Delegate是为容纳不同委托签名，类型化替代仍存在；去掉event并只公开委托字段会放宽权限，自定义存储不要求去掉event。不要沿用原“Control不能普通event”“必须只能Delegate/DynamicInvoke”的绝对答案。

<a id="c11-framework-stores"></a>
### EventHandlerList与WPF内部存储不是同一个公共字典API

WinForms常用System.ComponentModel.EventHandlerList，其官方说明是管理委托的列表，实现为链表；不是Dictionary，也不默认提供本例的共同锁协议。WPF的EventHandlersStore是框架内部实现背景，不是任意业务类型都能直接调用的公开通用EventSet类。不能把“FCL里有类似方案”扩写成“System.Windows里直接提供书中的EventSet”。实际框架也可以取出对应类型委托后直接调用，不是所有集中存储都必须DynamicInvoke。[EventHandlerList](https://learn.microsoft.com/en-us/dotnet/api/system.componentmodel.eventhandlerlist?view=net-10.0)、[WPF内部EventHandlersStore源码](https://github.com/dotnet/wpf/blob/main/src/Microsoft.DotNet.Wpf/src/PresentationCore/System/Windows/EventHandlersStore.cs)

<a id="c11-dynamic"></a>
## 为什么本版EventSet用DynamicInvoke，何时不需要

一个具体官方实现是.NET10 WinForms Control：OnClick从集中Events存储取得值，转为EventHandler后用`?.Invoke(this,e)`；OnControlAdded转为ControlEventHandler调用。每个OnXxx知道自己的协议，可以共享存储并类型化调用，原“WinForms集中存储也必须反射调用”并不成立。[固定.NET10版本Control源码](https://github.com/dotnet/winforms/blob/v10.0.0/src/System.Windows.Forms/System/Windows/Forms/Control.cs)

强类型变量`EventHandler<NewMailEventArgs> temp`在编译时有已知Invoke签名，可直接`temp(this,e)`；`Dictionary<EventKey,Delegate>`取出值时静态类型是Delegate，基类没有通用的Invoke方法。原`Delegate d = m_events[key]; d.Invoke(sender,e);`因此编译失败。**静态类型变成Delegate不抹掉对象的实际委托类型或泛型实参**；只是这个表达式的可访问成员依据Delegate查找。

<a id="c11-heterogeneous"></a>
### 同一存储中的三种签名

原异构例同时有EventHandler<FooEventArgs>、非泛型EventHandler和Action<int>，不能用“都接受object、EventArgs”的假设概括。以下完整程序保留三种签名及类型化转回的路径。

```csharp
using System;
class FooEventArgs : EventArgs { }
class Program {
    static void Foo(object sender, FooEventArgs e) { Console.WriteLine("Foo"); }
    static void Bar(object sender, EventArgs e) { Console.WriteLine("Bar"); }
    static void Main() {
        Delegate foo = new EventHandler<FooEventArgs>(Foo);
        Delegate bar = new EventHandler(Bar);
        Delegate count = new Action<int>(x => Console.WriteLine("Count: " + x));
        foo.DynamicInvoke(new object[] { null, new FooEventArgs() });
        bar.DynamicInvoke(null, EventArgs.Empty);
        count.DynamicInvoke(7);
        ((EventHandler<FooEventArgs>)foo)(null, new FooEventArgs());
        // foo.Invoke(null, new FooEventArgs()); // 反例：CS1061
    }
}
```

输出Foo、Bar、Count: 7、Foo。书中Raise(key,sender,e)只提供两参数EventArgs通知协议，不能直接用它引发Action<int>；存储Add/Remove接受Delegate不等于每种签名都能通过同一Raise调用。若扩展为通用params参数的Raise，必须明确每key协议和错误处理。

原现代API形状为`public object? DynamicInvoke(params object?[] args)`，这里的`?`是可空引用注解；在历史C# 5源码中应写object/object[]。DynamicInvoke在运行时检查参数并调用，签名不匹配可能异常。订阅者抛出的异常经这一路径通常包装为TargetInvocationException，InnerException才是原异常；强类型直接调用通常传播原异常。[DynamicInvoke API](https://learn.microsoft.com/en-us/dotnet/api/system.delegate.dynamicinvoke?view=net-10.0)

<a id="c11-dynamic-cost"></a>
### 调用代价的准确条件

本版`new object[] { sender,e }`有参数数组分配，sender/e已是引用类型，不会仅因放到object[]就装箱。Action<int>传入7时把int放到object数组会装箱；是否分配与装箱须看实际路径。动态检查和调用可能比已知类型委托直接调用有额外成本，但没有普遍“慢10倍”“所有UnityEvent都会反射装箱”等保证，也不能不测负载就说内存节省必然抵消调用成本。

DynamicInvoke以object表示返回结果；值类型返回值可能装箱，引用类型返回值无需因此装箱，void调用返回null。不能把“有返回值”统一解释为必装箱。

插头/插座/转接器类比可保留：强类型委托像已知规格的插头和匹配插座，编译时就能核对；Delegate变量像只知“这里放了某种插头”，DynamicInvoke这条转接路径到运行时才核对参数。具体插头型号仍在，并没有被擦除；若key契约给出型号，可转回对应委托直接调用。

原具体型号分别是EventHandler<FooEventArgs>三孔插头、EventHandler双孔插头和Action<int>的USB插头；通用插座面板可容纳它们，转接器需识别规格。类型化key相当于预先标注接口规格，同一面板仍可用，不必每种插头都改回一个独立存储。

<a id="c11-typed-set"></a>
### 替代一：同一参数类型的一组事件共用泛型EventSet

以下**类型片段**使用前文EventKey。原两行字段`EventSet<FooEventArgs> _fooEvents`和`EventSet<BarEventArgs> _barEvents`表达两个参数族分别存储；同参数类型的多个key仍能共享一个集合，不是强制每个事件创建一个集合。

```csharp
using System;
using System.Collections.Generic;
public sealed class EventSet<TEventArgs> where TEventArgs : EventArgs {
    private readonly Dictionary<EventKey, EventHandler<TEventArgs>> m_events =
        new Dictionary<EventKey, EventHandler<TEventArgs>>();
    public void Add(EventKey key, EventHandler<TEventArgs> handler) {
        if (handler == null) return;
        lock (m_events) { EventHandler<TEventArgs> old; m_events.TryGetValue(key, out old);
            m_events[key] = old + handler; }
    }
    public void Remove(EventKey key, EventHandler<TEventArgs> handler) {
        if (handler == null) return;
        lock (m_events) { EventHandler<TEventArgs> old;
            if (!m_events.TryGetValue(key, out old)) return;
            var next = old - handler;
            if (next == null) m_events.Remove(key); else m_events[key] = next; }
    }
    public void Raise(EventKey key, object sender, TEventArgs e) {
        EventHandler<TEventArgs> h;
        lock (m_events) { m_events.TryGetValue(key, out h); }
        if (h != null) h(sender, e);
    }
}
class TypedCollections {
    private readonly EventSet<FooEventArgs> _fooEvents = new EventSet<FooEventArgs>();
    private readonly EventSet<BarEventArgs> _barEvents = new EventSet<BarEventArgs>();
}
```

FooEventArgs/BarEventArgs取前文定义。本版无DynamicInvoke参数数组、签名为编译时已知，但多个参数族可能需要多个存储；所有Add/Remove/Raise须遵守同一key协议及非null键要求。

<a id="c11-typed-key"></a>
### 替代二：异构字典按key契约转为已知类型

异构字典不强制只能DynamicInvoke。已知某个key只存EventHandler<FooEventArgs>时，可以取得Delegate再强转；下面是**类型片段**，与非泛型EventSet、EventKey及FooEventArgs同编译。

```csharp
using System;
class TypedFooPublisher {
    private readonly EventSet events = new EventSet();
    private static readonly EventKey fooKey = new EventKey();
    public event EventHandler<FooEventArgs> Foo {
        add { events.Add(fooKey, value); } remove { events.Remove(fooKey, value); }
    }
    protected virtual void OnFoo(FooEventArgs e) {
        var h = (EventHandler<FooEventArgs>)events.Get(fooKey);
        if (h != null) h(this, e);
    }
}
```

也可封装泛型Raise<TArgs>，但字典本身不会验证某个key与TArgs永久一致；错误转型会失败。这里保留异构存储的灵活性，把检查责任移到类型化key/接口设计，不能直接称“没有运行时风险”。

<a id="c11-unity"></a>
## Unity里的三种表示和引擎回调

原问题想将书中事件知识用于Unity。Unity脚本仍遵守所用C#版本的事件封装规则；没有因游戏开发而放宽event语法，也没有“游戏能容忍更高GC压力”的通用保证。应先看成员声明，再看引擎提供的功能。

| 对比项 | 本书C#/.NET场景 | Unity场景 |
| --- | --- | --- |
| 回调基础 | 委托类型和委托对象 | C#委托仍适用；UnityEvent另提供封装 |
| event关键字 | 提供事件成员及订阅接口 | 完全相同语言权限，可以采用 |
| 直接公开委托字段 | 允许，但外部可覆盖和调用 | 同样允许，同样权限风险；“常见”不改变规则 |
| 序列化/Inspector | 语言event不自带Unity编辑器支持 | 合适的UnityEvent字段可配置持久回调 |
| 设计目的 | 根据框架与业务选择模式 | 根据代码订阅、内容配置、编辑器工作流选择；不是规范与效率二选一 |

<a id="c11-unity-delegate"></a>
### 原Health：裸DeadHandler和每帧死亡通知

以下**Unity脚本**需UnityEngine及C# 6+，按官方API核验，不冒充在本机Unity运行。补全原未声明hp，保留Update中`hp<=0`逻辑。

```csharp
using UnityEngine;
public class Health : MonoBehaviour {
    public delegate void DeadHandler();
    public DeadHandler OnDead;
    public int hp = 100;
    void Update() {
        if (hp <= 0) OnDead?.Invoke();
    }
}
```

把hp设为0后，每次执行Update都可能通知一次，原例不保证“死亡只发一次”。若需要一次通知，应另增加isDead转变控制。外部可写`health.OnDead=null`清空别人订阅，也可调用它；这是裸委托字段权限，不是Unity特有语法。`public Action OnDead;`是无需自定义无参委托类型的同类表示。

<a id="c11-unity-event"></a>
### 改成event Action与Die入口

这是**另一个独立Unity脚本**，原例使用Die方法引发通知，不与前例同时声明同名Health。

```csharp
using System;
using UnityEngine;
public class Health : MonoBehaviour {
    public event Action OnDead;
    public void Die() { OnDead?.Invoke(); }
}
```

外部可`+=`/`-=`，不能清空或Invoke；Die每次调用仍通知，是否“一生一次”由业务状态控制。订阅者可在OnEnable登记、OnDisable注销，但生命周期是否匹配须按对象是否禁用、销毁、发布者寿命等设计；不能把一套位置当成适用于所有对象的规则。

<a id="c11-unity-unityevent"></a>
### UnityEvent是可配置回调对象，字段本身仍是字段

以下**Unity脚本**保留原`public UnityEvent OnDead`，显式初始化避免普通C# new路径为空；引擎序列化与编辑器持久配置另有自己的规则。

```csharp
using UnityEngine;
using UnityEngine.Events;
public class Health : MonoBehaviour {
    public UnityEvent OnDead = new UnityEvent();
    public void Die() { OnDead.Invoke(); }
}
```

Inspector中可添加回调槽、选择目标GameObject/组件、选择方法；既有预配置参数调用，也有根据UnityEvent类型传参的动态绑定。这里“动态”是Unity编辑器调用模式，不等于C# dynamic或Delegate.DynamicInvoke。代码中可用AddListener、RemoveListener登记/注销运行时回调。公开OnDead字段可被外部替换、其Invoke也可外部调用；字段是UnityEvent类型不自动得到C# event封装。[UnityEvents手册](https://docs.unity3d.com/cn/2018.3/Manual/UnityEvents.html)、[UnityEvent API](https://docs.unity3d.com/cn/6000.0/ScriptReference/Events.UnityEvent.html)

| 原对照维度 | 修正后的说明 |
| --- | --- |
| 可序列化 | UnityEvent提供适用的持久回调序列化/编辑器支持，不是任意委托字段都支持 |
| 拖拽绑定 | 在Inspector配置目标对象和方法，支持相应参数模式 |
| “非C#原生” | Unity提供的类/API，用C#使用；不是C#事件成员关键字 |
| 性能 | 持久解析和分发有自己的代价，不能概括为每次必反射、必装箱、一定略慢 |

官方Unity源码存在建立并缓存InvokableCall、通过UnityAction等委托调用的路径；反射用于一些绑定/查找并不等于所有调用每次都反射。参数是否值类型、实际调用路径、引擎版本和负载影响代价。UnityEvent也会持有回调目标引用；UnityEngine.Object原生对象消失后还有特殊调用判断，不能用C# event替代词覆盖所有行为。[Unity官方UnityEvent源码](https://github.com/Unity-Technologies/UnityCsReference/blob/master/Runtime/Export/UnityEvent/UnityEvent.cs)

<a id="c11-unity-choices"></a>
### GameEvent<int>、UI.OnGameOver和选择依据

原游戏逻辑例保留为**普通C#类型片段**，不依赖UnityEngine。用event保护分数通知，允许派生类通过protected方法引发。

```csharp
using System;
public class GameEvent {
    public event Action<int> OnScoreChanged;
    protected virtual void RaiseScoreChanged(int score) {
        OnScoreChanged?.Invoke(score);
    }
}
```

原UI配置例`public UnityEvent OnGameOver;`和裸字段`public Action OnDead;`属于另外两种选择：前者面向编辑器回调配置，后者简单但外部能替换/调用。成员若用公开字段，可按需要初始化，例如UnityEvent OnGameOver = new UnityEvent()；不把它们写成`UnityEvent ⊂ event ⊂ delegate`。UnityEvent是类，event是成员机制，delegate定义类型，三者并非包含集合。

<a id="c11-unity-messages"></a>
### Update、Mono/IL2CPP和Job/Burst边界

原`void Update() { }`在C#层面是方法，不是用event声明的成员；Unity文档称Start、Update等为事件函数/生命周期回调。引擎在规定时机调用它们，不能因术语不同就说它们完全不涉及通知概念，也不能断言引擎每帧都靠普通反射查找执行。[Unity事件函数执行顺序](https://docs.unity3d.com/6000.0/Documentation/Manual/execution-order.html)

Mono后端与Microsoft .NET Framework CLR/JIT不同；IL2CPP将IL转换为C++再编译为平台机器码，主要是AOT。原书关于Microsoft JIT的特定实现说明不能直接外推到所有Unity后端。托管GC和持久订阅引用仍须管理，不因AOT就消失。[IL2CPP机制](https://docs.unity3d.com/cn/2021.3/Manual/IL2CPP.html)

原“热更新/脚本生命周期特殊”还需区分：编辑器重新编译、代码或域重载是开发时行为；部署更新是交付新的应用或资源产物；运行时加载新的执行逻辑则需要具体后端和更新架构支持。Unity不是所有平台都自动提供任意C#运行时热更，IL2CPP的AOT也不自动提供JIT式的新代码执行。这些生命周期/部署选择不改变event的语言封装规则。[Unity域重载说明](https://docs.unity3d.com/cn/6000.0/Manual/domain-reloading.html)

Unity主线程脚本常见不表示没有其它线程。Job System的数据和调度需遵守相应依赖/容器规则，Burst支持C#的受限子集，不能把普通托管委托、UnityEvent和托管对象随意放入Burst任务，也不能说一处Volatile.Read就使Unity API能从工作线程安全调用。CPU内存排序、集合访问安全和引擎API线程条件是不同问题。[Burst官方限制](https://docs.unity3d.com/ja/current/Manual/script-compilation-burst.html)

若某订阅链的登记、注销和引发确实都只在同一线程执行，就没有来自其它线程的订阅并发问题，无须为这个目的额外加Volatile.Read。UnityEvent本身不提供本章字典共同锁/CAS那样的通用并发协议，应按所用引擎API的线程条件调用。

以下列出改变结论或示例有效性的纠错；正文已使用正确版本。不同原时序表、不同Foo/Bar参数场景、思考区独有表和类比均保留；纯生成规划、寒暄和重复引用不作为新知识。
