<a id="c28-io-model"></a>
### Windows I/O 路径：谁等待，谁处理完成

同步的教学路径保留原来的五步：托管 `FileStream.Read` → Win32 `ReadFile` → 内核 I/O 管理器建立、路由请求 → 文件系统／设备驱动及设备执行 → 发起线程等结果后继续。IRP 会涉及文件句柄、偏移、缓冲区、请求字节数等信息，但它是内核 I/O 请求包；不能把图中 `ReadFile` 引起 IRP 建立理解为用户模式代码直接分配内核 IRP。缓存／快速路径也不要求每次都经历一次物理磁盘传输。[R28-S16][R28-S17]

原生异步路径保留六步及各自用途：以适当异步选项打开资源，提交带完成信息的请求，调用侧取得代表结果的 Task／ValueTask，设备或操作系统在等待期间处理请求，完成端口／运行时收到完成信息，随后根据 awaiter 与应用上下文执行后续代码。Windows 完成端口排队的是完成 packet；硬件不是把整个 IRP 对象直接放进 CLR 普通计算工作队列。完成端口的入队、唤醒策略与最终回调顺序也不能混为一件事。[R28-S18]

“等待时零个专属阻塞线程”是原生异步 I/O 的伸缩性要点。CPU 仍执行用户前段、进入内核、驱动、协议处理、完成通知和后续计算；共享完成线程仍存在。某个异步 API 可能由线程池包装同步工作，可能从内存直接完成，也可能在发起阶段执行同步工作。不能仅见 Task 或 `Async` 后缀就替它判定底层实现。指定 .NET v10.0.0 Windows portable pool 还有一组 I/O poller 与完成分发队列，并非每个进程永远一个 poller 或 poller 必亲自执行每个 await 续延。[R28-S19]

Windows FileStream 的 `FileOptions.Asynchronous`／`useAsync: true` 影响句柄的 overlapped 模式，适合原生异步文件操作；它没有把构造器、所有资源和所有平台统一改成硬件异步。调用的 Task 若已经完成，await 可以同步继续；若尚未完成，挂起的是该异步方法，物理线程返回调用方，调用方随后做什么取决于它自己的控制流。

原书“10幅图片，每幅5秒：串行约50秒、全部并发约5秒”的例子保留为条件性示意：假定各传输互不争抢同一瓶颈且能同时推进，全部完成时间接近最长单项；实际网络、磁盘、服务端、连接数、CPU 和内存预算会改变结果。原书“一线程处理许多请求、尽量少上下文切换”的 Windows 线程池说明也应按并发值、持续就绪工作及历史实现理解，不能保证所有服务器只有一个线程或根本没有任何上下文切换。GC、调试挂起扫描和 Silverlight／Windows Store 的描述属于当时实现与特定 API 环境。

<a id="c28-fcl"></a>
### FCL API 与语言写法各负责一层

文件的 `ReadAsync`／`WriteAsync`、Socket 收发、HttpClient Get／Post、数据库提供者的 `ExecuteReaderAsync` 等原例都保留。Windows FileStream、网络层、HttpMessageHandler、数据库提供者和其他平台各有具体实现；不能断言这些 API 全部直接走相同的 overlapped I/O＋IOCP。数据库查询还可能在服务端执行大量计算，HTTP 也有解析、解压、TLS 等软件工作；“I/O 限制”描述当前主要瓶颈，并未把 CPU 从系统中消失。

C#5 的普通异步返回常见为 void／Task／Task<T>，后来的 generalized task-like 返回、ValueTask 和异步流要标版本；构造器、属性／事件访问器不能直接标 async，普通 async 方法的 ref／out 参数限制仍在。`async Task Main` 从 C#7.1可用；C#6允许在 catch／finally await；`await using` 和异步流属 C#8。unsafe 区域、查询表达式和线程亲和锁的规则应按具体语言版本和位置读，不能笼统说任何现代方法只要包含 unsafe 就不能异步。[R28-S01][R28-S02][R28-S03][R28-S04]

<a id="c28-library-context"></a>

## “计算限制”与“I/O限制”：瓶颈、借线程和混合操作

“限制”（bound）指主要受哪种资源约束。计算限制常是 CPU 指令计算占主要时间；I/O 限制常是等磁盘、网络、远端服务等数据与响应。这是性能特征，不能缩成“CPU是硬件以外的东西／凡硬件都I/O”；CPU本身也是硬件，缓存、内存带宽、GPU计算和服务端计算也会成为瓶颈。真实方法通常混合多段，不是按方法名一眼就能确定全部实现。

原做菜／外卖类比保留：需要自己刀工、翻炒的计算不能凭空完成；提交配送请求后可以处理别的事情，收到完成通知再收尾。但发起请求、处理结果仍需线程执行，不能用类比证明任何 API 都没有同步前段或设备能力限制。

<a id="c28-cpu-offload"></a>
CPU 委托通过 `Task.Run` 排到默认线程池，由工作线程执行。调用方 await 一个尚未完成的任务时返回其调用方，UI可继续消息循环；ThreadPool可按策略复用已有线程或增减线程。并不是遇到 CPU 操作就自动新建 B。CPU 操作也可以直接调用或用其他并行方案；服务端是否额外 Task.Run 要按吞吐量和用途选择，不能把每段计算都无条件排队。

<a id="c28-q02-a012"></a>
<!-- C28-D01-Q002-A-B012 -->
```csharp
await Task.Run(() => ComputeBoundOp());
```

原图像／视频编解码、数学计算、加解密、排序聚合和大型正则例保留为常见计算场景；算法、输入、硬件加速或数据获取可能改变主瓶颈。委托里调用 `Thread.Sleep` 时，线程在同步等待并非持续占用 CPU 算术；后面的 Sleep 示例用来演示调度与延迟，应保其参数而纠正“正在计算”的解释。

| --- | --- | --- |
| **瓶颈资源**​ | CPU | 传输／外部响应等主要资源；仍有软件CPU阶段 |

| **不异步化的代价**​ | 若在UI线程直接做大量计算，会延迟消息处理 | 若在UI线程同步等慢IO，会延迟消息处理 |

### 保留原100MB读取→压缩→写入的按钮例

该例分三段：读取文件数据是 I/O，`Compress(data, bytesRead)` 的压缩是计算，写压缩结果又是 I/O。100MB数组、4096缓冲参数、两个异步打开选项、文件名和MessageBox用途全部保留。`Compress` 和控件由应用提供；这不是已补齐所有类型的独立项目。

原代码已把 `bytesRead` 传给 Compress，所以不能指控它一定使用整块未读满数组。它压缩的是本次实际读到的部分；单次ReadAsync并未保证读完整个文件或填满100MB。若目标是完整文件，应循环读取至EOF／目标数量，或采用分块／流式方案，并按源文件长度、内存预算和压缩器协议设计。原正文“硬盘读100MB后完成”应改为“请求最多100MB，实际返回count”。自造短读夹具一次只得2字节，循环才得全部10字节，支持这个边界。[R28-S23]

```csharp
    using var fs = new FileStream("bigfile.dat", 
        FileMode.Open, FileAccess.Read, 
        FileShare.Read, 4096, FileOptions.Asynchronous);
    
    // 支持原生异步IO的等待阶段不要求每请求专属阻塞线程；发起/完成仍需CPU。
    // 任务未完成时await可把控制交回调用方；也可能同步完成。
    int bytesRead = await fs.ReadAsync(data, 0, data.Length);
    
    // —— 第27章的计算限制部分 ——
    // 这步是 CPU 限制：压缩算法必须 CPU 线程一条条算
    // 如果不 Task.Run，UI 线程会被压缩计算卡住
    byte[] compressed = await Task.Run(() => Compress(data, bytesRead));
    
    // —— 又是第28章的 I/O 限制部分 ——
    using var outFs = new FileStream("compressed.dat", 
        FileMode.Create, FileAccess.Write, 
        FileShare.None, 4096, FileOptions.Asynchronous);
    
    // 写入磁盘也是 I/O 限制
    await outFs.WriteAsync(compressed, 0, compressed.Length);
    
    MessageBox.Show("搞定！");
}
```

代码中的 `using var` 属C#8，事件void签名可从C#5使用；正常 UI 默认Task await完成后，更新控件仍需合法上下文与控件生命周期。原输入例不是“任意FileStream异步调用必零线程”的证明，重CPU工作即便被移出UI，也可能因CPU竞争、GC和内存压力影响响应，不保证“完全不掉帧”。

从第27／28章对照建立直觉时，应先看操作真正做了什么、提供者提供了什么，再看调用方如何安排它和等待它。Task.Run并不把同步文件操作变成无专属等待线程的原生I/O；await也不自动给同步CPU方法安排工作线程。

<a id="c28-thread-flow"></a>
## 把A、B、C线程理解改为可恢复的控制流

Q3的三点理解逐一保留并核准。

1. CPU／I/O分类看主要瓶颈，不排除I/O软件阶段用CPU或混合工作。
2. 显式Task.Run安排CPU委托，不要求每次新建B；未在此处await，可以保存Task供后面等待、组合和观察错误，也可以选择明确管理的后台工作。未await不必等于“完全不关心任务”。
3. 对未完成awaitable注册续延后，异步方法返回给调用者。需要跨挂起保留的数据由状态机和相关对象保存，恢复执行时重新调用MoveNext，而不是恢复／复制某个线程原来的整段堆栈。方法返回不销毁物理线程，不清全部TLS，也不保证上层不会立即同步等待。

<a id="c28-continuation-policy"></a>
任务完成后“谁接着跑”要按Task awaiter、是否已完成、捕获SynchronizationContext、当前非默认TaskScheduler和续延选项理解。默认控制台／false常由完成线程或线程池工作线程续跑，但不保证B自己；自定义上下文／调度器还可指定其他执行安排。await不为每次完成自动new Thread；ThreadPool仍可能依负载增设线程，所以原“没有新线程这个选项”的绝对措辞也过宽。

GUI场景里，正常Task await捕获相应UI上下文，续延经Post／Dispatcher／消息泵等安排，再由UI线程自己执行。可以说“投递回UI调度”，不是把线程当方法任意跨线程调用；捕获发生在注册等待前，而不是到完成时临时查看发起线程当前有什么上下文。经典ASP.NET恢复请求关联环境，不要求原物理线程，现代Core情况后文另分。

<a id="c28-q03-a021"></a>
<!-- C28-D01-Q003-A-B021 -->
| 场景 | 后续代码在哪个线程执行 |
| --- | --- |
| 控制台程序 / 用了 `ConfigureAwait(false)` | 已成可留调用线程；未完成续延可能inline或另排队，false不保B／指定线程 |
| WPF/WinForms UI 线程上 `await` 且没用 `ConfigureAwait(false)` | 在合法UI上下文以默认Task await捕获/恢复时，回该上下文；控件须仍存活 |
| ASP.NET（经典，非 Core） | Framework时代按请求关联上下文调度，非固定原线程 |

保留原五维计算／I/O对照，注意“发起后返回”与“await后控制交回”不是同一条无条件规则：某个Task已经完成，后续便可在同一次调用中继续；异步方法在第一处未完成await之前也能执行同步连接、分配、解析或计算。

原书本来用状态机结构讲可挂起与恢复，后面有已完成awaiter直接继续的条件；这里把聊天中的“所有局部变量提升为堆上类、恢复堆栈、无Context必B”修到正确范围。状态的保存不等线程间数据自动同步；共享可变对象仍需独立考虑并发与生命周期。下一节把这个原则放回控制台和UI的具体输入、输出与时间线。

<a id="c28-state-x"></a>
### x=1与await的状态：保存数据，不是恢复线程栈

原SomeAsyncOp片段保留：x在await之后还需要使用，返回的y也参与x+y。外部必须提供返回可await整型结果的SomeAsyncOp；它不必是I/O，也不一定每次挂起。

<a id="c28-q04-a042"></a>
<!-- C28-D01-Q004-A-B042 -->
```csharp
int x = 1;
int y = await SomeAsyncOp(); // ← 暂停点
Console.WriteLine(x + y);    // ← 续延
```

原伪码整体保留，供对照其State／x／builder／MoveNext意图；它本来已标伪代码，不能当编译器实际生成且完整可编的类型。

<a id="c28-q04-a044"></a>
<!-- C28-D01-Q004-A-B044 -->
```text
class StateMachine
{
    public int State;          // 0=刚开始, 1=await之后
    public int x;              // 局部变量变成了字段！
    public AsyncTaskMethodBuilder builder;
    
    public void MoveNext()
    {
        if (State == 0)
        {
            // 执行 await 之前的代码
            x = 1;
            var awaiter = SomeAsyncOp().GetAwaiter();
            if (!awaiter.IsCompleted)
            {
                State = 1;
                awaiter.OnCompleted(MoveNext); // 注册续延
                return;
            }
        }
        
        if (State == 1)
        {
            // 执行 await 之后的代码
            int y = awaiter.GetResult();
            Console.WriteLine(x + y); // x 从字段里读出来，完美恢复！
            return;
        }
    }
}
```

伪码的具体缺口必须点出：awaiter只声明在第一个if的局部作用域，第二段和后来恢复拿不到它；异步完成时需要在状态机里保存对应awaiter，恢复时读取并调用GetResult。已经完成时也要沿当前调用执行后续段，原示意State不变0会跳过第二if。builder完成、异常、初始／终态和接口方法等也省略了。真正编译产物可以是struct，跨挂起所需的变量与awaiter按实际用途保留，不意味着所有局部变量都必提升；本章原ComputeAsync／ReadAsync编译元数据直接展示两者不同字段，相关代码后面保留。

“堆上的共享状态使数据还能取到”仅说明存储寿命；不能据此说谁都可无同步地修改这些数据，也不能把方法参数／this对象当深复制。状态机恢复的是程序控制状态与需要的数据，从来没有把CPU返回地址、整个线程调用栈或所有局部值序列化保存起来。

<a id="c28-async-chain"></a>
## A→B的挂起如何沿调用链返回

原Q5把sync改为async是术语修正：“方法”不能叫“接口”；C#没有用sync修饰这种方法。三点理解继续保留，但只在操作未完成并沿await挂起时，才产生所谓“逐层返回”。

<a id="c28-q05-a012"></a>
<!-- C28-D01-Q005-A-B012 -->
```text
线程a → async方法A() → await async方法B() → await Task.Run(...)
```

保原四步过程：Task.Run给出代表委托的Task；B取得awaiter，未完成便登记续延并返回B自己的完成Task；A正在await B而B未完成，A也登记续延并返回A自己的Task；最终到达仍在执行的调用方，它可能继续处理消息、做别的工作，或选择同步等待。每一层返回的Task代表本层方法最终完成，不是把同一个线程／同一Task对象一路“传上去”。

已完成的awaitable不要求挂起，下一层可能直接完成；选择保存Task／稍后await／组合的代码也不必立刻逐层退出。入口可本身是async void事件处理器，不能把“直到遇到不是async的UI入口”当语法规定。现代TaskMain更有生成入口等待，前节已给出实际条件。

线程A没有因挂起而被销毁；UI线程返回消息循环，池工作线程在其回调返回后可回到池调度，普通调用线程仍由原调用方控制。B完成只触发已登记的后续安排，不保证必B、必新建C或必回A。Windows原生I/O完成处理也不固定由名为X的唯一IOCP线程执行所有后续操作。

局部数据的保留仍由真实状态机所需字段与相关对象承担，不能继续称“恢复await时的完整堆栈”。未在此处await的Task也可以被明确管理；真正选择后台工作时，要安排完成、错误和生命周期观察，而不是把没有await自然当成安全发起即忘。

<a id="c28-async-void"></a>
## async Task与async void：异常容器、投递和catch位置

Task返回把完成／故障／取消交给调用方观察；await在GetResult阶段传播相应结果或保存异常，包围await的try/catch可以处理它。async void没有交给调用方的Task，所以无法直接await这个void返回值；未在方法内部处理的异常由builder向保存的SynchronizationContext投递，或在线程池安排抛出。不是异常“必须先经过await才存在”。[R28-S09]

原“防爆箱／挂号信”与“裸信／手榴弹”类比保留为异常交付方式：Task让收件人选择何时观察结果；void入口把未处理错误交给宿主。但Task中错误早已发生，不是等打开才开始失败；async void内部仍可用try/catch，UI环境也不是自动安全的异常容器。原T曾把UI上下文说成自然兜底安全，并把async void错误与UnobservedTaskException混同，应按实际机制纠正。

## 状态机同时服务计算、I/O、定时器与自造awaitable

Q7的核心判断正确：调用方用async／await表达控制流时，不因被等待的操作是CPU、I/O、定时器或人为完成的TCS而改用另一套语言原则。`Task.Run`委托本身若是普通同步函数，则该函数没有因Task.Run自动获得async状态机；状态机位于真正async的方法或async lambda。`new Task(...)`还需安排启动，单纯await未启动的Task不会替调用者Start它。

但协议并非“只认Task接口”，也不是只有一个GetAwaiter名称即可。可await表达式的awaiter需要可读bool IsCompleted、无参GetResult及INotifyCompletion；有ICriticalNotifyCompletion时采用对应注册路径。语言允许自定义awaitable。这里按原ASCII图保语言层与操作实现层，把各成员放回所属对象，并补GetResult；底层异步方法也未必用async关键字实现。[R28-S01]

原作者给出的类版状态机已标“伪代码简化版”。完整保其State、Builder、result、switch和三段用途，不能删掉伪码，也不能冒实际compiler会逐字生成这段合法类型。

<a id="c28-q07-a019"></a>
<!-- C28-D01-Q007-A-B019 -->
```text
class ComputeAsyncStateMachine : IAsyncStateMachine
{
    public int State;
    public AsyncTaskMethodBuilder<int> Builder;
    public int result;
    
    public void MoveNext()
    {
        switch (State)
        {
            case 0:
                Console.WriteLine("开始");
                // ① 创建一个Task，背后是线程池线程在计算
                var task = Task.Run(() => { Thread.Sleep(1000); return 42; });
                var awaiter = task.GetAwaiter();
                if (!awaiter.IsCompleted)
                {
                    State = 1;
                    // ② 注册续延：task完成后回调MoveNext
                    Builder.AwaitOnCompleted(ref awaiter, ref this);
                    return;
                }
                goto case 1;
                
            case 1:
                // ③ 线程池线程算完了，这里拿到结果
                result = awaiter.GetResult();
                Console.WriteLine($"结果是 {result}");
                Builder.SetResult(result);
                return;
        }
    }
}
```

下面保原书EventAwaiter作为自定义await协议的核心例。类自己返回自己为awaiter，队列保存事件参数、IsCompleted判断是否已有事件、GetResult取事件、OnCompleted保存续延、EventRaised取出续延后调用。其代码与原PDF671／672互核，并在受控注册竞争夹具使用完整类；没有运行无限FirstChance订阅循环。

<a id="c28-event-awaiter-book"></a>
```csharp
public sealed class EventAwaiter<TEventArgs> : INotifyCompletion {
    private ConcurrentQueue<TEventArgs> m_events = new ConcurrentQueue<TEventArgs>();
    private Action m_continuation;

    #region 状态机调用的成员
    // 状态机先调用这个来获得 awaiter；我们自己返回自己
    public EventAwaiter<TEventArgs> GetAwaiter() { return this; }

    // 告诉状态机是否发生了任何事情
    public Boolean IsCompleted { get { return m_events.Count > 0; } }

    // 状态机告诉我们以后要调用什么方法：我们把它保存起来
    public void OnCompleted(Action continuation) {
        Volatile.Write(ref m_continuation, continuation);
    }

    // 状态机查询结果；这是 await 操作符的结果
    public TEventArgs GetResult() {
        TEventArgs e;
        m_events.TryDequeue(out e);
        return e;
    }
    #endregion

    // 如果都引发了事件，多个线程可能同时调用
    public void EventRaised(Object sender, TEventArgs eventArgs) {
        m_events.Enqueue(eventArgs);    // 保存 EventArgs 以便从 GetResult / await 返回

        // 如果有一个等待进行的延续任务，该线程会运行它
        Action continuation = Interlocked.Exchange(ref m_continuation, null);
        if (continuation != null) continuation();   // 恢复状态机
    }
}

```

这段原例在顺序演示下可以展示await事件，但其“事件可来自多个线程”条件产生具体注册竞争：IsCompleted刚返回false，事件入队且看到continuation为空，随后OnCompleted只写continuation；现有事件没有再触发它，可能直到下个事件才恢复。单continuation字段也不支持任意多个并发等待者。Framework4.8／10.0.12受控次序实际得到callback0，下个事件才1；限定单consumer的修订在登记时与事件入队一起协调并再次检查队列，得到callback1。这个缺口属于原示例并发前提，不能据此删掉正确的awaiter协议，或声称原串行FirstChance示例本来必不能工作。具体订阅／退订、无界队列、取消和消费者寿命由完整应用处理。

### WaitAsync配对成功取得的许可

原GoodExample完整保initial1／max1、Delay1000和finally Release。等待许可用Task表示，后续可能别的线程执行，SemaphoreSlim不要求释放者是原物理线程；但只有成功取得许可后才进入应Release的try/finally，失败／取消／timeout后不能凭空Release。

<a id="c28-q08-a038"></a>
<!-- C28-D01-Q008-A-B038 -->
```csharp
private readonly SemaphoreSlim _semaphore = new SemaphoreSlim(1, 1); // 初始1，最大1 → 相当于互斥锁

async Task GoodExample()
{
    await _semaphore.WaitAsync();  // ← 异步等待，不阻塞线程！
    try
    {
        await Task.Delay(1000);    // 安全地 await
        // 做你的事...
    }
    finally
    {
        _semaphore.Release();      // 释放信号量
    }
}
```

<a id="c28-semaphore"></a>
## SemaphoreSlim.WaitAsync：许可、暂停与真正的计数时间线

原公共厕所／停车位类比保：3个资源位对应初始许可3，成功进入扣许可，满了等，释放后可让一个等待者取得。信号量限制的是同时持有多少许可，不是强制“只能有N个物理线程”或等待时给每个调用独占线程。这个许可协议需要使用者正确配对。

SemaphoreSlim通常以进程内轻量机制实现等待；不能说它永远无任何内核对象或任何内部同步。访问AvailableWaitHandle可按需建立ManualResetEvent；本章两环境实际看到该类型。WaitHandle被signaled不等成功取得SemaphoreSlim许可，不会自己扣计数。[R28-S13][R28-S14][R28-S15]

保原initial1／max1构造输入；它可用于一次只准一个逻辑操作访问资源，但不等具有Monitor所有语义。SemaphoreSlim无重入、owner身份检查与公平顺序保证；同一操作再等自己持有的唯一许可可以卡住，不能当lock的可重入替代。

<a id="c28-q09-a011"></a>
<!-- C28-D01-Q009-A-B011 -->
```csharp
// 创建一个最多允许 1 个线程同时进入的信号量
// 参数1：初始计数 = 1（现在有1个坑位可用）
// 参数2：最大计数 = 1（最多只允许1个人用）
var semaphore = new SemaphoreSlim(1, 1);
```

原重复object lock＋await片段是同一语言限制的反例，继续保其SomeAsyncOp用途；Monitor线程亲和与C#编译期拒绝分开，不说该片段已经实际运行后“直接崩”。

<a id="c28-q09-a015"></a>
<!-- C28-D01-Q009-A-B015 -->
```csharp
lock (someLock)
{
    await SomeAsyncOp();  // ❌ 编译错误
}
```

WaitAsync本身不会检查释放者是否原来的线程／Task。它也不会替使用者保证只Release真实取得的许可，重复Release到最大数会抛SemaphoreFullException。原“计数>0扣减，否则等；Release增加可用许可”的直觉保，实际把许可交给已有async等待者时，自由计数可以仍为0。

<a id="c28-q09-a026"></a>
<!-- C28-D01-Q009-A-B026 -->
```csharp
await semaphore.WaitAsync();  // 这一行是关键
```

原即时成功分支完整保：已有许可，成功扣减，返回已完成任务，await无需为这次等待挂起，不会因为await语法强制另换线程。此处“无需换线程”不保证操作系统从不抢占／上下文切换。

<a id="c28-q09-a028"></a>
<!-- C28-D01-Q009-A-B028 -->
```text
调用 WaitAsync()
  ↓
发现计数 = 1 > 0
  ↓
计数减为 0
  ↓
返回一个"已经完成的 Task"（IsCompleted = true）
  ↓
await 发现 Task 已经完成 → 不切出，直接同步往下执行
```

pending分支仍保注册等待→返回pending Task→方法挂起→其他调用Release→许可授予→续延执行的顺序；纠“必可见count1再由续延扣一次”。WaitAsync建立等待任务，调用方await才登记其后续；不是信号量先替调用方把整段continuation登记好。

<a id="c28-q09-a031"></a>
<!-- C28-D01-Q009-A-B031 -->
```text
调用 WaitAsync()
  ↓
发现计数 = 0
  ↓
等待许可不用专属阻塞线程；建立未完成等待Task，调用方await登记后续。
  ↓
await 发现 Task 没完成 → 状态机切出，线程解放去做别的事
  ↓
（过了一会儿）另一个线程调用了 semaphore.Release()
  ↓

  ↓
信号量找到那个等在门口的 Task，把它标记为"完成"
  ↓
await 的续延代码执行（可能在某个线程池线程上）
```

## 多次yield如何回到foreach：枚举器状态、Current和Dispose

Q11联想到状态机是正确的：普通iterator用保存枚举状态的对象实现多次MoveNext；async方法按awaiter完成机制恢复，异步iterator结合两种能力。两者共有“保存恢复所需状态”的思路，却有不同推进／产出协议，不能因此说现代同一方法里无法await与yield。

### 原for1..3与伪状态机完整对照

保原GetNumbers1..3方法和其消费者。

```text
// 编译器生成的类
class GetNumbersStateMachine : IEnumerable<int>, IEnumerator<int>
{
    private int _state;   // 0=还没开始, 1=执行中, -1=结束
    private int _current; // 存放 yield return 返回的值
    private int i;        // 你的局部变量，被提升为字段！
    
    // ===== IEnumerable<int> 的实现 =====
    public IEnumerator<int> GetEnumerator()
    {
        // 每次 foreach 都会创建一个新的状态机实例
        var machine = new GetNumbersStateMachine();
        machine._state = 0;
        return machine;
    }
    
    // ===== IEnumerator<int> 的实现 =====
    public int Current => _current;
    
    public bool MoveNext()
    {
        switch (_state)
        {
            case 0:
                // ---- 对应原始方法的开头 ----
                i = 1;                    // for 循环初始化
                goto case 1;               // 跳到循环体
                
            case 1:
                // ---- 对应 for 循环的条件判断 ----
                if (i <= 3)
                {
                    goto case 2;           // 条件成立，进入循环体
                }
                else
                {
                    _state = -1;           // 循环结束
                    return false;          // MoveNext 返回 false，foreach 停止
                }
                
            case 2:
                // ---- 对应 yield return i ----
                _current = i;              // 把 i 的值存到 Current 属性
                i++;                       // for 循环的 i++
                _state = 1;                // 下次 MoveNext 时回到 case 1
                return true;               // 告诉 foreach："我有数据，拿去吧"
        }
        return false;
    }
}
```

### 真正foreach展开不能丢掉Dispose

原while枚举展开能说明GetEnumerator→MoveNext→Current，但对实现IDisposable的枚举器，完整语义还包含finally里的Dispose；提前break或异常也会离开消费范围并释放。生产体中的using／try-finally在yield处保持活跃，yield返回本身不会立刻释放仍需保留的资源；结束或枚举器Dispose才处理适当finally。[R28-S06]

```csharp
using (IEnumerator<int> enumerator = GetNumbers().GetEnumerator())
{
    while (enumerator.MoveNext())
    {
        int n = enumerator.Current;
        Console.WriteLine(n);
    }
}
```

这是对这里已知IEnumerator<int>类型的完整消费写法；一般foreach还有pattern、结构体、数组及编译器优化，不能要求所有foreach都逐字降成同一种while或分配同一种接口对象。手动驱动迭代器时同样需要释放责任。

### 两种状态机的七维比较

保原实现接口、暂停、恢复、保存、驱动、线程与典型消费七行，纠“普通yield永远同线程／async恢复永远池线程”。某次MoveNext就在那次调用者线程同步执行，调用方可以在不同线程上有序驱动同一枚举器；这不提供并发MoveNext或共享字段的线程安全保证。受控两次serial调用实际发生在不同线程，之间调用者仍能做别的工作。

<a id="c28-q11-a017"></a>
<!-- C28-D01-Q011-A-B017 -->
| 对比维度 | `yield return` 状态机 | `async/await` 状态机 |
| --- | --- | --- |
| **实现接口**​ | `IEnumerable<T>` / `IEnumerator<T>` | `IAsyncStateMachine` |
| **"暂停"机制**​ | `yield return` 把值存到 `Current`，`return true`，方法退出 | `await` 发现 Task 没完成，注册续延，`return` |
| **"恢复"机制**​ | 下次调用 `MoveNext()` 时，从 `_state` 标记的 `case` 继续 | awaiter完成通知按其实现和调度安排恢复；不一定线程池/必须换线程 |
| **保存什么**​ | 跨yield需要的数据、状态和Current，依实际编译产物 | 所需跨await数据、state、builder与相应awaiter，非所有局部必字段 |
| **谁驱动恢复**​ | **调用者主动调 `MoveNext()`**（拉取模式） | **Task 完成时自动回调**（推送模式） |
| **线程模型**​ | 每次MoveNext由该次调用线程执行；可由不同线程串行推进，非天然线程安全 | 可同线程／换线程，取决于是否挂起、awaiter、上下文与调度等 |
| **典型消费方式**​ | `foreach` | `await` |

原Pull对话完整保：消费方问下一项，生产到yield返回，消费方再决定是否请求。消费方可以foreach、手写推进、LINQ／ToList／其他宿主，不能说没有foreach或显式while就必无人推进。

```text
状态机：我再跑一点，再给你一个
```

<a id="c28-yield-await"></a>
## yield与await是否“释放线程”：分清返回、阻塞和挂起

Q12追问最需要纠正的地方是原对照把yield暂停列成“被阻塞干等”。yield return把当前MoveNext返回给驱动者，这时枚举器保留状态，没有一个线程坐在yield语句里干等下一次调用；调用方可以处理工作、返回消息循环或等待其他条件。yield不自行启动异步I/O或另建线程，与“它本身必阻塞调用者”是两回事。

await也不是一出现就“线程释放回池”。若awaiter已完成，它直接继续；若未完成，它挂起异步方法并返回调用方，调用方和宿主决定物理线程下一步。同步前段、同步等待、CPU算法仍会占用执行它们的线程，现代asyncMain的生成入口仍可同步等整个主任务。

### 原三批同步数据与Sleep1000

完整保三个中文值、每次Sleep1000、三个yield和foreach消费。这个特定消费代码会在每次MoveNext内部Sleep，连续消费时约有三个1秒同步等待；不是yield自身制造这三秒，也不是每个同步迭代器都具有同样代价。

<a id="c28-q12-a009"></a>
<!-- C28-D01-Q012-A-B009 -->
```csharp
IEnumerable<string> GetDataSync()
{
    Thread.Sleep(1000);  // 等1秒（同步阻塞）
    yield return "第一批数据";
    
    Thread.Sleep(1000);  // 又等1秒（同步阻塞）
    yield return "第二批数据";
    
    Thread.Sleep(1000);  // 再等1秒（同步阻塞）
    yield return "第三批数据";
}

// 调用方：
foreach (var data in GetDataSync())
{
    Console.WriteLine(data);
}
```

原0、1、2、3秒时间线保各次推进与打印，但第一行改为foreach第一次调用MoveNext才进入生产body，时间为示意近似值而非本章精确测速。

<a id="c28-q12-a011"></a>
<!-- C28-D01-Q012-A-B011 -->
```text
0s - GetDataSync()先返回序列；foreach首次MoveNext才进入生产body
0s - Thread.Sleep(1000) → 线程被阻塞，干等1秒
1s - yield return "第一批数据" → 回到 foreach，打印
1s - foreach 再次调 MoveNext()
1s - Thread.Sleep(1000) → 线程又被阻塞，干等1秒
2s - yield return "第二批数据" → 打印
2s - 再调 MoveNext()
2s - Thread.Sleep(1000) → 又被阻塞
3s - yield return "第三批数据" → 打印
```

“整个foreach连续运行这段Sleep例会占住消费线程等待”是这个程序的行为；yield后若不立即再推进，调用方也可去做别的事。普通拉取协议未规定从构造序列起到枚举结束必须独占同一线程，更没有禁止用户自己按帧或条件调度它。

### 原三批异步数据与Delay1000

异步流版完整保相同三条中文数据、每次Delay1000和await foreach消费；本次.NET10/C#8已跑全部三个值。Delay的未完成等待能挂起推进，yield本身负责产出而不是替底层开始工作。

<a id="c28-q12-a014"></a>
<!-- C28-D01-Q012-A-B014 -->
```csharp

{
    await Task.Delay(1000);  // 等1秒（异步，不阻塞线程）
    yield return "第一批数据";
    
    await Task.Delay(1000);  // 等1秒（异步）
    yield return "第二批数据";
    
    await Task.Delay(1000);  // 等1秒（异步）
    yield return "第三批数据";
}

// 调用方：
await foreach (var data in GetDataAsync())
{
    Console.WriteLine(data);
}
```

原异步时间线保所有阶段，改开始条件和B／C必池线程的说法；A／B／C是示意名称，不会要求三次都用不同物理线程或在精确1、2、3秒时刻恢复。

<a id="c28-q12-a016"></a>

```text

     （线程A 不需要干等这1秒！）

     （线程B 又可以去干别的）

```

表中暂停、恢复和是否异步四个维度保全，按准确范围修正。

<a id="c28-q12-a019"></a>
<!-- C28-D01-Q012-A-B019 -->
|  | `yield return` | `await` |
| --- | --- | --- |
| 暂停时线程在干嘛 | 本次MoveNext已返回；调用方决定做什么/何时再推进，本身不干等 | 未完成await挂起方法并返调用方；已完成路径可同步继续 |
| 暂停的机制 | 保留枚举状态，MoveNext返回true，Current提供本项 | 未完成awaiter登记续延并返回，完成路径直接GetResult继续 |

| 算不算异步 | 普通yield不自行安排线程/异步等待；可被分时宿主使用 | 表达异步等待，是否挂起与底层是否阻塞看实际状态/实现 |

原手写while语句的作用是展示消费者主动驱动，不是证明消费者必须一直停在同一循环里；该示意还需对相应枚举器负责Dispose。

<a id="c28-q12-a022"></a>
<!-- C28-D01-Q012-A-B022 -->
```csharp

{

    // 处理 item
}
```

保原最短“先Delay1000，再yield数据”例。这里await在未完成时挂起推进，随后yield完成本次产出；两者都可能把方法返回给不同层次的调用者，却并不因关键字不同就把yield列为阻塞等待。

<a id="c28-q12-a027"></a>
<!-- C28-D01-Q012-A-B027 -->
```csharp
async IAsyncEnumerable<string> GetDataAsync()
{
    await Task.Delay(1000);  // ← 未完成await挂起本次推进，物理线程返回调用方。
    yield return "数据";      // ← 完成本次产出并返回；没有线程在yield本身干等。
}
```

原自助餐／外卖两类比仍保：自助餐每次主动到取餐台取下一盘，外卖可登记到货通知；异步流是每次请求一盘、必要时等配送，再把这盘交给消费方。但你取一盘后可以离开取餐台做别的事，并非必须站在台前一直干等；这正是不能把Pull当线程阻塞原因的地方。

异步流并不是无条件“最高效”方案；工作量、同步完成比例、分配、数据源、批量策略和消费者都影响成本。下一节Unity的分帧驱动使用同一种yield迭代器能力，正好说明暂停产出可以让主线程去处理其他逻辑，而无需篡改C#关键字的语义。


<a id="c28-unity-coroutine"></a>
## Unity的yield分帧：同一种迭代器，不同的驱动节奏

Q13观察Unity协程等待时游戏还能继续，这个观察正确，也暴露了前面“C#yield本身干等占线程”的错误。Unity没有给yield return换一套语言含义：C#编译器仍生成可逐次推进的IEnumerator对象，Unity作为宿主决定什么时候推进。yield使本次MoveNext返回，等待条件未满足时引擎不必推进该协程，主线程可以运行其他C#逻辑及输入、更新、渲染等工作。[R28-S30]

### 保原foreach、手写推进与Unity三段输入

原普通foreach片段保，GetNumbers由调用方定义；它是一个同步消费者，生产体内部若做长计算或Sleep，当前推进调用会耗时。foreach不是只有控制台才可用，也不是普通yield唯一驱动者。

<a id="c28-q13-a004"></a>
<!-- C28-D01-Q013-A-B004 -->
```csharp

}
```

```csharp
}
```

## Unity是否“改写CLR”：语言、后端与引擎调度三层

Q14的准确回答是：实现这种IEnumerator协程调度不需要修改yield语言语义或为它重写CLR；Unity用标准迭代器对象，在引擎中提供调度。不能因此进一步断言Unity所有运行时与Microsoft CLR一字未改、Unity没有任何自有运行时或编译管线。Unity6.0所用后端包含Mono的JIT托管环境和IL2CPP将IL转换C++并编译native的AOT管线；具体可用后端和API取决于版本／目标平台。[R28-S34]

### 原Step1／WaitForSeconds1／Step2

保原Coroutine方法；body在首个MoveNext才开始，不是在返回IEnumerator时自动执行完。StartCoroutine则在其启动调用里推进首段，两者不能混淆。

<a id="c28-q14-a005"></a>
<!-- C28-D01-Q014-A-B005 -->
```csharp
// 你写的代码
IEnumerator MyCoroutine()
{
    Debug.Log("Step 1");
    yield return new WaitForSeconds(1);
    Debug.Log("Step 2");
}
```

原伪码完整保为“显示意图的元数据风格示意”：状态、当前yield对象与MoveNext分支确实解释暂停点。`<MyCoroutine>d__0`、`1__state`、`2__current`等不是合法直接书写的C#标识符，且伪码省Current属性、Reset／Dispose和终态处理；不是可以复制进C#项目的完整编译器源码。

<a id="c28-q14-a007"></a>
<!-- C28-D01-Q014-A-B007 -->
```text
// 编译器自动生成的类
sealed class <MyCoroutine>d__0 : IEnumerator
{
    public int 1__state;          // 记录执行到哪个 yield
    public object 2__current;     // 缓存 yield return 返回的对象
    public bool MoveNext()
    {
        switch (1__state)
        {
            case 0:
                Debug.Log("Step 1");
                2__current = new WaitForSeconds(1);
                1__state = 1;
                return true;
            case 1:
                Debug.Log("Step 2");
                return false;  // 协程结束
        }
        return false;
    }
}
```

编译器负责把yield生产体降成迭代器；运行时执行相应方法；Unity负责什么时候调用推进。这三层合作既不把Unity协程变成独立线程，也不否定其他用户在控制台、UI或自造宿主中按条件调IEnumerator的能力。实际编译器与实现细节可随Unity版本变化，不能说任何历史Unity都是同一个Roslyn版本或同一生成类型。

### 原帧时间线与主循环图完整保

图的用途是对比紧接消费和按帧条件恢复。Frame60只是假设帧率／scaled时间等条件的标签；不能把“首帧从Update推进”当所有StartCoroutine首段的固定时机，也不能保证每帧只用很少时间或不会卡住。

<a id="c28-q14-a033"></a>
<!-- C28-D01-Q014-A-B033 -->
```text
标准 C# foreach:                   Unity 协程:

{                                  Frame 2: Update → 条件不满足 → 不调 MoveNext()
    执行一段代码                          （主线程在渲染、物理、输入处理……）
```

原Update／协程／LateUpdate／渲染图也保，紧邻注明粗图所省的FixedUpdate、EndOfFrame及其他yield种类。性能采样里，首段通常出现在启动它的位置，恢复段可在DelayedCallManager下；这描述调度，不是对整个引擎实现“没有动CLR一根毫毛”的证据。[R28-S33]

## 谁替控制台与Unity调用MoveNext：语法和宿主都只是驱动者

Q15的主要判断正确：控制台里不是无人调用MoveNext，而是用户写了foreach，编译器生成相应消费代码。宿主类别不决定必须手动还是自动调用；控制台可以手写推进／LINQ，Unity也可以普通foreach或其他消费者。

### foreach原例及显式IEnumerator两种输入

保foreach消费者。普通GetNumbers返回序列，实际body由消费推进时执行；一项项产值后仍可执行循环body里的任意代码、break或异常处理。

<a id="c28-q15-a005"></a>
<!-- C28-D01-Q015-A-B005 -->
```csharp
foreach (var item in GetNumbers())
{
    Console.WriteLine(item);
}
```

原“编译器展开”示意保显式IEnumerator<int>／MoveNext／Current，并强调省略Dispose；对于这个已知接口型枚举器，完整写法应使用using或try/finally释放，不宣称粗while字面就是所有foreach的全部语义。

<a id="c28-q15-a007"></a>
<!-- C28-D01-Q015-A-B007 -->
```csharp

{
    int item = enumerator.Current;
    Console.WriteLine(item);
}
```

原手动循环也保，不用foreach可以自己安排推进；手动驱动不只while这一种节奏，可以按帧、按钮、条件或其他调度有序调用，仍需负责释放和不得并发误用。

<a id="c28-q15-a010"></a>
<!-- C28-D01-Q015-A-B010 -->
```csharp

while (enumerator.MoveNext())  // ← 手动调用
{
    Console.WriteLine(enumerator.Current);
}
```

Unity拿到IEnumerator后，以StartCoroutine推进首段，之后按yield对象／条件／阶段安排。MoveNext返回bool，yield出的null、YieldInstruction、等待对象等从Current取得，不是MoveNext直接返回YieldInstruction。普通迭代器与宿主调度正是同一个语言机制的不同消费方式；不能据此把Unity工作流称“假的异步”。

<a id="c28-q15-a018"></a>
<!-- C28-D01-Q015-A-B018 -->
| 场景 | 谁在调用 `MoveNext()` | 调用节奏 |
| --- | --- | --- |
| 控制台 `foreach` | **C# 编译器生成的 `while` 循环**​ | foreach按消费循环推进，body/break/异常也决定何时继续 |
| Unity 协程 | **Unity 引擎主循环里的协程调度器**​ | StartCoroutine先推进首段；后按yield种类/条件/帧阶段恢复 |

原六步设计顺序保：取得／登记枚举器、判断适当yield条件、调用MoveNext、从Current读其yield值、以后按条件恢复、MoveNext false后结束管理。把“每帧固定阶段检查所有协程”缩为各类指令和就绪状态的调度示意；未就绪时不要求每个协程每帧执行body。

“没有外部驱动就不会进入yield生产体”是正确前提，但LINQ、ToList、引擎和其他消费者也可能隐式驱动。关键不是用户是否手写MoveNext字样，而是运行中的消费方／宿主如何推进、读取、处理和结束该枚举器。

## 确认foreach语法糖的边界与停止责任

Q16这次理解保留：“我们写foreach语句，编译器将其转换为相应的枚举／消费代码，运行时执行这些调用。”语法糖来自语言，用户使用它表达循环，并非用户自己定义一种新语法；它没有自动替生产者另开线程。

原两片段的代码和隐藏调用位置完整保，仍以GetNumbers／MoveNext／Current的实际迭代协议说明。

<a id="c28-q16-a005"></a>
<!-- C28-D01-Q016-A-B005 -->
```csharp
// 你写的代码
foreach (var item in GetNumbers())

    Console.WriteLine(item);
}
```

### SC是调度抽象，不是必须回原线程的通用邮局

原邮递员类比保：派生SC知道怎样安排一段代码，Post表达投递，不等待其执行完成。一般SC不必绑定单一线程，默认类的Post与GUI重写也不同；Task默认await在等待未完成操作前登记捕获的上下文／调度器，完成时执行已保存安排。已完成Task或自定义awaiter不必经过相同Post。[R28-S01][R28-S27]

原思考区的Post／Send对照也要保留：Post发起异步投递，调用者不等回调执行完成；Send发起同步调用，正常返回前回调已经执行完成，具体宿主可能在派发期间同步等待。同步不等于必切到另一个线程：固定.NET v10基类Send直接在当前调用线程调用回调，基类Post则排入线程池。派生SC可重写安排或不支持Send，不能保证一律投到UI或一律换线程。这恢复原问答技术对照，区别于默认Task await选择继续目标。[Send合同](https://learn.microsoft.com/en-us/dotnet/api/system.threading.synchronizationcontext.send?view=net-10.0)、[固定实现](https://github.com/dotnet/runtime/blob/v10.0.0/src/libraries/System.Private.CoreLib/src/System/Threading/SynchronizationContext.cs)。

## 取消I/O、取消等待和下载例的完整生命周期

Q18保原2GB下载、用户取消／窗口关闭、上传浪费资源等用途：应用需要结束不再需要的工作、观察终态、清理资源，并避免在已经失效的UI上继续更新。但“发取消信号”不保证硬件立刻停止、远端撤销效果、缓冲从此不会再被使用或所有Task立刻Canceled。

### 原token传入与取消按钮位置

### 原书WithCancellation主要取消的是等待

原书担心远端请求效果难撤回与完成竞争，提供原Task与令牌完成TCS的WhenAny竞争：取消任务先被选中，外层等待抛OCE；原Task胜出，读取它的真实结果／异常。它未把token传进底层原操作，不能解释成包装方法停止硬件。原Windows“通常不能取消未完成IO”表述过宽：Vista已有本地CancelIoEx／CancelSynchronousIo等请求取消入口，远端效果和取消race仍不是它们保证撤销的事。

<a id="c28-with-cancellation-book"></a>
```csharp
private struct Void { } // 因为没有非泛型的 TaskCompletionSource 类

private static async Task<TResult> WithCancellation<TResult>(this Task<TResult> originalTask,
    CancellationToken ct) {
    // 创建在 CancellationToken 被取消时完成的一个 Task
    var cancelTask = new TaskCompletionSource<Void>();

    // 一旦 CancellationToken 被取消，就完成 Task
    using (ct.Register(
        t => ((TaskCompletionSource<Void>)t).TrySetResult(new Void()), cancelTask)) {

        // 创建在原始 Task 或 CancellationToken Task完成时都完成的一个 Task
        Task any = await Task.WhenAny(originalTask, cancelTask.Task);

        // 任何 Task 因为 CancellationToken 而完成，就抛出 OperationCanceledException
        if (any == cancelTask.Task) ct.ThrowIfCancellationRequested();
    }

    // 等待原始任务(以同步方式)：若任务失败，等待它将抛出第一个内部异常，
    // 而不是抛出 AggregateException
    return await originalTask;
}

```

Void辅助“无非泛型TCS”是原Framework时代前提，现代库可有不同API；既有写法仍可工作。最终await在原Task已赢并完成时可以同步取结果，普通await并不是阻塞等待API；其传播的保存异常也可能本来就是Aggregate对象，不能照原注释无条件保证绝不是AggregateException。

受控本章原泛型wrapper／现代Task.WaitAsync都是取消外层等待后原Task仍pending，后来正常得到42。双方已完成且token已取消时，本次返回原7；完成竞争不是“token一取消就必须战胜已经完成的任务”。原任务的资源与错误观察仍由应用管理，不把外层取消当终止底层IO。[R28-S24]

WhenAll遇故障优先Faulted并保全故障，只有无故障且至少取消时才Canceled；原Q18写成取消优先是错。WhenAny外层RanToCompletion只给winningTask，winner可Faulted，其他task继续；本章真实outer成功／winner故障／remaining pending后来9，不能因胜者被选中就认为全组已停止。await一般传播一项保存异常，不承诺时间上的最先／最后故障；观察整个WhenAll.Exception和各任务能取得完整失败。[R28-S10][R28-S11]

## 必须同步的阶段、文件句柄模式与“假异步更慢”的边界

Q19的正确提醒保：API的Async后缀不等底层一定有无需专属阻塞线程的原生I/O。原书28.12首先讲FileStream构造／Win32 CreateFile的同步打开阶段、远端路径可能数秒等待，再讲FileStream读写模式。打开时配置overlapped影响随后合适读写，并没有让构造／文件属性／目录同步API自动成为异步调用。

原“设备驱动非常简单／没实现IRP异步所以任何Async只能同步”是过度推断。同步入口、同步句柄、具体操作可能同步处理、实现用工作线程包装，与设备／驱动根本没有异步能力不同。原T还把命名管道的PIPE_TYPE_MESSAGE与异步开关混同，应纠：消息／字节传输模式与overlapped／PipeOptions.Asynchronous配置是不同维度。

<a id="c28-q19-a009"></a>
<!-- C28-D01-Q019-A-B009 -->
| 场景 | 原因 |
| --- | --- |
| **NTFS 元数据操作**​ | 所列.NET/Win32入口常以同步形式执行；可有磁盘/远端/驱动等待，非总内存即成 |
| **控制台 I/O**​ | Console.ReadKey为同步键读取API；具体控制台/重定向/其他流能力需分，不按驱动“简单”推全系统 |
| **某些命名管道**​ | 同步/overlapped句柄与pipe message/byte模式是不同配置；未Async不等驱动不支持 |
| **某些网络重定向器**​ | 具体redirector/资源/operation和版本需核，不能见远程文件即断无异步 |

<a id="c28-io-priority"></a>
### 补原28.13的主线：CPU优先级不等I/O资源优先级

低CPU优先级线程仍可能迅速提交大量磁盘／网络请求，影响前台资源等待；原书用这个例说明不能只降低Thread.Priority就解决I/O压力。原native background mode通过SetThreadPriority／SetPriorityClass的特定Begin／End值调整相应资源调度，而普通THREAD_PRIORITY值主要影响CPU调度；Task PreferFairness也是任务调度建议，不是给IRP或设备设置I/O优先级。[R28-S39]

原书ThreadIO／BackgroundProcessingDisposer示意的目的，是在合法当前线程／进程范围进入background模式并在退出时恢复，native API、错误和资源寿命需按平台核。Begin／End线程模式要求当前同一物理线程，不应拿普通using包一个可能换线程的await就认为恢复正确。本章只核原意、API条件和native形状，不调整宿主优先级、不安装Windows/Unity工具或运行压力负载。

综观这些原例，判断性能与正确性要先确定实际操作、资源／句柄、平台、具体库、语言时代、同步前段、是否已成、取消响应和调度条件。所有源问答的代码、ASCII、输出、表行和不同参数用途都保在相应位置；纠错不替它们制造未出现的错误，也不以现代API或一次实测倒判历史主线。
