## 本章的主线与十类成员

源中的成员声明、编译后类型/成员资料、运行时访问和调用分别是不同层次。设计组件时，需要同时明确谁能使用一个类型/成员、哪些行为允许派生类型改变、怎样避免今后的版本演进破坏已有调用者。

原总览列出十类成员，保留如下。

| 成员 | 主要含义 | 元数据/实现要点 |
| --- | --- | --- |
| 常量 | 编译期可求值的符号 | 类型中的const成员隐含static（不能另写static）；有相应声明/常量资料，使用点可替换，不各自拥有用户IL方法体；局部const不属此成员分类 |
| 字段 | 实例或类型的存储状态 | 字段结构记录；初始化行为在相应初始化逻辑中 |
| 实例构造器 | 建立对象实例状态 | 特殊方法及相应实现 |
| 类型构造器 | 建立静态状态 | 类型初始化方法及执行规则 |
| 方法 | 查询/改变状态或实现操作 | 名称、签名、标志与相应方法体/实现形式 |
| 操作符重载 | 自定义运算行为 | 相应特殊方法，不只一个新符号 |
| 转换操作符 | 隐式/显式类型转换 | 相应方法及语言选择规则 |
| 属性 | 以属性语法提供访问逻辑 | 属性资料及访问器方法，未必独立存储字段，也不自动保证状态安全 |
| 事件 | 提供订阅/通知协议 | 事件资料及相关访问器；声明不等于已经触发通知 |
| 嵌套类型 | 类型中定义的另一类型 | 类型及嵌套关系资料，不是外部类型自动拥有的实例字段 |

原“为各种成员生成元数据和IL”是编译职责总述，不能说字段/const/abstract/extern等每种成员都有独立用户IL体。实际CLI表名为Field、Property等，属性/事件访问器另属方法。[第1章](第01章-CLR的执行模型.md#c01-metadata-il)保留了Employee.Name/CalculateSalary、Console引用、两个加法和元数据/IL对照；本章关注这些信息怎样参与成员访问和调用。

C#、VB.NET、F#等编译器按共同CLI格式表达相应定义与引用，使CLR可以处理；不同源语言生成的具体记录和代码不必逐字相同。跨语言API互操作还要满足相应CTS/CLS及语言能力，不能仅靠“存在IL”保证任何API在所有语言里同样好用。

<a id="c06-visibility"></a>
## 可见性、默认权限与嵌套类型

<a id="c06-defaults"></a>
### “类型默认internal，成员默认private”需要哪些条件

命名空间范围的普通顶级类型，未写public/internal时通常是internal。类/结构中的普通成员以及其嵌套类型通常默认private；不能把顶级默认规则无条件用到所有嵌套类型或接口/枚举成员。

两个独立类型片段E06-01，保留原MyClass默认示例：

```csharp
class MyClass // 顶级类型：默认internal
{
}
```

```csharp
public class MyClass
{
    int _myField;     // 默认private
    void MyMethod() { }
}
```

传统C#5接口的普通契约成员隐式public，声明规则不同于类成员；enum成员也为public，显式接口实现又有特殊访问语法，不能简单从是否写public推断调用形式。现代差异：C#8之后默认接口实现及成员权限扩展，不能把旧接口规则升级为所有版本“接口任何成员必public、任何public修饰都非法”。

默认限制体现谨慎公开的设计目的：先控制实现细节和依赖，再有意识提供外部契约。internal仍可在同程序集/适用友元关系中被使用，private也不是对恶意代码的系统级安全沙箱。

减少无意公开的细节能减轻外部耦合和API误用，也通常给内部重构留下更多空间；已经依赖internal的同程序集或朋友调用者仍可能受到修改影响，不能说任何内部修改都绝对没有影响。

<a id="c06-nested-container"></a>
### “任何嵌套类型”是什么意思

嵌套类型是外部类型声明中的一个类型成员。原ContainerClass例不仅说明私有NestedClass可从外部类型内部使用，还要分清它本身的成员权限。

类型片段E06-02：

```csharp
public class ContainerClass
{
    private class NestedClass
    {
        public void NestedMethod() { }
    }

    public void ContainerMethod()
    {
        NestedClass nested = new NestedClass();
        nested.NestedMethod();
    }
}

public class AnotherClass
{
    public void SomeMethod()
    {
        // ContainerClass.NestedClass nested = new ContainerClass.NestedClass();
        // 反例：私有嵌套类型本身不能在此访问。
    }
}
```

嵌套类型的方法能在相应规则下访问外部类型的private等成员，这正是表6-1反复提到嵌套类型的原因。C#嵌套实例不像某些语言自动捕获一个外部实例；要访问外部的实例字段，仍需要实际实例。下一例主动创建一个BaseClass，说明“访问权限”与“实例从哪里来”两件事。

<a id="c06-accessibility"></a>
## 表6-1：成员可访问性

<a id="c06-accessibility-table"></a>
### 历史CLR/C#术语表

下表保留原书C#5语境中的六种对应。类型本身必须在该访问点可见，才能进一步判断成员；同程序集/派生关系等条件并不跳过这个前提。

| CLR术语 | C#5表达 | 访问条件概要 |
| --- | --- | --- |
| Private | private | 定义类型及相应嵌套范围中的代码 |
| Family | protected | 定义类型/嵌套范围，及满足规则的派生类型访问 |
| Family and Assembly | C#5无直接修饰语法 | family条件与assembly条件同时满足 |
| Assembly | internal | 当前程序集及适用友元范围 |
| Family or Assembly | protected internal | family或assembly条件满足一边 |
| Public | public | 类型可见且其他相关调用条件满足的公开使用 |

现代差异：C#7.2引入private protected，对应相应“且”范围，不能说C#直到今天都不支持。适用的InternalsVisibleTo还会扩展相关assembly可访问关系；它不开放private成员。

设计时可用private隐藏实现，以public形成外部契约，按需要用protected给派生类型扩展点、internal给组件协作代码；protected internal适合两类访问都需要的相应框架成员。它们控制访问关系，不代替类型自身可见性及安全/信任判断。

<a id="c06-assemblya-base"></a>
### AssemblyA的1/2/3/4/5与嵌套访问

两程序集示例E06-03a，先编为AssemblyA.dll：

```csharp
namespace AssemblyA
{
    public class BaseClass
    {
        private int _privateField = 1;
        protected int ProtectedMethod() { return 2; }
        internal int InternalMethod() { return 3; }
        protected internal int ProtectedInternalMethod() { return 4; }
        public int PublicMethod() { return 5; }

        private class PrivateNestedClass
        {
            public int TestAccess()
            {
                BaseClass outer = new BaseClass();
                int x = outer._privateField;       // 嵌套类型可访问外部private
                int y = outer.ProtectedMethod();
                return x + y;
            }
        }

        public int TestNested() { return new PrivateNestedClass().TestAccess(); }
    }

    internal class AnotherClassInSameAssembly
    {
        public void Test()
        {
            BaseClass b = new BaseClass();
            // int a = b._privateField;     // private：反例
            // int c = b.ProtectedMethod(); // 非派生类型protected：反例
            int d = b.InternalMethod();
            int e = b.ProtectedInternalMethod();
            int f = b.PublicMethod();
        }
    }
}
```

PrivateNestedClass访问实际outer的私有1和protected2，说明嵌套权限；与外部类型同程序集的无关类能取internal3、protected internal4、public5，不能取private1/protected2。它们是不同场景，不能只用“嵌套能访问private”概括所有权限。

两程序集示例E06-03b，编为AssemblyB并参考AssemblyA.dll：

```csharp
namespace AssemblyB
{
    public class DerivedClass : AssemblyA.BaseClass
    {
        public void TestAccessFromDerived()
        {
            // int a = this._privateField;     // private：反例
            int b = this.ProtectedMethod();
            // int c = this.InternalMethod(); // 本例无友元：跨程序集internal反例
            int d = this.ProtectedInternalMethod();
            int e = this.PublicMethod();
        }
    }

    public class UnrelatedClass
    {
        public void Test()
        {
            AssemblyA.BaseClass b = new AssemblyA.BaseClass();
            int f = b.PublicMethod();
            // 本例无继承/友元，其他上述成员不能在这里直接访问。
        }
    }
}
```

派生类型在另一个程序集里仍可以通过this访问protected2和protected internal4；无关类型仅能访问public5。不要把两个namespace名字不同当作程序集边界证据，示例的条件是**实际分别编成两个程序集**。

<a id="c06-accessibility-example-table"></a>
### 对照具体访问者的六行详细表

原另一张表增加了“在例子中的体现”这一列，逐行将术语对应到BaseClass、PrivateNestedClass、DerivedClass和AnotherClassInSameAssembly。它与前面的术语概览用途不同，完整保留如下；这个两程序集例没有声明友元。

| CLR术语 | C#5表达 | 描述 | 在原例中的具体体现 |
| --- | --- | --- | --- |
| Private | private | 定义类型及相应嵌套范围中的方法可访问 | `_privateField`由BaseClass自身或PrivateNestedClass的方法按规则访问，后者主动取得outer实例 |
| Family | protected | 定义类型/嵌套范围，以及满足规则的派生类型访问 | `ProtectedMethod()`可供BaseClass、其嵌套类型及跨程序集DerivedClass使用；外部派生的原例用this，不开放任意BaseClass接收者 |
| Family and Assembly | C#5无直接修饰语法 | family与assembly条件同时满足 | 原C#5数值例没有该修饰成员；现代private protected对应相应“且”关系，适用friend仍需按规则判断 |
| Assembly | internal | 当前程序集及适用友元范围可访问 | 本例`InternalMethod()`可由AssemblyA中的AnotherClassInSameAssembly使用；AssemblyB未声明friend，DerivedClass不能仅凭继承访问它 |
| Family or Assembly | protected internal | family或assembly条件满足一边 | `ProtectedInternalMethod()`既供AssemblyA的AnotherClassInSameAssembly使用，也供AssemblyB的DerivedClass按family路径使用；并集不同于“且” |
| Public | public | 类型及相关访问条件满足时可公开使用 | 本例BaseClass为public，`PublicMethod()`可由两个程序集中的派生/无关类型调用，包括AssemblyB的UnrelatedClass |

这些访问关系不能简单排成一条由小到大的等级；family和assembly控制的集合不同，“且/或”分别表达相应交集/并集。现代friend、类型可见性和protected接收者条件仍适用，不能从表中省略的背景推出权限都无条件成立。

protected实例成员还有接收者规则：外部派生类型代码不能仅因自己“是派生类”，就任意从一个静态类型为BaseClass的无关基类实例读取protected实例成员。原代码使用this，满足这个场景；它不是让任何基类变量都自动开放protected。[访问修饰符说明](https://learn.microsoft.com/en-us/dotnet/csharp/programming-guide/classes-and-structs/access-modifiers)及[protected规则](https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/keywords/protected)可核对。

<a id="c06-protected-internal"></a>
## protected internal与protected

<a id="c06-protected-or-table"></a>
### 核心区别是OR，不是AND

| 访问情形 | protected | protected internal |
| --- | --- | --- |
| 定义类型及相应范围 | 可访问 | 可访问 |
| 同程序集的无关类型 | 不因“同程序集”获得protected权限 | 本例可按internal一边访问 |
| 不同程序集的派生类型 | 按family及接收者规则访问 | 可按family一边访问 |

原答用另一套字符串字段说明区别。保留两个程序集中的不同类型与条件，不与前面的1/2/3/4/5方法例合并。

两程序集示例E06-04a，AssemblyA.dll中的类型片段：

```csharp
public class MyBaseClass
{
    protected string ProtectedMember = "I am protected.";
    protected internal string ProtectedInternalMember = "I am protected internal.";
}

public class SomeHelperClassInAssemblyA
{
    public void Test()
    {
        MyBaseClass obj = new MyBaseClass();
        // string value1 = obj.ProtectedMember; // 非派生类：反例
        string value2 = obj.ProtectedInternalMember;
    }
}
```

E06-04b，另一程序集参考它：

```csharp
public class MyDerivedClassInAssemblyB : MyBaseClass
{
    public void Test()
    {
        string value1 = this.ProtectedMember;
        string value2 = this.ProtectedInternalMember;
    }
}

public class AnotherClassInAssemblyB
{
    public void Test()
    {
        MyBaseClass obj = new MyBaseClass();
        // string value1 = obj.ProtectedMember;         // 本例不可访问
        // string value2 = obj.ProtectedInternalMember; // 本例无派生/友元，也不可访问
    }
}
```

| 修饰符 | 原生活类比的设计意图 | 使用场景 |
| --- | --- | --- |
| protected | 家族的成员与相应范围可用，住同一小区的无关邻居不因此获得权限 | 供派生类型使用/重写的核心逻辑或钩子 |
| protected internal | 同组件内共享，同时允许外地家族成员按派生规则使用 | 同程序集助手及外部派生扩展都需要的成员 |

口诀可理解为“按family，或按assembly关系”。不是每次都必须同时两者满足；若有friend关系，还须按真实访问上下文看，而非只机械比文件夹或namespace。

<a id="c06-friend-assembly"></a>
## 友元程序集与PublicKey

<a id="c06-friend-key"></a>
### Wintellect公钥在声明里做什么

InternalsVisibleTo让适用的internal等成员对指定友元程序集开放，不把它们全部变成public，也不开放private。原Wintellect属性是字符串示意，省略号不能当有效公钥直接编译：

```text
[assembly: InternalsVisibleTo("Wintellect, PublicKey=12345678...90abcdef")]
```

在原Framework强名称场景里，声明需要友元的简单名称和**完整公钥PublicKey**，不是短PublicKeyToken，也不附dll路径、文化、版本等资料。公钥帮助匹配相应程序集身份；对应私钥用于签名，但不能把这种封装身份判断写成“公钥认证现实发布者可信、彻底建立安全边界”。[IVT API](https://learn.microsoft.com/en-us/dotnet/api/system.runtime.compilerservices.internalsvisibletoattribute?view=netframework-4.8)明确区分signed/unsigned及完整公钥条件。

原答把公钥比作“锁的齿形图”，能帮助理解为什么简单名之外还有匹配资料。该类比只表示身份与访问匹配，不是说private/internal能阻止所有恶意或全信任代码，或所有运行时都强制相同验签规则。

<a id="c06-friend-unsigned"></a>
### 未签名朋友与/out

相应Framework未签名程序集可以只写友元简单名。原答“只写名字必定严重安全漏洞”“所有声明必须带公钥”过度概括了强名称场景；不能因此删去合法未签名模式。

两程序集类型片段E06-05：主程序集声明一个供测试/兄弟组件访问的内部方法，编成Library.dll。

```csharp
using System.Runtime.CompilerServices;
[assembly: InternalsVisibleTo("Friend")]

public class Library
{
    internal static int ReadInternal() { return 7; }
    private static int ReadPrivate() { return 8; }
}
```

调用方完整程序，明确输出名Friend.exe并参考Library.dll：

```csharp
using System;
class Program
{
    static void Main()
    {
        Console.WriteLine(Library.ReadInternal());
        // Library.ReadPrivate(); // friend没有开放private：反例
    }
}
```

输出7。换成未被声明的其他程序集名称，其直接internal调用就不满足这条朋友身份。原书强调命令行友元编译使用`/out:<file>`，让编译器在绑定外部参考时知道输出程序集身份；不是给文件随意改后缀就能认证朋友，也不表示私钥必须与主库同一把。

现代差异：现代.NET仍支持这些语言/API访问资料，但强名称的运行时验证和安全作用不照搬Framework传统描述；源中的“加载时比较token”不能替代完整key身份及实际运行时规则。[第3章](第03章-共享程序集和强命名程序集.md#c03-signing)已区分身份、完整性和信任。

<a id="c06-static-class"></a>
## 静态类的骨架和实际用途

<a id="c06-static-skeleton"></a>
### 为什么AStaticClass没有业务功能仍有教学意义

原完整类型片段E06-06保留方法、属性、字段、事件：

```csharp
using System;
public static class AStaticClass
{
    public static void AStaticMethod() { }
    public static String AStaticProperty
    {
        get { return s_AStaticField; }
        set { s_AStaticField = value; }
    }
    private static String s_AStaticField;
    public static event EventHandler AStaticEvent;
}
```

空方法没有业务操作，属性只是读写字段；但属性确实可改变/读取状态，并非整个类型“运行时什么也不会发生”。事件没有提供触发代码不等于必然无人订阅，外部仍可以按公开事件声明订阅/退订。声明和触发是两个动作。

作者让读者编译并用ILDasm观察结构：静态类在元数据中标为abstract与sealed，不能实例化或继承；不生成实例构造器，但可以有类型初始化逻辑。属性的访问器及事件相关方法等可以在元数据/IL中观察。字段这里**显式写了private**，不是一个证明默认private的独立证据。

原“骨骼模型与肌肉/器官”类比说明这个类型主要演示声明与生成结构，业务逻辑不是示例目标。骨架仍有可观察的字段/访问器，不应把“没完整业务”说成“完全不存在执行逻辑”。

<a id="c06-static-boundaries"></a>
### static类的限制和有用成员

静态类不能作为普通字段/实参/局部变量的实例类型，也不能new或派生；这不意味着“每一个语法成员都要写static”：它可以包含常量及嵌套类型等，嵌套的类型本身又有自己的成员规则。C#源码也不能用普通`abstract sealed class`拼写代替static class。

原答给出的实用例是Math.Sqrt、Console.WriteLine以及DateTime.Now：前两者展示静态工具操作，后者是值类型DateTime上的静态属性，并不证明DateTime本身是static class。无状态工具更容易理解/测试，但不能由此断言静态类里任何可变状态都非法；共享状态还需对应同步和生命周期设计。

原答还提到静态工具类可作为相应扩展方法的容器。这同样是有具体调用用途的设计，与AStaticClass主要演示声明骨架的目的不同。

<a id="c06-partial"></a>
## partial分部类型

partial由C#编译器把相应类型的声明部分合并，CLR面对的是编译后的类型，不重新处理源文件“分部”的组织方式。声明部分需符合对应类型与编译范围规则，不能跨两个独立程序集自动拼成同一个类型。

原列举了三种目的：多人/源代码管理分工，按逻辑单元组织（甚至同一文件的不同部分），以及生成代码与手写代码分离，例如WinForms的designer.cs。它们是不同组织场景，不能只说“一个类拆几个文件”就略过合作和生成代码的条件。分部方法的后续规则见[第8章](第08章-方法.md#c08-partial-method)。

<a id="c06-method-signatures"></a>
## 重写、重载与返回类型

<a id="c06-override-return"></a>
### 原问题先问重写，后来纠正为重载

两种问题都保留，不能因为用户改口就删除第一次讨论。重写提供基类虚/抽象成员的新实现；重载按同一类型中不同签名表达同名操作。相同名字并不意味着同一种规则。

重写还要满足可访问性规则，C#不允许任意把protected重写成public等来放宽。跨程序集重写protected internal时另有按protected表达的规则，不能把“相同可访问性”记成任何上下文都机械使用同一串修饰符。CLI底层能够表示某些放宽访问的重写，不等于C#源码自动允许；返回类型、访问级别与重载签名是不同条件。

反例E06-07，故意保留不兼容返回类型，不能编译：

```csharp
class BaseClass
{
    public virtual string GetValue() { return "base"; }
}
class DerivedClass : BaseClass
{
    public override int GetValue() { return 42; } // CS0508
}
```

原类型安全说明可用方法片段理解，假设上面不兼容重写被允许：

```csharp
BaseClass obj = new DerivedClass();
string result = obj.GetValue(); // 静态基类契约需要string，不能任意收到int
```

C#5要求相应返回类型匹配等条件。现代差异：C#9引入受限制的协变返回，并需要支持的运行时；不能说所有旧CLR早已同样支持而仅是C#晚开放。

现代类型/方法片段E06-08，C#9及支持的.NET5+等环境：

```csharp
class Animal { public virtual Animal GetSelf() { return this; } }
class Dog : Animal { public override Dog GetSelf() { return this; } }

// 放在适当方法内：
Animal a = new Dog();
Animal animalRef = a.GetSelf();
Dog dogRef = ((Dog)a).GetSelf();
```

Dog可作为Animal结果，和string改int的反例不同；两引用均可指同一个Dog。使用相同源编译器但目标传统Framework也可能因运行时不支持协变返回而失败，不是把语言版本数字写9就保证有效。[override规则](https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/keywords/override)与[C#9历史](https://learn.microsoft.com/en-us/dotnet/csharp/whats-new/csharp-9)说明其时代和语义。

原回答提出的替代思路也保留：确有多种结果类型时，可按业务契约考虑泛型结果，或返回共同基类/接口再由调用方处理具体类型。它们仍需要可成立的类型与操作契约，不能直接解除重写的限制。

<a id="c06-overload-signature"></a>
### 返回类型不同不能单独构成C#重载

反例E06-09保留原Process，以及另一个Calculator.Add原例；两段独立片段分别不能编译：

```csharp
class MyClass
{
    public string Process(int x) { return x.ToString(); }
    public int Process(int y) { return y; } // CS0111，仅返回类型/参数名不同
}
```

```csharp
class Calculator
{
    public int Add(int a, int b) { return a + b; }
    public string Add(int x, int y) { return (x + y).ToString(); } // CS0111
}
```

C#方法签名包括名称、泛型形参数数量，以及参数数量、相应类型/顺序和传递模式；不计返回类型、参数名字、泛型形参名字、约束或params标记。ref/out/in也不能只靠相互交换构成同类型中的重载；按值与相应按引用的区别又需按规则判断。原答把params当作可单独区分的签名修饰符，并漏泛型arity，需要一并修正。[签名规范](https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/language-specification/basic-concepts)给出准确边界。

原假设调用`string result = Add(1, 2)`和`var result = Calculate(5)`不能依靠接收变量类型，替两个被禁止声明的返回版本自动择优。这说明这套语言规则的调用边界；不能把“其他语言理论上无法设计这样的规则”当成规范证明。

<a id="c06-overload-alternatives"></a>
### 原三个替代方法怎样正确表达

类型片段E06-10，方法名不同直接表达结果：

```csharp
public class Calculator
{
    public int AddInt(int a, int b) { return a + b; }
    public string AddString(int a, int b) { return (a + b).ToString(); }
}
```

原IAddable泛型例写`return a + b`，普通接口约束不自动赋予T这个运算符，不能当可运行的C#5例。修正类型/方法片段E06-11保留“通过约束表达加法能力”的目的，改用真实接口方法：

```csharp
public interface IAddable<T> { T Add(T other); }
public struct Number : IAddable<Number>
{
    public int Value;
    public Number(int value) { Value = value; }
    public Number Add(Number other) { return new Number(Value + other.Value); }
}
public class Calculator
{
    public T Add<T>(T a, T b) where T : IAddable<T>
    {
        return a.Add(b);
    }
}
```

用Number1、Number2调用得到Value3。现代泛型数学可用C#11+和对应接口/运行时表达静态运算能力，那是后来的路线，不把它偷偷写成旧IAddable已有operator契约。

原两个TryAdd的目的仅为签名比较；合法抽象签名片段E06-12：

```csharp
public abstract class Calculator
{
    public abstract bool TryAdd(int a, int b, out int result);
    public abstract bool TryAdd(int a, int b, out string result);
}
```

它们的out参数实际类型不同，因此不同签名；两个都用out不会让“仅ref/out不同”成为合法区分理由。此例没有指定加法算法、溢出或返回bool的业务契约，不虚构已经运行的TryAdd结果。调用者应提供具有已知类型的输出变量，不能期待一个无类型结果自动从返回bool挑选。

<a id="c06-il-return-types"></a>
### IL允许仅返回类型不同，为什么C#不用

CLR/CIL的完整方法引用签名包含返回类型，能够表达同名、同参数却不同返回的相应方法。C#的重载签名选择规则更受限制。这是底层表示能力与语言规则的区别，不能把两者都称为同一套“签名必须全一样”。

作者用ILAsm创建了两个`F(int32)`，一个返回int32，一个返回string；调用IL分别明确写返回签名，验证和运行成功，输出5及same parameter。与两个C# Add声明报CS0111的反例形成对照。原Calculate(5)/var假设保留用来说明C#调用语法的歧义问题，不把设计理由推测写成CLI规范不允许的事实。

原回答另从语言设计角度解释：不按返回类型区分可以让无接收上下文的调用更易读，简化相应重载/推断规则，也符合Java、C++等语言常见方法重载的使用习惯。这些是理解该选择的理由，不能据此证明规范制定者唯一的历史动机，或断言其他语言不能设计另一种规则。原书“除IL汇编以外未发现利用该特点的语言”也只是作者在当时的观察，不是对所有语言和版本的禁止条款。

<a id="c06-call"></a>
## CLR的call与callvirt

call可以表达静态或相应实例/虚方法的直接调用；例如base的实现调用可以采用非虚路径。callvirt用于实例调用及相应空引用检查，可以在虚方法需要时参与派发，但也能用于非虚实例方法，**不一定每次都做虚表动态查找**。不能由指令名有virt就断言方法声明必virtual。

原版本设计关键字也需保留各自意义：abstract提供抽象类型/未在此实现的成员；virtual提供可重写点；override提供相应重写；sealed限制继承/进一步重写；new显式隐藏相关基类成员。类型的成员资料、调用指令和源码关键字分别解释，不能见一个关键字就假定所有机器码调用方式。

<a id="c06-virtual-design"></a>
## Set.Find：少量核心虚扩展点

原书建议慎增虚方法，理由涉及分派成本、优化难度、继承契约及版本演进。JIT无法知道目标时确实较难内联；但目标可知或有适用优化时，虚调用可去虚化甚至内联，不能说任何JIT永远不能内联任何虚方法。

原版本风险例也保留：已发布的虚方法行为改变，或后来被sealed限制进一步重写，可能破坏现有派生类对该契约的使用。是否破坏要按实际改动和派生依赖判断，不把“有虚方法”本身当作必然无法升级组件的结论。

<a id="c06-set-find"></a>
### 简便重载转到一个核心方法

原Set有两个非虚简便Find和一个参数齐全的虚Find。它的最后参数实际是范围计数：`m_length - startIndex`，不能叫endIndex却按count传入。下面补可观察实现，保留三种入口目的。

完整程序E06-13：

```csharp
using System;

class Set
{
    private object[] items;
    private int m_length;
    public Set(object[] values) { items = values; m_length = values.Length; }
    public int Find(object value) { return Find(value, 0, m_length); }
    public int Find(object value, int startIndex)
    {
        return Find(value, startIndex, m_length - startIndex);
    }
    public virtual int Find(object value, int startIndex, int count)
    {
        return Array.IndexOf(items, value, startIndex, count);
    }
}

class TracedSet : Set
{
    public TracedSet(object[] values) : base(values) { }
    public override int Find(object value, int startIndex, int count)
    {
        Console.WriteLine("core:" + startIndex + "/" + count);
        return base.Find(value, startIndex, count);
    }
}

class Program
{
    static void Main()
    {
        TracedSet set = new TracedSet(new object[] { "A", "B", "C" });
        Console.WriteLine(set.Find("B"));
        Console.WriteLine(set.Find("C", 1));
    }
}
```

实际输出：

```text
core:0/3
1
core:1/2
2
```

使用者保留简便调用；派生类只重写核心操作，两个包装都能转到它。基类减少公开扩展点，有助于控制演进负担。但非虚包装仍被调用者和派生代码使用，其参数处理、缓存和调用次数变化也可能影响行为；“非virtual，所以随便改变完全不会影响派生类”错误。继承契约少不等于不存在契约。

原组件总览的五项特点也由此联系起来：组件有发布边界和身份；通过动态引用保持自身而非被复制成调用方源代码；指明依赖；版本资料参与管理；提供类/成员文档。身份包含名称/版本/文化/适用的公钥等，不是组件永远不能改版或每个组件必须相同强名称模式。

<a id="c06-nested-design"></a>
## OrderProcessor与公开嵌套类型

原OrderProcessor同时验证订单、计算价格、锁定库存、记录日志，逻辑混杂。可以提取OrderValidator、PriceCalculator、InventoryManager、OrderLogger各负其责。如果Validator确是OrderProcessor实现细节，可选择私有嵌套类型，例如`OrderProcessor.Validator`，限制外部依赖，并按规则访问外部的私有状态；实例状态仍需相应对象，不能凭嵌套声明自动出现。

这个“复杂时分出更多类型”的建议与“避免公开嵌套API”不冲突：前者组织实现，后者控制公开契约。internal嵌套类型也有程序集可访问范围，不严格等于仅外部类型私有。

原FxCop提示对应CA1034“嵌套类型不应可见”的设计规则，而不是C#编译禁止。公共`OuterClass.InnerClass`在语法上可表达；是否采用要考虑API发现/限定名成本、工具规则和设计。将它以后搬成顶级类型会改变名称和引用方式，可能是破坏性改动，不能说只是不重要的排版变化。[CA1034说明](https://learn.microsoft.com/en-us/dotnet/fundamentals/code-analysis/quality-rules/ca1034)规定了建议范围及可适用的例外。

因此保留原作者的偏好：私有辅助实现优先隐藏；若要公开一个广泛使用的类型，考虑独立顶级API的清晰性。它是组件设计选择，不能改写为所有公开嵌套类型都错误、任何项目都必须启用某分析器。

## 重要纠错与现代差异

| 编号 | 原错误、历史限制或过度概括 | 正确结论/适用条件 |
| --- | --- | --- |
| C06-F01 | 每种成员各有独立IL体，FieldDef/PropertyDef是准确表名 | 分清字段/常量/抽象extern/访问器；实际CLI表Field/Property等 |
| C06-F02 | Family-and-Assembly在C#永远不支持，所有接口任何版本必public | C#5历史表保留；7.2 private protected、8默认接口/权限变化另列 |
| C06-F03 | 类型一概internal、成员一概private | 顶级/嵌套/普通成员/接口/enum/显式实现分开 |
| C06-F04 | IVT必须带key、token就够、公钥认证可信公司、private也开放 | signed与unsigned条件、完整key、身份封装与信任不同，private不因此开放 |
| C06-F05 | 静态类任何成员都必须显式static、AStaticEvent必无人订阅、DateTime是静态类 | const/嵌套类型例外；外部可订阅但无触发；DateTime是结构上的静态属性 |
| C06-F06 | params可以区分重载，ref/out/in相互不同就可重载，忽略generic arity | C#签名数量/类型/传递模式准确规则；返回/名字/约束/params不计 |
| C06-F07 | 参数相同返回类型绝对不能override，旧CLR一直支持所有covariant返回 | 旧C#5条件与9+支持环境分开；任意不兼容string→int仍非法 |
| C06-F08 | 普通IAddable约束可用a+b、两个TryAdd无方法体即可普通类编译 | 约束需实际操作契约，修正接口方法；TryAdd标合法abstract签名示意 |
| C06-F09 | callvirt必定virtual分派、虚方法永不可内联 | 非虚实例也可callvirt；目标明确时可能去虚化/内联 |
| C06-F10 | Set最后endIndex却传m_length-startIndex，非虚包装可任意改而不影响派生 | 实际count语义和三入口保留；包装仍需行为契约 |
| C06-F11 | 公开嵌套类型语法被禁止、FxCop偏好是任何程序硬规则 | C#允许；CA1034是设计/分析规则及例外，公开名称演进有真实成本 |
| C06-F12 | C#重写可任意放宽权限，“相同权限”一律指相同修饰符字符串 | 满足C#访问规则；跨程序集protected internal另有protected表达条件，CLI表示能力与C#语法区别 |
| C06-F13 | 各源语言元数据逐字完全相同、有IL便保证任意跨语言API互操作 | 共同CLI格式与具体产物区别，仍需CTS/CLS/源语言能力等条件 |
| C06-F14 | 推测的重载设计理由是规范唯一历史因果，作者未发现即所有语言均禁止 | 保留清晰性/规则简化/常见习惯的解释，并标明理由/当时观察与规范规则不同 |

对应规范/API链接及实际分程序集、正反例和IL核验见相关主题及作者记录。框架语言规则、指定实现的优化和一次实测分别说明，原例目的通过修正保留。
