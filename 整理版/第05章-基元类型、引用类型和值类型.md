## 本章的主线与decimal溢出

语言内建类型、CLR底层表示和值/引用语义不是一个分类轴。C#的`int`对应`System.Int32`，`decimal`也是C#预定义类型，但CLR没有一套专用decimal算术指令；`dynamic`则带有语言编译/绑定语义，不是增加一个与Int32类似的CLR存储类型。

本章不断用三个问题拆开误解：变量或字段保存什么，操作使用什么签名或指令，运行时最终怎样实现。理解“值被复制”和“对象引用被复制”，比记住“struct在栈，class在堆”更可靠。

<a id="c05-decimal-overflow"></a>
### checked不让decimal溢出回绕

原问题觉得“checked/unchecked对decimal失去作用”与“溢出仍抛OverflowException”矛盾。实际讨论的是不同机制。对于普通整数算术，编译器可选择带溢出检查的`add.ovf`等指令或不带该检查的`add`；decimal算术则通过其相应运算成员完成，不能靠`unchecked`要求decimal结果按整数方式回绕。

decimal占128位表示，有自己的符号、尺度和有效数值范围，约为±7.9×10²⁸。超过可表示范围时，相应decimal运算会抛`OverflowException`。这不表示所有错误都同一异常，例如decimal除以零是`DivideByZeroException`；也不是说需要额外开启一个全局checked开关才能得到这些契约。

原问题还比较了decimal与CLR整数原语的运算成本。decimal没有专用的CLI算术指令，相应成员要处理较复杂的数值表示、尺度和范围；在这类算术工作负载中，通常比简单整数指令承担更多成本。这是选择数值类型时的一项权衡，不是所有操作、目标平台和优化环境都有固定的速度排序或倍数；本章没有据此虚构性能基准。

完整程序E05-01，先把MaxValue放进变量，保证观察运行时运算：

```csharp
using System;

class Program
{
    static void Main()
    {
        int i = int.MaxValue;
        Console.WriteLine(unchecked(i + 1));
        try { Console.WriteLine(checked(i + 1)); }
        catch (OverflowException) { Console.WriteLine("int checked: OverflowException"); }

        decimal d = decimal.MaxValue;
        try { Console.WriteLine(unchecked(d + 1m)); }
        catch (OverflowException) { Console.WriteLine("decimal unchecked: OverflowException"); }
        try { Console.WriteLine(checked(d + 1m)); }
        catch (OverflowException) { Console.WriteLine("decimal checked: OverflowException"); }
    }
}
```

实测输出：

```text
-2147483648
int checked: OverflowException
decimal unchecked: OverflowException
decimal checked: OverflowException
```

原答直接写`decimal result = decimal.MaxValue + 1m;`并声称一定到运行时才抛异常。这里两边可以构成常量表达式，编译器可能在编译期就报CS0463；此行可保留为编译失败反例，不能拿来代替上面的运行时演示。

| 对比项 | int/long等普通整数算术 | decimal算术 |
| --- | --- | --- |
| 执行表示 | 例如`add`或`add.ovf` | 调用decimal相应运算成员；普通C#加法常见为`op_Addition` |
| checked/unchecked | 影响相应整数溢出语义/指令选择 | 不让超范围结果改成整数式回绕 |
| 溢出结果 | unchecked可回绕，checked抛相应异常 | 超出可表示范围抛OverflowException |

原答把decimal的检查比作每个路口内置的交警，而整数checked设置像选择是否检查超载的交通规则。它说明decimal自己运算契约与编译器整数上下文的区别，不表示每个方法只是硬编码一段相同IL或所有问题都叫“超载”。实际普通C#代码常调用运算符成员，`Decimal.Add`可以说明等价加法目的，却不能冒充每次`a+b`生成的准确方法名。

思考区还提到`BigInteger`。它没有decimal这类固定上界，能按需要扩展整数表示，所以不会仅因跨过某个固定MaxValue数值而回绕或溢出；仍受内存、资源及具体操作的限制。这是不同数值类型的有意义对照，不能随生成思考过程删掉。[checked/unchecked规则](https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/statements/checked-and-unchecked)及[Decimal运算契约](https://learn.microsoft.com/en-us/dotnet/api/system.decimal.add)可用于核对。

<a id="c05-valuetype-enum"></a>
## ValueType和Enum自己是什么类型

`System.ValueType`和`System.Enum`本身都是抽象的引用类型。具体结构和枚举是值类型，不能把它们的基类叫作“值类型的class”。

```text
System.Object
 ├─ System.ValueType（自身为引用类型）
 │    ├─ System.Int32及其他具体结构（值类型）
 │    └─ System.Enum（自身为引用类型）
 │          └─ 具体枚举，例如GameState（值类型）
 └─ 其他普通引用类型
```

结构隐式以ValueType为基类；具体枚举以Enum为基类，Enum再以ValueType为基类。C#不允许把一个普通class直接声明成`: ValueType`来制造“值类型class”，struct也不能在源码中显式列出ValueType为基类。值类型可以实现接口，但不能用普通类继承方式派生另一个结构。

元数据签名示意，不是可独立编译的替代框架类：

```csharp
public abstract class ValueType { /* 框架成员 */ }
public abstract class Enum : ValueType { /* 框架成员 */ }
```

ValueType提供值类型的相关默认行为，例如Equals/GetHashCode/ToString的实现；Enum提供枚举相关API，例如Parse、GetValues、HasFlag。具体值类型可以按规则提供自己的行为，不能把默认字段比较、哈希实现或API优化当作所有运行时永远相同的底层算法。

原正式答把ValueType比作“可复制物品”的规章制度，具体结构是按值语义处理的产品；另一段用“模具和产品”说明隐式特殊基类。思考区用父亲和孩子的家规解释“基类是引用类型，具体孩子是值类型”。这些比喻只用于行为/类型关系，不能据此说规章纸张在哪里，就决定所有实例固定在栈或堆。

原问答还给出完整的三层类比：Object是共同地基，ValueType是特殊模具，具体struct和enum是按特殊规则形成的产品。具体enum的类型链还经过Enum；“模具”描述的是类型关系和行为规则，不是任意值类型都共享同一种存储、比较或哈希算法。

<a id="c05-api-documents"></a>
### 第五章提到的“文档”可以怎样查

原上下文谈“文档中称类、结构或枚举”，通常指.NET API参考资料，例如历史的MSDN Library、如今Microsoft Learn的API浏览器，以及Visual Studio F1上下文帮助。语言规范解释C#语义，CLI规范解释类型/指令模型，不应把“.NET Standard”名称直接当成一份规定所有CLR内部算法的规范。

看API声明时，`System.String`、`Exception`、`FileStream`、`Random`等class是引用类型，`System.Int32`等struct及`System.DayOfWeek`等enum是值类型。ValueType/Enum自己的class声明与其具体值类型后代仍要区别；这里查看类别是判断类型关系，不是保证某个局部变量物理分配在栈上。原Markdown漏掉的Microsoft Learn标签已依据完整JSON/PDF恢复。[ValueType API](https://learn.microsoft.com/en-us/dotnet/api/system.valuetype)展示了其声明与类型关系。

## 在Unity和VS观察隐式基类

<a id="c05-unity-ide-types"></a>
### 源码没有写基类，不代表没有该关系

在Unity C#项目里，System.Object、ValueType和Enum的基本关系仍适用。原操作先在IDE中对`System.Object`、`System.ValueType`、`System.Enum`使用F12“转到定义”，查看声明或元数据投影；对`UnityEngine.Object`则要先辨别这是引擎的Object，不是System.Object。

Mono与IL2CPP是不同后端，不能因后端选择就改写上述C#基本类型关系。这是语言及类型模型的核对，本章没有声称在本机分别运行了两个Unity后端。

独立类型片段E05-02，保留原三个定义场景：

```csharp
using UnityEngine;

public struct MyVector3 { public float x, y, z; }
public enum GameState { Menu, Playing, Paused }
public class Player : MonoBehaviour { }
```

MyVector3隐式从ValueType派生，GameState隐式从Enum派生；Player的显式基类是MonoBehaviour，再经过引擎类层次到UnityEngine.Object和System.Object。结构和枚举的特殊基类不需要也不能照普通类语法补到冒号后。不能承诺所有版本的悬停提示或F12页面都一定显示完整隐式链。

Unity脚本E05-03，需要前面的GameState类型：

```csharp
using System;
using UnityEngine;

public class InheritanceViewer : MonoBehaviour
{
    void Start()
    {
        Type intType = typeof(int);
        Debug.Log("int 的基类型: " + intType.BaseType);
        Debug.Log("再上一层: " + intType.BaseType.BaseType);

        Type enumType = typeof(GameState);
        Debug.Log("GameState 的基类型: " + enumType.BaseType);
        Debug.Log("再上一层: " + enumType.BaseType.BaseType);

        Debug.Log("MonoBehaviour 的基类型: " + typeof(MonoBehaviour).BaseType);
    }
}
```

相应类型关系为ValueType、Object；Enum、ValueType；MonoBehaviour的直接基类为UnityEngine.Behaviour。此脚本说明反射观察方法，没有在本机虚称运行过Unity2019.4。

<a id="c05-vs-object-browser"></a>
### 鼠标悬停没显示，怎样进一步查看

原用户把MyVector3称作“枚举”，而前面示例定义的是struct；下面同时保留结构和枚举，避免沿用混淆。

在Visual Studio可从“视图”打开对象浏览器或类视图，搜索MyVector3、GameState或System.Int32，检查类型及基类资料。原答给了对象浏览器Ctrl+W,J、类视图Ctrl+Shift+C等键位；键位会随IDE版本/键盘方案变化，菜单入口更稳。F12元数据投影中的`struct Int32 : IComparable, ...`展示接口，并不需要同时写出隐式ValueType；不要把“投影未打印冒号”当作真实元数据没继承。

原书时代的Int32投影签名示意，保留原列举的五种接口，不作可重新编译的框架替代类型：

```csharp
public struct Int32 : IComparable, IComparable<int>, IConvertible,
                      IEquatable<int>, IFormattable
{
    // 框架成员省略
}
```

现代框架还可能增加其他接口；这不改变“接口列表不等于要显式列出ValueType基类”的教学点。

原思考区另建议用类图观察关系。若Visual Studio安装了Class Designer，并且项目属于其支持的Framework等范围，可添加相应类型到类图作静态观察；不能保证所有Unity生成项目或所有VS平台都支持同一入口。当前[Class Designer说明](https://learn.microsoft.com/en-us/visualstudio/ide/class-designer/designing-and-viewing-classes-and-types?view=visualstudio)限定其支持范围，和对象浏览器、反射及IL观察是不同路径。

Unity脚本E05-04，保留原嵌套定义及完整链遍历，输出用真实嵌套FullName形式：

```csharp
using System;
using UnityEngine;

namespace Demo
{
    public class CheckInheritance : MonoBehaviour
    {
        public struct MyVector3 { public float x, y, z; }
        public enum GameState { Menu, Playing, Paused }

        void Start()
        {
            Debug.Log("MyVector3 (结构体) 的继承链:");
            PrintBaseTypes(typeof(MyVector3));
            Debug.Log("GameState (枚举) 的继承链:");
            PrintBaseTypes(typeof(GameState));
            Debug.Log("int 的继承链:");
            PrintBaseTypes(typeof(int));
        }

        void PrintBaseTypes(Type type)
        {
            int indent = 0;
            for (Type current = type; current != null; current = current.BaseType)
            {
                Debug.Log(new string(' ', indent * 2) + current.FullName);
                indent++;
            }
        }
    }
}
```

对应链：

```text
Demo.CheckInheritance+MyVector3
  System.ValueType
    System.Object

Demo.CheckInheritance+GameState
  System.Enum
    System.ValueType
      System.Object

System.Int32
  System.ValueType
    System.Object
```

原输出把嵌套类型写成`YourNamespace.MyVector3`/`GameState`，遗漏包含类型。反射的FullName中嵌套部分使用`+`；在C#源码中引用仍采用点等相应语法。`+`显示形式不是把结构的真实基类改变了。

原另一条静态观察途径是编译项目，再用ILDasm、ILSpy等查看程序集的IL/元数据。原书背景的结构定义可能显示：

```il

       extends [mscorlib]System.ValueType
{
    // 字段与成员省略
}
```

这是IL类型定义示意，重点是extends和类型属性；具体可见性、嵌套标志和所引用核心库要按实际类型/环境看。把现代或Unity参考元数据简单改名为mscorlib会丢掉环境条件。

<a id="c05-valuetype-object-projection"></a>
### 用户的netstandard元数据为什么没写`: Object`

用户提供的是Unity2019.4.12f1参考程序集的签名摘要。原场景保留如下，它是元数据投影，省略的方法体/签名不能当作待重新编译的框架源码：

```csharp
#region 程序集 netstandard, Version=2.0.0.0, Culture=neutral, PublicKeyToken=cc7b13ffcd2ddd51
// D:\Program Files\Unity\Hub\Editor\2019.4.12f1\Editor\Data\NetStandard\ref\2.0.0\netstandard.dll
#endregion

namespace System
{
    public abstract class ValueType
    {
        protected ValueType();
        public override bool Equals(object obj);
        public override int GetHashCode();
        public override string ToString();
    }
}
```

普通C#类没有指定其他基类时，默认继承System.Object；投影工具可以省略默认项。这里没打印`: Object`不否定ValueType的真实基类。原Q023正式答误读成“你已经看到了ValueType:Object”，而用户实际上说没看到；其思考区反而指出了默认省略，需要按真实问题纠正。

完整非Unity程序E05-05，保留原两个检查：

```csharp
using System;
class Program
{
    static void Main()
    {
        Console.WriteLine(typeof(ValueType).IsSubclassOf(typeof(Object)));
        Console.WriteLine(typeof(ValueType).BaseType == typeof(Object));
    }
}
```

两行均为True。Unity版独立脚本E05-06保留原VerifyInheritance的直接基类、比较及IsSubclassOf三个观察；两个using都存在时必须明确System.Object：

```csharp
using System;
using UnityEngine;

public class VerifyInheritance : MonoBehaviour
{
    void Start()
    {
        Type valueType = typeof(ValueType);
        Type objectType = typeof(System.Object);
        Debug.Log(valueType.BaseType.FullName);        // System.Object
        Debug.Log(valueType.BaseType == objectType);   // True
        Debug.Log(valueType.IsSubclassOf(objectType)); // True
    }
}
```

原片段的`typeof(Object)`在同时using System和UnityEngine时可能歧义；这是名字解析问题，不能用一段不能编译的脚本声称已经证明继承。省略默认Object也可类比省略数学式中的乘以1：展示更短，不表示原关系消失。参考程序集和实现程序集的区别见[第4章](第04章-类型基础.md#c04-compile-reference-result)。

<a id="c05-unity-object"></a>
## UnityEngine.Object与System.Object

UnityEngine.Object直接隐式派生System.Object。原答开头说“不直接、最终间接”，随后又说它本身派生Object，是自相矛盾；应以真实类型声明和规则为准。

System.Object提供通用对象行为；UnityEngine.Object在此基础上连接引擎对象与资源管理，提供名称、实例ID、Destroy/DestroyImmediate及特殊判空等功能。GameObject、Component、ScriptableObject、Texture2D、Material等是不同引擎类型；不能把“几乎所有脚本对象”都说成必然来自UnityEngine.Object。

原答将UnityEngine.Object比作“披着.NET类外衣的引擎管理者”：托管包装通过相应接口联系引擎对象和资源，帮助理解普通引用与原生对象寿命的区别。这个比喻不表示所有.NET核心行为都被重写，也不表示普通C#脚本里定义的每个类都变成了引擎对象。

原答还用`class MyBehaviour : UnityEngine.Object`说明这种类型关系最终通向System.Object。它可作为继承关系的声明例理解，不能把直接派生Object的类自动当作可挂载的MonoBehaviour脚本或已经具备某个原生引擎组件实例。

向上转型成System.Object不会改变对象的实际类型，ToString等虚方法仍能派发到运行时类型的实现。变化的是静态类型所能直接使用的成员及运算符绑定。例如，Unity Object的`==`判空会考虑底层引擎对象是否存在；object的引用比较看的是C#包装引用是否为null，不能据此推断引擎资源仍存活。

Unity脚本E05-07，保留原`GameObject("Test")`、上转型、as转换、名称和不同判空场景；等实际销毁后再观察：

```csharp
using System.Collections;
using UnityEngine;

public class Example : MonoBehaviour
{
    IEnumerator Start()
    {
        GameObject go = new GameObject("Test");
        System.Object sysObj = go;
        Debug.Log(sysObj.ToString()); // 仍按运行时类型虚派发

        // UnityEngine.Object unityObj = sysObj; // 无隐式向下转换：反例
        UnityEngine.Object unityObj = sysObj as UnityEngine.Object;
        if (unityObj != null) Debug.Log(unityObj.name);

        Destroy(go);
        yield return null; // 原Destroy实际执行在当前Update之后；这里观察下一帧

        Debug.Log(go == null);                        // True：引擎层对象已销毁
        Debug.Log(sysObj != null);                    // True：托管包装引用仍存在
        Debug.Log(System.Object.ReferenceEquals(go, null)); // False
    }
}
```

原答在Destroy之后立刻检查，并把“已销毁”当确定结果，忽略了延迟执行。DestroyImmediate的不同即时行为不应悄悄替换这个例子。[Unity2019.4 Destroy](https://docs.unity3d.com/2019.4/Documentation/ScriptReference/Object.Destroy.html)规定实际销毁在当前Update循环后、渲染前；[Unity官方Object参考源](https://github.com/Unity-Technologies/UnityCsReference/blob/master/Runtime/Export/Scripting/UnityEngineObject.bindings.cs)可核对声明和比较逻辑，不能冒充本机2019引擎实测。

<a id="c05-storage"></a>
## 定义值/引用语义，不等于固定物理位置

原问题对比C/C++使用方选择局部或动态分配，与C#定义者选择class或struct。C#类型设计者确实选择值/引用语义，但这不等于“物理位置永远由类型声明唯一决定，使用者无法使值出现在堆中”。

C++方法片段E05-08a，原局部Point例：

```cpp
struct Point { int x; int y; };
void MyFunction() {
    Point p1;
    p1.x = 10;
} // 自动存储期对象离开作用域
```

独立C++方法片段E05-08b，同一Point的动态分配例：

```cpp
void MyFunction() {
    Point* p2 = new Point();
    p2->x = 20;
    delete p2;
}
```

这展示使用方选择对象的存储期/分配方式；“一定保留一个物理栈槽”仍可能受原生优化影响。动态对象需要适当管理生命周期，delete是此简化例的对应释放。

独立C#类型/方法片段E05-09，保留原Point与Rectangle的两个字段：

```csharp
public struct Point { public int X; public int Y; }
public class Rectangle { public Point TopLeft; public Point BottomRight; }

public class UseTypes
{
    public void MyMethod()
    {
        Point p1;
        p1.X = 10; // Y尚未赋值，不可把完整p1当已确定赋值的值读出
        Rectangle r1 = new Rectangle();
        // 两个Point字段是Rectangle对象状态的一部分，并非各自一次装箱。
    }
}
```

结构值可存在于局部变量、对象字段、数组元素或box的payload中；局部值/引用也可能放寄存器或被优化，而不是一律线程栈槽。使用方虽然不能把同一Point声明改成引用语义，却能选择包含/数组/装箱等使用环境。Rectangle中的Point字段内嵌在该对象状态里，是“值类型可以在堆上”的直接反例。

原思考的建筑师/施工队类比经修正后仍适用：建筑师选择值或引用的使用契约，施工队按契约及具体环境安排实现；它不是一条规定所有材料固定地点的“内存宪法”。自动内存管理减少许多手工错误，但不保证所有托管程序都没有资源泄漏、长寿命引用或原生互操作错误。

<a id="c05-struct-design"></a>
## 什么时候适合设计struct

原书建议谨慎选择值类型：类型行为简单、像一个值，最好不可变；不需要自定义类继承层次，也不作为其他类型的基类。Point坐标、Money金额/币种、范围或复数是原答给的候选；需按具体语义判断，不能因为名字叫Point就自动决定所有设计。

值类型赋值和按值传参产生值副本。可变结构容易让人修改副本却误以为原状态已改变，装箱/拆箱场景更明显。不可变设计能减少这类误解，但**不可变是设计建议，不是C#所有struct的强制语法要求**。readonly字段也不能深冻结它引用的可变对象。

结构不接受普通自定义基类，且不能被其他类/结构继承，这是语言/类型模型的限制；它仍可实现接口、重写继承的相关虚方法，并在适当约束下参与接口多态，不能泛称“值类型没有任何多态”。

原文还有大小和传参考虑，例如较小的实例（16字节或更小）或避免频繁复制较大实例。它是成本判断建议，不是保证“16字节一定快”或“所有泛型结构大小都由csc一次确定”的定理。字段、平台、封闭类型及运行时实现影响布局，实际热点应测量。

<a id="c05-explicit-layout"></a>
## 显式字段布局与重叠字节

<a id="c05-readonly-overlap"></a>
### Byte和Int16都从偏移0开始

原片段的特性应拼作`FieldOffset`，不是`FiledOffset`。`StructLayout(LayoutKind.Explicit)`要求相应实例字段给出明确偏移；偏移是相对该类型的实例字段布局，不是让字段放到绝对地址0。

独立类型片段E05-10，保留SomeValType的两个private readonly重叠字段，并补一个合法构造入口及只读观察：

```csharp
using System;
using System.Runtime.InteropServices;

[StructLayout(LayoutKind.Explicit)]
internal struct SomeValType
{
    [FieldOffset(0)] private readonly Byte m_b;
    [FieldOffset(0)] private readonly Int16 m_x;

    public SomeValType(short value)
    {
        this = default(SomeValType);
        m_x = value;
    }
    public byte ByteValue { get { return m_b; } }
    public short Int16Value { get { return m_x; } }
}
```

Byte占1字节，Int16占2字节；两个字段都从偏移0起，因此Byte视角使用其中一个字节，Int16视角使用前两个字节。这类似C/C++的union：同一段数据可以按不同类型视角解释。原答给的协议、设备或文件格式场景是要从一个16位数据同时理解整体与某个字节，不是把两个独立值神奇地同步。

<a id="c05-mutable-overlap"></a>
### 修改一个字段，另一个一定变化吗

原字段是private readonly，外部`val.m_b = ...`本来不合法。要演示可变读写，应另立公开非readonly示例，不能在注释中假定原字段可随时修改。

完整程序E05-11，下面结果明确限定本机小端平台：

```csharp
using System;
using System.Runtime.InteropServices;

[StructLayout(LayoutKind.Explicit)]
struct Union
{
    [FieldOffset(0)] public byte m_b;
    [FieldOffset(0)] public short m_x;
}

class Program
{
    static void Main()
    {
        Union val = new Union();
        Console.WriteLine(val.m_x);
        val.m_b = 0xAB;
        Console.WriteLine(val.m_x.ToString("X4"));
        val.m_x = 0x1234;
        Console.WriteLine(val.m_b.ToString("X2"));
        val.m_x = 0x2234;
        Console.WriteLine(val.m_b.ToString("X2"));
        Console.WriteLine(BitConverter.IsLittleEndian);
    }
}
```

实测输出：

```text
0
00AB
34
34
True
```

原例用0x1000作为假想实例起始地址，m_b读取0x1000，m_x读取0x1000和0x1001。在这个小端说明中，写0xAB使前一字节成为AB，另一字节初始是0，整体为00AB；写0x1234时低字节34在起始处、高字节12在下一处。`new Union()`后的默认字节不是“随机未初始化残值”。

改变重叠字节会改变相应解释，但写同样的字节可能不改变数值；把Int16从1234改为2234只改高字节，Byte仍34。变化由明确布局、已有字节和端序决定，不是“不可预测地总变化”。

<a id="c05-layout-verification"></a>
### 显式布局、可访问性与验证要分开

原答把验证提示扩大为“所有重叠字段必须public”及“private重叠结构默认都不可验证”，不准确。2012年CLI标准对相应字段访问验证的条件是：重叠该字段的其他字段也必须在该访问点可访问。类型内部能访问自己的两个private字段，不同于外部只可见一个public字段却覆盖另一个不可见private字段。

引用字段还有另外的严格限制：object引用不能与内建值字段或另一引用的一部分重叠；两个object引用完全重叠的情况即使布局可表达，也有不可验证限制。不能因数值Byte/Int16演示可用，就推广为任意对象引用混合union。[CLI六版](https://www.ecma-international.org/wp-content/uploads/ECMA-335_6th_edition_june_2012.pdf)的II.10.7及III.4.10/4.11/4.28规定了这些不同条件。

作者在Framework4.8工具中另外运行PEVerify：数值字段的全private内部访问、全public、混合public/private的内部和外部访问实例均被该工具接受；故意令方法声明返回Int32而实际留下String的负控制则被检出。这里**如实保留工具与标准算法预期的不同**。标准IL验证模型允许实现依据自身知识接受更多程序，工具通过不能推出对所有CLI实现都具备同一种可移植验证保证；编译成功、运行成功和验证器结果也不是同一证据。

这项技术适合有明确布局需要的互操作和数据表示。原书验证提示应按上述访问点和字段种类理解，不应为了“修复验证”而盲目把封装字段全部改public。

<a id="c05-generics-storage"></a>
## 泛型集合为什么少装箱

<a id="c05-arraylist-list"></a>
### ArrayList的object[]与List的T[]

原问题的重点是`ArrayList`与`List<int>`传参和存储的区别。ArrayList的Add接受object、索引器返回object，内部用object[]；List的泛型API则按T接收和返回元素，内部使用T[]。在List<int>的普通泛型Add/索引器路径中，整数以未装箱值放入int[]，不需要每个元素先变成一个独立box。

概念类型示意E05-12a，仅解释相关存储/签名，省略真实容量检查等集合实现，不能作为完整替代ArrayList：

```csharp
public class ArrayListModel
{
    private object[] _items;
    private int _size;
    public int Add(object value)
    {
        _items[_size++] = value;
        return _size - 1;
    }
    public object this[int index] { get { return _items[index]; } }
}
```

独立概念类型示意E05-12b，保留原`List_int`讲解目的，**不是csc真正生成的新类**，同样省略容量等实现：

```csharp
public class List_int
{
    private int[] _items;
    private int _size;
    public void Add(int value) { _items[_size++] = value; }
    public int this[int index] { get { return _items[index]; } }
}
```

C#生成泛型元数据/IL，运行时处理封闭类型并可能对不同类型参数特化或共享代码。不能说看到List<int>时csc就把List<T>源码改成一个实际List_int类；Unity AOT等路线又有其实现步骤。

独立方法片段E05-13，保留原123的两种真实使用：

```csharp
// 使用System.Collections.ArrayList
var oldList = new System.Collections.ArrayList();
oldList.Add(123);                // int作为object传入，装箱
int oldValue = (int)oldList[0];   // object取值转换为int

// 使用System.Collections.Generic.List<int>
var list = new System.Collections.Generic.List<int>();
list.Add(123);                   // 普通泛型API，直接传int
int value = list[0];
```

| 操作 | ArrayList保存int | List<int>普通泛型路径 | 实际优势/边界 |
| --- | --- | --- | --- |
| 添加 | object参数需要box，object[]存其引用 | int参数/数组直接存值 | 避免逐元素box，不等于集合/扩容从不分配 |
| 访问 | 取object引用，再以int取出相应值 | 索引器返回int | 避免这条object转换路径 |
| GC | 逐元素box增加独立对象 | 值元素内嵌于数组 | List对象及数组通常仍是不同堆对象，扩容还可能换数组 |

泛型同时带来编译期类型检查，例如List<string>不能通过相应Add直接加int。若转去非泛型IList的object API等路径，仍可能出现装箱，不能从“使用了List<T>”推出所有使用方式绝对零装箱。[泛型运行时处理](https://learn.microsoft.com/en-us/dotnet/csharp/programming-guide/generics/generics-in-the-run-time)可核对编译与运行阶段。

减少逐元素box和额外间接访问，通常能减轻GC负担并改善这类值元素工作负载的成本；实际速度和分配变化仍要按使用路径、容量及运行环境测量，不能把概念表当作一项对所有程序的性能保证。

<a id="c05-list-memory-diagram"></a>
### List<int>是在栈上分配吗

List<T>是类，内部数组也是引用类型；元素类型是int，不会把整个List变成struct。普通实现中，List对象引用其int[]存储，值元素直接在数组内，而不是每个int再指向另一个box。

原图保留对象、引用及三个元素的关系；左侧是变量的使用位置示意，不承诺所有局部引用始终都有物理栈槽：

```text
变量list（引用，可在局部/寄存器或其他对象状态中）
       │
       ▼
  List<int>对象（通常托管堆）
  ┌─────────────────────┐
  │ 计数/容量相关状态    │
  │ _items数组引用 ──────┼────┐
  └─────────────────────┘    │
                             ▼
                         int[]数组对象
                         ┌─────────────────┐
                         │ [0] 123         │
                         │ [1] 456         │
                         │ [2] 789         │
                         └─────────────────┘
                         值元素直接在数组中，无逐元素box
```

原思考区的搬家纸箱/书类比也保留：纸箱像集合存储，书直接放进箱里，不必每本书另套一个对象包装；方便搬运并节省逐本包装，不表示纸箱自己没占空间或不会换更大的箱子。

<a id="c05-unboxing"></a>
## 装箱对象、unbox与取值副本

<a id="c05-box-payload"></a>
### “已装箱实例中的未装箱部分”是什么

装箱把一个值放进相应托管对象的payload，产生可作为object/相应接口使用的引用。该对象有运行时对象信息，payload保存原值的数据；“未装箱部分”指payload按该值类型布局的那部分数据，不是说这个box里面又分配了一个独立的栈对象。

原Point(5,10)图修正后保留：

```text
托管堆中的boxed Point（概念图，不规定物理头字段顺序/大小）
┌───────────────────────────────────┐
│ 运行时类型/对象相关信息           │
│ 类型指针关联MethodTable等信息     │
├───────────────────────────────────┤
│ Point.x = 5  ◄─ unbox取得payload地址│
│ Point.y = 10                      │
└───────────────────────────────────┘
```

原答把类型对象指针直接画成指向System.Type反射对象，不准确；实际对象表示关联运行时类型数据，获取Type对象还涉及运行时实现。同步块等对象头表示及位置不是C#层面的固定字段契约。

<a id="c05-unbox-any"></a>
### 获取byref与复制一个值要区别

CIL的`unbox`检查相应对象/类型并取得指向box内数据的托管指针；`unbox.any`对普通已装箱值类型取得值，效果相当于unbox之后ldobj。普通C#的`Point p2 = (Point)o`通常生成unbox.any，不能无条件说源编译器一定生成两条unbox、ldobj。

这也解释了原问题“拆箱为什么通常比装箱代价低”的比较范围：单独unbox主要做空值/类型检查并取得payload的byref，不需要像常见的新box路径那样另建对象并复制值。普通C#强转的unbox.any还要取出值副本，成本与类型大小和使用方式有关；JIT也可能消除相关工作。因此这里比较的是具体步骤，不能推出固定倍数或所有拆箱调用都绝对更快。

方法片段E05-14，需要一个具有相应构造器的Point值类型：

```csharp
Point p1 = new Point(5, 10);
object o = p1;       // 装箱，保留当时值的副本
Point p2 = (Point)o; // 取出值副本，不是让p2直接变成box内字段的别名
```

对非nullable值类型，null输入引发NullReferenceException，错类型引发InvalidCastException；不能把所有拆箱失败都归为一种异常，或以为先把boxed int直接拆成long就能顺便数值转换。

在原书语境中，C++/CLI可使用相应的box内部值访问方式；C#常通过已装箱的相应接口调用来修改box里的值，而直接强转得到的值表达式往往是副本。现代差异：提供相应API/语言支持时也可在C#中用`Unsafe.Unbox<T>`取得ref，再按其契约处理，不能把“历史普通强转取副本”扩成“所有C#版本永远没有ref路径”。该API仍有受控可变性限制，不能把返回ref当作可随意整体替换任意boxed值的许可证。[Unbox_Any API](https://learn.microsoft.com/en-us/dotnet/api/system.reflection.emit.opcodes.unbox_any)与[Unsafe.Unbox](https://learn.microsoft.com/en-us/dotnet/api/system.runtime.compilerservices.unsafe.unbox?view=net-10.0)区分这些层次。

<a id="c05-method-boxing"></a>
## ToString、GetType与接口调用

<a id="c05-int-tostring"></a>
### int v=1; v.ToString()会装箱吗

Int32提供自己的ToString实现，直接在int变量上调用不需要为了接收者而先装箱。原问题的小写`tostring`应为区分大小写的`ToString`。

方法片段E05-15：

```csharp
int v = 1;
string text = v.ToString();
```

这不等于字符串结果本身一定无分配，也不表示任意继承方法或任意接口转换都一样。转换为object/接口变量的路径，和直接调用值类型自己的重写，是不同情形。

原列表还举了Object.MemberwiseClone这样的继承非虚方法。它是protected，使用时首先要满足访问性，再理解所需接收者表示；不能把任意外部调用的错误代码当成实际装箱验证。浅拷贝及保护访问的具体场景见[第4章](第04章-类型基础.md#c04-memberwiseclone)。

思考区还提醒了另一个条件：值类型的重写方法内部若调用基类实现，例如`base.ToString()`，该内部调用又可能要求装箱。不能因为最外面的直接调用可避免接收者装箱，就删除内部行为的区别。

<a id="c05-gettype"></a>
### GetType与继承关系为什么还涉及box

继承了Object的方法，不代表未装箱值就具有一个完整对象头。原书以非虚Object.GetType说明对象表示路径；常见C#生成的IL可包含box再调用GetType，与直接Int32.ToString不同。但现代JIT知道具体值类型时可能把GetType结果直接化简，消除真实装箱分配，不能从IL有box就宣称每次一定在堆上实际分配对象。

| 对比 | GetType | 直接调用具体值类型重写的ToString |
| --- | --- | --- |
| 声明来源 | Object的非虚方法 | 值类型提供自己的重写 |
| 未装箱值表示 | 没有独立对象头 | 仍有值数据及已知类型 |
| 典型C# IL路径 | 可能含box后调用Object.GetType | 可以传值地址调用相应实现 |
| 最终实现 | JIT可以知道类型并消除分配等步骤 | 不需为了接收者装箱，但方法内其他行为另看 |
| 判断证据 | 分清语言语义、生成IL及最终机器码/分配测量 | 不把“无需接收者装箱”写成整个方法绝对零分配 |

原身份证类比经限定后仍有用：普通对象路径像读取带身份资料的卡，未装箱数据像数据纸条；box提供能走对象接口的表示。但优化器有时已知“纸条类型”，可以直接给结果，不必真造每次卡套。不能把对象头“缺陷”当成值类型不配调用继承方法。

本机.NET10对相同的`Get(int n) { return n.GetType(); }`进行了一项实现对照：100000次调用的一次默认分层配置测得分配2400000字节；同一程序关闭分层编译、直接采用相应优化后测得0字节，两次都返回System.Int32。这只证明具体环境和配置能改变真实分配，不把一次0字节测量升级为所有GetType调用必无分配的规范。

<a id="c05-compareto"></a>
### c.CompareTo(p2)为什么给参数装箱

原场景先把p1赋给非泛型IComparable变量c，c已经引用一个boxed Point；p2是Point(20,20)。c的编译时接口只有CompareTo(object)，所以传p2时需要object参数路径。实现仍属于Point，不是“跑去调用一个Object类里的CompareTo方法”。

类型片段E05-16，补全原两个重载：

```csharp
using System;
struct Point : IComparable
{
    private int x, y;
    public Point(int a, int b) { x = a; y = b; }
    public int CompareTo(Point other)
    {
        int n = x.CompareTo(other.x);
        return n != 0 ? n : y.CompareTo(other.y);
    }
    public int CompareTo(object other) { return CompareTo((Point)other); }
}
```

对应方法片段：

```csharp
Point p1 = new Point(10, 10);
Point p2 = new Point(20, 20);
IComparable c = p1;                 // p1进入接口引用路径，装箱
Console.WriteLine(c.CompareTo(p2));  // 参数p2需要object路径
Console.WriteLine(p1.CompareTo(p2)); // 选CompareTo(Point)，p2不因该签名装箱
```

两行均输出-1，类型/签名路径却不同。c不再因为这次调用重新装箱接收者；给参数装箱不等于给已有box再套一层。泛型约束的constrained调用也不能简单套用“所有接口调用必装箱”的口号，后续[第12章](README.md#chapter-12)再讨论其条件。

<a id="c05-point-copy"></a>
## Console.WriteLine与Point.Change完整例

原用户给了一个完整程序，问题是第一次WriteLine(p)为何装箱。但后面的修改/box/取值副本也有独立结果，必须一并保留。

完整程序E05-17：

```csharp
using System;

struct Point
{
    private int m_x, m_y;
    public Point(int x, int y) { m_x = x; m_y = y; }
    public void Change(int x, int y) { m_x = x; m_y = y; }
    public override string ToString()
    {
        return String.Format("({0}, {1})", m_x.ToString(), m_y.ToString());
    }
}

class Program
{
    static void Main()
    {
        Point p = new Point(1, 1);
        Console.WriteLine(p);
        p.Change(2, 2);
        Console.WriteLine(p);

        object o = p;
        Console.WriteLine(o);
        ((Point)o).Change(3, 3);
        Console.WriteLine(o);
    }
}
```

实测四行：

```text
(1, 1)
(2, 2)
(2, 2)
(2, 2)
```

WriteLine没有这个自定义Point的专用参数重载，通常选择WriteLine(object)，p因object转换被装箱；这与p直接调用自身ToString不同。第二次WriteLine看到修改后的p。随后object o=p保存一个值为(2,2)的box；`((Point)o).Change(3,3)`修改强转得到的临时值副本，因此最后o仍表示(2,2)。

对照方法片段E05-18：

```csharp
Console.WriteLine(p.ToString()); // 直接调用Point重写，再传给WriteLine(string)
```

它避免了此处为object参数而装箱p的路径；最终字符串及ToString内部行为仍按实现看。原思考还指出WriteLine(int)等已有相应重载时路径不同，因此不能泛称“任何值类型传给Console都装箱”。

<a id="c05-mutable-key"></a>
## Student键：哈希、桶与相等性

<a id="c05-student-scenario"></a>
### Id从1改为2，为什么字典找不到

原Student根据Id生成hash，根据Id与Name判断相等。保存键时Dictionary保留键引用，并保存相关hash/组织信息；之后查找重新用查询键的当前hash定位及筛选候选。

完整程序E05-19，保留Alice、成绩A及修改前先移除/再添加的不同步骤：

```csharp
using System;
using System.Collections.Generic;

class Student
{
    public int Id;
    public string Name;
    public override int GetHashCode() { return Id.GetHashCode(); }
    public override bool Equals(object obj)
    {
        Student other = obj as Student;
        return other != null && Id == other.Id && Name == other.Name;
    }
}

class Program
{
    static void Main()
    {
        Student student = new Student { Id = 1, Name = "Alice" };
        var grades = new Dictionary<Student, string>();
        grades.Add(student, "A");
        student.Id = 2;
        string grade;
        Console.WriteLine(grades.TryGetValue(student, out grade)); // False

        // 这个失败演示恢复旧状态后，再演示真正正确的修改顺序。
        student.Id = 1;
        grade = grades[student];
        grades.Remove(student);
        student.Id = 2;
        grades.Add(student, grade);
        Console.WriteLine(grades[student]); // A
    }
}
```

不能在键已被破坏之后直接照抄`grade=grades[student]`当作必定成功的修复。正常使用应在修改hash/相等性依据**之前**移除，保留值，再修改并添加；上例恢复旧Id只为串联失败与正确两种演示，不是通用恢复任意受损字典的算法。

<a id="c05-same-bucket"></a>
### 原100桶、1改10001的场景怎样解释

原答假设100个桶，1%100与10001%100都为1。这个算术说明“不同hash可能落同一桶”，不能变成“hash已经相同”。实际Dictionary桶大小/选取算法也不能固定为100，此处保留为概念场景。

原后续断言“因为保存的是原Id=1，所以修改后Equals不同”不对：字典保存的是同一个Student对象的引用，不是一份自动冻结旧Id的Student快照。若与自身比较，Id/Name当然相等；但保存时的完整hash与新的hash不同，候选筛选可能在Equals之前就拒绝，这才是同桶仍查找失败的重要原因。

作者另外用实际桶长度构造同桶实例：保存Id1，再令Id变成`1 + bucketCount`；实测SameBucket=True、SelfEquals=True、Found=False，分别验证了“桶相同”“相等自身”“查找失败”可以同时成立。它不把本机内部字段名和桶策略推广为公开API契约。

也不能说改键对象的任意字段都必然导致失败。若改变不参与比较/hash的字段，或同一对象的某个相等条件改变而hash仍相同，具体查找行为不同；修改键的比较身份仍会破坏集合应保持的契约。可靠设计是使参与hash/相等性的身份稳定，或在改变前按正确顺序移除并重加。[Dictionary键的要求](https://learn.microsoft.com/en-us/dotnet/api/system.collections.generic.dictionary-2)与相应实现可对照。

<a id="c05-dynamic"></a>
## dynamic、var与运行时绑定

<a id="c05-dynamic-loop"></a>
### 同一段加法和调用，为什么两轮行为不同

dynamic让某些表达式的绑定留到运行时。存储签名通常用object及相应DynamicAttribute等表示，不是增加一个新的CLR primitive对象；编译器知道“这里使用dynamic语义”，不是完全不知道任何事。普通赋值、语法和若干静态规则仍会检查，不能说所有涉及dynamic的操作都无条件延后。

完整程序E05-20，补全原M(int)/M(string)，保留5与字符串A两轮：

```csharp
using System;

class Program
{
    static void M(int value) { Console.WriteLine("Int32: " + value); }
    static void M(string value) { Console.WriteLine("String: " + value); }

    static void Main()
    {
        dynamic value;
        for (int demo = 0; demo < 2; demo++)
        {
            value = demo == 0 ? (dynamic)5 : (dynamic)"A";
            value = value + value;
            M(value);
        }
    }
}
```

输出：

```text
Int32: 10
String: AA
```

第一轮绑定整数加法及M(int)，第二轮绑定字符串连接及M(string)。运行时绑定器/调用点机制负责相关决策，不能只说CLR读取object变量就能自动决定任意C#重载。相应规则/结果可以按调用点缓存，动态语言对象还可能提供自己的动态行为。[dynamic说明](https://learn.microsoft.com/en-us/dotnet/csharp/advanced-topics/interop/using-type-dynamic)说明了其编译与运行语义。

<a id="c05-var-versus-dynamic"></a>
### var与dynamic的两个原例

方法片段E05-21，故意保留错误赋值；此片段不能编译：

```csharp
var num = 10;   // 静态推断为int
num = "hello"; // 不能把string赋给int
```

独立方法片段E05-22：

```csharp
dynamic val = 10;
val = "hello";
val.Foo(); // 语法/绑定留待运行；字符串无此成员时RuntimeBinderException
```

var是类型推断，不是任意变换类型的容器。例中初始化为整数便得到int；若初始化表达式本身是dynamic，var也可推断成dynamic，不能把“使用var”绝对等同于完全消除动态绑定。第二例可改变所指对象的实际类型，但调用不存在的Foo会失败，不是任意成员都真的可用。

这还影响原答提到的编译检查和IDE成员提示：对直到运行时才知道的成员，通常无法提供与确定静态类型相同的成员存在性检查或可靠成员列表，错误可能到运行时才暴露。语法、已知静态部分及IDE的其他功能仍然存在，不能说所有检查或整个智能提示都失效。

<a id="c05-dynamic-scenarios"></a>
### COM、Excel和动态语言场景为何方便

原答列了Python/Ruby等动态语言对象、IDispatch COM对象、HTML DOM，以及旧Silverlight/Web交互背景。dynamic可以让调用形式接近普通成员使用，减少某些显式反射/转换代码；不同平台、语言宿主和对象能力仍决定是否支持相应操作。

思考区另外提到Excel COM互操作：例如从动态COM对象取某个Excel成员时，运行时才按对象提供的接口绑定，源码不必逐项写繁琐反射步骤。这保留“与外部组件交互”的独有具体场景，不表示本书泛型/CLR理论自动让Unity AOT或非Windows平台具有Excel COM运行环境。

原书Framework常需相关Microsoft.CSharp/System.Core支持，调用点绑定、缓存和生成规则带来时间/内存成本。思考中提到动态生成代码/匿名动态程序集的历史实现背景，应理解为相应运行时实现路径，不是每个dynamic变量声明都会生成一个新匿名程序集。现代AOT、裁剪和Unity限制要按目标环境判断。

不宜把“dynamic昂贵”又倒推为“显式反射一定更快”。调用点缓存、调用频率、对象种类及JIT/AOT条件都会影响结果；优先选择能表达正确契约的静态接口，确有动态交互再评估它的便利和成本。
