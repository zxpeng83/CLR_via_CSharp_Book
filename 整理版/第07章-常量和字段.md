## const的因果关系：语言规定和不变化要分开

原提问的链条是“值从不变化→定义时必须编译期确定→值放进元数据→只能定义编译器识别的基元类型常量”。其中需要分清**const的语言定义**和一般意义上的“不变化”。

C# const要求声明时使用相应常量表达式，值在编译期可确定；以后不能重新给该常量赋值。编译器利用这个条件，在编译使用方时把相应值替换到使用位置。可是“不变化”本身并不在逻辑上推出“必须编译期知道”：例如对象创建时取得的日期可以存进readonly字段，构造后不再重赋，日期仍是运行时才知道的。

因此，合理的理解顺序是：语言先规定const允许的类型与常量表达式；编译器能在这些规则内求值并记录资料；使用常量的源码按规则替换该值，得到相应编译和运行行为。这套设计能减少运行时读取字段等工作，但不能倒过来证明任何运行时确定的值都一定会变化，或“保存在元数据”自然禁止所有用户类型。

思考区还有一个有价值的区别：**元数据记录常量是实现/表示机制，不能单独作为允许类型范围的充分原因**。程序集元数据当然能描述大量非基元类型，问题在于C# const语义允许哪些值和表达式，不是元数据只能认识Int32。

<a id="c07-constant-types"></a>
## 常量类型、null和decimal的特殊表示

<a id="c07-constant-type-list"></a>
### “编译器识别的基元类型”不是所有值类型的另一名字

原书列出的常量类型包括Boolean、Char、Byte、SByte、Int16、UInt16、Int32、UInt32、Int64、UInt64、Single、Double、Decimal和String，对应常用C#别名bool、char、byte、sbyte、short、ushort、int、uint、long、ulong、float、double、decimal、string。字面量5、3.14、true、"hello"及`10 + 20`这样的合法常量表达式，能说明“编译期可求值”。

枚举类型也可用于相应常量。其他引用类型允许值为null的常量，例如`const object Missing = null`，这并不是在编译期创建一个任意类实例。数组/普通用户类的非null实例、DateTime及任意用户struct不能因为“内容以后不改”就成为合法const。decimal是C#预定义类型，但不意味着CLR有专用decimal算术指令；参见[第5章](第05章-基元类型、引用类型和值类型.md#c05-decimal-overflow)。

类型片段E07-01，展示几种允许形式和独立的反例：

```csharp
using System;

public enum Mode { Normal, Fast }
public class Constants
{
    public const int MaxEntries = 50;
    public const int Thirty = 10 + 20;
    public const double Ratio = 3.14;
    public const bool Enabled = true;
    public const string Greeting = "hello";
    public const decimal Price = 1.5m;
    public const Mode Selected = Mode.Fast;
    public const object Missing = null;

    // 反例，取消注释不能编译：
    // public const DateTime Started = default(DateTime);
    // public const object Present = new object();
}
```

常量需在声明时初始化，也不能当作可写字段地址传给ref/out；它并不是先留一个可变槽，之后再“锁住”。[C#常量说明](https://learn.microsoft.com/en-us/dotnet/csharp/programming-guide/classes-and-structs/constants)给出替换、允许值及版本影响。

<a id="c07-decimal-metadata"></a>
### decimal常量不能照搬所有整数常量的元数据形式

普通Int32 const可在CLI常量资料中表达，编译使用方得到相应整数值。decimal则有特殊编译表示；本机Framework C#编译`const decimal D = 1.5m`时，反射看到其字段为static initonly，并带DecimalConstantAttribute，不是普通Int32的literal标志。

以`const int N = 50`和`const decimal D = 1.5m`为独立探针的实测对照：

```text
N Literal=True InitOnly=False
DecimalConstantAttribute=False
D Literal=False InitOnly=True
DecimalConstantAttribute=True
```

这些反射标志不把源码D变成可由调用者重赋的字段，也不取消C#编译器读取其常量值并在使用点处理的语义。decimal使用点可能需要构造相应值，不能要求所有const都用同一条ldc指令，或说其定义库永远不含初始化逻辑。[DecimalConstantAttribute API](https://learn.microsoft.com/en-us/dotnet/api/system.runtime.compilerservices.decimalconstantattribute?view=net-10.0)说明它保存decimal常量的元数据用途。

<a id="c07-constant-storage"></a>
## MaxEntries=50：定义、使用、运行

原问题问：“常量属于静态成员吗？存储在类型还是实例里？”答案先分语言使用方式与运行时存储。

const成员按类型成员使用，隐式具有静态性质，不需要实例，也不再加static修饰符。原Math.PI例可按`Math.PI`使用；这不表示运行时必须为每个实例或每个类型都另放一个普通可读写字段槽。

原`public const Int32 MaxEntries = 50;`的三阶段完整保留：

| 阶段 | 发生什么 | 不应推出来的结论 |
| --- | --- | --- |
| 定义DLL | 编译器记录MaxEntries名称、类型及常量值50等资料 | 元数据不能表示其他类型 |
| 编译EXE | 根据参考输入找到该符号，取得50，替换到相应使用位置 | 每次运行都先从DLL读取这个普通const整数值 |
| 运行EXE | 执行包含相应值的代码，例如JIT处理带50的IL | 一定另有名为MaxEntries的普通实例或静态字段存储槽 |

典型普通整数使用方法可生成`ldc.i4.s 50`等指令，而不是`ldsfld`读取原常量字段。这里是符号和值的编译关系，不是说程序集元数据、IL、JIT机器码乃至字符串对象全部不占内存。

<a id="c07-constant-only-dependency"></a>
### 为什么某些只用const的EXE可以没有原DLL

若调用者只需要已经替换的整数常量，生成程序没有其他运行时类型/成员依赖，相应定义DLL可能不必加载。作者实际把只读取MaxEntries的已编译EXE单独复制到一个没有Limits.dll的验证目录，仍输出50。

这解释了原书“删除DLL也可能运行”的例子。条件是**生成结果没有其他所需依赖**；不能把该现象推广为任何参考了该库的程序都可删除它。若还创建库里的对象、读静态字段、反射或调用其方法，就要按那些实际依赖判断。验证只操作新生成的测试文件，原始资料没有删除或移动。

字符串常量的使用仍可在运行时形成/取得字符串对象；decimal又有上面的特殊表示。“没有一个为普通const整数专设的变量地址”比“常量运行时完全不需要任何内存”准确。

<a id="c07-versioning"></a>
## const与static readonly的完整对照

原PDF中的五行对照保留，并修正“静态字段存在System.Type反射对象里”“更换库总能自动更新”等过度概括。

| 特性 | `public const int Max = 50;` | `public static readonly int Max = 50;` |
| --- | --- | --- |
| 是否静态 | 隐式按静态成员使用，不另写static | 显式static字段 |
| 值确定时机 | 源码要求相应编译期常量表达式 | 字段初始化在运行时进行，可由初始化器/类型构造器计算 |
| 存储位置/表示 | 定义中的常量资料及相应使用点的值/代码；decimal等有特殊表示 | 类型关联的静态字段存储，不应画成直接塞进System.Type反射对象 |
| 内存分配 | 普通整数const无独立可变字段槽；代码/元数据/string等仍有各自成本 | 有相应静态字段存储，引用值所指对象也需按其类型判断 |
| 版本控制 | 已编译调用者保留旧值，想采用新const值通常需重新编译 | 调用者在运行时读实际绑定库的字段；若正确部署并绑定到更新库，可不重编调用者而取得新值 |

Framework静态字段通常与相应类型和AppDomain加载有关；不同封闭泛型类型、加载上下文/类型身份可以有不同静态状态。不能把“一个类型的共享字段”说成全世界、所有加载实例都同一份，也不能以反射Type对象的位置解释实际CLR字段存储。

<a id="c07-version-experiment"></a>
### 更换库，两个已编译读取路径出现什么区别

两程序集验证E07-02，以50为初版值。Library类型片段，编成Limits.dll：

```csharp
public class Limits
{
    public const int MaxEntries = 50;
    public static readonly int RuntimeMaxEntries = 50;
}
```

调用者完整程序，参考该库编译一次：

```csharp
using System;
class Program
{
    static void Main()
    {
        Console.WriteLine(Limits.MaxEntries);
        Console.WriteLine(Limits.RuntimeMaxEntries);
    }
}
```

初次运行输出50/50。然后只把测试目录中库的两个定义值改成60，重新编译并部署该库，在新进程运行相同EXE，输出50/60。这里60是作者用于检验原版本问题的后续值；原场景的MaxEntries=50保留。const使用点没有重编，静态readonly路径读到了更新库的字段。

这不保证任何部署中换任意DLL都会成功：程序集身份、版本绑定策略和应用实际加载的库都要满足条件。static readonly解决的是“运行时读取这个字段的值”这一问题，不是替所有组件版本和API契约自动兜底。[字段规范中的版本例](https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/language-specification/classes#1553-readonly-fields)解释相同机制。

<a id="c07-field-modifiers"></a>
## 表7-1：四种字段修饰符

字段可以表达类型共享状态或实例状态，还可以对赋值/访问施加限制。原表中的四行、原字段名和用途全部保留：

| CLR术语 | C#表示 | 说明 | 原例及条件 |
| --- | --- | --- | --- |
| Static | static | 与相应类型关联的状态 | `public static int InstanceCount = 0;`可保存类型相关计数；仅这行声明还没有在创建实例时自动加一 |
| Instance | 不写static的普通字段 | 每个实例的状态 | `private string _name;`各实例有自己的字段值；其引用可指同一个或不同字符串对象 |
| InitOnly | readonly | 约束字段赋值的位置 | `public readonly DateTime CreationTime = DateTime.Now;`在声明初始化器/定义它的相应实例构造器赋值，之后不能普通重赋 |
| Volatile | volatile | 对相应并发字段访问施加排序/优化限制 | `private volatile bool _stopRequested = false;`表达停止标志；不保证所有处理器立即看到最新写入，也不是完整线程生命周期协议 |

static与instance决定“字段关联谁”，readonly决定“在哪些位置可给字段赋值”，volatile决定“相关访问需满足什么并发语义”。它们不是四种互斥的存储类别；static readonly就是合法组合。另有语言组合限制，例如不能直接把readonly和volatile随意同时用在一个字段上。

## AppSettings和User的readonly字段

<a id="c07-appsettings"></a>
### 运行时取得共享设置，和编译期常量不同

原AppSettings用了LoadFromConfig和MaxRetryCount=3。类型片段E07-03补一个配置读取的**示意实现**，使原缺失的方法有明确来源；这个返回字符串不是声称已经读取真实配置文件。

```csharp
public static class AppSettings
{
    public static readonly string ConnectionString = LoadFromConfig();
    public static readonly int MaxRetryCount = 3;

    private static string LoadFromConfig()
    {
        // 示意配置结果；真实应用在这里实现相应配置读取。
        return "Server=demo;Database=Example;";
    }
}
```

ConnectionString由运行时初始化逻辑取得，const不允许这样调用任意方法求值。MaxRetryCount虽然目前写字面量3，采用字段读还是常量替换仍是不同契约。原提到书中InvalidChars的static readonly用法也同理：可让调用者在运行时读更新定义，但若字段引用的是可变数组，还需看数组内容的公开方式，不能把readonly当深冻结。

<a id="c07-user-readonly"></a>
### 每个User自己的ID和注册时间

类型片段E07-04，保留UserId和RegisteredAt原例：

```csharp
using System;
public class User
{
    public readonly string UserId;
    public readonly DateTime RegisteredAt;

    public User(string id)
    {
        UserId = id;
        RegisteredAt = DateTime.Now;
    }
}
```

每个User有自己的这两个字段；不同实例可传不同id，创建时取得的时间也可能不同，并不保证两个紧邻创建的实例必有不同时间戳。readonly不是所有实例共用一个值，也不要求这个值编译期可知。

原“任何构造器可以赋值”要限定为**声明字段的类型中相应构造器**：实例readonly在声明处或该类型实例构造器按规则赋值；static readonly在声明处或该类型的静态构造器赋值。不能跑到派生类型构造器、普通方法或另一类型里重赋。相应合法初始化范围内可以多次赋值，也不等于整个构造过程只允许一条赋值指令。[readonly规则](https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/keywords/readonly)明确这些位置。

<a id="c07-readonly-array"></a>
## DefaultNames数组：引用只读不等于对象不变

原问题里的只读数组A/B/C与元素Z完整保留。完整程序E07-05：

```csharp
using System;
public class MyClass
{
    public static readonly string[] DefaultNames = new string[] { "A", "B", "C" };
}

class Program
{
    static void Main()
    {
        MyClass.DefaultNames[0] = "Z";
        Console.WriteLine(MyClass.DefaultNames[0]);

        // 反例，取消注释会报CS0198：不能从这里给字段换引用。
        // MyClass.DefaultNames = new string[] { "X", "Y", "Z" };
    }
}
```

输出Z。readonly限制DefaultNames这个字段的引用重赋，数组对象内容仍可修改。数组里有string也不改变这一点：string对象自身的不可变性，与数组槽从"A"引用改成"Z"引用，是不同问题。

要设计不可变对象或公开线程安全状态，需要考虑可达对象、写入入口及同步协议。仅有readonly关键字不自动保证整个对象图不可变或所有并发使用正确。它可以帮助维护赋值契约，不能代替这些更完整的设计。

<a id="c07-volatile"></a>
## Worker的volatile标志与同步边界

<a id="c07-worker-flag"></a>
### 原启停标志的作用

原Worker示意了一个线程写运行标志、另一线程在循环读。类型片段E07-06保留Start/Stop/Work，不补造一个已经运行的完整线程管理器：

```csharp
public class Worker
{
    private volatile bool _isRunning;

    public void Start()
    {
        _isRunning = true;
        // 原例在此启动工作线程，具体启动代码省略。
    }
    public void Stop()
    {
        _isRunning = false;
    }
    private void Work()
    {
        while (_isRunning)
        {
            // 原例在此执行工作，具体逻辑省略。
        }
    }
}
```

这种标志访问需要遵守volatile相关语义，不能把一次普通读取的结果永久当作循环里的不变值来替代每次需要的访问。原表说“不会执行某些线程不安全优化”应理解为相应优化/重排限制，不是让编译器、CLR及硬件停止所有优化或缓存。

<a id="c07-volatile-boundaries"></a>
### 可见性、排序和原子性分别看

C#规范规定volatile读具有acquire语义，写具有release语义，从而限制相应内存访问重排。原“立即看到最新值”的说法过强：多处理器上，并不保证一次读必取得任何处理器刚写的最新值，也不保证写入在一个固定时间内立刻被其他处理器看见；所有线程观察的volatile写也不要求一个单一全局总序。[字段规范](https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/language-specification/classes#1554-volatile-fields)及[volatile说明](https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/keywords/volatile)区分这些保证。

原总结“volatile不能保证操作原子性”同样要限定。它不把`count++`这样的读—算—写复合操作变成原子操作；允许的相应类型有基本读/写的原子性规则，不能因此断言一个bool标志的基本赋值也被撕裂。共享计数、多个状态之间的一致性及等待/通知等复杂协议，应使用满足该用途的Interlocked、lock或其他同步构造，后续见[第29章](README.md#chapter-29)。

本章核验了编译后的IsVolatile修饰资料及相应volatile读写前缀，没有用一次线程循环“恰好停了”证明所有排序或时效保证，也没有把示意Start当作可以反复启动、停止和复用的完整并发组件。

<a id="c07-inline-initialization"></a>
## SomeType和MyClass的声明处初始化

<a id="c07-sometype"></a>
### 同样写在字段旁，底层类别仍不同

类型片段E07-07，保留原_count、_startTime和_items：

```csharp
using System;
using System.Collections.Generic;
public class SomeType
{
    private int _count = 0;
    private static readonly DateTime _startTime = DateTime.Now;
    private readonly List<string> _items = new List<string>();
}
```

声明处初始化让初始状态容易看见；实例_count/_items和静态_startTime却不能搬进同一类构造器来执行。实例初始化器参与相应实例构造逻辑；静态初始化器参与类型初始化逻辑。const则按前述编译期规则处理，不能因为声明外形相似，就说每个对象构造都执行一遍const赋值。

对象的字段先有默认值，然后才发生相应初始化逻辑；例如普通int字段默认0，引用字段默认null。原说“值类型不写初始化也会归零”在对象字段语境成立，但不能扩大为任意未赋值局部变量都能直接读取。值/字段/局部的区别见[第8章](第08章-方法.md#c08-local-vs-field)。

<a id="c07-simple-initializers"></a>
### _x=5和_y="Hello"的两个原片段

类型片段E07-08a：

```csharp
public class MyClass
{
    private int _x = 5;
    private string _y = "Hello";
    public MyClass() { }
}
```

原回答的对应手写版本E07-08b，独立类型片段：

```csharp
public class MyClass
{
    private int _x;
    private string _y;
    public MyClass()
    {
        _x = 5;
        _y = "Hello";
    }
}
```

在这里，两者使用普通Object基类且没有其他可观察回调，完成构造后的字段均为5和Hello，足以说明初始化赋值参与构造逻辑。但编译器生成的实例字段初始化器通常放在相应base构造调用之前，手写构造器body赋值发生在base返回之后；不能把这两个片段的最终状态相同升级为所有继承场景严格等价。

“CLR不再处理C#声明处初始化语法”是源码与编译产物分工的说法。运行时执行相应构造/初始化代码和默认状态规则，不表示运行时不存在字段、默认零值或任何其他初始化行为。

<a id="c07-multiple-constructors"></a>
## 三个构造器与InitializeCache

<a id="c07-cache-inline"></a>
### 三份构造器IL不等于一个对象初始化三次

原List<ExpensiveObject>场景完整保留。类型片段E07-09a，补空的元素类型让示意可编译：

```csharp
using System.Collections.Generic;
public class ExpensiveObject { }
public class MyClass
{
    private List<ExpensiveObject> _cache = new List<ExpensiveObject>();
    public MyClass() { }
    public MyClass(int capacity) { }
    public MyClass(string name) { }
}
```

这三个独立构造器都走base入口，编译器可以在每个入口的IL中插入_cache初始化，增加代码体积。**选一个构造器创建一个对象时，该对象这项初始化执行一次**；分别创建三个对象才有三个对象的初始化。原答把“有多份IL”直接解释成“同一个昂贵操作无谓执行多次，而希望只一次”，混淆了代码复制和执行次数。

`new List<ExpensiveObject>()`创建空列表，不是在这一句构造大量ExpensiveObject元素；原例capacity/name参数也还没有实际用于列表容量或命名。不能凭类型名Expensive就声称已经测出很大的开销。若字段初始化确实有昂贵操作，再根据实际对象创建频率、分配和生成代码判断。

<a id="c07-cache-helper"></a>
### 辅助方法集中实现，仍要按每个对象调用

原提取InitializeCache的三个构造器例E07-09b，独立类型片段：

```csharp
using System.Collections.Generic;
public class ExpensiveObject { }
public class MyClass
{
    private List<ExpensiveObject> _cache;

    public MyClass()
    {
        InitializeCache();
    }
    public MyClass(int capacity)
    {
        InitializeCache();
        // 原例省略基于capacity的其他逻辑。
    }
    public MyClass(string name)
    {
        InitializeCache();
        // 原例省略基于name的其他逻辑。
    }
    private void InitializeCache()
    {
        _cache = new List<ExpensiveObject>();
    }
}
```

初始化实现在源代码里集中到一处，便于维护；每个选中的构造器仍调用一次，分别创建三个对象仍有三个列表。辅助方法不是全类型单例缓存，也不自动减少每个对象必须的初始化次数。JIT还可能内联，不能把源码集中直接当作最终机器码体积或固定性能收益的证明。

构造器body能根据capacity/name选择不同初始化策略，确实可以使逻辑更明确；但要实际实现并保持需要的语义。本例保留原参数和省略处，不虚构已经实现了容量/命名优化。

<a id="c07-constructor-chain"></a>
### this构造链为什么需要另外判断

若用`this(...)`转到同类其他构造器，实例初始化器通常在最终通向base入口的那个构造器执行，不是每一级this链各插入一次。作者的计数验证中，三个独立构造器分别创建三个对象累计3；一条this链创建一个对象累计1，再创建另一个对象累计2。它说明对象数量/入口和代码复制的区别。

也要避免在this链的每层body又手动重复调用同一个初始化辅助方法；那才可能真的让同一对象执行多次。是否重复应检查实际生成代码和调用链，不能仅看“构造器有几个”。[第8章初始化器复制例](第08章-方法.md#c08-initializer-duplication)进一步展开这一选择。

<a id="c07-initialization-timing"></a>
## 初始化顺序和静态初始化时机

思考区独有的“继承链或静态初始化会影响顺序”应该保留，但其结论需要纠正。

作者用基类构造器调用派生重写作为观察探针：派生字段声明处`x=5`的版本在该回调中输出inline:5；把赋值移到派生构造body的版本输出body:0。说明搬动赋值可能改变基类构造期间能观察到的状态。此探针用于解释顺序，不鼓励把构造器虚调用当设计惯例；详见[第8章](第08章-方法.md#c08-virtual-constructor)。

静态方面，只有静态字段初始化器而未显式声明静态构造器的类型，C#可产生beforefieldinit标志；显式静态构造器影响相应触发语义。不能说“内联一定惰性、显式静态构造器一定更早加载”，也不能把类型被加载、JIT某方法和实际运行类型初始化当同一个时刻。具有beforefieldinit的类型反而允许实现选择更宽的初始化时机范围；具体规则及验证见[第8章](第08章-方法.md#c08-beforefieldinit)。

原提醒“便利语法有性能和顺序权衡”仍成立：检查是否需要每个实例的状态、是否共享静态状态、是否有this链、基类期间是否可观察、生成代码是否重复，以及实际目标运行时的初始化契约。选择手写body或辅助方法要服务这些目的，不能因为它更显式就一律判定更快、更早或更安全。

## 重要纠错与现代差异

| 编号 | 原误解/过度概括 | 修正及原因 |
| --- | --- | --- |
| C07-F01 | 不变化必然要求编译期已知；放进元数据便推出只允许所有基元类型 | const是语言规定的常量类型/表达式；运行时readonly可不再重赋，元数据机制不是唯一因果 |
| C07-F02 | 非基元等于引用类型，任何值类型都能const，所有const均同一CLI表示 | enum/decimal/string/其他引用null按语言规则区别，普通struct不自动允许；decimal有特殊常量属性/字段表示 |
| C07-F03 | const运行时完全不占内存，参考该库的任何程序都可没有DLL | 普通整数常量无专设可变槽，代码/元数据/string等仍有成本；只有生成结果无其他库依赖才可省加载 |
| C07-F04 | 静态字段直接存在System.Type对象，全世界只一份，换库必获新值 | 相应类型/加载实例的字段存储；闭合泛型及上下文区别；新值要求实际部署和绑定到更新库 |
| C07-F05 | 任何构造器都能写readonly，引用对象也不可变，readonly自动线程安全 | 定义类型的相应构造位置限定；字段引用不重赋不等深冻结/同步；DefaultNames内容仍可改 |
| C07-F06 | volatile保证立即最新，或任何基本读写都不原子，禁止全部优化 | acquire/release与相应重排限制；不保证立即最新，基本读写和复合操作原子性区别 |
| C07-F07 | const/实例/静态初始化都搬进每个实例构造器，未赋局部也可读默认0 | 分类看const编译、实例构造和类型构造；对象字段默认值与局部确定赋值规则不同 |
| C07-F08 | 两个初始化片段在任意继承环境严格等价，显式静态构造器总更早 | base之前初始化与body之后赋值可观察不同；beforefieldinit改变允许时机范围，不能绝对早/晚 |
| C07-F09 | 三份构造器IL就是一个对象重复初始化三次；提取辅助方法减少对象应有初始化 | 独立入口/this链/每个对象的次数分开；辅助集中实现仍按调用执行，空List不创建昂贵元素 |

常量、字段、读取/赋值契约、初始化生成代码和一次环境测量各自有明确范围。关键语言规则使用上述官方资料及[CLI六版](https://www.ecma-international.org/wp-content/uploads/ECMA-335_6th_edition_june_2012.pdf)，实测源码/命令/结果见作者核验记录；原错误也已在代码注释、表格和解释中落实修正。
