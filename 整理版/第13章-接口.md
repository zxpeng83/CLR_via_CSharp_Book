<a id="c13-contract"></a>
## 单类继承、多接口契约与历史语境

CLR的普通类模型只允许一个直接基类，允许实现多个接口。原“缩水版多继承”类比表示接口提供多个能力协定，不等于复制多个基类的实例状态/实现；第四版所讲的传统接口主要声明实例契约，不能把“接口没有实现”写成全部现代C#接口的定律。

原章路线还包括泛型接口、接口约束、一类型实现同一泛型接口的不同构造（如IComparable<int>和IComparable<string>）、同名接口成员、EIMI的类型安全用途及基类/接口设计选择。IS-A与CAN-DO可辅助判断继承的对象模型与能力契约；Stream通过基类集中提供实现，集合通过接口暴露能力，只是原对照场景，不排除同一类型同时继承Stream并实现其他接口。

泛型接口能保留元素/参数类型，减少某些object入口装箱，但不是任意接口调用都不装箱。添加接口成员可能影响既有实现者，基类新增成员也须看抽象/默认实现及版本契约；现代默认接口成员有另一套规则，不据此宣称任何升级都自动兼容。

<a id="c13-collection-contracts"></a>
### IDisposable、IEnumerable、IEnumerable<T>与ICollection<T>

原用户给的四接口是类库契约形状，以下保留全部方法和属性，作为**声明示意**而不在自己的System命名空间重新定义BCL。

```text
public interface IDisposable { void Dispose(); }
public interface IEnumerable { IEnumerator GetEnumerator(); }
public interface IEnumerable<T> : IEnumerable {
    new IEnumerator<T> GetEnumerator();
}
public interface ICollection<T> : IEnumerable<T>, IEnumerable {
    void Add(T item);
    void Clear();
    bool Contains(T item);
    void CopyTo(T[] array, int arrayIndex);
    bool Remove(T item);
    int Count { get; }
    bool IsReadOnly { get; }
}
```

IDisposable约定Dispose入口，资源处理行为还看实现；IEnumerable提供获取枚举器的能力；ICollection<T>再提供Add/Clear/Contains/CopyTo/Remove及Count/IsReadOnly。只读集合仍可能对Add等调用拒绝操作，接口中有方法不等于任何实例都可修改。

```text
IEnumerable
    ↑
IEnumerable<T>
    ↑
ICollection<T>
```

IEnumerable<T>包含非泛型契约，因此实现者还须满足非泛型入口。ICollection<T>声明重复列IEnumerable在这组继承关系下不会新增一个独立协定；不能从重复列名臆测作者必为防将来变化或文档生成等动机。

Count和IsReadOnly是只读属性契约，降低后的形状对应get_Count/get_IsReadOnly，不是两个实例字段，也不是此处一定有一对get/set。实现者可以返回自己的_count字段或计算结果；类中仅写`public int Count;`不能用字段履行该属性契约。传统接口不声明实例字段；现代静态成员要另按语言版本判断。

<a id="c13-two-getenumerators"></a>
### new隐藏接口成员，与返回类型契约并存

IEnumerable<T>中new表示有意隐藏继承的同名方法，提供泛型返回契约；省new通常是隐藏警告，不是删除父接口方法。两个契约分别存在。

| 接口 | GetEnumerator返回 |
| --- | --- |
| IEnumerable | IEnumerator |
| IEnumerable<T> | IEnumerator<T> |

普通C#不能声明两个仅返回类型不同、同名同参数的public方法。实现者常保留一个public泛型入口，再显式实现非泛型入口；不是强行把它们当同一个返回类型的方法。

<a id="c13-enumeration"></a>
## GetEnumerator返回枚举器，Current返回元素

原用户追问“不是IEnumerator吗”是对上一轮不准确解释的纠正。非泛型GetEnumerator确实返回IEnumerator；object是非泛型Current的类型。

```text
public interface IEnumerator {
    object Current { get; }
    bool MoveNext();
    void Reset();
}
```

| 成员 | 类型 |
| --- | --- |
| IEnumerable.GetEnumerator() | 返回IEnumerator对象/视图 |
| IEnumerator.Current | 返回object表示的当前元素 |

泛型IEnumerator<T>则有T Current，实际BCL还继承IDisposable与非泛型IEnumerator。它是out T协变声明，不能继续沿用第12章原答的in T错误。

Current返回object只限定调用者看到的静态返回契约，不表示枚举器或CLR不知道某个实际元素的类型。若容器已经存了一个装箱对象，读取该对象引用不需要重新猜测并再次装箱该元素。

<a id="c13-arraylist-current"></a>
### ArrayList.Add(123)已经装箱，读取Current不再给同一元素装箱

以下完整程序保留ArrayList和非泛型while路径，也保留foreach入口。

```csharp
using System;
using System.Collections;
class Program {
    static void Main() {
        ArrayList list = new ArrayList(); list.Add(123); // object入口：装箱发生在这里
        foreach (object x in list) Console.WriteLine(x);
        IEnumerator e = list.GetEnumerator();
        while (e.MoveNext()) {
            object x = e.Current; // 取得已存的object引用，不再次给该int元素装箱
            Console.WriteLine(x);
        }
    }
}
```

输出两次123。若把当前object转换为int，有相应拆箱检查。不是看到`object x=e.Current`就必新增盒，须看枚举器如何得到object；ArrayList已经存盒，而其它枚举器也可能在Current中将值转object。

<a id="c13-list-enumerator"></a>
### List<int>的元素与枚举器装箱要分开

完整程序保留泛型foreach、显式IEnumerator<int>变量及while读取。

```csharp
using System;
using System.Collections.Generic;
class Program {
    static void Main() {
        List<int> list = new List<int> { 123 };
        foreach (int x in list) Console.WriteLine(x);
        using (IEnumerator<int> e = list.GetEnumerator()) {
            Console.WriteLine(e.GetType().IsValueType);
            while (e.MoveNext()) { int x = e.Current; Console.WriteLine(x); }
        }
    }
}
```

输出123、True、123。List<int>.GetEnumerator返回结构体枚举器，赋给IEnumerator<int>按语言语义转换为接口时可装箱枚举器；Current仍返回int元素，不经object入口逐个装箱。对具体List的foreach可选择public枚举器模式，不必按原伪代码先声明接口变量。编译器/运行时优化还可能影响实际分配，不能据泛型二字断言全部对象零装箱。

“IEnumerable是能枚举、IEnumerator是正在枚举、Current是当前元素”可作记忆；foreach的真实降低还包括清理枚举器和类型检查等规则，原两行GetEnumerator/while只是步骤示意。

<a id="c13-eimi"></a>
## MyList<T>的两个入口与EIMI

原问题连续问“为什么不能写public、访问范围是否未知、派生类可否使用”。先给完整类型：它保持一个public泛型GetEnumerator和一个显式非泛型入口，两个接口路径复用同一逻辑。

```csharp
using System;
using System.Collections;
using System.Collections.Generic;
public class MyList<T> : IEnumerable<T> {
    private readonly List<T> items = new List<T>();
    public void Add(T item) { items.Add(item); }
    public IEnumerator<T> GetEnumerator() { return items.GetEnumerator(); }
    IEnumerator IEnumerable.GetEnumerator() { return GetEnumerator(); }
}
class Program {
    static void Main() {
        var list = new MyList<int>(); list.Add(123);
        using (IEnumerator<int> e1 = list.GetEnumerator()) {
            if (e1.MoveNext()) Console.WriteLine(e1.Current);
        }
        IEnumerable list2 = list;
        IEnumerator e2 = list2.GetEnumerator();
        try { if (e2.MoveNext()) Console.WriteLine(e2.Current); }
        finally { var d = e2 as IDisposable; if (d != null) d.Dispose(); }
    }
}
```

输出123、123。显式入口属于类型内的接口实现成员，只是不作为类的普通public API被点名访问；不能说它根本“不属于类”。public入口依然可见，因此`list.GetEnumerator()`并不是原答标记的编译反例。通过IEnumerable调用才选非泛型契约。

只写public泛型方法不能满足这组同参数但返回类型不同的非泛型声明；两个public GetEnumerator仅凭返回类型也不能重载。以下是**反例形状**，不是完整可用MyList。

```text
public IEnumerator<T> GetEnumerator() { ... }
public IEnumerator GetEnumerator() { ... } // 反例：同名同参不能仅返回类型重载
public IEnumerator IEnumerable.GetEnumerator() { ... } // 反例：显式实现不能加public
private IEnumerator IEnumerable.GetEnumerator() { ... } // private也不能这样写
```

<a id="c13-derived-eimi"></a>
### 类内、类外和派生类的准确调用范围

以下类型片段与前述MyList<T>编译，保留原this、base、castthis三种调用，全部合法。它们不等于用类成员语法直接点名显式入口。

```csharp
using System;
using System.Collections;
public class MyDerivedList<T> : MyList<T> {
    public void Foo() {
        Console.WriteLine(this.GetEnumerator() != null); // 继承的public泛型方法
        Console.WriteLine(base.GetEnumerator() != null); // 同一public基类方法
        Console.WriteLine(((IEnumerable)this).GetEnumerator() != null); // 接口入口
    }
}
```

调用Foo输出三个True；实际使用取得的枚举器应按契约管理其寿命，此处只验证成员选择。原表中“派生类完全不能调用”改为“不能直接点名/override基类EIMI，但可按接口视图调用”；若存在public同名入口，普通类视图调用也正常。

原OldMethod(IEnumerable items)可取其非泛型枚举器，这指基于非泛型契约的调用方，不表示今天写的代码无法采用它。IntelliSense通常按当前静态类型展示可见成员，不把一次编辑器提示当语言可编译性的证明。

原思考提出“遥控器切换信号源”类比：同一个对象可以从不同接口契约进入各自入口；切换视图不等于复制对象，具体选择仍由成员查找与接口映射决定。

<a id="c13-eimi-access-tables"></a>
### 原两张访问表分别保留

| 调用方式 | 是否允许 | 条件 |
| --- | --- | --- |
| MyList<T>实例直接点名EIMI | 不允许普通成员语法点名 | 同名public泛型入口仍可调用 |
| 派生类使用 | 可按接口视图调用 | 不能直接点名或override基类EIMI |
| 接口变量调用 | 接口及成员可访问时允许 | 按该契约映射实现 |
| 反射调用 | 相应反射能力下可定位非public实现 | 不当作无条件绕过全部平台/运行权限限制 |

另一表侧重调用场景和继承/元数据原因，不只整表合并掉。

| 调用场景 | 能否调用 | 原原因的修正 |
| --- | --- | --- |
| MyList<T>普通实例视图 | 可调用public入口，不能点名EIMI | 语言成员查找决定，非成员毫无归属 |
| MyDerivedList<T>派生视图 | 可public/base或接口转换 | final限制重写，不禁止接口调用 |
| IEnumerable视图 | 相应成员可访问时可调用 | 接口映射选择实现 |
| 反射 | 可按反射API定位及调用 | 规则与普通源码不同，非一律无限制 |

EIMI在C#中不写public/protected/private修饰符，不等于“没有访问控制”。普通编译器生成的CLI方法通常为private、final、virtual、newslot，并带接口实现映射；private实现能通过可访问接口契约被调用，和普通类成员可见性是不同层次。源码不能直接写virtual/override EIMI，不能反解释为IL non-virtual。[显式接口实现规则](https://learn.microsoft.com/en-us/dotnet/csharp/programming-guide/interfaces/explicit-interface-implementation)

公司前台/员工通道与身份验证的原类比可说明访问视角不同，但接口转换是在检查类型是否支持契约，不是权限认证或安全隔离。藏掉普通API不阻止消费者通过已暴露接口使用成员。

<a id="c13-virtual-bridge"></a>
### 需要派生扩展时，转发到真实virtual桥

原第一段转发public GetEnumerator却未标virtual，不能称它已经调用可重写方法。下面完整类型片段保留protected virtual GetEnumeratorVirtual桥、public入口和显式入口三部分，避免在EIMI本身上要求override。

```csharp
using System.Collections;
using System.Collections.Generic;
public class ExtensibleList<T> : IEnumerable<T> {
    private readonly List<T> items = new List<T>();
    public void Add(T item) { items.Add(item); }
    protected virtual IEnumerator<T> GetEnumeratorVirtual() { return items.GetEnumerator(); }
    public IEnumerator<T> GetEnumerator() { return GetEnumeratorVirtual(); }
    IEnumerator IEnumerable.GetEnumerator() { return GetEnumeratorVirtual(); }
}
public class DerivedList<T> : ExtensibleList<T> {
    protected override IEnumerator<T> GetEnumeratorVirtual() {
        return base.GetEnumeratorVirtual();
    }
}
```

这是可选择的扩展设计，不凭聊天推定原书必推荐唯一方案。EIMI的文档/普通API发现性与派生扩展成本确实要考虑；它也不能自动消除值类型接口转换的装箱，更不能用“性能最优”作为选择定律。

<a id="c13-accessibility"></a>
## 接口类型、成员契约与实现方法的可见性

“接口方法不能声明访问修饰符”和“实现接口方法必须public”讲的是不同对象。在第四版的C# 5中，普通接口实例抽象成员不写访问修饰符，默认public；类的**隐式实现**通常需要public实例成员。EIMI是独立的实现语法，不写public。接口类型本身又有自己的可见范围。

<a id="c13-interface-members"></a>
### 原历史反例与C# 8以后的差异

以下保留原Foo/Bar/Baz场景，是**历史语言反例**；用C# 5编译，public Bar、protected Baz均不合法。原答把protected抽象成员写成“永远不行”，还把现代抽象成员写成“仍不能有修饰符”，都超过了历史结论。

```csharp
interface ITest {
    void Foo();
    public void Bar();     // C# 5反例：CS0106
    protected void Baz(); // C# 5反例：CS0106；不能泛化到现代C#
}
```

以下是**C# 8+/.NET现代运行时类型片段**。MustImplement/WithBody/Helper/Factory保留原现代例；补上原答漏掉的显式public抽象Bar和protected抽象Baz。私有Helper必须有实现，不能照抄成无实现的私有抽象成员。

```csharp
public interface IModernTest {
    void MustImplement();
    public void Bar();
    protected void Baz();
    public void WithBody() { Helper(); }
    private void Helper() { }
    protected void Factory() { }
}
```

另一个原例把抽象入口叫MustOverride，而不是MustImplement：`void MustOverride(); public void WithBody() { } private void Helper() { }`也表达同一现代接口结构；MustOverride这个名字不要求实现者在C#类方法上写override。默认接口实现需要相应编译器和运行时支持，不能仅凭新编译器就推定.NET Framework具有同样的默认接口执行能力。[接口成员规范](https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/language-specification/interfaces)

原两层要求表保留其C#/CLR比较用途，并把“CLR必须公开”与方法标记分开：

| 层级 | 要求 | 备注 |
| --- | --- | --- |
| C#编译器 | 隐式实现按接口映射选择合适的public实例成员；EIMI另有规则 | public是这种语言映射的条件，不是所有CLI实现方法的可见性定律 |
| CLR/CLI | 通过接口实现映射与相应虚方法语义分派；典型C#实现可带virtual/final | final不禁止接口调用；private EIMI仍可被映射 |

<a id="c13-protected-implementation"></a>
### protected实现为什么不能直接隐式匹配

原MyFile场景是**编译反例**：消费者想写`IDisposable d = new MyFile(); d.Dispose();`，但类型本身并未合法实现契约，不能先把这一调用当成真实运行成功。

```csharp
using System;
class MyFile : IDisposable {
    protected void Dispose() { } // CS0737：不满足C#隐式接口实现
}
```

另一个原场景保留Base.Foo、IFoo.Foo与Derived：

```csharp
class Base { protected void Foo() { } }
interface IFoo { void Foo(); }
class Derived : Base, IFoo { } // CS0737：protected Base.Foo不是隐式实现
```

这可以说明C#自动映射不把受保护入口变成public接口契约，不能据此证明CLR绝不允许非public实现，也不能把“基类作者不愿暴露”当成已查证的唯一设计动机。开发者确实可以在Derived中显式提供接口转发，下面为**正确完整类型片段**：

protected普通方法也供声明类本身使用，并非只供派生类。接口实现是否被C#隐式选择，与实现方法能否从某个调用位置访问，不能混成同一个判断。

```csharp
class Base { protected void Foo() { } }
interface IFoo { void Foo(); }
class Derived : Base, IFoo {
    void IFoo.Foo() { base.Foo(); }
}
```

这与前面的`IEnumerator IEnumerable.GetEnumerator() { return GetEnumerator(); }`是同类桥接设计。EIMI内部可以调用自身或基类中可访问的成员，不会因调用者拿接口视图就失去实现体的访问权限。

原提到VB允许非public成员配Implements，以下**独立VB完整程序**保留Protected Overridable场景；本机Framework vbc实测输出`protected VB`。不同语言的接口实现声明规则可以不同。

```vb
Imports System
Interface IFoo
    Sub Foo()
End Interface
Class Example
    Implements IFoo
    Protected Overridable Sub Foo() Implements IFoo.Foo
        Console.WriteLine("protected VB")
    End Sub
End Class
Module Program
    Sub Main()
        Dim value As IFoo = New Example()
        value.Foo()
    End Sub
End Module
```

[VB Implements规则](https://learn.microsoft.com/en-us/dotnet/visual-basic/language-reference/statements/implements-statement)支持通过接口使用非public实现；它不能反过来改变C#的隐式映射语法。

<a id="c13-interface-type-access"></a>
### 顶层与嵌套接口不能混为一谈

原public/internal ITest场景分别为`public interface ITest { }`和`internal interface ITest { }`，须在不同示例命名空间或不同程序中声明，不能把两个同名定义原样并排编译。顶层`protected interface ITest { }`是反例，现代编译器报告CS1527。

原顶层/嵌套四行表按类型可见性保留：

| 修饰符 | 顶层interface | class里的嵌套interface |
| --- | --- | --- |
| public | 可以；仍受程序集/外围可见性等条件约束 | 可以；外围类型也必须可访问 |
| internal | 可以 | 可以 |
| private | 不可以 | 可以 |
| protected | 不可以 | 可以，按派生访问规则 |

以下为**合法类型片段**，保留原Outer及protected嵌套ITest。

Outer自己的成员也能使用这个嵌套类型，派生类型再按protected规则访问；“protected嵌套”不是只允许派生类、反而禁止Outer本类。

```csharp
class Outer {
    protected interface ITest { void Foo(); }
}
```

原书若笼统提到接口可以protected，可能在讲嵌套类型；不能只凭顶层限制宣布书错。还有protected internal等组合规则，不因原表只列四种就认定表已穷尽所有现代修饰符。

原另一张两层表比较的是“接口类型”与“接口成员”，维度与上一表不同：

| 层级 | 说的是什么 | 能写什么 |
| --- | --- | --- |
| 接口类型 `interface ITest` | 谁能命名、引用这个类型 | 顶层public/internal；嵌套类型还可private/protected等，受外围约束 |
| 接口成员 `void Foo()` | 类型可见范围内的成员契约与实现 | 历史抽象成员不写修饰符、隐式public；C# 8+允许显式public、protected抽象成员及合适的带实现成员 |

internal接口的public隐式实现方法，可能作为某public类的普通API对外可见；这不使internal接口类型本身跨程序集可命名。private EIMI也不意味着所有外部代码都能调用：代码首先必须能访问相应接口类型和成员。必须分别看类型、成员、实现这三个层次。

<a id="c13-remapping"></a>
## new、override与重新实现接口

原六次调用的核心条件是Derived既隐藏Base.Dispose，又**重新列出IDisposable**。new只表达隐藏继承成员；重新列接口才触发重新实现时的接口映射。省掉new通常产生隐藏成员警告，仍可能编译并执行，不能把new描述成编译必需。

<a id="c13-six-calls"></a>
### 原Base/Derived六调用完整程序

以下修复原用户代码中重复/嵌套Main的结构，保留原类型关系、六个调用和输出。每一个调用都是非virtual源码入口或接口入口各自规则的结果。

```csharp
using System;
internal class Base : IDisposable {
    public void Dispose() { Console.WriteLine("Base's Dispose"); }
}
internal class Derived : Base, IDisposable {
    public new void Dispose() {
        Console.WriteLine("Derived's Dispose");
        // base.Dispose(); // 下一场景启用，先保留原注释条件
    }
}
class Program {
    static void Main() {
        Base b = new Base();
        b.Dispose();
        ((IDisposable)b).Dispose();
        Derived d = new Derived();
        d.Dispose();
        ((IDisposable)d).Dispose();
        Base other = new Derived();
        other.Dispose();
        ((IDisposable)other).Dispose();
    }
}
```

输出顺序为：

```text
Base's Dispose
Base's Dispose
Derived's Dispose
Derived's Dispose
Base's Dispose
Derived's Dispose
```

第三组`Base other = new Derived()`保留同一对象、两种入口的原疑问。other.Dispose按Base的非virtual方法入口调用；接口视图使用Derived重新实现后的映射。基类变量不会把实际对象变成Base实例。

<a id="c13-base-call"></a>
### 如何从Derived调用Base.Dispose

把上例Derived.Dispose里的注释启用，方法体为下面的**替换片段**：

```csharp
public new void Dispose() {
    Console.WriteLine("Derived's Dispose");
    base.Dispose();
}
```

一次调用这个Derived入口输出`Derived's Dispose`再`Base's Dispose`；若运行上例全部六调用，第3、4、6次各多一次Base输出。base指定当前实现体可访问的基类方法入口，不是先转成Base对象或重新装箱；也不能推成实际机器码地址永远固定。

<a id="c13-hide-only"></a>
### 仅new隐藏与接口重映射的对照

以下**完整程序**保留隐藏、重列接口和EIMI三种不同条件。Hidden没有重列IDisposable，所以接口入口仍用继承的Base实现；Explicit的普通类入口也仍是Base入口，但它另给接口提供显式实现。

```csharp
using System;
class Base : IDisposable {
    public void Dispose() { Console.WriteLine("Base"); }
}
class Hidden : Base {
    public new void Dispose() { Console.WriteLine("Hidden"); }
}
class Remapped : Base, IDisposable {
    public new void Dispose() { Console.WriteLine("Remapped"); }
}
class Explicit : Base, IDisposable {
    void IDisposable.Dispose() { Console.WriteLine("Explicit"); }
}
class Program {
    static void Main() {
        Hidden h = new Hidden(); h.Dispose(); ((IDisposable)h).Dispose();
        Remapped r = new Remapped(); r.Dispose(); ((IDisposable)r).Dispose();
        Explicit e = new Explicit(); e.Dispose(); ((IDisposable)e).Dispose();
    }
}
```

输出`Hidden/Base/Remapped/Remapped/Base/Explicit`，各占一行。原“绝不要new，只EIMI才正确”的建议过强；EIMI同样可能有类入口与接口入口行为不同，选择须符合类型契约。[接口重新实现规范](https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/language-specification/interfaces)

不同入口产生不同输出本身不足以断言必然违反里氏替换原则；要看基类和接口承诺的行为是否保持。virtual桥和EIMI也不是唯一两种可选设计，不能把聊天的建议改写成书或语言规定。

<a id="c13-override-alternative"></a>
### 原virtual/override替代设计

下面**完整类型片段**保留原Base virtual、Derived override与base.Dispose。若想让类与接口入口共享正常虚派发，这是一种合适结构；它不是对所有资源类型都保证“安全”的自动开关。

```csharp
using System;
class Base : IDisposable {
    public virtual void Dispose() { }
}
class Derived : Base {
    public override void Dispose() { base.Dispose(); }
}
```

Derived无需重新列接口来获得继承的接口实现与虚方法覆盖行为。原另一替代场景`class Derived : Base, IDisposable { void IDisposable.Dispose() { } }`属于重新实现而非C# override；上节Explicit完整程序已经保留该结构与两路输出。源码未写virtual的隐式接口实现，也可能被编译为CLI virtual final，不能因此当成C#可重写入口。

<a id="c13-boxing"></a>
## 值类型实现接口：字段副本、调用入口与装箱

struct实现IDisposable完全合法。调用接口不要求该类型从某个用户类派生；struct不能再作为普通类继承的基类，也不因此失去实现接口的能力。原把装箱原因归为“CLR认不出值类型”不正确：未装箱值仍有确定类型，运行时和JIT可以根据签名、元数据、泛型上下文等处理它。

<a id="c13-myval-original"></a>
### Count=10的原MyVal程序

以下为**完整程序**，把原插值字符串改为C# 5可用的格式化输出，保留public Dispose、Count=10和两次调用。

```csharp
using System;
struct MyVal : IDisposable {
    public int Count;
    public void Dispose() { Console.WriteLine("MyVal's Dispose, Count={0}", Count); }
}
class Program {
    static void Main() {
        MyVal v = new MyVal { Count = 10 };
        v.Dispose();
        IDisposable d = v;
        d.Dispose();
    }
}
```

两次都输出`MyVal's Dispose, Count=10`。前一次直接以MyVal实例为接收者；`IDisposable d = v`在语言/IL层面执行值到接口的装箱转换，箱里保存字段副本。后一次调用使用箱里的值。这个程序的Dispose没有修改Count，不应拿另一修改程序的结果冒充它的输出。

原三行布局表保留对象头/字段比较，其“类型对象指针”改为CoreCLR常用的运行时方法表指针概念：

| 布局内容 | 引用类型对象/装箱对象 | 未装箱的值实例 |
| --- | --- | --- |
| 对象头/同步相关信息 | 对象布局有相应机制，具体运行时表示有差异 | 不为每个内嵌值单独增加对象头 |
| 运行时类型/方法表指针 | 对象表示中有关联，不是指向managed System.Type的简单等价物 | 值数据自身通常没有同样对象头指针，类型仍已知 |
| 实例字段 | 有；装箱值含被复制的字段 | 有；可在局部、字段、数组元素或寄存器中 |

<a id="c13-box-copy"></a>
### 原值变20，箱里的Count仍为10

以下保留原显式MyVal、转换后修改原值以及`((MyVal)d).Count`读副本的不同场景，为**完整程序**。显式实现不能用v.Dispose点名，但可以通过接口，或经泛型约束调用。

```csharp
using System;
struct MyVal : IDisposable {
    public int Count;
    void IDisposable.Dispose() { Console.WriteLine("MyVal's Dispose, Count={0}", Count); }
}
class Program {
    static void Main() {
        MyVal v = new MyVal { Count = 10 };
        IDisposable d = v;
        v.Count = 20;
        d.Dispose();
        Console.WriteLine(v.Count);
        Console.WriteLine(((MyVal)d).Count);
        // v.Dispose(); // 反例：EIMI不参与普通类/struct成员查找
    }
}
```

输出`MyVal's Dispose, Count=10`、`20`、`10`。拆箱到MyVal表达式得到值，通常不是允许随意修改箱字段的源码变量。装箱复制结构体字段，若字段本身是引用，复制的引用仍可指向同一对象，不能把“副本”说成任意嵌套数据的深拷贝。

两个不同struct实现同一IDisposable时，接口视图按各自类型的映射调用相应实现，并不会把两个结构体的Dispose统一成同一方法体。引用类型转接口则通常改变使用视图、保存同一对象引用；不像上述值到接口转换那样为字段建立箱副本。

原思考用“接口引用直接指局部值，栈帧结束后悬空”解释装箱。普通接口变量确实不是保存任意局部值地址的托管byref；值到接口按既定转换建立对象表示。但这只是普通转换的说明，不能推成CLR不能安全处理任何指向局部值的托管引用，也不能把所有值都假定在栈上。后面的ref T约束路径正体现了不同表示与生命周期规则。

<a id="c13-box-mutation"></a>
### 修改方法如何暴露“修改原值还是箱”

以下是**额外完整程序**，用于验证原疑问的边界，原Count=10只打印程序仍单独保留。显式实现给Count加一；普通接口参数会拿箱，而`ref T`约束路径可以直接作用于原结构体。

```csharp
using System;
struct MyVal : IDisposable {
    public int Count;
    void IDisposable.Dispose() { Count++; Console.WriteLine(Count); }
}
class Program {
    static void DisposeValue<T>(ref T value) where T : IDisposable { value.Dispose(); }
    static void Main() {
        MyVal original = new MyVal { Count = 10 };
        IDisposable boxed = original;
        original.Count = 20;
        boxed.Dispose();
        Console.WriteLine("original={0}, box={1}", original.Count, ((MyVal)boxed).Count);
        MyVal direct = new MyVal { Count = 10 };
        DisposeValue(ref direct);
        Console.WriteLine("after-constrained={0}", direct.Count);
    }
}
```

输出`11`、`original=20, box=11`、`11`、`after-constrained=11`。这里“EIMI只能通过装箱对象调用”的原定律已经被ref T约束路径反证。泛型方法若按值收T，仍可能只修改传入副本；ref T是本例保留原变量更新的条件。

<a id="c13-box-diagrams"></a>
### 原四步图：值、箱、接口引用、接口分派

下面保留原另一程序的`Dispose: 10`结果与全部四步图意。它的输出与前节`MyVal's Dispose, Count=10`不同，单独列出，不用代表性程序替代。

```csharp
using System;
struct MyVal : IDisposable {
    public int Count;
    public void Dispose() { Console.WriteLine("Dispose: {0}", Count); }
}
class Program {
    static void Main() {
        MyVal v = new MyVal { Count = 10 };
        IDisposable d = v;
        d.Dispose();
    }
}
```

输出`Dispose: 10`。以下为**概念图**，假定这个局部值和引用当前以栈位置示意；JIT实际可用寄存器等，不保证物理布局相同。

```text
1. 创建值：                         2. box复制字段：
局部v: MyVal                       托管堆中的MyVal箱
┌─────────────┐                    ┌────────────────────┐
│ Count = 10  │                    │ 对象头/同步相关信息 │
└─────────────┘                    │ 运行时方法表关联 ───────> MyVal运行时类型结构
                                   │ Count = 10（副本） │       │ 接口实现映射
                                   └────────────────────┘       └> Dispose实现入口

3. 保存接口引用：                  4. 调用接口契约：
局部v: Count=10                    d.Dispose()
局部d: IDisposable ───────────> 箱     └> 映射IDisposable.Dispose
                                        └> MyVal.Dispose（箱内字段Count=10）
```

原把“MyVal Type Object、Method Table和方法代码”全部画成托管堆中的同一对象，属于教学混层。这里将箱的对象表示、运行时类型结构、映射及代码入口分开；managed `System.Type`反射对象不是这张方法表本体。

这里Dispose()仍无参数，Count=10不是偷偷添加的实参；方法通过指向箱内MyVal数据的相应this读取Count字段。接口接收者的表示与方法原声明的参数列表应分开。

原五行需求表按“值是否可直接被接口引用”与“CLR是否识别类型”分别修正：

| 需求/性质 | 未装箱值实例 | 装箱对象 |
| --- | --- | --- |
| 有实例字段 | 有 | 有被复制字段 |
| 有对象头/同步相关信息 | 值数据没有独立对象头 | 有相应对象表示 |
| 有每对象的类型/方法表关联 | 不需要相同对象头形式 | 对象有运行时类型关联 |
| 普通接口变量能直接保存该值 | 需要值到接口转换，语言层面装箱 | 能保存箱对象引用 |
| CLR能识别类型 | 能，不能因没对象头说“不知道” | 能 |

引用类型对照仍保留原`Base b = new Derived(); IDisposable d = b; d.Dispose();`场景，但须假定Derived具有相应映射（如前面的重新实现示例）：

```text
b ─┐
   ├> 同一个Derived对象（没有值复制箱）
d ─┘       └> Derived运行时类型关联
                 └> IDisposable契约映射 ─> 所选Dispose实现
```

若Derived只是隐藏而未重新实现接口，所选实现可以仍是Base；不能脱离类型定义直接把末端画成Derived.Dispose。引用转换不等于每次重新分配对象。

<a id="c13-code-storage"></a>
### 方法代码在哪里，调用时需要什么

“方法代码也跟着值在栈里吗？”答案是实例字段与方法代码分开。原四行存储表的Code Heap/Method Table混写、值只在栈等说法按运行时概念修正：

| 内容 | 存储/表示范围 |
| --- | --- |
| 方法IL与JIT机器码 | IL来自程序集等元数据/映像；JIT代码在执行代码区域，方法表可关联入口，不等于代码本体 |
| 类型信息 | CLR有原生运行时类型结构；System.Type是反射对象，不能两者统称只在托管堆 |
| 实例字段 | 可在引用对象、箱、数组内嵌值、局部/寄存器等位置 |
| 局部变量、参数、返回地址 | 按ABI/JIT有栈与寄存器等表示，不把所有局部/参数一律放栈 |

直接`MyVal v = new MyVal(); v.Dispose();`时，源码编译器可确定方法标识和调用形态，并不在C#编译时知道进程中最终JIT机器码的绝对地址。原示意`call MyVal_Dispose`只表示可直接调用一个已确定实现；真实代码还可能内联、通过入口桩或受运行时优化影响。

原`MyVal.Dispose(ref v)`是解释值类型实例方法接收者的**概念伪代码**，不是把实例方法当静态方法的合法C#写法。实例方法需要访问接收者字段；值类型this通常通过相应托管引用传递语义处理，不会因为值实例没有对象头就找不到方法。

直接调用public MyVal.Dispose的形式不等于它没有实现IDisposable.Dispose；成员可以既是普通API又满足接口映射。接口变量的静态契约较宽，也不妨碍编译器/JIT根据对象流证明具体实现并去虚化，不能说接口入口绝不可能知道目标、每次必须查表。

原四行调用表保留比较维度，同时区分源码绑定、运行时派发和普通转换装箱：

| 调用方式 | 绑定/分派 | 类型信息作用 | 装箱边界 |
| --- | --- | --- | --- |
| `v.Dispose()` | 成员选择由编译规则确定；实现可能直接调用/内联 | JIT知道MyVal类型，不需先建箱才能认识它 | 本例public struct方法无需接收者装箱 |
| `base.Dispose()` | 指定可访问基类实现入口 | 仍有接收者，不是没有类型信息 | 引用类型基类调用不因此装箱 |
| `((IDisposable)v).Dispose()` | 普通值到接口转换后使用接口映射 | 接口引用具有对象表示；优化可能去虚化 | 语言/IL层面有接收者装箱；实际分配可优化 |
| virtual/override调用 | 语义按虚派发；优化可去虚化/内联 | 运行时或已证明的具体类型参与选择 | 引用类型接收者无值装箱；别据表泛化所有泛型调用 |

厨房类比保留原三个对象：墙上菜谱像共享方法代码，盘中食材像实例字段，贴标签的盒子像箱对象。拿盘子可以按已知菜谱做菜，不要求每份食材各复制一本菜谱；盒子标签帮助普通接口引用识别对象。类比不意味着CLR原生方法表、managed Type和机器码实际都挂在一面“堆墙”上。

原两个整数格式化入口为**方法体片段**：

```csharp
string a = ((IFormattable)1).ToString(null, null);
string b = (1).ToString();
Console.WriteLine(a);
Console.WriteLine(b);
```

补`using System;`和Main后两行输出都为`1`。接口转换的原语义可能含值装箱，直接Int32方法没有同样转换；实际JIT可消除一些箱，不能用“所有接口必查表、慢很多、能不用就不用”替代具体性能证据。[CoreCLR类型系统说明](https://github.com/dotnet/runtime/blob/main/docs/design/coreclr/botr/type-system.md)

<a id="c13-implicit"></a>
## 编译器怎样匹配隐式接口实现

原“为简化编程，编译器假定某public方法实现接口”应理解为明确的接口映射规则，不是猜开发者意图。类型声明中的接口契约、可用成员及继承结构决定映射。适合的public实例成员可以来自当前类型或继承关系，不要求每个实现类都重新引入一个方法。

<a id="c13-signature"></a>
### 方法签名与接口匹配不是同一个术语

C#方法签名包含名称、类型参数数量、参数类型及相应传递方式等信息，**不把返回类型作为普通方法重载签名的一部分**。但是实现接口时仍必须满足相应成员的返回类型及其他匹配要求；所以`public int Dispose()`不能实现`void IDisposable.Dispose()`。不能因为它不是“签名”的组成就随意改变返回类型。

原思考又把C# 9协变返回与接口实现混写：类方法覆盖等特定协变返回规则，不自动放宽普通隐式接口成员匹配。当前无参void Dispose案例没有返回协变问题，不能凭现代版本就接受int Dispose。

ref/out与按值参数有各自规则：按值和按引用可构成不同形态，仅ref和out的差别不能作为普通C#方法重载的唯一区别。也不能省略接口契约的参数或用可选参数自动凑成另一个成员匹配。

原猜测的**struct SimpleType完整程序**保留独立类型与`SimpleType Dispose`输出，不当成原书sealed class的原字面。

```csharp
using System;
struct SimpleType : IDisposable {
    public void Dispose() { Console.WriteLine("SimpleType Dispose"); }
}
class Program {
    static void Main() {
        SimpleType value = new SimpleType();
        value.Dispose();
    }
}
```

下面合列原三种**独立编译反例**。它们分别缺public、参数不符、返回类型不符；不是三个重载在同一类型里彼此竞争。

```csharp
using System;
struct MissingPublic : IDisposable { void Dispose() { } } // CS0737
struct WrongParameter : IDisposable { public void Dispose(int x) { } } // CS0535
struct WrongReturn : IDisposable { public int Dispose() { return 0; } } // CS0738
```

原没有public的EIMI则合法，作为**完整类型片段**：

```csharp
using System;
struct SimpleType : IDisposable {
    void IDisposable.Dispose() { }
}
```

下面保留原自检问题“已有void Dispose，再加Dispose(object)会怎样”，为**正确类型片段**：

```csharp
using System;
struct SimpleType : IDisposable {
    public void Dispose() { }
    public void Dispose(object o) { }
}
```

无参void方法提供IDisposable.Dispose实现；额外重载本身不破坏映射。不能把“这个额外重载不匹配接口”误答成“整个类型没有实现接口”。只写Dispose(int)或只写int Dispose才是上述不同失败场景。

餐厅类比保留原“菜单要求鱼香肉丝”“额外微辣参数”“后厨私有菜谱”三点：接口是精确定义的调用契约，消费者不能因为名字相似就知道是否需要加参数；private普通方法不能按C#隐式规则匹配，但显式接口转发能另外提供契约。方法返回要求也需匹配，类比不替代语言中的签名定义。

原用Java `@Override`表示“必须显式声明实现”的对照也须纠正：Java实现接口方法不以该注解为必需，注解会要求编译器检查相应覆盖关系。C#的EIMI是另一种语言结构，不能由注解存在推出Java全部接口实现都强制写它。[Java @Override规范](https://docs.oracle.com/javase/specs/jls/se25/html/jls-9.html#jls-9.6.4.4)

Java的implements列出接口类型，不是用`implements IDisposable.Dispose`声明一个方法；聊天所写的假想冗余匹配语法只是说明目的，不能充作Java真实语法。[Java类的接口声明规则](https://docs.oracle.com/javase/specs/jls/se25/html/jls-8.html#jls-8.1.5)

<a id="c13-method-ownership"></a>
### EIMI不是override，new也不是接口实现标记

原两行三列表保留方法归属与调用视图，其“public只能通过SimpleType变量调用”改为普通成员可访问的类视图，而非排除所有基类/其他接口/泛型入口：

| 方法 | 归属 | 调用方式/限制 |
| --- | --- | --- |
| public void Dispose() | SimpleType的public实例成员 | 可通过相应可访问类视图调用；是否又实现别的契约看实际映射 |
| void IDisposable.Dispose() | SimpleType中的显式接口实现方法 | 用相应接口契约或受约束调用；不按st.Dispose普通成员查找调用它 |

EIMI不是覆盖Object.Dispose，因为Object没有该方法；原无Base的SimpleType也不需要new。CLI典型virtual/final标记是运行时实现形态，不将其变成C# override语法。

C# override可覆盖合适的继承virtual、abstract或override成员，目标还不能被sealed封住；不是要求基类那一行字面必须写virtual。接口实现语法与类方法覆盖规则仍须分开。[override规则](https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/keywords/override)

下面保留原有Base.Dispose的**完整程序**。T独有短文本Base/SimpleType/Interface场景与正式答Base Dispose/SimpleType Dispose/Interface Dispose具有相同路由但不同文本，这里用参数保留两组实际输出，而不是删掉前一组。

```csharp
using System;
class Base {
    private readonly bool shortText;
    public Base(bool shortText) { this.shortText = shortText; }
    public void Dispose() { Console.WriteLine(shortText ? "Base" : "Base Dispose"); }
}
internal sealed class SimpleType : Base, IDisposable {
    private readonly bool shortText;
    public SimpleType(bool shortText) : base(shortText) { this.shortText = shortText; }
    public new void Dispose() { Console.WriteLine(shortText ? "SimpleType" : "SimpleType Dispose"); }
    void IDisposable.Dispose() { Console.WriteLine(shortText ? "Interface" : "Interface Dispose"); }
}
class Program {
    static void Main() {
        foreach (bool shortText in new[] { true, false }) {
            SimpleType st = new SimpleType(shortText);
            st.Dispose();
            ((Base)st).Dispose();
            ((IDisposable)st).Dispose();
        }
    }
}
```

输出`SimpleType/Base/Interface/SimpleType Dispose/Base Dispose/Interface Dispose`，各一行。原new写在这里表达隐藏Base入口，去掉new会产生警告而通常仍编译；接口路线仍映显式实现。不能用“必须new”来解释接口是否满足。

<a id="c13-comparable"></a>
## 强类型入口与非泛型接口适配

IComparable历史入口接收object；IComparable<T>接收T，在.NET 2.0已有泛型接口，in变型标记是后来的.NET 4/C# 4背景。原用object?/T?与表达式体是现代显示语法，不能当成.NET 1.0的原源码。传统声明形状是`int CompareTo(object other)`与`int CompareTo(T other)`。

<a id="c13-object-comparison"></a>
### 原MyInt32把object当int的失败场景

以下为**完整程序**，保留class MyInt32、值10、参数20以及"hello"反例。这里设计的是与int比较的包装类，并不是可直接用于MyInt32数组排序的“比较两个包装对象”协议。

```csharp
using System;
class MyInt32 : IComparable {
    private readonly int _value;
    public MyInt32(int value) { _value = value; }
    public int CompareTo(object other) { return _value.CompareTo((int)other); }
}
class Program {
    static void Main() {
        MyInt32 a = new MyInt32(10);
        Console.WriteLine(a.CompareTo(20));
        IComparable c = a;
        try { c.CompareTo("hello"); }
        catch (InvalidCastException) { Console.WriteLine("InvalidCastException"); }
    }
}
```

输出`-1`和`InvalidCastException`。object参数允许字符串通过编译，方法内强制拆箱int时失败。20是值类型参数，进入object入口需要装箱；MyInt32本身是class，其接收者到接口是引用转换。"hello"本来是引用类型，不因送进object参数而装箱。

这里失去的是“参数静态类型只允许int”的那一层约束，整个程序的编译期类型检查并没有完全失效；编译器仍检查参数转换、成员可访问性及方法体等其他规则。

<a id="c13-strong-adapter"></a>
### 强类型public方法加显式旧接口适配

以下为**完整程序**，保留原强类型CompareTo(int)、显式object适配、错误参数检查与ArgumentException。把现代`is not int`改为C# 5可用条件，改变语法不改变原教学条件。

```csharp
using System;
class MyInt32 : IComparable, IComparable<int> {
    private readonly int _value;
    public MyInt32(int value) { _value = value; }
    public int CompareTo(int other) { return _value.CompareTo(other); }
    int IComparable.CompareTo(object other) {
        if (!(other is int)) throw new ArgumentException("必须是 int");
        return CompareTo((int)other);
    }
}
class Program {
    static void Main() {
        MyInt32 a = new MyInt32(10);
        Console.WriteLine(a.CompareTo(20));
        Console.WriteLine(((IComparable)a).CompareTo(20));
        try { ((IComparable)a).CompareTo("x"); }
        catch (ArgumentException) { Console.WriteLine("ArgumentException"); }
        // a.CompareTo("hello"); // 强类型入口反例：无法把string传给int参数
    }
}
```

输出`-1/-1/ArgumentException`。增加IComparable<int>明确实现后面泛型约束需要的协议；只写一个同名public方法不自动声明实现所有同形接口。

CompareTo(int)是强类型的普通方法，本身没有自己的方法类型参数；IComparable<T>才是泛型接口。不能把“避免object参数”与“方法必须是泛型方法”画等号。

原三行表按接收者、参数和检查位置修正，保留三个调用场景：

| 调用方式 | 发生什么 | 类型安全边界 | 装箱 |
| --- | --- | --- | --- |
| a.CompareTo(20) | 调用public CompareTo(int) | 参数编译时要求int | class接收者与int参数无此object转换装箱 |
| ((IComparable)a).CompareTo(20) | EIMI检查后转发 | object入口较宽，方法内验证int | int参数20装箱；class接收者不装箱 |
| ((IComparable)a).CompareTo("x") | EIMI抛ArgumentException | 错误调用仍能编译，不是编译时类型安全 | string参数不装箱，原表这里的装箱勾号错误 |

<a id="c13-real-int32"></a>
### 真正Int32的object版本是public

原把FCL Int32示意成只有EIMI的`IComparable.CompareTo(object)`不准确。.NET Framework参考源码和现代.NET固定版本源码均有public CompareTo(object)，并有public CompareTo(int)。因此`x.CompareTo("hello")`对真正int可能选object重载并在运行时抛ArgumentException，不能套用上面仅暴露强类型方法的自定义MyInt32结论。[Int32.CompareTo契约](https://learn.microsoft.com/en-us/dotnet/api/system.int32.compareto?view=net-10.0)、[现代.NET 10 Int32源码](https://github.com/dotnet/runtime/blob/v10.0.0/src/libraries/System.Private.CoreLib/src/System/Int32.cs)

以下为**完整程序**，保留原int10比较20及接口路径，显式显示参数不合法时的契约。

```csharp
using System;
class Program {
    static void Main() {
        int x = 10;
        Console.WriteLine(x.CompareTo(20));
        IComparable c = 10;
        Console.WriteLine(c.CompareTo(20));
        try { x.CompareTo("hello"); }
        catch (ArgumentException) { Console.WriteLine("ArgumentException"); }
    }
}
```

输出`-1/-1/ArgumentException`。`IComparable c = 10`有接收者装箱，`c.CompareTo(20)`又有参数20到object的装箱，所以原“只装箱一次”必须拆位置。箱创建后，多次接口调用不是每次重新对接收者装箱；object参数每次是否转换另看传入表达式。实际分配仍受JIT优化影响。

<a id="c13-old-new-algorithms"></a>
### 原Array.Sort与List<int>.Sort的兼容路径

旧Array.Sort(Array,Array)的签名参数是Array，不是IComparable；默认比较过程才会使用相应比较协议。旧ArrayList也能依赖非泛型契约。兼容入口的存在服务既有调用，不等于所有API永远禁止变更，或所有旧接口都必须EIMI实现。

原MyInt32[]中3和1的场景要求比较**另一个MyInt32对象**，不能沿用上节只接受boxed int的适配方法。以下为**完整程序**，同时实现两种比较协议并打印正/旧路径；强制`(Array)`保留旧API场景，避免现代重载选择悄悄改为泛型路径。

```csharp
using System;
using System.Collections.Generic;
class MyInt32 : IComparable, IComparable<MyInt32> {
    public int Value { get; set; }
    public int CompareTo(MyInt32 other) {
        Console.WriteLine("Strong-typed path");
        return other == null ? 1 : Value.CompareTo(other.Value);
    }
    int IComparable.CompareTo(object other) {
        Console.WriteLine("Legacy path (EIMI)");
        if (other == null) return 1;
        MyInt32 value = other as MyInt32;
        if (value == null) throw new ArgumentException("必须是 MyInt32");
        return Value.CompareTo(value.Value);
    }
}
class Program {
    static void Main() {
        MyInt32[] numbers = { new MyInt32 { Value = 3 }, new MyInt32 { Value = 1 } };
        Array.Sort((Array)numbers);
        Console.WriteLine("legacy first={0}", numbers[0].Value);
        MyInt32[] other = { new MyInt32 { Value = 3 }, new MyInt32 { Value = 1 } };
        Array.Sort(other);
        Console.WriteLine("generic first={0}", other[0].Value);
        List<int> ints = new List<int> { 3, 1 };
        ints.Sort();
        Console.WriteLine("list first={0}", ints[0]);
        int x = 10;
        Console.WriteLine(x.CompareTo(5));
    }
}
```

两数组和List的首项都为1，最后CompareTo结果为1。排序期间旧数组打印Legacy path，泛型数组打印Strong-typed path；实际比较次数由排序实现决定，不写成固定只调用一次。class MyInt32对象作为object参数是引用转换，本例不能宣称“因为旧接口，每个比较参数必装箱一次”。

原三行算法路径表保留调用者/代码性质的用途，限定默认比较与重载：

| 调用方 | 代码性质 | 相应路径 | 结果/前提 |
| --- | --- | --- | --- |
| Array.Sort((Array)oldArray) | 强制原非泛型API场景 | 默认比较用IComparable；本例映EIMI | 接收另一个MyInt32，不能接错boxed int协议 |
| List<int>.Sort() | .NET 2.0+泛型集合 | 默认比较器可用IComparable<int> | int元素无需经object比较参数 |
| int x=10; x.CompareTo(5) | 直接强类型调用 | public CompareTo(int) | 返回正值，编译时参数为int |

自定义包装类的另一原场景以int为比较对象，打印`Strong-typed path`与`Legacy path (EIMI)`，可在[c13-strong-adapter](#c13-strong-adapter)的两个CompareTo体开始加入相应WriteLine，并仍由显式入口转发。此时一次旧接口调用先打印Legacy，再打印Strong，最后返回比较值；上面用于数组排序的MyInt32比较另一包装对象，两个协议不能混为同一完整例。

<a id="c13-constrained"></a>
## 接口约束与constrained：接收者、参数分别计算

原问引用非泛型IComparable约束，正式答改讲IComparable<int>；两者在参数装箱上有实质差异，必须保留两条路径。受约束调用避免接收者装箱并不保证所有参数、返回值或枚举器都无装箱。

<a id="c13-nongeneric-constraint"></a>
### 原IComparable约束：接收者可以免箱，int参数仍可能装箱

以下为**完整程序**，保留原M<T>(T t)与M(IComparable t)比较、x=5、参数10。用不同方法名Legacy与LegacyInterface让读者明确选择路径，避免测试时重载推断掩盖意图。

```csharp
using System;
class Program {
    static int Legacy<T>(T t) where T : IComparable { return t.CompareTo(10); }
    static int LegacyInterface(IComparable t) { return t.CompareTo(10); }
    static void Main() {
        int x = 5;
        Console.WriteLine(Legacy(x));
        Console.WriteLine(LegacyInterface(x));
    }
}
```

输出两行-1。Legacy<T>对int接收者可以用constrained调用避免箱；由于CompareTo(object)的参数是object，字面10仍需装箱。LegacyInterface(x)入口把x转成接口时已有接收者装箱，体内10又需装箱。原书“避免装箱”的焦点应按接收者解释，不扩大为所有位置都零装箱。

<a id="c13-generic-constraint"></a>
### 正式答新增IComparable<int>约束

以下为**完整程序**，保留原强类型M<T>(T t)与M(IComparable<int> t)、x=5及比较10场景。同样用不同方法名表达两个实验，而不是让编译器自动选重载后误读结果。

```csharp
using System;
class Program {
    static int M<T>(T t) where T : IComparable<int> { return t.CompareTo(10); }
    static int InterfaceM(IComparable<int> t) { return t.CompareTo(10); }
    static void Main() {
        int x = 5;
        Console.WriteLine(M(x));
        Console.WriteLine(InterfaceM(x));
        Console.WriteLine(x.CompareTo(10));
        Console.WriteLine(((IComparable)x).CompareTo(10));
        IComparable<int> value = x;
        Console.WriteLine(value.CompareTo(10));
    }
}
```

五行均为-1，性能语义不同：M(x)不需要接收者和int参数的object转换；InterfaceM(x)与接口变量value的初始化在语言层面有接收者装箱；显式IComparable转换既有接收者箱，参数10也进object入口。相同返回结果不是相同内存行为的证据。

<a id="c13-constrained-il"></a>
### 泛型IL是constrained. !!T，不是固定Int32

以下为前述泛型M<T>的**IL教学形状**，具体程序集限定名随Framework/现代.NET不同。不把现代JIT对int的特化伪写成原泛型方法的固定签名。

```il
ldarga.s t
ldc.i4.s 10
constrained. !!T
callvirt instance int32 System.IComparable`1<int32>::CompareTo(!0)
ret
```

constrained修饰随后的callvirt，接收者是指向T的托管指针。对引用类型可经指针得到引用后按调用规则分派；对实现了目标方法的值类型可直接调用适当实现；在某些值类型未覆盖Object/ValueType/Enum目标方法的情形，仍可能需要箱。它不是“假装值变成引用类型”，也不保证值永远留在物理栈上。[Constrained操作码的三种情况](https://learn.microsoft.com/en-us/dotnet/api/system.reflection.emit.opcodes.constrained?view=net-10.0)

非泛型接口参数版本在调用点会有`box System.Int32`等形态；constrained用于接收者不消除普通object实参的box。InterfaceM的参数已经是接口引用，进入体内不需要再把该接收者box一次。

<a id="c13-unconstrained"></a>
### 没有接口约束也可能出现constrained

以下为**完整类型片段**，保留额外边界验证的无约束ToString，以及显式struct IDisposable受约束调用。不能把“接口约束给出可调用契约”误说成“constrained只有在接口约束时才存在”。

```csharp
using System;
struct ExplicitDisposable : IDisposable {
    public int Count;
    void IDisposable.Dispose() { Count++; }
}
class Demo {
    public static string Text<T>(T value) { return value.ToString(); }
    public static void DisposeValue<T>(ref T value) where T : IDisposable { value.Dispose(); }
}
```

Text<T>调用Object成员也可发出constrained；当T=Int32且其ToString有合适覆盖时可直接处理，不能因此保证所有T的实际路径都免箱。DisposeValue(ref struct)通过约束契约可调用EIMI并修改原值，前面的Count实测已保留。

本机Framework与.NET 10编译后的IL反查得到：Legacy<T>有1条box（参数10）和1条constrained；泛型M<T>有0条box和1条constrained；无约束ToString也有0条显式box和1条constrained；显式IDisposable的ref T调用同样0条box/1条constrained。四者constrained类型操作数都是**方法泛型参数T**，不是固定Int32。IL中没有box不充分证明任何T在运行时都不分配对象，也不是JIT分配基准。

<a id="c13-constrained-tables"></a>
### 原关键词表和调用决策表

原四行关键词表保留定义用途：

| 关键词 | 解释 |
| --- | --- |
| 接口约束 | where T:IComparable或IComparable<int>提供相应成员契约；两种参数类型不同 |
| 特殊IL指令 | constrained.修饰callvirt，以T的托管指针处理相应接收者 |
| 直接在值类型上调用 | 已知或受约束的适当实现可不先建立接口箱；并非每个目标方法都保证如此 |
| 不装箱 | 不执行所讨论位置的值到对象表示转换；不等于变量物理上永久在栈 |

原五行调用决策表保留，最后EIMI行增加受约束条件而不是删除它：

| 调用方式 | 语言/IL装箱边界 | 原因与限制 |
| --- | --- | --- |
| x.CompareTo(10)，x为int | 强类型入口无需接收者/参数箱 | public CompareTo(int) |
| M<T>(x)，where T:IComparable<int> | 对int无需上述两位置箱 | constrained接收者加int参数契约 |
| M(IComparable<int> t)，调用点传int | 调用点值到接口有接收者箱 | 体内t已有引用，不是每次调用再次box t |
| ((IComparable)x).CompareTo(10) | 接收者箱加object参数10箱 | 两个位置分别计算 |
| EIMI调用 | 普通struct转接口有箱；受约束ref T可免接收者箱 | 显式实现语法本身不决定是否装箱 |

List<int>.Sort可经泛型比较器处理int，不意味着任意“带泛型”API都没有箱。类与接口契约、元素、枚举器、接收者、参数及JIT分配观察应分别讨论；本章用真实编译/IL/输出验证调用路径，没有伪造固定纳秒差或假称跨所有运行时保证同样内存分配。

<a id="c13-myval-thinking"></a>
### 原思考中的两个不带Count版本

原技术思考先用不带Count的MyVal演示调用，再加入字段副本问题。下面保留其不同程序条件、短输出及显式版本的public Foo；两个程序相互独立，不与前面的同名MyVal合编。

第一个为**完整程序**，public Dispose只打印`MyVal's Dispose`，直接调用与转换后调用各打印一次：

```csharp
using System;
struct MyVal : IDisposable {
    public void Dispose() { Console.WriteLine("MyVal's Dispose"); }
}
class Program {
    static void Main() {
        MyVal v = new MyVal();
        v.Dispose();
        IDisposable d = v;
        d.Dispose();
    }
}
```

第二个为**完整程序**，保留public Foo与显式Dispose；Foo是可点名普通API，v.Dispose仍是注释中的反例，接口入口才打印一次`MyVal's Dispose`：

```csharp
using System;
struct MyVal : IDisposable {
    void IDisposable.Dispose() { Console.WriteLine("MyVal's Dispose"); }
    public void Foo() { }
}
class Program {
    static void Main() {
        MyVal v = new MyVal();
        v.Foo();
        // v.Dispose(); // 反例：普通成员查找不找到EIMI
        ((IDisposable)v).Dispose();
    }
}
```

这两例只验证成员视图与普通转换路径，不因为Foo为空或箱没有业务字段，就把装箱模型解释为“CLR不知道未装箱值的类型”。Count=10/20副本、修改箱与受约束修改原值仍分别见前述程序。

<a id="c13-access-negative-detail"></a>
### 原另组成员与sealed protected反例

原类型/成员可见性解释还用Foo、protected Bar、private Baz的不同组合。下面为**独立编译反例**：C# 5拒绝接口成员的修饰符；C# 8+的protected抽象Bar可以声明，但private Baz没有方法体仍不合法。不能把两版本都报错归成“protected抽象永远非法”。

```csharp
public interface ITest {
    void Foo();
    protected void Bar();
    private void Baz(); // 现代也失败：私有成员没有实现
}
```

原protected实现的sealed SimpleType也单独保留为**编译反例**，有别于前面的struct和MyFile：

```csharp
using System;
internal sealed class SimpleType : IDisposable {
    protected void Dispose() { } // 不满足隐式实现；sealed/protected还可能有警告
}
```

前者本机旧csc报告CS0106，现代C# 8报告私有接口成员相关CS0501；后者报告CS0737并有CS0628警告。诊断和条件分开记录，不把sealed当成允许protected隐式实现或新增virtual的豁免。
