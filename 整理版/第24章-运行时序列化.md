## 历史序列化处理对象状态及引用关系

序列化把对象图按指定格式写入流，反序列化按格式及类型合同重建对象。历史 BinaryFormatter 不只是把对象内存逐字节倾倒：它会写类型/程序集身份、成员名称、值及对象引用记录。具体通信协议、端序和类型兼容性仍由格式与调用场景决定，不能因“.NET透明处理”就不考虑双方合同。

原典型用途分别保留：应用状态持久化至文件/数据库、某些历史 ASP.NET Session 提供程序、桌面剪贴板中的可序列化数据、对象图克隆/备份，以及 Remoting/跨 AppDomain 按值传对象。这些是不同场景；并非任何 Session 或剪贴板 API 都无条件使用同一格式化器，也不意味着克隆能自动管理非托管资源。

BinaryFormatter 的完整命名空间是 `System.Runtime.Serialization.Formatters.Binary`，基础类型在 `System.Runtime.Serialization`。历史调用关系是 `formatter.Serialize(stream, objectGraph)` / `formatter.Deserialize(stream)`。普通类/结构体可用 `[Serializable]` 声明相应字段序列化合同；它不是安全权限开关，也不是所有 serializer 的共同要求。属性本身不按属性访问器保存，自动属性可能因其实例后备字段参与。枚举、委托的历史可序列化形态与现代 BF 的不支持状态另分；派生类不能靠基类特性继承而自动获准。

本地摘录24.3脚注（MD243，同版PDF565/印刷548）确实说后备字段名每次重新编译都不同；这不是问答凭空捏造。常见编译器实际不会每次随机改名，这个原书断言过宽，仍应保其避免持久化合同依赖编译器细节的用意。自动属性不是每次编译都随机改后备字段名。常见编译器名称如 `<Name>k__BackingField` 有固定形状，但依赖编译器生成字段作为长期存储协议仍有耦合风险；应显式规划持久化合同。第10/18章关于字段目标特性及伪特性的版本结论继续适用，不将“避免耦合”的建议改成语言禁止自动属性。

### 普通字段路径与特殊构造路径

原四个自动写入步骤：`GetSerializableMembers(type, context)` 取得适用的 public/private 实例字段（排除 NonSerialized），`GetObjectData(obj,members)` 得到平行值数组，格式化器写身份，再按格式写成员名称/值及图记录。原六个读回步骤：读身份/必要时解析程序集，取得 Type，建立未初始化对象，取得成员描述，准备值，再 `PopulateObjectMembers` 并完成引用修复/回调。它是机制概述，不承诺每种格式、每个对象逐字遵循完全相同内部调用链。

`GetUninitializedObject` 的关键是普通实例字段从零/null状态开始，未运行普通实例构造函数及字段初始化；不能说对象头、类型数据乃至整个图所有字节都是0。实现 `ISerializable` 时还会使用特殊 `(SerializationInfo, StreamingContext)` 构造函数；所以“反序列化完全不跑任何构造函数”也过宽。特殊 ctor 或单个对象的回调不代表所有关联对象已完成自己的修复。

补充实证 State 有 Number7、private secret="keep"、NonSerialized Skip="temp"：成员清单只有 Number/secret；未初始化对象 Number0/secret null、普通 ctor次数仍1；填回后7/keep，Skip仍null。它说明普通字段路径，没有据此保证所有 CLR 类型都可用这个入口。

原本还讨论了流上下文、ISerializable、自定义版本、SetType、IObjectReference、SurrogateSelector 和 Binder；下面分别保留其不同用途，而不把导读扩写成未讨论的整章教材。

## 反序列化为什么会重新遇到程序集绑定

用户追问的是：已用 LoadFrom 加载插件，为什么读回对象仍可能找不到它。流里通常保存身份和状态，不保存原插件文件的任意本机路径。下面是原 Player 类，实际在全局命名空间：

<a id="c24-player-class"></a>
<!-- C24-D01-Q002-A-B004 -->
```csharp
[Serializable]
public class Player {
    public string Name;
    public int Level;
}
```

原身份示意也保留，但要认识两个缺口：MyGame.Player 与上面的全局 Player 不匹配；Version1/tokenxxxx 是示意占位，不能当成编译产物实测值：

<a id="c24-player-identity"></a>
<!-- C24-D01-Q002-A-B006 -->
```text
程序集: MyGame, Version=1.0.0.0, Culture=neutral, PublicKeyToken=xxxx
类型:   MyGame.Player
```

程序集名称并不自动给类型加命名空间。保留全局声明时应查 `GetType("Player")`；若要用 MyGame.Player，就显式定义 `namespace MyGame`。下面仍是原 Main/plugins 目录场景：

<a id="c24-player-directories"></a>
<!-- C24-D01-Q002-A-B009 -->
```text
Main.exe
plugins\
    └── MyGame.dll
```

原创建和写入片段修准确类型名；`File.Create` 产生真实文件，文件名没有类型身份的魔法：

<a id="c24-player-write"></a>
<!-- C24-D01-Q002-A-B011 -->
```csharp
// 加载插件
Assembly pluginAsm = Assembly.LoadFrom(@"plugins\MyGame.dll");
Type playerType = pluginAsm.GetType("Player");

// 创建一个 Player 并序列化
object player = Activator.CreateInstance(playerType);
BinaryFormatter formatter = new BinaryFormatter();
using (var fs = File.Create("player.bin"))
{
    formatter.Serialize(fs, player);  // 写实际程序集身份；原Version/token示意不等本次真实产物
}
```

名称查找失败会经过格式化器的绑定逻辑，外层可表现为 SerializationException；但 LoadFrom 并不承诺在任何条件下必失败。原读取片段应按名称能否解析理解：

<a id="c24-player-read"></a>
<!-- C24-D01-Q002-A-B013 -->
```csharp
using (var fs = File.OpenRead("player.bin"))
{
    object obj = formatter.Deserialize(fs);  // 若流中身份按当前策略无法解析，可抛SerializationException；不是无条件失败
}
```

原按名称加载的身份示意保留为文本，xxxx 不是合法的实际公钥标记：

<a id="c24-player-display-name"></a>
<!-- C24-D01-Q002-A-B017 -->
```text
Assembly.Load("MyGame, Version=1.0.0.0, Culture=neutral, PublicKeyToken=xxxx")
```

Framework 的默认 probing 不是自动扫描任意子目录；基目录/私有路径、缓存与身份策略都会影响结果。原书用Assembly.Load概括按名称绑定，不能据FormatterServices.LoadAssemblyFromString内部调用就断言默认BF总逐字走这一API。对应ReferenceSource的BinaryFormatter默认AssemblyFormat.Simple；ObjectReader先考虑Binder与缓存，Full的FastBindToType分支调用Assembly.Load，带FEATURE_FUSION的Simple分支经ResolveSimpleAssemblyName调用RuntimeAssembly.LoadWithPartialNameInternal，并有类型解析及fallback。这里区分名称绑定主旨与指定实现分支，不声称旧实证做了内部API tracing。已有LoadFrom仍可能不满足本次绑定条件。[BinaryFormatter默认值](https://raw.githubusercontent.com/microsoft/referencesource/main/mscorlib/system/runtime/serialization/formatters/binary/binaryformatter.cs)，[ObjectReader绑定分支](https://raw.githubusercontent.com/microsoft/referencesource/main/mscorlib/system/runtime/serialization/formatters/binary/binaryobjectreader.cs)

<a id="c24-resolve"></a>
### 给失败绑定提供明确解析

原完整事件方案包含缓存返回和按 plugins 路径加载两条分支。保留方法、输入和日志，增加名称/身份范围校验；示意处理器不是安全沙箱：

<a id="c24-resolve-full"></a>
<!-- C24-D01-Q002-A-B023 -->
```csharp
using System;
using System.IO;
using System.Reflection;
using System.Runtime.Serialization.Formatters.Binary;

class Program
{
    // 缓存我们手动加载的程序集
    static Assembly _loadedPlugin;

    static void Main()
    {
        // 1. 订阅 AssemblyResolve 事件（必须在反序列化之前）
        AppDomain.CurrentDomain.AssemblyResolve += OnAssemblyResolve;

        // 2. 用 LoadFrom 加载插件
        _loadedPlugin = Assembly.LoadFrom(@"plugins\MyGame.dll");

        // 3. 反序列化
        BinaryFormatter formatter = new BinaryFormatter();
        using (var fs = File.OpenRead("player.bin"))
        {
            object obj = formatter.Deserialize(fs);  // ✅ 现在能正常工作了
            Console.WriteLine($"反序列化成功: {obj.GetType().FullName}");
        }
    }

    // AssemblyResolve 事件处理程序
    static Assembly OnAssemblyResolve(object sender, ResolveEventArgs args)
    {
        // args.Name是本次失败绑定请求的程序集显示名；默认BF具体Simple/Full路径见上文
        // 例如: "MyGame, Version=1.0.0.0, Culture=neutral, PublicKeyToken=xxxx"
        
        Console.WriteLine($"CLR 找不到程序集: {args.Name}，尝试手动解析...");

        // 方案A：如果我们有缓存的程序集，且名称匹配，直接返回
        if (_loadedPlugin != null && 
            new AssemblyName(args.Name).FullName == _loadedPlugin.FullName)
        {
            Console.WriteLine($"  ✅ 返回已加载的程序集: {_loadedPlugin.Location}");
            return _loadedPlugin;
        }

        // 方案B：根据名字去 plugins 目录找
        AssemblyName requested = new AssemblyName(args.Name);
        string asmName = requested.Name;
        if (asmName != "MyGame") return null; // 只处理本示例已知插件
        string pluginPath = Path.Combine(AppDomain.CurrentDomain.BaseDirectory, 
                                         "plugins", asmName + ".dll");
        if (File.Exists(pluginPath))
        {
            Console.WriteLine($"  ✅ 从 plugins 目录加载: {pluginPath}");
            Assembly found = Assembly.LoadFrom(pluginPath);
            return found.FullName == requested.FullName ? found : null;
        }

        // 都找不到，返回 null，让 CLR 继续报错
        return null;
    }
}
```

这是失败解析事件，只负责自己认识的请求；`null` 表示本处理器不能解析，不保证所有调用场景最后都是同一个 FileNotFoundException。应在需要的加载/反序列化前订阅，避免处理器内部再次执行同一失败名称加载而递归；稍后加入处理器能否重试还受失败缓存/调用路径影响。

原流程图保留“默认名称绑定失败”这个前提，不把事件当成每一次读取必经步骤：

<a id="c24-resolve-flow"></a>
<!-- C24-D01-Q002-A-B025 -->
```text
formatter.Deserialize(fs)
    ↓
从流中读出: "MyGame, Version=1.0.0.0, ..."
    ↓
按当前Simple/Full等策略解析名称 "MyGame, Version=1.0.0.0, ..."
    ↓
默认探测路径找不到 → 触发 AssemblyResolve 事件
    ↓
我们的 OnAssemblyResolve 被调用
    ↓
匹配到 _loadedPlugin → 返回它
    ↓
反序列化成功 ✅
```

原简洁 lambda 方案也是一条独立写法，限制本例名字，仍须对实际返回身份和部署规则负责：

<a id="c24-resolve-lambda"></a>
<!-- C24-D01-Q002-A-B028 -->
```csharp
AppDomain.CurrentDomain.AssemblyResolve += (sender, args) =>
{
    string asmName = new AssemblyName(args.Name).Name;
    if (asmName != "MyGame") return null; // 补限定请求范围
    string path = Path.Combine(AppDomain.CurrentDomain.BaseDirectory, 
                               "plugins", $"{asmName}.dll");
    return File.Exists(path) ? Assembly.LoadFrom(path) : null;
};
```

补充实证分清条件：原全局 Player 查 MyGame.Player 为null，真实库标Version1/token null；插件只在 plugins 的本次 Framework夹具中，同进程和新进程读回都出现绑定失败。补 MyGame 命名空间后的安全张三/Level25 数据，经上述两类限定 resolver 都读回；缓存分支也生效。另在独立 base-probing 目录把同DLL放入名称可探测位置，未挂 resolver 的新进程可直接读回。后一个输入不同，不能抹去前面的真实失败。

现代动态加载还应按 ALC/宿主部署合同处理（见第22/23章），不是用旧 LoadFrom/Resolve 任意代替所有现代依赖解析；迁移 JSON 也不能自动解决插件类型身份和部署问题。

## Circle：少存派生值，读回时修复

用户要求详细解释哪些数据应该随对象走。原搬家类比保：冰箱中的冰或可重新置办的东西不必原样搬，到了目的地按需要恢复；它说明可重算/地点相关状态，不等于序列化自动替你安全重开所有资源。

```csharp
{
    public double Radius;

    [NonSerialized]
    public double Area;

    public Circle(double radius)
    {
        Radius = radius;
        Area = Radius * Radius * Math.PI;
    }

    {
```

```csharp
}
```

<a id="c24-lifecycle"></a>
### 四个生命周期回调与临时缓存

单个普通对象的教学流程是 OnSerializing→写数据→OnSerialized，以及 OnDeserializing→填字段→OnDeserialized。方法要符合回调签名；图内不同对象相对调用顺序不是公共“内层必先”保证。先看原LifecycleDemo：

<a id="c24-lifecycle-class"></a>
<!-- C24-D01-Q003-A-B023 -->
```csharp
[Serializable]
public class LifecycleDemo
{
    public string Name;

    [NonSerialized]
    public string TempCache;  // 临时缓存，不需要持久化

    public LifecycleDemo() { }

    [OnSerializing]
    private void OnSerializing(StreamingContext context)
    {
        Console.WriteLine("  ① [OnSerializing] 马上要序列化了");
        TempCache = "序列化前的临时数据";
    }

    [OnSerialized]
    private void OnSerialized(StreamingContext context)
    {
        Console.WriteLine("  ③ [OnSerialized] 序列化完了");
        TempCache = null;  // 清理掉临时数据
    }

    [OnDeserializing]
    private void OnDeserializing(StreamingContext context)
    {
        Console.WriteLine("  ④ [OnDeserializing] 马上要反序列化了");
        // 通常在这里初始化一些必要的非序列化字段
        TempCache = "等待数据填充...";
    }

    [OnDeserialized]
    private void OnDeserialized(StreamingContext context)
    {
        Console.WriteLine("  ⑥ [OnDeserialized] 反序列化完了");
        // 本对象字段已填充；关联对象的自定义修复仍不能据此假定全部完成
        Console.WriteLine($"     最终状态: Name={Name}, TempCache={TempCache}");
    }
}
```

原运行片段第二个using中的 `ms.ToArray()` 错用了前一个局部变量。保存字节再新建流，仍用张三和同一数据：

<a id="c24-lifecycle-call"></a>
<!-- C24-D01-Q003-A-B025 -->
```csharp
byte[] savedBytes;
var demo = new LifecycleDemo { Name = "张三" };

Console.WriteLine("=== 序列化 ===");
using (var ms = new MemoryStream())
{
    new BinaryFormatter().Serialize(ms, demo);
    savedBytes = ms.ToArray();
}

Console.WriteLine("\n=== 反序列化 ===");
using (var ms = new MemoryStream(savedBytes))
{
    new BinaryFormatter().Deserialize(ms);
}
```

<a id="c24-secureuser"></a>
### SecureUser的自定义数据骨架

原把密码加工后写入的场景保，纠函数名/日志：这里的Base64只是编码，绝不等于加密或密码安全存储。非sealed类通常用protected特殊ctor便于派生类调用；并非所有类型必须protected。

<a id="c24-secureuser-class"></a>
<!-- C24-D01-Q003-A-B037 -->
```csharp
[Serializable]
public class SecureUser : ISerializable
{
    public string Username;
    private string _password;  // 敏感字段，不能直接存明文

    public SecureUser(string username, string password)
    {
        Username = username;
        _password = password;
    }

    // 非sealed可继承类型常用protected特殊ctor；这是设计建议
    protected SecureUser(SerializationInfo info, StreamingContext context)
    {
        Username = info.GetString("user");
        // 从流里读出Base64编码值并解码
        _password = Decrypt(info.GetString("pwd"));
        Console.WriteLine($"反序列化完成: {Username}, Base64已解码");
    }

    // ★ 序列化方法 —— 完全由你决定写什么
    public void GetObjectData(SerializationInfo info, StreamingContext context)
    {
        info.AddValue("user", Username);
        // Base64编码后写入流；不是安全加密
        info.AddValue("pwd", Encrypt(_password));
        Console.WriteLine("序列化完成: Base64已编码");
    }

    private string Encrypt(string s) => Convert.ToBase64String(System.Text.Encoding.UTF8.GetBytes(s));
    private string Decrypt(string s) => System.Text.Encoding.UTF8.GetString(Convert.FromBase64String(s));
}
```

原Encrypt/Decrypt名称仍可看出调用关系，但实现就是UTF8↔Base64。作者安全alice/123456夹具实际回读123456，编码MTIzNDU2，可直接逆转；没有密码安全方案或加密强度实证。

T的SecureData只有特殊ctor/GetObjectData骨架，Encrypt/Decrypt另需定义，不当完整可独立创建的程序：

<a id="c24-securedata-skeleton"></a>
<!-- C24-D01-Q003-T-B038 -->
```csharp

{
    private string _password;

    protected SecureData(SerializationInfo info, StreamingContext context)
    {
        // 从info里读，可以解密
        _password = Decrypt(info.GetString("pwd"));
    }

    public void GetObjectData(SerializationInfo info, StreamingContext context)
    {
        // 加密后写进去
```

### hello用UTF8，为何整个文件仍不是UTF8文档

“hello”是字符串而不是一个字符。CLR字符串采用UTF16代码单元；一个char代码单元16位，不等每个Unicode标量或用户眼中的字符都恰两字节。原hello逐字母编码正确，保原五个输入：

<a id="c24-hello-encoding"></a>
<!-- C24-D01-Q006-A-B006 -->
```text
h = 0x68
e = 0x65
l = 0x6C
l = 0x6C
o = 0x6F
```

NRBF里的字符串可以用UTF8写入，但整个记录还含类型标记、长度/ID、整数和浮点字段。原框图本来就有错误标注，现作为**原错误示意**完整保留：

<a id="c24-original-layout-error"></a>
<!-- C24-D01-Q006-A-B010 -->
```text
┌─────────────────────────────────────────┐
│ 01 00 00 00  ← 格式化器版本标记           │
│ FF FF FF FF  ← 对象引用标记               │
│ 01 00 00 00  ← 字段计数                   │
│ 0C           ← 字符串长度"12"（包括类型名） │
│ 4D 79 47 61 6D 65 ...  ← "MyGame.Circle" │
│ 00           ← 分隔符                      │
│ 0C           ← 又是一个长度标记             │
│ 52 61 64 69 75 73  ← "Radius"（字段名）   │
│ 00                                  │
│ 0A           ← 10（double 类型的二进制表示的一部分）│
│ ...                                        │
│ 68 65 6C 6C 6F  ← 这里才是 "hello" 的 UTF-8 字节 │
│ ...                                        │

```

这里不能把每个0C都解释为“字符串长度12”，也不能把头中的FFFF直接叫任意对象引用标记。Double10不是一个整数0A；数值按具体格式规定编码，不是任意“本机原生布局”。真实头/字节见下节。

UTF8的68 65 6C 6C 6F可解为hello；01/00是控制字符/NUL，FF不是合法UTF8开头。替换解码通常得到U+FFFD（�），`ï¿½`是替换字符的UTF8字节又被按另一编码误读的显示，不能称它就是UTF8替换字符。严格decoder可以抛异常。结构字节并非都非法UTF8或不可见；选编码仍不会将数值记录自动变成带字段语义的文本。

### 自造安全Person的真实NRBF记录

```text

Int32 30: 1E 00 00 00
Double 10:   00 00 00 00 00 00 24 40
Double 95.5: 00 00 00 00 00 E0 57 40
```

## ISerializable：自己定义键和值

原问题列了四个不同需求：将A/B合并值、加工敏感字段、Name改Username兼容旧数据、新字段版本演进。NonSerialized/回调适合少存和修复；ISerializable可定制数据表示，OptionalField只负责适用字段路径的缺失容忍，不是这些需求都必须同时实现两个机制。

原接口签名及特殊ctor形状保为API/类型骨架，不是另定义一个与FCL不同的替代接口：

<a id="c24-iserializable-signature"></a>
<!-- C24-D01-Q007-A-B010 -->
```csharp
public interface ISerializable
{
```

### user/pwd/version/savedAt四个键

原User与前面SecureUser不同：增加version2和savedAt UTC时间、GetPassword演示方法及读取输出，保全部输入。Base64函数虽叫Encrypt/Decrypt，日志修为编码：

<a id="c24-user-class"></a>
<!-- C24-D01-Q007-A-B018 -->
```csharp
[Serializable]
public class User : ISerializable
{
    public string Username;
    private string _password;  // 敏感字段

    public User(string username, string password)
    {
        Username = username;
        _password = password;
    }

    // ★ 序列化时调用：完全由我们决定写什么
    public void GetObjectData(SerializationInfo info, StreamingContext context)
    {
        info.AddValue("user", Username);                    // 用户名明文存
        info.AddValue("pwd", Encrypt(_password));          // Base64编码后存，不是安全加密
        info.AddValue("version", 2);                       // 我们自己加一个版本标记
        info.AddValue("savedAt", DateTime.UtcNow);         // 存一个时间戳
        
        Console.WriteLine("GetObjectData: 数据已写入流（密码已Base64编码）");
    }

    // ★ 反序列化时调用：从 info 里取数据
    protected User(SerializationInfo info, StreamingContext context)
    {
        Username = info.GetString("user");
        _password = Decrypt(info.GetString("pwd"));
        int version = info.GetInt32("version");
        DateTime savedAt = info.GetDateTime("savedAt");
        
        Console.WriteLine($"反序列化完成: user={Username}, version={version}, savedAt={savedAt}");
    }

    // 原函数名Encrypt/Decrypt，实际是可逆Base64编码/解码；仅演示数据转换
    private string Encrypt(string s) => Convert.ToBase64String(Encoding.UTF8.GetBytes(s));
    private string Decrypt(string s) => Encoding.UTF8.GetString(Convert.FromBase64String(s));

    public string GetPassword() => _password;  // 仅供演示
}
```

```csharp
// 输出: GetObjectData: 数据已写入流（密码已Base64编码）

{
```

### 类型身份与新增字段是两个问题

原Customer_V1与Customer_V2的声明分别保：

<!-- C24-D01-Q007-A-B047 -->

| 本次Framework输入 | 默认Simple | 显式Full |
| --- | --- | --- |
| V1→V2缺Phone且非Optional | 本机容忍，Phone null | SerializationException |
| V1→V2 Optional Phone | Phone null | Phone null |

<a id="c24-document"></a>
### Document的missing键默认值

原Document含VersionAdded2/3和SchemaVersion3，保完整特殊ctor；它缺普通创建ctor，是上下文骨架。ISerializable下缺键处理由自己的GetXXX代码决定，OptionalField不自动接管：

<a id="c24-document-class"></a>
<!-- C24-D01-Q007-A-B051 -->
```csharp
[Serializable]
public class Document : ISerializable
{
    public string Title;
    public string Content;
    
    [OptionalField(VersionAdded = 2)]  // 标记这是 V2 加入的
    public DateTime CreatedAt;
    
    [OptionalField(VersionAdded = 3)]  // V3 加入的
    public string Author;
    
    [OptionalField(VersionAdded = 3)]
    public int WordCount;

    // 当前代码总写这些键；VersionAdded不会自动根据版本删键
    public void GetObjectData(SerializationInfo info, StreamingContext context)
    {
        info.AddValue("Title", Title);
        info.AddValue("Content", Content);
        info.AddValue("CreatedAt", CreatedAt);
        info.AddValue("Author", Author ?? "");
        info.AddValue("WordCount", WordCount);
        info.AddValue("SchemaVersion", 3);  // 我们自己记录的版本
    }

    // 反序列化：老版本数据可能缺字段，用 try-catch 保护
    protected Document(SerializationInfo info, StreamingContext context)
    {
        Title = info.GetString("Title");
        Content = info.GetString("Content");
        
        // 老数据可能没有 CreatedAt
        try { CreatedAt = info.GetDateTime("CreatedAt"); }
        catch (SerializationException) { CreatedAt = DateTime.MinValue; }
        
        // 老数据可能没有 Author 和 WordCount
        try { Author = info.GetString("Author"); }
        catch (SerializationException) { Author = "未知"; }
        
        try { WordCount = info.GetInt32("WordCount"); }
        catch (SerializationException) { WordCount = Content?.Length ?? 0; }
    }
}
```

原代码写SchemaVersion3却未读取它；CreatedAt/Author/WordCount有catch默认值，但Title/Content依旧必须存在且转换适用。WordCount fallback是Content.Length（UTF16代码单元长度），不是通用字数算法。作者仅用自己LegacyDocument经SetType生成Title=Old/Content=Hello且缺新键的数据，读回MinValue/未知/5；缺Title则特殊ctor抛SerializationException，在本机被TargetInvocationException包装。不能承诺“任意历史数据永不崩”。

原机制ASCII归纳保，VersionAdded改准确标注：

<a id="c24-data-map"></a>
<!-- C24-D01-Q007-A-B054 -->
```text
控制序列化/反序列化的数据
├── ISerializable 接口
│   ├── GetObjectData()：序列化时调用，决定流里写什么
│   └── 特殊构造函数：反序列化时调用，从流里读数据
│   用途：加密、字段改名、合并/拆分字段、自定义版本标记
│
└── OptionalField 特性
    ├── 标在字段上：告诉格式化器"流里没有这个字段也不要报错"
    └── VersionAdded 属性：标记字段是哪个版本加入的
    用途：适用字段路径的缺字段版本容忍；不同类型身份迁移另处理
```

少存派生值优先NonSerialized/回调；改键/合并/自定义版本可用ISerializable。JSON新增Phone的原属性模型也保在下节；它有合同规则，不是文本天然解决所有类型演进。

<a id="c24-context"></a>
## StreamingContext告诉对象预期用途

State为可组合位标志，Context为调用者自定义对象引用；不是基础设施自动侦测任意文件/网络的真实性。原八个表项的不同用途保，实际名称是CrossMachine单数：

<a id="c24-context-table"></a>
<!-- C24-D01-Q001-A-B061 -->
| 标志 | 含义 |
| --- | --- |
| `CrossProcess` | 同一机器不同进程 |
| `CrossMachine` | 不同机器 |
| `File` | 来源/目的地是文件 |
| `Persistence` | 存储（数据库/文件） |
| `Remoting` | 远程未知位置 |
| `Clone` | 对象图克隆，合同允许同进程资源访问假设；资源寿命/所有权仍由调用方设计 |
| `CrossAppDomain` | 不同 AppDomain |
| `All` | All=255，各种来源/目的地都可能；不是选定的唯一实际场景 |

Clone同进程访问句柄的假设与[官方合同](https://learn.microsoft.com/en-us/dotnet/api/system.runtime.serialization.streamingcontextstates?view=net-10.0)一致，保这个历史用途；另外补充：原始句柄值不因此复制内核对象，也不自动延长寿命、避免双重关闭或确认句柄没有被复用。组合标志判断应按位处理，不能任意用State==Clone代替“包含Clone”。本次File|Clone的State与自定义Context引用同一对象均实测；没有执行或验证真实内核句柄所有权。

### SetType只影响当前正在写出的描述

原OldUser→NewUser流程图保：

<a id="c24-settype-flow"></a>
<!-- C24-D01-Q008-A-B014 -->
```text
实际对象: OldUser        →  GetObjectData 里调用 SetType(typeof(NewUser))
                              ↓
流里记录的类型: NewUser   →  反序列化时直接创建 NewUser
```

原完整程序定义、字段Username/Age、张三25、日志与输出完整保。SetType不回头修改一年前已经写好的旧字节；真正读旧身份可用Binder/显式迁移策略。T另称旧数据OldNamespace.OldType可经SetType改成NewNamespace.NewType，这个既有字节的前提不成立；其LegacyUser在当前GetObjectData中SetType(typeof(ModernUser))并写目标期望字段，是另一个正确的当前写身份示意，不是已给出另一套完整程序。

<a id="c24-settype-classes"></a>
<!-- C24-D01-Q008-A-B016 -->
```csharp
using System;
using System.IO;
using System.Runtime.Serialization;
using System.Runtime.Serialization.Formatters.Binary;

// ===== 旧版本类型（假设在旧程序集中）=====
[Serializable]
public class OldUser : ISerializable
{
    public string Name;
    public int Age;

    public OldUser(string name, int age)
    {
        Name = name;
        Age = age;
    }

    // 序列化时：告诉格式化器"把我伪装成 NewUser"
    public void GetObjectData(SerializationInfo info, StreamingContext context)
    {
        Console.WriteLine("OldUser.GetObjectData: 正在把类型改为 NewUser...");
        
        // ★ 核心：篡改流里的类型信息
        info.SetType(typeof(NewUser));
        
        // 按照 NewUser 期望的字段名写入（注意字段名映射）
        info.AddValue("Username", Name);   // 旧字段 Name → 新字段 Username
        info.AddValue("Age", Age);
    }
}

// ===== 新版本类型 =====
[Serializable]
public class NewUser : ISerializable
{
    public string Username;
    public int Age;

    // 反序列化构造函数
    protected NewUser(SerializationInfo info, StreamingContext context)
    {
        Console.WriteLine("NewUser 反序列化构造函数: 正在从流中读取数据...");
        Username = info.GetString("Username");
        Age = info.GetInt32("Age");
    }

    public void GetObjectData(SerializationInfo info, StreamingContext context)
    {
        info.AddValue("Username", Username);
        info.AddValue("Age", Age);
    }

    public override string ToString() => $"NewUser {{ Username={Username}, Age={Age} }}";
}
```

```text
NewUser 反序列化构造函数: 正在从流中读取数据...
反序列化结果: NewUser { Username=张三, Age=25 }
```

<a id="c24-settype-steps"></a>
<!-- C24-D01-Q008-A-B022 -->
```text
1. 你传入的是 OldUser 实例
2. 格式化器调用 OldUser.GetObjectData()
3. GetObjectData 里调用 info.SetType(typeof(NewUser))
   → 流里写的类型信息变成了 "NewUser"
4. 格式化器把数据写入流
5. 反序列化时，格式化器从流里读到 "NewUser"
6. 直接创建 NewUser 实例，调用 NewUser 的反序列化构造函数
7. 你拿到的就是 NewUser，完全跳过了 OldUser
```

目标NewUser按其期望键读取，所以源Name必须写成Username，Age也要对上；“完全跳过OldUser”指读回类型路径，并非序列化时未执行OldUser.GetObjectData。T另一个短OldUser/NewUser没有同样日志/ToString，是独立形状，保：

<a id="c24-settype-thinking"></a>
<!-- C24-D01-Q008-T-B046 -->
```csharp
[Serializable]
public class OldUser : ISerializable
{
    public string Name;
    public int Age;

    public OldUser(string name, int age) { Name = name; Age = age; }

    public void GetObjectData(SerializationInfo info, StreamingContext context)
    {
        // 关键：告诉格式化器，流里的类型信息是 NewUser
        info.SetType(typeof(NewUser));
        
        // 按照 NewUser 期望的字段名写入数据
        info.AddValue("Username", Name);  // 旧字段名 Name -> 新字段名 Username
        info.AddValue("Age", Age);
    }
}

[Serializable]
public class NewUser : ISerializable
{
    public string Username;
    public int Age;

    // 反序列化构造函数
    protected NewUser(SerializationInfo info, StreamingContext context)
    {
        Username = info.GetString("Username");
        Age = info.GetInt32("Age");
    }

    public void GetObjectData(SerializationInfo info, StreamingContext context)
    {
        info.AddValue("Username", Username);
        info.AddValue("Age", Age);
    }
}
```

### 返回全局单例

原class没有sealed，不因原注释误说sealed而删掉其private特殊ctor；本机此形状能正常调用。它只在本程序内返回静态实例，不保全用户未声明的全部外部状态：

<a id="c24-singleton-class"></a>
<!-- C24-D01-Q008-A-B040 -->
```csharp
[Serializable]
public class Singleton : ISerializable, IObjectReference
{
    // 全局单例实例
    private static readonly Singleton _instance = new Singleton();

    public static Singleton Instance => _instance;

    // 私有构造函数，防止外部 new
    private Singleton() { }

    // 本原class未sealed；private特殊ctor本机可调用，非sealed可继承设计通常建议protected
    private Singleton(SerializationInfo info, StreamingContext context) { }

    public void GetObjectData(SerializationInfo info, StreamingContext context)
    {
        // 不需要写任何字段，因为单例的状态是全局共享的
    }

    // ★ 无论反序列化多少次，都返回同一个单例实例
    public object GetRealObject(StreamingContext context)
    {
        Console.WriteLine("GetRealObject: 返回全局单例");
        return _instance;
    }
}
```

<a id="c24-substitution-comparison"></a>
<!-- C24-D01-Q008-A-B045 -->
| 对比维度 | `SetType()` | `IObjectReference` |
| --- | --- | --- |
| 作用阶段 | 序列化时 | 反序列化图修复/替换阶段 |
| 核心思想 | 篡改流里的类型标记 | 替换最终返回的对象 |
| 适合场景 | 类型重命名/迁移、版本升级 | 返回不同对象（字符串、单例、代理） |
| 是否需要目标类型配合 | 是（目标类型要能从流中读取数据） | 返回值需满足接收对象图的真实用途/相容要求；不是不受限制地替换任意强类型槽 |
| 灵活性 | 可调整当前写入描述，仍需目标合同 | 可返回单例/代理/其它相容对象，按实际图与生命周期约束 |

现代JsonConverter<T>可以实现数据表示转换或返回相容T/派生类型，却不能直接返回一个无关string而仍宣称Read返回T。此限制是JSON合同补充，不反标原“类似类型转换”的合理建议。

## 不改类型源码时的代理与身份映射

原ISerializationSurrogate接口签名保，实际GetObjectData/SetObjectData由选中的代理处理：

<a id="c24-surrogate-signature"></a>
<!-- C24-D01-Q001-A-B073 -->
```csharp
public interface ISerializationSurrogate {
    void GetObjectData(Object obj, SerializationInfo info, StreamingContext context);
    Object SetObjectData(Object obj, SerializationInfo info, StreamingContext context, ISurrogateSelector selector);
}
```

SurrogateSelector可按类型及适用StreamingContext选择代理，再设formatter.SurrogateSelector。原书24.8的DateTime目标是把机器本地值**写成UTC**发送，读回再**转成本地**；原问答只说“序列化时UTC转本地”把阶段/方向说反。本地MD712—727与同版PDF579—580/印刷562—563的原算法保：

<a id="c24-book-time-surrogate"></a>
```csharp
internal sealed class UniversalToLocalTimeSerializationSurrogate : ISerializationSurrogate {
    public void GetObjectData(Object obj, SerializationInfo info, StreamingContext context) {
        // 将 DateTime 从本地时间转换成 UTC
        info.AddValue("Date", ((DateTime)obj).ToUniversalTime().ToString("u"));
    }

    public Object SetObjectData(Object obj, SerializationInfo info, StreamingContext context,
        ISurrogateSelector selector) {
        // 将 DateTime 从 UTC 转换成本地时间
        return DateTime.ParseExact(info.GetString("Date"), "u", null).ToLocalTime();
    }
} 
```

原书演示使用SoapFormatter以查看XML，本任务针对相同代理算法的补充实证使用BinaryFormatter，明确这项适配。China Standard Time本地2024-01-01 08:00:00.123写wire为2024-01-01 00:00:00Z，读回本地08:00:00.000；“u”格式只保秒，毫秒123丢失。这是原例精度边界，未捏原曾保证所有ticks不变。此前作者另用UTC→local ticks→UTC的补充TimeSurrogate同机可恢复UTC，那是不同方向/表示的对照，不冒为书原算法。

原历史循环引用提醒保：原书24.8还明确wrapper模式下SetObjectData应修改传入obj，并返回null或obj（MD781），不能把上面返回新DateTime的普通代理写法直接搬为任意循环图替换。`FormatterServices.GetSurrogateForCyclicalReference(inner)`返回相应wrapper，Framework源码有此入口并转发内部代理。本任务安全探针只确认入口可用，没有穷尽循环图、也没有把导读“某bug”泛化到所有运行时版本。[Framework代理wrapper](https://raw.githubusercontent.com/microsoft/referencesource/main/mscorlib/system/runtime/serialization/formatterservices.cs)

SerializationBinder.BindToType(assemblyName,typeName)可把旧程序集A/类型T的描述映到合适B/T'；BindToName可影响当前写出身份。它仍需目标数据合同、真实类型可用、图相容和版本策略，不是给不安全BF装一个Binder就安全。SetType当前写与Binder读旧身份不是同一个时点。

## 历史机制与当前选型分开

原第24章问答围绕Runtime Serialization/Serializable/ISerializable/Context/FormatterServices/Surrogate/Binder，后来另外讨论JSON。System.Text.Json由官方[2019年Core3.0文章](https://devblogs.microsoft.com/dotnet/try-the-new-system-text-json-apis/)引入，不能把它当第四版时代本章的原机制；但本任务没有为此逐页审核全书，不能凭出版时点断言全书从未提到任何其他JSON方式。

原逐版本表保，要区分编译诊断、项目开关和运行时API：

<a id="c24-bf-version-table"></a>
<!-- C24-D01-Q009-A-B014 -->
| .NET 版本 | 状态 |
| --- | --- |
| .NET 5 | `BinaryFormatter` 标记为**过时**，编译时出现 `SYSLIB0011` 警告 |
| .NET 7 | Serialize/Deserialize相关过时诊断升级为编译错误（仍须看具体API/目标配置） |
| .NET 8 | 多数项目默认禁用；存在相应历史开关/项目例外，不能只凭版本断任意调用结果 |
| **.NET 9**​ | 内置使用路径被移除，旧允许开关不再恢复；本机9.0.8/10.0.12两API实测PNSE |

作者只自己的hello/空流，在已有9/10即使设置旧enable switch仍看到：BF对象可构造，Serialize/Deserialize各PlatformNotSupportedException。没有安装不受支持的兼容包，现代失败也不倒判Framework历史原例非法。[移除说明](https://learn.microsoft.com/en-us/dotnet/core/compatibility/serialization/9.0/binaryformatter-removal)

安全问题与“人看不懂的二进制”无必然关系。BF数据影响运行时类型重建和执行路径，可以触发危险代码/资源消耗；不应从来源不可靠的数据构建对象图，Binder或开关不能把这个机制修为安全。JSON按代码/合同及显式派生类型建立对象范围，仍可能执行构造器、setter、getter、转换器与回调，需相应输入/资源/合同限制，不是“任何JSON都不执行逻辑”。

<a id="c24-serializer-choice"></a>
原四类替代的用途保：STJ的JSON适于可读协议/跨平台；DCS的XML支持Serializable/ISerializable模型但known types与集成还需适配；需要紧凑二进制时可按合同考虑MessagePack for C#或protobuf-net。没有一个直接读原BF字节的drop-in替代，不据名称承诺任何工作负载绝对最快/最小或所有配置天然安全。[选型与迁移合同](https://learn.microsoft.com/en-us/dotnet/standard/serialization/binaryformatter-migration-guide/choose-a-serializer)

<a id="c24-product-convention"></a>


```csharp

        foreach (var property in info.Properties)

});
```

### UserConverter沿用user/pwd两键

原BF User的短GetObjectData片段保，它不是完整可独立new/反序列化的类型（Encrypt等上下文省略）；密码加工演示改准确注释：

<a id="c24-json-user-bf-skeleton"></a>
<!-- C24-D01-Q010-A-B053 -->
```csharp
// BinaryFormatter 方式
public class User : ISerializable
{
    public string Username;
    private string _password;
    
    public void GetObjectData(SerializationInfo info, StreamingContext context)
    {
        info.AddValue("user", Username);
        info.AddValue("pwd", Encrypt(_password));  // 本例语境是Base64编码；实际安全加密需要另外方案
    }
}
```

原STJ UserConverter.Write调用了User.GetPassword，原User未定义这个成员，真实CS1061；补演示方法，保alice/123456、所有Read/Write步骤：

<a id="c24-user-converter"></a>
<!-- C24-D01-Q010-A-B055 -->
```csharp
public class User
{
    public string Username { get; set; }
    
    // 私有属性，JSON 不直接读写
    private string _password;
    
    // 公共方法操作密码
    public void SetPassword(string pwd) => _password = pwd;
    public bool VerifyPassword(string pwd) => _password == pwd;
    public string GetPassword() => _password; // 补Write所需演示方法
}

// 自定义转换器：控制 User 的 JSON 读写
public class UserConverter : JsonConverter<User>
{
    public override User Read(ref Utf8JsonReader reader, Type typeToConvert, JsonSerializerOptions options)
    {
        using var doc = JsonDocument.ParseValue(ref reader);
        var root = doc.RootElement;
        
        var user = new User();
        user.Username = root.GetProperty("user").GetString()!;
        var encryptedPwd = root.GetProperty("pwd").GetString()!;
        user.SetPassword(Decrypt(encryptedPwd));  // Base64解码，非安全解密
        return user;
    }
    
    public override void Write(Utf8JsonWriter writer, User value, JsonSerializerOptions options)
    {
        writer.WriteStartObject();
        writer.WriteString("user", value.Username);
        writer.WriteString("pwd", Encrypt(value.GetPassword()));  // Base64编码，非安全加密
        writer.WriteEndObject();
    }
    
    private static string Encrypt(string s) => Convert.ToBase64String(Encoding.UTF8.GetBytes(s));
    private static string Decrypt(string s) => Encoding.UTF8.GetString(Convert.FromBase64String(s));
}
```

```csharp
    public string? CouponCode { get; set; }
}
```

## JSON也要知道类型结构，目的不同

用户问“是不是也读程序集元数据”。默认反射路径确会取得成员访问、构造、特性和JsonSerializerOptions信息，建立JSON合同；JSON文档不需要把实际程序集显示名称作为默认CLR绑定协议写入。开发者可以自己设计含名字的数据，显式多态也有discriminator，所以“不含程序集信息”要限定默认合同，不是JSON语法禁止字符串。

<a id="c24-json-metadata-table"></a>
<!-- C24-D01-Q012-A-B005 -->
| 维度 | BinaryFormatter 的"元数据" | System.Text.Json 的"元数据" |
| --- | --- | --- |
| **关注点**​ | CLR身份、字段/自定义数据与引用记录；不复制内存布局 | 哪些属性/字段需要读写 + 如何读写 + 特性配置 |
| **包含程序集信息？**​ | NRBF相关记录可写程序集/类型身份 | 默认JSON合同不写用于自动CLR绑定的程序集显示名；用户数据可有名字 |
| **用途**​ | 反序列化时**定位并加载程序集**，创建对应类型实例 | 仅仅是"如何把对象映射成 JSON 键值对"的契约 |
| **安全性**​ | 危险的——数据指定类型，可能导致 RCE | 已知合同控制类型范围；getter/ctor/converter/callback仍可执行逻辑 |

原反射五步保：发现适用属性/字段，检查Json特性，选构造/创建方式，建立JSON名↔CLR成员映射，并缓存合同。作用于实际类型与options/配置范围，不意味着后续应用任何操作、任何上下文都绝不再反射或分配。

原首次/后续两次Serialize片段保，修绝对“无反射开销”的注释：

<a id="c24-json-cache-call"></a>
<!-- C24-D01-Q012-A-B014 -->
```csharp
// 第一次调用：通过反射收集 Person 的元数据，有性能开销
string json1 = JsonSerializer.Serialize(person1);  
// 同类型/相容options下可复用合同；不是保证整个应用所有层都无反射/初始化
string json2 = JsonSerializer.Serialize(person2);
```

作者modifier只计Person合同：相同options两次建立计数1，配置不同的另一个options后累计2。它验证这些具体输入的缓存行为，不是耗时或内存基准。BF也不需每一次读回都重新把同程序集文件物理加载一遍；已可用的身份/类型、代理/Binder与缓存会改变路径。

### JsonTypeInfo真实API与原伪形状

原伪形状含不存在的JsonConstructorInfo、Converter setter以及过宽构造描述，保为**API错误示意，不能当库声明使用**：

<a id="c24-jsontypeinfo-original-invalid"></a>
<!-- C24-D01-Q012-A-B026 -->
```text
public class JsonTypeInfo
{
    public JsonConstructorInfo? ConstructorAttributeProvider { get; set; }
    public JsonConverter Converter { get; set; }
    public Func<object>? CreateObject { get; set; }  // 反序列化的工厂
    public JsonTypeInfoKind Kind { get; }
    // ... 还有其他元数据
```

对应现有.NET9/10的公开API节选（略实现，并非重新定义FCL类型）：

```csharp
public abstract class JsonTypeInfo
{
    public JsonConverter Converter { get; }
    public Func<object>? CreateObject { get; set; }
    public ICustomAttributeProvider? ConstructorAttributeProvider { get; }
    public JsonTypeInfoKind Kind { get; }
    // Properties、类型及回调等其它合同信息另略

```

| 对比维度 | BinaryFormatter | System.Text.Json（默认反射） | System.Text.Json（源码生成） |
| --- | --- | --- | --- |
