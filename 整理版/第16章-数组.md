<a id="c16-types"></a>
## 数组是引用类型，元素类型与数组形状确定类型身份

int[]本身是引用类型，即使每个元素是int值类型；string[]的元素区域保存引用，字符串字符存储在各自对象中。所有数组类型都从System.Array派生，Array又从Object派生。数组实例创建时确定各维长度，长度不是类型身份的一部分，也不能改变该实例的长度；换成另一个数组引用与改变原数组长度不同。

一维零基向量（SZ array）、多维数组与一维非零基数组有不同表示/操作路径。交错数组如int[][]是数组的数组，不是int[,]矩形数组；不能把SZ与交错数组当成一组同义词。[C#数组规范](https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/language-specification/arrays)

原导读还包括对象头、类型关联、长度/秩/下界等开销。以下是**概念图**，不是所有CPU/CLR的固定偏移：

```text
SZ int[]：对象表示/类型关联 + 长度及必要对齐 + 连续int元素
string[]：对象表示/类型关联 + 长度及必要对齐 + 连续对象引用
int[,]：对象表示/类型关联 + 多维形状信息 + 按约定排列的元素
非零基数组：还需按各维下界修正索引
```

运行时方法表等类型结构不等于托管堆里的System.Type反射对象。GC根据类型/元素是否含引用扫描，不能把每个int字节都当对象引用，也不能仅凭手画“插MyField”图保证运行时立刻崩溃。

<a id="c16-base-array"></a>
### 原int[3]与显式继承的对照

以下为**完整程序**，保留原3元素、BaseType、is Array和is object三观察：

```csharp
using System;
class Program {
    static void Main() {
        int[] a = new int[3];
        Console.WriteLine(a.GetType().BaseType);
        Console.WriteLine(a is Array);
        Console.WriteLine(a is object);
        Type known = typeof(int).MakeArrayType();
        Console.WriteLine(known == typeof(int[]));
    }
}
```

输出System.Array、True、True、True。源码没有写`class int[] : Array`，数组语法/元数据签名和运行时共同确定数组类型。类型可以由typeof、签名或MakeArrayType等路径先被解析，不保证一定等到某个newarr首次执行才“诞生”。

以下**反例形状**保留原疑问，但不是合法类型定义：

```text
class int[] : System.Array { ... } // 非合法C#声明
class Foo : int[] { ... }        // 数组类型不可作为此基类
class MyArray : System.Array { } // C# CS0644：特殊基类限制
```

Array.IsAbstract为True、IsSealed为False。abstract阻止直接实例化抽象类，不能解释为一般抽象类不能被继承。原说“Array抽象且密封”错误；String不能被继承的直接C#原因是sealed，不能把普通abstract规则也说成“只有自己知道实现才可继承”。

<a id="c16-bounds"></a>
## 索引范围检查：保证不越界，不保证每个循环只查一次

托管数组访问的语义要求索引有效，否则相应访问抛IndexOutOfRangeException。JIT可根据程序证明安全，从而消除、合并、提升检查；检查语义存在与机器码每次都保留独立分支是两件事。原书“通常循环开始前只检查一次”是教学概括，不是每个优化循环一定多出一次单独索引检查。

<a id="c16-sum-simple"></a>
### 原Sum和循环自身的终止条件

以下为**完整方法片段**，保留原sum、i从0到Length-1和arr[i]：

```csharp
static int Sum(int[] arr) {
    int s = 0;
    for (int i = 0; i < arr.Length; i++) s += arr[i];
    return s;
}
```

数组引用未改变时，循环条件本身能证明该索引在范围内；Length不能被写成别的数字。本机.NET 10的NoInlining、optimize+、关闭分层编译/ReadyToRun、FullOpts反汇编中，简单循环无额外RNGCHKFAIL路径，仍有循环终止判断；不能把长度零判断随意叫作“留下的一次索引检查”。输入1、2、3、4时sum=10。

<a id="c16-bounds-counterexamples"></a>
### 原步长2、引用替换与有界偏移例分别保留

下面是**方法体片段**，第一种原场景在奇数长度时arr[i+1]确实可能越界；不能仅因为i+=2就断言arr[i]也必不能优化。

```csharp
int s = 0;
for (int i = 0; i < arr.Length; i += 2) {
    s += arr[i];
    s += arr[i + 1]; // 奇数长度最后一次可能越界
}
```

第二种原场景是**方法体片段**，需同文定义GetAnotherArray；它改变的是引用，新的数组长度可能不同，而非修改Array.Length：

```csharp
for (int i = 0; i < arr.Length; i++) {
    if (i == 10) arr = GetAnotherArray();
    s += arr[i];
}
```

第三种原建议实验也必须保留并纠正其“必多一次检查”结果：

```csharp
static int SumShiftBounded(int[] arr) {
    int s = 0;
    for (int i = 0; i < arr.Length - 1; i++) s += arr[i + 1];
    return s;
}
```

本机同配置JIT也消除了此有界偏移的额外检查，输入1、2、3、4得到9。另补`arr[i+offset]`与`arr[indices[i]]`的未知偏移/间接索引场景，实际反汇编有cmp/jae及CORINFO_HELP_RNGCHKFAIL；offset=0得到10，offset=1受控抛IndexOutOfRangeException。这些都是具体生成观察，不能推广所有Debug/Release、PGO、CPU、Framework或JIT版本。

原foreach经接口、多维/非零基遍历不一定与同样的SZ循环同形；性能仍按具体代码判断。未跑速度基准，不用“unsafe/Span必快/几乎一样”代替证据。[微软JIT范围证明与优化实例](https://devblogs.microsoft.com/dotnet/performance-improvements-in-net-6/)

<a id="c16-copy"></a>
## Array.Copy、Buffer.BlockCopy、ConstrainedCopy

Copy按元素计数与相应类型转换规则复制；BlockCopy按字节偏移/字节数复制支持的基元数组；ConstrainedCopy保证受控失败时目标未改变。三者不是固定性能星级，也不是共享一个“blittable就都能用”的前提。

<a id="c16-blockcopy-units"></a>
### 原UTF-16 LE的AB与只复制2字节

以下为**完整程序**，完整保留四字节输入、char[2]、命名参数和源count。增加第二个目标数组用于独立演示原“只复制2”的场景：

```csharp
using System;
class Program {
    static void Main() {
        byte[] bytes = { 0x41, 0x00, 0x42, 0x00 };
        char[] chars = new char[2];
        Buffer.BlockCopy(src: bytes, srcOffset: 0, dst: chars,
            dstOffset: 0, count: bytes.Length);
        Console.WriteLine(chars);
        char[] partial = new char[2];
        Buffer.BlockCopy(bytes, 0, partial, 0, 2);
        Console.WriteLine("{0:X4},{1:X4}", (int)partial[0], (int)partial[1]);
    }
}
```

本机little-endian下输出AB和0041,0000。BlockCopy不做字符编码转换，这个输入按UTF-16 LE排列，字节序条件不能丢。只复制2字节是合法的前缀复制，第一个char是A、第二个仍为NUL；它未实现“整个AB”的意图，但不因此必内存破坏或抛异常。

char在托管表示中为2字节，不意味着所有封送配置都与native char相同。BlockCopy检查支持的数组类型和字节范围，不能说它完全绕过类型系统、任意连续存储都可作为输入。

<a id="c16-copy-widen-upcast"></a>
### 原整数加宽与字符串上转

以下为**完整程序**，保留int1、2、3→long和string a、b、c→object[3]只复制2元素的两个不同例：

```csharp
using System;
class Program {
    static void Main() {
        int[] ints = { 1, 2, 3 };
        long[] longs = new long[3];
        Array.Copy(ints, longs, ints.Length);
        Console.WriteLine(String.Join(",", longs));
        object[] objs = new object[3];
        string[] strs = { "a", "b", "c" };
        Array.Copy(strs, objs, 2);
        Console.WriteLine("{0},{1},{2}", objs[0], objs[1], objs[2] == null ? "null" : objs[2]);
    }
}
```

输出1,2,3与a,b,null。Copy还可在支持的场景执行装箱、拆箱或逐元素引用转型；相同类型等适当路径可以批量搬运，不是每次都逐项反射检查。[Array.Copy规则](https://learn.microsoft.com/en-us/dotnet/api/system.array.copy?view=net-10.0)

<a id="c16-copy-behavior-table"></a>
### 原两方法行为表与复印机类比

原两行表比较行为，不与下节三方法的用途表合并：

| 方法 | 行为与前提 |
| --- | --- |
| Array.Copy | 元素复制，适当路径可加宽/装箱/拆箱/转型；无需转换时可批量复制 |
| Buffer.BlockCopy | 对支持的基元数组按字节复制，不做元素数值/编码转换；不是保证一条CPU指令或永远更快 |

复印机整页复制与人工抄写识别格式是原T类比：前者说明字节单位，后者说明可能的元素转换，不意味着Copy永远像人工逐项抄写。比较速度必须保持相同工作量/输入类型并测量；本章没有给未经验证的固定倍率。

<a id="c16-constrained-original"></a>
### 原混合object→object两个try都成功

原对比程序实际源/目标都是object[]，输入1、"two"、3.0全部适合目标；以下为**完整程序**，保留该条件与两个操作，而不将它冒充失败后半修改的证据。

```csharp
using System;
class Program {
    static void Main() {
        object[] src = { 1, "two", 3.0 };
        object[] ordinary = new object[3];
        object[] reliable = new object[3];
        try { Array.Copy(src, ordinary, src.Length); }
        catch (Exception e) { Console.WriteLine(e.GetType().Name); }
        try { Array.ConstrainedCopy(src, 0, reliable, 0, src.Length); }
        catch (Exception e) { Console.WriteLine(e.GetType().Name); }
        Console.WriteLine("{0},{1},{2}", ordinary[0], ordinary[1], ordinary[2]);
        Console.WriteLine("{0},{1},{2}", reliable[0], reliable[1], reliable[2]);
    }
}
```

两次成功，均输出1,two,3。被复制的是对象引用；原1和3.0作为object元素在初始化时已经装箱，并非每次复制再为同一元素重箱。

<a id="c16-constrained-failure"></a>
### 补足原教学意图：失败时目标有无部分改变

以下为**完整程序**，保持引用元素复制场景，补上真正会失败的目标类型和初始内容，原成功例仍在上一节。

```csharp
using System;
class Program {
    static void Main() {
        object[] src = { "new0", 42 };
        string[] ordinary = { "old0", "old1" };
        string[] reliable = { "old0", "old1" };
        try { Array.Copy(src, ordinary, 2); }
        catch (Exception e) { Console.WriteLine(e.GetType().Name); }
        Console.WriteLine(String.Join(",", ordinary));
        try { Array.ConstrainedCopy(src, 0, reliable, 0, 2); }
        catch (Exception e) { Console.WriteLine(e.GetType().Name); }
        Console.WriteLine(String.Join(",", reliable));
    }
}
```

本机Framework/.NET 10均观察InvalidCastException、new0,old1、ArrayTypeMismatchException、old0,old1。普通Copy前项已经写入，再因42不能作string失败；ConstrainedCopy拒绝该需要向下元素转换的路径，目标不变。

这个“失败不破坏目标”保证不是让其他线程无法观察整个复制中的任何中间状态，也不证明内部一定实现事务回滚。兼容性预检和可保证完成的复制路径同样可以实现契约。CER是原Framework的约束执行区历史语境，现代运行时对相关机制另有支持差异，不把方法名字当全面事务系统。[ConstrainedCopy保证](https://learn.microsoft.com/en-us/dotnet/api/system.array.constrainedcopy?view=net-10.0)

<a id="c16-constrained-directions"></a>
### 原hello两个方向的注释恰好相反

下面为**完整程序**，保留两组hello与不同源/目标类型。源数组元素恰好全是string，不足以让object[]→string[]的ConstrainedCopy成为安全上转。

```csharp
using System;
class Program {
    static void Main() {
        object[] wider = { "hello" };
        string[] narrow = { "old" };
        try { Array.ConstrainedCopy(wider, 0, narrow, 0, 1); }
        catch (ArrayTypeMismatchException) { Console.WriteLine("downcast rejected"); }
        Console.WriteLine(narrow[0]);
        string[] source = { "hello" };
        object[] destination = new object[1];
        Array.ConstrainedCopy(source, 0, destination, 0, 1);
        Console.WriteLine(destination[0]);
    }
}
```

输出downcast rejected、old、hello。ConstrainedCopy也拒绝需要装箱、拆箱或一般数值加宽的复制，int[]→long[]不能因普通Copy成功就照用。支持的同表示特殊数组兼容还须按运行时核查，不能把“相同/派生”简化描述当穷尽任何版本。

<a id="c16-copy-int-uint"></a>
### int/uint：复制与别名视图是不同操作

额外边界实验输入int[] {-1,2}、独立uint[] {10,20}：Framework4.8的Copy和ConstrainedCopy都ArrayTypeMismatchException且目标不变；.NET10.0.12两者成功，uint读值为4294967295,2。只表示这些具体运行时的特殊兼容实现，不表示所有数值数组都可互转。

另一个操作`uint[] view=(uint[])(object)ints`在两运行时都接受，这是同一数组的特殊视图，不是分配并复制。静态uint索引读取首项为4294967295，view.GetType()仍为System.Int32[]；通过Array.GetValue读同一对象返回盒装Int32并显示-1。不能把后一条打印结果误说成uint索引返回负数，也不能拿现代Copy成功去覆盖历史Framework观察。

<a id="c16-copy-three-table"></a>
### 原三方法比较表独立保留

原星级是没有测量依据的速度排序，保留原“速度/转换/安全/用途”五维用途并改为可核条件：

| 方法 | 速度条件 | 类型转换 | 安全/失败条件 | 典型用途 |
| --- | --- | --- | --- | --- |
| Buffer.BlockCopy | 基元数组字节复制；不保证比适当Copy路径更快 | 无数值/编码转换 | 校验支持类型/字节范围，业务解释字节由调用方负责 | 原始字节/已匹配表示复制 |
| Array.Copy | 与元素类型、转换及批量路径有关 | 支持相应装/拆/加宽/引用转换 | 某些失败可已改部分目标 | 一般元素复制 |
| Array.ConstrainedCopy | 可靠性限制是契约，非固定最慢星级 | 只允许可可靠完成的相应路径 | 失败不改目标，非跨线程原子保证 | 原Framework CER/可靠复制 |

<a id="c16-blittable"></a>
## blittable是封送表示条件，不是BlockCopy万能通行证

BLT/Bit Block Transfer与“blit”是原词源类比，强调按位传输，不是所有跨语言类型都能任意memcpy。blittable涉及指定托管/非托管表示、布局和封送规则；unmanaged是C#类型性质，连续内存或“是struct”也不是充分判断。[互操作表示与条件](https://learn.microsoft.com/en-us/dotnet/standard/native-interop/best-practices#blittable-types)

<a id="c16-int-string-layout"></a>
### 原int=1与string/char*对照

在本机Windows ABI与little-endian条件下，C# int为4字节，数值1可写为01 00 00 00；相应native32位整数可匹配。按值传参可能走寄存器/栈上的值，不是任何int都“把托管地址扔给C++”。

string包含类型关联/对象表示、长度和内嵌UTF-16字符，不能说它又单独保存一个指向真实char[]的引用；字符串对象地址、字符数据地址和native ANSI char*是不同表示。未匹配表示的指针不能随意当另一种布局用，但没有执行“立刻崩溃”原危险示意。

适当Unicode字符串封送可以利用其字符内容并固定对象，不是每次必分配native缓冲、逐字符编码。ANSI等需求可能要转换；对象整体也不等于纯字符内容。原“非blittable只能Array.Copy”混淆封送与集合复制，不能作为一般选择规则。

<a id="c16-blittable-table"></a>
### 原八行速查表按指定规则纠正

下表保留全部原类别，主要谈默认运行时封送背景；关闭运行时封送等配置另有规则，不能把条件表当所有P/Invoke配置的定律。

| 类别 | 表示/封送条件 | 原原因的修正 |
| --- | --- | --- |
| byte/sbyte/short/ushort/int/uint/long/ulong | 相应固定布局数值通常blittable | native声明仍应匹配宽度/符号与ABI |
| float/double | 相应表示通常blittable | 不由此保证任何native格式/字节序都兼容 |
| char | 依CharSet/上下文，Unicode字符内容等可直接表示 | 托管2字节不等任意native char都是2字节 |
| bool | 默认运行时封送可能转为1/2/4字节并规范化 | C# sizeof(bool)=1；Win32 BOOL为4，不能说C++bool普遍为4 |
| string | 具有相应Unicode条件下可利用的blittable内容 | 字符内嵌，不是另char[]指针，也不总分配/编码 |
| object/普通class | 普通对象引用不作为裸结构字节解释；固定布局class可有blittable内容 | 不能以“所有class有对象头”否定任何格式化内容方案 |
| 一维数组，如int[] | 可具有blittable元素内容，数组对象仍有自己的表示 | 不是整个对象头也可以随意交给native当元素区 |
| struct | 固定布局且字段表示满足相应规则时可blittable | Sequential/Explicit及字段条件；无引用还需区分bool/char封送 |

<a id="c16-point-blockcopy"></a>
### 原Point/BadPoint与结构数组反例

以下为**完整类型片段**，保留Point X/Y和BadPoint Name/X：

```csharp
using System.Runtime.InteropServices;
[StructLayout(LayoutKind.Sequential)]
struct Point { public int X; public int Y; }
struct BadPoint { public string Name; public int X; }
```

Point的字段布局可以适于相应native结构，BadPoint的string字段是引用且需要相应封送处理。但原`Point[]→byte[]可以安全Buffer.BlockCopy`错误：公共BlockCopy只支持基元数组，Point[]即使没有引用字段也被拒绝。本机两运行时Point[]、decimal[]、object[]都ArgumentException，bool[]、char[]却可进行字节复制。

这正说明“BlockCopy支持”与“互操作blittable”不是同一分类；不要因为图形/网络/游戏热点就无条件抛弃string/class或认为struct/Span自动成为已验证的最快最安全方案。

<a id="c16-il"></a>
## 数组IL、Array抽象基类与运行时构造

IL是中间语言和计算栈上的指令体系，不是当前CPU的机器汇编。C#编译和JIT/AOT生成代码是不同阶段；普通成员方法在编译时确定的标识不等于当时已知道进程中的native绝对地址。

<a id="c16-array-opcodes"></a>
### 原new int[10]、store5、load5

以下为**完整方法片段**，保留原长度10、索引0、值5与x：

```csharp
static int ArrayOperations() {
    int[] arr = new int[10];
    arr[0] = 5;
    int x = arr[0];
    return x;
}
```

本机两编译器实际反查有newarr System.Int32、stelem.i4、ldelem.i4，返回5。原完整栈步骤保留为**IL教学形状**，局部编号、程序集限定名随上下文/编译选项变化：

```il
ldc.i4.s 10
newarr System.Int32
stloc.0
ldloc.0
ldc.i4.0
ldc.i4.5
stelem.i4
ldloc.0
ldc.i4.0
ldelem.i4
stloc.1
```

newarr的类型token是**元素类型**，不是数组类型token；原答“操作数必须是数组类型”写反。长度由计算栈提供，newarr创建一维零基向量。ldelem读取，stelem存储，ldlen取长度，ldelema取得相应元素地址；安全/可验证使用仍满足各操作码的类型规则，不是只要元素宽度4就可任意拿一个对象操作。[Newarr语义](https://learn.microsoft.com/en-us/dotnet/api/system.reflection.emit.opcodes.newarr?view=net-10.0)

另一原store例是int[]上的`arr[i] = 10;`，对应`stelem.i4`，保持原索引i和写入值10。其教学栈步骤是先加载数组引用、再加载int索引i、再加载常量10，最后由stelem.i4消费这三项并存储；这段语句以前面已初始化arr、已声明i且索引合法为条件，不是把store替换为固定0/5。

string的公共合同提供不可变字符串，也有加载字符串的`ldstr`指令，指定实现中的表示与GC/JIT支持可有专门处理；这些背景事实不意味着凡有专门处理的类型都必然禁止继承。

List<int>的`list[0]=5`通常是set_Item方法调用的IL，后续JIT可能内联/去掉相应开销；不能因看到call就证明一定“找方法表、巨大慢”。原ETC/VIP通道类比只说明不同IL表达形式，不保证最快或免一切检查。

<a id="c16-abstract-comparison"></a>
### 普通abstract可继承，Array的禁止是另规则

以下为**合法完整类型片段**，保留原MyAbstract、protected Foo与Derived override：

```csharp
abstract class MyAbstract { protected abstract void Foo(); }
class Derived : MyAbstract { protected override void Foo() { } }
```

开发者不需要父类源代码、所有实现细节或native地址才能继承可继承类型；metadata签名和相应语言规则足以支持通常的跨程序集派生。Array.Length/Rank/GetLength/GetValue/SetValue有完整API元数据，部分实现由运行时提供不意味着定义不完整、成员不可调用、所有方法都是extern或找不到base入口。

原**Array API形状**保留如下，不能把它当可重定义System.Array的源文件：

```text
public abstract class Array : ICloneable, IList, ICollection, IEnumerable
public int Length { get; }
public int Rank { get; }
public int GetLength(int dimension);
public object GetValue(int index);
public void SetValue(object value, int index);
```

原`public extern int Length {get;}`等“全extern”片段只是错误近似，正文采用真实API形状。无法重写Length的原因也不是不认识C++实现；需先看它是否是可覆盖的虚成员，而C#还独立禁止class MyArray:Array。

使用Reflection.Emit声明extends Array的普通类，本机两运行时CreateType都TypeLoadException。固定.NET 10 v10.0.0的类型加载实现还显式检查父类型是否为g_pArrayClass，是则抛TypeLoadException；这项特殊规则独立于Array.IsSealed标志，也没有以探索构造器IL是否能调用为唯一证据。[实际加载规则](https://github.com/dotnet/runtime/blob/v10.0.0/src/coreclr/vm/methodtablebuilder.cpp#L11504-L11513) 探索中的构造器IL未调用，没有执行假数组的Length或非法布局；这支持具体加载拒绝观察，不把“ILASM必在组装时拒绝”当已跑的结论。数组类型本身也不可作为普通派生基类，须区分Array这个class_type与int[]这个array_type。

<a id="c16-array-shape-table"></a>
### 原四种形状表

| 数组形状 | 元素/布局 | 索引处理 |
| --- | --- | --- |
| int[] | 连续int值元素 | 对应向量索引与长度条件 |
| string[] | 连续引用槽，字符串另为对象 | 引用存储须维持元素类型/GC写屏障等条件 |
| int[,] | 矩形二维形状与元素 | 使用维度长度/下界计算位置，不是“行×列”即可完整表达 |
| 非零基一维数组 | 通过Array.CreateInstance长度/下界描述 | 索引修正；原int[0..10]不是这种类型的合法C#声明 |

以下为**完整程序**，保留非零基主题并明确长度3、下界1、上界3：

```csharp
using System;
class Program {
    static void Main() {
        Array a = Array.CreateInstance(typeof(int), new[] { 3 }, new[] { 1 });
        Console.WriteLine(a.GetType());
        Console.WriteLine(a.GetLowerBound(0) + ":" + a.GetUpperBound(0));
        a.SetValue(10, 1);
        Console.WriteLine(a.GetValue(1));
    }
}
```

输出System.Int32[*]、1:3、10。现代`arr[0..10]`若在适当数组表达式上表示Range切片，也不等于声明一个非零基数组。

### 原四需求方案表与三个工厂类比

| 原需求 | 可选择的设计与条件 |
| --- | --- |
| 封装数组 | 自己的wrapper、List<T>/Collection<T>等，按契约决定暴露能力 |
| 访问一段存储 | 现代Span<T>/Memory<T>等，按生命周期/修改权/异步需求选择，不自动保证更快 |

原Array宪法/禁止修宪、Car/BMW与交通工具、生物与猫狗类比表达“运行时支持的特殊构造”与普通派生不同。但“父类不是你定义的，所以不能继承”不是规则；许多库基类本就供外部派生。乐高模板/工厂模具类比则强调受支持的布局，不证明任何额外字段都必让GC立即崩溃。

<a id="c16-class-array-table"></a>
### 原五维普通class与数组表

| 维度 | 普通class | 数组int[] |
| --- | --- | --- |
| 声明 | class定义产生相应metadata | 用数组类型语法/签名，不手写Int32Array class |
| 分配 | 普通new表达通常用newobj/构造器，实际分配可优化 | 向量new通常用newarr；其他形状有不同路径 |
| 元素访问 | 可用方法或索引器，JIT可内联 | 向量元素常用ldelem/stelem，维持相应语义检查 |
| 继承 | 按可见性/基类/sealed等规则，非自由任意继承 | 运行时数组以Array为基类，数组类型不供用户再派生 |
| 类型构造 | class的TypeDef与运行时加载分层 | 数组签名/需要token时的TypeSpec等由运行时解析构造，非普通class TypeDef |

原“数组是类型引用产物，因此编译器写TypeRef”不准确：数组在签名中有相应编码，需要表示constructed type token时可用TypeSpec；element自身的TypeRef/TypeDef与数组表示不同。数组和Array有真实类型关系，不能因为[]是特殊语法就否认OO类型系统，也不能把Span说成栈数组的同义词。

<a id="c16-newarr-type-flow"></a>
### 原长度5、helper伪汇编与完整流程图

原`int[] a=new int[5]; a[0]=5;`用newarr Int32创建向量，store5用stelem.i4。数组类型可以已经存在，或在相关类型解析/加载过程中获得；指令需要正确类型和实例，不保证“类型从未先存在”。

此处原长度5输入的**历史IL教学形状**完整保留为三步；mscorlib为Framework上下文，stloc.0假定a为第0局部，其他目标/编译选项的程序集限定名和局部编号可不同：

```il
ldc.i4.5
newarr [mscorlib]System.Int32
stloc.0
```

第一步将元素数量5压栈，第二步以元素类型Int32创建向量并将引用压回栈，第三步把该引用存入a。它是原长度5的独立例，不以先前长度10的IL替代。

原**helper概念伪汇编**表达请求长度5与相应类型信息，并非真实抓取：

```text
提供长度5及相应数组/元素类型信息
调用适当运行时分配辅助路径，或采用允许的内联/特化路径
确保所需类型已解析，按正确布局/对齐分配并建立零初始化元素
返回数组引用
```

具体CoreCLR helper可能接收数组类型handle，不能把固定ecx/edx寄存器、元素Int32 MethodTable与JIT_NewArr1函数原型当所有架构的真实ABI。原`lea target,[array_base+0x10+index*4]; mov[target],5`是x64某种引用/布局视角的地址示意，不是普遍固定偏移或忽略写屏障/类型约束的证明。

原完整图按相同阶段保留，并修正唯一触发/每次造类型的说法：

```text
C#：new int[5] + a[0]=5
       │                │
       ▼                ▼
IL：newarr Int32      stelem.i4
       │                │
       ▼                ▼
运行时：解析/使用int[]类型   JIT按已知数组布局和语义生成store
       │
       ├> 类型可已由typeof/签名/MakeArrayType等路径得到
       └> 分配该形状实例、长度5、默认元素值 → 返回引用
```

原对象大小“header+4+5×4=28字节”不能脱离位数、对象引用指向位置、完整对象头和对齐使用。元素数据20字节不等于完整对象20/28字节；具体大小是实现条件，正文不拿错误算式作实测。

原三角色表保留：

| 角色 | 是什么 | 与Int32[]的关系 |
| --- | --- | --- |
| newarr | 元素type token与栈上长度的IL指令 | 创建相应SZ实例，类型并非必须首次由执行该指令才出现 |
| Int32[] | 运行时数组类型，有类型结构与Array基类 | 无用户手写class定义，不等只有一个managed Type对象或唯一一条表记录 |
| ldelem.i4/stelem.i4 | 读取/存储相应整数数组元素的指令 | JIT可按已知布局实现；仍满足安全类型/索引语义，不称所有实现绝不读取任何类型信息 |

newobj Foo::.ctor的operand是构造器方法标识；MD/non-SZ数组也可通过相应构造/运行时API创建。语义不因newobj一定比newarr慢：JIT可内联、特化、去掉分配，必须按具体操作观察。

<a id="c16-interfaces"></a>
## 数组实现集合接口：首先撤销不存在的C#禁令

**int[]和string[]都可以隐式转换为System.Collections.IEnumerable、ICollection、IList。**数组本身是引用类型，转换接口视图不立即把每个int装箱，也不要求“写完整名字或显式cast表示愿承担代价”。Q11—16原答对此反复错误解释，后来只部分更正；本章统一采用真实语言规则。

<a id="c16-nongeneric-conversions"></a>
### 原int[10]、string[10]、is与显式cast

以下为**完整程序**，保留原10长度、三个非泛型接口、显式cast及is，修正原错误成功标记。原User `new int[10;`缺]是独立语法笔误，不是接口转换规则。

```csharp
using System;
using System.Collections;
class Program {
    static void Main() {
        int[] array = new int[10];
        ICollection collection = array;
        IEnumerable enumerable = array;
        IList list = array;
        ICollection explicitView = (ICollection)array;
        Console.WriteLine(collection.Count);
        Console.WriteLine(array is ICollection);
        Console.WriteLine(Object.ReferenceEquals(array, explicitView));
        string[] strings = new string[10];
        ICollection stringsView = strings;
        Console.WriteLine(stringsView.Count);
    }
}
```

输出10、True、True、10。Count可以读数组长度，不因此箱每个元素；非泛型枚举Current返回object时，int元素才涉及相应值到object转换。泛型int元素通常不需该object转换，仍不能说泛型接口“零所有性能损耗”。

<a id="c16-generic-interfaces"></a>
### 原int1、2、3与string a、b、c的泛型入口

下面是**完整程序**，保留原三泛型接口赋值和string入口，分别输出Count/首项：

```csharp
using System;
using System.Collections.Generic;
class Program {
    static void Main() {
        int[] intArray = { 1, 2, 3 };
        string[] strArray = { "a", "b", "c" };
        IEnumerable<int> ie = intArray;
        ICollection<int> ic = intArray;
        IList<int> il = intArray;
        IEnumerable<string> ie2 = strArray;
        Console.WriteLine(ic.Count);
        Console.WriteLine(il[0]);
        foreach (string x in ie2) Console.WriteLine(x);
    }
}
```

输出3、1、a、b、c。SZ数组支持IList<T>及相应基接口，Array本身提供非泛型契约；不是源文件里存在一个可以手写的`class Int32[] : Array, ...`。实现还可通过实际helper方法与运行时映射提供，不是所有Add/Remove只是“没有代码所以CLR凭空抛异常”。

<a id="c16-fixed-size-operations"></a>
### set_Item、Add、两种Clear不能混成一个定律

以下为**完整程序**，保留原修改首项10/Add4，并实测泛型/非泛型Clear的不同合同：

```csharp
using System;
using System.Collections;
using System.Collections.Generic;
class Program {
    static void Main() {
        int[] arr = { 1, 2, 3 };
        IList<int> list = arr;
        list[0] = 10;
        Console.WriteLine(arr[0]);
        try { list.Add(4); }
        catch (NotSupportedException) { Console.WriteLine("Add rejected"); }
        try { list.Clear(); }
        catch (NotSupportedException) { Console.WriteLine("generic Clear rejected"); }
        IList nonGeneric = arr;
        nonGeneric.Clear();
        Console.WriteLine(String.Join(",", arr));
        Console.WriteLine(arr.Length);
    }
}
```

输出10、Add rejected、generic Clear rejected、0,0,0、3。数组长度固定，但非泛型IList.Clear清内容而不改长度；原“Add/Remove/Clear全部改变长度所以一律不支持”错误。泛型接口IsReadOnly=True也不表示数组元素永远不能通过其索引设置；具体成员行为按数组实现契约看。[当前Array的IList实现](https://github.com/dotnet/runtime/blob/v10.0.0/src/libraries/System.Private.CoreLib/src/System/Array.cs)

<a id="c16-array-variance"></a>
### stringhello可作object序列，int不能靠自动逐元素装箱变型

以下为**完整程序**，保留hello引用场景与typed int反射检查：

```csharp
using System;
using System.Collections.Generic;
using System.Linq;
class Program {
    static void Main() {
        string[] strs = { "hello" };
        IEnumerable<object> objects = strs;
        Console.WriteLine(objects.First());
        int[] ints = { 1, 2, 3 };
        Console.WriteLine(ints.GetType().GetInterfaces().Contains(typeof(IEnumerable<int>)));
        Console.WriteLine(ints.GetType().GetInterfaces().Contains(typeof(IEnumerable<object>)));
        foreach (object o in ints) Console.WriteLine(o);
    }
}
```

输出hello、True、False、1、2、3。原foreach(object o in ints)本来可编译；它每个元素的object表示与把整个int[]直接赋给IEnumerable<object>是不同操作。

以下为**独立编译反例片段**，补using System.Collections.Generic：

```csharp
int[] ints = { 1, 2, 3 };
IEnumerable<object> objects = ints; // CS0029
```

值类型到object是装箱转换，不是泛型接口引用变型所需的引用转换；无需猜“CLR不愿偷偷box”的设计动机。DateTime[]也不能直接成为IEnumerable<object>；short[]到IEnumerable<int>不因short可数值加宽而成立。需要每元素转换时可以明确投影/装箱，不把它称为原数组同一个兼容视图。

原还列IEnumerable<IComparable>：int虽实现IComparable，int[]也不能通过逐元素自动装箱得到这种接口视图；它与非泛型IEnumerable合法转换不是同一前提。Array参数则可以接收各种数组，原`void Foo(Array arr)`签名利用的是Array基类引用转换。

### 原三数组接口表

| 数组 | 相应IEnumerable<T> | IEnumerable<object>视图 | Add |
| --- | --- | --- | --- |
| string[] | 支持string元素接口 | 支持相应引用兼容/变型 | 长度固定，Add不支持 |

<a id="c16-name-resolution"></a>
## CS0305是名称/类型实参问题，不是数组转换限令

System.Collections.ICollection是arity为0的非泛型类型；System.Collections.Generic.ICollection<T>需要一个类型实参。**同时using两个命名空间，短名ICollection可解析为非泛型接口，并不会优先猜成泛型而报CS0305。**

<a id="c16-both-using"></a>
### 原两个using、strs5与int10完整程序

以下为**完整程序**，保留原两个using、string5、int10、全限定名/泛型显式选择与var：

```csharp
using System;
using System.Collections;
using System.Collections.Generic;
class Program {
    static void Main() {
        string[] strs = new string[5];
        ICollection shortName = strs;
        System.Collections.ICollection fullName = strs;
        ICollection<string> generic = strs;
        var inferred = strs;
        int[] array = new int[10];
        ICollection ints = array;
        Console.WriteLine(shortName.Count);
        Console.WriteLine(fullName.Count);
        Console.WriteLine(generic.Count);
        Console.WriteLine(inferred.GetType());
        Console.WriteLine(ints.Count);
    }
}
```

本机旧C#5和现代.NET编译运行都成功，输出5、5、5、System.String[]、10。var推断为string[]，不是“选最合适的泛型接口”。全限定名能明确目标类型，但没有凭此触发“用户知情免性能拦截”的规则。

<a id="c16-import-variants"></a>
### only Generic、only Collections、无导入与原变量笔误

以下为**编译反例完整类型片段**：仅导入Generic，短名ICollection在此可见环境中指向需要实参的泛型名，报告CS0305；不是int元素造成，也不是两命名空间冲突。

```csharp
using System.Collections.Generic;
class Demo {
    void M() {
        int[] a = new int[10];
        ICollection c = a; // CS0305
    }
}
```

仅using System.Collections时，原`int[] a=new int[10]; ICollection c=a;`合法；只using Generic但写全限定System.Collections.ICollection也合法；完全不导入相应类型、无其他名字/global using时短名报告CS0246。原T把“only Generic”报成CS0246，又把“both using”报成CS0305，两处都需分别修正，不能把自述“我刚试过”当真实实验。

原User `string[] strs=...; ICollection collection=array;`还混用strs和array变量名；若array未声明是独立CS0103问题。修为collection=strs才能保持要讨论的string[]场景。`ICollection<> collection=...`是未提供类型实参的伪形状，不是可用的开放接口变量类型。

<a id="c16-generic-process"></a>
#### 原泛型Process与类型推断调用

原泛型例是另一可用合同，以下补足**完整类型片段**中的成员和调用上下文；空方法本身没有输出：

```csharp
using System.Collections.Generic;
class GenericProcessExample {
    void Process<T>(IEnumerable<T> items) { }
    void Example() {
        int[] array = new int[10];
        Process(array);
    }
}
```

这里从int[]到IEnumerable<int>的转换可推断T为int，不需显式写Process<int>。转换数组引用本身不会逐项装箱；若通过IEnumerable<int>/IEnumerator<int>按int读取元素，也无须把每个int转为object。原“用泛型，零装箱”只能按这些位置理解：空方法没有枚举，不能据此证明所有泛型调用、枚举器接口化和JIT路径都零分配或零性能成本。此片段已用历史C#5编译为库检查类型推断，不伪造它的运行输出。

[ArrayList.AddRange](https://learn.microsoft.com/dotnet/api/system.collections.arraylist.addrange)参数是ICollection；[Queue.Enqueue](https://learn.microsoft.com/en-us/dotnet/api/system.collections.queue.enqueue?view=netframework-4.8.1)参数是object，Array.Copy参数是Array等，不能说这些API都声明ICollection/IList。它们各有实际签名，数组可按对应规则传入，不需要把书的原说明解释成省略了某个不存在的C#限制。

原T还用`void Foo(object obj) { }`配`Foo(ints)`的空体形状只演示object参数接受数组：它本身没有输出，不需显式cast；上面的Foo增加Count观察是另一个已经完整保留的场景。

<a id="c16-foreach-paths"></a>
### 数组foreach、接口foreach与List模式

原`foreach(int i in intArray)`的直接数组静态类型可降为索引/Length遍历；以下保留**形状示意**：

```text
for (int i=0; i<intArray.Length; i++) {
    int value = intArray[i];
    // 原foreach体
}
```

而`IEnumerable<int> ie=intArray; foreach(int i in ie)`是接口枚举形态，实际编译有GetEnumerator/Current/MoveNext/Dispose调用。其中`IEnumerable<int> ie=intArray`是普通隐式接口引用赋值；原注释称“强制转换”不准确，该语句没有显式cast。List<int>静态视图也按相应枚举器模式，而不必都先转IEnumerable接口。

以下完整保留原list模式的**展开形状示意**：先取得枚举器，循环MoveNext取得Current，离开using时负责Dispose；原空循环体仅取出x，没有打印结果。

```text
using (var enumerator = list.GetEnumerator())
{
    while (enumerator.MoveNext())
    {
        var x = enumerator.Current;
    }
}
```

它适用于这里具有相应GetEnumerator/Current/MoveNext与Dispose合同的List<int>模式，不是全部foreach实现的统一展开，也不提供性能保证；数组上面的for形状与其他枚举器的Dispose规则分别判断。

原1000个int非泛型读取场景保留为**方法体片段**：

```csharp
int[] ints = new int[1000];
System.Collections.ICollection c = ints;
foreach (object o in c) { /* 使用o时有对应int对象表示 */ }
```

未跑它的速度基准；不能从元素箱语义推定一律巨大成本，也不能把IEnumerable返回值说成编译器自动恢复原数组for路径。实际两编译器IL反查：数组循环ldelem/ldlen，接口/List循环有对应枚举方法call；JIT后续可进一步优化，IL不等实际耗时。

<a id="c16-special-cases"></a>
### “特判”与AOP的类比如何用

原new/foreach/cast、string+、delegate闭包、Span遍历等并非同一层“拦截器”。语言绑定/lowering、JIT优化、运行时类型规则与API实现应分开。AOP可通过代理、改写等实现，ASP.NET管道又是应用行为；不能统称都比托管if-else更快且没有分支预测失败。

字符串+可生成适当Concat等表达，不保证自动换成StringBuilder；业务需要的类型判定也不一概是坏代码。数组引用协变与泛型接口in/out规则不同，现代泛型接口并非“通用不支持变型”。Span在某些编译器/静态形态可有特殊处理，不能凭“后来设计”断言所有foreach固定同一种机器码。

<a id="c16-passing"></a>
## 数组参数：默认复制引用的值，修改元素与重绑引用不同

数组不是唯一“定长但元素可改”的引用对象；这里的关键是变量与对象分开。默认参数按值传递，数组引用的值被复制到形参，双方可以引用同一个数组；形参重新赋值不会重绑调用方的普通变量。ref/out才涉及相应变量槽的不同传递规则，不能由数组是引用类型就推成默认参数为ref。

<a id="c16-change-reset"></a>
### 原ChangeArray100、Length3与Reset0

以下为**完整程序**，保留原1、2、3→首项100/形参新长度5的例，以及另一ResetFirstElement0例：

```csharp
using System;
class Program {
    static void ChangeArray(int[] arr) {
        arr[0] = 100;
        arr = new int[5];
    }
    static void ResetFirstElement(int[] arr) { arr[0] = 0; }
    static void Main() {
        int[] a = { 1, 2, 3 };
        ChangeArray(a);
        Console.WriteLine(a[0]);
        Console.WriteLine(a.Length);
        int[] myArray = { 1, 2, 3 };
        ResetFirstElement(myArray);
        Console.WriteLine(myArray[0]);
    }
}
```

输出100、3、0。原“arr换新数组后原数组完全不受影响”只针对重绑步骤；此前写100已经修改原数组，两个操作顺序不能省掉。是否允许方法修改数据应在API合同中说明；不是每个改变元素的工具方法都必污染或违反封装。

<a id="c16-print-and-store"></a>
### 原a/b读取与new object写入分开

以下为**完整程序**，保留T的PrintObjects a、b，以及正式答的string[2]写入失败两种输入：


<a id="c16-fill-buffer"></a>
### FillArray、FillFirstThree与Stream.Read长度契约

以下为**完整程序**，保留T填满数组的循环和固定填前三项的不同前提：

```csharp

    static void FillFirstThree(int[] arr) { arr[0]=1; arr[1]=2; arr[2]=3; }
```

```csharp
using System;
```

<a id="c16-return-raw"></a>
## 返回数组：共享、快照与可访问API合同

返回内部数组可以有意允许共享修改，不能无依据称“90%bug来源、永远致命错误”。若要保护私有状态，就不能只靠private字段修饰符或把返回类型写成接口；先决定是否交出共享修改权、只读视图或独立数据。

下面完整保留User分数的IEnumerable返回场景，为**完整程序**。附带安全可重复的cast测试，揭示原“调用方只能遍历所以内部绝不会被改”缺少的条件。

<a id="c16-readonly-wrapper"></a>
### 原ReadonlyCollection分数与live view

以下为**完整程序**，保留原User返回ReadOnlyCollection<int>，明确原setter注释到底是编译错误还是运行异常：

```csharp
using System;
using System.Collections.Generic;
using System.Collections.ObjectModel;
class User {
    private int[] _scores = { 90, 85, 95 };
    public ReadOnlyCollection<int> GetScores() { return Array.AsReadOnly(_scores); }
    public void ChangeFirst(int score) { _scores[0] = score; }

class Program {
    static void Main() {
        User u = new User();
```

### 原Clone分数与三种T方案

以下为**完整程序**，保留原分数Clone、外部改0与内部仍90；原等价Array.Copy方式保留为另一实现方法，两个都返回新数组。

```csharp
    static void Main() {
        User u = new User();
        int[] scores = u.GetScores();
        scores[0] = 0;
        Console.WriteLine(u.GetScores()[0]);
        int[] another = u.GetScoresByCopy();
        another[0] = 0;
        Console.WriteLine(u.GetScores()[0]);

```

两行90。以下为**完整类型片段**，保留T的GoodClass1/2/3、相同1、2、3数据与三个不同返回合同，不能只留正式分数例代替：

```csharp
using System;

using System.Collections.ObjectModel;
class GoodClass1 {
    private int[] _data = { 1, 2, 3 };
    public int[] GetData() { return (int[])_data.Clone(); }

class GoodClass2 {

class GoodClass3 {
```

<a id="c16-new-return"></a>
### 原新数组返回与String.Split/List.ToArray

原GetNewScores与T GetNewArray是**完整类型片段**，分别保留90/85/95和1/2/3：

```csharp

    public int[] GetNewArray() { return new int[] { 1, 2, 3 }; }

```

新创建、准备交给调用方拥有的数组无需为了“返回数组”再复制一遍。共享内部数组也可以是明确API合同，不是全世界只允许这一种返回情况。

String.Split返回字符串结果数组，调用方更换数组槽不改变原string；List<T>.ToArray复制槽，改int槽不改原List，但引用对象内部的修改仍可共同看到。这里保留原非空教学输入；“返回新结果”不保证每次得到不同数组对象。固定.NET 10 v10.0.0实现中，非空List的ToArray执行new及Copy，空List返回共享s_emptyArray；String.Split的count为0时可返回Array.Empty<string>()。空数组没有可修改元素槽，这不影响本节保护原状态的目的，也不能将该实现观察倒写为所有历史版本的分配保证。[List.ToArray实现](https://github.com/dotnet/runtime/blob/v10.0.0/src/libraries/System.Private.CoreLib/src/System/Collections/Generic/List.cs#L1049-L1060)、[Split空结果路径](https://github.com/dotnet/runtime/blob/v10.0.0/src/libraries/System.Private.CoreLib/src/System/String.Manipulation.cs#L1654-L1672) 原“List.ToArray怎么改都不影响原List”只在槽替换/相应值元素条件下成立；未查证的“早期_items从未暴露所以设计只有这个动机”不当历史事实。现代还有显式暴露存储视图的API，它们采用不同的调用契约。

<a id="c16-unsafe"></a>
## unsafe、fixed、stackalloc与固定大小缓冲区

unsafe允许相应指针上下文；fixed语句在期间固定相关可移动存储；stackalloc为方法执行期间取得栈存储。三者不是同一个“关闭全部安全检查”的按钮。普通arr[i]在fixed块内仍保持托管索引语义；原复杂循环一定更快、每帧百万像素必须unsafe等说法没有本章速度证据。

<a id="c16-fixed-original"></a>
### 原1、2、3、4、5的fixed指针遍历

以下为**完整程序**，保留原全部元素、pin作用域和指针访问；需/unsafe。

```csharp
using System;
class Program {
    unsafe static void Main() {
        int[] arr = { 1, 2, 3, 4, 5 };
        fixed (int* p = arr) {
            for (int i=0; i<arr.Length; i++) Console.WriteLine(*(p+i));
        }
    }
}
```

输出1、2、3、4、5。p指向首元素数据，不是数组对象头；GC可在合适的压缩过程中移动可移动对象，托管引用可被维护，而未经管理的旧指针不能据此自动跟随。不是每次GC都搬全部对象，fixed也不是锁定业务线程或让其他线程不能修改元素。

原**危险反例方法体**保留如下，只有编译/语义核验，未执行越界写入：

```csharp
fixed (int* p = arr) {
    *(p + 100) = 999; // 编译可接受，但超出原5元素存储；禁止据示例运行
}
```

错误可能破坏数据、导致后续故障或其他行为，不能保证每次立即“炸”。另一个受控例在fixed内执行普通arr[100]，两运行时都IndexOutOfRangeException，证明pin不关闭普通数组检查。

<a id="c16-stackalloc-squares"></a>
### 原5个int先写平方再读

以下为**完整程序**，保留原两循环和0、1、4、9、16。不要省略先初始化的教学步骤。

```csharp
using System;
class Program {
    unsafe static void Main() {
        int* p = stackalloc int[5];
        for (int i=0; i<5; i++) p[i] = i*i;
        for (int i=0; i<5; i++) Console.WriteLine(p[i]);
    }
}
```

新stackalloc存储的内容未定义，不可没初始化就拿来读。栈存储与普通new数组默认元素初始化不同；大尺寸/循环内重复stackalloc也需考虑栈使用，不能把所有线程可用栈写死为1MB或把它当保证最快。

<a id="c16-stack-table"></a>
### 原new与stackalloc四维表

| 维度 | new int[5] | stackalloc int[5] |
| --- | --- | --- |
| 分配 | 托管数组表示与相应GC分配/初始化；未测固定速度 | 方法栈存储，可能受大小/代码形态影响；不保证只有一条移动栈指针 |
| 回收/释放 | 按可达性与GC过程，变量作用域结束不等立即回收 | 生命周期受当前方法执行与引用安全规则限制，不能把指针带走后继续读 |
| 生命周期 | 合法引用可使数组继续存活 | 取得的局部栈存储不能作为有效逃逸数据使用 |
| 容量约束 | 受数组限制/内存/运行时条件 | 受实际可用栈与分配模式约束，非普遍1MB保证 |

<a id="c16-pointer-escape"></a>
### 原GetPtr反例编译接受，不等于安全

以下为**危险类型片段**，两运行时编译器接受，原“必有警告/错误”不成立；仅编译，没有调用返回后解引用。

```csharp
class Demo {
    unsafe int* GetPtr() {
        int* p = stackalloc int[5];
        return p; // 编译接受，但返回后不能继续将该栈地址当有效存储使用
    }
}
```

裸指针不受与Span相同的引用安全逃逸检查；编译成功不能改变栈存储生命周期。不能用“编译器会兜底”代替这个反例的说明。

<a id="c16-span-stackalloc"></a>
### 原Span0=1与ProcessSpan完整现代上下文

以下是**现代C# 7.2/7.3以后相应语言/BCL条件的完整程序**，本机C#14/.NET10验证，非原Framework自带Span。保留span[0]=1/ProcessSpan：

```csharp
using System;
class Program {
    static void ProcessSpan(Span<int> span) { Console.WriteLine(span[0]); }
    static void Main() {
        Span<int> span = stackalloc int[5];
        span.Clear();
        span[0] = 1;
        ProcessSpan(span);
    }
}
```

输出1，访问与生命周期受Span规则约束，不要求unsafe。Span也可以引用托管数组等存储，不是类型名就保证“栈上的数组”。本机返回局部stackalloc Span的负例CS8352，与前节裸指针编译接受形成对照；本章不把Span说成完全复制了所有数组接口/持有方式。

<a id="c16-fixed-buffer"></a>
### BadStruct数组引用与C内嵌数组

原“struct不能定义数组”错误，以下为**合法类型片段**，字段存的是数组引用，并非内嵌5个int：

```csharp
struct BadStruct { public int[] Arr; }
```

BadStruct值副本会复制引用；更改副本引用所指数组的元素，可被原值观察。本机辅助例观察修改后原读21。引用槽大小与位数/布局有关，原8字节仅某x64条件，不是任何struct/interop表示保证。

原C/C++的**声明片段**保留内嵌Arr[5]语义：

```cpp
struct MyStruct { int Arr[5]; };
```

在相应native int为4字节的声明条件下，这些元素直接占20字节，不是另一个托管数组对象的引用。

<a id="c16-goodstruct-original"></a>
### 原GoodStruct Arr5加Value与未整初始化局部

以下为**完整程序**，保留原GoodStruct、固定5int、Value、局部s未整体初始化、只写首项/Value后sizeof的条件；需/unsafe。

```csharp
using System;
using System.Runtime.InteropServices;
[StructLayout(LayoutKind.Sequential)]
unsafe struct GoodStruct {
    public fixed int Arr[5];
    public int Value;
}
class Program {
    unsafe static void Main() {
        GoodStruct s;
        s.Arr[0] = 10;
        s.Value = 20;
        Console.WriteLine(sizeof(GoodStruct));
    }
}
```

本机旧C#5和现代编译都接受，sizeof为24。原程序没有读取其余未赋值元素，不能误报它必编译失败；辅助验证额外读已赋值首项为10。fixed-buffer声明按支持的类型/布局工作，不能把“比普通托管数组少检查”变成已测速度优势。

<a id="c16-unmanaged-marshalling"></a>
### unmanaged、blittable与P/Invoke不是一个条件

指针/stackalloc要求相应unmanaged类型，fixed-buffer字段有专门支持列表；不等于全部必须按默认封送blittable。bool可用作这里的栈/固定缓冲区元素，本机sizeof(bool)=1，bool[5]缓冲为5；无引用Point也可stackalloc，辅助例字段和7。引用string不能当同样unmanaged元素，只是这些要求的一部分。

P/Invoke可以声明托管数组参数并由合适的封送约定转换/固定，native函数接收指针不意味着调用方必手工写unsafe。结构体内嵌native数组也有ByValArray/SizeConst等另一类封送设计；其托管字段仍为引用表示，不能混成GoodStruct直接托管布局，也不能写“只有fixed否则必错位”。未执行真实native DLL/设备业务。[数组封送](https://learn.microsoft.com/en-us/dotnet/standard/native-interop/default-marshalling-for-arrays)

```csharp
using System;
```
