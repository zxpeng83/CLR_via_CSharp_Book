<a id="c23-loading"></a>
## 程序集如何进入执行环境

通常托管执行中，JIT/类型解析会按IL token、TypeRef/AssemblyRef等关联定位所需定义并触发绑定/加载。并非每条引用都只能是TypeRef（本模块定义、泛型TypeSpec等也有各自token），也不代表JIT逐条解释IL。Assembly.Load是应用程序显式按身份加载的入口；不能把概念联系简化为“每次CLR必先调用这一public managed方法”，或与Win32 LoadLibrary完全等同。

<a id="c23-load-name"></a>
Assembly.Load(AssemblyName/string)按程序集身份请求加载，字符串不是任意文件路径。原SomeLib、MyLib与Plugin.dll输入分别保留：`Assembly.Load("SomeLib")`/`Assembly.Load("MyLib")`要求名称可按当前策略解析；原`Assembly.Load("Plugin.dll")`把文件名当身份不正确，通常应为`Assembly.Load("Plugin")`或路径入口`Assembly.LoadFrom("Plugin.dll")`。本机两环境实际Plugin.dll名称请求FileNotFound、正确路径/已可解析的Plugin简单名成功。

<a id="c23-framework-binding"></a>
Framework传统绑定先确定版本策略、查看已绑定/失败缓存，再按适用合同查GAC（强名称），指定codeBase若有优先检查，随后才按应用基目录、culture、私有子目录等probing。原“先GAC→基目录/私有路径→最后codebase”的次序需纠正；codeBase指定位置不存在/不匹配可能直接绑定失败，不保证再一路找完。弱名称不按强名称的版本策略/GAC机制处理。现代.NET没有这套完整Framework GAC/绑定重定向模型，应按ALC和宿主依赖解析看。[Framework实际查找步骤](https://learn.microsoft.com/en-us/dotnet/framework/deployment/how-the-runtime-locates-assemblies)

<a id="c23-load-contexts"></a>
原各入口的不同用途保全：LoadFrom按位置，在Framework可涉及URI/权限等历史条件；LoadFile可在不同绝对路径加载相同身份的文件并产生不同类型身份；ReflectionOnlyLoad/From在Framework的只读反射上下文分析而不执行目标代码，现代.NET不支持同入口，不能把现代PNSE倒判历史错误。Load(byte[])可以从内存字节建立加载实例，但不是免费解决依赖与身份问题。

LoadFrom存在同加载上下文身份缓存的重用合同，不是每次新对象；原“必先GetAssemblyName，再public Assembly.Load，找不到再path”的实现描述不能当真实CLR4调用链。Framework参考实现public LoadFrom实际调用RuntimeAssembly.InternalLoadFrom，绑定/路径/身份策略在内部处理。[真实Framework源码](https://raw.githubusercontent.com/microsoft/referencesource/main/mscorlib/system/reflection/assembly.cs)、[加载上下文及多身份风险](https://learn.microsoft.com/en-us/dotnet/framework/deployment/best-practices-for-assembly-loading)

作者受控同字节Plugin两个路径：LoadFile同绝对路径复用、不同路径得到不同实例/Type且FullName相同；两次Load(byte[])同FullName但不同实例/Type。混用LoadFile后的Framework探针LoadFrom两个路径返回不同引用，而现代探针相同；另新进程仅LoadFrom对照，两次请求路径分别为scope-a/Plugin.dll与copy/Plugin.dll，两环境返回相同引用/Type；实际Location在Framework两次都为scope-a/Plugin.dll，在.NET10两次都为夹具根目录Plugin.dll，请求路径不能当作真正选中的文件位置。全部真实顺序/输出保留，不能把不同上下文/绑定历史当完全同输入来保证任何路径总合并或总重复。原“相同标识多次”须加不同路径/上下文条件，不把同一路径缓存说没了。

<a id="c23-resolve"></a>
### 嵌入依赖与AssemblyResolve

原可把DLL作为嵌入资源、从资源流取byte[]后Assembly.Load，并在失败绑定的AssemblyResolve事件提供解析。它处理“未能找到请求程序集”，不是Unload的清理通知；应按请求名称返回匹配程序集/不认识时null，并避免处理函数再次触发同一失败绑定造成递归。单文件部署也须处理实际依赖/资源/平台合同，不是所有程序嵌一个DLL就只需一个文件。

作者补充两环境夹具将MyLib.dll资源放在不含该磁盘DLL的宿主目录，实际打印resolve:MyLib、loaded:MyLib、type:UserService；这是受控资源解析，不是现场数据库/插件下载或Unload触发。[解析失败绑定](https://learn.microsoft.com/en-us/dotnet/standard/assembly/resolve-loads)

## 导读中的类型发现、构造与成员入口

原23.3.1用Assembly.ExportedTypes发现对外可见类型，public nested还要所属外层可见等条件；GetTypes是该程序集类型视图，范围不同，遇依赖加载失败可能抛ReflectionTypeLoadException。名称须按真实CLR类型/namespace/解析范围：Type.GetType("int")不会把C#关键字自动翻译成Int32，当前返回null；Type.GetType("System.Int32")可取得相应类型。原“反射字符串调用缺编译时类型保证”指查找/参数错误推迟至运行时，不表示runtime完全不核类型安全。

<a id="c23-construct"></a>
原23.3.4各入口分别保：Activator.CreateInstance(Type,...)返回所构造对象；指定assemblyName+typeName等string重载可返回ObjectHandle并Unwrap，不是任意单一字符串都有该重载。AppDomain.CreateInstanceFrom指定相应域/位置的历史构造合同，当前域兼容方法也可能仍支持；ConstructorInfo.Invoke直接调用合适构造器；Array.CreateInstance创建数组（不自动构造每个引用元素）；MethodInfo.CreateDelegate建立合适签名/目标的委托。这些是不同对象/数组/委托用途，不说都是同一种类ctor入口。

作者实际两环境Type构造UserService、ConstructorInfo构造、数组长2且首元素null、typed PrintUser委托成立；CurrentDomain.CreateInstanceFrom两环境也返回UserService。Framework在外部path ctx已载后按名称Activator仍FileNotFound，现代此夹具可按名取ObjectHandle；名称可解析是前提，不凭原路径已载就保证name API一定成功。首轮遗漏catch的退出日志保留，只包catch完成剩余观察；未把现代旧名字API一概判PNSE。

<a id="c23-member-flags"></a>
原23.5.1—3用GetMembers/MemberInfo派生类（FieldInfo、MethodInfo、PropertyInfo等）发现成员；BindingFlags选择Public/NonPublic、Static/Instance、DeclaredOnly等范围，适当组合须指定所需访问与实例/静态类别。Type.GetInterfaces发现实现的接口（可含继承接口），与IsAssignableFrom做相容判定不同。原23.5.5缓存具体成员后多次调用、23.5.6句柄缓存分别关注查找与保存成本，后面各原例具体说明。

## 元数据是类型说明书，也包含程序集清单信息

原Word文档类比保留：正文像IL方法体，作者/创建时间/样式等描述信息像元数据。这是说明“描述数据的数据”，不是说程序集使用Word文件格式或所有这些文档属性都对应CLR标准列。

CLR元数据可描述类/接口/struct/enum/delegate定义、字段/方法/属性/事件、访问权限、签名、类型/程序集引用等。它包含表、签名blob、字符串等heap及索引关联，不只是每行都能一对一包装成一个MemberInfo。运行时内部缓存/类型信息也参与反射；GetMembers既可涉及继承和合成视图，反射Invoke还实际执行成员，不能把所有反射操作都定义成纯扫几张磁盘表。

<a id="c23-metadata-tables"></a>
原九项表逐项保留，定义类表的实际CLI名称与原教学别称分列说明：

<a id="c23-metadata-tables-detail"></a>
| 表名 | 存的内容 |
| --- | --- |
| Module（原称ModuleDef） | 模块定义 |
| **TypeDef**​ | 类型定义（类、接口等） |
| Field（原称FieldDef） | 字段定义 |
| **MethodDef**​ | 方法定义 |
| **MemberRef**​ | 成员引用 |
| **AssemblyRef**​ | 程序集引用 |
| **TypeRef**​ | 类型引用 |
| Assembly（原称AssemblyDef） | 当前程序集的定义 |
| ... | 共几十张表 |

TypeDef行可含名字、namespace、基类coded index、flags与字段/方法列表起点；TypeRef/AssemblyRef帮助解析外部定义，TypeSpec处理构造类型等。表是模块级元数据，程序集可含一个或多个模块（多模块执行是Framework历史功能，现代不支持同执行模型）。原“几十张表”是概览，本稿不扩大为完整ECMA表目录。

<a id="c23-manifest"></a>
原程序集构成ASCII保留为教学视图，清单栏明确属于元数据，避免四项互斥相加误解：

```text
程序集 (.dll / .exe)
├── 清单元数据 (Manifest)        ← 程序集的"身份证"：名称、版本、文化、公钥、入口点
├── 其它元数据 (Metadata)      ← 类型的详细描述（一堆表）
├── IL 代码                ← 方法体里的实际指令
└── 资源 (Resources)       ← 图片、字符串表等嵌入资源
```

Manifest中的名称、版本、culture、公钥、文件、导出类型/依赖关系等是程序集级元数据，不是在Metadata之外的另一块完全互斥物。托管入口token/标志还涉及CLR header，不能把所有“入口点”塞成Assembly表一列。常见单文件程序集在PE内含元数据/IL/资源；资源可以为空，程序集也可仅manifest/引用描述或动态生成，并非任何assembly必有四份实体内容。[程序集清单定义](https://learn.microsoft.com/en-us/dotnet/standard/assembly/manifest)

<a id="c23-il-view"></a>
可用合适的ILDasm类工具打开托管DLL，观察类型、字段、方法声明及方法体的可读表示；dotnet-ildasm需要另有可用工具，不能将这一步泛化到任意本机DLL。下面是原Person的观察示意。

原Person ILDasm形状完整保留，含mscorlib引用、Name后备字段与getter；花括号省略号是示意，不当可直接汇编的完整IL：

```il
// 元数据里的 TypeDef 表（节选）
.class public auto ansi beforefieldinit MyApp.Person
    extends [mscorlib]System.Object
{
    // 字段（FieldDef 表的记录）
    .field private string '<Name>k__BackingField'

    // 方法（MethodDef 表的记录）
    .method public hidebysig specialname instance string
        get_Name() cil managed { ... }
}
```

它是IL汇编器/反汇编器的可读表示，既有类型/字段/方法声明，也有方法体；不能说“完全不是代码”，更不能说dotnet-ildasm必已安装。元数据语言中立使C#/VB.NET等可按CLI合同互操作，compiler能从引用元数据认识类型而不需C++式头文件；实际源码互操作还受CLS/签名/可见性约束。GC可利用运行时由类型描述构建的引用布局跟踪对象，不是在每轮GC直接扫TypeDef字符串；serializer、IDE、debugger也会消费适当元数据/运行时信息。

<a id="c23-offline-metadata"></a>
“需要反射一个类型，通常先让包含它的程序集在对应执行/分析上下文可用”不等“元数据不可能脱离程序集存在、必须先正常执行加载全文件”。独立netmodule有元数据/IL而没有Assembly manifest；PEReader/MetadataReader可离线读取PE或独立metadata image，Framework ReflectionOnly/现代MetadataLoadContext也有自己的分析模型。本任务未安装MetadataLoadContext。

实际补充：Framework compiler生成StandaloneModule.netmodule，离线reader见IsAssembly=False、两TypeDef/两MethodDef/两IL body；两MyLib各四TypeDef/七MethodDef。FromMetadataImage从字节描述读取同类型数，读完GetAssemblies中MyLib/StandaloneModule均False。它证明不用正常运行加载目标即可分析，并不证明文件所有页同时物理驻留。[模块编译](https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/compiler-options/output#outputtype)、[元数据image入口](https://learn.microsoft.com/en-us/dotnet/api/system.reflection.metadata.metadatareaderprovider.frommetadataimage?view=net-10.0)

## 第22章提供运行环境，第23章操作加载与类型

原舞台/表演与容器/内容物两个类比保留：Framework宿主启动CLR，域组织相关程序集，反射在相应范围发现/使用类型。现代单AppDomain/ALC范围见第22章，不能说现代几乎所有API仍隐藏传统多域机制。

原总体链图保A/B/C三个程序集和插件域输入：

```text
Windows 进程
   └─ CLR (通过寄宿加载，第22章 22.1)
         ├─ 默认 AppDomain (第22章 22.2)
         │     └─ 程序集 A ──┐
         ├─ 插件 AppDomain 1 │← 程序集在这里加载 (第23章 23.1)
         │     └─ 程序集 B ──┤   Assembly.Load / LoadFrom
         └─ 插件 AppDomain 2 │
               └─ 程序集 C ──┘
                    ↓
            用反射发现类型、构造实例 (第23章 23.2~23.5)
                    ↓
            跨 AppDomain 通信 (第22章 跨越边界)
                    ↓
            AppDomain.Unload 卸载 (第22章 22.3)
```

原回顾五宿主用途——提供内存/加载/安全/线程协调管理器、初始化启动、执行程序集、管理生命周期、Stop——按Framework具体接口理解，不等任意Windows进程可无条件把任意CLR版本随便拔插。ASP.NET用应用域组织应用，virtual directory只有配置成相关application等时才进入该模型，并非任意虚拟目录各一域；SQL托管存储过程与自写宿主是另两个原例。

原四能力表与22章导读表用于不同串联场景，仍完整保留；历史权限机制与当前CAS不再认可安全边界均见表注：

<a id="c23-bridge-domain-table"></a>
| 特性 | 说明 |
| --- | --- |
| **隔离**​ | 类型安全托管代码按封送/合同跨域，非OS内存故障屏障 |

<a id="c23-domain-load"></a>
### 想在别的域加载，为何不直接取回Assembly

原AppDomain.Load提醒成立于Framework：从B调用代表A的域对象Load，程序集可能在两域都要加载；Assembly不派生MarshalByRefObject，返回表示需在调用方按其策略重新定位，可能FileNotFound或绑定到不同产物。它不是“只在目标域放进去但调用方什么都不用”的透明加载器。优先在目标域的MarshalByRef loader内部执行适当Assembly.Load/From，向调用方暴露合适合同。[AppDomain.Load双域合同](https://learn.microsoft.com/en-us/dotnet/api/system.appdomain.load?view=netframework-4.8.1)

<a id="c23-plugin-domain"></a>
原完整拼图保留：创建PluginDomain(含setup)→其中创建Mbr loader→path加载插件→Activator创建→转IPlugin→与宿主交流。图不能保证IPlugin任意对象都自动封送：

```text
默认 AppDomain (宿主)
    │
    │  1. 创建独立 AppDomain
    ▼
插件 AppDomain
    │
    │  2. 创建宿主的 MarshalByRefObject 派生类型实例
    ▼
宿主代理对象 (在插件 AppDomain 中)
    │
    │  3. Assembly.LoadFrom 加载插件 DLL
    │  4. Activator.CreateInstance 构造插件类型
    │  5. 转型为已知接口 IPlugin
    ▼
IPlugin 实例
    │
    │  6. 通过代理返回接口引用给默认 AppDomain
    ▼
宿主代码通过 IPlugin 接口调用插件
```

共享接口只是调用合同。跨Framework域时，按值封送（Marshal-by-Value）会将满足序列化合同的对象序列化，再在目标域重建一份副本；两域操作的是各自的对象。按引用封送则让MarshalByRefObject原对象留在其所属域，调用方通过代理调用它。返回插件实例必须满足其中适当的封送合同，也可以仅让远端loader代为调用、不返回实例。作者补充普通IPlugin实现返回时SerializationException；Mbr+IPlugin则透明proxy=True，Name为PluginDomain且Activate执行。现代同进程不同ALC的接口调用不使用这个Remoting代理模型，真实合同Type身份仍要共享。

原六对应关系表逐项保留，最后AssemblyResolve不再冒卸载清理：

<a id="c23-bridge-relations-table"></a>
| 第 22 章概念 | 第 23 章对应物 | 串联关系 |
| --- | --- | --- |
| CLR 寄宿 | JIT 编译时读 AssemblyRef 元数据表触发加载 | 寄宿启动 CLR → CLR 才有能力加载程序集 |
| AppDomain 是程序集容器 | `Assembly.Load` 把程序集加载进 AppDomain | 容器决定了程序集的隔离边界 |
| AppDomain 不能单独卸载程序集 | 插件 DLL 加载后常驻 | Framework适当插件域卸载是卸程序集的一种组织方式；不保证所有资源立即释放 |
| 跨 AppDomain 通信：MarshalByRefObject | 插件类型转型为已知接口 | 已知接口 + 合适MarshalByRef合同可普通代理调用；未测高性能差值 |

## 原彩虹猫例是一个假想.NET宿主

原以VS Code、C#扩展、Python扩展、GitLens和彩虹猫讲“宿主编译时不知道未来具体插件”的目的保留，但真实VS Code扩展入口是JS/TS与package.json/Extension API，在local/remote Node.js或web extension host运行，不能称其扫描C# DLL并执行本例IPlugin。1.0发布是2016-04-14，原2015年份不准。后续RainbowCatPlugin.dll代码用作**原假想.NET插件宿主教学例**，不要求把它放真实VS Code extensions即可运行。[真实扩展入口](https://code.visualstudio.com/api/get-started/extension-anatomy)、[Extension Host](https://code.visualstudio.com/api/advanced-topics/extension-host)、[1.0发布](https://code.visualstudio.com/blogs/2016/04/14/vscode-1.0/)

<a id="c23-unknown-type"></a>

<a id="c23-exception-A"></a>
原完整递归树/ArgumentNullException链代码保留并修重复末端Object、缺using；这是**原例修订**，输出数与版本相关，源Where实际还包括Exception自身：

```csharp
using System.Reflection;
using System;
using System.Collections.Generic;
using System.Linq;

class Program
{
    static void Main()
    {
        // 第1步：拿到 Exception 所在的程序集
        Assembly coreAssembly = typeof(Exception).Assembly;

        // 第2步：找出所有具体的（非抽象）Exception 派生类
        var allExceptions = coreAssembly.GetTypes()
            .Where(t => t.IsClass 
                     && !t.IsAbstract 
                     && typeof(Exception).IsAssignableFrom(t))
            .ToList();

        Console.WriteLine($"共找到 {allExceptions.Count} 种异常类型\n");

        // 第3步：构建父子关系字典（层次结构）
        // Key = 父类型, Value = 直接子类列表
        Dictionary<Type, List<Type>> hierarchy = new Dictionary<Type, List<Type>>();

        foreach (var exType in allExceptions)
        {
            Type parent = exType.BaseType;
            if (parent == null) continue;

            if (!hierarchy.ContainsKey(parent))
                hierarchy[parent] = new List<Type>();
            
            hierarchy[parent].Add(exType);
        }

        // 第4步：从 Exception 开始，递归打印整棵树
        PrintTree(typeof(Exception), hierarchy, 0);

        // 额外演示：打印某个具体类型的完整继承链
        Console.WriteLine("\n===== 单个类型的继承链 =====");
        PrintInheritanceChain(typeof(ArgumentNullException));
    }

    /// <summary>
    /// 递归打印异常层次树
    /// </summary>
    static void PrintTree(Type parent, Dictionary<Type, List<Type>> tree, int depth)
    {
        Console.WriteLine($"{new string(' ', depth * 2)}{parent.Name}");

        if (tree.ContainsKey(parent))
        {
            foreach (var child in tree[parent].OrderBy(t => t.Name))
            {
                PrintTree(child, tree, depth + 1);
            }
        }
    }

    /// <summary>
    /// 打印某个类型的完整继承链（从自身一直到 object）
    /// </summary>
    static void PrintInheritanceChain(Type type)
    {
        Type current = type;
        while (current != null)
        {
            Console.WriteLine(current.FullName);
            current = current.BaseType;
            if (current != null) Console.WriteLine("  ↑ 继承自");
        }

    }
}
```

### 原ORM两个缓存方案及可用修订

原BadEntityMapper/GoodEntityMapper完整错误对照保1000×10目的、CacheProperties与MapToDb形状；缺using与不存在API不伪称可跑/省内存：

```text
// ❌ 不好的做法：直接缓存 PropertyInfo
class BadEntityMapper
{
    // PropertyInfo 是大对象，1000 个实体类 × 10 个属性 = 10000 个大对象常驻内存
    Dictionary<Type, PropertyInfo[]> _cache = new Dictionary<Type, PropertyInfo[]>();
}

// ✅ 好的做法：缓存句柄
class GoodEntityMapper
{
    // 句柄很小，只存值类型
    Dictionary<RuntimeTypeHandle, RuntimePropertyHandle[]> _cache = 
        new Dictionary<RuntimeTypeHandle, RuntimePropertyHandle[]>();
    
    public void CacheProperties<T>()
    {
        Type type = typeof(T);
        var handles = type.GetProperties()
            .Select(p => p.PropertyHandle)
            .ToArray();
        
        _cache[type.TypeHandle] = handles;
    }
    
    public void MapToDb<T>(T entity)
    {
        var handles = _cache[typeof(T).TypeHandle];
        
        foreach (var handle in handles)
        {
            // 需要时再还原
            PropertyInfo prop = PropertyInfo.GetPropertyFromHandle(handle);
            var value = prop.GetValue(entity);
            // 写入数据库...
        }
    }
}
```

PropertyInfo缓存本身不天然坏，10000对象与保留图是否昂贵需实际量测/缓存策略；所谓Good的RuntimePropertyHandle[]/PropertyHandle/GetPropertyFromHandle不存在。**补充可用形状**用getter方法句柄、声明类型与属性名字；不是声称它一定比原PropertyInfo缓存省空间：

```csharp
class GetterMapping {
    public string Name;
    public RuntimeMethodHandle Method;
    public RuntimeTypeHandle DeclaringType;
}
// 对可读public instance非indexer属性：
var getter = property.GetGetMethod();
var mapping = new GetterMapping {
    Name = property.Name,
    Method = getter.MethodHandle,
    DeclaringType = getter.DeclaringType.TypeHandle
};
// 有效相同上下文中使用；getter无显式实参：
var method = (MethodInfo)MethodBase.GetMethodFromHandle(
    mapping.Method, mapping.DeclaringType);
object value = method.Invoke(entity, null);
```

完整安全EntityMapper夹具实际缓存Person.Name/Age并读回Age=30、Name=Ada；值和打印是补充，没有连接数据库，也没有给性能/总内存排名。真正数据库映射还需属性选择、类型转换、参数和错误处理合同。

## 加载可用不等于所有依赖/类型/方法立即初始化

对执行反射而言，包含目标类型的程序集/模块需在合适上下文可用；原“映射PE头、清单、元数据和IL到进程内存”保留为逻辑映像的说明，不能由此推出所有页面立即驻物理内存。原另句“元数据全在内存里”需限定这个区别。加载也不证明所有引用DLL先递归加载，或立即预建全部System.Type表示，更不等于触发所有静态构造器。解析依赖通常按所需类型/签名/执行路径触发，实际触发点依合同/实现，不能拿一次样例推广所有时点。

原SomeLib/MyLib/Newtonsoft依赖叙述需要这个限定。作者补充依赖夹具在两环境均用Assembly.LoadFrom(Path.GetFullPath("MyLib.dll"))，MyLib另含LazyUse静态引用Dep，PE确有该AssemblyRef。在这些补充输入下，路径加载/查UserService/创建它后Dep仍未加载，调用LazyUse.Use方法才加载；没有把原Assembly.Load("MyLib")逐字放进这一依赖夹具实测。它是“全启动载入”断言的具体反例，不规定任何引用都直到第一次调用才解析。

<a id="c23-automatic"></a>
## 普通exe启动无需手写加载入口，但依赖按需解析

用户的核心问题“正常运行exe要不要自己写Assembly.Load？”回答通常不需：运行时宿主负责启动和入口/适当依赖加载，普通静态类型调用触发绑定。Framework传统Windows exe路径与现代apphost/dotnet/CoreCLR别混同；只在这个Framework例里使用mscoree→CLR→默认域。

原九步流程保，修第8步与“全由shim”泛化：

```text
1. Windows 创建进程
2. 检查 PE 头，发现是 .NET 程序
3. 加载 mscoree.dll（CLR 的引导 DLL）
4. mscoree 启动 CLR（相当于 22.1 节的"CLR 寄宿"）
5. CLR 创建默认 AppDomain（相当于 22.2 节）
6. CLR 加载 MyApp.exe 这个程序集本身（相当于 23.1 节）
7. 检查 MyApp.exe 的 AssemblyRef 元数据表
8. 按实际所需引用/解析路径加载依赖，不保证Main前递归全载
9. 执行 Main() 方法
```

这是宿主/运行时加载器/JIT等合作，不全部由shim一个模块执行。添加编译引用也不保证compiler为每个完全未用引用写AssemblyRef，更不保证该引用在Main前全部加载。
