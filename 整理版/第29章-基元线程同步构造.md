原书主张尽量减少不必要的共享和同步，目的是降低出错、调度与资源成本；不能把它读成“需要保护的状态也不用同步”。同步还用于发布／观察顺序、线程间通知、阶段交接和限制并发，不只有互斥修改一种用途。只读共享与不可变String的原例成立，但数据应已正确构造和发布，查询本身不能暗中修改共享缓存或其他状态。

原书LinkedList.Add的两个赋值`newNode.m_next=m_head; m_head=newNode;`很快，但两个调用交错会丢节点；加同一把锁后可以串行更新该链表，获取／释放也有成本。这是具体数据结构的权衡，不代表所有线程执行所有代码都被那一把锁串行化。锁示意中的SomeKindOfLock是占位类型；完整应用仍应在成功获取后用finally保证释放，且要考虑节点的外部共享。

原“没有办法证明加锁正确，只能压力测试”过强。压力测试可找到发生过的错误，不能穷尽所有调度；在明确的内存模型、访问协议和不变式下，可以推理某个算法，也有基于契约的并发验证研究。证明有假设和范围，不能由一次测试通过推成任意应用都安全。[VCC concurrent verification research](https://www.microsoft.com/en-us/research/publication/vcc-a-practical-system-for-verifying-concurrent-c/)

避免静态可写状态、保持对象不向并发使用者公开，是原建议的主线。普通值实参复制可以减少共享；值类型也可以位于共享字段、数组元素或ref指向的同一存储，内部引用成员的副本仍可能指向同一List。这是必要边界，不是说Math.Max的两个独立Int32实参例本来不安全。

### 原子读写与发布次序先分清

C#保证bool、char、byte／sbyte、short／ushort、int／uint、nint／nuint、float、引用及适当底层类型的枚举的单次读写不撕裂；语言不要求long／ulong／double／decimal及普通用户结构的读写都原子。指定.NET实现还对本机字长以内、正确对齐的基本类型提供相应保证，因此不能笼统说x64的所有普通long都要拆两次或本来必撕裂。原子单次访问也没有把`++`、两个字段或读取—判断—更新自动合成原子操作。[C#9.6 atomic variable references](https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/language-specification/variables#96-atomicity-of-variable-references)[v10.0.0 .NET memory model](https://github.com/dotnet/runtime/blob/v10.0.0/docs/design/specs/Memory-model.md)

原5／1字段例完整保。普通字段的跨线程观察不能仅由源代码行序推成“看见flag=1就必见value=5”；不一定每次测试都打印0，Debug和Release的差别也不是只有Release才可能出问题。


<a id="c29-q01-a027"></a>
<!-- C29-D01-Q001-A-B027 -->
```csharp
class ThreadsSharingData {
    private Int32 m_flag = 0;
    private Int32 m_value = 0;
    public void Thread1() {        // 线程1执行
        m_value = 5;
        m_flag = 1;
    }
    public void Thread2() {        // 线程2执行
        if (m_flag == 1)
            Console.WriteLine(m_value);
    }
}
```

发布端把数据准备好后以release方式写标志，消费端以acquire方式观察到这一发布标志后再读数据；在原一次发布、无后续写入的例中，观察到1就能读到5。若还存在其他写入、多轮重用或对象被另一处修改，应另设计访问协议，不能写成“以后任何数据都全球最新”。


<a id="c29-q01-a037"></a>
<!-- C29-D01-Q001-A-B037 -->
```csharp
public void Thread1() {
    m_value = 5;
    Volatile.Write(ref m_flag, 1);   // 保证 m_value=5 先发生
}
public void Thread2() {
    if (Volatile.Read(ref m_flag) == 1)
        Console.WriteLine(m_value);   // 在本例看见该发布的flag=1时，读到先前发布的5；假定没有后续写入
}
```

Volatile.Write限制此前内存访问越过该release写，Volatile.Read限制此后访问越过该acquire读；这是可观察顺序，不能照问答写成强迫所有数据写到DRAM、马上对所有核心可见或绕过缓存。[C#15.5.4 volatile fields](https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/language-specification/classes#1554-volatile-fields)[Volatile class](https://learn.microsoft.com/en-us/dotnet/api/system.threading.volatile?view=net-10.0)

原问答还列`Volatile.MemoryBarrier()`，这个成员不存在，现有Framework4.8和.NET10引用编译都报CS0117。合法全栅栏例可用`Thread.MemoryBarrier()`或`Interlocked.MemoryBarrier()`，两者本次已实际调用；.NET10另有方向不同的Volatile.ReadBarrier／WriteBarrier，不能把新方法当成原不存在的MemoryBarrier别名。[v10.0.0 Volatile source](https://github.com/dotnet/runtime/blob/v10.0.0/src/libraries/System.Private.CoreLib/src/System/Threading/Volatile.cs)[Volatile.ReadBarrier](https://learn.microsoft.com/en-us/dotnet/api/system.threading.volatile.readbarrier?view=net-10.0)[Volatile.WriteBarrier](https://learn.microsoft.com/en-us/dotnet/api/system.threading.volatile.writebarrier?view=net-10.0)

C#volatile只适用支持类型的字段，包含char而不包含long／double或局部变量。库的nongeneric Volatile.Read／Write支持某些64位类型、ref位置与数组元素，不等给任意T一个泛型版本；当前泛型Read<T>仍限引用类型。原“关键字自动调用库方法”应读作访问语义相应，不是一定生成同名call指令。实际volatile++的IL有两处volatile前缀和add，仍不成为RMW原子更新。


<a id="c29-morph-overview"></a>
### 原Q1的Anything轮廓：先补缺失的泛型声明

原轮廓引用TArgument／TResult，却没有声明它们；这里补回原书PDF704／687中完整的泛型参数。原缺失的两处头形是`delegate Int32 Morpher(...TArgument...out TResult...)`与`static TResult Morph(...)`；真实负例报CS0246。循环业务和全部参数、结果载体保留，后面继续讲重试条件与独立变体。


<a id="c29-q01-a048"></a>
<!-- C29-D01-Q001-A-B048 -->
```csharp
delegate Int32 Morpher<TResult, TArgument>(Int32 startValue, TArgument argument, out TResult morphResult);

static TResult Morph<TResult, TArgument>(ref Int32 target, TArgument argument, Morpher<TResult, TArgument> morpher) {
    TResult morphResult;
    Int32 currentVal = target, startVal, desiredVal;
    do {
        startVal = currentVal;
        desiredVal = morpher(startVal, argument, out morphResult);
        // 若CAS此刻仍匹配startVal，就换成desiredVal；相等不证明期间没有ABA变化
        currentVal = Interlocked.CompareExchange(ref target, desiredVal, startVal);
    } while (startVal != currentVal);  // 被改过就重来
    return morphResult;
}
```

Increment／Decrement／Add返回更新后的数；Exchange／CAS返回原值，CAS失败后拿此原值重新计算。框架时代常用的Int32／Int64／引用等重载与现代版本不同：.NET9起泛型Exchange／CAS可支持引用、primitive与enum；本机.NET10的bool／enum成功而普通struct被NotSupportedException拒绝。原书旧“不能接受Boolean”应保为当时范围。

## 同一次async调用是顺序推进，传入对象未必独占

Q2引用原书开篇，强调不同线程执行一次异步方法的不同用户代码阶段，不等并发执行这些阶段。对该调用自身的私有状态，不需要仅因为换了线程再包一把锁。应同时保留三个前提：awaiter遵守协议、状态不向并发使用者暴露、共享数据的发布和寿命正确；不能由此推成任何可从这个方法到达的对象都不用同步。[C#12.9.9 await expressions](https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/language-specification/expressions#1299-await-expressions)

原Order例中的price是该调用保留的数据，order是调用者给出的对象。db.SaveAsync也可能持有、读取该对象，调用者还可能保留order引用；不能说挂起期间没有任何线程访问它。以下业务顺序完整保：Validate、CalculatePrice、保存、写回价格、发送通知；Order／db／notification及其业务合同由应用提供。


<a id="c29-q02-a008"></a>
<!-- C29-D01-Q002-A-B008 -->
```csharp
async Task ProcessOrderAsync(Order order)
{
    // 第一部分：在线程 A 上执行
    order.Validate();
    var price = order.CalculatePrice();   // 写 order.TotalPrice
    
    await db.SaveAsync(order);            // ← await 点，发生"交接"
    
    // 第二部分：可能在线程 B 上执行
    order.TotalPrice = price;             // 写 order.TotalPrice
    await notification.SendAsync(order);  // 读 order 数据
}
```

本次自造provider保留原Order引用，原方法在SaveAsync挂起时，夹具可把价格改99，provider持有的同一引用再改100；恢复后原方法仍按先前price写回42、通知读42。这只是受控顺序观察，已经说明“单调用自身阶段顺序”与“对象全局独占”不同，未运行真实数据库或数据竞争负载。

多个独立调用共享静态计数时，`TotalProcessedCount++`确有丢更新风险；“不同订单”并不隔离这个计数。原示意如下，static字段、两个任务与方法声明属于相应类型／调用位置的片段，不是把全部声明直接塞进任意方法即可编译的完整应用。


<a id="c29-q02-a018"></a>
<!-- C29-D01-Q002-A-B018 -->
```csharp
// 两个线程同时调用，处理不同的订单
Task t1 = ProcessOrderAsync(order1);  // 线程 A 和 B 参与
Task t2 = ProcessOrderAsync(order2);  // 线程 C 和 D 参与

// 但它们共享了一个静态字段！
static int TotalProcessedCount = 0;

async Task ProcessOrderAsync(Order order)
{
    await db.SaveAsync(order);
    
    // 危险！线程 B 和线程 D 可能同时执行这一行
    TotalProcessedCount++;  // 读-改-写，非原子
}
```

| 场景 | 多线程？ | 同时访问共享数据？ | 需要同步？ |
| --- | --- | --- | --- |
| 异步函数的不同阶段（同一调用内） | 可能A→B，也可能同一线程／已完成路径 | 同一合法调用的用户代码阶段顺序；可达对象仍可能外部共享 | 自身私有状态不因换线程另加锁；外部共享状态另判 |

同步不是只防同一微秒的两个CPU写指令。多个访问缺少正确的排序关系，即便某次实际执行没有撞在同一时刻，也不能因此推成安全；反过来，已用正确协议串行交接的私有数据也不因物理线程不同就必有数据竞争。

## 锁阻塞为什么可能让线程池扩大

Q3原书“线程池就可能创建新线程”应保可能条件。线程池工作线程等待同一把锁时，不能处理其队列后续工作；若队列仍有请求、近期取出工作不足、线程目标与上限允许，运行时可能增加工作线程。它不保证每次失败立即新建一条，更不以32为所有版本的默认上限。

原用WaitSleepJoin描述锁阻塞工作者的托管状态；本轮没有观测100个线程的瞬时状态，也不用状态查询代替正确的同步协议。池会按相应目标／条件调节工作者，长期闲置线程也可回收，不等每个任务完毕就销毁线程。这些调节与“该阻塞者暂时不能取后续队列项”的原说明一起保留。

现代.NET6起对某些阻塞Task API有更快的协作补偿；指定v10.0.0的gate还有队列请求、取出延迟、CPU使用与上限判断，Blocking源有启用条件和线程池身份检查。不能把它说成完全不知所有阻塞，也不能把所有Monitor／Sleep都说成走同一通知路径。这些是指定实现与版本补充，不是对原书历史每个实现字节的复现。[ThreadPool starvation diagnostics](https://learn.microsoft.com/en-us/dotnet/core/diagnostics/debug-threadpool-starvation)[v10.0.0 pool gate source](https://raw.githubusercontent.com/dotnet/runtime/v10.0.0/src/libraries/System.Private.CoreLib/src/System/Threading/PortableThreadPool.GateThread.cs)[v10.0.0 pool blocking source](https://github.com/dotnet/runtime/blob/v10.0.0/src/libraries/System.Private.CoreLib/src/System/Threading/PortableThreadPool.Blocking.cs)

保原10秒长持锁和100个任务的完整例；其中先Task.Run排入长任务，不保证它一定先获取锁。只有假定A先拿锁且仍持有期间，B／C／D才会依示意等待；十秒过后锁可释放，`Never reached`只是原字符串标签，不能读成这行永远不会执行。


<a id="c29-q03-a013"></a>
<!-- C29-D01-Q003-A-B013 -->
```csharp
object lockObj = new object();

void LongHeldLockTask()
{
    lock(lockObj)
    {
        Thread.Sleep(10000);  // 持有锁 10 秒
    }
}

void BlockedTask()
{
    lock(lockObj)  // 拿不到锁，阻塞
    {
        Console.WriteLine("Never reached"); // 原字符串标签；锁可用后实际能够到达。
    }
}

// 向线程池排入 1 个 LongHeldLockTask + 100 个 BlockedTask
Task.Run(LongHeldLockTask);
for (int i = 0; i < 100; i++)
    Task.Run(BlockedTask);
```

思考区另有假设“最大25、初始4”的WorkItemA／B版本。这个25是给定假设，可以用于说明，不能按其主题直接归为所有runtime上限错误；其中“永远不会执行到”注释仍须限定为锁不释放期间。


<a id="c29-q03-t014"></a>
<!-- C29-D01-Q003-T-B014 -->
```csharp
// 假设线程池最大25个线程，初始有4个线程
object lockObj = new object();

void WorkItemA()
{
    lock(lockObj)  // 线程1获取锁
    {
        // 长时间持有锁
        Thread.Sleep(10000);  // 模拟耗时操作
    }
}

void WorkItemB()
{
    lock(lockObj)  // 线程2-25都会在这里阻塞
    {
        // 持有者尚未释放时不会到达；获取锁后可以执行。
    }
}

// 将WorkItemA和大量WorkItemB排入线程池
```

| **线程数量爆炸**​ | 可能增线程；增长速度、初始数与上限依版本／设置／工作量，不保证4→32+ |
| **CPU 饱和 ≠ 有用工作**​ | 等待期间完成不了此共享工作；阻塞线程不持续在CPU忙等，池还可能处理其它任务 |
| **内存浪费**​ | 每线程栈有reserve／commit等成本；1MB是常见历史默认reserve示例，32MB不等全部物理驻留 |
| **上下文切换开销**​ | 阻塞／唤醒／恢复就绪会有成本；OS不在仍不可运行的几十个线程间持续执行它们 |
| **锁释放后的惊群效应**​ | 释放后等待者按实现竞争／通知；Monitor.Exit不能据此保证几十个线程全部同时唤醒 |

减少长期持锁，通常可以降低这种等待；原对照保两段10秒Sleep。所谓“锁外算／等”需要计算所用数据的快照与更新协议正确，不能机械搬动有依赖的代码；`sharedData.Calculate()`也未因名字保证很快。


<a id="c29-q03-a029"></a>
<!-- C29-D01-Q003-A-B029 -->
```csharp
// 坏：在锁里做耗时操作
lock(lockObj)
{
    Thread.Sleep(10000);  // 灾难
}

// 好：只在修改共享数据时加锁
int computedValue;
lock(lockObj)
{
    computedValue = sharedData.Calculate();  // 快
}
Thread.Sleep(10000);  // 锁外做耗时操作
```

SemaphoreSlim.WaitAsync可以让等待许可的调用保留一个待完成任务，避免为这段许可等待专占一条阻塞工作线程；内部短同步协调、等待队列内存、超时／取消及成功后Release配对仍要考虑。Monitor.TryEnter带超时会在到期前同步等待，零超时才是立即尝试；不能把带超时解释成在等待期间可以让同一线程同时做别的任务。



<a id="c29-library-safety"></a>
## 类库线程安全是实现责任，static不会让CLR自动保护

Q4问“是不是CLR保证，实例方法为什么不安全”。原答正确澄清了重要的一层：static和实例调用都没有因为声明形式自动取得同步锁；线程安全是该类型如何处理自己的共享状态、以及调用者是否满足成员约定的结果。原书／设计指南对静态共享状态和默认实例状态有不同设计建议，但不是语言把所有static方法变成互斥或事务。[Managed threading best practices](https://learn.microsoft.com/en-us/dotnet/standard/threading/managed-threading-best-practices)

静态方法可以没有共享可写状态，也可以内部用锁或Interlocked；“线程安全”不等“每次内部必须加锁”。以下原Math.Max完整例成立：两个Int32按值实参属于各次调用，比较与返回不修改共享字段。实参在语义上复制，不要求每次一定以一个可观察的物理栈帧存放，JIT也可以优化或内联。


<a id="c29-q04-a015"></a>
<!-- C29-D01-Q004-A-B015 -->
```csharp
public static Int32 Max(Int32 val1, Int32 val2)
{
    return (val1 < val2) ? val2 : val1;
}
```

Console的原伪码说明多个调用协调同一个共享输出资源；这里的_lock只是教学命名，不冒某个现存Console版本逐字使用这个字段／这一实现。即使每次WriteLine受到内部协调，多次Write／WriteLine组合也未因此成为调用者的一笔原子日志事务。


<a id="c29-q04-a022"></a>
<!-- C29-D01-Q004-A-B022 -->
```csharp
private static readonly object _lock = new object();

public static void WriteLine(string value)
{
    lock (_lock)
    {
        // 操作控制台这个共享资源
    }
}
```

第三种原策略是Interlocked更新一个状态位置。它可以减少一类简单更新所需的锁操作，但不能固定为所有架构每个方法只一条指令、所有负载都比任何lock快。静态API内部不损坏自身状态，也不替调用者保护它接收的所有可变对象；应读该成员的适用合同和共享对象寿命。

实例通常可以单独使用，因此许多普通集合不默认为每个成员加锁；“不保证”并不是“实例方法一定线程不安全”。CancellationTokenSource／Token、专门的并发集合和协调对象就是不同设计目的。原List私有使用例完整保，前提本来写明没有向另一线程公开。


<a id="c29-q04-a032"></a>
<!-- C29-D01-Q004-A-B032 -->
```csharp
var list = new List<int>();  // 线程 A 创建
list.Add(1);                 // 线程 A 使用
list.Add(2);                 // 仍然是线程 A
// list 从未离开线程 A，不存在并发访问
```

原书“所有实例方法各取锁会使整个应用只有一个线程运行”的推论过宽，问答进一步说所有List实例在整个AppDomain都串行，也错误。若每实例有自己的gate，这两把锁独立，两个线程可分别进入；本次两个自造实例用短受控交接确同时在各自锁内。只有共享同一锁、同一资源，或同步依赖形成瓶颈时，相应工作才协调等待。

ArrayList.Synchronized的选择示意完整保。这个包装协调单个成员访问，但枚举期间、复合步骤与所有绕过包装的访问仍需匹配协议；不能因提供一个包装就说任何多步操作自动原子。原普通实例／显式包装与“检查后添加”例保持原输入和用途。

```csharp
// 线程安全包装 —— 调用方显式选择要线程安全的版本
```

| 维度 | 静态方法 | 实例方法 |
| --- | --- | --- |

<a id="c29-mode-concepts"></a>
## 用户模式与内核模式：原语、忙等、阻塞和混合方案

Q5的会议室类比保：忙等者像在门口不断问“好了没”，阻塞者像登记后等待通知。类比说明等待策略，不保证公平排队、先来先得或每次“快／慢”都是同一数量级。用户模式基元包含易变访问和原子更新，未取得自旋锁时才反复尝试；不能说一次Volatile.Read本身就是持续抢锁。


<a id="c29-q05-a005"></a>
<!-- C29-D01-Q005-A-B005 -->
|  | 用户模式 | 内核模式 |
| --- | --- | --- |
| 拿不到锁时线程在干嘛 | 自旋锁失败可忙等；单次Volatile／Interlocked不等始终等锁 | 相应对象未就绪时可使线程阻塞；已就绪可直接通过 |
| 速度 | 常有较低同步调用成本；不是所有调用纳秒固定 | 有系统等待管理成本；不把实际等待时间当固定系统调用耗时 |
| 代价 | 自旋浪费 CPU | 系统调用、可能阻塞／唤醒／调度；模式切换不等必切换到另一线程 |
| 跨进程 | 本章这些进程内托管位置不能直接跨进程使用 | 适当Windows具名对象／共享句柄可跨进程，Slim另分 |

<a id="c29-spin-first"></a>
### 原自旋方法：0／1位置与获取、释放配对

以下原方法保持完整0／1标志、CAS、SpinWait(1)、DoSomething和Volatile释放。sharedData由包含类型提供，所有相关使用者必须协调同一份lockFlag存储；成功获取后才进入保护段。原短示意省略异常处理，DoSomething可能抛出时应用应加try/finally；不能在取得这把非重入锁后又尝试在同一线程递归Enter。


<a id="c29-q05-a010"></a>
<!-- C29-D01-Q005-A-B010 -->
```csharp
private int lockFlag = 0;  // 0 = 无人，1 = 有人

public void UserModeLock()
{
    // 尝试把 lockFlag 从 0 改成 1，如果改成功说明抢到锁
    while (Interlocked.CompareExchange(ref lockFlag, 1, 0) != 0)
    {
        // 没抢到！自旋——空转等待
        // 这里的空转是此自旋锁的等待方式，不是所有用户模式操作都如此
        Thread.SpinWait(1);  // 或者干脆 while 循环什么都不做
    }
    
    // === 临界区：访问共享数据 ===
    sharedData.DoSomething();
    
    // 释放锁
    Volatile.Write(ref lockFlag, 0);
}
```

“持锁10秒、其他10线程连续忙等，CPU100%”是说明浪费的示意，实际占用依CPU数、调度、暂停策略与其他工作。单纯长时间竞争但持有者最终放锁，不必就是工程语境中的livelock；原书把无法取得进展的持续忙等叫活锁，应把这个用词和“活动但相互阻碍、一直无进展”的典型活锁分别。线程仍可被操作系统抢占，SpinWait(1)不禁止其它线程获得CPU。

极短临界区可能适合短自旋；长等待可能适合阻塞。原“count++这样原子操作”只能在所用锁确保护整体更新时成立，裸`count++`不原子。也没有统一的几微秒／几毫秒分界，可以把程序、处理器和负载的假设写清，再衡量等待策略。


<a id="c29-manual-slim-example"></a>
### 原ManualResetEventSlim示意的两个实际缺口

原答把这个类当“纯内核互斥锁”，但ManualResetEventSlim是混合等待对象：可先短自旋，再走阻塞；读取WaitHandle会创建底层ManualResetEvent。Set是打开信号，允许多个等待者通过，不是归还一个排他所有权。下面保完整原片段，并修正“唤醒一个”的注释；初始false且只有此方法最后调用Set时，前面的Wait不会等到本方法自身那条Set。因此需要另一通知者，或者改成确具排他语义的构造。[ManualResetEventSlim](https://learn.microsoft.com/en-us/dotnet/api/system.threading.manualreseteventslim?view=net-10.0)


<a id="c29-q05-a026"></a>
<!-- C29-D01-Q005-A-B026 -->
```csharp
private readonly ManualResetEventSlim gate = new ManualResetEventSlim(false);

public void KernelModeWait()
{
    // 尝试进入临界区，如果资源不可用，线程在此 BLOCK（挂起）
    gate.Wait();  // ← 关键：这里线程被挂起，不占 CPU
    
    // === 临界区 ===
    sharedData.DoSomething();
    
    // 原Set是打开手动信号，可允许所有等待者通过；不是互斥许可的归还。
    gate.Set();
}
```

这并不意味着ManualResetEventSlim不能使用；本次自身0ms等待初始false，Set后两个等待都成功，并实际看到WaitHandle的类型ManualResetEvent。它适用于就绪通知、阶段交接等，与单人会议室锁是两种协议。


内核等待者不可运行期间不持续执行空转指令；持有者、被唤醒后的处理和其他任务仍会消耗CPU。内核对象有跨进程、超时、WaitAny／WaitAll、安全权限等能力，使用相应API仍须满足具体条件，不会自动把十个等待者全部同一时刻叫醒。

<a id="c29-primitive-tools"></a>
## “同步构造”和“基元”是工具分类，不是不可拆的一条指令

Q6的卫生间、门锁／叫号器／信号灯、化学元素／化合物、扳手和螺丝刀类比保：同步构造是协调工具总称，“基元”指讨论层次上的基本组成。它不是数学证明不能再实现为若干操作，也不保证叫号器类比就让所有锁FIFO。SpinLock本身已经包含尝试、等待、状态和可选owner检查，Mutex的所有权／递归亦不只有一个布尔位。

原最小原语清单保。flag先在包含上下文中声明；其中AutoResetEvent(false)的WaitOne和后面Set，不能在同一线程顺序执行并期待自行通过，应当理解成两方角色／分开步骤。所有取得Mutex的调用需要在正确线程配对释放和结束后协调Dispose。


<a id="c29-q06-a033"></a>
<!-- C29-D01-Q006-A-B033 -->
```csharp
// ===== 用户模式基元 =====

// 1. Interlocked —— 最基础的原子操作
int counter = 0;
Interlocked.Increment(ref counter);  // 一条 CPU 指令完成 读-改-写

// 2. Volatile —— 最基础的时序控制
Volatile.Write(ref flag, 1);  // release限制此前访问越过此写，不是禁止全部优化
int v = Volatile.Read(ref flag);  // acquire限制随后访问越过此读，不保证全球最新值


// ===== 内核模式基元 =====

// 3. AutoResetEvent —— 最基础的"信号"原语
var gate = new AutoResetEvent(false);  // false = 初始关闭
gate.WaitOne();  // 内核级等待，线程被挂起
gate.Set();      // 内核级唤醒，释放一个等待线程

// 4. Mutex —— 最基础的"互斥"原语
var mutex = new Mutex();
mutex.WaitOne();    // 内核级抢锁，抢不到就挂起
// 临界区
mutex.ReleaseMutex();  // 释放锁
```

Interlocked.Increment在合适实现中可降低成处理器原子指令，但不能固定所有架构都是LOCK XADD。Volatile在不同架构未必额外生成同一条硬件barrier。同步构造的用户模式／内核模式分类和C#／CLR／native三层调用关系也不同，下一部分保原大楼图并校准这一点。

下面保原明确标“伪代码／概念上”的lock对照。`ref object lockObj`与整数字面值1／0的CompareExchange并不是Monitor真实状态编码；这个形状不应当复制成一个可工作的对象锁，也没有表达owner、递归和释放。正确的object lock由编译器用Monitor.Enter／Exit与try/finally表达；C#13／.NET9起已知System.Threading.Lock类型还有EnterScope分支，不能将新分支倒推成第四版已讨论的实现。[C# lock statement](https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/statements/lock)


<a id="c29-q06-a036"></a>
<!-- C29-D01-Q006-A-B036 -->
```csharp

object lockObj = new object();

// 你写的：
```

<a id="c29-spin-steps"></a>
## 把自旋例拆到每个参数、分支与交接

Q7用户复引Q5的UserModeLock，思考区又给了一个较短但完整的代码版本。保0空闲／1占用的协议、目标ref、desired1、comparand0、失败循环、临界区与释放；同一小例的短版本不能连同其具体解释一起当纯写作计划排除。


<a id="c29-q07-t003"></a>
<!-- C29-D01-Q007-T-B003 -->
```csharp
private int lockFlag = 0;  // 0 = 无人，1 = 有人

public void UserModeLock()
{
    while (Interlocked.CompareExchange(ref lockFlag, 1, 0) != 0)
    {
        Thread.SpinWait(1);
    }
    
    sharedData.DoSomething();
    
    Volatile.Write(ref lockFlag, 0);
}
```

CAS此刻比较lockFlag与0，相等则存1，不相等则保持它，并返回该操作之前读到的值。原协议只允许0／1：返回0说明这次抢占成功，while条件不成立；返回1说明该次仍被占用，继续尝试。不能用普通读取后普通赋值替代CAS，否则多个线程可同见0并都进入。


<a id="c29-q07-a016"></a>
<!-- C29-D01-Q007-A-B016 -->
```text
如果 lockFlag == 0:
    lockFlag = 1
    返回 0
否则:
    不动
    返回 1
```

“原子”是相对于相应位置观察与更新的不可分割效果，不是让当前线程此后所有语句不可抢占，也不是让一个线程锁住全CPU。`Thread.SpinWait(1)`给出短自旋迭代的处理器提示；时间取决于平台和实现，不保证“几个固定周期”或让出OS时间片。普通空循环亦可被调度器抢占，不能称它会禁止其它线程运行。[Thread.SpinWait](https://learn.microsoft.com/en-us/dotnet/api/system.threading.thread.spinwait?view=net-10.0)

成功后原临界区占位保；sharedData的其它使用者只有遵守同一个标志和访问协议，才得到这一保护。


<a id="c29-q07-a030"></a>
<!-- C29-D01-Q007-A-B030 -->
```csharp
sharedData.DoSomething();
```

Volatile.Write释放0的作用，是使临界区此前的修改按release顺序先于相应释放可观察；下一取得者的CAS提供相应协调。它不是“马上绕过寄存器／CPU缓存、所有人零延迟都看到0”。原A／B五时刻完整保，箭头表达一种可行顺序，不是所有竞争的调度保证。


<a id="c29-q07-a037"></a>
<!-- C29-D01-Q007-A-B037 -->
```text
时刻1: lockFlag = 0（初始状态，门开着）

时刻2: 线程A 执行 CompareExchange
       检查 lockFlag == 0？是！
       改成 1，返回旧值 0
       while(0 != 0) = false → 跳出循环
       线程A 进入临界区 ✓

时刻3: 线程B 执行 CompareExchange
       检查 lockFlag == 0？不是！现在是 1
       不改，返回当前值 1
       while(1 != 0) = true → 留在循环里
       执行 SpinWait(1)，空转等一会儿
       然后再来一次 CompareExchange...
       再来一次...
       再来一次...
       （线程B 在 CPU 上疯狂重试，这就是"自旋"）

时刻4: 线程A 干完了，执行 Volatile.Write(ref lockFlag, 0)
       门开了！

时刻5: 线程B 的下一次 CompareExchange
       检查 lockFlag == 0？是！
       改成 1，返回 0
       while(0 != 0) = false → 跳出循环
       线程B 进入临界区 ✓
```

原AutoResetEvent(true)替代方法的基本互斥用途成立：每个成功WaitOne消费一个信号，工作完成后Set允许下一次消费。事件没有线程owner检查，因此异常释放和所有调用者配对是应用责任；已signaled时WaitOne可立即成功，不是每次都必睡觉。

<a id="c29-morph-pattern"></a>
### 保第二个Morph：重试的计算与一次成功的更新

Q9另有非泛型Morpher和out int result变体，不能用Q1泛型版本直接替掉它。以下完整签名、current／start／desired、循环和两个结果出口保；只精改“期间没改过”的过强注释。


<a id="c29-q09-a040"></a>
<!-- C29-D01-Q009-A-B040 -->
```csharp
// 通用模式：对 target 做一个复杂的原子操作
delegate int Morpher(int startValue, out int result);

static int Morph(ref int target, Morpher morpher, out int result)
{
    int currentVal = target;
    int startVal, desiredVal;
    
    do
    {
        startVal = currentVal;
        desiredVal = morpher(startVal, out result);
        
        // CAS此刻仍匹配startVal时更新；相等不证明期间没有ABA变化。
        currentVal = Interlocked.CompareExchange(ref target, desiredVal, startVal);
        
    } while (startVal != currentVal);  // 被改过就重试
    
    return result;
}
```

本次两个有界自造线程控制一次干扰：第一次计算基于0，另一个线程把target改10；第一次CAS发现不匹配，第二次重新算21并成功，结果和返回都是21。计算器被调用两次，不表示两次外部副作用也变成一次原子事务。生产计算一般应能安全重试，对一次位置的成功提交才是这个模式所保证的核心。

原“target=value期间未修改”还遗漏ABA：0被改1再改回0，CAS期待0仍成功；是否需要版本号或其他协议由数据结构用途决定。引用位置应按引用身份判断CAS返回值是否匹配预期，不用可能重载的`==`或Equals。两个同方法的不同Action实例`==`为true而ReferenceEquals为false，本次CAS保持旧slot；若据delegate==判断成功就会误读结果。

浮点也不能简单把Int32的`!=`退出条件照抄到所有情况。指定v10源通过bitcast进行对应浮点CAS；本次Frame／10相同NaN位型可以交换成42，但NaN数值==为false，-0与+0数值==为true却未交换。这是相关实现与观察的边界说明，不是宣称原书已经提供了错误的完整浮点算法。[Interlocked.CompareExchange](https://learn.microsoft.com/en-us/dotnet/api/system.threading.interlocked.compareexchange?view=net-10.0)[v10.0.0 Interlocked shared source](https://raw.githubusercontent.com/dotnet/runtime/v10.0.0/src/libraries/System.Private.CoreLib/src/System/Threading/Interlocked.cs)

### 保护多语句时，保原class自旋锁与finally用法

这个Q9版本是class，和原书SimpleSpinLock／BCL SpinLock的struct形式分开：复制class引用仍指向同一对象，不会仅因普通赋值复制整份锁状态。保其Enter／Exit完整方法及原已有的try/finally使用例，所有共享访问仍需用同一个锁实例。


<a id="c29-q09-a044"></a>
<!-- C29-D01-Q009-A-B044 -->
```csharp
class SimpleSpinLock
{
    private int lockFlag = 0;  // 0=空闲, 1=被占用
    
    public void Enter()
    {
        // 自旋等待，直到成功把 lockFlag 从 0 改成 1
        while (Interlocked.CompareExchange(ref lockFlag, 1, 0) != 0)
        {
            // 抢不到，空转等
            Thread.SpinWait(1);
        }
        // 抢到了，进入临界区
    }
    
    public void Exit()
    {
        // 释放锁
        Volatile.Write(ref lockFlag, 0);
    }
}

// 使用示例
var spinLock = new SimpleSpinLock();
spinLock.Enter();
try
{
    // 临界区：安全地访问共享数据
    sharedData.Modify();
}
finally
{
    spinLock.Exit();
}
```

<a id="c29-q09-a049"></a>
<!-- C29-D01-Q009-A-B049 -->
```csharp
// 如果持有锁的线程要占用锁 10 秒
// 其他 10 个等待线程就会在 CPU 上自旋 10 秒
// 这就是"活锁"——CPU 100% 但没干正事
while (Interlocked.CompareExchange(ref lockFlag, 1, 0) != 0)
{
    Thread.SpinWait(1);  // 原10秒长持锁示意：实际次数取决于实现与调度，未测固定几十亿次
}
```

### 原书互锁主例：AsyncCoordinator的哨兵与一次汇报

原29.3.2的MultiWebRequests有三个URI：`http://Wintellect.com/`、`http://Microsoft.com/`、`http://1.1.1.1/`，timeout默认Infinite。它在每次GetByteArrayAsync前AboutToBegin(1)，ContinueWith将结果交ComputeResult，最后AllBegun指定AllDone和超时；每项把异常或返回字节长度记录后JustEnded。结果、取消、超时可能竞争汇报，原算法用下面完整类控制一次状态回调。这里不访问三个公网地址，也不拿它的“最多CPU数量线程”表述作为现代线程池固定上限。

```csharp
internal enum CoordinationStatus { AllDone, Timeout, Cancel }
internal sealed class AsyncCoordinator {
    private Int32 m_opCount = 1;            // AllBegun 内部调用 JustEnded 来递减它
    private Int32 m_statusReported = 0;     // 0=false, 1=true
    private Action<CoordinationStatus> m_callback;
    private Timer m_timer;

    // 该方法必须在发起一个操作之前调用
    public void AboutToBegin(Int32 opsToAdd = 1) {
        Interlocked.Add(ref m_opCount, opsToAdd);
    }

    // 该方法必须在处理好一个操作的结果之后调用
    public void JustEnded() {
        if (Interlocked.Decrement(ref m_opCount) == 0)
            ReportStatus(CoordinationStatus.AllDone);
    }

    // 该方法必须在发起所有操作之后调用
    public void AllBegun(Action<CoordinationStatus> callback,
    Int32 timeout = Timeout.Infinite) {
        m_callback = callback;

        if (timeout != Timeout.Infinite)
            m_timer = new Timer(TimeExpired, null, timeout, Timeout.Infinite);
        JustEnded();
    }

    private void TimeExpired(Object o) { ReportStatus(CoordinationStatus.Timeout); }
    public void Cancel() { ReportStatus(CoordinationStatus.Cancel); }

    private void ReportStatus(CoordinationStatus status) {
        // 如果状态从未报告过，就报告它；否则忽略它
        if (Interlocked.Exchange(ref m_statusReported, 1) == 0)
            m_callback(status);
    }
}

```

opCount初始1是“所有发起动作尚未完成”的哨兵，不是始终精确只有1。每个操作开始加数、结束减数，AllBegun先保存callback再减掉初始那1；所以两个操作都提前结束时也不会在callback登记前汇报AllDone。Exchange把statusReported写1，只有拿到旧0的调用者汇报一次；赢得汇报的是这个状态，不是停止所有原HTTP。受控两runtime得到登记前callback0、登记后AllDone一次；Cancel先汇报后两个原工作仍可结束，不再二次回调。

这个类的正常MultiWebRequests用法在构造结束后才公开Cancel入口。把它独立重用时，必须明确AllBegun、callback、发起／结束数量和timer寿命协议；本次额外在登记前Cancel出现NullReference且状态已标汇报。这是新增协议边界，不能据此说原正常构造器场景本来必失败。

原MultiWebRequests还有真正的并发前提缺口：它说Dictionary键只读就不需要同步，但ComputeResult可并发写不同值，普通Dictionary的合同不保证这些并发写安全。应对相关字典访问用同一锁，或使用合适的并发集合；多项完整快照还要另定义。Task取消时Exception可以为空而Result抛异常，因此记录结果／JustEnded的分支还须考虑取消和finally配对。这些是对原示例的具体修正，不是运行危险并发字典写来“撞出错误”。[Dictionary<TKey,TValue>](https://learn.microsoft.com/en-us/dotnet/api/system.collections.generic.dictionary-2?view=netframework-4.8)

## 一次读写不撕裂，为什么还需要同步

原数据清单是Boolean、Char、SByte／Byte、Int16／UInt16、Int32／UInt32、IntPtr／UIntPtr、Single和对象引用。它表达相关普通位置单次读／写不产生半旧半新的值；不是说一条源码内所有动作原子，也不是所有CLR内存操作只提供这一个性质。C#语言9.6列举相应原子读写，明确不把普通long、ulong、double、decimal和用户定义类型的读写作为通用语言保证；实现还能对适当对齐的本机字大小提供更强保证。UIntPtr等涉及版本／语言类型规则时，应同时看运行时和实际API，不将旧清单误当任意重叠、不对齐或unsafe位置的全称。[C#9.6 atomic variable references](https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/language-specification/variables#96-atomicity-of-variable-references)[v10.0.0 .NET memory model](https://github.com/dotnet/runtime/blob/v10.0.0/docs/design/specs/Memory-model.md)

“不可分割”的词源atomos可以帮助记忆：读取不会得到某次写入的一半与另一半拼接的撕裂值。另一线程仍可能读到允许的旧值。原32位Int64两次32位写示意保；这是一种可能实现／撕裂风险说明，不是说所有32位JIT必逐字两条mov，或现代64位环境的每个long都必撕裂。


<a id="c29-q10-a009"></a>
<!-- C29-D01-Q010-A-B009 -->
```text
写低 32 位  →  mov [address], eax
写高 32 位  →  mov [address+4], edx
```

如果另一线程在两次相应写之间读取，可能得到“新低32位＋旧高32位”。指定实现／对齐可加强保障，Interlocked.Read或对应Volatile长整型访问可按其合同使用；本次只顺序验证long位值0123456789ABCDEF、double95.5等API，不进行为了碰出撕裂的竞态负载。


<a id="c29-q10-a016"></a>
<!-- C29-D01-Q010-A-B016 -->
| 操作类型 | CLR 是否保证原子性 | 说明 |
| --- | --- | --- |
| 单次读 `x` | 对上述受保证的类型／合法位置，是 | 不会得到一次写一半的撕裂值；不保证始终最新 |
| 单次写 `x = 5` | 对上述受保证的类型／合法位置，是 | 该单次写不撕裂；不是发布整个对象图 |
| **读-改-写**​ `x++` | ❌ **否**​ | 这是"读 + 改 + 写"三步，CLR 不保证这三步整体原子 |
| **多变量组合**​ `flag=1; data=42;` | ❌ **否**​ | 单次原子性不提供这组操作所需的跨线程顺序／发布协议；本行flag先写也不是正确发布data的顺序 |
| **跨线程可见性**​ | ❌ **否**​ | 原子性本身不保证及时可见或一定读到最新；须按相应同步合同建立关系 |

三个问题分别是复合操作、访问顺序和跨线程观察。Interlocked可对一个支持的位置完成相应原子RMW；例如Increment替代原x++。某些x86／x64路径可用带LOCK语义的指令，但不能把所有架构、所有操作、所有数据宽度都固定成LOCK XADD一条指令，也不能把“复杂操作”推广成任意多个位置组成的事务。


<a id="c29-q10-a025"></a>
<!-- C29-D01-Q010-A-B025 -->
```csharp
// 不安全的写法（x++ 不是原子操作）
x++;  // 多线程下会丢更新

// 安全的写法（Interlocked 保证整体原子性）
Interlocked.Increment(ref x);  // 硬件级原子
```

第二个原片段仍使用data42／flag1。普通单次写的原子性不会替两个线程建立所需发布关系；生产者先写data，再release写flag，消费者对应acquire读到那次发布后才使用data。代码只画生产者一侧，应和前面的Consumer配起来；没有其它改data的写者，是这类示例的重要前提。


<a id="c29-q10-a028"></a>
<!-- C29-D01-Q010-A-B028 -->
```csharp
// 可能出错的写法
data = 42;      // 原子写
flag = 1;       // 原子写，但可能被重排到上一行之前执行

// 安全的写法
data = 42;
Volatile.Write(ref flag, 1);  // release约束此前data写与此flag发布的顺序；由消费者对应acquire观察
```

Volatile.Write的release约束此前相关访问不移到它之后；Volatile.Read的acquire约束随后相关访问不移到它之前。两者不是一堵任何访问都不能双向跨过的完整屏障，也不保证总有某一条物理屏障指令。根据架构，必要的机器指令和缓存一致性机制不同。[C#15.5.4 volatile fields](https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/language-specification/classes#1554-volatile-fields)[Volatile class](https://learn.microsoft.com/en-us/dotnet/api/system.threading.volatile?view=net-10.0)[v10.0.0 Volatile source](https://github.com/dotnet/runtime/blob/v10.0.0/src/libraries/System.Private.CoreLib/src/System/Threading/Volatile.cs)

原第三片段把x5写／读说成“强制刷到／从主内存读，看到5”，这个物理解释和无条件结果都过强。保输入和两个线程角色，改成真实单次访问语义：


<a id="c29-q10-a032"></a>

```csharp

// 线程B

```

```text
  ↓ 不保证：复杂操作原子性、顺序、可见性
  ↓

  ├── Interlocked：提供支持的单位置原子读-改-写

  │
  ├── Volatile：修补"顺序"和"可见性"的坑
  │    例：flag=1 → Volatile.Write(ref flag, 1)
  │

```

### SharedData：计数和Hello发布是两项协议

原完整类把三个问题串起来：Int32计数、Boolean准备标志、string引用都能单次原子访问，但count++仍需要RMW；先准备Hello，再发布isReady；消费者观察到那次发布后才读message和原子增加计数。没有后续重新赋值／复用这个消息状态，是给定例的条件。


<a id="c29-q10-a036"></a>
<!-- C29-D01-Q010-A-B036 -->
```csharp
class SharedData
{
    // CLR 保证这些类型的单次读写是原子的
    private int _count = 0;           // Int32，单次读写原子
    private bool _isReady = false;    // Boolean，单次读写原子
    private string _message = null;   // 引用类型，单次读写原子
    
    // 线程1：生产者
    public void Produce()
    {
        // 问题1：_count++ 不是原子操作（读-改-写三步）
        // 解决：用 Interlocked
        Interlocked.Increment(ref _count);  // ✅ 原子自增
        
        // 问题2：需要先写 _message，再置 _isReady=true
        // 但编译器和 CPU 可能重排这两行
        // 解决：用 Volatile.Write 保证顺序
        _message = "Hello";                // 写数据
        Volatile.Write(ref _isReady, true);// 置标志，且保证上面的写入先发生
    }
    
    // 线程2：消费者
    public void Consume()
    {
        // 问题3：需要先检查 _isReady，再读 _message
        // 观察到此生产者发布后，应看到此前准备的_message
        // 解决：用 Volatile.Read
        if (Volatile.Read(ref _isReady))   // acquire；观察到这次发布后读取此前准备的Hello
        {
            Console.WriteLine(_message);    // 本例无其它message写者，观察到该发布时读到Hello
            
            // 问题4：_count++ 在消费端也需要原子
            Interlocked.Increment(ref _count);  // ✅ 原子自增
        }
    }
}
```

本次顺序调用Produce／Consume得Hello和count2，主要验证原类及相应API可运行；release／acquire保证取自语言／运行时合同，不能靠一次顺序输出证明。这三类问题由CLR提供的不同语言、库与运行时机制共同处理，“CLR不管顺序和可见性”不适合做总体结论。单次易变访问、单位置RMW和同一临界区保护各有范围，不因都是用户模式相关操作而产生公平、取消或整个应用不变式。

## 内核同步对象：信号、许可和线程所有权

原Q12提问称“29.7”，对应第四版本章目录实际29.4；后面的Event／Semaphore／Mutex内容仍完整保，不能沿用误编号来定位书节。Windows历史实现通过WaitHandle封装相应对象，托管代码调用其native用户态入口，再由所需系统服务完成内核等待。未满足条件时，阻塞的线程可停止执行等待通知；并非每次WaitOne都必须发生阻塞／线程上下文切换，已经有信号／许可时可以立即返回，也不是对象每个普通属性都必进入内核。

门上灯的类比：Set使事件处于signaled，Reset使它回到nonsignaled；AutoReset一次满足一个等待者后自动复位，ManualReset保持signaled直到Reset，所以其广播放行不表示所有CPU上恰同时执行。WaitOne也可能超时；Set不附带Mutex式持有者身份。

<a id="c29-auto-event"></a>
### AutoResetEvent：一份待消费的通知

以下Consumer／Producer必须分别在相应线程上驱动。Consumer先WaitOne可等待，Producer准备好数据后Set让一次等待有机会完成，自动事件在满足等待后回到未设置。Producer先Set且没有等待者，也会保留一次可消费的信号；不需要Set发生时恰有人等才有效。


<a id="c29-q12-a017"></a>
<!-- C29-D01-Q012-A-B017 -->
```csharp
// 初始状态：门关着（false）
private static AutoResetEvent gate = new AutoResetEvent(false);

// 线程1：生产者
void Producer()
{
    Console.WriteLine("生产者：准备好数据了，开门！");
    gate.Set();  // 开门，放一个等待者进来
}

// 线程2：消费者
void Consumer()
{
    Console.WriteLine("消费者：等门开...");
    gate.WaitOne();  // 门没开？睡觉去，不占CPU
    Console.WriteLine("消费者：进门了，开始干活！");
}
```

旋转栅门类比保：一次有效信号允许一次消费。但未消费前连续Set不会累计两张票；被消费后再Set可以完成另一次等待。是否合并由消费／设置交错决定，不宜只数Set语句。唤醒也不保证哪一个具体线程先得到调度。


<a id="c29-manual-event"></a>
### ManualResetEvent：发令后继续开放

<a id="c29-q12-a025"></a>
<!-- C29-D01-Q012-A-B025 -->
```csharp
// 初始状态：门关着（false）
private static ManualResetEvent gate = new ManualResetEvent(false);

// 线程1：发令枪
void Starter()
{
    Console.WriteLine("裁判：预备...跑！");
    gate.Set();  // 开门，而且门一直开着
}

// 线程2、3、4：运动员
void Runner(int id)
{
    Console.WriteLine($"运动员{id}：等发令枪...");
    gate.WaitOne();  // 门没开？睡觉
    Console.WriteLine($"运动员{id}：开跑了！");
}
```

三个Runner在Starter之前等待，Set后它们都可继续，后来的Runner也可直接过；Reset后才重新关闭。体育馆大门保持开放这个类比保，广播意味着都有资格继续，不是同一时间点在三个处理器上齐步运行。本次原Set／Reset形状得到Reset返回true、复位后WaitOne(0)为false；本地摘录写Reset返回false是转录差异，同版PDF708/印691和实际API都是true。[EventWaitHandle.Reset](https://learn.microsoft.com/en-us/dotnet/api/system.threading.eventwaithandle.reset?view=net-10.0)


<a id="c29-q12-a034"></a>
<!-- C29-D01-Q012-A-B034 -->
|  | AutoResetEvent | ManualResetEvent |
| --- | --- | --- |
| `Set()` 后放几个 | 满足一个等待；无等待者时保留一份待消费信号 | 置为signaled，所有等待可继续；调度不保证同时执行 |
| 之后门的状态 | 自动关闭 | 保持开着 |
| 连续多次 `Set()` | 若其间没有消费，多次Set合并；已消费后再次Set可完成另一等待 | 门一直开着 |
| 典型用途 | 一份通知；配队列时消费者可以一次唤醒后排空多项 | 广播通知（所有人同时开始） |

<a id="c29-semaphore"></a>
### Semaphore：计数限制，谁来释放由程序配对

停车场3位的类比保。原初始3／最大3完整Worker在成功WaitOne后进入try/finally、Sleep2000模拟工作、Release归还。前三份许可可3→2→1→0；第四次等待要等许可。Release可以给等待者机会继续，计数若被马上消费未必能在CurrentCount等观察里看到短暂1；原Semaphore这个例子也没有公平FIFO保证。


<a id="c29-q12-a039"></a>
<!-- C29-D01-Q012-A-B039 -->
```csharp
// 初始有 3 个空位，最多 3 个
private static Semaphore semaphore = new Semaphore(3, 3);

void Worker(int id)
{
    Console.WriteLine($"工人{id}：想进停车场...");
    semaphore.WaitOne();  // 还有空位吗？没有就睡觉等
    
    try
    {
        Console.WriteLine($"工人{id}：进来了，干活中...");
        Thread.Sleep(2000);  // 模拟干活
    }
    finally
    {
        Console.WriteLine($"工人{id}：干完了，离开");
        semaphore.Release();  // 腾出一个车位
    }
}
```

下面的AutoReset与Semaphore(1,3)保持原两次Set、两次Release及两次Wait输入：在同一线程先连Set且未消费，事件只有一份信号，第二个无超时WaitOne会一直等新的Set；**这段是行为反例，不要把它当完整可结束程序执行**。相反许可从1累到3，两次等待后还剩1。原初始值一样但最大值不同，这是解释累计的要点。


<a id="c29-q12-a048"></a>
<!-- C29-D01-Q012-A-B048 -->
```csharp
// AutoResetEvent：连续 Set 两次，仍然只放一个
var auto = new AutoResetEvent(false);
auto.Set();  // 放一个
auto.Set();  // 再放一个？不，多余的 Set 无效（内部计数最大就是1）
auto.WaitOne();  // 一个人进
auto.WaitOne();  // 第二个人？睡觉去

// Semaphore(初始1, 最大3)：连续 Release 两次，计数累加
var sem = new Semaphore(1, 3);
sem.Release();  // 计数变2
sem.Release();  // 计数变3（累加！）
sem.WaitOne();  // 一个人进，计数变2
sem.WaitOne();  // 第二个人直接进，计数变1（不用等 Release）
```

本次受控验证无等待者时事件Set两次，零超时两次等待依次true／false；Semaphore(1,3)两次Release返回旧计数1／2，四次WaitOne(0)为true／true／true／false。最大1的许可再次Release若已满会抛SemaphoreFullException；不是默默合并。没有内建所有权不表示任意业务代码都可以不计配对地Release，仍须维护数量和生命周期。[AutoResetEvent](https://learn.microsoft.com/en-us/dotnet/api/system.threading.autoresetevent?view=net-10.0)[Semaphore.Release](https://learn.microsoft.com/en-us/dotnet/api/system.threading.semaphore.release?view=net-10.0)


<a id="c29-mutex"></a>
### Mutex：递归持有者是物理线程

<a id="c29-q12-a054"></a>
<!-- C29-D01-Q012-A-B054 -->
```csharp
private static Mutex mutex = new Mutex();

void DoWork(int threadId)
{
    Console.WriteLine($"线程{threadId}：想拿钥匙...");
    mutex.WaitOne();  // 拿钥匙，拿不到就睡觉等
    
    try
    {
        Console.WriteLine($"线程{threadId}：拿到钥匙，进屋干活");
        Thread.Sleep(1000);  // 模拟干活
    }
    finally
    {
        Console.WriteLine($"线程{threadId}：干完了，还钥匙");
        mutex.ReleaseMutex();  // 只有拿钥匙的人才能还
    }
}
```

带钥匙的类比用来强调owner：成功等待得到Mutex所有权，只有相同物理线程能ReleaseMutex；它也允许该线程递归取得，多取得几次就要释放几次。原两个线程标签是两条执行路径，不能把连续代码贴在同一个线程然后声称释放者不同。同一线程也可以重复进入Monitor及普通object的lock，因此“可重入”是二者共同属性，不能作为Mutex相对它们的区别；相应命名Mutex可跨进程，而普通Monitor/object锁只协调本进程内同一对象。[C# lock statement](https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/statements/lock)


<a id="c29-q12-a057"></a>
<!-- C29-D01-Q012-A-B057 -->
```csharp
var mutex = new Mutex();

// 线程A
mutex.WaitOne();      // 线程A 拿到锁
// 此时内核记录：这个 Mutex 属于 线程A

// 线程B
mutex.ReleaseMutex(); // ❌ 报错！线程B 不是所有者，不能释放
```

<a id="c29-q12-a059"></a>
<!-- C29-D01-Q012-A-B059 -->
```csharp
var auto = new AutoResetEvent(false);

// 线程A
auto.WaitOne();   // 线程A 等待
// ... 线程B 可以随便 Set
auto.Set();       // ✅ 线程B 唤醒线程A，没问题

var sem = new Semaphore(0, 3);
sem.Release();    // ✅ 任何线程都可以 Release
```

本次同owner两次取得，其他线程释放抛ApplicationException；另一个零超时等待在仍有2层／剩1层时false，归还第2层后true。owner退出而未释放时，后来的等待可抛AbandonedMutexException，**同时取得这把Mutex**；若要继续，必须按所保护数据的不变式恢复／校验，并在持有者线程正确释放。它提醒资源状态可能不一致，不等于任何遗弃都必有已损坏数据或必须整个程序崩溃。[Mutex](https://learn.microsoft.com/en-us/dotnet/api/system.threading.mutex?view=netframework-4.8)[Mutex.ReleaseMutex](https://learn.microsoft.com/en-us/dotnet/api/system.threading.mutex.releasemutex?view=net-10.0)

原书RecursiveAutoResetEvent用m_owningThreadId＋m_recursionCount模拟同线程递归，Leave检验owner并在最后一层Set。这能解释递归计数，但不是与OS Mutex“完全一样”：缺少命名跨进程对象和内核遗弃检测；持有者死去时自动事件可能永远留在关闭状态，不能仅靠换等待者自动恢复。本次只检查底层WaitOne(0)关闭及wrongowner Leave抛InvalidOperationException，不运行那条可能永等的Enter。[BOOK29-17]


<a id="c29-named-waits"></a>
### 命名、等待组和结束寿命是另外三件事

原两个进程用相同MyAppGlobalLock名字取得同一命名Mutex例保。应在所有成功取得路径以正确owner释放、协调结束后Dispose；名字中的Global这个普通子串不会自动成为Windows的`Global\\`命名空间，跨session、权限和名称冲突还须单独配置。


<a id="c29-q12-a063"></a>
<!-- C29-D01-Q012-A-B063 -->
```csharp
// 进程A
var mutex = new Mutex(false, "MyAppGlobalLock");  // 起个名字
mutex.WaitOne();  // 拿锁
// 做操作...

// 进程B（另一个exe程序）
var mutex = new Mutex(false, "MyAppGlobalLock");  // 用同一个名字
mutex.WaitOne();  // 如果进程A拿着锁，进程B就等着
// 确保同一时刻只有一个进程在操作共享资源
```

Event／Semaphore也可以通过相应命名API跨进程共享，这一段原“它们做不到”需纠正。AutoResetEvent的常用构造器只取bool；需要命名自动事件可用EventWaitHandle(false, EventResetMode.AutoReset, name)，不是给AutoResetEvent硬造名称重载。同名且已存在时通常打开同一对象，createdNew用来判断新建；本次自己GUID的Local对象两个句柄得到true／false，最后都关闭后再新建true，这是同进程对象存在／生存期观察，不能冒跨进程实测。

<!-- C29-D01-Q012-A-B066 -->
|  | AutoResetEvent | ManualResetEvent | Semaphore | Mutex |
| --- | --- | --- | --- | --- |
| **类比**​ | 旋转栅门 | 体育馆大门 | 停车场 | 带线程所有权的钥匙（命名是可选能力） |
| **核心行为**​ | 放一个，自动关 | 放所有，手动关 | 限制并发数量 | 互斥 + 所有权 |
| **所有权**​ | ❌ 无 | ❌ 无 | ❌ 无 | ✅ 有 |
| **跨进程**​ | 可以，通过相应命名EventWaitHandle API；普通AutoResetEvent(bool)不带名称 | 可以，通过相应命名事件API | 可以，通过命名Semaphore | 可以，通过命名Mutex |

WaitHandle统一的WaitOne／WaitAny／WaitAll属于等待协议；WaitAny成功返回相应索引，超时返回WaitTimeout=258，WaitAll表示组条件是否满足，并不随意省略超时、遗弃和平台限制。通常组最多64句柄；STA上的WaitAny按文档最多63，WaitAll多个句柄不支持。实际两个环境65个均拒绝，MTA64立即成功；STA两句柄WaitAll均拒绝；Framework4.8对64个已signaled／零超时WaitAny在所测路径返回0，.NET10拒绝。这一历史实现观察不提供Frame所有STA64等待安全的合同。[WaitHandle.WaitAll](https://learn.microsoft.com/en-us/dotnet/api/system.threading.waithandle.waitall?view=net-10.0)[WaitHandle.WaitAny](https://learn.microsoft.com/en-us/dotnet/api/system.threading.waithandle.waitany?view=net-10.0)

Dispose／Close最终释放底层对象句柄；先保证没有其它调用仍在访问再结束生命周期，不要求一律靠GC才“安全”，也不应在等待线程仍依赖对象时随手释放。原书对从不显式Dispose的偏好只能作为特定寿命策略讨论，不替程序的owner／结束协议。等待组、命名同步、安全描述符与跨进程通信各有条件，单凭对象能命名不传递全部业务数据。[BOOK29-14]

## 自动事件与最大1信号量：保不同初值和实际条件

Q13复引“AutoResetEvent等价于最大计数1的信号量”，后面的原回答却先写了Semaphore(1,3)。不能把最大3例改名为最大1而照抄结论。初始1／最大3的原构造保，它表示已经有1份许可、最多3份，而不是“初始1就是最大1”。


<a id="c29-q13-a003"></a>
<!-- C29-D01-Q013-A-B003 -->
```csharp
// 初始计数=1，最大计数=3
var sem = new Semaphore(1, 3);
```

<a id="c29-no-waiters"></a>
### 无等待者时的两次设置／释放

原A和T分别给出完整流程，注释、var有无、A/B/C/D等待路径均保。自动事件未消费前两次Set只有一份待消费信号；首个等待直接通过并复位，第二个要等新Set。反例的最后无超时WaitOne不作为可结束程序运行，本次验证用零超时等待记录true／false。


<a id="c29-q13-a007"></a>
<!-- C29-D01-Q013-A-B007 -->
```csharp
var gate = new AutoResetEvent(false);  // 初始关闭

// 此时没有任何线程在 WaitOne()
gate.Set();    // ① 门开了（变为 signal 状态）
gate.Set();    // ② 门已经是开的，再 Set 没有额外效果

// 现在线程 A 来了
gate.WaitOne();  // 门是开的，A 直接进，进门后门自动关上
// 现在门又关了

// 线程 B 来了
gate.WaitOne();  // 门关着 → B 阻塞！睡觉去
```

<a id="c29-q13-t043"></a>
<!-- C29-D01-Q013-T-B043 -->
```csharp
gate = new AutoResetEvent(false);  // 初始关闭

gate.Set();    // 门开了（signal），但没有人在等
gate.Set();    // 门已经是开的，再 Set 没效果

// 现在线程A来了
gate.WaitOne();  // 门是开的，直接进，然后门自动关上
// 现在门又关了

// 线程B来了
gate.WaitOne();  // 门关着，阻塞！
```

信号量这两个独立版本的初始许可都是1、最大3，两次Release后3份，A/B/C取得后为2／1／0，D等待。不能把“能通过3个”错误地都归于两次Release——另外1份来自初始计数。它也不是任意Release都成功、最大值真的不限：通常必须给出合法有限Int32最大计数，越上限会抛SemaphoreFullException。


<a id="c29-q13-a012"></a>
<!-- C29-D01-Q013-A-B012 -->
```csharp
var sem = new Semaphore(1, 3);  // 初始1个许可，最多3个

// 此时没有任何线程在 WaitOne()
sem.Release();  // ① 计数 +1 → 变成 2
sem.Release();  // ② 计数 +1 → 变成 3（累加！）

// 现在线程 A 来了
sem.WaitOne();  // 拿到1个许可，计数变 2

// 线程 B 来了
sem.WaitOne();  // 拿到1个许可，计数变 1

// 线程 C 来了
sem.WaitOne();  // 拿到1个许可，计数变 0

// 线程 D 来了
sem.WaitOne();  // 没许可了 → D 阻塞！
```

<a id="c29-waiters-consumption"></a>
### 已经有人等时：两次消费的交错条件

原两个等待者的片段想表达Set满足一个等待后，再次Set可以满足另一个，这个有条件知识是对的。但只连写两个Set，不控制消费，就不能保证A／B各被唤醒。原T也提到了中间无人消费会合并；保这条正确限制，明确“消费信号”比“那个线程已经被调度跑起来”更准确，API不保证具名等待者顺序。


<a id="c29-q13-a017"></a>
<!-- C29-D01-Q013-A-B017 -->
```csharp
var gate = new AutoResetEvent(false);

// 线程A和线程B都已经调用了 gate.WaitOne() → 都在睡觉

gate.Set();  // 一个等待消费信号后自动复位；具体A/B不保证
gate.Set();  // 第一信号已经消费后，可完成另一次等待；否则可能合并
```

<a id="c29-q13-t049"></a>
<!-- C29-D01-Q013-T-B049 -->
```csharp
gate = new AutoResetEvent(false);

// 线程A和B都在等
// 线程A: gate.WaitOne() -> 阻塞
// 线程B: gate.WaitOne() -> 阻塞

gate.Set();  // 在第一信号已被消费后，可完成A的等待，自动复位
gate.Set();  // 此信号再被消费可完成另一个等待，不保证具体名字B
// 此两次Set各有一次消费才能完成两次等待；仅两行连写不保证这个交错
// 关键是：如果连续快速调用两次 Set 而中间没有一次有效信号消费，第二次 Set 不会"存起来"
```

<a id="c29-q13-a022"></a>
<!-- C29-D01-Q013-A-B022 -->
|  | AutoResetEvent | Semaphore |
| --- | --- | --- |
| **内部模型**​ | 开关（只有 开/关 两种状态） | 桶里有几个令牌（计数器） |
| **Set() / Release()**​ | 把开关拨到"开" | 增加许可计数，超出最大值则失败 |
| **连续调用两次**​ | 其间无消费且已signaled时，第二次不累计 | 成功Release可累计，受初始计数／上限／消费约束 |
| **WaitOne()**​ | 如果开关是"开"，通过，然后**自动关上**​ | 如果桶里有令牌，拿走一个，桶里少一个 |
| **本质**​ | 不累积 | 可累计到指定最大计数 |

<a id="c29-event-queue"></a>
### 两次通知不等于两条数据必然丢失

拨开关与令牌桶两个类比保：前者只有一份待消费状态，后者有计数。原生产者连续Set的片段没有实际数据容器，不能仅据合并就证明第二条业务数据已丢；若另有线程安全队列保存数据，一次通知可让消费者排空多项。


<a id="c29-q13-a025"></a>
<!-- C29-D01-Q013-A-B025 -->
```csharp
// 生产者线程
void Produce()
{
    // 生产了数据
    gate.Set();   // 通知消费者
    gate.Set();   // 又生产了一条，再通知
}
```

本次自己ConcurrentQueue先存1／2，再连续Set两次；第一次WaitOne(0)为true后排出1／2，下一次等待false，没有凭通知合并丢队列元素。若协议硬规定一次唤醒只处理一项却不再次检查队列，的确可能把剩余项搁置；这是通知与数据协议的条件问题。计数许可也必须和成功入队／出队、失败／取消配对，使用Channel等有数据队列协议的库是另一个方案，而不是AutoResetEvent概念上禁用于任何生产者消费者系统。[AutoResetEvent](https://learn.microsoft.com/en-us/dotnet/api/system.threading.autoresetevent?view=net-10.0)[Semaphore.Release](https://learn.microsoft.com/en-us/dotnet/api/system.threading.semaphore.release?view=net-10.0)


<a id="c29-event-maxone"></a>
## Semaphore(1,1)接近AutoResetEvent(true)，仍有可观察区别

Q14用户问初始1／最大1，原给出的首个例子恰是合法的失败反例：尚未消费时Release超过最大1而抛异常；AutoReset(false)先Set到true，再Set不抛且不累计。保该反例，不能把故意抛异常本身判成API写错。


<a id="c29-q14-a004"></a>
<!-- C29-D01-Q014-A-B004 -->
```csharp
// 场景：没有任何线程在 WaitOne()

var auto = new AutoResetEvent(false);
auto.Set();    // 状态变"开"
auto.Set();    // 已经是"开"了，没额外效果
// 结果：累计了 1 次信号

var sem = new Semaphore(1, 1);
sem.Release(); // 计数 1→2？不对！当前计数是1，最大是1，所以抛异常！
```

无人等待时第一次Set也不浪费：它保留一次待消费信号，所以之后第一个WaitOne可直接通过。原下一段已写出这个结果，改掉其前面与结果矛盾的“浪费”注释。


<a id="c29-q14-a008"></a>
<!-- C29-D01-Q014-A-B008 -->
```csharp
// 没有任何线程在等待

var auto = new AutoResetEvent(false);
auto.Set();    // 内部状态变为signal；没人等时保留一次信号，随后可消费
// 之后第一个 WaitOne() 会直接通过，然后自动关闭

var sem = new Semaphore(1, 1);
// 初始计数已经是 1，不能再 Release
// 第一个 WaitOne() 直接通过，计数变 0
```

Semaphore(1,1)初始已有1，AutoResetEvent(true)初始已有一次信号，在匹配的取得／释放协议下有近似效果；最大1信号量同样不能累计超过1，并不是它能积累很多而自动事件不行。原将区别说成“唯有初始0时”过窄：初始1时未消费便Release也会满，首例已经展示。下面初始0／最大1是另一个条件，仍保两次Release与Set的区别。


<a id="c29-q14-a012"></a>
<!-- C29-D01-Q014-A-B012 -->
```csharp

var auto = new AutoResetEvent(false);  // 初始false

// 此时都没有线程在等待

sem.Release();    // 计数 0→1 ✅ 成功
sem.Release();    // 计数已经是1，最大是1 → ❌ 抛异常

auto.Set();       // 状态变 signal ✅
auto.Set();       // 已经是 signal → ✅ 没效果，不抛异常
```

<a id="c29-q14-a015"></a>

```csharp
auto.Set();       // 线程A设置的
auto.WaitOne();   // 线程B可以等待并通过 ✅（无所有权）
```

| --- | --- | --- |

<a id="c29-await-vs-wait"></a>
## WaitOne与await：阻塞调用者，还是挂起异步方法

Q15把Set说成等待，原A已正确自纠为WaitOne等待／Set通知，保这条纠正而不反标成A仍说反。WaitOne在条件未满足且未超时的时候阻塞当前线程；完成等待后同一线程继续。await先取得awaiter并检查IsCompleted：已完成时同步GetResult并继续；未完成才登记延续、返回当前调用者，等完成后恢复状态机。它没有指定“当前线程一定回池、另一个池线程一定接力”。[C#12.9.9 await expressions](https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/language-specification/expressions#1299-await-expressions)


<a id="c29-q15-a005"></a>
<!-- C29-D01-Q015-A-B005 -->
|  | WaitOne()（内核构造） | await（异步） |
| --- | --- | --- |
| **线程在干嘛**​ | 信号未满足而进入阻塞等待时，该线程不能执行后续调用 | awaiter未完成时挂起方法并返回调用者；已完成可直接继续 |
| **线程还属于你吗**​ | 阻塞仍占用该线程及其相关资源，是否合适取决于用途 | 挂起期间不必专占等待线程；同步执行／内部工作仍需要线程 |
| **醒来后谁干活**​ | 成功结束等待后，同一调用线程继续 | 取决于awaiter和捕获的上下文／调度，可为原线程、池线程或其它线程 |
| **底层机制**​ | Windows相应等待服务；已signaled时可立即完成 | 编译器的awaiter协议／状态机；所等操作可能另用OS服务 |

### 同一个下载用途，保两套完整方法与时间线

原事件版由UI或池线程A调用，自己排一个池工作项执行DownloadFile，耗时5秒后Set，A以WaitOne等通知再ProcessFile。DownloadFile／ProcessFile是应用提供的方法；原主线正常完成路径保，异常时仍需保证通知、传播失败与对象寿命，不能让下载失败后A永等。本章未执行真实下载或5秒池负载。


<a id="c29-q15-a009"></a>

```csharp

{
    ThreadPool.QueueUserWorkItem(_ =>
    {
        // 后台线程去下载

}
```

<a id="c29-slim-async"></a>
## SemaphoreSlim.WaitAsync：许可取得、超时结果与配对

Q16从Web API限制同时3个下游数据库请求出发。先保原同步Wait版：信号量没有空位时调用可能阻塞当前线程，已有空位时立即取得。async方法内的同步Wait不会因为方法有async关键字就变成异步等待。


<a id="c29-q16-a005"></a>
<!-- C29-D01-Q016-A-B005 -->
```csharp
private static readonly SemaphoreSlim _sem = new SemaphoreSlim(3, 3);

public async Task<string> GetData()
{
    _sem.Wait();          // ← 没许可时可能阻塞当前线程；立即有许可时无需等待
    try
    {
        return await CallDatabaseAsync();
    }
    finally
    {
        _sem.Release();
    }
}
```

若100个调用确实同时走到同步入口而前三个长期持有许可，其余97个可能占着线程等；这不是每个ASP.NET请求从到来到结束必须独占一线程的固定模型，也不是必然马上耗尽。用WaitAsync在无许可时返回未完成任务，await可把等待状态保存而不专占97个等待线程；对象、队列、Task、上下文和后续业务仍有成本，不能宣称无限／完美伸缩。

<!-- C29-D01-Q016-A-B009 -->

```csharp
{
```

<a id="c29-slim-implementation"></a>
### 快速路径和队列是受同一内部协议保护的

保原WaitAsync伪码表达“先尝试立即取得，否则等待异步完成”。TryTakeImmediate和_waiters是假想辅助，原未给锁与配对实现；不能把它当现成SemaphoreSlim源码或完整正确的自制信号量：检查许可、入队和Release必须协调，否则可在检查后入队前丢掉应完成的等待，取消／超时也要处理队列移除及配额。


<a id="c29-q16-a015"></a>
<!-- C29-D01-Q016-A-B015 -->
```csharp
public async Task WaitAsync()
{
    // 第一步：尝试快速拿许可（用户模式自旋）
    if (TryTakeImmediate())
        return;  // 拿到了，直接返回，不 await
    
    // 第二步：没拿到，创建一个 TaskCompletionSource
    var tcs = new TaskCompletionSource<bool>();
    
    // 把自己加入等待队列
    _waiters.Enqueue(tcs);
    
    // 第三步：返回一个 Task，调用者 await 这个 Task
    await tcs.Task;
    // 当别的线程 Release() 时，会从队列里取出 tcs 并调用 tcs.SetResult(true)
    // 这里的 await 就会完成，调用者继续执行
}
```

指定.NET10源的WaitAsync会用短内部Monitor锁协调计数与等待者；异步TaskNode本身是派生Task<bool>的双向链表节点并用RunContinuationsAsynchronously，不是每个等待者都实际创建TaskCompletionSource。有许可时可返回已完成任务，无许可时把节点入队，Release按协议将许可交给等待者并完成相应任务；交接后的计数可能仍为0。同步Wait可短自旋后Monitor.Wait阻塞，AvailableWaitHandle还能懒创建ManualResetEvent。因此“纯托管”不等于所有路径永不调用OS／不会阻塞；async等待队列没有要求把每个等待的线程堵在那里。[SemaphoreSlim class](https://learn.microsoft.com/en-us/dotnet/api/system.threading.semaphoreslim?view=net-10.0)[SemaphoreSlim.WaitAsync](https://learn.microsoft.com/en-us/dotnet/api/system.threading.semaphoreslim.waitasync?view=net-10.0)[v10.0.0 SemaphoreSlim source](https://github.com/dotnet/runtime/blob/v10.0.0/src/libraries/System.Private.CoreLib/src/System/Threading/SemaphoreSlim.cs)

<!-- C29-D01-Q016-A-B021 -->
| 你学的概念 | 在 WaitAsync 里的体现 |
| --- | --- |
| 信号量限流 | 同一SemaphoreSlim实例最多3份已取得许可；其它路径绕过它不受控 |
| 用户模式快速路径 | 尝试立即取得；示意TryTakeImmediate不是真实公开BCL API或必自旋 |
| async/await 非阻塞 | 未完成许可任务可挂起方法；立即完成任务可在当前调用继续 |

<a id="c29-slim-timeout"></a>
### 五秒超时返回false；取消才按取消协议抛出

原带CancellationToken的方法有一个具体错误：WaitAsync(TimeSpan,ct)返回Task<bool>，超时结果是false，不会自动抛TimeoutException。原忽略bool后仍调用数据库，finally还归还一份从未取得的许可。保原方法和5秒／token输入，给错误行紧邻标识；这段是待比较的原反例。


<a id="c29-q16-a024"></a>

## 对照原书自旋与延迟：锁存储、策略和处理器分开

原29.3.3的SimpleSpinLock是struct，Enter循环Exchange(0→1)抢占，Leave以Volatile.Write置0；SomeResource把同一个锁放在字段里访问。其短使用轮廓只写Enter／访问／Leave，实际异常路径需要finally。书对值类型复制和readonly字段的警告是正确的：复制会得到另一份锁状态，readonly成员调用可能操作防御副本。本次BCL SpinLock两份初始副本各TryEnter(0)都成功、readonly副本两次也各成功；这说明不能靠不同锁存储协调，不是运行长争用来做性能结论。Q9的class版本普通复制的是同一对象引用，不能反套这条struct警告。

单CPU或优先级不利时，忙等线程可能妨碍持有者尽快运行，故纯自旋适用于非常短且能及时释放的临界区；不是只要短就必然最快或保证公平。原作者建议禁止某些PriorityBoostEnabled作为当时调优意见保留，没有调整主机优先级或把它写成.NET正确性合同。

Thread.SpinWait(iterations)是指定次数的自旋延迟；SpinWait结构的SpinOnce／NextSpinWillYield帮助选择短自旋与让出执行的策略，会涉及Thread.SpinWait、Yield或Sleep。这类策略不等普通一次Volatile／Interlocked访问必自旋等锁。Thread.Sleep的milliseconds／TimeSpan、Sleep(0)、Sleep(1)、Timeout.Infinite=-1和Yield各有不同用途：正时间是暂停请求，不保证Windows在该毫秒准点恢复；0让出机会后也可能继续调度自己；Yield是否有合适线程运行不能预先保证，亦不是C# yield生成迭代元素。无需靠Infinite把自己永久停住来演示这些关系。[SpinWait struct](https://learn.microsoft.com/en-us/dotnet/api/system.threading.spinwait?view=net-10.0)[Thread.SpinWait](https://learn.microsoft.com/en-us/dotnet/api/system.threading.thread.spinwait?view=net-10.0)

原书把SMT／超线程说成“一次只允许一个线程运行”过强。Intel的解释是多个硬件执行上下文可共享同一核心资源并同时推进；忙等和PAUSE等提示的行为须看架构／实现，不能说所有非超线程处理器上相关指令都作为通用.NET合同被忽略。本章未采集硬件指令时序，既不把缓存一致性写成每次全局锁总线，也不把Thread.SpinWait当成保证调度到某个具体owner的OS让出操作。[Intel HT/core/vCPU](https://www.intel.com/content/www/us/en/support/articles/000098959/processors/intel-xeon-processors.html)[Intel LOCK/cache-coherence](https://www.intel.com/content/www/us/en/support/articles/000099741/processors/intel-xeon-processors.html)

Interlocked类也不是“每一个方法都写一次位置”：MemoryBarrier只提供相关屏障，Read是相应原子读取；具体RMW方法及其排序按指定合同。现代And／Or返回原值，本次3经And1得到1、再Or8得到9，返回分别3／1；NET10实际公开shape未找到Interlocked.Xor，不能把所有数学／位运算说成已经有同名BCL原子方法。普通Read、release／acquire、full fence和一次CAS提交分别讲范围。
