## 参数这一章讨论什么

本章把方法声明与调用联系起来：参数可以有默认值，可以按名匹配，可以按值或按引用传递，也可以接收可变数量的输入。C#编译器负责语法、类型推断和确定赋值检查；程序集记录参数相关元数据；CLR执行最终的IL调用。语言规则与运行时表示有关，却不能简单认为两者完全相同。

原章回顾的六个主题如下，具体类型例子也保留在相应主题中：

| 主题 | 核心问题 | 使用边界 |
| --- | --- | --- |
| 可选与命名参数 | 可以省略哪些实参，按名称怎样匹配 | 省略默认值通常在调用方编译时补入，库更新须考虑旧调用方 |
| `var` | 初始化表达式怎样确定局部变量类型 | 是静态类型推断，与`dynamic`的动态绑定不同 |
| `ref/out` | 是复制值，还是让被调用方访问调用方变量 | 初始化责任不同，调用方要显式表达传引用意图 |
| `params` | 怎样接收不固定数量的实参 | 原书采用数组形式，展开调用可能分配数组 |
| 参数与返回类型 | API应接受多宽的类型，承诺何种返回能力 | 用满足契约所需的参数抽象，返回能力与未来实现替换须权衡 |
| 常量性 | 是否能禁止经某访问路径修改对象，是否真正不可变 | C#的编译期常量不等同于C++对象常量性或深层不可变 |

原介绍也提到`OptionalAttribute`、`DefaultParameterValueAttribute`及`ParamArrayAttribute`。它们是相关的元数据约定，不意味着每一种可选参数声明必然以三个同样的自定义特性原样保存；参数标志、默认值记录和特定类型的常量表示也参与其中。

## 默认值为什么固化在调用方

<a id="c09-call-site"></a>
### call site是调用方法的地方

原问题疑惑：为什么只改参数默认值，旧调用方仍收到旧值？普通的静态C#调用在编译时发现省略了可选实参，便把当时已知的默认值写入调用代码。运行时传给方法的是一个实际参数值，不是一个“稍后去查询库默认值”的请求。

思考区的整数例E09-01（方法片段）：

```csharp
public static int M(int x = 5) { return x; }
// 调用方写 M()，编译后的调用已经传入 5。
```

库后来改为`M(int x = 10)`，但旧调用方未重编，旧调用仍传`5`；调用方重新编译后才会补入`10`。这与下面的文件名例是不同输入，分别保留。讨论的是编译后的调用行为，不能由此推断所有动态调用、反射调用或其他语言都会采用完全相同的默认值处理方式。[命名与可选实参官方说明](https://learn.microsoft.com/en-us/dotnet/csharp/programming-guide/classes-and-structs/named-and-optional-arguments)。

<a id="c09-makepath"></a>
### 保留`MakePath`的字符串例

原例的方法片段E09-02a：

```csharp
private static string MakePath(string filename = "Untitled")
{
    return string.Format(@"C:\{0}.txt", filename);
}
```

调用`MakePath()`得到字符串`C:\Untitled.txt`。代码只是构造字符串，没有建立文件。`private`版本只能由允许访问它的代码调用；讨论跨程序集库升级时，要把可访问的API放到库中，不能把私有方法说成其他程序集可直接调用。

采用哨兵值的独立方法片段E09-02b：

```csharp
private static string MakePath(string filename = null)
{
    return string.Format(@"C:\{0}.txt", filename ?? "Untitled");
}
```

`null`表示采用当前默认行为；默认文件名由方法体决定。以后只改`??`右侧，旧调用方仍传`null`，却执行新版库中的默认行为。显式传`"Report"`仍得到`C:\Report.txt`，不会被默认逻辑覆盖。原解释也提到把内部默认改成`"NewFile.txt"`；同样传入`null`时会采用新字符串，本例保留固定追加`.txt`逻辑，所以结果是`C:\NewFile.txt.txt`。

<a id="c09-library-experiment"></a>
### 库更新、旧调用方、新调用方的完整过程

跨程序集实验E09-03：先把以下库V1编译成`Api.dll`，再把调用方编译成`Client.exe`。为说明跨程序集调用，把两个API改为`public`并使用不同方法名；这不改变原两个`MakePath`场景的目的。

```csharp
using System;

public static class Api
{
    public static string MakePath(string filename = "Untitled")
    {
        return String.Format(@"C:\{0}.txt", filename);
    }
    public static string MakeSentinel(string filename = null)
    {
        return String.Format(@"C:\{0}.txt", filename ?? "Untitled");
    }
}
```

独立的调用方完整程序：

```csharp
using System;

class Program
{
    static void Main()
    {
        Console.WriteLine(Api.MakePath());
        Console.WriteLine(Api.MakeSentinel());
    }
}
```

Framework编译步骤：先运行`csc /target:library /out:Api.dll Api.cs`，再运行`csc /out:Client.exe /reference:Api.dll Client.cs`。此时运行客户端，两行都是`C:\Untitled.txt`。

库V2只做两处修改：第一方法声明中的默认值变成`"Default.txt"`，第二方法体中的`?? "Untitled"`变成`?? "Default.txt"`。重新编译并替换同名库，保持程序集身份和方法签名不变，暂不重编调用方。

| 运行阶段 | `MakePath()` | `MakeSentinel()` |
| --- | --- | --- |
| 库V1与客户端初版 | `C:\Untitled.txt` | `C:\Untitled.txt` |
| 仅库换成V2，旧客户端保持原二进制 | `C:\Untitled.txt` | `C:\Default.txt.txt` |
| 客户端也针对V2重新编译 | `C:\Default.txt.txt` | `C:\Default.txt.txt` |

这是本机实际观察。原解释用了`"Default.txt"`作为新默认值，但方法还会追加`.txt`，实际结果出现两次扩展名，不能写成`C:\Default.txt`。如果业务只想生成一个扩展名，应改传入不带扩展名的`"Default"`，或重新设计扩展名处理；这与默认值固化机制是两个问题。

<a id="c09-sentinel-boundary"></a>
### 哨兵值的条件：稳定、合法、不与业务含义冲突

原解释列举`null`、`0`和`Guid.Empty`。这些值不能一律称为“无意义”：若`0`或`null`本身是有效业务输入，把它们解释为默认请求会改变业务含义。必须明确契约，并保持用于发信号的默认值稳定。修改方法内部行为免于客户端重编，并不自动保证所有业务兼容性；有的客户端可能依赖旧行为。

反例E09-04a（类型片段，不能编译）：

```csharp
class Example
{
    static void M(System.Guid id = System.Guid.Empty) { }
}
```

`Guid.Empty`是静态只读字段，不能直接作为这里的可选默认表达式，本机报CS1736。保留“空Guid代表默认请求”的原场景，可用语言允许的默认值形式E09-04b：

```csharp
using System;

class Example
{
    static void M(Guid id = default(Guid))
    {
        Console.WriteLine(id == Guid.Empty);
    }
    static void Main() { M(); } // True
}
```

也可用`Guid? id = null`把“未指定”和一个实际Guid值区分开，再在方法内部确定默认行为。可选参数默认值除常量表达式外，还允许规范规定的值类型默认值形式；不能把这些形式理解为运行时任意调用构造器或方法来算默认值。[可选实参官方说明](https://learn.microsoft.com/en-us/dotnet/csharp/programming-guide/classes-and-structs/named-and-optional-arguments#optional-arguments)。

<a id="c09-named-ref-out"></a>
## 命名实参与引用参数的语法

<a id="c09-ref-default"></a>
### 为什么`ref/out`不能指定默认值

普通默认值提供一个值；`ref/out`需要符合语言规则的变量位置，让被调用方读写该变量。字面量`5`不能作为可写的`ref`实参。把“常量没有地址”当作物理内存的普遍事实不够精确，真正决定合法性的是变量与参数规则。

反例E09-05，补齐方法体后仍不能编译：

```csharp
class Example
{
    void Process(ref int value = 10) { value++; }
    void GetResult(out string data = null) { data = "ready"; }
}
```

本机两处均报CS1741。`out`必须在正常返回前完成赋值，调用前则不要求该变量已有值；若方法通过抛异常离开，不是“所有离开方式都必须赋值”。[参数修饰符官方说明](https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/keywords/method-parameters)。

<a id="c09-named-order"></a>
### 位置实参、命名实参与C#版本

完整程序E09-06，保留`Print`例中的Alice、默认年龄20、New York，以及错位命名反例：

```csharp
using System;

class Program
{
    static void Print(string name, int age = 20, string city = "Unknown")
    {
        Console.WriteLine("{0}, {1}, {2}", name, age, city);
    }
    static void Main()
    {
        Print("Alice", city: "New York"); // Alice, 20, New York
        // Print(city: "New York", "Alice"); // 反例：错位命名后跟位置实参
    }
}
```

原书时期规则是命名实参放在位置实参之后；全部按名传递时可以按名称调整匹配次序。现代差异：C#7.2起，处于其正确参数位置的命名实参后可以跟位置实参。例如方法`M(int a, int b)`可调用`M(a: 1, 2)`；但`M(b: 1, 2)`仍不满足规则。本机C#5前一写法报CS1738，C#7.2编译运行输出`1,2`，后一写法报CS8323。不要把“任意顺序”理解为任意混合命名和位置输入都合法。

另外，实参表达式按**调用处写出的顺序**求值，不是先按照参数声明顺序重排再求值。[命名与可选实参](https://learn.microsoft.com/en-us/dotnet/csharp/programming-guide/classes-and-structs/named-and-optional-arguments)、[C#7.2版本历史](https://learn.microsoft.com/en-us/dotnet/csharp/whats-new/csharp-version-history)。

<a id="c09-required-arguments"></a>
### 命名参数不会让必需参数变成可选

完整程序E09-07：

```csharp
using System;

class Program
{
    static void Calculate(int required1, int required2, int optional = 0)
    {
        Console.WriteLine("{0}, {1}, {2}", required1, required2, optional);
    }
    static void Main()
    {
        Calculate(1, 2);                          // 1, 2, 0
        Calculate(required1: 1, required2: 2);    // 1, 2, 0
        // Calculate(required2: 2);               // 反例：缺少required1
    }
}
```

按位置或按名称都能提供必需参数，但不能省掉它。这里的输入和下一例不同，不能合并为同一个`M`调用后省略规则。

<a id="c09-no-comma-gap"></a>
### 不能靠空逗号跳过一个可选输入

完整程序E09-08：

```csharp
using System;

class Program
{
    static void M(int a = 1, int b = 2, int c = 3)
    {
        Console.WriteLine("{0}, {1}, {2}", a, b, c);
    }
    static void Main()
    {
        // M(1, , 3); // 反例：空实参位置，无法编译
        M(1, c: 3);   // 1, 2, 3
    }
}
```

用户引文中的`M(1, , DateTime.Now)`同样是空实参反例。这里还需要一个与`DateTime`输入匹配的方法签名，才能单独讨论类型；它没有让C#获得“空位代表默认值”的语法。命名`c`表达了要提供哪个输入，也避免靠数逗号才能判断。

<a id="c09-named-byref"></a>
### 命名`ref/out`：名称在前，修饰符在冒号后

完整程序E09-09，补齐原`M(ref int x)`的示例方法体：

```csharp
using System;

class Program
{
    static void M(ref int x) { x++; }
    static void Main()
    {
        int a = 5;
        M(x: ref a);
        Console.WriteLine(a); // 6
        M(ref a);             // 传统位置形式，同样合法
        // M(ref x: a);        // 反例：ref不能写在参数名称之前
        // M(ref x: 5);        // 思考区原反例：顺序不合法，5也不是可写变量
        // M(a);               // 反例：普通静态调用缺少ref
        // M(x: ref 5);         // 反例：字面量5不是可写变量
    }
}
```

原正式回答一度写成“在参数名前加`ref/out`”，随后正确示例又把它放在冒号后；正文统一为`参数名: ref 变量`或`参数名: out 变量`。思考区还声称这从C#7.3才允许，这不成立：本机C#4与原书语境的C#5都成功编译命名`ref/out`，C#4起已有命名实参功能。

完整程序E09-10，保留原更复杂的`Process`及两种调用：

```csharp
using System;

class Program
{
    static void Process(ref int x, string name, out bool success)
    {
        success = true;
    }
    static void Main()
    {
        int num = 10;
        bool result;
        Process(ref num, "test", success: out result);
        Console.WriteLine("{0}, {1}", num, result); // 10, True
        Process(x: ref num, name: "test", success: out result);
        Console.WriteLine("{0}, {1}", num, result); // 10, True
    }
}
```

它没有给`x`赋值，故`num`仍是10；`ref`提供修改能力，却不保证一定发生修改。`out`为`result`赋了值，之后可以读取。显式修饰符让阅读者看见传参方式，并与普通`名称: 实参`匹配形式一致。

| 原表中的场景 | 正确形式 | 保留的错误形式 |
| --- | --- | --- |
| 跳过有默认值的中间参数 | `M(1, c: 3)` | `M(1, , 3)` |
| 提供两个必需参数 | `M(1, 2)`或`M(a: 1, b: 2)`，这里M的a/b均必需 | 仅`M(b: 2)`，缺少a |
| 命名引用实参 | `M(x: ref a)` | `M(ref x: a)` |
| 命名输出实参 | `M(result: out data)` | `M(out result: data)` |

每行使用各自的假定签名，不能把整表的`M`误当作上面只有一个`ref int`参数的方法。

<a id="c09-ref-intent"></a>
## `ref/out`为什么要求调用方显式写出

<a id="c09-ref-out-values"></a>
### 明确的是调用方变量的使用方式

原问题认为编译器已经看到方法签名，为什么还要调用方写一次？这是普通C#调用的设计规则：阅读调用处就能看出方法取得了调用方变量的别名，以及调用前后的赋值责任。编译器不是因为无法了解签名才要求写它。不过具体重载解析和诊断也由这些规则决定，不能把规则视为一个现在可以省掉的提示。

完整程序E09-11，保留乘2与输出42两个方法：

```csharp
using System;

class Program
{
    static void UpdateValue(ref int data) { data = data * 2; }
    static void GetResult(out int result) { result = 42; }
    static void Main()
    {
        int x = 10;
        // UpdateValue(x); // 原答的假想调用：实际C#静态调用不能编译
        UpdateValue(ref x);
        Console.WriteLine(x); // 20
        int result;
        GetResult(out result);
        Console.WriteLine(result); // 42
    }
}
```

`ref`要求传入前确定赋值，被调用方可读可写；`out`允许调用前未赋值，被调用方须在正常返回前赋值。CLR方法参数的传引用类型用于表示这两种路径，元数据还可记录`out`方向等信息，C#规定不同的确定赋值责任；“CLR层完全没有任何区别”也过于笼统。

思考区独有输入例E09-12（方法与语句片段）：

```csharp
static void Modify(ref int x) { x = 10; }
// 调用方法体内：
int a = 5;
Modify(ref a);
System.Console.WriteLine(a); // 10
// Modify(a);               // 反例：实际普通C#调用缺少ref
```

这个例子把5改为10，与乘2例的10→20不同。审查者看到`ref a`就知道变量可能改变，调试时应检查前后值；看到`out`就知道正常返回后将获得一个赋值结果。这些是代码阅读和维护的作用，不等于关键字本身保证业务正确。

<a id="c09-unspecified-method"></a>
### `SomeMethod(importantValue)`要结合签名判断

原例给出`importantValue = 100`，然后调用没有定义的`SomeMethod(importantValue)`，询问最后还是不是100。对普通的整数值传递，方法内改自己的形参不会改调用方变量；如果方法需要`ref`，原写法会编译失败，不能说编译器悄悄替你传了引用。

完整程序E09-13补齐两个不同签名，保留原输入100：

```csharp
using System;

class Program
{
    static void SomeMethod(int value) { value++; }
    static void SomeMethod(ref int value) { value++; }
    static void Main()
    {
        int importantValue = 100;
        SomeMethod(importantValue);
        Console.WriteLine(importantValue); // 100
        SomeMethod(ref importantValue);
        Console.WriteLine(importantValue); // 101
    }
}
```

独立的传值/传引用对比E09-14保留原输入5（方法和语句片段）：

```csharp
static void ProcessByValue(int value) { value++; }
static void ProcessByRef(ref int value) { value++; }
// 调用方方法体内：
int a = 5;
ProcessByValue(a);
System.Console.WriteLine(a); // 5
int b = 5;
ProcessByRef(ref b);
System.Console.WriteLine(b); // 6
```

如果`ProcessByRef`不写入形参，`b`也不会变；`ref`表达能力与意图，实际结果仍取决于方法体。

<a id="c09-reference-object"></a>
### 不写`ref`也可能修改对象：保留账户例并纠正用途

原答用`account.Withdraw(100)`说明没有`ref`可能看不出状态会改变。但它修改的是账户对象的余额，并不是改传入的整数100，也不是把调用方的`account`变量换成另一个引用。

完整程序E09-15仅为对象状态示例，不涉及真实账户：

```csharp
using System;

class BankAccount
{
    public int Balance { get; private set; }
    public BankAccount(int balance) { Balance = balance; }
    public void Withdraw(int amount) { Balance -= amount; }
}

class Program
{
    static BankAccount GetMyAccount() { return new BankAccount(150); }
    static void Main()
    {
        BankAccount account = GetMyAccount();
        account.Withdraw(100);
        Console.WriteLine(account.Balance); // 50
    }
}
```

实例方法可以修改其对象；把对象引用按值传给另一方法，也可以通过复制的引用修改同一对象。若要让被调用方**替换调用方变量保存的对象引用**，才通常需要`ref/out`。所以“不含`ref/out`的调用不会改变任何状态”不是本章规则。

原介绍里的泛型`Swap`例E09-16（完整程序）补齐该引用传递用途：

```csharp
using System;

class Program
{
    static void Swap<T>(ref T first, ref T second)
    {
        T temp = first;
        first = second;
        second = temp;
    }
    static void Main()
    {
        int a = 1, b = 2;
        Swap(ref a, ref b);
        Console.WriteLine("{0}, {1}", a, b); // 2, 1
    }
}
```

`T`也可以是引用类型，此时交换的是两个变量中保存的引用，不是把对象内部所有字段互换。

<a id="c09-language-comparison"></a>
### 与C++、Java的对照及COM例外

保留原比较表的三个语言：

| 语言/场景 | 调用方的表达 | 与变量修改的关系 |
| --- | --- | --- |
| 普通C#的`ref/out`参数 | 声明和调用处都有相应修饰符 | 传递变量位置，规则明确初始化责任 |
| C++的引用参数`T&` | 声明中表达引用，通常调用处不再写`&` | 被调用方可按类型规则经该引用操作对象/变量 |
| Java参数 | 按值传递，包括复制对象引用值 | 不能给调用方变量换值，却可修改可变对象的内容 |

原另一轮介绍还提到COM互操作中C#允许某些调用省略`ref`。这是针对COM API的有限规则，不是普通C#方法随意省略`ref/out`；也不能把它解释为调用方变量仍必然被原样传引用并修改。[COM与C#引用参数说明](https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/keywords/method-parameters)。

<a id="c09-constness"></a>
## C++常量性与C#不可变类型

<a id="c09-cpp-const"></a>
### 对象的常量性与编译期常量是两件事

用户先要求解释原书9.6，随后追问：“C#不是有`const`关键字吗？”C++可以用`const`限定成员函数或通过`const T&`限制某访问路径的修改；C#的`const`主要表达编译期能确定的值，不能直接提供“任意对象图永不可改”或“某引用类型方法不改对象”的通用契约。

C++完整示例E09-17（语义核验，未安装/运行C++编译器）。保留`MyObject`的读取、`mutate`赋20、`const&`调用，补默认初始化避免读取未初始化整数：

```cpp
#include <iostream>

class MyObject {
private:
    int value = 0;
public:
    int getValue() const {
        return value;
        // value = 10; // 反例：const成员函数不能这样写非mutable成员
    }
    void mutate() { value = 20; }
};

void printValue(const MyObject& obj) {
    std::cout << obj.getValue() << '\n';
    // obj.mutate(); // 反例：不能经这个const引用调用非const成员函数
}

int main() {
    MyObject obj;
    printValue(obj); // 0
    obj.mutate();
    printValue(obj); // 20
}
```

`const`成员函数不意味着任意所指对象、全局状态或`mutable`成员也绝对不能改变。它表达的是C++类型系统规定的访问限制，不能缩成“运行时啥都不能改”。

<a id="c09-const-cast"></a>
### `const_cast`不是修改真正`const`对象的合法通行证

原`Deceptive`例E09-18保留`secret=0`、`getSecret`和写42，同时明确底层对象的条件：

```cpp
class Deceptive {
private:
    int secret = 0;
public:
    int getSecret() const {
        const_cast<Deceptive*>(this)->secret = 42;
        return secret;
    }
};

int main() {
    Deceptive mutableObject;                // 对象本来不是const
    const Deceptive& view = mutableObject;
    int value = view.getSecret();           // 可写底层非const对象，value为42

    const Deceptive immutableObject;
    // immutableObject.getSecret();          // 反例：试图写真正const对象，未定义行为
    return value == 42 ? 0 : 1;
}
```

移除的是访问路径上的限定。若对象本来不是`const`，示例中的写入可以成立；若对象本来是`const`，尝试修改其非`mutable`状态属于未定义行为，不能承诺“运行时仍正常改成42”。编译通过不证明行为合法。[C++工作草案dcl.type.cv](https://eel.is/c++draft/dcl.type.cv)。

原书用“撒谎”表达常量访问路径与真正不可变并非同一保障，可以保留这个讨论目的；正文不把未定义行为当作可依赖的正常功能。

<a id="c09-clr-constness"></a>
### CLR为何没有通用的对象常量性验证

原解释提出三个方面：持续验证写入的成本；对象图、反射与非托管互操作的复杂度；类型设计中怎样划定不可变范围。例如只固定一个对象引用，其所指列表是否也要禁止修改？是否要传递到列表元素引用的其他对象？这些是不同的契约。

原书讨论的是如果加入普遍运行时写保护会涉及的权衡，不是对某种现代实现做了性能测量。不能从这些理由推导“任何不可变设计都零运行时开销”或“任何语言都不可能在编译期提供额外只读检查”。C#后来已有`in`、`readonly struct`、只读结构体成员等功能，但它们依然不是任意引用对象图的深层写保护。

<a id="c09-immutable-string"></a>
### `String`通过API设计保持其值不变

语句片段E09-19：

```csharp
string s1 = "Hello";
string s2 = s1.ToUpper();
System.Console.WriteLine(s1); // Hello
System.Console.WriteLine(s2); // HELLO
// s1[0] = 'h';                // 反例：字符串索引器没有可用的set
```

原字符串内容未改变，得到转换后的字符串值。`Replace`、`ToUpper`这类方法不修改当前实例，但“每次一定建立新对象”过强：在不需要变化等情况下，实现可以复用已有字符串。不可变性关注的是可观察的字符串值不被修改，不是每次调用的引用身份都不同。

<a id="c09-person-immutable"></a>
### 通过返回新实例表达“修改”

完整程序E09-20保留原`Person`的Alice、30→31及`WithAge`：

```csharp
using System;

public class Person
{
    public readonly string Name;
    public readonly int Age;
    public Person(string name, int age) { Name = name; Age = age; }
    public Person WithAge(int newAge) { return new Person(Name, newAge); }
}

class Program
{
    static void Main()
    {
        Person person = new Person("Alice", 30);
        Person olderPerson = person.WithAge(31);
        Console.WriteLine("{0}, {1}", person.Name, person.Age);           // Alice, 30
        Console.WriteLine("{0}, {1}", olderPerson.Name, olderPerson.Age); // Alice, 31
    }
}
```

正常API没有改原实例，而是创建另一个实例。两个字段类型`string`与`int`也适合这个例子的不可变值契约。若字段换成可变集合，单独加`readonly`就不再说明整个对象不可变。

原提到的现代工具分别有作用范围：`readonly`限制字段赋值，`init`限制普通源码中的属性赋值阶段，`record`提供记录语义与`with`等表达，`System.Collections.Immutable`提供不可变集合API。它们都不能通过一个关键字自动使整个对象图深层不可变；记录类型可以自行声明可写成员，普通`record struct`的位置成员通常还可以设置。[readonly官方说明](https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/keywords/readonly)、[record官方说明](https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/builtin-types/record)。

| 原比较维度 | C++的`const` | C#中的类型设计与相关功能 |
| --- | --- | --- |
| 机制 | 对象或访问路径的类型限定 | 编译期常量、只读字段/访问器等不同规则，配合API设计 |
| 可靠性 | 不能合法修改真正const的非mutable状态；const视图不保证底层对象原本const | readonly引用仍可指可变对象；需要明确深层契约 |
| 性能 | 常量限定本身不是每次写入都做运行时检查的API | 是否分配新对象、复制数据、检查条件取决于实现，不能统一称零成本 |
| 灵活性 | 可限定成员函数和引用等访问路径 | 可设计只读入口、返回新对象、不可变集合等 |
| CLR支持 | 非托管C++不依赖CLR | CLR有相关字段/签名表示，但没有本章设想的通用对象图const契约 |

<a id="c09-const-metadata"></a>
## `const`、`readonly`、`init`和元数据

<a id="c09-const-types"></a>
### `const`的值必须满足语言常量规则

原代码E09-21（类型片段）：

```csharp
class Constants
{
    public const int Max = 100;
    public const string Name = "hello";
    // public const System.DateTime T = new System.DateTime(); // 反例：不是允许的const类型
}
```

`int`与字符串这两个例子合法，`DateTime`例不合法。但是可用类型不止“primitive/string”：还包括枚举、`decimal`等允许的类型；除字符串外的引用类型可以把`null`声明为常量，却不能把`new SomeClass()`实例声明为编译期常量。例如`const object Empty = null`合法。[const官方说明](https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/keywords/const)。

常量字段仍有元数据，反射可以发现它。普通的整数常量使用`Literal`标记，调用方通常直接嵌入其值；“运行时没有该符号”应改为“普通调用不必读取这个字段的运行时存储”。用户手写的`const`也不会仅因是常量就自动带`CompilerGeneratedAttribute`。

`decimal`是一个需要注意的表示特例：本机C#5的`const decimal`反射显示`IsLiteral=false`、`IsInitOnly=true`，并有相关十进制常量特性表示，不能由整数常量反射结果概括所有常量。

<a id="c09-readonly-reference"></a>
### 固定引用不等于固定引用对象的内容

完整程序E09-22保留正式答的列表与思考区的数组两个不同场景：

```csharp
using System;
using System.Collections.Generic;

class Example
{
    private readonly List<int> list = new List<int>();
    private readonly int[] array = { 1, 2 };
    static void Main()
    {
        Example value = new Example();
        value.list.Add(7);
        value.array[0] = 7;
        Console.WriteLine(value.list[0]);  // 7
        Console.WriteLine(value.array[0]); // 7
        // value.list = new List<int>();   // 反例：此处不能给readonly字段换引用
    }
}
```

字段保存的引用未变，但列表和数组内容都变了。`readonly`在声明初始化器、相应构造器等允许的上下文中可赋值；现代`init`访问器也有其针对声明类型只读实例字段的规则。它不是面向任意对象、所有反射及非托管操作的通用“内存永不写入”承诺。反射对只读字段的行为还受静态/实例字段和运行时版本影响，不能宣称反射在所有环境都随便改。

<a id="c09-keyword-comparison"></a>
### 三个关键字的层次不同

| 功能 | 主要对象 | 关键表示与使用含义 |
| --- | --- | --- |
| `const` | 允许类型的编译期常量字段/局部量 | 调用方可嵌入值；整数常量字段有Literal，decimal等表示需分别判断 |
| `readonly` | 字段；现代语法另有只读结构体/成员 | 字段有InitOnly等表示，限制普通代码中的赋值位置；引用对象内容不自动冻结 |
| `init`（C#9+） | 属性/索引器初始化访问器 | setter签名使用`IsExternalInit`所需修饰符；语言约束初始化赋值阶段，不是CLR在每次调用时检查对象已锁定 |

`init`不能与字段的`IsInitOnly`标志混为一谈。本机反射可找到`init`属性的setter，返回参数的必需修饰符包含`IsExternalInit`，再经反射调用后属性值实际改变，说明它不是原回答想象的运行时对象写锁。JSON对`init`属性的正常反序列化属于[第10章](README.md#chapter-10)的合同讨论。[init功能规范](https://github.com/dotnet/csharplang/blob/main/proposals/csharp-9.0/init.md)。

<a id="c09-inlining"></a>
## 内联的两种含义

<a id="c09-inline-analogy"></a>
### 保留餐厅与菜谱的类比

原追问“内联是什么”来自前一轮的常量说明。原类比是去餐厅点鱼香肉丝：通常调用像服务员把请求送到厨房，再把结果送回；内联像菜单背面已经有菜谱，在使用处直接展开做法，省去那段传递过程。

这个“复制粘贴”类比说明展开效果，不代表编译器用纯文本替换源码；常量值嵌入与JIT方法体内联又是两个不同阶段。实际调用成本也不限于固定的压栈/出栈步骤，会受调用约定和优化影响。

<a id="c09-constant-inline"></a>
### 常量值嵌入：`MaxCount`从100改为200

独立跨程序集例E09-23，保留原`Utils.MaxCount`名称和输入：

```csharp
// Assembly A：编译为Utils.dll
public class Utils
{
    public const int MaxCount = 100;
}
```

调用方B完整程序：

```csharp
using System;

class Program
{
    static void Main()
    {
        int x = Utils.MaxCount;
        Console.WriteLine(x); // 100
    }
}
```

编译B时，整数100嵌入B的IL。下面是相关IL片段，表示推入整数100，并非完整方法：

```il
ldc.i4.s 100
```

A后来把常量改为200并重新编译，未重编的B仍用100；针对新版A重编B才用200。若改成通常的`static readonly`字段，则调用方IL通常保留字段读取路径，运行时可取得所加载类型中的字段值，两者的版本行为不同。此处不能再把C#常量解释成普通运行时只读变量，也不能说元数据中字段已消失。常量嵌入说明的是数值传播和库版本；对象级常量性涉及写入契约，两者不能作因果推论。

<a id="c09-method-inline"></a>
### 方法内联：`Add(3,5)`的展开与常量折叠

完整程序E09-24（原答箭头方法写法属于C#6+，原书语境可以改成普通方法体）：

```csharp
using System;

class Program
{
    static int Add(int a, int b) => a + b;
    static void Main()
    {
        int result = Add(3, 5);
        Console.WriteLine(result); // 8
    }
}
```

假如JIT决定内联，可以把加法逻辑并入调用处；随后还可能把常量表达式折叠为8。原答的等价语句片段E09-25保留如下，用来说明语义，不冒充实际反编译结果：

```csharp
int result = 3 + 5;
System.Console.WriteLine(result); // 8
// 对这个恒定表达式，还可用8代替加法结果。
```

输出8本身不能证明方法已经被内联；没有内联也能得到8。方法可能没有在该调用路径产生独立的机器码，但不能由某个调用被内联断言方法在整个程序所有路径都不存在。

C#通常由JIT决定具体内联策略；`MethodImplOptions.AggressiveInlining`是“尽可能内联”的提示，`NoInlining`可禁止内联，并非程序员完全不能影响它。C++的`inline`也不是必须手写才可能内联，更不保证写了必定内联。原解释用“JIT比人类更懂”表达自动选择的意图，正文以可核验的规则说明。[MethodImplOptions官方API](https://learn.microsoft.com/en-us/dotnet/api/system.runtime.compilerservices.methodimploptions)。

| 原优缺点表的项目 | 正确理解 |
| --- | --- |
| 消除调用路径 | 可能减少调用成本，不保证所有例都“速度极快” |
| 更深的优化 | 展开后可能帮助常量折叠等优化，须区分两种优化 |
| 代码膨胀 | 多处展开可能增加机器码体积，具体净变化由优化决定 |
| 版本维护问题 | 跨程序集常量嵌入会固化旧值；不能把它概括成所有JIT内联都同样固化旧库值 |

<a id="c09-summary"></a>
## `var`、`params`及API类型选择

<a id="c09-var"></a>
### `var`是局部静态类型推断

原回顾使用匿名类型和复杂泛型`Dictionary<string,int>`作为省去重复类型名的场景。语句片段E09-26：

```csharp
var counts = new System.Collections.Generic.Dictionary<string, int>();
counts["Alice"] = 1;
var person = new { Name = "Alice", Age = 30 };
System.Console.WriteLine(counts[person.Name]); // 1
```

`counts`仍有确定的静态类型，并不是运行时随意变成任意类型。`var`用于这种隐式类型声明，不能代替字段、普通方法参数或返回类型位置的类型名；后来的解构、`out var`等场景也属于各自的类型推断规则。`dynamic`则让某些操作延迟到运行时绑定，其元数据表示和对象实际类型也不能混称为“一个新的运行时类型”。[隐式类型局部变量](https://learn.microsoft.com/en-us/dotnet/csharp/programming-guide/classes-and-structs/implicitly-typed-local-variables)。

<a id="c09-params"></a>
### `params`的展开形式与分配边界

原书时期`params`参数位于末尾，是一维数组，相关元数据包括`ParamArrayAttribute`。完整程序E09-27补足回顾中的最小输入场景：

```csharp
using System;

class Program
{
    static int Sum(params int[] values)
    {
        int total = 0;
        foreach (int value in values) total += value;
        return total;
    }
    static void Main()
    {
        Console.WriteLine(Sum(1, 2, 3));            // 6：展开实参形式
        int[] values = { 1, 2, 3 };
        Console.WriteLine(Sum(values));             // 6：传入已有数组
    }
}
```

展开多个实参通常需要相应数组；传已有数组的正常形式不会仅因`params`再包装一个新数组。空输入和JIT的具体优化还要看版本，不能说“每次调params一定new数组”。原回顾提到`String.Concat`为常见输入数量提供重载，意图是减少某些调用路径的包装成本；不能从这个设计断言所有重载在所有版本都绝不分配。

现代差异：C#13把参数集合扩展到一些非数组集合形式，包括适用的span等，原书的“一维数组”规则是历史形式。[参数集合官方参考](https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/keywords/method-parameters#params-modifier)。

<a id="c09-api-types"></a>
### 参数“弱”、返回“强”是API契约的权衡

原回顾用`IEnumerable<T>`和`Stream`说明参数不应无必要地要求某一个具体实现。例如只是遍历数据，就不必强制传`List<T>`；只需要流接口能力，就不必强制传`FileStream`。所谓“弱”是满足操作所需的最小类型契约，不是把任何参数都改成`object`。

原返回例有`FileStream`、`List<String>`与`IList<String>`：较具体的返回类型让调用方可以使用更多已承诺的功能，也使API更依赖当前实现；返回接口可能给以后换实现留下空间。它不是“返回越具体永远越好”的规则。`IList<T>`本身仍表达一定的可变集合能力，返回它也不自动成为只读契约。

把这一点和前文联系起来：参数形式、默认行为、对象可变性、返回能力都属于公开契约。设计时要明确调用方真正需要什么，再决定哪些细节应稳定、哪些行为允许随库更新变化。
