<a id="c18-route"></a>
## 特性生命周期：标签、元数据、消费者

特性让程序声明额外信息。常见自定义特性由直接或间接派生System.Attribute的类定义；应用语法记录构造器参数和命名成员值，实例查询在运行时按这些数据调用构造器/赋命名成员。编译应用标记本身不执行该构造器。这个“配方”模型适合普通定制特性，但不能覆盖所有特殊元数据：Serializable、DllImport、AssemblyVersion等会由编译器编码到专门的标志或表中。

`AttributeUsage`也是特性，其构造参数是AttributeTargets枚举，ValidOn指定可应用目标；AllowMultiple默认false，重复同一单用特性是编译错误；Inherited默认true，影响支持继承查询的API。没有写AttributeUsage相当于All、单用、可继承。继承查询不会在派生类型元数据里复制一份原标记；标记是否记录、怎样查询、是否构造对象是三个不同阶段。

<a id="c18-use"></a>
## 先会应用：目标、参数与后缀

原四个用途：`[DllImport("Kernel32")]`提供本机入口声明；`[Serializable]`参与传统formatter的类型可序列化合同；`[assembly: AssemblyVersion("1.0.0")]`设置程序集版本；`[Flags]`声明枚举值按位标志使用，并影响如ToString的解释，不改变位运算或整数载荷。Flags详见[第15章](第15章-枚举类型和位标志.md)。

特性可以应用于程序集、模块、类型、字段、方法、参数、返回值、属性、事件、泛型参数等，但每个具体特性还受ValidOn限制。原目标片段保留为示意，省略号不是可编译实参：

```text
[assembly: SomeAttr]      // 贴到整个程序集
[return: MarshalAs(...)]  // 贴到方法返回值
[param: In, Out]          // 贴到参数
```

多数目标可由语法位置确定；泛型参数列表内也可直接写特性，不是一概必须另写typevar前缀。返回值须区分方法本身和return目标，程序集/模块全局应用须明确assembly/module。与第10/11章相连的历史边界：旧Framework csc/C#5在自动属性上忽略field目标并给CS0657；Roslyn C#7.3已有支持。**事件的field目标在旧C#5就可用**，不能把属性限制移到事件。作者复用第10章真实同源日志；本章事件field:NonSerialized补充探针在旧compiler反射True/True，无需重跑锁章。

<a id="c18-positional"></a>
原DllImport应用片段：

```csharp
[DllImport("Kernel32", CharSet = CharSet.Auto, SetLastError = true)]
```

"Kernel32"是构造器位置实参，该构造器确实要求它；CharSet和SetLastError是命名公共成员值。位置实参不意味着所有特性构造器参数永远必填：自定义构造器可有可选参数。补充探针`OptionalAttribute(int x=10)`配合`[Optional(Name="hello")]`得到10/hello。命名特性参数的`Name = value`指字段/属性赋值，和普通调用中的`parameterName: value`不是同一个语法角色。

<a id="c18-equivalent"></a>
四组原写法分别保留。将每组应用到一个合法枚举声明上，表示相同两个标记；不是把四组全叠到一个单用特性目标上：

```csharp
[Serializable][Flags]
[Serializable, Flags]
[FlagsAttribute, SerializableAttribute]
[FlagsAttribute()][Serializable()]
```

可分开方括号、可逗号组合、无参构造的括号可省、Attribute后缀可省。顺序不规定业务执行次序。四个独立枚举的本机检查都具有Serializable状态与Flags标记。

<a id="c18-suffix"></a>
### 为什么 Attribute 后缀可以省略

这是C#名称解析规则，不是CLR自动把运行时名字改短。非逐字标识符会尝试原名字和追加Attribute的名字，并只接受真正派生自Attribute的候选：恰好一个成功才可用。若Foo是普通非Attribute类、FooAttribute才是特性，`[Foo]`仍可解析到后者；不是只要两个类名都存在就必歧义。

两者都是真特性时，原两环境实际诊断是CS1614，源CS0104不准确。原@两行修正注释后保留：

```csharp
[@Foo]       // 只匹配 Foo，不匹配 FooAttribute
[@FooAttribute] // 只精确匹配FooAttribute，不再追加Attribute查找
```

`[@Foo]`只查Foo，`[@FooAttribute]`只查FooAttribute；即使还有FooAttributeAttribute，也不会再追加后缀。若只定义FooAttribute，`[@Foo]`不能借后缀找到它。短名Serializable/DllImport的类型名仍是SerializableAttribute/DllImportAttribute；特殊元数据可能没有对应普通CA row，不能将“反射可以表示该特性”误说成文件里必有同样命名的一条CA记录。[C#特性名称解析](https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/language-specification/attributes#233-attribute-specification)

## “允许序列化”在哪里实现

用户的关键疑惑是：贴Serializable就能序列化，允许动作究竟在哪？SerializableAttribute不实现序列化算法；传统BinaryFormatter/SoapFormatter等消费者按照类型状态、字段与序列化合同执行过程。消费者模型也包括编译器和CLR，并不一定是应用代码调用GetCustomAttribute。

原SerializableAttribute空构造器形状保留为**框架类型的简化示意，不定义一个新的System同名类型来代替它**；补上其不继承的usage范围：

```text
namespace System
{
    [AttributeUsage(AttributeTargets.Class | AttributeTargets.Struct | AttributeTargets.Enum | AttributeTargets.Delegate, Inherited = false)]
    public sealed class SerializableAttribute : Attribute
    {
        // 注意：构造器是空的，没有任何逻辑
        public SerializableAttribute() { }
    }
}
```

Serializable是伪特性：对本例自定义class，compiler写TypeAttributes.Serializable标志，而非普通CustomAttribute记录；Type.IsSerializable不是简单在底层调用Attribute.IsDefined。反射可能合成伪特性的观察结果。派生类型不会仅因基类标了Serializable就自动获得自己的Serializable状态。

原formatter检查片段保留为**教学伪代码，不是从BinaryFormatter真实源码逐字抄录**；原使用了C#6插值，第四版语境以字符串拼接亦可表达：

```csharp
// BinaryFormatter.Serialize 内部大致逻辑
internal static void CheckSerializable(Type t)
{
    if (!t.IsSerializable)   // 查询类型的可序列化状态；不等于底层调用Attribute.IsDefined
        throw new SerializationException(
            $"Type '{t}' is not marked as serializable.");
}
```

这段意图是说明消费者可以拒绝不符合其合同的类型；并非所有serializer都要求Serializable。DataContractSerializer可支持多种合同，JSON等也有自己的模型。现代.NET9起内置BinaryFormatter实现不再可用，.NET10不能拿现代运行失败倒判Framework原行为；更完整历史流程留到[第24章入口](README.md#chapter-24)。[官方迁移范围](https://learn.microsoft.com/en-us/dotnet/standard/serialization/binaryformatter-migration-guide/)

<a id="c18-consumer-table"></a>
七个原消费者用途逐行保留：

<a id="c18-consumer-table-detail"></a>
| 特性 | 贴它的你 | 真正读它、干活的那一方 |
| --- | --- | --- |
| `[Serializable]` | 业务代码 | 传统BinaryFormatter/SoapFormatter及可识别Serializable合同的DataContractSerializer；并非所有serializer必需此标记 |
| `[DllImport("xxx")]` | 业务代码 | **CLR 的 Interop 层**（加载 DLL、绑函数、marshal 参数） |
| `[Obsolete]` | 业务代码 | **C# 编译器**（编译期报 warning/error） |
| `[Conditional("DEBUG")]` | 业务代码 | **C# 编译器**（条件不满足就不把调用指令 emit 进 IL） |
| `[Test]`（NUnit）；xUnit使用`[Fact]`/`[Theory]` | 测试代码 | **测试 Runner**（扫描程序集，找带 `[Test]` 的方法来跑） |
| `[Authorize]` (ASP.NET) | Controller/Action | 历史ASP.NET MVC过滤器/相应授权管道；现代端点授权可由中间件读取元数据 |
| `[Table("Users")]` (EF) | 实体类 | **EF Core 的模型构建器**（把类映射到哪张表） |

DllImport的消费者是互操作实现，处理加载、函数绑定和封送；Obsolete的消费者是compiler，警告或拒绝调用，但其标记仍可存在元数据中；Conditional由compiler决定调用/标记的记录；测试Runner读取其约定的标签，[NUnit的Test](https://docs.nunit.org/articles/nunit/writing-tests/attributes/test.html)与[xUnit的Fact/Theory](https://xunit.net/docs/getting-started/v2/getting-started)名称要区分；Authorize、EF的Table("Users")由相应框架解释。原“所有Attribute派生类逻辑零行”错误：构造器、setter或其它方法都能执行用户逻辑，下面危险构造器正说明这一点。声明标签不会凭空自动运行任意业务功能，也不强制消费者必须用实例查询。

<a id="c18-autorun"></a>
### AutoRun 小例把声明和消费者连起来

原完整场景保留，补必要using；表达式体方法是C#6语法：

```csharp
using System;
using System.Reflection;

// 1. 定义（纯数据，无逻辑）
[AttributeUsage(AttributeTargets.Method)]
public class AutoRunAttribute : Attribute { }

// 2. 贴标签
class Program
{
    [AutoRun]
    static void Hello() => Console.WriteLine("跑了");
    
    static void Main()
    {
        // 3. 消费者：启动时任扫一遍，找到就 Invoke
        var methods = typeof(Program).GetMethods(BindingFlags.Static | BindingFlags.NonPublic);
        foreach (var m in methods)
        {
            if (m.IsDefined(typeof(AutoRunAttribute), false))
                m.Invoke(null, null);
        }
    }
}
```

Hello输出“跑了”，因为Main扫描到它再Invoke；AutoRun自身不是自动执行器。原后续追问的同输入片段用来对照存在性与Order数据需求，连同原注释保留：

```csharp
if (m.IsDefined(typeof(AutoRunAttribute), false))   // 18.4 的 API
    m.Invoke(null, null);
```

`m.IsDefined(..., false)`在这个普通MethodInfo场景不构造AutoRun实例，随后**执行的是Hello方法**。没有参数无需读取实例；若另用`[AutoRun(Order = 10)]`，须先给AutoRunAttribute新增public Order成员，这在源原定义中没有，属于补充。可以请求实例读取Order，也可以用CAD的NamedArguments读取后排序，不能说参数排序只剩GetCustomAttribute一条路。

<a id="c18-parameters"></a>
## 应用参数是可编码数据，不是任意运行时对象

Attribute派生类仍是普通类；可有普通构造器/字段/属性以及任意内部数据。限制针对方括号中的attribute application使用哪些构造实参/命名成员值，不能反向说该类所有成员都只能用常量类型，或普通`new Attr(...)`也受同一表达式限制。

<a id="c18-parameter-table"></a>
原四类表补齐其遗漏，修正Type编码：

<a id="c18-parameter-table-detail"></a>
| 分类 | 允许的具体类型 |
| --- | --- |
| 简单类型 | bool、byte、sbyte、char、short、ushort、int、uint、long、ulong、float、double、string；另有object（值仍须可编码） |
| 枚举 | 任意 `enum`（本质是整型） |
| Type | System.Type；应用中用typeof(Foo)等合法typeof表达式，值按类型名字串编码 |
| 数组 | 允许参数类型的一维零基数组，例如int[]、string[]；元素仍受应用表达式限制 |

不允许decimal/DateTime等任意值类型或List/Dictionary等任意对象值；允许的object参数也不能让`new object()`变成合法常量。AttributeUsage的AttributeTargets枚举实参是本章T中的独立联系。[参数类型与表达式规范](https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/language-specification/attributes#2324-attribute-parameter-types)

<a id="c18-blob-string"></a>
### 10 和 hello 存在哪里

原输入：

```csharp
[MyAttr(10, "hello")]
```

普通CA记录关联目标、构造器和一个#Blob；例中10编码为Int32，hello编码为带长度的UTF8 SerString，不是#US堆偏移。编译应用本身不new特性实例。两compiler产物的真实PEReader观察均得到：

```text
01 00 | 0A 00 00 00 | 05 68 65 6C 6C 6F | 00 00
prolog   Int32=10      SerString="hello"    命名成员数0
```

这是实际blob格式说明，不是另造属性表。#US实际大小在两产物是8/4字节，不因此宣称整个#US为空；这里的结论是此实参在blob里直接编码，不按#US索引存储。[CLI II.21.2、II.22.10、II.23.3](https://www.ecma-international.org/wp-content/uploads/ECMA-335_6th_edition_june_2012.pdf)

<a id="c18-parameter-negative"></a>
原三种非法应用片段保留，假设有匹配MyAttr构造器：

```csharp
[MyAttr(DateTime.Now)]   // ❌ DateTime 不是常量
[MyAttr(new object())]   // ❌ new 表达式
[MyAttr(GetValue())]     // ❌ 方法调用
```

DateTime.Now、GetValue()依赖运行时；普通new object()也不属于可编码attribute argument。`new int[]{...}`是规范允许的特定数组形状，不能从“某些new不合法”推导所有new表达式都非法。

<a id="c18-blob-type"></a>
原typeof(FileStream)与GetType对照分别保留：

```csharp
[MyAttr(typeof(FileStream))]
```

```csharp
[MyAttr(fileStream.GetType())] // ❌ 运行期才能知道
```

typeof说明一个合法确定类型，fileStream.GetType是执行方法，依赖当前对象。**Type实参值**在CA blob中编码为规范类型名字SerString，可带程序集限定；不是把TypeRef/TypeDef token当实参载荷写进去。构造器引用本身则使用相应元数据引用，这两层不能混为一个token。本机两个真实产物分别编码FileStream加mscorlib或System.Runtime限定；现代System.Runtime可为引用/转发外观，运行时实际类型来自实现程序集，不等于读取时一定新增System.IO程序集。

<a id="c18-blob-array"></a>
原MyAttr/Values/Test完整声明保留（get-only自动属性为C#6）：

```csharp
[AttributeUsage(AttributeTargets.Class)]
public class MyAttr : Attribute
{
    public int[] Values { get; }

    public MyAttr(int[] values)
    {
        Values = values;
    }
}

[MyAttr(new int[] { 1, 2, 3 })]
class Test { }
```

其应用数组1/2/3在blob中记录长度3和三个Int32元素值，不是先生成某static readonly数组再保存对象引用。请求实例时会按数据构造实际数组及特性；CAD给typed argument集合，另在下节说明。原数组对照中的一维零基条件和元素白名单保留。

<a id="c18-enum-value"></a>
原枚举例：

```csharp
enum Color { Red, Blue }

[MyAttr(Color.Red)]
```

Color.Red在此为0，编译时记录底层值。改变enum声明的名字/顺序/值，已编译的CA数据不会自行重写；重新编译才会按新常量记录，加载/部署条件另见[第15章常量版本规则](第15章-枚举类型和位标志.md)。这不是表明枚举参数保存名字来动态跟随新定义。

<a id="c18-values-original"></a>
所有不同原输入/非法对照保留如下，属于独立应用片段，各自须有合适的MyAttr构造器；不是把不相容片段一次粘贴到原int[]构造器上：

```csharp
// ✅ 合法
[MyAttr(42)]
[MyAttr("abc")]
[MyAttr(typeof(string))]
[MyAttr(new int[] {1,2})]
[MyAttr(MyEnum.A)]

// ❌ 非法
[MyAttr(DateTime.Now)]
[MyAttr(new List<int>{1,2})]
[MyAttr(new Dictionary<string,int>())]
[MyAttr(new FileStream(...))]
[MyAttr(GetValue())]
```

42、abc、typeof(string)、数组1/2和MyEnum.A都有不同值/类型作用；DateTime.Now、List1/2、Dictionary、FileStream实例构造、GetValue各自非法。`new FileStream(...)`的省略号是概念形状，不能当可编译程序。作者实际正例和可编译负例保留原值域，未运行真实文件打开。

<a id="c18-named-data"></a>
原DllImport命名成员例和概念赋值分别保留：

```csharp
[DllImport("kernel32", CharSet = CharSet.Auto)]
```

```csharp
var attr = new DllImportAttribute("kernel32");
attr.CharSet = CharSet.Auto;
```

对普通特性，取得实例时会使用编码值设置命名成员；这不意味着compile阶段真的执行该setter。DllImport本身还有伪特性/专用interop元数据，不能将这个普通对象赋值片段视为编译器实际执行过程。

`public string Name {get;set;}`可作为命名特性成员；`public DateTime Time {get;set;}`的**普通属性声明也合法**，只是不能被用作此类application中的命名特性参数。作者实测普通类定义编译成功，`[A(Time=default(DateTime))]`得到CS0655。原“DateTime属性本身打叉”应限定使用场合。

<a id="c18-query"></a>
## IsDefined、实例查询与数据查询

<a id="c18-write-read-one-a"></a>
原追问用另一组具体输入说明写入和读取的对偶，不能由10/hello或1/typeof(Bar)替代：

```csharp
[Foo(1, "a")]
```

这是应用片段，假设FooAttribute有可访问的`FooAttribute(int, string)`构造器和允许该目标的usage。compiler记录构造器位置数据1与a；运行时数据查询可读到两位置参数，而实例查询可据此调用FooAttribute(1,"a")并设置另有记录的命名成员。原输入本身没有展示任何命名成员赋值，不自行新增命名参数。它与下一段普通CA配方/实例查询形成写→读关系，片段按已核参数/实例规范静态核验，未无因重跑57实证。

原“元数据是配方”的用途保留，但Serializable不是普通CA示例。原错误示意明确保留供纠正：

```text
Parent: TypeDef → MyClass
Type: TypeRef → SerializableAttribute
Constructor Args: (empty)
Named Args: (empty)
```

它把Serializable写成普通CA row，并把Type列解释成TypeRef，均不是该场景的真实文件形状。普通Author("Jeffrey")才可用如下正确概念形状说明（**补充对照**）：目标Book的TypeDef，构造器是AuthorAttribute..ctor(string)的MethodDef/MemberRef关联，Value blob中有Jeffrey及命名参数数据。真实元数据探针对SerializableCase看到Serializable标志true且CA row数0；反射可显示伪特性，不等于实际存在那一行。

<a id="c18-query-signatures"></a>
原三个API入口签名保留为API形状，不是可编译方法定义：

```text
bool Attribute.IsDefined(MemberInfo element, Type attributeType)
bool Attribute.IsDefined(MemberInfo element, Type attributeType, bool inherit)
```

```text
Attribute Attribute.GetCustomAttribute(MemberInfo, Type)
Attribute[] Attribute.GetCustomAttributes(MemberInfo, Type, bool inherit)
```

IsDefined用于回答是否存在；GetCustomAttribute返回单个匹配实例或null（多项匹配还可能歧义），GetCustomAttributes返回数组。原MyClass的Serializable存在性片段保留，假设前面已有相应类型声明：

```csharp
// 判断 MyClass 有没有 [Serializable]
bool ok = Attribute.IsDefined(typeof(MyClass), typeof(SerializableAttribute));
```

普通实例查询执行特性构造器，再设置命名字段/属性；构造器可能有逻辑。CAD则提供参数数据，而不是Attribute对象。

<a id="c18-author"></a>
原Author/Book及Jeffrey输出场景保留；get-only属性和表达式体构造器是C#6，调用语句需放在方法内：

```csharp
class AuthorAttribute : Attribute
{
    public string Name { get; }
    public AuthorAttribute(string name) => Name = name;
}

[Author("Jeffrey")]
class Book {}

var attr = (AuthorAttribute)Attribute.GetCustomAttribute(
    typeof(Book), typeof(AuthorAttribute));
Console.WriteLine(attr.Name); // "Jeffrey"
```

```csharp
var attrs = typeof(Book).GetCustomAttributes(typeof(AuthorAttribute), false);
```

第一个查询得到Name为Jeffrey；第二个查询得到匹配实例数组。普通类型/方法上的IsDefined常不构造目标特性，所以只需要存在性时不必先求对象；这不能推出所有重载永远不执行构造器或绝对“最快”。

<a id="c18-isdefined-parameter"></a>
**必要补充边界**：静态 `Attribute.IsDefined(ParameterInfo, type, inherit:true)`的某些继承路径会通过GetCustomAttributes检查祖先参数，因此会构造目标特性。两环境受控Base.M参数[Count]、Derived.override参数未标的真实输出是：

```text
ParameterInfo实例IsDefined(true): False，Count ctor次数0
静态Attribute.IsDefined(..., true): 打印ctor，结果True，次数1
```

这是具体重载/继承路径，不能反过来将普通Type.IsDefined也说成会构造。Framework官方[参数继承实现](https://raw.githubusercontent.com/microsoft/referencesource/main/mscorlib/system/attribute.cs)调用祖先参数GetCustomAttributes；本机.NET10同样观察到，未以未获取的固定现代源码冒充已读实现。要求不执行目标特性构造器时，应选择CAD等明确的数据路径并考虑依赖解析。

<a id="c18-inherit"></a>
## inherit 不是统一的“默认false”开关

原Author Base/Derived场景保留，使用前面Author定义：

```csharp
[Author("Base")]
class Base {}

class Derived : Base {}   // 自己没贴

// inherit = false → 找不到
Attribute.GetCustomAttribute(typeof(Derived), typeof(AuthorAttribute), false); // null

// inherit = true → 追到 Base，找到了
Attribute.GetCustomAttribute(typeof(Derived), typeof(AuthorAttribute), true);  // Base 那个
```

false只查当前类型，返回null；true可追到Base的Author("Base")。两参数的静态Attribute.GetCustomAttribute/IsDefined常采用inherit=true，不能说三个API默认都false；有些实例API要求显式提供bool。还须看该特性Inherited和具体carrier/overload。

<a id="c18-inherited-false"></a>
原单独Inherited=false例保留为独立定义版本：

```text
[AttributeUsage(AttributeTargets.Class, Inherited = false)]
class AuthorAttribute : Attribute { ... }

[Author("Base")]
class Base {}
class Derived : Base {}

Attribute.GetCustomAttribute(typeof(Derived), typeof(AuthorAttribute), true); // null！
```

即使查询时inherit=true，也不会继承这份Author标记。它不能与前面的同名Author版本混在一个重复声明程序中；目的在比较不同usage条件。

<a id="c18-inherit-overloads"></a>
类型继承、virtual/override方法查询与property/event/参数不是完全相同的入口：静态Attribute方法对override property/event可沿相应访问器追查，PropertyInfo/EventInfo实例查询的inherit会被忽略。ParameterInfo不继承MemberInfo，有单独静态重载；本机两环境的override普通参数静态查询取得BaseP，实例查询为空。接口上的标签不会自动传给实现类方法。

返回参数还要如实区分：本机Framework4.8静态Attribute.GetCustomAttributes(override ReturnParameter, type, true)遇到位置-1，在GetParentDefinition里实际抛IndexOutOfRangeException；原始未捕获日志已保留，作者只加探针catch让后续观察完成。NET10同源正常取得BaseR，实例查询仍为空。这是指定API/实现的观察，不是“所有ReturnValue或Param都不参与继承”的一般规则。[静态ParameterInfo合同](https://learn.microsoft.com/en-us/dotnet/api/system.attribute.getcustomattributes?view=net-10.0)

字段不按override那样另追祖先声明，但派生Type.GetField可能返回基类声明的FieldInfo，该对象直接有BaseField标记；因此“field的inherit被忽略”不等于“经派生类型反射永远看不到基类字段上的特性”。程序集/模块bool继承选项也有各自忽略语义。

<a id="c18-override-obsolete"></a>
原Obsolete new msg例保留，修原private默认权限导致virtual/override非法的问题：

```csharp
class Base
{
    [Obsolete]
    public virtual void M() { }
}

class Derived : Base
{
    [Obsolete("new msg")]   // 此处查询得到派生方法自己的标记；Obsolete本身Inherited=false
    public override void M() { }
}
```

Derived.M查询得到new msg，但不能只据此说是AllowMultiple=false“覆盖”了可继承的基类Obsolete；Obsolete自身Inherited=false。补充未标override的查询实际为false。对真正Inherited=true的自定义特性，AllowMultiple=false时派生同类标记阻止合并祖先同类；AllowMultiple=true可在支持的查询路径累积多个，GetCustomAttribute单例入口则还要考虑多匹配。

<a id="c18-match"></a>
T独有的Match提醒保留：默认Match调用Equals，比较同类型与字段值；需要忽略某些字段或采用自定匹配标准时可重写Match。它和查询inherit不是一回事，重写Match也不自动重写所有Equals语义。源未给完整Match程序，不另用外部完整例代替源。[Match合同](https://learn.microsoft.com/en-us/dotnet/api/system.attribute.match?view=net-10.0)

<a id="c18-carriers"></a>
## typeof 为什么能传给 MemberInfo

Type位于System，继承System.Reflection.MemberInfo；typeof返回Type，可隐式向上转换。类型运算的操作数由编译器解析，运行时返回Type对象，不能说编译阶段已经分配了那个反射对象。原完整层次图保留：

```text
Object
 └─ MemberInfo          （抽象基类：所有“成员”的抽象）
     ├─ Type            （类型本身）
     ├─ MethodBase
     │   ├─ MethodInfo
     │   └─ ConstructorInfo
     ├─ PropertyInfo
     ├─ FieldInfo
     ├─ EventInfo
     └─ ...
```

ParameterInfo不在此树；Assembly和Module也不继承MemberInfo，但均有自己的查询入口/重载。MemberInfo不仅表示“类型内部成员”，也包括Type本身，不能用狭窄日常含义排除Type。

<a id="c18-upcasts"></a>
原三个不同转型/typeof输入各保留，片段按各自上下文理解：

```csharp
MemberInfo mi = typeof(string);
```

```csharp
Type t = typeof(String);
```

```csharp
object o = "hello";   // string → object
MemberInfo mi = typeof(MyClass); // Type → MemberInfo
```

`object o="hello"`与Type→MemberInfo同样是合法上转，但表示对象字符串与描述类型的反射对象是两件事。

原MyClass检测片段另用于说明Type可传给MemberInfo，保留这个教学用途（同样需MyClass声明上下文）：

```csharp

```

原九目标映射表保留：

| 目标 | 对应的反射类型 |
| --- | --- |
| class / struct / enum | `Type` |

## CustomAttributeData：不运行普通用户特性构造器，仍需解析数据

原Q8再给Author("Jeffrey")的请求片段，用来问“这一步发生了什么”，与前面API入门场景分别保留；仍在拥有Author定义的独立示例上下文中：

```csharp
[Author("Jeffrey")]

var attr = (AuthorAttribute)Attribute.GetCustomAttribute(
    typeof(Book), typeof(AuthorAttribute));
// ↑ 这一步发生了什么？
```

步骤是找到元数据/构造器、解析必要依赖、new实例、赋命名成员，得到真实对象。并不是每次都必须重新加载已经加载的程序集。

<a id="c18-evil"></a>
### 构造器可以有动作

下面是原Evil危险反例，**只静态阅读，不执行、不实例化**：


目标是说明请求Attribute实例可以触发特性作者的任意代码。File.Delete不保证所有条件下都删得掉（路径/权限/不存在等各有行为），但消费者不应把此类实例查询当纯读取。作者没有编译运行这个删除反例；安全计数/打印探针足以检查构造阶段，不用真实删除替代教学。

<a id="c18-data-query"></a>

```csharp

    CustomAttributeData.GetCustomAttributes(typeof(Book));
```

它返回CustomAttributeData集合，可访问AttributeType、ConstructorArguments和NamedArguments，不返回AuthorAttribute实例。请求实例与数据三维原表分别保留，修正依赖项：

<a id="c18-data-three-table"></a>
|  | GetCustomAttribute | CustomAttributeData |
| --- | --- | --- |
| new 实例？ | ✅ 是，调构造器 | 不构造普通用户特性实例；对外返回CAD描述数据 |

CAD不调用所描述的普通用户特性构造器/命名setter，因此适于避免这些副作用；这不等于加载所有程序集绝对安全，也不保证解析依赖失败永不会发生。[CAD合同](https://learn.microsoft.com/en-us/dotnet/api/system.reflection.customattributedata?view=net-10.0)

<a id="c18-data-dependency"></a>
### typeof 参数和依赖加载

原`[MyAttr(typeof(FileStream))]`场景不会因用了CAD就获得“不拉入System.IO”的通用保证。Framework/FileStream实现来自mscorlib，现代实现类型与System.Runtime引用外观应分开；若所需程序集本来已加载，就不一定观察到新加载。

**补充受控依赖实证**以Foo.dll/MyClass的Type参数指向单独ExtraBar库：before、加载Foo后、取得CAD描述对象后均未见ExtraBar；读取ConstructorArguments.Value并取得Type后，ExtraBar已加载。两环境均如此且没有执行MyAttr构造器。它只证明这种具体可触发依赖的路径，不规定所有实现/所有操作都在这一精确时点才加载。

<a id="c18-reflectiononly"></a>
### 原 Framework ReflectionOnly 场景

原三个风险方向是：实例化可执行构造器；Type等参数需要依赖解析；ReflectionOnly上下文不能执行目标IL。它可以用于反编译、静态分析、插件声明扫描，但仍是AppDomain中的一种加载上下文，并不是“程序集根本没加载”。

原完整Foo.dll/MyClass扫描片段保留，前提为文件存在、类型名正确、必要依赖可解析：

```csharp
// 1. Framework反射仅加载上下文：不执行目标程序集代码，但需要加载/解析元数据
Assembly asm = Assembly.ReflectionOnlyLoadFrom("Foo.dll");

Type t = asm.GetType("MyClass");

// 2. ❌ 这条路走不通
// Attribute.GetCustomAttribute(t, typeof(SerializableAttribute)); 
//     → 要 new 对象 → ReflectionOnly 禁止

// 3. ✅ 18.6 给的路
IList<CustomAttributeData> list = CustomAttributeData.GetCustomAttributes(t);
foreach (var d in list)
{
    // d.AttributeType 本身也是在 ReflectionOnly 上下文里的 Type
    // 但没关系，我们只是读名字
    Console.WriteLine(d.AttributeType.FullName);
}
```

原前一段针对MyAttr的拒绝路径片段也保留；type/MyAttr须属于可确定的原加载场景，不能以变量未定义当完整程序：

```csharp
// ReflectionOnly 加载的 Assembly
var attrs = Attribute.GetCustomAttribute(type, typeof(MyAttr)); 
// ❌ 可能直接失败：
//   - 要 new MyAttr → 要执行 IL → ReflectionOnly 不允许
//   - typeof(X) 参数也需依赖解析，须按ReflectionOnly上下文处理
```

Framework本机安全夹具实际扫描出MyAttr，实例查询拒绝并有InvalidOperationException；现代.NET10同ReflectionOnlyLoadFrom入口抛PlatformNotSupportedException。这是历史平台差异，不能判原Framework API错误。现代MetadataLoadContext可用于类似分析，但本任务没有安装对应新环境/包或声称已实测；依赖仍需按其resolver处理。[ReflectionOnly版本范围](https://learn.microsoft.com/en-us/dotnet/api/system.reflection.assembly.reflectiononlyloadfrom?view=net-10.0)、[现代只读分析入口](https://learn.microsoft.com/en-us/dotnet/fundamentals/reflection/accessing-custom-attributes)

<a id="c18-data-five-table"></a>
原五维表与前面三维表用途不同，分别保留：

<a id="c18-data-five-table-detail"></a>
| 维度 | GetCustomAttribute | CustomAttributeData |
| --- | --- | --- |
| new 实例？ | ✅ 是，调构造器 | 不构造普通用户特性实例；内部可合成BCL伪特性对象 |
| 执行特性作者代码？ | ✅ 会 | 不执行所描述的普通用户特性构造器/命名setter |
| 加载依赖程序集？ | 需要时会解析/加载依赖 | 也可能解析/加载依赖，不执行普通用户特性构造器 |
| ReflectionOnly 能用？ | Framework反射仅加载ctx禁止构造实例 | Framework反射仅加载ctx可读，依赖需解析；现代此API不支持 |

表中CAD返回的是描述对象，内部伪特性合成的范围见前表注。原“全程没有new任何Attribute”的概括过强；普通用户特性不实例化和内部完全没有Attribute对象不能合为一个结论。
<a id="c18-data-choice-table"></a>

<a id="c18-data-choice-table-detail"></a>
| 你的需求 | 用哪个 |
| --- | --- |
| 只想知道"有没有" | 适当IsDefined重载；不要假定所有继承helper不构造或绝对最快 |
| 要读参数数据/或确需Attribute对象 | 前者可CAD；后者GetCustomAttribute，考虑副作用 |
| 不执行目标构造器/Framework ReflectionOnly/分析工具 | CustomAttributeData，仍考虑依赖解析 |
| 扫描全程序集做静态分析 | CustomAttributeData等元数据工具，按环境限制选择 |

三档“存在/实例/数据”表达选择维度，不能作所有情况下固定成本排名，更不能把CAD当不加载依赖的沙箱保证。

<a id="c18-conditional"></a>
## Conditional控制记录，不控制类是否存在

Conditional可应用于合适的void方法和派生自Attribute的类。原类型形状保留为**框架声明教学示意**，补上真实AllowMultiple=true；这正是可叠多个Conditional的前提：

```text
namespace System.Diagnostics
{
    [AttributeUsage(AttributeTargets.Method | AttributeTargets.Class, Inherited = false, AllowMultiple = true)]
    public sealed class ConditionalAttribute : Attribute
    {
        public ConditionalAttribute(string conditionString) { ... }
    }
}
```

<a id="c18-conditional-method"></a>
原Log("hello")方法/调用片段保留（表达式体C#6，方法与调用分别放在声明/方法上下文）：

```csharp
[Conditional("DEBUG")]
static void Log(string s) => Console.WriteLine(s);

// 调用处
Log("hello");
```

使用点编译时未定义DEBUG则该直接调用不emit，包括参数求值的相应调用路径；方法定义本身仍在，反射仍可能执行它。“所有调用点都消失”只能指使用点符号不满足的这些编译结果，不管不到其它已编译调用者或反射。

<a id="c18-conditional-attribute-method"></a>
原TestAttribute带打印构造器与Program.M应用分别保留：

```csharp
[Conditional("DEBUG")]
[AttributeUsage(AttributeTargets.Method)]
public class TestAttribute : Attribute
{
    public TestAttribute() { Console.WriteLine("TestAttribute ctor"); }
}
```

```csharp
class Program
{
    [Test]
    static void M() { }
}
```

DEBUG在标记使用点定义时记录[Test]；没定义时使用点不写该CA数据，TestAttribute类仍编译存在。标记被保留不等于constructor在编译或IsDefined时立即执行，Get实例才会在本例执行它。

<a id="c18-conditional-class-program"></a>
原另一个MyClass完整程序保留。补using放在#define之后；原“注释掉等于Release”改成真实符号含义：

```csharp
#define DEBUG
// 取消本定义用于演示未定义DEBUG；配置名称不是符号判据
using System;
using System.Diagnostics;

[Conditional("DEBUG")]
class TestAttribute : Attribute
{
    public TestAttribute() => Console.WriteLine("ctor run");
}

[Test]
class MyClass { }

class Program
{
    static void Main()
    {
        var ok = Attribute.IsDefined(typeof(MyClass), typeof(TestAttribute));
        Console.WriteLine(ok);  // DEBUG 开 → True；关 → False
    }
}
```

DEBUG有/无时分别只打印True/False，**均不打印ctor run**；IsDefined针对这里的Type不构造TestAttribute。原四列开关表修正对应构造器列：

<a id="c18-conditional-presence-table"></a>
| 使用点DEBUG符号 | 元数据里有 `[Test]`? | `IsDefined` | 构造器执行? |
| --- | --- | --- | --- |
| DEBUG 开 | ✅ 有 | True | 本例仅IsDefined：不执行；另Get实例才执行 |
| DEBUG 关 | ❌ 没有 | False | 本例仅IsDefined：不执行 |

不定义DEBUG不等于一定是Release构建，Debug配置也可取消该符号，Release也可自行定义；以使用点符号为判据。

<a id="c18-conditional-tests"></a>
### 测试与诊断的原用途

原测试框架**假设形状**保留，并非声称真实NUnit/xUnit内部类都有此Conditional策略：

```text
// 单元测试框架的内部
[Conditional("TEST")]
public class TestAttribute : Attribute { ... }

[Conditional("TEST")]
public class ExpectedExceptionAttribute : Attribute { ... }
```

```csharp
[Test]
public void Calculator_Add_Works()
{
    Assert.AreEqual(3, Calc.Add(1, 2));
}
```

Calculator_Add_Works验证1+2得到3；Assert/Calc/Runner未在源定义，此处是框架使用片段，不是假称已安装库运行。TEST定义时Runner按标记可发现方法；无标记时按此策略不会发现，但方法体还存在，并不保证世界上没人直接/反射调用它。若void测试方法本身另标Conditional("TEST"), 只影响合适源码调用点。NUnit常用Test，xUnit用Fact/Theory；这些框架通常也允许Release跑测试，不应用该假设形状冒充它们实际全部实现。

AutoTracing/DumpToLog两个原自定义诊断用途保留：用条件特性省去开发期标记应用记录，仍要有消费者。Conditional不是唯一compiler消费的特性；Obsolete、DllImport、AssemblyVersion等前面已说明，不能说本章其它特性全是运行时反射的活。

<a id="c18-conditional-or"></a>
原双Conditional OR形状保留：

```csharp
[Conditional("DEBUG")]
[Conditional("TEST")]
class TestAttribute : Attribute {}
```

DEBUG或TEST任一个在应用位置被定义，就记录该特性；都没有则不记录。两个符号都定义也不会凭此复制两份Test应用。原方法Conditional多个条件也有OR语义，依据C#条件特性规则，不要把此语言裁剪机制全归成ECMA-335虚拟机自动做的事。[条件特性语言规则](https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/language-specification/attributes#2353-the-conditional-attribute)

<a id="c18-conditional-phase-table"></a>
原三阶段表保留，条件不满足才裁掉应用记录：

<a id="c18-conditional-phase-table-detail"></a>
| 节 | 维度 | 干了啥 |
| --- | --- | --- |
| 18.4 `GetCustomAttribute` | 运行期 | 反序列化，new 对象 |
| 18.6 `CustomAttributeData` | 运行期 | 只拿配方，不 new |
| **18.7 `Conditional`** | **编译期** | 按使用点条件决定是否记录应用；不满足时不写该CA，不删除特性类 |

框架不能假定源码写了[Test]就一定能扫到相应元数据，但仍能检查特性类本身的定义/Conditional信息。类存在也意味着显式new TestAttribute仍可执行constructor，不会被类上的Conditional裁掉。

<a id="c18-if"></a>
## #if 与 Conditional：先说清包住什么

C#预处理指令是编译过程的一部分，影响哪些输入参与后续分析；不必有一个独立比compiler“上班更早”的外部文本程序。决定差异的是#if的具体范围与符号，以及Conditional应用规则。

<a id="c18-if-usage-only"></a>
### Q9：只包使用点，类定义仍在

原两种形状分别保留：

```csharp
#if DEBUG
[Test]
#endif
class MyClass {}
```

```csharp
[Conditional("DEBUG")]
class TestAttribute : Attribute {}

[Test]
class MyClass {}
```

第一种假设TestAttribute定义在#if之外，无DEBUG时只删此[Test]使用，MyClass和TestAttribute仍存在；其它未包#if的[Test]仍可能合法。第二种类上Conditional同样在无DEBUG时不记录此应用，但类仍在；不能根据第一段片段断言裸使用会找不到类。

原Q9四维表按这个**只包使用点**范围保留：

<a id="c18-if-usage-table"></a>
| 维度 | `#if DEBUG` | `[Conditional("DEBUG")]` 在特性类上 |
| --- | --- | --- |
| 作用阶段 | 预处理指令参与编译，选择后续输入 | compiler按使用点条件选择元数据记录 |
| 特性类本身 | 还在程序集里 | 还在程序集里 |
| `[Test]` 使用点 | 此处删除受#if包住的应用；定义在外时其它裸使用仍合法 | 按条件决定记录；仍需名称/目标等正常合法 |
| 多个条件 | 可用#if DEBUG \|\| TEST，不必嵌套 | 叠多个Conditional为OR |

这张表不能和下一轮删除定义的表合并抹去前提。

<a id="c18-if-definition"></a>
### Q10：类定义和使用点都包住

用户追问后，源给出的A方案扩大#if范围，完整片段保留（声明/方法须置于合适类上下文，表达式体C#6）：

```csharp
#define DEBUG
// 取消本行定义，用于演示未定义DEBUG；不等于配置名称

#if DEBUG
[AttributeUsage(AttributeTargets.Method)]
public class TestAttribute : Attribute
{
    public TestAttribute() => Console.WriteLine("TestAttribute ctor");
}
#endif

#if DEBUG
[Test]
#endif
static void M() { }

// 如果上面 TestAttribute 被 #if 砍了，下面这行 Release 下直接编译报错：
// [Test]  // ❌ CS0246：找不到类型或命名空间 TestAttribute
```

无DEBUG时TestAttribute类定义也不参与编译，因此还有未保护裸[Test]且没有其它同名定义/引用就会CS0246。M方法本身依然存在。原删除类后裸使用反例保留其条件，作者实测该诊断。

<a id="c18-if-conditional-definition"></a>
源B方案保留，类没有放进#if：

```csharp
//#define DEBUG   // 仅演示是否定义符号

[Conditional("DEBUG")]
[AttributeUsage(AttributeTargets.Method)]
public class TestAttribute : Attribute
{
    public TestAttribute() => Console.WriteLine("TestAttribute ctor");
}

// 注意：这里【没包 #if】
[Test]

```

TestAttribute类型始终在本例程序集里；未定义DEBUG只不记录该应用，不是删除类。源码应用仍须符合派生Attribute、目标、参数、名称等正常规则，不能将“无需每个使用点#if”泛化成无条件永远合法。

<a id="c18-if-definition-table"></a>
原六维（含源残缺行）表独立保留。多个条件那一行在原HTML cells与PDF图中左格仅残缺`#if DEBUG`，右格为空；下面明确按**同轮后文真实OR例补足**，不说提取器丢了完整源码：

<a id="c18-if-definition-table-detail"></a>
| 维度 | `#if DEBUG` + 特性类 | `[Conditional("DEBUG")]` 在特性类上 |
| --- | --- | --- |
| 作用阶段 | C#预处理指令选输入，属于编译过程 | compiler按使用点条件选择应用记录 |
| `TestAttribute` 类本身 | 未定义DEBUG→本例定义不参与编译 | 未定义DEBUG→类仍在程序集里 |
| `[Test]` 使用点合法性 | 定义也被删且没有别处定义时，裸使用会CS0246 | 无需#if；仍须正常名称/目标/参数合法 |

| 多个条件 | 按同轮后文补足：#if DEBUG \|\| TEST | 按同轮后文补足：多个Conditional按OR |

T最后说“两方案类都在”与Q10实际A范围矛盾，只对Q9那类未删定义的场景可成立。正文不能按“思考生成过程”整段排掉这个技术冲突。

<a id="c18-runner-if"></a>
### 第三方Runner看见什么

原用户方法应用片段分别保留，与上面两个不同定义范围一起理解：

```csharp
#if DEBUG
[Test]
#endif
void M() { }
```

```csharp
[Test]   // 本例类定义存在且普通应用条件合法，无需另包#if
void M() { }
```

无DEBUG时按标记发现的Runner不会发现这些未记录标记。是否仍有TestAttribute类、裸使用会不会错，取决于类定义有没有被#if删除；不取决于“用户代码脏不脏”。Runner执行/跳过示意不等于实际安装测试框架结果。

<a id="c18-if-or"></a>
原Q10双Conditional及其方法应用是独立场景，保留原空构造器形状：

```csharp
[Conditional("DEBUG")]
[Conditional("TEST")]
class TestAttribute : Attribute {}
```

```csharp
[Test]
void M() { }
```

与其相对的真实#if OR片段保留：

```csharp
#if DEBUG || TEST
[Test]
#endif
```

DEBUG或TEST任一满足。#if本就支持布尔OR，原“必须嵌套，难搞”不成立；条件特性省去重复使用点#if是另一种维护选择，不代表多条件能力只有Conditional有。

<a id="c18-if-constructors"></a>
原“hi”构造器的两个方案分别保留为片段（...是示意usage实参）：

```text
#if DEBUG
[AttributeUsage(...)]
class TestAttribute : Attribute
{
    public TestAttribute() { Console.WriteLine("hi"); }
}
#endif
```

```csharp
[Conditional("DEBUG")]
class TestAttribute : Attribute
{
    public TestAttribute() { Console.WriteLine("hi"); }
}
```

A未定义DEBUG时类被删，当然不能构造不存在的本例类；B类仍存在，缺的是此应用记录。实例查询不会从不存在记录创建这份应用的对象，但显式`new TestAttribute()`仍能打印hi。它不同于CAD在运行时保留记录但只读数据：裁应用记录/不创建对象是不同阶段。
