## 本章的主线

“方法”这一章的讨论重点是几种有特殊用途的方法。实例构造器设置对象的初始状态；类型构造器设置类型的静态状态；操作符重载和转换操作符让自定义类型参与运算与转换；扩展方法提供调用上的便利；分部方法给生成代码留下可定制的挂钩。它们涉及三个层次：C# 源码怎样表达、编译器怎样生成 IL 和元数据、CLR 在运行时怎样执行。把这三个层次分开，能解释许多看似矛盾的说法。

| 机制 | 主要用途 | 原书语境中的实现要点 |
| --- | --- | --- |
| 引用类型实例构造器 | 初始化每个新对象 | 对象字段先取默认值；构造器链完成各层初始化 |
| 值类型实例构造器 | 按指定参数建立一个值 | 值可以直接取默认值，不能把每次存在一个值都理解为调用了用户构造器 |
| 类型构造器 | 初始化静态状态 | CLR 管理触发与同步；初始化状态按 AppDomain 隔离 |
| 操作符重载 | 定义自定义类型的运算含义 | 源码 `operator` 对应有标准名称的特殊方法 |
| 转换操作符 | 定义类型之间的转换 | `implicit` / `explicit` 对应 `op_Implicit` / `op_Explicit` |
| 扩展方法 | 以实例调用形式使用静态方法 | 编译期绑定，不改变被扩展类型的定义 |
| 分部方法 | 给分部类型提供可选挂钩 | 传统可选形式没有实现时，声明和调用被编译器移除 |

<a id="c08-reference-constructors"></a>
## 引用类型：默认构造器与构造器链

<a id="c08-default-constructor"></a>
### `abstract` 与 `static` 的默认构造器规则为什么不矛盾

原问题把“抽象类的默认构造器为 `protected`”与“静态类在元数据中是 `abstract sealed`，不生成默认构造器”放在一起，疑惑它们是否冲突。这里描述的是不同种类的类。

| 类的种类 | 没有声明实例构造器时 | 原因 |
| --- | --- | --- |
| 普通非静态类 | 编译器提供 `public` 无参实例构造器 | 可通过通常的对象创建语法建立实例 |
| 抽象非静态类 | 编译器提供 `protected` 无参实例构造器 | 派生对象仍需初始化抽象基类所定义的那部分状态 |
| 静态类 | 没有实例构造器 | 静态类不可实例化、不可继承 |

类型片段：

```csharp
public class Ordinary { }
public abstract class AbstractBase { }
public static class Utilities { }
```

前两个类型分别等效于具有 `public Ordinary() : base() { }` 与 `protected AbstractBase() : base() { }`。第三个类型在 CLI 元数据中被标记为抽象且密封，但 C# 的 `static class` 是专门的语言构造；不能在 C# 源码中把普通类写成 `abstract sealed class` 来代替它。静态类可以有**静态构造器**，这里“不生成”的是实例构造器。

抽象类不能直接 `new` 是 `abstract` 类型规则的效果，不能单独归因于构造器为 `protected`。抽象类也可以显式声明 `public` 构造器，仍不能直接实例化。普通类一旦显式声明任何实例构造器，编译器便不再额外提供上述默认实例构造器。这些规则以 [C# 规范“默认构造器”](https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/language-specification/classes#15115-default-constructors)为准。

<a id="c08-base-constructor"></a>
### 基类没有无参构造器时，派生类为什么要写 `base(...)`

创建一个派生对象时，只有一个最终对象，并不是分别 `new` 出一个基类对象和一个派生类对象。该对象中含有各层定义的实例字段，基类构造器负责建立基类部分的状态。构造器不会被继承；派生类有自己的实例构造器，可以由编译器生成或由开发者声明，并通过构造器初始化器接入构造器链。

没有 `: base(...)` 或 `: this(...)` 的类实例构造器，隐含 `: base()`。编译器要找到唯一、可访问且适用于无实参调用的基类构造器；无参构造器存在但不可访问，也不能使用。若隐含的 `base()` 无法选中这样的构造器，开发者需要显式提供参数，或经 `this(...)` 转交给其他构造器。带全可选参数或适用的 `params` 参数的基类构造器即使不是无参声明，也可能由 `base()` 调用，例如 `BaseClass(int data = 5)`；下面的例子使用没有可选参数的必需整数参数。

反例 E08-01：下面是完整的类型片段，故意保留错误的无参派生构造器；此片段不能编译。

```csharp
public class BaseClass
{
    private int _data;
    public BaseClass(int data) { _data = data; }
}

public class DerivedClass : BaseClass
{
    public DerivedClass() { } // 隐含 base()，但 BaseClass 没有无参构造器
    public DerivedClass(int value) : base(value) { }
    public DerivedClass(string s) : base(s.Length) { }
}
```

错误是第一条派生构造器无法完成基类构造器调用。旧版 Framework 编译器实测报 CS1729；现代编译器实测报 CS7036，具体文字依编译器版本变化。第二条把调用者的值传给基类；第三条把字符串长度传给基类，是计算参数的不同例子。`s` 若为 `null`，计算 `s.Length` 会抛 `NullReferenceException`，甚至尚未进入基类构造器。

修正后保留三个入口的类型片段 E08-02：

```csharp
public class BaseClass
{
    private int _data;
    public int Data { get { return _data; } }
    public BaseClass(int data) { _data = data; }
}

public class DerivedClass : BaseClass
{
    public DerivedClass() : base(0) { }
    public DerivedClass(int value) : base(value) { }
    public DerivedClass(string s) : base(s.Length) { }
}
```

分别创建 `new DerivedClass()`、`new DerivedClass(7)`、`new DerivedClass("abc")`，`Data` 分别是 `0`、`7`、`3`。也可把第一个入口写成 `public DerivedClass() : this(0) { }`，由同类的另一个构造器继续调用 `base(value)`。因此“每个派生构造器必须直接写 `base(...)`”过于严格；**每条构造器链最终必须到达可访问的基类构造器**。

原回答的“入口和门票”类比可以这样理解：基类构造器提供初始化入口，参数是进入这个入口所需的资料。基类没有“无需资料的入口”时，派生类不能省略资料，编译器也不能代替业务代码猜测资料。

<a id="c08-base-timing"></a>
### 能在派生构造器函数体中决定何时调用基类构造器吗

原追问把“子类的 `new`”和“基类的 `new`”当作两个能调度的动作。对于正常的 C# 类构造器，`base(...)` / `this(...)` 写在声明后的初始化器里，发生在该构造器的函数体之前，不能推迟到函数体中间或末尾；也不能把它当作函数体中的普通方法调用。

完整程序 E08-03：

```csharp
using System;

public class BaseClass
{
    protected int _baseField;
    public BaseClass(int val) { _baseField = val; }
}

public class DerivedClass : BaseClass
{
    public DerivedClass(int val) : base(val)
    {
        Console.WriteLine(_baseField);
    }
}

public static class Program
{
    public static void Main() { new DerivedClass(42); }
}
```

输出 `42`，因为执行派生构造器函数体时，基类构造器函数体已经返回。不过，“基类构造器是派生构造过程的第一个操作”不准确：派生类实例字段初始化器也会先执行，下面专门说明。

正常对象分配会先把字段设置为默认值。这保证字段读到的不是任意残留数据，却不保证所有后续操作都安全：引用字段的默认值是 `null`，对它调用方法仍可能空引用；整数零值也可能导致除零等业务错误。尤其要注意构造器中的虚方法回调，以及 `MemberwiseClone`、某些旧序列化器 / `FormatterServices.GetUninitializedObject` 这类不沿普通实例构造器链建立对象的路径。后者属于特殊 API 场景，不能据此推翻普通 C# 构造器的执行规则；现代 .NET 中相应旧格式化序列化 API 另有弃用限制。

<a id="c08-initialization-order"></a>
## 字段初始化顺序与虚方法陷阱

<a id="c08-two-layer-order"></a>
### 派生类内联初始化、基类构造器、派生构造器函数体的顺序

这里的“内联初始化”指字段声明上的初始化器，例如 `int derivedField = 2;`，与 JIT 的方法内联优化不是同一个概念。编译器把它转成构造器中的赋值。

对于普通类、通过 `base(...)` 到达基类的构造路径，顺序是：对象全部字段取默认值 → 派生类字段初始化器 → 进入基类构造过程 → 返回后执行派生构造器函数体。基类构造过程内部同样先执行自己的字段初始化器，再进入它的基类，最后执行自己的函数体。依据为 [C# 规范“实例变量初始化器”与“构造器执行”](https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/language-specification/classes#15113-instance-variable-initializers)。

完整程序 E08-04 保留原例的 `baseField: 1 → 10` 和 `derivedField: 2 → 20`，增加日志显示实际顺序：

```csharp
using System;

static class Trace
{
    public static int Value(string text, int value)
    {
        Console.WriteLine(text);
        return value;
    }
}

class BaseClass
{
    private int baseField = Trace.Value("Base 字段初始化：1", 1);
    public BaseClass()
    {
        Console.WriteLine("Base 函数体：10");
        baseField = 10;
    }
    public int BaseField { get { return baseField; } }
}

class DerivedClass : BaseClass
{
    private int derivedField = Trace.Value("Derived 字段初始化：2", 2);
    public DerivedClass()
    {
        Console.WriteLine("Derived 函数体：20");
        derivedField = 20;
    }
    public int DerivedField { get { return derivedField; } }
}

static class Program
{
    public static void Main()
    {
        DerivedClass obj = new DerivedClass();
        Console.WriteLine("最终：{0}, {1}", obj.BaseField, obj.DerivedField);
    }
}
```

实测输出：

```text
Derived 字段初始化：2
Base 字段初始化：1
Base 函数体：10
Derived 函数体：20
最终：10, 20
```

归零发生在这些日志之前；`System.Object` 构造器在基类字段初始化之后、基类函数体之前执行。原问答曾把基类完整初始化列在派生类字段初始化之前，又在下一步重新“调用基类”，产生重复调用的假象。正确过程每层只进入一次，不能把已经返回的那层再列成一次新的调用。

<a id="c08-recursion-order"></a>
### “2 → 3 → 2 → …”为什么不是死循环

用户看到原顺序列表后追问是否死循环。关键在于，进入的是**直接基类的另一个构造器**，而不是再次调用当前派生构造器。继承链有限，最终到达 `System.Object`，随后逐层返回。

三层类型片段 E08-05：原示意中自行声明的 `class Object` 并不是 `System.Object`，仍会隐含继承 `System.Object`。为避免把教学根节点当作真实 CLR 根类型，改名为 `RootClass`，保留其单独的函数体层次：

```csharp
class RootClass
{
    public RootClass() { /* 根示例类的构造器函数体 */ }
}

class BaseClass : RootClass
{
    private int baseField = 1;
    public BaseClass() { /* BaseClass 的构造器函数体 */ }
}

class DerivedClass : BaseClass
{
    private int derivedField = 2;
    public DerivedClass() { /* DerivedClass 的构造器函数体 */ }
}
```

保留原问答的逐层过程与缩进图，补出真正的根类型。逐步执行过程如下：

| 步骤 | 所在层 | 执行内容 |
| --- | --- | --- |
| 1 | 对象分配 | 全部实例字段取默认值 |
| 2 | `DerivedClass` | `derivedField = 2`，进入 `BaseClass` 构造过程 |
| 3 | `BaseClass` | `baseField = 1`，进入 `RootClass` 构造过程 |
| 4 | `RootClass` | 无字段初始化器；调用真正的 `System.Object`，返回后执行根示例类函数体 |
| 5 | 返回 `BaseClass` | 继续执行 `BaseClass` 构造器函数体 |
| 6 | 返回 `DerivedClass` | 继续执行 `DerivedClass` 构造器函数体，对象构造完成 |

相同场景的缩进图：

```text
new DerivedClass()
├── 为整个对象分配内存，全部实例字段取默认值
└── 进入 DerivedClass 构造过程
    ├── derivedField = 2
    ├── 进入 BaseClass 构造过程
    │   ├── baseField = 1
    │   ├── 进入 RootClass 构造过程
    │   │   ├── RootClass 没有字段初始化器
    │   │   ├── 调用 System.Object 构造器并返回
    │   │   └── 执行 RootClass 构造器函数体并返回
    │   └── 执行 BaseClass 构造器函数体并返回
    └── 执行 DerivedClass 构造器函数体并返回
```

思考区另用了 `Object → A → B` 命名：对应同一过程是 `B` 字段初始化 → `A` 字段初始化 → `Object` 构造器函数体 → `A` 函数体 → `B` 函数体。这里的 `Object` 必须指真正的 `System.Object`，它没有该例设想的实例字段初始化器。原回答中的“上”“下”方向前后不一致，直接用“派生类到基类”和“基类到派生类”更清楚：字段初始化器沿前一方向执行，构造器函数体沿后一方向返回执行。

同类构造器通过 `this(...)` 互调时，字段初始化器不是沿链反复执行；在最终调用 `base(...)` 的那条构造器路径中执行一次。C# 也会拒绝直接或间接调用自身的构造器链，不能通过 `this(...)` 建立无限构造递归。

<a id="c08-initializer-duplication"></a>
### 多个构造器与初始化代码的重复

思考区补充了一个正文未展开的点：若同一个类有多条直接调用基类的构造器，字段初始化器会被编译进这些构造器，可能重复生成代码。这不意味着创建一个实例时每个重载都执行。

类型片段 E08-06，保留“公共初始化构造器 + `this(...)`”方案：

```csharp
sealed class SomeType
{
    private int m_x;
    private string m_s;
    private double m_d;
    private byte m_b;

    public SomeType()
    {
        m_x = 5;
        m_s = "Hi there";
        m_d = 3.14159;
        m_b = 0xff;
    }
    public SomeType(int x) : this() { m_x = x; }
    public SomeType(string s) : this() { m_s = s; }
    public SomeType(int x, string s) : this() { m_x = x; m_s = s; }
}
```

先由无参构造器给出公共初始状态，其他入口再覆盖指定字段。这是组织代码的选择；实际优化与收益要看编译结果，不能把“生成了重复 IL”直接等同于某个固定的运行时性能损失。

<a id="c08-virtual-constructor"></a>
### 字段已经归零，为什么构造器里的虚调用仍可能报错

基类构造器调用虚方法时，会分派到实际派生类型的重写。此时派生字段初始化器已执行，但派生构造器函数体尚未执行；所以“派生字段都还是零”也不对。真正的风险是对象的不变条件尚未建立。

完整程序 E08-07：

```csharp
using System;

class BaseClass
{
    public BaseClass() { Inspect(); }
    protected virtual void Inspect() { }
}

class DerivedClass : BaseClass
{
    private int inlineValue = 2;
    private string bodyValue;

    public DerivedClass() { bodyValue = "ready"; }
    protected override void Inspect()
    {
        Console.WriteLine(inlineValue);           // 2：字段初始化器已经执行
        Console.WriteLine(bodyValue == null);      // True：派生构造器函数体尚未执行
        Console.WriteLine(bodyValue.Length);       // 抛 NullReferenceException
    }
}

static class Program
{
    public static void Main()
    {
        try { new DerivedClass(); }
        catch (NullReferenceException) { Console.WriteLine("NullReferenceException"); }
    }
}
```

实测为 `2`、`True`、`NullReferenceException`。这同时回答了“提前访问是否一定不报错”：字段值确定，使用这个值的操作却可能抛异常。应避免在构造器中调用可被派生类重写的方法。

<a id="c08-value-initialization"></a>
## 值类型字段、局部变量与构造器

<a id="c08-local-vs-field"></a>
### 对象字段默认初始化与局部变量确定赋值

原问题引用了书中“嵌套在引用类型中的值类型字段保证为零，而基于栈的值类型字段要先写后读”的注意。适合 C# 代码的理解方式是区分**变量的种类**：类的字段与数组元素有默认初始值；普通局部变量必须满足确定赋值分析。不要把规则简化成“值类型总在栈上，引用类型总在堆上”，也不要把“读前赋值”说成“编译器替你把所有局部变量赋零”。[C# 变量规范](https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/language-specification/variables#929-local-variables)规定了局部变量的初始赋值状态。

类型片段 E08-08，原答区的类字段例：

```csharp
class ReferenceTypeClass
{
    private int _valueTypeField;
    public void Method()
    {
        System.Console.WriteLine(_valueTypeField);
    }
}
```

调用 `new ReferenceTypeClass().Method()` 输出 `0`，因为字段有默认初始值。思考区的 `class MyClass { private int _value; public void Print() { ... } }` 是相同教学例的变量改名，合并在这里。

方法片段 E08-09，保留答区的先赋 `5` 再读：

```csharp
static void MyMethod()
{
    int localVariable;
    // System.Console.WriteLine(localVariable); // 反例：取消注释会报 CS0165
    localVariable = 5;
    System.Console.WriteLine(localVariable);    // 输出 5
}
```

思考区另一个方法片段 E08-10 用值 `10` 展示同一规则，保留其不同输入：

```csharp
public void MyMethod()
{
    int localValue;
    // System.Console.WriteLine(localValue); // 反例：未赋值的局部变量
    localValue = 10;
    System.Console.WriteLine(localValue);     // 输出 10
}
```

普通 C# 生成的 IL 常带 `.locals init`，运行时可能把局部存储清零；JIT 也可能把局部变量放到寄存器。这些实现行为不改变 C# 的读前确定赋值要求。原解释的安全动机仍成立：不能让可验证代码任意读到未初始化存储的残留内容。但“堆只创建一次、栈频繁创建”不是普遍事实，对象同样可以频繁创建；不应把这种笼统成本故事当作语言规则的证明。

<a id="c08-struct-fields"></a>
### 结构体局部变量可以逐字段赋值

类型片段：

```csharp
struct MyStruct
{
    public int X;
    public int Y;
}
```

方法片段 E08-11，答区的“只赋一个字段”场景：

```csharp
static void Example1()
{
    MyStruct s1;
    // System.Console.WriteLine(s1.X); // 反例：X 尚未赋值
    s1.X = 10;
    System.Console.WriteLine(s1.X);    // 输出 10：X 已经赋值
    // System.Console.WriteLine(s1.Y); // 反例：Y 仍未赋值
    // System.Console.WriteLine(s1);   // 反例：整个 s1 尚未确定赋值
}
```

编译器可以分别跟踪结构体字段的赋值状态；不必等所有字段都赋值才读取已赋值的 `X`，但不能因此使用整个结构体。读取 `Y` 实测报 CS0170；整个值的使用仍不满足确定赋值。

方法片段 E08-12，思考区的“全部字段赋值”场景：

```csharp
public void MyMethod()
{
    MyStruct myStruct;
    // System.Console.WriteLine(myStruct.X); // 反例：尚未赋值
    myStruct.X = 5;
    myStruct.Y = 10;
    System.Console.WriteLine(myStruct.X);    // 输出 5
    // 此时两个字段均已赋值，可以把 myStruct 作为完整值使用
}
```

这两个例子输入、赋值范围和可用时机不同，不能合成一句“结构体也要赋值”后丢掉。

<a id="c08-embedded-struct"></a>
### 结构体作为类字段时，内部字段也有默认值

类型和方法片段 E08-13，答区从外部读取公有字段的场景：

```csharp
class MyClass
{
    public MyStruct StructField;
    public int IntField;
}

static class Examples
{
    public static void Example2()
    {
        MyClass obj = new MyClass();
        System.Console.WriteLine(obj.StructField.X); // 0
        System.Console.WriteLine(obj.StructField.Y); // 0
        System.Console.WriteLine(obj.IntField);      // 0
    }
}
```

类型片段 E08-14，思考区通过实例方法读取私有结构体字段的场景：

```csharp
public class MyClass
{
    private MyStruct _myStruct;
    public void Print()
    {
        System.Console.WriteLine(_myStruct.X); // 0
    }
}
```

这两段 `MyClass` 是独立示例，不能同时放在同一个命名空间。无论从外部访问公有字段还是从内部访问私有字段，正常 `new MyClass()` 后嵌套结构体的字段都已获得默认值。这不是偷偷执行了 `MyStruct` 的用户实例构造器。

<a id="c08-explicit-initialization"></a>
### 显式初始化与保留的反例

方法片段 E08-15 保留原答区的两种写法：

```csharp
static void GoodPractice()
{
    int value = 0;
    MyStruct s = new MyStruct();
    System.Console.WriteLine(value); // 0
    System.Console.WriteLine(s.X);   // 0
}

static void BadPractice()
{
    int value;
    // 中间若有很多代码，仍不能在赋值前读 value
    // System.Console.WriteLine(value); // 反例：取消注释会编译失败
}
```

在本例 `MyStruct` 没有用户定义的无参构造器，`new MyStruct()` 得到默认值。`BadPractice` 仅声明而不读取，本身能编译；“可能忘记赋值”会在实际读操作处被编译器挡住。`int value = 0` 是需要零值时的一种明确表达，不是所有局部变量都必须先赋零的统一最佳实践；可以直接赋业务所需的值。

因此，原书“可以忽略此注意”的实用结论应理解为：在遵循 C# 规则的普通代码中，不必担心合法读取会取得任意未初始化数据。它不授权读取未赋值局部变量，也不意味着每个值类型的业务初始值必然是零。

<a id="c08-struct-version"></a>
### 第 4 版规则与现代结构体构造器的差异

在原书时期，C# 禁止显式声明结构体的无参实例构造器，也禁止结构体的实例字段初始化器；有参实例构造器必须把全部字段确定赋值。CLR 自身并不禁止值类型拥有无参实例构造器，这一限制来自当时的 C#。

现代差异：C# 10 允许公有的无参结构体构造器及实例字段初始化器；C# 11 会为构造器中未显式赋值的字段提供默认初始化。它们不改变 `default(S)` 与结构体数组元素的默认值行为。[C# 10 无参结构体构造器规范](https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/proposals/csharp-10.0/parameterless-struct-constructors)、[C# 11 自动默认结构体说明](https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/compiler-messages/feature-version-errors)。

现代完整程序 E08-16（C# 10+）：

```csharp
using System;

struct Point
{
    public int X, Y;
    public Point() { X = Y = 5; }
}

class Rectangle
{
    public Point TopLeft, BottomRight;
}

static class Program
{
    public static void Main()
    {
        Console.WriteLine(new Point().X);            // 5：调用公有无参构造器
        Console.WriteLine(default(Point).X);         // 0：默认值，不调用该构造器
        Console.WriteLine((new Point[1])[0].X);      // 0：数组元素取默认值
        Console.WriteLine(new Rectangle().TopLeft.X);// 0：嵌套字段取默认值
    }
}
```

结构体即使提供用户无参构造器，也不能阻止默认零值出现，因此业务设计必须容纳 `default` 状态。

<a id="c08-appdomain"></a>
## AppDomain 的含义与三个场景

<a id="c08-appdomain-definition"></a>
### 进程内部的托管隔离与卸载边界

原问题先问“AppDomain 是什么”，再要求结合例子。原书的 .NET Framework 中，AppDomain（应用程序域）是一个进程内部由 CLR 管理的执行边界，程序集被加载到域中，代码在域中运行。一个进程可以包含多个域，同一个程序集也可参与多个域；通常每个域有自己的静态字段状态和类型初始化状态。

原回答的“轻量级进程”与“大楼套房”两个类比都保留：操作系统进程隔离不同应用，AppDomain 在托管进程中隔离组件；进程像大楼，域像套房，程序集像房间，静态状态像设施，域配置像规则，CLR 可以卸载一个套房中的代码而保持进程运行。原总结还把类型称作域的“租客”：在通常的程序集加载场景，域卸载时相应类型状态也随之清退。不过套房共用同一栋楼，AppDomain 不等同于操作系统进程、容器或能够承受任意插件行为的安全沙箱。

| 在原书语境中的能力 | 含义与边界 |
| --- | --- |
| 对象访问隔离 | 跨域对象通常通过序列化复制或远程处理代理访问，不能当作同域对象随意直接引用 |
| 卸载边界 | 对通常加载的程序集，不能任意卸载单个类型 / 程序集；可卸载其非默认 AppDomain |
| 配置隔离 | 域可有各自配置文件路径等设置；原书时代还涉及权限与安全策略 |
| 静态状态隔离 | 在每个域中分别运行相应类型初始化，保存各自静态字段值 |
| 有限的可靠性隔离 | 卸载一个组件可以避免终止整个宿主；仍不能保证任意异常、非托管破坏或进程资源耗尽只影响该域 |

官方的 [.NET Framework AppDomain 文档](https://learn.microsoft.com/en-us/dotnet/framework/app-domains/application-domains)描述这些能力。域可以共享某些运行时代码等实现资源，“独立”不意味着所有元数据和机器码字节必然复制一份。未处理异常在通常策略下仍可能导致整个进程终止，参见 [AppDomain.UnhandledException 说明](https://learn.microsoft.com/en-us/dotnet/fundamentals/runtime-libraries/system-appdomain-unhandledexception)。

<a id="c08-appdomain-plugin"></a>
### 场景一：文本编辑器加载和卸载拼写检查插件

原例创建 `PluginDomain`，执行 `SpellCheckPlugin.dll`，然后卸载域，编辑器继续运行。`ExecuteAssembly` 要求目标程序集有入口点；普通插件类库 DLL 没有 `Main`，不能直接这样执行。为保留原文件名与流程，下面明确把插件编译为**带入口点的可执行程序集**，仅使用 `.dll` 作为文件名。真实类库插件可改用 `CreateInstanceAndUnwrap` 等跨域调用方案。

完整插件程序 E08-17a（仅限 .NET Framework）：

```csharp
using System;

public static class SpellCheckPlugin
{
    public static void Main()
    {
        Console.WriteLine("拼写检查插件运行于：" + AppDomain.CurrentDomain.FriendlyName);
    }
}
```

完整宿主程序 E08-17b（与插件分开编译）：

```csharp
using System;

class TextEditor
{
    static void Main()
    {
        AppDomain pluginDomain = AppDomain.CreateDomain("PluginDomain");
        pluginDomain.ExecuteAssembly("SpellCheckPlugin.dll");
        // 用户使用插件；现在决定卸载它
        AppDomain.Unload(pluginDomain);
        Console.WriteLine("插件域已卸载，编辑器继续运行");
    }
}
```

步骤：以 `/target:exe /out:SpellCheckPlugin.dll` 编译第一份代码；以 `/out:TextEditor.exe` 编译宿主；在两文件所在目录运行宿主。实测先输出插件所在域 `PluginDomain`，再输出编辑器继续运行。之后可以创建新的域加载插件的新版本。若把通常的程序集加载到主程序默认域，不能仅因用户关闭插件就单独卸载；但资源仍需按 API 正常释放，不能把卸载说成所有非托管资源立即且必定清理。也不能声称插件崩溃绝不会影响编辑器。

<a id="c08-appdomain-web"></a>
### 场景二：经典 ASP.NET / IIS 中的访问计数器

原例假设 IIS 中的两个**经典 ASP.NET（.NET Framework）**应用分别在 `Blog` 与 `Shop` 域运行。它说明静态状态属于域，不能把 Web 应用的第一次请求、JIT 编译、类型加载和类型构造器执行视为完全同一件事。

类型片段 E08-18：

```csharp
using System;

public class VisitorCounter
{
    static VisitorCounter()
    {
        Console.WriteLine("计数器在 AppDomain: {0} 中初始化",
            AppDomain.CurrentDomain.FriendlyName);
        Count = 0;
    }
    public static int Count;
}
```

当 `Blog` 域中的代码第一次触发这个类型的初始化，构造器打印 `Blog`，该域的 `Count` 从 `0` 开始；访问并修改后不重复运行同一域的静态构造器。`Shop` 域第一次触发初始化时打印 `Shop`，它的 `Count` 独立从 `0` 开始。一个域里改成 `1` 不会把另一个域的计数器也改成 `1`。本机用两个命名域运行相同类型，实测 `Blog` 中为 `1`、`Shop` 中首次读取为 `0`。

“每域静态字段独立”与“并发计数安全”是两件事，`Count++` 本身不是跨线程原子计数方案。域名称仅为教学示意，真实 IIS 域名称与应用回收策略取决于宿主。现代 ASP.NET Core 不采用这个经典多 AppDomain 模型。

<a id="c08-appdomain-test"></a>
### 场景三：测试运行器隔离配置与静态状态

原例是说明性伪代码 E08-19；`[Test]` 的来源取决于具体测试框架，不能作为无依赖可编译程序：

```csharp
[Test]
public void TestInIsolation()
{
    // 运行器可能创建新的 AppDomain，配置为 test.config。
    // 在该域加载被测程序集，运行测试，得到独立的静态状态。
    // 测试完成后卸载该域，下一批测试再使用新的域。
}
```

这种安排能避免前一批测试的静态状态或域配置污染后一批，但并不代表每个框架都按“每个测试用例一域”执行，也不代替测试自身的资源清理。在 .NET Framework 中这是可用的运行器策略；不能推广为现代 .NET 测试框架的通用实现。

<a id="c08-appdomain-modern"></a>
### 现代差异：AssemblyLoadContext

现代 .NET 保留 `AppDomain.CurrentDomain` 等兼容入口，但不支持用 `CreateDomain` / `Unload` 建立、卸载多个应用程序域；原例必须在 .NET Framework 中运行。插件的程序集加载与可回收加载上下文通常使用 `AssemblyLoadContext`。它提供加载与版本隔离，**不提供安全隔离**，卸载也要求对象和相关引用都可释放。[AssemblyLoadContext 官方说明](https://learn.microsoft.com/en-us/dotnet/core/dependency-loading/understanding-assemblyloadcontext)、[不受支持的 .NET Framework 技术](https://learn.microsoft.com/en-us/dotnet/core/porting/net-framework-tech-unavailable)。需要抵御不可信插件或进程级故障时，应选择具有相应保障的进程边界，而不能仅把旧域例替换一个类名。

<a id="c08-type-constructor"></a>
## 类型构造器何时执行

<a id="c08-type-constructor-rules"></a>
### 类型构造器初始化的是静态状态

类型构造器也称静态构造器、类型初始化器，在元数据中名为 `.cctor`。原书语境中一个类或结构体最多一个，无参；C# 声明不能写访问修饰符，不能由通常的源码调用，也不能继承或重载。它与实例构造器 `.ctor` 的“初始化对象”职责不同。

其初始化同步由 CLR 负责，原书的 .NET Framework 中相应类型在每个 AppDomain 中至多运行一次。这个“线程安全”只指初始化过程受保护，不意味着初始化之后的所有静态对象操作也自动线程安全。原书用 JIT 检查初始化状态、生成检查或调用的方式说明实现，但不能据此认为“只要 JIT 编译一个引用该类型的方法，就已经执行了构造器”。执行语义应以触发条件为准。[静态构造器官方说明](https://learn.microsoft.com/en-us/dotnet/csharp/programming-guide/classes-and-structs/static-constructors)。

<a id="c08-type-constructor-trigger"></a>
### 第一次使用，还是 AppDomain 启动时统一初始化

用户的两个选项中，“启动 AppDomain 就遍历所有类型的构造器”不成立。带**显式静态构造器**的普通类在第一次触发其初始化的操作之前运行该构造器，例如建立该类实例或调用该类声明的静态方法、访问需要初始化的静态字段。只取得 `typeof(T)`、引用常量等不等于这种触发操作。

完整程序 E08-20 保留原答区的 `MyClass.Method()` 场景，增加前后标记及第二次调用：

```csharp
using System;

class MyClass
{
    static MyClass()
    {
        Console.WriteLine("MyClass的静态构造器被执行！");
    }
    public static void Method() { Console.WriteLine("Method"); }
}

class Program
{
    static void Main()
    {
        Console.WriteLine("Main开始");
        Console.WriteLine(typeof(MyClass).Name); // 取得 Type 本身不触发该静态构造器
        MyClass.Method();
        MyClass.Method();
    }
}
```

实测输出 `Main开始`、`MyClass`、静态构造器提示、`Method`、`Method`。若程序根本不执行触发这个显式静态构造器的操作，就没有该构造器的输出。第二次调用不会再次初始化。同一类型若在另一个 Framework 域中初始化，又有该域自己的初始化状态。

<a id="c08-beforefieldinit"></a>
### “首次访问”需要补上 `beforefieldinit` 边界

若 C# 源码只有静态字段初始化器，没有显式静态构造器，编译器仍可能生成 `.cctor`，同时给类型标记 `beforefieldinit`。运行时可以在首次静态字段访问之前更早初始化它；仅调用一个不访问字段的静态方法也不必在该时刻初始化。因此不能把所有类型都概括为“任何首次使用必定立刻执行”，也不能保证这类初始化一定紧贴第一次读字段。[TypeAttributes.BeforeFieldInit 契约](https://learn.microsoft.com/en-us/dotnet/api/system.reflection.typeattributes)。

类型加载、方法 JIT、类型初始化是相关但不同的事件。用“按需初始化”理解显式静态构造器场景很有帮助；用它推导一个所有运行时、所有类型通用的精确日志时间点则会出错。值类型的默认值、数组创建和直接字段访问还有各自边界，不能把“存在一个值类型实例”都视为类型构造器已触发。

<a id="c08-type-lifetime"></a>
## 实例回收与类型卸载

<a id="c08-instance-type-lifetime"></a>
### 没有实例时，类型也会被 GC 回收吗

原追问把两个生命周期联系起来：如果没有在使用任何实例，类型是否销毁？对于 .NET Framework 中通常加载的程序集，实例都不可达，并不导致该类型单独卸载。类型仍可能用于静态成员访问或创建后续实例，其卸载由所在加载环境管理。

实例对象是否可回收看 GC 的可达性与终结等条件。局部变量只是可能的引用来源；“没有使用”不等于没有引用，写 `obj = null` 也不等于对象已立即回收。静态字段还可能持有实例，令它继续存活。

完整程序 E08-21 保留原答区的创建、置空、强制 GC、访问静态字段、重新创建实例流程，并修正原来“此处已确定回收”的注释：

```csharp
using System;

public class MyClass
{
    public static int StaticValue = 5;
    public MyClass() { }
}

class Program
{
    static void Main()
    {
        MyClass obj = new MyClass();
        obj = null;   // 不再通过此局部变量引用第一个实例
        GC.Collect(); // 请求回收；不能仅凭这行证明某个实例实际已经回收

        Console.WriteLine(MyClass.StaticValue); // 输出 5：类型的静态状态仍可访问
        MyClass obj2 = new MyClass();           // 仍能创建该类型的新实例
        GC.KeepAlive(obj2);
    }
}
```

实测输出 `5`；这个实验验证后续仍可使用类型，没有声称直接观察到第一个实例被回收。JIT 优化可能改变局部引用的实际存活时间，所以“写空再 `Collect`”不是准确的对象死亡证明。

<a id="c08-unload-boundaries"></a>
### 类型卸载规则的适用范围与例外

原书的普通程序集场景可以概括为：卸载非默认 AppDomain 后，其中通常加载的代码和相应类型状态可卸载；默认域不能通过 `AppDomain.Unload` 单独卸载，其生命周期通常持续到进程结束。不能因没有实例就随意卸载某个普通类型或程序集。

保留原回答的设计理由：重新加载类型信息、代码和初始化状态有成本；程序也可能再次访问静态成员或创建实例，域为这组代码提供生命周期边界。这里“类型是蓝图”的类比强调实例与类型不同，不能把 `System.Type` 托管对象、元数据、方法表、静态字段存储统称为一块由普通实例 GC 直接回收的“类型对象”。

“唯一方式是卸载 AppDomain”若没有限定范围就过强：.NET Framework 已有通过 Reflection.Emit 的 `RunAndCollect` 创建的可回收动态程序集，可以在不卸载域的情况下释放；现代 .NET 还支持可回收的 `AssemblyLoadContext`。两种情形都需要没有阻止回收的相关引用，仅仅“类型没有实例”不足以证明可卸载。[可回收动态程序集文档](https://learn.microsoft.com/en-us/dotnet/fundamentals/reflection/collectible-assemblies)、[现代 .NET 程序集卸载说明](https://learn.microsoft.com/en-us/dotnet/standard/assembly/unloadability)。

<a id="c08-operators"></a>
## 操作符重载与基元类型

<a id="c08-operator-paths"></a>
### 为什么旧 FCL 的 `Int32` 加法不需要 `op_Addition`

原问题引用书中对 `Int32`、`Int64`、`UInt32` 的观察：原书时代这些类型的基本运算由编译器识别并生成对应 IL，而不需要由它们提供通常的操作符重载方法。例如非恒定 `int` 加法通常对应 `add`；在检查溢出的上下文中可能对应 `add.ovf`。C# 编译器负责生成 IL，JIT 再把 IL 转成本机指令，这两个阶段不能混称成编译器直接把源码输出为本机加法。

普通自定义类型的 `a + b` 则会根据重载规则绑定到用户声明的操作符方法，元数据名称为 `op_Addition`，带特殊名称标志。原书语境中这类操作符是静态方法。

| 场景 | 编译器采用的路径 | 教学含义 |
| --- | --- | --- |
| `int` 的基本加法 | 预定义运算 → 对应 IL 运算指令 | 不需要先查找 `Int32` 的普通重载方法 |
| 自定义 `Complex` 加法 | 重载解析 → 调用相应操作符方法 | 运算逻辑由类型作者提供 |
| 不提供某基元运算支持的语言 | 无法依赖旧类型上不存在的同名重载方法 | 该运算可能不可直接表达，并非所有实例操作全部消失 |

正式方法调用在 IL 层多一道调用，但 JIT 可能内联它；不能仅由“出现方法调用”保证固定额外开销。基元运算的直接 IL 路径则清晰表达了运行时的运算语义。

<a id="c08-complex-example"></a>
### 自定义 `Complex` 与语言互操作的对比

原答区使用了“自定义 `Complex` 有 `op_Addition`，其他语言可调用；旧 `Int32` 没有这个后备入口”的对比。完整程序 E08-22 补齐该对比的实现，并加入普通命名方法：

```csharp
using System;

public sealed class Complex
{
    public double Real { get; private set; }
    public double Imaginary { get; private set; }
    public Complex(double real, double imaginary)
    {
        Real = real;
        Imaginary = imaginary;
    }
    public static Complex operator +(Complex a, Complex b)
    {
        return new Complex(a.Real + b.Real, a.Imaginary + b.Imaginary);
    }
    public static Complex Add(Complex a, Complex b) { return a + b; }
    public override string ToString() { return Real + " + " + Imaginary + "i"; }
}

static class Program
{
    static void Main()
    {
        Complex a = new Complex(1, 2), b = new Complex(3, 4);
        Console.WriteLine(a + b);              // 4 + 6i
        Console.WriteLine(Complex.Add(a, b));  // 4 + 6i
        // Complex.op_Addition(a, b);          // C# 反例：不能这样显式调用操作符
    }
}
```

通过 `+` 可以使用 C# 的操作符；`Add` 提供更普通的跨语言 API。其他语言能否直接以 `op_Addition` 名称调用，要看该语言规则；在 C# 中显式调用真正的操作符元数据方法会报 CS0571。[微软 CS0571 说明](https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/compiler-messages/property-declaration-errors)。

原书“若语言不支持便不能执行任何操作”应按当前上下文理解为某些运算缺少该语言可用的直接路径。它不否定读取、传递、装箱、`ToString` 等其他操作，也不排除通过另一个支持运算的程序集包装功能。

<a id="c08-operator-modern"></a>
### 现代差异：泛型数学与新的操作符形式

从 .NET 7 起，`Int32` 等实现泛型数学接口，提供相关静态接口操作符实现；现代反射能看到相关非公有方法。不能对现代 FCL 继续绝对断言“完全没有操作符方法”。普通 C# `int + int` 仍属于预定义运算，这与泛型数学接口路径同时存在。[IAdditionOperators 官方 API](https://learn.microsoft.com/en-us/dotnet/api/system.numerics.iadditionoperators-3)、[Int32 的加法接口实现](https://learn.microsoft.com/en-us/dotnet/api/system.int32.system-numerics-iadditionoperators-system-int32-system-int32-system-int32--op_addition)。

另一个版本边界是 C# 14 引入了实例复合赋值操作符与实例自增、自减形式；本章原书讨论和 `Complex` 的二元 `+` 仍是传统静态形式。因此“所有操作符方法永远都是静态方法”只能作为原书时期规则，不能不加限定地推广到现代语言。[操作符重载官方说明](https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/operators/operator-overloading)。

<a id="c08-conversions"></a>
## 转换操作符：源码、调用与元数据

<a id="c08-conversion-motivation"></a>
### 先看需求：构造器和 `ToXxx` 方法

原问题要求解释 8.5 小节，并追问两种声明的关系。原小节的脉络是：需要类型转换 → 普通构造器和方法实现转换 → 用 C# 操作符表达 → 查看编译后的元数据 → 讨论适用边界。

`int` 转 `decimal` 是预定义数值转换；字符串 `"123"` 转整数通常是 `int.Parse` 一类解析操作。它们都涉及数据转换，但不能都当作用户定义转换操作符。自定义 `Rational`（有理数）可以先提供 `new Rational(5)` 与 `r.ToInt32()`，再让 `Rational r = 5`、`(int)r` 使用同一套转换逻辑。原解释也提到与 `double` 互转的需求；这种方向要另外设计表示、范围与舍入规则，并不是声明了整数转换就自动具备，下面的具体例子实现整数与 `float` 目标。

<a id="c08-rational-example"></a>
### `implicit` 与 `explicit` 的完整示例

传统转换操作符写为 `public static`，单一参数是源类型，返回类型是目标类型，定义所在类型必须是源类型或目标类型之一。隐式形式允许编译器在赋值或参数传递等处自动插入转换；显式形式要求调用者使用转换语法。隐式转换应避免丢失信息和意外异常，显式转换用来表达可能丢信息、抛异常或需要特别确认的转换。它们是设计约定，编译器不会证明用户代码绝不抛异常。[用户定义转换官方说明](https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/operators/user-defined-conversion-operators)。

完整程序 E08-23，把原问答中的操作符片段和 `ToInt32` 调用补成可运行的有理数场景。这里保留 `int` 与 `float` 两个显式目标；不引入与本章无关的完整有理数运算库：

```csharp
using System;

public sealed class Rational
{
    private readonly int numerator;
    private readonly int denominator;

    public Rational(int num) : this(num, 1) { }
    public Rational(int num, int den)
    {
        if (den == 0) throw new DivideByZeroException();
        numerator = num;
        denominator = den;
    }
    public int ToInt32() { return numerator / denominator; }
    public float ToSingle() { return (float)numerator / denominator; }

    public static implicit operator Rational(int num)
    {
        return new Rational(num);
    }
    public static explicit operator int(Rational r)
    {
        return r.ToInt32();
    }
    public static explicit operator float(Rational r)
    {
        return r.ToSingle();
    }
}

public static class Program
{
    public static void Main()
    {
        Rational five1 = new Rational(5);       // 普通转换构造器
        Rational five2 = 5;                     // 隐式操作符
        Rational five3 = (Rational)5;           // 显式转换语法也可以使用隐式操作符
        Rational r = new Rational(3, 2);
        Console.WriteLine(five1.ToInt32());      // 5
        Console.WriteLine((int)five2);          // 5
        Console.WriteLine((int)five3);          // 5
        Console.WriteLine(r.ToInt32());         // 1：普通方法
        Console.WriteLine((int)r);              // 1：整数除法舍去小数，向零截断
        Console.WriteLine((float)r);            // 1.5（显示格式随区域设置）
        // int x = r;                          // 反例：没有 Rational → int 隐式转换
    }
}
```

步骤是创建整数 `5` 的三种 `Rational` 值，再把 `3/2` 转为整数和浮点数。整数转换丢掉小数；`float` 的结果一般可能有精度损失。此例也有边界：`r` 为 `null` 时转换方法会空引用，整数除法的极值也可能溢出。因此把可能失败的方向设计成显式是合理选择；显式语法并不自动增加业务校验。

<a id="c08-conversion-metadata"></a>
### 用户引用的两种声明不是同一方法的两个写法

原引用一是 `public static explicit operator Int32(Rational r) { return r.ToInt32(); }`，方向为 **Rational → Int32**，模式是显式。原引用二是 `public static Rational op_Implicit(Int32 num);`，方向为 **Int32 → Rational**，模式是隐式。它们属于同一类型的两种转换，却不是一对源码 / 元数据对应项。

| C# 源码形式 | 源类型 → 目标类型 | 编译后的元数据签名示意 |
| --- | --- | --- |
| `public static implicit operator Rational(int num)` | `Int32 → Rational` | `public static Rational op_Implicit(Int32 num)` |
| `public static explicit operator int(Rational r)` | `Rational → Int32` | `public static Int32 op_Explicit(Rational r)` |
| `public static explicit operator float(Rational r)` | `Rational → Single` | `public static Single op_Explicit(Rational r)` |

元数据示意 E08-24，以下不是独立可编译的普通 C# 方法声明文件：

```text
public static Rational op_Implicit(System.Int32 num);
public static System.Int32 op_Explicit(Rational r);
public static System.Single op_Explicit(Rational r);
```

编译器读取 `implicit operator` / `explicit operator` 语法，生成标准特殊名称方法，再在相应转换表达式处生成调用。源码友好语法与 CLI 约定的双层设计便于不同语言识别程序集中的转换契约，但不能保证每一种语言语法都能直接调用每一种特殊方法。

<a id="c08-conversion-return-type"></a>
### 为什么两个 `op_Explicit` 的参数一样，返回类型却能不同

上例两个显式方法都是 `Rational` 参数，却分别返回 `Int32` 和 `Single`。普通 C# 方法不能仅靠返回类型重载，例如同时声明 `int M(Rational r)` 与 `float M(Rational r)` 会冲突；转换操作符则按源类型和目标类型区分，转换表达式 `(int)r` / `(float)r` 给出了目标类型。

CLI 方法签名可表达返回类型，因而能描述上述两个方法；这不意味着 C# 的所有方法调用都按返回类型选重载，也不意味着只有名字和返回类型就足以在任意上下文唯一标识方法。转换操作符有自己的语言规则。[C# 规范“转换操作符”](https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/language-specification/classes#15104-conversion-operators)。本机反射确认两个 `op_Explicit` 均存在，参数类型相同，返回类型不同。

<a id="c08-is-as-boundary"></a>
### `is` / `as` 不会调用用户定义转换

原问答正确强调：用户定义转换与 `is` / `as` 无关。`is` 判断类型兼容性或匹配模式，`as` 在其允许的转换范围内返回转换后的引用或可空值；它们不限于“两个引用类型之间的强制转换”，也不搜索用户的 `op_Implicit` / `op_Explicit`。[用户定义转换官方说明](https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/operators/user-defined-conversion-operators)。

在 E08-23 的 `Main` 中追加下面的语句片段 E08-25：

```csharp
object boxedFive = 5;
Console.WriteLine(boxedFive is Rational);       // False
Console.WriteLine(boxedFive as Rational == null);// True
Rational converted = (Rational)(int)boxedFive;  // 先拆箱为 int，再调用隐式转换
Console.WriteLine((int)converted);              // 5
```

即使 `int` 能转换成 `Rational`，装箱整数也没有因此成为 `Rational` 对象。`(Rational)boxedFive` 按对象的引用转换路径检查实际类型，不会自动帮你拆箱再串联用户转换；上面的两步写法把所需过程写清楚。

内置数值转换常由相应 IL 转换指令表达，用户定义转换则在 IL 中是方法调用。和操作符重载一样，JIT 可能内联，不能由这一区别宣称每次转换都有固定不可消除的调用开销。

<a id="c08-extension-partial"></a>
## 扩展方法与分部方法

<a id="c08-extension-method"></a>
### 扩展方法：调用形式上的扩展

原章末回顾指出：扩展方法是静态方法，其第一个参数用 `this` 修饰，编译器把实例形式的调用绑定到相应静态方法。它让已有类型看起来增加了方法，而不必修改其定义或派生新类型，也不真正把方法写进原类型的元数据。LINQ 的许多标准查询操作便采用这个机制。

理解用类型与语句片段 E08-26：

```csharp
public static class StringExtensions
{
    public static int CharacterCount(this string value)
    {
        return value.Length;
    }
}

// 调用方的方法体内：
string text = "abc";
System.Console.WriteLine(text.CharacterCount());             // 3
System.Console.WriteLine(StringExtensions.CharacterCount(text));// 3
```

传统扩展方法声明放在顶层、非泛型静态类里；声明所在命名空间须在调用处可见。扩展方法只能按正常可访问性访问目标类型成员，不能因扩展就访问私有实现。绑定发生在编译期，适用的真实实例成员优先，也不能用扩展方法重写虚方法。[扩展成员官方说明](https://learn.microsoft.com/en-us/dotnet/csharp/programming-guide/classes-and-structs/extension-methods)。

现代差异：C# 14 增加 `extension` 块，可表达更多扩展成员及静态扩展；传统 `this` 参数形式仍可用。本章“第一个参数必须 `this`”描述的是原书使用的传统语法，并不是所有现代扩展声明的唯一语法。[`extension` 声明参考](https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/keywords/extension)。

<a id="c08-partial-method"></a>
### 分部方法：生成代码里的可选挂钩

原章末回顾使用的传统模式是在分部类型里声明方法，在另一部分按需实现。没有实现时，编译器移除声明及调用，连调用参数表达式也不求值，因而没有这次挂钩调用的运行时开销。分部类型的各部分必须一起编译，不是在运行时拼接程序集。

完整程序 E08-27，展示没有实现时的效果：

```csharp
using System;

partial class Customer
{
    public void Save() { OnSaving(BuildMessage()); Console.WriteLine("保存"); }
    partial void OnSaving(string message);
    private string BuildMessage() { Console.WriteLine("构造消息"); return "saving"; }
}

class Program
{
    static void Main() { new Customer().Save(); }
}
```

输出只有 `保存`，没有 `构造消息`。若在同一次编译中加入以下类型片段 E08-28：

```csharp
partial class Customer
{
    partial void OnSaving(string message) { System.Console.WriteLine(message); }
}
```

则输出依次为 `构造消息`、`saving`、`保存`。声明、实现与调用恢复为一个实际方法。原书的可选形式隐式为 `private`、返回 `void`，不能有 `out` 参数；这使移除调用后不会留下必须使用的返回值或输出值。

现代差异：C# 9 扩展了分部方法，允许显式可访问性、非 `void` 返回等形式；这些需要实现，不能沿用“无实现就删除”的结论。即使写 `private partial void M();`，显式访问修饰符也使其成为必须实现的形式。来源：[C# 版本历史](https://learn.microsoft.com/en-us/dotnet/csharp/whats-new/csharp-9)、[分部方法规范](https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/language-specification/classes#1569-partial-methods)。

这些机制的共同点是把类型设计映射到语言表达和运行时行为；它们的性能、互操作性与组织代码的能力各有边界。阅读本章时，始终分别判断源码规则、元数据表示和运行时行为，就能避免把“语法糖”误解成类型本身被修改，也能避免把书中历史限制套到所有现代代码上。
