## 异常处理首先是状态管理

<a id="c20-overview"></a>

异常并不等同于“小概率事件”。一个成员未完成其契约承诺的工作，才需要用异常报告失败；读到文件末尾可以是正常结果，读取操作本身失败则是另一回事。理解这一章时，可以沿几条线索阅读：`try/catch/finally`管理异常路径，`Exception`保存诊断信息，自定义异常表达不同失败类别，可靠性设计保护部分完成操作，CER和代码协定则是原书讨论的特定机制。

原问答还提出了几项背景：异常体系宜浅而宽，`ApplicationException`和`SystemException`不宜作为按“应用/系统责任”分类的依据；非CLS对象异常可由`RuntimeWrappedException`包装；泛型`Exception<TExceptionArgs>`是书中减少重复实现的方案。反射的`TargetInvocationException`包装与`dynamic`调用有不同语义。后文将分别解释这些话的实际条件。

原导读强调：一行LINQ可能隐含分配、装箱、委托构造、虚调用、程序集加载或历史AppDomain跨域等失败点；把所有隐含失败都防完并不现实，重点是明确失败后必须保持的状态。

**补充边界：** 这些是潜在失败条件，不表示每一行LINQ必然触发全部操作；也不能从“无法防完全部失败”推成“任何保护都无用”。先确定失败状态与责任，再选具体保护措施。

**历史提示：** Framework的CER需要可靠性契约和受限代码配合，不能保证任意`finally`永不失败。JIT、加载、静态构造触发的失败也不能一概叫作异步异常。现代.NET已经不支持CER；`PrepareConstrainedRegions`有相应弃用提示。[官方CER API说明](https://learn.microsoft.com/en-us/dotnet/api/system.runtime.compilerservices.runtimehelpers.prepareconstrainedregions?view=net-10.0)

<a id="c20-try-roles"></a>
### try、catch、finally分别承担什么

`try`放需要保护的操作；`catch`处理某类失败，例如恢复状态、转换异常或在边界记录失败；`finally`放无论正常退出还是异常退出都需要执行的收尾，例如关闭文件、释放锁、撤销临时状态。清理与恢复是设计职责，不是语言强制的两种互斥功能：`finally`也能撤销临时状态，`catch`也能记录后重新抛出，并非每个`catch`都让业务继续成功。

合法的基本组合有三种：`try/catch`、`try/finally`、`try/catch/finally`。下列是**语法反例**，单独的`try`不合法：

```csharp
try
{
    DoSomething();
}
// 编译错误：必须跟catch或finally
```

ATM类比可以帮助区分职责：插卡、输密码、取款对应`try`；卡被吞后联系客服处理对应恢复；最后取回能取回的卡和收据对应清理。它只解释职责，不能保证失败时银行卡一定能被自动取回。

本章的“finally会执行”指正常控制流和可按运行时异常机制展开的退出路径。进程被强制结束、`Environment.FailFast`等情况不在这个承诺内。`FailFast`明确跳过活动`finally`和终结器，本章不执行该终止示例。[FailFast契约](https://learn.microsoft.com/en-us/dotnet/api/system.environment.failfast?view=netframework-4.8.1)

<a id="c20-state-file"></a>
### 文件的三个步骤：try的边界由恢复策略决定

关键疑问是：“同一个`try`里要放多少代码？”如果几个步骤抛出相同类型的异常，但失败前已经完成的工作不同，单靠异常类型通常无法决定恢复动作。

原文件场景依次打开文件、解析头、读取载荷。下列是**状态设计反例片段**，方法是示意API：

```csharp
try
{
    OpenFile();      // ①打开文件
    ParseHeader();   // ②解析头
    ReadPayload();   // ③读数据
}
catch (IOException)
{
    // ①失败：可能尚未取得文件；②失败：可能已有文件与部分header；
    // ③失败：可能header已完成、payload只完成了一部分。
    // 若没有契约、状态标记或独立处理边界，仅看IOException不能确定如何恢复。
}
```

同样的困难也可发生在思考区提出的三阶段场景：A处理文件句柄，B加载配置，C建立缓存，都报告`FileNotFoundException`，但需要撤销的东西不同。首先查各操作是否保证失败不改变状态，再决定独立`try`、事务或显式阶段标记；异常名称不会自动保存“哪项工作已经提交”。

下面保留原分层片段。假定`OpenFile`成功后返回由调用者负责关闭的流；`ParseHeader`的失败不会留下必须另外修复的可见header状态，`ReadPayload`失败需要标记载荷无效。实际API如果不具备这些条件，就要增加对应恢复措施。

```csharp
var stream = OpenFile(); // 若失败，本段没有取得流；API自身须处理其部分创建状态
try
{
    ParseHeader();
    try
    {
        ReadPayload();
    }
    catch (IOException)
    {
        // 已打开文件、header已成功，此处只处理payload阶段的失败
        MarkPayloadInvalid(); // 此动作本身也可能失败，必须按其契约设计
        throw;
    }
}
finally
{
    if (stream != null) stream.Close();
}
```

原聊天写`stream?.Close()`；这里用第四版时代可用的显式null检查，条件与教学目的相同，`?.`是C#6语法。`Close`仍可能抛出异常，后节解释其影响。也可以内层`try/finally`负责资源、外层`try/catch`负责恢复；嵌套并不是只允许二选一。

<a id="c20-state-bank"></a>
### 银行100元转账：部分完成与补偿

这与文件例参数、状态和用途不同，需要单独看。假定扣款`Withdraw(100)`在余额不足时**不改余额**，收款`Deposit(100)`在账户冻结时**不改余额**。若把它们放进同一个`try`：

```csharp
try
{
    account1.Withdraw(100); // ①扣钱
    account2.Deposit(100);  // ②加钱
}
catch (InvalidOperationException ex)
{
    // ①失败可能无需补偿；②失败则可能需要把已扣的100退回。
    // 本片段缺少阶段信息，无法只凭ex的类型选择正确恢复动作。
}
```

两个失败在给定假设下的恢复需求是：

| 操作 | 异常含义 | 恢复动作 |
| --- | --- | --- |
| Withdraw | 余额不足，未扣款 | 不必退款，但须向调用方报告转账失败 |
| Deposit | 收款账户冻结，未入账 | 尝试把已扣款退回account1；退款失败须另外处理 |

原两阶段片段保留为**简化示意**，修正原来的未定义变量`threw`为`withdrew`：

```csharp
bool withdrew = false;
try
{
    account1.Withdraw(100);
    withdrew = true;
}
catch (InvalidOperationException)
{
    withdrew = false; // 原例threw=false是变量笔误
    // 教学片段只决定是否进入第二步；完整业务还必须向调用方报告失败
}

if (withdrew)
{
    try
    {
        account2.Deposit(100);
    }
    catch (InvalidOperationException)
    {
        account1.Deposit(100); // 补偿可能失败，并非天然原子回滚
        throw;                // 补偿成功后仍向上报告本次转账失败
    }
}
```

这说明恢复动作为什么要知道阶段；它不是金融事务的完整实现。网络超时可能发生在服务端已提交之后，多个线程也可能同时改余额，退款可能再失败；仅用两个`try`并不能排除这些问题。这里没有执行真实账户操作。

决定边界时要明确三件事：失败后的对象状态是什么，这个处理器能否确定该状态，有没有可行的恢复措施。拆`try`是常见做法，但有可靠状态机或事务契约时也可在一个边界处理；“不同失败必然只能写两个try”过于绝对。

<a id="c20-file-cleanup"></a>
### test.txt文件的收尾与状态恢复不同

原例只说明打开成功后要关闭，打开失败时变量仍为null：

```csharp
FileStream fs = null;
try
{
    fs = new FileStream("test.txt", FileMode.Open);
    // 读文件...
}
finally
{
    if (fs != null) fs.Close();
}
```

关闭资源不会自动把之前的业务修改恢复；反过来，把余额退回也不替代释放连接等收尾。异常是常规路径之外也必须考虑的控制路径，这也是部分完成操作需要状态管理的原因。

## 先搜索处理器，再展开内层finally

<a id="c20-unwind"></a>

用户对“内层finally先于catch执行”的疑惑来自把源码三块看成平面结构。要同时看调用栈深度和每个异常区域的嵌套关系。

原抽象调用图是：

```text
Main()
 └─ MethodA()
     └─ MethodB()
         └─ MethodC()  ← 原抽象图在这里throw new Exception()
```

CLR通常先从抛出点向外**搜索**匹配的处理器；找到后进行第二遍栈展开，执行该处理器与抛出点之间需要离开的`finally`；随后进入所选`catch`。所选`catch`自己所关联的`finally`在该`catch`退出时执行。不能说“搜索时每遇到finally便执行再继续找”。历史微软CLR团队文档明确区分这两遍。[搜索与展开的解释](https://devblogs.microsoft.com/dotnet/catch-rethrow-and-filters-why-you-should-care/)

<a id="c20-unwind-thinking"></a>
### 思考区的另一组条件：C抛出，B只有finally，A捕获

原思考区另给了三层区域关系：MethodA调用MethodB，MethodB只有try/finally并调用MethodC，异常在MethodC抛出，MethodA有try/catch/finally。当A的catch匹配该异常且B的清理正常完成时，先搜索确定A的处理器，再展开执行B的finally，随后进入A的catch；A自己同层的finally在该catch退出后执行。这里“内层”是C抛点到A所选catch之间需要离开的B区域，不包括A与该catch同层的finally。

这组处理器在A的条件，与下面处理器在Main、实际最深抛点在B的完整程序分别保留。原T已经正确区分展开途中清理与所选catch同层finally；“先搜索、再展开”是补足阶段的说明，不将这段原T改判成“搜索时每遇finally立即执行”的错误。

<a id="c20-unwind-program"></a>
### Main、MethodA、MethodB的完整原场景

下列方法放在同一个类中，并添加`using System;`即可构成程序；它的实际最深调用是MethodB，和上面的抽象四层图不是同一个调用深度。

```csharp
static void Main()
{
    try
    {
        MethodA();
    }
    catch (InvalidOperationException ex)
    {
        Console.WriteLine("catch in Main");
    }
    finally
    {
        Console.WriteLine("finally in Main");
    }
}

static void MethodA()
{
    try
    {
        MethodB();
    }
    finally
    {
        Console.WriteLine("finally in A");
    }
}

static void MethodB()
{
    try
    {
        throw new InvalidOperationException();
    }
    finally
    {
        Console.WriteLine("finally in B");
    }
}
```

正常的可展开异常路径中，顺序为B抛出，搜索确认Main的处理器，然后B和A的`finally`依次完成，进入Main的`catch`，最后Main的`finally`。原输出：

```text
finally in B
finally in A
catch in Main
finally in Main
```

时间线保留原图的视角，并明确两遍：

```text
throw
  │
  ▼
[搜索catch：找到Main.catch]
  │
  ├─ 展开内层finally：B.finally → A.finally
  ├─ 执行Main.catch本体
  └─ catch退出时执行Main.finally
```

再看原立体区域图：

```text
┌─ Main      ─ try/catch/finally （所选catch在这里）
│  └─ A      ─ try/[无catch]/finally  ← 内层
│     └─ B   ─ try/[无catch]/finally  ← 更内层，throw起点
│
│  搜索沿栈向外；随后展开到选中的catch
└───────────────────────────────
```

以下两个原平面视角都是**错误理解的示意**，不是合法控制流：

```text
try { ... }
finally { ... }   // 错把finally看成在同一try的catch前面
catch { ... }    // C#语法也不允许这个顺序
```

```text
try
  finally   ← 错误：以为它是源码中插在try与catch之间的一块
catch
```

“内层”并不要求在不同方法中；同一个方法的嵌套异常区域也有内外层。内层资源清理通常已在所选`catch`进入前完成，但这依赖那些清理代码确实成功，不是“文件必然已关闭”的额外保证。

**补充：异常过滤器。** CLR早已支持filter；第四版年代的C#还不能写`when`，C#6才提供该语法。filter在搜索阶段执行，因此可以发生在内层`finally`之前。不要在filter中假定内层收尾已经完成。此说明用于澄清两遍机制，不把补充探针当作原聊天程序。[C#规范try语句](https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/language-specification/statements#1311-the-try-statement)

## catch或finally又抛异常，会发生什么

<a id="c20-secondary"></a>

新异常若逃出正在执行的`catch`或`finally`，按外围异常区域继续传播；它不会被这同一`try`的其他兄弟`catch`重新接住。如果原异常还在传播，新异常会替代这条传播路径。这里的“原异常信息丢失”是说外围处理器不自动收到原异常或因果链，**不是CLR把原异常对象的字段擦除或立刻销毁**。仍有引用、已记日志，或明确作为`InnerException`保存时，原信息可以继续存在。[规范的传播规则](https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/language-specification/statements#1311-the-try-statement)

<a id="c20-rollback-failure"></a>
### 恢复代码也会失败：100元转账回滚

下面保留原风险场景。先假定account1已成功扣100，account2因冻结未能入账，catch中的退款又失败：

```csharp
try
{
    account1.Withdraw(100);
    account2.Deposit(100);
}
catch (InvalidOperationException ex)
{
    account1.Deposit(100); // 假定退款又抛InvalidOperationException
}
```

执行过程是收款失败→进入catch→退款失败→传播退款异常。上层若只记录收到的新异常，不能自动看到原收款异常；已扣款且补偿未完成是本场景需要处理的危险状态。原解释把Deposit失败举成“余额不足”，此处改为收款账户冻结；余额不足通常属于Withdraw的前提。

这个大try本身还存在前节的阶段歧义：若Withdraw先失败，就不应无条件退款。保留它是说明“恢复动作可再次失败”的反例，不将其作为推荐转账实现。

<a id="c20-close-failure"></a>
### data.txt的读取失败与关闭失败

原片段使用FileStream，并在读取位置主动抛出“读取失败”：

```csharp
FileStream fs = null;
try
{
    fs = new FileStream("data.txt", FileMode.Open);
    throw new IOException("读取失败");
}
finally
{
    if (fs != null) fs.Close(); // 若这个操作又抛异常，新异常向外传播
}
```

这个程序形状并不保证`Close`一定失败；如果关闭成功，继续传播的仍是“读取失败”。若关闭又抛且未在finally内部处理，新异常取代原传播；这里不会自动生成两异常的集合。Framework FileStream源码中的Dispose可能先刷新未写完的缓冲，再在自己的finally释放句柄，说明清理可以包含仍会失败的I/O；不能只凭清理异常推出GC句柄表损坏，也不能断言失败后句柄一定泄漏。[Framework FileStream.Dispose源码](https://raw.githubusercontent.com/microsoft/referencesource/main/mscorlib/system/io/filestream.cs)

<a id="c20-cleanup-policy"></a>
### 设计清理策略，不能普遍吞掉所有错误

下面是原聊天提出的**有条件做法片段**，不是普遍规则：

```csharp
finally
{
    try
    {
        if (fs != null) fs.Dispose();
    }
    catch
    {
        // 原片段仅预留日志位置：没有实际日志实现。
        // 只有明确允许忽略这类清理失败时，才可采用此策略。
    }
}
```

这样会吞掉清理异常。它也可能吞掉写入或刷新失败，令调用方误以为数据已保存，因此不能一律推荐。真实方案要决定主操作失败与清理失败如何记录、哪个向上传播、需不需要用`InnerException`或`AggregateException`显式保存两个异常，并防止日志操作再次覆盖它们。

原另一个片段是：

```csharp
catch (Exception ex)
{
    Log(ex);
    // 原片段仅示意记录，没有给出真正的恢复或重新抛出。
}
```

记录不等于恢复，`Log`也可能失败；若没有可行恢复措施，在记录后通常仍需`throw;`。反之，在顶层任务边界捕获并明确报告失败也可以是设计的一部分。

现代语法原例：

```csharp
using var fs = new FileStream("data.txt", FileMode.Open);
// 业务逻辑
```

`using var`是C#8的using声明，它在作用域结束时安排Dispose；原书时代可用传统using语句。两者都不屏蔽Dispose抛出的异常，清理错误也不自动等于“致命环境错误”。尽量避免在收尾中引入新的失败是设计建议，不能宣称任意Dispose都保证不抛。

若新异常最终未处理，常规.NET应用的进程可能按未处理异常政策终止；不是CLR检查到“钱没退回”后主动决定杀进程。终止会结束该进程中的执行并释放其持有的资源，却不撤销已经写到文件、数据库或远端服务的状态，也不能说所有共享内核对象和锁都被清零。状态已不可安全恢复时停止业务是重要设计选择，但不是用崩溃代替事务。

原问答以“逃生舱再次爆炸”“最后防线塌了”说明恢复/收尾也会失败的风险。这些类比不能证明后来异常总比先前异常更严重。“一个线程只有一个异常槽所以谁最后炸谁说话”也不是准确的实现保证：程序能保存多个异常对象，只是普通传播不会替你自动合并。

原跨语言比较提到Java的suppressed exceptions和Python的`__context__`。两者确有对应机制：Java的Throwable可保存被抑制异常，try-with-resources可使用它；Python在处理一个异常时引发另一个异常，会记录异常上下文。这只是机制比较，不能倒推.NET自动覆盖的设计动机是“调试更省事”。[Java Throwable文档](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/lang/Throwable.html)、[Python raise语句](https://docs.python.org/3/reference/simple_stmts.html#the-raise-statement)

<a id="c20-catch-finally-cases"></a>
### 追问：第一个异常的catch和finally直接不执行了吗

要看新throw实际发生在哪里。原场景一是catch已进入后再抛；放进一个外围处理器观察时，外围收到“第二个异常”：

```csharp
try
{
    throw new Exception("第一个异常");
}
catch (Exception ex)
{
    Console.WriteLine("catch 执行了");
    throw new Exception("第二个异常");
}
finally
{
    Console.WriteLine("finally 执行了");
}
```

顺序是第一异常→进入catch→打印catch→抛第二异常→本层finally→第二异常继续向外。catch不是完全没执行，而是在新throw处以异常方式退出。

原场景二保留同层catch与finally，原回答曾把同层finally误放到catch之前，随后自行撤回。最终顺序如下：

```csharp
try
{
    throw new Exception("第一个异常（读文件失败）");
}
catch (Exception ex)
{
    Console.WriteLine("catch：准备恢复");
}
finally
{
    Console.WriteLine("finally 开始");
    throw new Exception("第二个异常（关文件失败）");
}
```

```text
try抛第一个异常
  → 匹配到同层catch → 打印“catch：准备恢复”
  → catch正常结束，第一异常已被处理
  → 执行finally，打印“finally开始”并抛第二异常
  → 第二异常向外传播；本层finally在throw后的其余语句不执行
```

这里第一异常已经由catch处理，不是还在展开时被finally覆盖。若内层只有try/finally而所选catch在外层，内层finally的新异常才会在进入原所选catch前取代仍在传播的第一异常；外层要重新按新异常的类型选择处理器。

原场景三是内层catch再抛，外层还有catch：

```csharp
try
{
    try
    {
        throw new Exception("内层第一个异常");
    }
    catch
    {
        Console.WriteLine("内层 catch");
        throw new Exception("内层第二个异常");
    }
    finally
    {
        Console.WriteLine("内层 finally");
    }
}
catch (Exception ex)
{
    Console.WriteLine("外层 catch");
}
```

顺序是内层catch→内层finally→外层catch；外层变量ex引用“内层第二个异常”。不能把“外层没有接到第一异常”误说成“外层catch一定不执行”。它仍可能匹配新异常。

| 场景 | 第一个异常的catch | 该区域的finally |
| --- | --- | --- |
| catch里抛新异常 | 已进入，执行到新throw | 正常展开时执行；新异常随后继续向外 |
| 同层catch处理后，finally抛新异常 | 已进入并正常结束 | 执行到新throw；后续语句不执行 |
| 内层catch抛新异常，外层有catch | 内层catch已进入；外层重新匹配新异常 | 内层finally在进入外层处理器前执行 |

若原对象还被保存，其Message、StackTrace等信息仍可读取。“信息不会自动到达外层”与“对象已被销毁”必须分开理解。

## CLS与跨语言异常：两种不同的包装

<a id="c20-cls"></a>

用户先问非CLS异常的历史规则，又回头问CLS到底是什么。原三概念表应这样理解：

| 缩写 | 全称 | 角色 |
| --- | --- | --- |
| CLR | Common Language Runtime | 执行托管代码的运行时，提供JIT、GC、异常及程序集加载等服务 |
| CTS | Common Type System | 公共类型系统，规定类型、成员和它们的行为 |
| CLS | Common Language Specification | 供跨语言公开组件遵循的共同规则，选取CTS等基础设施中的共同能力 |

CLI是Common Language Infrastructure，指标准化基础设施；CIL是Common Intermediate Language，指其中的中间语言。它们不是CLS的别名。

原“全量菜单/儿童餐”类比想表达：平台能支持的能力比跨语言公开接口的共同集合更大。不能把CTS说成所有语言特性的简单并集，也不能说每种.NET语言、每段内部代码都必须只用CLS。组件遵循CLS，可以让**支持CLS的语言**按共同规则使用它；不相容成员仍可由能理解其签名的语言调用。[语言独立性及CLS规则](https://learn.microsoft.com/en-us/dotnet/standard/language-independence)

原例中的差异仍值得分别看：C#区分`Foo`和`foo`，VB.NET不区分标识符大小写，因此希望相容的公开API不能只靠大小写区分两个成员；`Int32`在CLS范围内，`UInt32`不在，但`Byte`是相容的无符号类型。VB.NET支持`UInteger`，对应`UInt32`，所以“VB没有uint，必然调不了public uint X”不成立。[VB UInteger文档](https://learn.microsoft.com/en-us/dotnet/visual-basic/language-reference/data-types/uinteger-data-type)

VB早就能写可选参数，C#从C#4支持可选参数；语言语法出现的年代与CLS公开契约不是同一问题。运算符有相应CLS元数据规则，不能只用“没有所有语言都支持的运算符语法”把所有运算符成员都判成不相容。

<a id="c20-cls-attribute"></a>
### CLSCompliant声明检查公开接口

原程序集标记：

```csharp
[assembly: CLSCompliant(true)]
```

源文件需要`using System;`或全名。这个特性让支持检查的编译器对不相容的公开签名给出诊断，不把运行时改成“只执行CLS代码”的模式。规则关注程序集外可见部分，包括相应protected接口，而不是要求private/internal实现一概遵循相容子集。

原`Test.Bad`和`Test.Ok`例：

```csharp
using System;
[assembly: CLSCompliant(true)]
public class Test
{
    public uint Bad; // CS3003：公开字段类型不符合CLS

    [CLSCompliant(false)]
    public uint Ok;  // 明确把这个成员排除在本程序集宣称的相容接口外
}
```

标false抑制相应相容性警告，不表示字段从此不可访问或类型变了。公开`Foo`/`foo`同时存在，也会触发大小写相容性警告。原表中的所有.NET语言强制CLS、原VB无无符号类型说明已按这些边界修正；更早基础背景见[第1章CTS/CLS](第01章-CLR的执行模型.md#c01-fcl-cts-cls)。

<a id="c20-noncls-managed"></a>
### 非Exception托管对象与RuntimeWrappedException

CLS要求直接抛出的对象是`System.Exception`或其派生类型；C#的throw/catch类型语法也要求这一类型关系。CLI可表示更宽的托管抛出对象。C#中`throw 123;`和`catch(object obj)`都非法，不能把后者当作.NET1.x时代合法C#写法。

第四版所述.NET2.0以后的C#程序集通常由编译器设置包装行为。处理真正的非Exception**托管对象**时，catch中看到`RuntimeWrappedException`，可以从`WrappedException`读取原对象。这个包装不是`InnerException`：被包的对象本来就不必是Exception。[C#捕获非CLS异常](https://learn.microsoft.com/en-us/dotnet/csharp/how-to/how-to-catch-a-non-cls-exception)

原回答的“旧代码”是下列**错误C#形状**；它混用了不合法的catch类型和后来C#6才有的字符串插值，不能用于复现.NET1.x：

```csharp
try {
    ThrowNonException();
}
catch (Exception ex) {
    Console.WriteLine($"C#异常：{ex.Message}");
}
catch (object obj) { // 反例：C#不允许该catch类型
    Console.WriteLine($"非C#异常：{obj}");
}
```

书中历史双处理器指`catch(Exception)`后跟**无类型catch**。对默认包装的C#程序集，它通常产生CS1058警告，因为前者已能匹配包装后的异常：

```csharp
try
{
    ThrowNonException(); // 此处须确实是非Exception托管对象，不用native int冒充
}
catch (Exception ex)
{
    Console.WriteLine("异常：" + ex.Message);
}
catch
{
    Console.WriteLine("无类型catch"); // 默认包装下通常不可达，编译器给CS1058警告
}
```

C#一般catch没有变量，不能写`catch{ Console.WriteLine(obj); }`假装自动获得原对象。若需读取原值，采用包装路径更直接。

<a id="c20-rwe-explicit"></a>
### 原123包装演示：显式构造不等于自动包装实证

原演示中被改正的非法分支形状单独保留为静态反例，它要求一个C#不接受的catch类型；不能以改成一般catch就假称这个原变量仍可取得：

```csharp
catch (object obj) {
    // 原意：声称默认包装下此分支永远到不了
    Console.WriteLine("进入第二个catch");
}
```

原“验证例子”的目的，是展示捕获包装类型并读回123。下列保留输入和输出，修正其非法`catch(object obj)`为一般catch，并明确这是**现代.NET、默认包装配置**下人为创建包装对象的演示，不是C++/CLI自动包装证明。模式变量语法是C#7，字符串插值是C#6。

```csharp
try {
    throw new RuntimeWrappedException(123); // 现代.NET可调用的object构造
}
catch (Exception ex) {
    Console.WriteLine($"进入第一个catch：{ex.GetType().Name}");
    if (ex is RuntimeWrappedException rwe) {
        Console.WriteLine($"原始非Exception对象：{rwe.WrappedException}");
    }
}
catch {
    Console.WriteLine("进入第二个catch");
}
```

原意输出在上述条件下成立：

```text
进入第一个catch：RuntimeWrappedException
原始非Exception对象：123
```

本机.NET Framework4.8的C#编译器不能调用该object构造，真实诊断CS1729；它不能作为第四版时代可直接编译的验证程序。现代.NET10关闭包装时，这个显式RuntimeWrappedException也在处理器处被解包并落入一般catch；不能只凭该类型继承Exception就推定任何配置都走typed catch。

<a id="c20-noncls-migration"></a>
### 两种迁移策略与程序集设置的范围

第一种策略把旧的两种处理合并：默认包装配置下，在`catch(Exception)`中分别处理包装对象和普通异常。原合并片段保留现代写法：

```csharp
try {
    ThrowNonException(); // API确实可能发出非Exception托管对象
}
catch (Exception ex) {
    if (ex is RuntimeWrappedException rwe) {
        Console.WriteLine($"非C#异常：{rwe.WrappedException}");
    } else {
        Console.WriteLine($"C#异常：{ex.Message}");
    }
}
```

打印“非C#异常”只是原例标签，不能据异常类型可靠判断源语言；C#也可调用发出非Exception对象的库，而Exception派生对象可以来自不同语言。

第二种是给需要保留旧处理语义的程序集明确设置：

```csharp
using System.Runtime.CompilerServices;
[assembly: RuntimeCompatibility(WrapNonExceptionThrows = false)]
```

**原书精度出处：** 20.2、本地MD211/原书物理423印406本来概括Wrap=false时“CLR不会包装”。这在区分旧程序集处理器所见行为上有迁移用途，但内部机制说法不够精确；按官方RuntimeCompatibility备注，内部仍包装而到相应catch/filter解包。保程序集级兼容主旨，不声称实测CLR2.0以前或用现代差异倒判旧迁移意图。

这个设置控制**该程序集的catch和filter中所见的包装语义**，不是全进程开关。官方备注还说明运行时内部仍包装，只是在不希望包装的处理器/filter处解包；原“CLR不再创建任何包装对象”的说法过宽。同一程序集不能用该程序集特性分别为不同方法指定true/false；不同程序集则可有不同设置。[RuntimeCompatibility官方说明](https://learn.microsoft.com/en-us/dotnet/api/system.runtime.compilerservices.runtimecompatibilityattribute?view=netframework-4.8.1)

原关闭包装的双catch场景修正为以下片段；程序集特性应放在文件级，不是方法体中：

```csharp
// 文件级先放using和[assembly: RuntimeCompatibility(WrapNonExceptionThrows=false)]
try {
    ThrowNonException(); // 真正的非Exception托管对象
}
catch (Exception ex) {
    Console.WriteLine($"C#异常：{ex.Message}");
}
catch {
    Console.WriteLine("非C#异常：进入无类型catch，不能直接读取原对象");
}
```

原声称此分支可以输出“非C#异常：123”，依赖不存在的obj变量，不能成立。程序集里的新代码也应尊重这项兼容设置；否则仅写catch(Exception)可能漏掉非Exception托管对象。异常可以继续由外围其他程序集处理，并非此处没有一般catch就必然立刻结束进程。

这个原关闭包装分支的不同用途和输出形状也保留为静态反例，C#类型约束不会被程序集特性取消：

```csharp
catch (object obj) {
    // 原意：关闭包装后读取int 123
    Console.WriteLine($"非C#异常：{obj}"); // 原声称输出123，实际不能这样编译
}
```

原纯C#项目建议“基本不需要”针对C#源码本身不能throw123等非Exception对象，这个原判断保留。**补充条件：** 项目若调用其他语言或IL组件，仍须考虑其真正抛出对象和程序集兼容设置，不能把该建议读成所有跨语言依赖永不需要处理。

<a id="c20-noncls-native"></a>
### 原C++/CLI的throw123是native int

原CPP形状仍保留：

```cpp
void ThrowNonException() {
    throw 123; // 原生C++ int异常；不是装箱的托管System.Int32
}
```

C++/CLI同时涉及native和managed异常。这个native int经过托管异常适配，不能直接断言成为RuntimeWrappedException。微软文档明确区分非托管对象经`SEHException`适配、CLI值类型须装箱后抛，以及原生catch与托管catch的不同匹配方式。[C++/CLI异常基础](https://learn.microsoft.com/en-us/cpp/dotnet/basic-concepts-in-using-managed-exceptions?view=msvc-170)

本机独立实验以原`throw 123`构建CLI DLL，用默认和Wrap=false的两个Framework消费者调用，两者catch(Exception)都收到`System.Runtime.InteropServices.SEHException`，都不是RuntimeWrappedException。补充native catch(int)能读回123，这不等于C#一般catch有对象变量。结果只对应Windows x64、现有MSVC14.44.35207和Framework4.8，没有复现.NET1.x或所有C++/CLI配置。[限定实测记录](整理记录/核验与验收/共享-第20原生CLI异常核验.md)

追问中的`throw 42;`与`throw "error";`同样需要区分native类型；如果C++/CLI明确抛`gcnew System::String(...)`或装箱的CLI值对象，才是另一个托管非Exception场景。自定义CLI值类型也须装箱；不能笼统把任意native结构抛出都说成同一种managed包装。IronPython/IronRuby等实现名称本身也不能证明某次调用的具体异常合同，需看实际实现和对象。

**补充受控实证：** 另用IL库直接`box System.Int32(123)`后throw，以及`ldstr "error"`后throw，避免native映射混入。两环境的默认消费者都捕到RuntimeWrappedException并读到Int32/123或String/error；两环境Wrap=false消费者都进入一般catch。现代显式newRWE的false配置也进一般catch。原第一次Framework构造失败、现代初次缺少依赖部署失败及一次错误预设均保存；最终按真实输出校正，没有把这些失败改写成历史成功。[源码与实际命令/输出](整理记录/验证工作区/第20章/非CLS托管包装/结果.json)

## Exception的诊断信息与自定义异常

<a id="c20-exception-members"></a>

Exception是普通托管异常对象的公共基类，提供报告失败和保存上下文的常用接口。不能将“统一契约中心”“宪法”类比理解为任何CLR、native或跨语言异常对象原本就都具有这一类型；前节已区分内部包装和处理器视图。

<a id="c20-message"></a>
### Message供人阅读，不是稳定机器错误码

原输入`abc`不能按整数解析，例子如下：

```csharp
try
{
    int.Parse("abc");
}
catch (Exception ex)
{
    Console.WriteLine(ex.Message);
    // 中文环境可能显示“输入字符串的格式不正确。”；消息随版本/文化变化
}
```

Message是只有getter的虚属性，描述当前异常。用清楚、完整的句子是设计建议，英文首字母/句号规范不能不加条件套到所有语言和已有库消息。不要靠`ex.Message.Contains("abc")`识别失败类别；本地化与版本都可能改变文本。日志需要上下文时也不必一律只记录Message或一律只记录ToString，取决于读者和用途。

<a id="c20-inner-chain"></a>
### 数据层与转账层：InnerException保留因果

原两层方法用不同消息说明同一次失败的两个抽象层次：

```csharp
void TransferMoney()
{
    try
    {
        DeductBalance();
    }
    catch (InvalidOperationException ex)
    {
        // 把原始异常"装进去"
        throw new InvalidOperationException(
            "转账失败，余额不足。",
            ex); // ← InnerException
    }
}
```

```csharp
void DeductBalance()
{
    throw new InvalidOperationException("账户余额为负数。");
}
```

外围处理器读取这两条消息：

```csharp
catch (Exception ex)
{
    Console.WriteLine(ex.Message);
    // 转账失败，余额不足。

    Console.WriteLine(ex.InnerException?.Message);
    // 账户余额为负数。
}
```

这里外层Message是“转账失败，余额不足。”，InnerException.Message是“账户余额为负数。”。原“前驱指针”类比把InnerException看作指向失败前因的引用，而非可随意改写的普通链表槽。`?.`是聊天采用的C#6写法；第四版年代可用显式null判断。包装用于表达“本层操作因底层失败而失败”，不是把失败抹掉。通常应保留有价值的原异常，但要按公开契约决定哪些信息传给哪一层，不能把“任何场景永远把完整内部异常暴露给所有调用方”当唯一规则。

原用于寻找最深原因的片段：

```csharp
try
{
    Foo();
}
catch (Exception ex)
{
    var root = ex.GetBaseException();
    Console.WriteLine(root.Message);
}
```

普通Exception.GetBaseException沿InnerException链寻找最深对象；没有内层时返回自己。这是该实现的链语义，不说明AggregateException的多分支一定能缩成一个真正“罪魁祸首”，也不能无视派生类重写。

<a id="c20-stack-basic"></a>
### StackTrace记录的抛出轨迹与两种throw

原读取片段及示意结果：

```csharp
try
{
    Foo();
}
catch (Exception ex)
{
    Console.WriteLine(ex.StackTrace);
}
```

```text
在 MyApp.Foo()
   在 MyApp.Main()
```

方法名、路径、行号和显示语言是示意；是否有PDB、是否内联及具体运行时会影响可见结果。下面的两个catch是**供替换对比的片段**，不能把它们接在同一个try后面，误写成前者已捕获全部后仍靠后者处理：

```csharp
catch (Exception ex)
{
    // ❌ 错误：堆栈从这一行重新开始
    throw ex;
}

catch
{
    // ✅ 正确：保留原始堆栈
    throw;
}
```

`throw ex;`是带表达式的throw，对同一对象建立当前点的抛出轨迹；`throw;`是在catch上下文重新抛出当前异常，保留已有异常轨迹。对象身份与轨迹信息是两件事，前者不因为用了变量就自动new一个异常。

<a id="c20-stack-program"></a>
### Main→A→B的完整原比较程序

```csharp
using System;

class Program
{
    static void Main()
    {
        try
        {
            A();
        }
        catch (Exception ex)
        {
            Console.WriteLine("=== 外层 catch 拿到的 StackTrace ===");
            Console.WriteLine(ex.StackTrace);
        }
    }

    static void A()
    {
        try
        {
            B();
        }
        catch (Exception ex)
        {
            // 我们重点对比这里的两种写法
            throw ex;   // 对比反例：以当前点重新抛出同一实例
            // throw;   // ✅ 写法2：不带变量的throw
        }
    }

    static void B()
    {
        // 异常最初在这里抛出
        throw new InvalidOperationException("B方法出错了");
    }
}
```

原throwex分支的显示示意：

```text
=== 外层 catch 拿到的 StackTrace ===
   在 Program.A() in C:\xxx\Program.cs:行号 22
   在 Program.Main() in C:\xxx\Program.cs:行号 9
```

把A内的throwex换成throw后的原显示示意：

```text
=== 外层 catch 拿到的 StackTrace ===
   在 Program.B() in C:\xxx\Program.cs:行号 30
   在 Program.A() in C:\xxx\Program.cs:行号 22
   在 Program.Main() in C:\xxx\Program.cs:行号 9
```

这两组22/9/30行号只属于原说明的假定布局，不是这份Markdown或本机程序必然产生的行号。本机原完整程序在两环境优化编译后的实际方法序列分别是`A/Main`与`B/A/Main`；没有PDB时不显示原示意路径或行号。规范保留轨迹的意义也不等于所有优化/所有栈帧的文字输出完全相同。

思考区还用了另一个名为Test的定位示意：原`Test.B():line20 → Test.A():line14 → Test.Main():line8`，带变量抛后成为`Test.A():line16 → Test.Main():line8`。这组不同的名称和数字仍是说明用途的示意，没有另一个已经运行的Test程序。

原“案发现场变成警察局地址”类比强调后来读到的轨迹起点变了；“出生证明小本本”类比强调同一对象记录的信息可能变化。异常对象可以早于实际throw构造，构造时通常还没有抛出轨迹，所以这里的“出生地点”应理解为记录的抛出现场，而非new表达式的位置。

<a id="c20-wrap-information"></a>
### 加说明可以包装，包装不会自动隐藏内部信息

思考区提出了不同场景：B除零失败，A需要说明“处理订单时出错”。可以让上层异常保存原除零异常为InnerException；两层各有自己的轨迹，不用throwex删掉原现场。

原具体包装片段：

```csharp
catch (Exception ex)
{
    // 对外暴露一个新的异常，原始异常作为 InnerException
    throw new InvalidOperationException("对外暴露的错误信息", ex);
}
```

该片段保存内部异常，对诊断有用，**不能说它隐藏了内部细节**；完整ToString仍可能递归输出InnerException的信息。向外部用户展示的消息与内部诊断日志应按该边界的真实合同决定，throwex或包一层并不是可靠的敏感信息过滤机制。原提到的微服务多层日志、中间件和拦截器也可能因此只记录到中间层，具体影响没有固定“N倍”量化。也不能把Visual Studio当前执行调用栈与Exception.StackTrace混为同一份记录；后节解释两种观察。

<a id="c20-tostring"></a>
### ToString默认包含什么

原日志片段：

```csharp
catch (Exception ex)
{
    Console.WriteLine(ex.ToString());
}
```

普通Exception的默认表示包含类型、消息、内层异常表示和存在的异常轨迹；**不自动列出Source、Data、HelpLink或HResult所有属性**。特定派生类可以重写，日志框架也可以自己添加属性，不能据此改变普通Exception默认合同。Framework源码和固定.NET10源码均与本机不同marker实测相符。[ToString官方说明](https://learn.microsoft.com/en-us/dotnet/api/system.exception.tostring?view=netframework-4.8.1)

<a id="c20-exception-hierarchy"></a>
### ApplicationException与SystemException不能按责任划分恢复

原设想图：

```text
SystemException     ← CLR / FCL 抛的
ApplicationException ← 开发者自己抛的
```

原按两个分支捕获的设计片段：

```csharp
catch (SystemException) { /* 系统问题 */ }
catch (ApplicationException) { /* 业务问题 */ }
```

这只表示一种不可靠的分类设想；实际继承树并不严格按“框架抛/开发者抛”划分，不能据基类判断损坏程度、业务责任或能否恢复。NullReferenceException、IndexOutOfRangeException、InvalidOperationException都属于SystemException，所需处理却明显不同。

原两个MyException形状是互相替换的定义，不能在同一作用域同时定义同名类：

```csharp
// ❌ 旧规范
public class MyException : ApplicationException { }

// ✅ 新规范
public class MyException : Exception { }
```

直接继承Exception通常是新自定义异常的建议；旧的ApplicationException派生类仍是合法类型，不会因为设计建议就变成编译错误。优先使用能准确表达失败的现成异常，需要自定义时再定义新类型；typed catch匹配派生类型也可以适合一个共同处理策略，不应绝对禁止任何基类catch。

<a id="c20-balance-exception"></a>
### BalanceInsufficientException保留两项业务数据

原完整定义包含当前余额和所需金额两个decimal属性、三个常见普通构造、业务构造以及历史序列化成员。聊天用C#6的get-only自动属性、nameof和字符串插值表达；机制与语言版本要分开，不能说原Framework自带C#5编译器可直接编译此语法。

```csharp
using System;
using System.Runtime.Serialization;
[Serializable]
public class BalanceInsufficientException : Exception
{
    public decimal CurrentBalance { get; }
    public decimal RequiredAmount { get; }

    // 无参构造（常见设计惯例，不是C#编译语法强制）
    public BalanceInsufficientException() { }

    // 带消息的构造（常见设计惯例，不是C#编译语法强制）
    public BalanceInsufficientException(string message)
        : base(message) { }

    // 带消息 + 内部异常的构造（常见设计惯例，不是C#编译语法强制）
    public BalanceInsufficientException(string message, Exception inner)
        : base(message, inner) { }

    // 业务构造函数
    public BalanceInsufficientException(decimal current, decimal required)
        : base($"余额不足。当前余额：{current}，所需金额：{required}")
    {
        CurrentBalance = current;
        RequiredAmount = required;
    }

    // 反序列化构造函数（历史序列化合同；现代.NET新设计按实际需求决定）
    protected BalanceInsufficientException(SerializationInfo info, StreamingContext context)
        : base(info, context)
    {
        CurrentBalance = info.GetDecimal(nameof(CurrentBalance));
        RequiredAmount = info.GetDecimal(nameof(RequiredAmount));
    }

    // 序列化方法
    public override void GetObjectData(SerializationInfo info, StreamingContext context)
    {
        base.GetObjectData(info, context);
        info.AddValue(nameof(CurrentBalance), CurrentBalance);
        info.AddValue(nameof(RequiredAmount), RequiredAmount);
    }
}
```

三个常见构造是有用的API设计惯例，**不是C#语言要求每个Exception派生类都必须具备的语法条件**。业务构造才设置两个余额属性；使用无参/仅消息构造时，两值默认是0，不能凭存在属性就知道真正失败时的余额。

在原Framework序列化/Remoting的具体合同中，需要让异常类型定义在相应两端可用，保证基类与新增业务状态都按合同保存/恢复。不是“程序可能有异常，所以所有类型永远都必须序列化”。现代.NET去除了该Remoting机制，.NET8起相关旧序列化构造和GetObjectData有SYSLIB0051提示；新设计按实际序列化需要选择，不静默删掉本历史例。[自定义异常设计](https://learn.microsoft.com/en-us/dotnet/standard/exceptions/how-to-create-user-defined-exceptions)、[现代旧序列化API变化](https://learn.microsoft.com/en-us/dotnet/fundamentals/syslib-diagnostics/syslib0051)

本机以Roslyn的C#6模式、现有Framework程序集编译原完整类型，Framework运行时受控内存往返保持CurrentBalance=12.5、RequiredAmount=100、Data.UserId=123和Message；原类型代码没有改算法。另在现代.NET10只编库，实际有SYSLIB0051/CS0672提示，没有运行现代formatter或真实Remoting。[限定历史验证](整理记录/验证工作区/第20章/余额异常历史序列化/结果.json)

## Data：沿传播路径附加上下文

<a id="c20-data"></a>

原API形状（IDictionary来自System.Collections）：

```csharp
public virtual IDictionary Data { get; }
```

它是**非泛型**字典接口，键和值都是object；字符串键是常用约定，不是`IDictionary<string,object>`的类型保证。本机普通异常接受整数123作键。Data属性只有getter，不等于所返回字典不可修改；反过来，虚属性和特定运行时例外也不保证任何异常的Data都可写。Framework源码按需建立容器，某些不可变异常使用只读空容器，不能说所有异常构造时已经分配一个随意写的字典。

“便签”“随身行李箱”类比说明上层可以给同一个对象追加诊断信息，而不是重新定义每种异常组合。行李箱不是受保护存储，也不是必须只存字符串的业务契约。

<a id="c20-data-timeout"></a>
### 无上下文的Timeout例：原SQL构造是反例

原DAL→Service→Controller场景如下，**不能直接编译**，因为SqlException没有可调用的public string构造；其余层次说明传播用途仍保留：

```csharp
void Dal_GetUser()
{
    throw new SqlException("Timeout");
}

void Service_GetUser()
{
    try
    {
        Dal_GetUser();
    }
    catch
    {
        throw;
    }
}

void Controller_GetUser()
{
    try
    {
        Service_GetUser();
    }
    catch (Exception ex)
    {
        Log(ex);
        throw;
    }
}
```

日志只有Timeout等消息时，未必能确定触发用户、请求ID和连接条件。若做一个受控教学替身，可以把DAL抛出改为`new InvalidOperationException("Timeout")`，这是**补充替身**，不冒称创建了真实SQL连接超时异常。本章未连接数据库。

原另外两种表达方式分别是：

```csharp
throw new MySqlException("Timeout", userId, connStr, requestId);
```

MySqlException只是示意自定义构造，源没有该类型定义；强类型业务字段有价值，不能一概说自定义异常“总是太重”。

```csharp
throw new Exception($"Timeout, UserId={userId}, Conn={conn}");
```

把字段拼进人类消息不适合当稳定机器解析合同，但不等于Message不能包含必要的人类上下文。原Data方式保留三个不同键：

```csharp
catch (Exception ex)
{
    ex.Data["UserId"] = userId;
    ex.Data["ConnectionString"] = connStr;
    ex.Data["RequestId"] = requestId;
    throw; // 保留原始堆栈
}
```

ConnectionString只是原示意字段名，真实含凭据连接串不应原样作为任意处理器可读/日志公开的诊断值；可以选不含秘密的连接标识。修改Data也可能因只读容器、分配或不合适的键值而失败，添加诊断应避免让这个新失败盖掉业务异常。[Data合同及冲突说明](https://learn.microsoft.com/en-us/dotnet/api/system.exception.data?view=netframework-4.8.1)

<a id="c20-data-program"></a>
### userId三层原例与Layer覆盖

下面是放在一个类中的方法片段，需`using System; using System.Collections;`。Dal使用普通InvalidOperationException模拟超时，不是SQL库实际抛出：

```csharp
void Dal_GetUser(int userId)
{
    throw new InvalidOperationException("数据库连接超时");
}

void Service_GetUser(int userId)
{
    try
    {
        Dal_GetUser(userId);
    }
    catch (Exception ex)
    {
        ex.Data["Layer"] = "DAL";
        ex.Data["UserId"] = userId;
        ex.Data["Timestamp"] = DateTime.UtcNow;
        throw; // ✅ 保留原始堆栈
    }
}

void Controller_GetUser(int userId)
{
    try
    {
        Service_GetUser(userId);
    }
    catch (Exception ex)
    {
        ex.Data["Layer"] = "Controller";
        ex.Data["RequestId"] = Guid.NewGuid();
        Log(ex);
        throw;
    }
}

void Log(Exception ex)
{
    Console.WriteLine(ex.ToString());

    foreach (DictionaryEntry entry in ex.Data)
    {
        Console.WriteLine($"  {entry.Key} = {entry.Value}");
    }
}
```

以userId=123调用时，Service先写Layer=DAL，Controller后来用同一个键覆盖为Controller；不是保留了两个Layer值。原输出示意仍保留：

```text
System.InvalidOperationException: 数据库连接超时
   at ...
   at ...
   at ...
  Layer = Controller
  RequestId = xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx
  UserId = 123
  Timestamp = 2026-01-15 10:30:00
```

真实Guid每次生成、UTC时间是运行时值，原2026-01-15时间不是固定输出；字典枚举顺序也不作为IDictionary合同。后面的键值来自代码里显式foreach，不是之前的ToString自动展开。

<a id="c20-data-inner-table"></a>
### Data和InnerException职责表

| 特性 | InnerException | Data |
| --- | --- | --- |
| 用途 | 表达原失败与包装失败的因果 | 附加周围诊断上下文 |
| 数量/形状 | 普通属性是一条异常引用链 | 键值字典；聚合异常另有多分支合同 |
| 是否新建异常 | 通常new包装异常并把原异常传入构造；InnerException没有public setter | 通常可给现有异常的可写字典追加，无需new包装异常 |
| 典型内容 | 原始异常 | 用户ID、请求ID、配置名 |
| 对语义影响 | 表达因果关系 | 不直接改变类型/轨迹；若API约定解释键值，也能影响处理逻辑 |

“因为什么失败”偏向InnerException，“失败时处在什么环境”偏向Data。不要把“Data无任何语义影响”或“错误码绝不可放Data”说成运行时禁令；明确、可验证的API合同可以约定键值，不过强类型业务属性通常更清楚。`if(ex.Data["Code"].Equals("A"))`没有处理键不存在/null或被别人改动等情况，不能当可靠一般判断。

<a id="c20-data-limits"></a>
### 共享、大小、键名与手工输出

只在catch里写不自动获得线程安全，同一个异常仍可能被多个线程同时处理；要避免并发改同一容器，或按真实共享边界同步/隔离。大对象会延长引用链、增加诊断/序列化成本；原负面片段：

```csharp
ex.Data["HugeObject"] = someBigDto; // ❌
```

string、int、Guid、DateTime、enum是原建议的小值，不是Data只允许这些类型的白名单。历史跨域序列化还需值满足其实际序列化约定。

键名碰撞的两个不同片段：

```csharp
ex.Data["UserId"] = 1;
// 别人也写了 UserId，把你的值盖了
```

```csharp
ex.Data["MyLib.UserId"] = 1;
```

MyLib前缀降低碰撞概率，不是类型系统保证键全球唯一。Layer原例正好演示后来赋值覆掉先前值。

原声称下列调用会自动追加Data：

```csharp
Console.WriteLine(ex.ToString());
```

**这个断言不成立。** 原希望展示的内容是：

```text
---> Data:
     UserId = 123
     RequestId = xxx
```

它必须来自手工枚举、特定logger或ToString重写；本章三层例已经用foreach完成。Data可以保存用户/请求/租户标识、机器/环境/配置名、循环索引/重试次数等诊断值；错误类型的核心业务状态，如BalanceInsufficientException.CurrentBalance，则更适合作为明确强类型属性。

保留原犯罪现场职责类比表：

| 成员 | 角色类比 |
| --- | --- |
| Message | 给人看的一句话描述 |
| StackTrace | 已记录的案发轨迹 |
| InnerException | 案底，即失败前因 |
| Data | 案发现场的环境信息 |

## HelpLink与HResult的实际合同

<a id="c20-helplink"></a>

**原书表格错误出处：** 20.3表20-1、本地MD234/原书物理424印407把HelpLink访问标“只读”，实际Exception.HelpLink是public virtual get/set，原官方例也有显式赋值。本节原用途及两个帮助地址保，不把表中的访问标记误作API只读合同。[HelpLink定义与赋值例](https://learn.microsoft.com/en-us/dotnet/api/system.exception.helplink?view=netframework-4.8.1)

HelpLink可以给错误附一份说明书：

```csharp
public virtual string HelpLink { get; set; }
```

它可保存URL/URN形式的帮助地址，适合库/SDK或复杂错误文档，也可用于业务代码；不能因“使用不多”断言业务代码不应使用。它与临时调试键值的用途不同。原连接场景：

```csharp
try
{
    ConnectToDatabase();
}
catch (Exception ex)
{
    ex.HelpLink = "https://docs.mycompany.com/errors/db/timeout";
    throw;
}
```

docs.mycompany.com是原示意字符串，没有访问该地址或声称文档真实存在。外围原打印片段：

```csharp
catch (Exception ex)
{
    Console.WriteLine(ex.ToString());
}
```

默认ToString不会自动产生原声称的以下行：

```text
HelpLink: https://docs.mycompany.com/errors/db/timeout
```

要显示它，应显式打印HelpLink或由支持它的日志/调试界面读取；本章没有验证所有Visual Studio版本的异常助手一定显示可点击帮助链接。

| 属性 | 用途 |
| --- | --- |
| Data | 结构化诊断键值，如UserId、RequestId |
| HelpLink | 人工查阅帮助说明的地址 |

<a id="c20-hresult"></a>
### 32位错误值并非类型唯一身份证

HResult保留在Exception中有互操作的历史理由：早期COM接口用HRESULT报告调用结果，.NET采用托管异常模型后仍需与大量既有COM组件互通，所以保存/映射这个值。原“Windows世界主要靠HRESULT”收窄到这里的COM语境；普通Win32还可能使用返回值与last-error，.NET引入自身的托管异常模型也不等发明全部try/catch机制。

Framework4.5以后的历史签名应是**非virtual**：

```csharp
public int HResult { get; protected set; }
```

更早Framework中get/set都是protected；现代.NET10本机getter和setter都是public、getter仍非virtual。它确实是公开可用的错误信息，不是“官方禁止应用读取的实现细节”。按类型处理多数普通托管失败更清楚，按某API明确约定的HRESULT处理互操作或诊断也可以正确。[HResult版本说明](https://learn.microsoft.com/en-us/dotnet/api/system.exception.hresult?view=netframework-4.8.1)、[固定.NET10实现](https://github.com/dotnet/runtime/blob/v10.0.0/src/libraries/System.Private.CoreLib/src/System/Exception.cs)

原将中间4位全称为保留位的ASCII图修为协议布局：

```text
| S严重性 | R | C客户 | N NTSTATUS | X | Facility | Code |
|  1位    |1位|  1位  |    1位    |1位|   11位   |16位  |
```

S为0表示成功，为1表示失败；按有符号Int32看是**非负**成功、负值失败，S_OK=0不能漏掉。中间位C/N有实际含义，不是四个位都保留。Facility指出来源类别，Code给具体编号。[HRESULT协议结构](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-erref/0642cb2f-2075-4469-918c-4441e69c548a)

原两个值：COR_E_INVALIDOPERATION=0x80131509；ArgumentNullException常见的COR_E_ARGUMENTNULL/E_POINTER=0x80004003。但NullReferenceException也可使用80004003，本机两环境确实相同，所以HResult不是异常类型的一一唯一标识，更不是对象身份编号。

原错误码判断与按类型处理的两个不同片段：

```csharp
catch (Exception ex)
{
    if (ex.HResult == unchecked((int)0x80131509))
    {
        // 若该API明确约定此码则可以判断；若只想区分异常类型，优先typed catch
    }
}
```

```csharp
catch (InvalidOperationException ex)
{
    // 要识别InvalidOperationException类型时使用这一合同
}
```

前者不是语法错误，是否合适取决于想识别API约定的码还是准确异常类型。不能因为跨平台而笼统断言所有规定的HResult都随机改变，也不能将读取码一律判为违背面向对象。

### 三种HRESULT场景

原COM失败读取片段：

```csharp
try
{
    comObject.DoSomething();
}
catch (COMException ex)
{
    int hr = ex.HResult;
    // 映射 COM 错误码
}
```

comObject是外部示意API，本章没有调用真实COM。已知HRESULT可以映射为具体托管异常，未明确映射的值才通常映射COMException，因而catch(COMException)不代表接到每一种COM调用失败；IErrorInfo还会影响诊断信息和相应映射。[HRESULT与Exception映射](https://learn.microsoft.com/en-us/dotnet/standard/native-interop/how-to-map-hresults-and-exceptions)

原向COM暴露DoWork、自定义8004ABCD场景：

```csharp
public void DoWork()
{
    try
    {
        // ...
    }
    catch (MyException ex)
    {
        ex.HResult = unchecked((int)0x8004ABCD); // 原例0x8004ABCD；Framework此处外部protected赋值非法，现代.NET10可赋值
        throw;
    }
}
```

该外部setter在Framework的protected合同下不合法，不能假称可用；可以在MyException自己的构造/成员中设置HResult，这是**补充修正形状**：

```csharp
class MyException : Exception
{
    public MyException(string message) : base(message)
    {
        HResult = unchecked((int)0x8004ABCD); // 保留原例数值；实际COM接口须约定其错误码
    }
}
```

现代.NET10原外部赋值本机可以编译且读回8004ABCD，应按现代合法代码保留；这项观察不证明真实COM客户端的全部映射行为。本章也未执行WinDbg/SOS/CrashDump分析，HResult仅是这类诊断的重要线索。

## 为什么访问StackTrace会调用运行时服务

<a id="c20-stack-runtime"></a>

原思考的“委托给CLR”类比也保留：公开属性可以让BCL/运行时服务处理已经保存的异常诊断数据；这不是说创建了一个C# Delegate对象，也不是getter直接读取此刻调用者栈、全部为native代码的承诺。

原问题没有写属性名。实际核本地第四版20.3，物理425/印刷408的前后段落确认该句指**System.Exception.StackTrace**，不是猜测某个属性；物理424的表TargetSite只是另一个成员。辅助定位已保存原页和散列，没有扩写原书整章。[原书定位记录](整理记录/验证工作区/作者B原书辅助定位/第20章属性定位说明.md)

原假想实现仅作**教学假模型**，不能命名后当真实System.Exception源码：

```csharp
public class Exception
{
    private string _stackTrace; // 假设有个私有字段

    public string StackTrace
    {
        get { return _stackTrace; } // 只是读内存
    }
}
```

属性访问本来就可以执行getter，不等于只读字段；即使getter只读字段，该托管程序仍是在运行时/JIT支持下执行，不能说“完全不需要CLR”。Exception本身是普通托管对象，并非new时移到非托管堆。

实际机制要分几步：new一个普通Exception时通常StackTrace为null；throw/传播阶段保存相应异常轨迹；读取时可依据这些保存信息得到方法与位置，再格式化为文字。**读取异常的旧轨迹不是遍历读取当下的当前线程栈**。原所列IP、方法/元数据与PDB只是帮助说明保存/符号化层次，具体内部布局不是公共合同；PDB主要提供文件/行号，方法名还可依元数据确定。

Framework GetStackTrace有已有字符串/远程轨迹路径，也有向运行时请求轨迹再返回字符串的路径，源码明确此路径不把格式化结果普遍写回_stackTraceString；固定.NET10也有已有字符串或new StackTrace(this,true)路径。因而“仅第一次读取后必缓存、整个过程100%native”都没有这样的保证；普通同步getter调用也不等于一个额外的特殊暂停机制。托管BCL和运行时服务协作，不是每个Exception属性都重新走完整栈采集。[Framework Exception源码](https://raw.githubusercontent.com/microsoft/referencesource/main/mscorlib/system/exception.cs)、[固定.NET10 Exception源码](https://github.com/dotnet/runtime/blob/v10.0.0/src/libraries/System.Private.CoreLib/src/System/Exception.cs)

原两个片段仍体现可见语义：

```csharp
catch (Exception ex)
{
    throw ex; // 重置堆栈
}
```

```csharp
catch
{
    throw; // 保留堆栈
}
```

带表达式的throw更新本次抛出轨迹，rethrow保留；这两个输出差异不能独立证明原答描画的每一步IP存储、缓存清空或所有底层结构完全不变。

Data在Framework某些路径会调用运行时判断是否使用不可变容器，再由托管代码创建字典；HResult普通get/set则读写字段，COM映射发生在互操作边界，不是getter每次都去做映射。

<a id="c20-edi-intro"></a>
### ExceptionDispatchInfo和黑匣子类比

原进阶单行片段需要`using System.Runtime.ExceptionServices;`与已取得的ex：

```csharp
ExceptionDispatchInfo.Capture(ex).Throw();
```

EDI保存捕获时的调度状态，稍后Throw可以保留相应轨迹，并常在异步边界传播中使用；它不是“只有纯native强制做事，编译器无关”的单一层机制。捕获尚未抛出的对象也不能凭空创造此前不存在的抛出轨迹，后节再结合更完整场景解释。[EDI Capture官方合同](https://learn.microsoft.com/dotnet/api/system.runtime.exceptionservices.exceptiondispatchinfo.capture)

“黑匣子—询问杆—飞行记录仪—打印纸条”类比可理解为getter请求读取**已保存的事故轨迹**并格式化，而不是让CLR重演当下所有调用栈。实际异常的抛出、展开和格式化都有成本，本章没有做性能基准；在循环中写catch并不意味着每次循环都抛异常或每次都读取StackTrace，不能据此给任意循环catch下绝对禁令。

## 调试器的当前栈、异常轨迹与错误报告

<a id="c20-debugger-views"></a>

用户追问的矛盾是：throwex既然更新了抛出点，为什么原解释说Visual Studio还能看到`B→A→Main`？关键要先确定**观察时刻和对象**，不能先假设有一份专供调试器、永不被改变的完整快照。

Visual Studio可配置在异常刚引发、在用户代码未处理或最终未处理时暂停；在B首次抛出时暂停，B仍处在当前调用栈中。在异常已经展开、进入A的catch后，B的活动帧已经退出；异常对象仍可记得此前的B轨迹。到了A的throwex再次引发异常时，当前活动栈已经是A及其调用者。调试器的当前调用栈不是Exception.StackTrace属性的另一个名字，也不能说所有CLR异常默认都会在第一次引发时中断。[Visual Studio异常设置](https://learn.microsoft.com/en-us/visualstudio/debugger/managing-exceptions-with-the-debugger?view=visualstudio)

保留原三对象对比表的维度，改成实际观察合同：

| 你查看的内容 | 数据对象/来源 | throwex之后怎样理解 |
| --- | --- | --- |
| VS的当前“调用栈” | 调试器当前暂停位置对应的线程栈 | 在B首次暂停与在A重抛处暂停是不同时间点，不能固定说不受影响 |
| ex.StackTrace | 异常已保存的抛出/传播轨迹及其文字表示 | 普通带表达式throw会以该点更新轨迹；先前另存日志并不会被擦除 |
| WER/转储所展示的诊断 | 采集的原生上下文、转储内容、托管异常诊断及工具解释等 | 取决于运行时、采集方式、符号和转储类型，不是一列固定的B/A/Main合同 |

<a id="c20-before-after-trace"></a>
### 在A里读取，然后到外层再读取

原思考区先提出一个很短的片段，在同一catch中**先打印，再throwex**：

```csharp
catch (Exception ex)
{
    Console.WriteLine("ex.StackTrace:");
    Console.WriteLine(ex.StackTrace); // 此时尚未执行下一行的throwex
    throw ex;
}
```

原思考曾误说这个首次打印已经是`A/Main`，后来又改成`B/A`。不能把新throw尚未执行时的读取与随后更新后的读取混在一起。

思考区完整静态Program与正式答的实例方法在输出文字和异常消息上不同，分别保留。思考区的两条===标题、`B炸了`消息：

```csharp
using System;

class Program
{
    static void Main()
    {
        try
        {
            A();
        }
        catch (Exception ex)
        {
            Console.WriteLine("=== 外层 catch 的 StackTrace ===");
            Console.WriteLine(ex.StackTrace);
        }
    }

    static void A()
    {
        try
        {
            B();
        }
        catch (Exception ex)
        {
            Console.WriteLine("=== A 中 catch 里的 ex.StackTrace ===");
            Console.WriteLine(ex.StackTrace); // 这里输出的是啥？
            throw ex; // 重置点
        }
    }

    static void B()
    {
        throw new InvalidOperationException("B炸了");
    }
}
```

正式答的`外层 StackTrace:`/`A 中 catch 的 StackTrace:`与`B 炸了`消息，是可放进一个类中的实例方法片段，需要相应using及调用入口：

```csharp
void Main()
{
    try { A(); }
    catch (Exception ex)
    {
        Console.WriteLine("外层 StackTrace:");
        Console.WriteLine(ex.StackTrace);
    }
}

void A()
{
    try { B(); }
    catch (Exception ex)
    {
        Console.WriteLine("A 中 catch 的 StackTrace:");
        Console.WriteLine(ex.StackTrace);
        throw ex; // 重置点
    }
}

void B()
{
    throw new InvalidOperationException("B 炸了"); // 原始抛出点
}
```

两环境实际对这两个原场景观察到：

```text
A的catch先读：B → A
执行throwex之后，Main的catch再读：A → Main
```

第一次并不自动包含更外的Main；A帧的位置信息通常对应调用B的相关位置，不是因为进入catch就自动记录“catch语句行号”。原正式答把“异常变成未处理，外层catch接住”写在一起也矛盾：该原程序有Main处理器，异常在这里被处理；去掉它才是另一个可能未处理的场景。

若在VS中使用原提到的Ctrl+Alt+E异常设置入口，勾选相关CLR异常“引发时中断”可在处理器前检查它；取消这个选项并不表示所有应用只有一种固定的未处理暂停行为，还要看Just My Code等设置。上述有外层catch的程序也不会因为取消首次暂停就变成真正未处理异常。本章没有实际操作VS或生成WER转储。

<a id="c20-firstchance"></a>
### FirstChance通知与原时间线

原T0—T3可以这样区分：T0在B引发，通知发生在搜索相应处理器之前；随后搜索、展开至A的catch；T1先读取旧轨迹；T2用throwex再次引发；T3在Main处理并读取新的普通轨迹。通知不是处理失败或恢复状态的catch。[FirstChanceException合同](https://learn.microsoft.com/en-us/dotnet/api/system.appdomain.firstchanceexception?view=netframework-4.8.1)

**补充受控观察：** 用明确NoInlining的方法Origin/Transit/Entry/Main，在两个运行时登记FirstChance事件：第一处通知的当前栈含Origin/Transit/Entry/Main；在Transit再抛时第二处通知当前栈只含Transit/Entry/Main。裸rethrow保留的异常轨迹仍能含Origin，而当前物理栈不会因此恢复Origin。四条路径在本探针均有两次对应事件；数量不作为所有宿主/所有异常的保证，也不当作真正VS调试器或Windows异常地址实证。[实际轨迹与调度记录](整理记录/验证工作区/第20章/轨迹与调度/结果.json)

<a id="c20-wer-contract"></a>
### 原书的Windows错误报告语境

“在字段那里失败”是在说明部署到客户现场后出错，即in the field，和C#成员字段没有关系。现场问题可能不容易复现，保存的诊断轨迹因中间层处理改变，会增加定位难度，这是原问题真正关心的事。

实际第四版物理425/印刷408在throwe/throw比较后讨论Windows错误报告的位置，并紧接trySucceeds/finally另一种写法。这里是原书的**历史Windows/CLR诊断说明**，不能把它扩大成所有平台、所有现代WER转储的固定规则，也不能说第四版属于.NET2.0时代或当时还没有EDI。

Windows SEH可以传播并被处理，异常事件不等于“程序已崩溃”。EXCEPTION_RECORD、线程CONTEXT、托管异常的StackTrace、Watson诊断和转储读取方式又是不同层次。原回答用“Windows只看当前IP”“CLR偷偷给WER一份永不变的快照”“每个C#throw都用同一native API把异常地址设成C#源码行”“查询时覆盖Windows记录”解释，未提供这种一套固定协议的依据，不能作为准确实现模型。

微软.NET4.5时期的官方说明明确谈到throwe会更新异常轨迹和相关Watson信息，EDI则保存并恢复异常的调度信息，后来抛出的当前调用信息可以追加到已有信息。**保存诊断不是逆转物理栈展开，也不是保证每份WER报告第一帧必定是B。** 本章没有真实WER/dump实验，不把托管轨迹的本机输出冒充该保证。[.NET4.5异常诊断与EDI](https://devblogs.microsoft.com/dotnet/task-exception-handling-in-net-4-5/)

原“交警—保险公司—车祸监控”类比的用途，是区别报告时所在位置与保存的第一现场记录。可以把Windows/采集工具比作现场记录者、CLR保存的异常轨迹比作事故资料，但不能把这个类比说成CLR真的删除或覆盖一份专供调试器的监控、欺骗Windows的内部协议。“凶案现场变成中间层”“调试与部署现场信息断层”也只是诊断用途类比，不证明一定永远找不到B。

原三行五维throw对照保留这些不同输入和观察维度：

| 行为 | Windows原生上下文 | 托管已有轨迹 | 调试器当前栈 | WER/转储所见 |
| --- | --- | --- | --- | --- |
| throw new Ex() | 产生异常的运行时/平台路径，不能只用C#语法确定全部字段 | 新对象通常没有此前的异常轨迹，开始记录此次失败 | 取决于暂停时刻和优化 | 按实际采集/诊断合同判断 |
| throw; | 不从托管保栈合同推原生记录的每个字段不变 | 重新抛出当前异常，保留相应已有轨迹 | A重抛时不会凭空恢复已退出的B帧 | 保存的异常诊断可以仍有B，不保证固定转储列表 |
| throw ex; | 同样不能简化成所有Windows上的单一源码地址规则 | 普通场景以当前点更新该对象的抛出轨迹 | 原B首次暂停与A后来暂停是不同阶段 | 原信息若未另外保存，诊断可能丢失；不能说所有dump必无任何B痕迹 |

<a id="c20-null-rethrow"></a>
### A重抛、B读null字符串的原场景

原B中的`s.Length;`是非法表达式语句，编译会先报CS0201，并不会成为可运行的NullReferenceException程序。以下仅将它改为合法读取，保留A/B和null输入：

```csharp
void A()
{
    try
    {
        B(); // B 里抛出了 NullReferenceException
    }
    catch (Exception ex)
    {
        // 糟糕！这里写了 throw ex;
        throw ex; // 更新此对象的托管抛出轨迹，不用本片段保证所有WER记录
    }
}

void B()
{
    string s = null;
    int length = s.Length; // 修正原s.Length;非法语句；仍读取null字符串
}
```

在外围受控catch中，本机两环境确实观察到NullReferenceException和A/入口的更新后轨迹；该例的B可能受优化影响，不能据此讲“所有Debugger/WER都会出现固定两行”。没有执行未处理崩溃。

<a id="c20-edi-pattern"></a>
### EDI的公开调度合同与私有反射例

原EDI片段需要System.Runtime.ExceptionServices：

```csharp
catch (Exception ex)
{
    // 捕获此异常已有的调度状态（轨迹/相关诊断信息）
    var edi = ExceptionDispatchInfo.Capture(ex);
    
    // 做一些清理工作...
    
    // 重新抛出，但保留原始上下文
    edi.Throw(); // 使用公开EDI调度合同；不是原答声称的私有方法调用
}
```

EDI在Framework4.5已有。Capture保存这个异常在捕获时已有的调度状态，Throw恢复并抛出，让旧异常信息继续可诊断；它不是对Windows发一个“不要更新任何native异常记录”的指令。捕获从未抛出过的对象也没有旧的异常轨迹可保存。

原另一个例子用反射调用内部方法，需要System.Reflection：

```csharp
catch (Exception ex)
{
    // 原聊天的私有反射做法；本机可保存已有托管轨迹，不是阻止Windows原生事件
    typeof(Exception).GetMethod("InternalPreserveStackTrace", 
        BindingFlags.NonPublic | BindingFlags.Instance)
        .Invoke(ex, null);
    throw ex; // 本机结果可含保存的旧轨迹与新增抛出片段，不冻结当前物理栈
}
```

这是**聊天提供的私有实现做法**，不是本地原书408紧接文字的那个flag例。Framework源码的InternalPreserveStackTrace把已有文字存进远程轨迹字符串并清除相应当前字段；EDI恢复调度状态有自己的路径，不能说EDI就是调用此私有方法。[Framework两路径源码](https://raw.githubusercontent.com/microsoft/referencesource/main/mscorlib/system/exception.cs)

本机两环境内部方法都存在，原思路的受控反射与EDI都能让输出包含保存的Origin轨迹和新增Transit片段；此为特定实现观察。内部名字、可访问性和行为不是可依赖的公共API合同，也不意味着反射把物理栈或WER上下文“冻结”。

## trySucceeds与部分完成的收尾

<a id="c20-completion-flag"></a>

原思考还建议名为isTryCompleted，也认可trySucceeds。名字可强调“是否到达本次调用的完成点”，但名称本身不改变控制流，更不能把false一律当作只发生了异常；过早return同样可以没有到达最后赋true的位置。

用户贴的书例本身是省略体示意，完整形状应连起来看：

```csharp
private void SomeMethod()
{
    Boolean trySucceeds = false;
    try
    {
        ... // 示意操作，不是可直接编译的省略号
        trySucceeds = true;
    }
    finally
    {
        if (!trySucceeds) { /* 捕捉代码放到这里：实际是失败路径的收尾 */ }
    }
}
```

只要成功标记还未执行而控制离开try，就执行相应false分支。常规抛出会导致这一情形，**提前return也可以导致false**；false不能作为“必有异常对象”的无条件判断。finally中没有隐式提供ex变量，它执行的是收尾/补偿逻辑，而不是语言上的catch。

原T的提前return反例，省略号仍为伪代码：

```csharp
try
{
    ...
    return;
    trySucceeds = true; // 不可达；finally执行时仍为false
}
```

标记应在预定的“操作已完成”点赋值，在需要成功返回之前；如果内部已经捕获并修复过一个异常，也可能继续完成并设true。局部变量是每次调用独立状态的简单方案，字段/静态字段需相应隔离、重入和同步设计，不能说语言禁止使用任何字段标记。

<a id="c20-cooking"></a>
### 厨房便利贴的完整原例

```csharp
private void CookDinner() {
    bool mealFinished = false; // 冰箱上贴的便利贴：默认饭没做完

    try {
        // 做饭步骤：洗菜→切菜→炒菜→盛盘
        WashVegetables();
        CutVegetables();
        StirFry();
        ServeOnPlate();
        
        mealFinished = true; // 所有步骤做完，把便利贴改成"饭做好了"
    }
    finally {
        // 不管饭有没有做完，都要打扫厨房
        CleanKitchen();
        
        if (!mealFinished) { 
            // 便利贴还是false：饭没做完，做补救
            PutOutFire(); // 比如炒糊了要灭火
            ThrowAwayRawFood(); // 扔掉没处理的食材
            CallForHelp(); // 喊人来修
        }
    }
}
```

洗菜→切菜→炒菜→盛盘都完成后，便利贴变true；中途离开时仍false。T另举炒到一半油锅出事、没法盛盘或修改标记的情境。这是状态与步骤类比，没有真的调用厨房操作；CleanKitchen或任何补救本身如果失败，后续步骤不会自动全部完成。finally也不在FailFast等终止路径下获得无限保证。

<a id="c20-tempfile-original"></a>
### temp.txt原先删除、后关闭的反例

下面完整保留原FileStream两参数构造、GetLargeData、Write、Flush与flag输入，**作为存在清理顺序错误的教学反例**：

```csharp
private void WriteTempFile() {
    bool trySucceeds = false;
    FileStream fs = null;

    try {
        fs = new FileStream("temp.txt", FileMode.Create);
        byte[] data = GetLargeData(); // 可能抛 OutOfMemoryException
        fs.Write(data, 0, data.Length); // 可能抛 IOException
        fs.Flush(); // 可能抛 IOException
        
        trySucceeds = true; // 所有写操作都完成，才标记为成功
    }
    finally {
        if (!trySucceeds) {
            // try 被异常中断：文件没写完，删除半成品
            File.Delete("temp.txt");
        }
        fs?.Dispose(); // 不管成功失败，都要释放资源
    }
}
```

原想说明成功时true/保文件，失败时false/删半成品。但两参FileStream默认没有允许共享删除；仍开着时先File.Delete，在本机Windows可以产生真实sharing violation。删除失败后，finally后面的Dispose也不会执行，原异常被新IOException替代向外传播。

独立受控实测用自己新建的文件，让GetLargeData只抛一个普通InvalidOperationException，没有耗尽内存；两环境原序均得到IOException/HResult80070020、DisposeReached=False、流仍开、文件仍在。外部探针随后关闭并清理了自己的文件。只改变顺序为先Dispose后Delete，原受控异常身份保留，流已关、文件已删。[原清理顺序实测](整理记录/核验与验收/共享-第20临时文件清理核验.md)

<a id="c20-tempfile-corrected"></a>
### 纠正本场景的顺序，不把清理成功普遍化

下面修正原场景，仍须事先保证temp.txt是此次调用独占拥有的临时文件，而不是别人的既有数据；它是展示顺序的片段，不是任意失败都完全可靠的文件事务：

```csharp
private void WriteTempFile()
{
    bool trySucceeds = false;
    bool created = false;
    FileStream fs = null;
    try
    {
        fs = new FileStream("temp.txt", FileMode.Create);
        created = true;
        byte[] data = GetLargeData();
        fs.Write(data, 0, data.Length);
        fs.Flush();
        trySucceeds = true;
    }
    finally
    {
        if (fs != null) fs.Dispose(); // 先关闭，避免本次打开句柄阻止删除
        if (created && !trySucceeds) File.Delete("temp.txt");
    }
}
```

Dispose/Delete仍会因其他具体I/O条件失败；若Dispose失败，上例的后续Delete不会执行，若Delete失败也会替换尚在传播的原异常。需要保留两个失败信息或保证更强的文件提交语义时，应另外设计清理与诊断策略，不能一律吞掉全部清理错误。构造失败后的部分资源状态也要按实际API合同处理，created标记只证明本代码已经成功取得该流。

原T还用“写100行、第50行抛IOException”的不同数据场景说明半成品；false只指出未到完成点，不自动知道写到哪行或哪些外部效果已提交。删临时文件、退款、重置对象字段都是不同的补偿措施，适用条件各有自己的合同。

<a id="c20-catch-versus-flag"></a>
### catch重新抛出与flag自然传播

原catch比较片段同样包含先Delete后Dispose问题；省略号表明它是形状，不是完整程序：

```csharp
try { ... }
catch (IOException ex) {
    File.Delete("temp.txt");
    throw; // 必须手动重新抛出，否则上层不知道异常
}
finally {
    fs?.Dispose();
}
```

catch不写throw会结束该处理的普通传播；写throw可以继续并保存相应异常轨迹。多个异常类型有同一个处理策略时可用适当共同基类/过滤器，并不必然每个类型都写一份处理器。flag/finally避免在本层接住再抛这一额外步骤，但清理仍可能失败，所以不能称为“完全不干扰异常、覆盖所有异常没有任何风险”。

原成功标记过早的反例：

```csharp
try {
    trySucceeds = true; // ❌ 错误：放在了可能抛异常的代码前面
    fs.Write(...); // 这里抛异常，但 flag 已经是 true 了
}
finally {
    if (!trySucceeds) { ... } // 永远不会执行，半成品文件不会被删除
}
```

其中fs.Write后续失败而标记已经true，false分支不执行。把标记放在正确提交点是程序逻辑条件；CER不会替程序自动判断这个逻辑是否正确，也不是让任意flag和finally代码不再失败的“升级”。

**补充受控观察：** 本机两环境的flag正常完成为True；中途抛出为False并自然继续原异常；提前return也为False但外围正常返回。相同原异常的自然传播有一次对应FirstChance通知，catch/rethrow有两次；这些数量只属于此受控环境，不是原生Windows地址合同。[完成标记及传播实证](整理记录/验证工作区/第20章/完成标记与传播/结果.json)

<a id="c20-flow-patterns"></a>
### Rollback与三种不同的传播模式

原支付情境说，客户失败日志只显示中间A，真正空引用在B：中间层又负责释放/回滚，重抛轨迹会妨碍查原失败。这仍是假定的支付诊断情境，没有实际客户转储或支付调用。

原RollBack后带表达式抛的A：

```csharp
void A() {
    try {
        B(); // 真实bug在这里
    }
    catch (Exception ex) {
        // 做恢复操作，比如回滚未完成的转账
        Rollback();
        throw ex; // 带表达式throw更新托管轨迹；本片段不保证所有dump内容
    }
}
```

原先存originalEx、再在finally中Rollback并用EDI抛出的A：

```csharp
void A() {
    bool trySucceeded = false;
    Exception originalEx = null; // 捕获并保存原异常引用
    try {
        B(); // 真实bug在这里
        trySucceeded = true; // 只有B完全执行完，才标记成功
    }
    catch (Exception ex) {
        originalEx = ex; // 这里先保存；稍后必须显式传播或向调用方报告失败
        // 本catch退出时暂停普通传播，不是此刻已自然向外抛
    }
    finally {
        if (!trySucceeded) {
            // 做恢复操作，比如回滚转账
            Rollback();
        }
        // 如果真有异常，需要向外抛的话，用不会破坏栈的方式
        if (originalEx != null) {
            // Framework4.5起的公开EDI合同：保留已有异常轨迹
            System.Runtime.ExceptionServices.ExceptionDispatchInfo.Capture(originalEx).Throw();
            // 另一个不同方案是完全不catch，只用try/finally；并非本代码已经如此
        }
    }
}
```

它先捕获而停止普通传播，再显式用EDI再次抛出，不能说“这里完全没有重新抛出”。Rollback若再失败，也可能让后面的EDI根本没有执行，保原异常仍需要清理策略。

另一个原A不使用catch：

```csharp
void A() {
    bool trySucceeded = false;
    try {
        B(); // 异常直接抛给上层，不经过任何catch的throw
        trySucceeded = true;
    }
    finally {
        if (!trySucceeded) { Rollback(); }
    }
}
```

这才是“操作抛出后，不在本层接住再抛，收尾结束后继续传播”的模式。若Rollback成功，已有异常继续；若它抛出新异常，旧传播可能被替代。不能单凭flag断言恢复本身总正确或转储必然完整准确。

<a id="c20-deferred-anti"></a>
### 思考区保存异常却不传播的不同尝试

原T-B013围栏还混入大量方法之后的解释，不能把整个容器当作可编译C#。其中真正的方法尝试有如下不同状态，保留为**吞传播的反例**：

```csharp
void A()
{
    bool trySucceeded = false;
    Exception originalEx = null;
    try
    {
        B();
        trySucceeded = true;
    }
    catch (Exception ex)
    {
        originalEx = ex; // 仅保存局部引用，没有继续抛出
    }
    finally
    {
        if (!trySucceeded)
        {
            // 原尝试只有恢复逻辑的说明，没有真正的后续throw
        }
    }
    // 若没有随后报告失败/抛出，方法会正常返回；局部存引用不等于传播
}
```

T另有更短的`void A(){try{B();}catch(Exception ex){throw ex;}}`比较，没有Rollback；它与上面带回滚的A用途不同：单独说明中间捕获后重抛的轨迹更新。若把保存对象留待catch之外抛出，裸`throw;`不在catch上下文中可用，应选明确返回失败/保留调度后抛出等合同；不能只把局部originalEx存起来就声称自然向外传播。

原四行对照表保留诊断与客户反馈的不同用途，去掉“任意dump永远找不到/一定正确”的断言：

| 场景 | 普通throwex路径 | flag/finally、rethrow或EDI的适用路径 |
| --- | --- | --- |
| 调试器里的栈 | 在原B首次暂停或A后来重抛暂停，当前栈不同 | 同样按暂停时刻判断；保栈不复活退出帧 |
| 部署现场诊断 | 普通异常对象轨迹可能只剩中间层，未另存旧信息时难定位 | 自然传播/保留调度可以保已有信息，转储显示仍有采集条件 |
| 排查难度 | 中间层轨迹缺原现场时要找额外诊断，不能说永远无法发现B | 保存异常诊断通常更有助于回查B，不保证仅凭一条轨迹定位全部问题 |
| 原客户反馈情境 | “程序总崩，但日志啥也没记”是原假设的症状描述 | “B方法里有个空引用”是原例期待查明的结果，没有真实客户实测 |

## 两种StackTrace输入与优化、符号

<a id="c20-stack-construction"></a>

原关键疑问是：异常已经被处理器接住，怎么查看更外面的调用者？不要只靠“高/低”猜栈方向；更稳妥地说，异常轨迹通常描述此前抛出并传播到当前处理位置的相关路径，当前线程栈描述此刻还活动的调用关系。

原Main/A/B/C简图保留为常见Windows/x64物理堆栈的教学类比，不作为C#跨平台地址布局保证：

```text
[Main]        <- 栈底 (Base)  <- 地址高 (高)
[A]
[B]
[C]           <- 栈顶 (Top)   <- 地址低 (低)
```

调用可以让更深层方法变成当前栈顶，返回使它退出。译注的逻辑“升高/降低”与图中物理高低地址不是一个必然统一的命名；应直接用“更深调用/更外调用者”。优化、内联等也使“每个源码方法都压一份独立StackFrame”不是无条件保证。

<a id="c20-main-catch-original"></a>
### Main捕到Boom!的完整原程序

```csharp
using System;

class Program
{
    static void Main() // ① 本例处理器所在的方法
    {
        try
        {
            A();
        }
        catch (Exception ex)
        {
            // ③ 在这里捕获异常
            Console.WriteLine("=== Exception.StackTrace ===");
            Console.WriteLine(ex.StackTrace);
        }
    }

    static void A() // ② 调用B的方法；未禁止内联
    {
        B();
    }

    static void B() // ③ 抛出点所在的方法
    {
        throw new InvalidOperationException("Boom!");
    }
}
```

原输出只列B/A而据此说“Main不见了”，这个结论错了。捕获所在方法可以在异常轨迹里：本机原程序Framework显示B/Main，现代.NET10显示B/A/Main；未禁止优化时A是否展示已有差异。补充明确NoInlining后，两环境都显示B/A/Main。没有用原源不存在的NoInlining替换掉原普通程序。

<a id="c20-current-stack-original"></a>
### 同一个catch里再new StackTrace

原追加片段：

```csharp
catch (Exception ex)
{
    Console.WriteLine("=== Exception.StackTrace ===");
    Console.WriteLine(ex.StackTrace);

    Console.WriteLine("\n=== Diagnostics.StackTrace ===");
    // 获取此刻当前栈；此前B/A已退出，不会被这个构造器复活
    var st = new System.Diagnostics.StackTrace();
    Console.WriteLine(st.ToString());
}
```

原第二组输出把当前栈写成Main/A/B，与真实状态不符：为了到Main的catch，原A/B已经展开退出。两环境这个原追加场景的当前栈都只显示Program.Main；前一组异常轨迹仍可能记得B/A/Main。当前栈并不是把异常的旧轨迹倒过来重新排一遍。

原两个构造器片段分别保留：

```csharp
// 这种方式生成的栈，和 ex.StackTrace 类似，但你可以编程访问每个栈帧
var st_from_exception = new System.Diagnostics.StackTrace(ex);

// 这种方式生成当前位置可取得的当前栈，受优化/展示边界影响
var st_current = new System.Diagnostics.StackTrace();
```

以Exception为参数得到该异常已保存轨迹的可编程栈帧视图；无参数得到当前位置的当前视图。它们都可用StackTrace/StackFrame的API分析，而不是保证同时恢复所有早已退出的帧或所有native内部调用。方法调用及符号位置通常与返回位置/相应序列点有关，不能把所有调用者的显示行解释成“抛出/进入catch那一行”。

<a id="c20-inlining"></a>
### 小方法的内联示意与NoInlining原方法

原还给出“源码写过C()，日志里却只看见B()”的诊断情境：内联可能解释部分方法未单独呈现，但需结合该次活跃路径、优化和呈现条件判断，不能凭两名字就确认唯一原因。它与上面的A/B内联代码是不同原表达，未补造原未给的C/B整程序。

原内联形状：

```csharp
static void A()
{
    B(); // JIT 可能会把 B 的代码直接搬到这里
}

static void B()
{
    throw new Exception(); // 如果内联了，这里抛出的异常，栈上可能只有 A
}
```

若一个方法真的被JIT内联，就没有普通独立调用帧；“复制粘贴”是机器码整合的类比，不是把源文件或IL简单复制后的逐字保证。不能仅凭本章某次少了一帧就证明所有JIT优化因果，本章没有该程序的JIT反汇编。

用户原省略体SomeType形状是：

```csharp
using System;
using System.Runtime.CompilerServices;
internal sealed class SomeType
{
    [MethodImpl(MethodImplOptions.NoInlining)]
    public void SomeMethod()
    {
        ... // 用户引文中的示意体，不是完整可编译程序
    }
}
```

正式答另给真实抛出`I'm here!`的SomeType：

```csharp
using System;
using System.Runtime.CompilerServices;

internal sealed class SomeType 
{
    [MethodImpl(MethodImplOptions.NoInlining)]
    public void SomeMethod() 
    {
        // 这个方法永远不会被 JIT 内联
        // 非常适合放在容易出错的复杂逻辑上
        throw new Exception("I'm here!");
    }
}
```

NoInlining的合同就是禁止这个方法被内联，适用于相应生成方式；这是正确的原规则，不要把它因为邻段错误而标成错误。要显示某帧还须看该帧是否在所取的栈中及其他展示条件，NoInlining不单独保证所有源码方法/行号都完整可见。本机两环境该SomeMethod有NoInlining实现标志，调用捕获的轨迹含SomeMethod和调用者。[NoInlining API合同](https://learn.microsoft.com/en-us/dotnet/api/system.runtime.compilerservices.methodimploptions?view=netframework-4.8.1)

<a id="c20-debug-options"></a>
### /debug、优化和PDB各控制什么

原命令形状：

```bash
csc /debug YourCode.cs
```

`/debug`产生相应调试信息，`/optimize`是另一项控制；可以一起指定。Framework早期编译器选项、默认未优化状态和当时的Debuggable标志应按实际组合理解，不能说任何版本只要有PDB就必关闭内联。

原`[Debuggable(DisableOptimizations = true)]`不是合法C#特性声明，本机真实CS0117；合法枚举形状例如以下**补充语法说明**：

```csharp
using System.Diagnostics;
[assembly: Debuggable(DebuggableAttribute.DebuggingModes.DisableOptimizations)]
```

本机两个编译器显式debug+optimize-组合的IsJITOptimizerDisabled为True；debug+optimize+组合为False，后者仍取得了此受控PDB样例的文件行号。Debuggable与NoInlining是不同层次的控制，原“NoInlining精准阻止一个方法、全局优化设置影响范围更广”的用途保留。[编译器DebugType/Optimize文档](https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/compiler-options/code-generation)

<a id="c20-pdb"></a>
### PDB是源位置映射，Release也可以有

原行号示意`Program.B() in C:\MyProject\Program.cs:line25`解释匹配符号如何帮助定位，它不是保证所有构建都产生这条路径或25行。PDB包含相应序列点与源位置等信息；没有可用符号或某位置没有映射时，通常只有方法层次或有限位置。可用的符号格式、匹配版本与运行时支持也影响结果。

现代C#项目的Debug/Release默认都可生成portable PDB；Release优化开启与有没有PDB不是一回事。也能把portable PDB嵌入程序集，不能把“Release默认没有源信息”“exe/dll绝对只含IL和元数据、符号永远外部文件”当普遍规则。保存对应构建的符号有助于部署现场诊断，不保证单凭它恢复已经丢弃的原异常轨迹。

原“破案”“调试救星”“行号钥匙”类比强调这些工具的用途；原所谓排查困难“指数级上升”没有本章量化证据。CER仍是后文的历史可靠性机制，不是保证所有JIT失败、OOM、恢复代码和栈信息都永不失败的终极开关。

## 自定义异常的泛型壳与传统序列化

<a id="c20-generic-exception"></a>

用户问为什么要定义一个泛型异常。原思想是把重复的构造/传统序列化代码集中在一个固定壳中，把每种失败的数据放进参数对象，而不是为每个异常类型重复写同一组成员。这是减少重复实现的设计选择，不是C#规定所有项目都必须使用的异常模型。

原“壳+参数”图保留FileNotFoundArgs.Path和InvalidUserArgs.UserName两个不同数据用途：

```text
┌─────────────────────────────┐
│  固定壳（只写一次，永不复制）  │
│  Exception<TExceptionArgs>   │  ← 负责 Serializable/四个ctor/ISerializable
│  where T : ExceptionArgs     │
├─────────────────────────────┤
│  可变参数（每个场景一个）      │
│  TExceptionArgs              │  ← 比如 FileNotFoundArgs { string Path; }
│  （就一两个字段 + Message）    │     InvalidUserArgs { string UserName; }
└─────────────────────────────┘
```

原泛型骨架如下，需要System及System.Runtime.Serialization命名空间。无泛型参数的基类名Exception在该上下文指System.Exception；泛型Exception<TExceptionArgs>是自定义类型：

```csharp
[Serializable]
public sealed class Exception<TExceptionArgs> : Exception, ISerializable
    where TExceptionArgs : ExceptionArgs
{
    private readonly TExceptionArgs m_args;
    public TExceptionArgs Args => m_args;

    // 固定构造/传统序列化逻辑可集中在壳内；此骨架只给出一个构造
    public Exception(TExceptionArgs args, string message = null, Exception inner = null)
        : base(message, inner) { m_args = args; }
    // ... 序列化ctor / GetObjectData 也只写一次
}
```

配套ExceptionArgs：

```csharp
[Serializable]
public abstract class ExceptionArgs
{
    public virtual string Message => string.Empty;
}
```

原FileNotFoundArgs类型、C:\foo.txt输入和“配置文件丢失”调用：

```csharp
[Serializable]
public sealed class FileNotFoundArgs : ExceptionArgs
{
    public string Path { get; }
    public FileNotFoundArgs(string path) => Path = path;
    public override string Message => $"File not found: {Path}";
}

// 用的时候：
throw new Exception<FileNotFoundArgs>(
    new FileNotFoundArgs(@"C:\foo.txt"),
    "配置文件丢失");
```

这只是骨架，注释略掉了传统序列化实现，并非完整往返程序。Args表达体/get-only属性/插值使用C#6语法，FileNotFoundArgs表达体构造使用C#7语法；这些现代写法可以由新编译器生成Framework可运行代码，不能冒称第四版时代自带编译器可直接接受全部语法。

**补充原书对应：** 本地20.6完整泛型壳明列两个公共构造和一个密封类私有反序列化构造，并保存Args、重写Message，在有Args时拼接base.Message与args.Message；其DiskFullExceptionArgs/DiskPath书例与聊天FileNotFoundArgs/配置文件丢失骨架是不同材料。这里保留聊天实际给出的一个构造及未合成Message的算法，不用它冒原书完整壳；原書集中重复实现的主旨与具体成员分别说明。

原骨架也没有重写外层异常Message去合并args.Message：读取异常Message得到构造中传给base的“配置文件丢失”，读取Args.Message才是`File not found: C:\foo.txt`。参数类提供Message不表示泛型壳会自动调用它。

<a id="c20-generic-tradeoffs"></a>
### 闭合类型仍不同，Args是否sealed是设计选择

传统例子是分别定义FileNotFoundException、InvalidUserException并重复普通/序列化成员；泛型例子是Exception<FileNotFoundArgs>与Exception<InvalidUserArgs>共享源码壳。后一方案仍有两个**不同的闭合类型**，不是把运行时所有错误压成同一个类型。可以分别写两个typed catch处理它们；Generic class没有因此变成协变，Exception<ExceptionArgs>也不自动匹配Exception<FileNotFoundArgs>。

T中提到FileNotFound/InvalidUser等不同失败类别，用泛型参数作类型标签与带数据的身份并不是“catch不能按T分派”。readonly字段/get-only属性也不自动保证任意Args对象图不可变；具体参数类可以设计为不可变。`where TExceptionArgs:ExceptionArgs`没有sealed或“只能一两个简单字段”的约束，非sealed参数类照样可以合法使用。

原书时代某些未处理异常对话框对泛型类型参数显示有限，是特定工具/版本的显示问题；不能推成现代VS或所有日志工具都无法查看Args字段。只记录GetType().Name也可能只得到泛型定义名，完整类型身份/参数对象可用相应API读取。相对独立名称还是泛型参数身份是否更直观，是原工程权衡，不是语言功能缺失。少量自定义异常采用普通独立类同样清楚。

<a id="c20-generic-serialization"></a>
### 补充固定壳的序列化成员

为了说明原略号里要负责什么，下列是加入上述sealed泛型壳的**补充成员**，不声称原聊天已提供它们，也不替代原FileNotFoundArgs场景：

```csharp
private Exception(SerializationInfo info, StreamingContext context)
    : base(info, context)
{
    m_args = (TExceptionArgs)info.GetValue("Args", typeof(TExceptionArgs));
}

public override void GetObjectData(SerializationInfo info, StreamingContext context)
{
    base.GetObjectData(info, context);
    info.AddValue("Args", m_args, typeof(TExceptionArgs));
}
```

sealed类可以采用private的序列化构造；可继承类型通常采用protected以供派生配合。可序列化标记、每项对象图的合同仍要满足，壳不会替任意T、任意Data值和版本变化自动担保。

受控Framework验证以C#7.3编译器运行原Cfoo/配置消息和补充壳成员：Args.Path与Message在内存往返中保留；非sealed InvalidUserArgs合法，两个closed typed catch各自执行，基类参数实例化无类协变。没有做真实AppDomain/远程传输。[泛型及序列化实际证据](整理记录/验证工作区/第20章/序列化合同/结果.json)

<a id="c20-exception-serialization"></a>
### Exception基类已经处理基础状态，派生业务状态仍有合同

问题“为什么基类不实现序列化”先要纠正前提：历史Framework的Exception自己已有Serializable标记、ISerializable接口、GetObjectData及相应序列化构造；派生类也继承其接口实现，不必为了继承这个行为再声明一次同一接口。

原OrderProcessingException类型片段：

```csharp
[Serializable]
public class OrderProcessingException : Exception
{
    public int OrderId { get; }  // ← 你加的新字段
    
    // 基类不自动列此业务字段；本片段也没有给出序列化构造，实际可能先反序列化失败
}
```

Exception选择显式记录自身状态，默认GetObjectData不会自动把这个新OrderId加进去。原给出的内部字段示意是**伪代码**：

```csharp
// Exception 自己的 GetObjectData
info.AddValue("Message", this._message);
info.AddValue("InnerException", this._innerException);
info.AddValue("StackTrace", this._stackTrace);
info.AddValue("HResult", this._hresult);
// ……它只知道这几个基类字段的名字
```

它只表达显式列出基础信息的思路，不是可粘进派生类访问基类private字段的代码，也不是实际序列化键名/二进制栈布局。真实实现包含Message、Data、InnerException、HelpURL、StackTraceString等约定状态，具体版本的键与恢复逻辑应按对应源码理解。

原派生类新增保存/恢复成员：

```csharp
protected OrderProcessingException(SerializationInfo info, StreamingContext context)
    : base(info, context)
{
    OrderId = info.GetInt32("OrderId");  // ← 派生类自己还原
}

public override void GetObjectData(SerializationInfo info, StreamingContext context)
{
    base.GetObjectData(info, context);
    info.AddValue("OrderId", OrderId);   // ← 派生类自己塞
}
```

原OrderId示意先只给只读属性，没有业务构造或序列化构造。如果缺后者，反序列化可以首先报SerializationException，而不是只是“默默丢OrderId”。有构造却不写/读新字段时，值可能回到默认值；完整合同才能保留业务值。受控补充把OrderId设42，实际三种情形分别是缺构造失败、只调base恢复为0、自己保存/恢复为42；补充普通构造不是原片段已经给出的成员。

OrderId、UserId、FileName的业务意义和版本策略不同，基类既没有选择它们的稳定外部表示，也没有为它们约定所有恢复规则。其他类当然可以选择反射或不同的显式合同；不能断言基类技术上“无法反射”，或者“唯一解决方法一定是反射”，也不能把未证实的性能/稳定性或2002年历史动机说成已知事实。

<a id="c20-serializable-marker"></a>
### Serializable与属性继承、对象图

Serializable不是泛型接口约束，C#不能写`where T:[Serializable]`。它自己的AttributeUsage指定Inherited=false，派生Exception类没有自动获得它；其他特性是否在相应查询/使用中继承，按自己的AttributeUsage判断，**不是所有C# attribute都不继承**。[Serializable标记定义](https://learn.microsoft.com/en-us/dotnet/api/system.serializableattribute?view=netframework-4.8.1)

类型标了Serializable也不证明所有可达对象都可以用该formatter保存。还要看被选取的字段、对象图中其他类型、自定义GetObjectData和版本合同。原Data“放任何object到序列化才失败”的话需分环境：本机Framework普通Exception.Data插入非Serializable Plain值当场抛ArgumentException；现代.NET10同值可插入。因此不能只按最终formatter阶段推定失败时机；也不能据一个标记把所有输入和序列化方式都说成安全。

四个常见普通/序列化构造是原历史设计建议，不是C#编译器强制每个异常子类必须带全。没有相应传统传输需求时，更不必因为“可能写日志/落数据库”就自动采用BinaryFormatter合同。

<a id="c20-serializer-contracts"></a>
### Person字段、ISerializable手册与ErrorTime片段

原“通行证/入场券”类比指相关传统formatter识别一个参加者，“操作手册/装箱拆箱”类比指自定义数据写入/恢复合同。应给类比加上具体serializer条件，而不是让CLR在任何场合看到这个标记就自动序列化。

原Person的Name/Age公有字段：

```csharp
[Serializable]
public class Person
{
    public string Name;
    public int Age;
}
```

传统默认字段模式通常会处理相应公有、私有实例字段，也尊重NonSerialized等规则。不是标记保证“内部绝没有不可序列化东西”。如果Age改名为CurrentAge，默认持久化名称可能需要版本策略；可用自定义稳定键、OptionalField、回调等相应机制处理，不能说自动模式完全无法管理版本。Password不想存原值的原讨论可以使用排除、单独数据表示或自定义合同；是否需要哈希及其用途是另一项设计，不能只靠这个序列化标记决定。

原接口教学形状：

```csharp
public interface ISerializable
{
    // 序列化：把对象的数据装进箱子（SerializationInfo）
    void GetObjectData(SerializationInfo info, StreamingContext context);
    
    // 反序列化构造约定：用来从箱子里取出数据（不是第二个接口成员）
    // 注意：这不是接口的方法，而是实现 ISerializable 必须遵循的约定
    // .ctor(SerializationInfo info, StreamingContext context)
}
```

ISerializable真正定义的是GetObjectData一个方法；SerializationInfo/StreamingContext构造是配套反序列化约定，注释不使它变成第二个接口成员。default字段模式和该接口路径由formatter选择，并非ISerializable接管所有系统、所有对象图的全部行为。

原MyException新增ErrorTime的片段：

```csharp
[Serializable]
public class MyException : Exception
{
    // 这是基类没有的新字段
    private readonly DateTime _errorTime; 

    // 1. 序列化方法：把 _errorTime 塞进去
    public override void GetObjectData(SerializationInfo info, StreamingContext context)
    {
        base.GetObjectData(info, context); // 调用父类，让它把自己的字段（Message等）塞进去
        info.AddValue("ErrorTime", _errorTime); // 把自己的私有字段塞进去
    }

    // 2. 反序列化构造函数：把 _errorTime 取出来
    protected MyException(SerializationInfo info, StreamingContext context) 
        : base(info, context) // 调用父类构造函数，让它还原自己的字段
    {
        _errorTime = info.GetDateTime("ErrorTime"); // 还原自己的私有字段
    }
}
```

它示范派生类自己加“ErrorTime”并在自己的构造中给readonly字段赋值；base构造还原基础状态，不是base替它给_errorTime赋值。原只提供了protected序列化构造，没有普通创建构造，应按片段读，不能直接假定`new MyException()`可用。

私有readonly也可以在默认字段序列化/恢复中参与，不是“只有实现ISerializable才能恢复”。本机补充Person的private readonly secret=7往返保留，[NonSerialized]的Transient变null。自定义写入v1_ErrorTime/v2_ExtraInfo和检查缺键可以用于某种版本合同，但单凭键前缀不能“完美兼容任意旧数据”。

原另一个泛型声明形状保留为略号片段：

```csharp
[Serializable]
public sealed class Exception<TExceptionArgs> : Exception, ISerializable
{
    // ...
}
```

源这段没有展示泛型字段或保存/恢复逻辑，实际工作仍由具体壳的相应成员实现；单独写了接口名不自动补出丢掉的业务数据。

保留原五维关系表，并限定传统formatter场景：

| 特性 | Serializable | ISerializable |
| --- | --- | --- |
| 角色 | 类型的相关可序列化标记 | GetObjectData接口及配套恢复约定 |
| 作用 | 让按该规则工作的formatter识别类型 | 选择自定义的显式数据表示 |
| 控制权 | 具体formatter可按默认字段模式等规则处理 | 支持该合同的formatter调用实现，图中其他对象仍有自己的合同 |
| 适用场景 | 简单字段对象，也可配合排除、版本/回调等功能 | 需要明确基础与业务字段、稳定表示等合同的类型 |
| 关系 | 传统formatter中的必要条件之一，不是所有JSON/XML序列化的通用门票 | 相关自定义路径还需标记/构造等条件，不能说只写接口就全部自动正确 |

<a id="c20-modern-serialization"></a>
### BinaryFormatter、JSON、XML不是同一套规则

SerializableAttribute本身现代.NET仍存在且未标Obsolete；被弃用/移除的是某些旧formatter及其支持API。现代.NET9起内建BinaryFormatter实现被移除，相关API仍可能以抛错实现保留；不能说该类及所有Serializable标记/接口都同时消失。.NET8起Exception旧序列化支持成员有相应弃用提示，Framework历史代码与现代限制分开。[官方迁移说明](https://learn.microsoft.com/en-us/dotnet/standard/serialization/binaryformatter-migration-guide/)

原三场景表按实际平台收窄：

| 原场景 | 应采用的合同 |
| --- | --- |
| Framework历史AppDomain/Remoting中需要按值传异常 | 对应formatter的类型及状态合同；Exception的ISerializable实现是继承来的，不能说必须再次声明同一接口 |
| System.Text.Json/XmlSerializer日志 | 不自动照搬Exception的传统ISerializable路线；分别看字段/属性/构造/转换器等支持，不等于任意Exception可直接自动往返 |
| 旧远程payload/格式兼容 | 是否需要读取旧数据与当前写入格式分开，现代内建formatter支持有变化；本章只做自己的受控内存对象验证 |

**Json.NET反例于原泛化说法：** 默认可识别标Serializable并实现ISerializable的类型，只用GetObjectData给的值，反序列化调用info/context构造；JsonObject可强制普通对象合同，IgnoreSerializableInterface也可改变选择。仅有Serializable而无接口时，IgnoreSerializableAttribute=false可选择字段模式，包含相应私有字段。它不是“这两个完全不起作用”的统一现代JSON规则。[Json.NET官方合同](https://www.newtonsoft.com/json/help/html/SerializationGuide.htm)

本机只复用已有SDK依赖，Framework和现代.NET各有一次JSON探针：自定义Wire把值写为WireValue42，GetObjectData与序列化构造各执行一次；IgnoreInterface/JsonObject则输出普通DisplayValue42。原Person公有字段在Json.NET默认输出Name/Age，字段模式又出现private Hidden7。

System.Text.Json不会自动调用这个传统GetObjectData路径。该字段型Person默认输出{}，IncludeFields=true才输出Name/Age；Wire按普通公开属性输出DisplayValue42，GetObjectData次数为0。其他设置/转换器可以改变合同，所以“现代JSON只看public属性、从不看字段”的概括也不成立。两个SDK依赖分别面向Framework4.5和NETCoreApp6.0，输出相同不表示程序集字节相同；源码、依赖SHA、版本和实际命令均留档。[真实序列化/JSON结果](整理记录/验证工作区/第20章/序列化合同/结果.json)

## 什么错、哪里错与业务阶段

<a id="c20-error-models"></a>

Win32原例是C风格的**假定API示意**，Transfer(hAccount,amount)不是本文已核到的真实Windows转账API：

```c
BOOL result = Transfer(hAccount, amount);  // 返回 TRUE/FALSE
if (!result) {
    DWORD err = GetLastError();  // 再单独查"为什么失败"
    // err == ERROR_ACCESS_DENIED? 还是 ERROR_NOT_ENOUGH_MEMORY?
}
```

只有API规定失败时设置相应last-error，才按该合同读取；应该在可能覆盖它的其他调用前及时取得，错误信息与线程有关。不是所有Win32/C函数都只返回BOOL，再统一调用GetLastError。HRESULT、特殊返回值等也有自己的合同。[GetLastError官方说明](https://learn.microsoft.com/en-us/windows/win32/api/errhandlingapi/nf-errhandlingapi-getlasterror)

CLR模型可以用类型/Message表达失败，并用轨迹帮助诊断路径，但业务契约仍需要知道已完成哪一步。原SecurityException转账片段：

```csharp
public void Transfer(Account from, Account to, decimal amount)
{
    from.Withdraw(amount);   // ← 假设这里抛 SecurityException
    to.Deposit(amount);
}
```

这里是假定Withdraw抛SecurityException，不是实际访问检查实验。类型不自动保证Message一定写着那条中文权限解释，错误报告方式也不能替代转账状态一致性。源所比较SecurityException/OutOfMemoryException等“为什么”与Transfer失败这个“哪项操作”，是两种不同信息需求。

<a id="c20-source-business-paths"></a>
### Transfer与GetBalance共用Withdraw

原冻结账户的两个路径：

```csharp
public void Transfer(Account from, Account to, decimal amount)
{
    from.Withdraw(amount);   // 路径 A：Transfer → Withdraw
    to.Deposit(amount);
}

public void GetBalance(Account a)
{
    a.Withdraw(0);           // 路径 B：GetBalance → Withdraw（试探一下）
    // ...
}
```

源还有Form1.btnTransfer_Click直接调用Withdraw的不同上层情境：同一个底层失败可以被不同业务入口触发。Source默认通常是抛出方法所在程序集的简单名，不是最内层方法名，也不等同AppDomain.FriendlyName或带扩展名的exe文件名。可显式设ex.Source="Transfer"或重写其属性，但EDI不会自动把它改成某个业务方法名。[Source API说明](https://learn.microsoft.com/en-us/dotnet/api/system.exception.source?view=netframework-4.8.1)

**原书归因说明：** 第4版20.7、本地MD711/原书物理437印420把Source概括为可告诉失败方法，继而说必须解析StackTrace字符串。这个概括不够精确：未显设Source时默认是异常起源程序集名；而20.3及本章已有的new StackTrace(ex)可程序化取得StackFrame/GetMethod，不只有解析人类字符串一条路。书要区分“业务哪项操作失败”与“底层为什么失败”的主旨保留，Transfer/GetBalance等聊天不同路径例仍分别保。

原希望对比的两条异常轨迹仍是不同路径的示意：

```text
at Account.Withdraw(...)
at Program.Transfer(...)      ← 这条才是你想要的"真正哪里出错"
at Program.Main(...)
```

```text
at Account.Withdraw(...)
at Program.GetBalance(...)   ← 另一条路径
at Program.Main(...)
```

原CRLF字符串例也保留作为格式示意：

```text
"   at Account.Withdraw(Account a)\r\n   at Program.Transfer()\r\n   at Program.Main()"
```

它的Withdraw(Account a)/Transfer()签名不是上面Withdraw(decimal)和三参Transfer的逐字实际签名。不同文化、符号、优化会改变显示，不应把split或正则解析人类输出当稳定业务协议；**也不是只能解析字符串**，前节new StackTrace(ex)可枚举相应StackFrame/GetMethod。

本机补充明确NoInlining的Account替身验证：Transfer和GetBalance的Source都是同一个本程序集简单名，TargetSite都是Withdraw；Frame API区分Withdraw/Transfer/Main与Withdraw/GetBalance/Main。原Security不同输入另得到SecurityException，Source仍同一个程序集。没有真实支付、冻结账户或权限策略操作。[业务路径实证](整理记录/验证工作区/第20章/业务来源与调用者/结果.json)

<a id="c20-transfer-stage"></a>
### Operation与Stage的原类型片段需要构造

原聊天把Source/业务何处失败这段说成20.6之前，或称“接下来下一段20.6”，章节次序有误：实际20.7的MD711/原书物理437印420在20.6泛型异常壳之后。业务上下文的教学联系保留，不据该错序推只有新异常类型才能记录操作/阶段。

原TransferFailedException只给两个get-only属性，却调用未声明的三参构造。为让这个**原场景**成立，补齐构造和字段赋值；下面的base消息文字是补充，原没有给该消息内容：

```csharp
public class TransferFailedException : Exception
{
    public string Operation { get; }
    public string Stage { get; }
    public TransferFailedException(string operation, string stage, Exception inner)
        : base("转账步骤失败", inner) // 补齐的消息，非原源已有值
    {
        Operation = operation;
        Stage = stage;
    }
}

// 原用法保留：
try { from.Withdraw(amount); }
catch (Exception e)
{
    throw new TransferFailedException("Withdraw", "Transfer.from", e);
}
```

Operation/Stage表达业务上的哪里失败，InnerException保存什么底层失败，不能说这是丢掉原StackTrace的替代。包装什么失败、是否该使用这么宽的catch仍按服务契约决定；Data或明确的日志上下文也可承载相应诊断，不只有自定义异常一个选项。

TargetSite在原书20.3属性表已列，CallerMemberName等调用者信息也在C#5/Framework4.5时代存在，不能归为第四版以后才有。TargetSite主要表示相应抛出方法；CallerMemberName是编译器为被调用方法的特定可选参数填入调用者文本，不是自动从任意异常还原完整业务因果链。[调用者信息合同](https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/attributes/caller-information)

保留原三维Win32/CLR模型表的用途，原“CLR更好”是评价，不能当所有API应统一一种错误模型的规范：

| 维度 | 原BOOL/last-error示意 | 托管异常模型 | 业务判断 |
| --- | --- | --- | --- |
| 哪里出错 | 这个调用返回FALSE，可识别失败的调用点 | 异常轨迹描述相应调用/抛出路径 | 还需识别实际业务阶段与完成效果 |
| 什么出错 | 对有合同的API及时读取last-error | 具体类型、Message及附加诊断 | 人类消息不是稳定错误码合同 |
| 哪个业务操作失败 | 调用方明确记录自己的操作 | Source不是完整业务路径，Frame/类型也不自动给全部语义 | Operation/Stage、Data或日志可明确上下文，按服务契约选择 |

## 线程中止的历史保护与两步转账

<a id="c20-abort-history"></a>

用户问空try、把更新放进finally为什么可能更健壮。这里讨论的是Framework时代的**普通Thread.Abort/AppDomain卸载与受保护区**，不是资金操作的事务原子性。普通abort请求在catch/finally等区域会受到延期处理；线程执行native代码时也可能等返回托管代码后才发生，不能说“任何单条IL、任何时刻必立刻掐断”。普通请求、强制终止、同步业务异常与宿主策略不同。[Thread.Abort历史/现代说明](https://learn.microsoft.com/en-us/dotnet/api/system.threading.thread.abort?view=netframework-4.8.1)

原两个余额字段操作：

```csharp
from.Balance -= amount;
// ⚠️ 如果线程在这里被 Abort 了呢？
to.Balance += amount;
```

原书Account运算符场景，保留空try和-=、+=：

```csharp
public static void Transfer(Account from, Account to, Decimal amount) {
    try {
        // 这里什么都不做
    }
    finally {
        from -= amount;
        // 原书Framework普通abort延期语境；这不是事务原子性/任何终止方式的保证
        to += amount;
    }
}
```

它没有在此定义Account运算符。若Account是引用类型且operator直接修改传入对象，第一步已扣款后第二步同步失败，仍能留下只扣未加。若operator返回一个新的Account，复合赋值可能只是重绑定本方法的局部参数，调用者原对象未改变。不能只看这两行就把所有实现都当作完整转账。

原正式答先承认to+=可能抛，却又说“至少不会只扣不加”，两句不成立。受控补充以余额100/100、金额10验证：修改原对象的operator在第二步失败后是90/100；返回新对象的operator只改局部，调用者仍100/100。没有实际调用Abort/Unload、真实银行或远端服务。[两操作语义实证](整理记录/验证工作区/第20章/Monitor与转账状态/结果.json)

<a id="c20-cancellation"></a>
### 现代协作式取消不是让任意操作原子完成

原Abort版本表收窄为：

| 版本/语境 | 状态 |
| --- | --- |
| .NET Framework | API仍可用，但不能安全推断被中止处状态；本机Abort方法未带现代Obsolete标记 |
| .NET Core/.NET5+ | 不支持Thread.Abort，调用有相应PlatformNotSupportedException合同；5+编译有SYSLIB0006提示 |
| 新业务取消 | 按协作式取消/失败/清理合同设计，而非把任意更新搬进finally就保证不半完成 |

原`CancellationToken.ThrowIfCancellationRequested();`若CancellationToken是类型名，不是合法静态调用；它需要实例。本章采用以下修正片段，token由调用方传入：

```csharp
token.ThrowIfCancellationRequested();
```

检查点可以在当前代码或被调用的支持取消API中；请求取消不自动撤销已提交状态。受控实例检查抛OperationCanceledException，静态反例真实CS0120。原“核弹/掐断/保命区域”比喻只表达强制中止使状态难推断，不作99%使用频率或“邪恶API”的技术分类。[现代Abort弃用](https://learn.microsoft.com/en-us/dotnet/fundamentals/syslib-diagnostics/syslib0006)

原CER预告骨架仍保留为历史说明：

```csharp
RuntimeHelpers.PrepareConstrainedRegions();
try
{
}
finally
{
    // CER：比普通 finally 更强的保证
}
```

CER真实章节是20.12；此骨架没有提供可靠性契约和完整准备条件，不让任意finally变成无错误的更新事务。现代.NET不支持该机制，后节按完整原例说明。

## Monitor的对象身份与明确的锁生命周期

<a id="c20-monitor-basics"></a>

Monitor.Enter取得一个对象对应的监视器锁；同一线程可以重入，其他线程若参与同一锁且无法取得，可能等待。它不自动使所有后续代码或对象里的任意数据都被互斥保护，需要参与者遵守共同同步约定。

原“厕所单坑、进门上锁、出门开锁”类比说明互斥；“钥匙扣/令牌”说明共享数据与用于锁的对象可以分开。不能把真实对象身份简化为一张按永远固定的内存地址查找的公开表；GC可以移动对象，Monitor的API合同仍按对象身份、持有线程和重入次数理解。

原money初值100例：

```csharp
int money = 100;

void Withdraw()
{
    money -= 10; // 这一行不是原子的！
}
```

两个线程各扣10，串行完整结果应为80；非原子读改写重叠可能丢一次更新而为90。80本身不是错误结果，源码一行也不等整个复合操作原子。

原共享对象的取得与单独令牌声明：

```csharp
object lockObj = new object();

Monitor.Enter(lockObj);
```

```csharp
object lockObj = new object(); // 这个对象在堆上
```

这些只是局部片段，未给出释放路径，不能把裸Enter当作独立运行后无需配对的安全例。

<a id="c20-monitor-boxing"></a>
### int装箱能编译，问题在于取锁与退出的对象不同

原int0片段的“编译不过”注释修正如下：

```csharp
int lockObj = 0;
Monitor.Enter(lockObj); // 可编译：装箱成object；单独运行此裸Enter会遗留未准确配对的锁
```

Monitor.Enter参数类型是object，值类型可装箱，因此两编译器都接受这个源形状。另一次Monitor.Exit(lockObj)又装箱成另一个对象，通常并不是刚取得的同一个监视器；问题在身份和配对。补充静态对照`lock(int)`确实有CS0185，但不能拿它代替Monitor.Enter的合同。

受控补充保存两个箱a/b，ReferenceEquals为False；取得a后退出b真实SynchronizationLockException，随后准确退出a。没有单独执行会遗留锁的原裸Enter片段，也没有造成永久等待。

原驻留字符串abc场景：

```csharp
string lockObj = "abc";
Monitor.Enter(lockObj);
```

string是引用类型，调用合法；共享/驻留可能让无意参与者使用同一个对象，造成意外耦合，具体死锁仍需要相应等待依赖，不能说用了字符串就必死锁。通常给自己的同步边界一个明确私有令牌：

```csharp
private readonly object _lockObj = new object();
```

readonly保护的是字段不被重新赋值，不是把共享业务数据自动变成线程安全。实际两次Enter同一对象、一次Exit后本机IsEntered仍True，第二次Exit后False，说明重入须对应释放。

<a id="c20-monitor-lifetime"></a>
### 没有finally的两个原失败路径

原DoSomething抛异常、跳过Exit的三行：

```csharp
Monitor.Enter(lockObj);
DoSomething();      // 可能抛异常
Monitor.Exit(lockObj);
```

原流程图：

```text
Monitor.Enter ✅
DoSomething() ❌ 抛异常
Monitor.Exit ❌ 永远不会执行
```

这里的“永远”应理解为这次异常控制流不再走到该Exit，不是所有线程立即死亡或每个程序一定永久死锁。遗漏配对会让后续同锁参与者受影响，不能任意继续依赖该状态。

不同的Transfer早return反例：

```csharp
void Transfer()
{
    Monitor.Enter(_lock);
    // 几百行代码
    if (xxx) return;
    Monitor.Exit(_lock);
}
```

它的失败条件是xxx分支提前return，而不是DoSomething抛；用它看没有finally的隐藏出口。源xxx和“几百行”是示意，没有给完整业务程序。

<a id="c20-monitor-enter-window"></a>
### Enter在try之外：成功后的窗口与Enter自身失败分开

原手写基础形状：

```csharp
Monitor.Enter(lockObj);
try
{
    DoSomething();
}
finally
{
    Monitor.Exit(lockObj);
}
```

原Transfer配对片段也保留：

```csharp
void Transfer()
{
    Monitor.Enter(_lock);
    try
    {
        // 几百行代码
    }
    finally
    {
        Monitor.Exit(_lock);
    }
}
```

正常进入保护区域、执行主体并可展开退出时，这些finally配对对称释放。释放锁不等于撤销主体已经修改的业务状态。受控主体把money改70后抛，finally正常解锁，money仍70。

原再问“Enter本身抛会不会Exit未持有锁”的片段：

```csharp
Monitor.Enter(lockObj); // 若Enter自身在try外抛，这个关联finally尚未进入
try
{
    ...
}
finally
{
    Monitor.Exit(lockObj); // 不是因为前面的Enter抛就会执行这一行；已取得后保护区前还有窗口
}
```

因为Enter在该try之外，若它自身抛，**关联finally尚未进入**；两环境Enter(null)观察finally标记False。要讨论的另一个窗口，是已经取得锁而尚未进入相应保护区就被打断，不能把这两个失败位置混成同一路径。

第四版年代已可用refbool形状：

```csharp
bool lockTaken = false;
try
{
    Monitor.Enter(lockObj, ref lockTaken);
    DoSomething();
}
finally
{
    if (lockTaken)
        Monitor.Exit(lockObj);
}
```

lockTaken初始为False，进入API在其合同下记录是否取得；调用也放在try里，finally只在持有时退出。Enter(null,refbool)的本机结果是False并抛ArgumentNullException，关联finally按False跳过Exit。这使获取结果可明确处理，但仍不保证任意业务状态/所有进程终止都无失败。[Monitor.Enter合同](https://learn.microsoft.com/en-us/dotnet/api/system.threading.monitor.enter?view=netframework-4.8.1)

<a id="c20-lock-lowering"></a>
### lock的历史/当前降低要看编译器与静态类型

Monitor.Enter(object, ref bool lockTaken)从Framework4.0已有；官方该重载Applies to首列4.0，本章旧四形状与后来C#13精确Lock的EnterScope分支分开。[Enter双参版本](https://learn.microsoft.com/en-us/dotnet/api/system.threading.monitor.enter?view=netframework-4.8.1)

原lockObj与money两个不同用途的lock片段分别保留：

```csharp
lock (lockObj)
{
    DoSomething();
}
```

```csharp
lock (_lockObj)
{
    money -= 10;
}
```

原正式答把下列传统形状直接说成当前lock生成的代码：

```csharp
Monitor.Enter(lockObj);
try
{
    DoSomething();
}
finally
{
    Monitor.Exit(lockObj);
}
```

这与该源前面的手写形状字面相同，但用途是错误的编译器降低解释，不能只按相同文本丢掉其不同教学目标。对本机Framework C#5和现代编译器的object表达式，真实IL都调用Enter(object,refbool)，在finally按结果Exit，较适合原Q8给出的这种形状：

```csharp
bool lockTaken = false;
try
{
    Monitor.Enter(_lockObj, ref lockTaken);
    money -= 10;
}
finally
{
    if (lockTaken)
        Monitor.Exit(_lockObj);
}
```

严谨的降低还需要对锁表达式求值一次，保存同一对象再配对；源固定_lockObj字段省略了这一临时局部，不应扩成任意可变表达式都可反复求值。

C#13及以后在静态类型精确为System.Threading.Lock时有另一种EnterScope/Scope.Dispose降低。本机.NET10 IL已经确认，不能说“所有现代lock本质一律Monitor”。这是现代版本差异，没有用它替换原object/Monitor场景。[lock语句规则](https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/statements/lock)

原把资源生命周期“清晰、安全、无歧义”与CER串联的四行表保留各维度：

| 原联系 | 核心目的 | 此例实际边界 |
| --- | --- | --- |
| finally | 正常/可展开退出收尾 | 取得结果和进入保护区位置要正确，特殊终止及收尾失败另有条件 |
| 状态破坏 | 共享数据一致性 | 解锁不自动回滚业务修改，所有参与者需同一同步合同 |
| 明确方法设计 | 清楚表示获取/释放责任 | refbool/保存对象与配对使成功路径可判，不承诺所有代码绝对成功 |
| CER | 历史受限可靠性机制 | 不是普通Monitor配对自动无失败的升级，现代不支持 |

原Q8另一个三行表也按其不同问题保留：

| 主题 | 原核心问题 | 适用说明 |
| --- | --- | --- |
| finally | 中止/异常会不会打断收尾 | 分普通Framework中止延期与其他终止/同步失败 |
| 锁 | 异常会不会遗漏释放 | 正确获取、记录结果及配对finally/lock；不保证业务回滚 |
| CER | 清理代码尚未准备怎么办 | 原书历史20.12的准备与可靠性合同，非任意现代保证 |

## 可靠性取舍与潜在失败点

<a id="c20-reliability-tradeoff"></a>

原20.7强调，隐藏在简短源码后的分配、调用、初始化等失败，也需要纳入可接受的状态合同；想在任何故障下自动恢复全部状态，会增加大量复杂性。这个工程取舍不等于C++拥有绝对可靠性、托管代码无法保护状态，或“开发效率必须在所有场合高于可靠性”。

RAII能让成功构造的局部对象在普通C++栈展开时配对析构，仍有自己的失败与终止边界。C++并不绝对不能有元数据、反射库、GC/跨语言框架；现代CLR也不能被称为自动提供任意代码安全沙箱。要比较的是实际管理模型与应用约束，不把原“极低开发效率/绝对可靠”评价升级为规范。[MSVC异常机制说明](https://learn.microsoft.com/en-us/cpp/cpp/exception-handling-in-visual-cpp?view=msvc-170)

### 原Transfer的十类潜在失败

原方法与前节参数相似，但教学目的是列出隐藏操作和失败，不用它替代那些状态/诊断例：

```csharp
public void Transfer(Account from, Account to, decimal amount) {
    from.Withdraw(amount);
    to.Deposit(amount);
}
```

按源的不同角度逐项看：null接收者可在调用时失败，不是传null本身就抛；虚派发/需要加载的相关依赖各有条件，不是每次查表必加载类型。decimal传给decimal签名不需要箱，若另一个API接object才有箱这个附加条件。JIT准备针对实际方法及运行策略，不是每次对象引用访问都重新编整个类型；准备在哪里发生，也影响外层是否已经进入try。

Withdraw内部若调用事件订阅者，订阅者可以抛；分配或数组/集合访问也会失败，List常规越界与数组越界的API异常不同。历史MarshalByRefObject只有实际跨域调用才涉及相应代理/传输失败，不是继承它就每次跨域。Framework强制中止还要按前节延期/交付条件理解，不能在清单中写成任何单条IL随时必终止。

源只提到OneStatement示例名称，没有给其整个函数，本章不补造原来没保存的书码。它实际提供的不同场景——转账、静态初始化、LINQ、域/远程失败——仍分别保留。

### Foo“我炸了”：失败与元数据访问不同

原类型：

```csharp
class Foo {
    static Foo() {
        throw new Exception("我炸了");
    }
}
```

在相应已经加载的类型身份中，触发静态初始化失败会有TypeInitializationException包装，通常不会靠再次普通触发就重试成功。本机同一Foo两次new都失败并保留内部“我炸了”消息，但typeof(Foo)和GetConstructors仍可使用；不能把“类型永久不可用”扩大成任何元数据都消失。历史AppDomain/现代加载上下文与不同类型身份另有生命周期，失败不是所有进程里同名类型永远失效。[初始化异常说明](https://learn.microsoft.com/en-us/dotnet/api/system.typeinitializationexception?view=net-10.0)

### LINQ构建与枚举发生在不同阶段

原表达式片段：

普通Enumerable.Where/Select中的lambda是编译器产生的方法/委托等表示，运行时可能准备相关代码，不是在每次MoveNext时重新调用C#编译器。查询构建的参数检查与之后延迟枚举、谓词/投影调用、Owner为null是不同失败点。表达式树/特殊provider的机制又需它们自己的合同，不能拿来替普通源片段解释。[Where延迟执行合同](https://learn.microsoft.com/en-us/dotnet/api/system.linq.enumerable.where?view=netframework-4.8.1)

## C#终结器及基类finally调用

<a id="c20-finalizer-lowering"></a>

Object有受保护的Finalize成员，C#通过~ClassName语法声明终结器，不能说成员本身不存在。它与C++确定性局部析构不是同一个对象生命周期机制。

原MyClass：

```csharp
class MyClass
{
    ~MyClass()
    {
        Console.WriteLine("Cleanup");
    }
}
```

原编译器生成结构用C#风格表示如下，**是伪代码，不是可直接写出的C# override，更不是真正IL文本**：

```csharp
protected override void Finalize()
{
    try
    {
        Console.WriteLine("Cleanup");
    }
    finally
    {
        base.Finalize();   // ← 关键：编译器自动帮你加的
    }
}
```

实际编译方法的元数据可以是protected/virtual的Finalize，finally里调用相应基类。源用户问的“在finally里调基类”正是编译器自动安排的形状，不是要求程序员在析构体手工再写一次。[C#终结器说明](https://learn.microsoft.com/en-us/dotnet/csharp/programming-guide/classes-and-structs/finalizers)

<a id="c20-finalizer-chain"></a>
### 同一Derived对象的继承清理链

原两类及打印分别保留：

```csharp
class Base
{
    ~Base()
    {
        Console.WriteLine("Base cleanup");
    }
}

class Derived : Base
{
    ~Derived()
    {
        Console.WriteLine("Derived cleanup");
    }
}
```

原调用链图：

```text
Derived.Finalize()
→ Base.Finalize()
→ Object.Finalize()
```

这是同一对象的生成调用链，不是三个独立对象都被回收一次。终结准备/执行不等于对象存储此刻已经回收，仍可能有引用和复活等行为；不同对象之间的终结顺序更不是这里的继承次序。

本机两环境原Base/Derived输出依次Derived cleanup、Base cleanup；实际Derived方法的异常区域为Finally，并解码看到末尾调用Finalize。补充线程ID和Main不同（两环境具体ID值也不同），不能把终结器统称普通“GC线程”或把某个数字当恒定ID。探针NoInlining创建和10秒信号是受控补充，没有执行会让终结线程未处理失败的反例。[真实终结降低/执行证据](整理记录/验证工作区/第20章/终结器降低与LINQ/结果.json)

<a id="c20-finalizer-negatives"></a>
### 原手写base.Finalize反例，语法已先失败

```csharp
~Derived()
{
    Console.WriteLine("Derived cleanup");
    base.Finalize();   // C#本身禁止直接调用base.Finalize，真实CS0250，不能当可运行样例
}
```

它不是先跑到Console异常才漏基类调用；C#在编译时就给CS0250。直接声明protected override void Finalize也有CS0249。原再次展示的生成finally形状仅供理解：

```csharp
try
{
    // 你的清理逻辑
}
finally
{
    base.Finalize();   // 生成结构伪码：正常可展开路径尝试基类清理；不保证所有终止或清理结果
}
```

finally在正常可展开流程尝试基类清理，不能保证任何进程退出、FailFast、阻塞或清理效果都成功。原“父类资源永远没机会”“无论如何基类必执行”需要这个适用边界；也可能有别的显式Dispose路径，不能把一种调用责任说成所有资源只有唯一机会。

<a id="c20-filewrapper-fragment"></a>
### FileWrapper句柄片段没有给完整IDisposable实现

原FileWrapper保留为**不完整类型片段**：

```csharp
class FileWrapper : IDisposable
{
    private IntPtr _handle; // 非托管文件句柄

    ~FileWrapper()
    {
        if (_handle != IntPtr.Zero)
        {
            CloseHandle(_handle); // 释放非托管资源
            _handle = IntPtr.Zero;
        }
    }
}
```

源未给Dispose实现、CloseHandle声明或取得句柄的构造，不能叫完整真实可运行程序。两编译器真实先报告CS0535；没有执行假定句柄的native释放。后面的对应形状仍是C#风格生成伪码：

```csharp
protected override void Finalize()
{
    try
    {
        if (_handle != IntPtr.Zero)
        {
            CloseHandle(_handle);
            _handle = IntPtr.Zero;
        }
    }
    finally
    {
        base.Finalize(); // Object.Finalize 是空的，但必须调
    }
}
```

它说明生成的基类finally调用，并不补出完整资源所有权、并发和释放失败合同。Object.Finalize本身的内容与继承中其他类型的实际清理责任也要分开。

<a id="c20-safefile-fragment"></a>
### SafeHandle包装的原SafeFile片段

```csharp
class SafeFile : IDisposable
{
    private SafeHandle _handle; // ✅ CLR 为你管理 Finalize

    public void Dispose()
    {
        _handle.Dispose();
        GC.SuppressFinalize(this); // 告诉 GC：不用调 Finalize 了
    }
}
```

SafeHandle字段在这个源片段没有初始化，不能直接new此类再Dispose而假定一定有有效资源；默认null会使该访问失败。字段应该接到具有相应所有权的有效包装对象，完整来源后几问再给不同资源例。

SafeHandle及Dispose建议是Framework历史也已有的设计，不是第四版以后才刚成熟；并非所有IDisposable都有native句柄，也并非任何包装都绝对不应有自己的终结责任。这个SafeFile自己没有终结器，SuppressFinalize(this)不等于取消SafeHandle自身的终结，也不会消除SafeFile原本不存在的终结队列负担。

现代SafeHandle仍有相应终结保障/引用计数机制，但现代.NET不支持CER，不能把它叫作现代CLR仍支持任意CER代码的证明。终结是后备清理而非确定时刻的主力；正常退出、Framework关闭、现代退出、不可恢复进程终止各有条件，后文资源/GC章节结合原例进一步说明。

## 让SafeHandle管理句柄，仍要说明所有权与使用寿命

<a id="c20-safehandle-original"></a>

用户追问为什么现在很少手写析构器。SafeHandle并非第四版之后才出现的现代替代物，Framework历史已提供它。普通业务包装通常可以把句柄释放责任交给一个合适的SafeHandle，再提供IDisposable；若只是List、string、Dictionary、Person这类对象所占的托管内存，不需要为此写终结器。“几乎所有开源代码”“99%初级程序员”是原回答未给数据的评价，不作为使用比例或规范。

原直接持有IntPtr的MyResource类型片段：

```csharp
class MyResource
{
    private IntPtr _nativePtr; // 非托管内存/句柄

    ~MyResource()
    {
        if (_nativePtr != IntPtr.Zero)
        {
            NativeMethods.CloseHandle(_nativePtr);
        }
    }
}
```

它没有给出取得资源的构造或NativeMethods声明，也没有确定性Dispose。这里CloseHandle应对应真实取得的Windows句柄，不能拿任意AllocHGlobal指针去关。终结时机不确定，过久持有可能造成耗尽；终结代码由专门终结线程执行，不能解释成“GC闲下来在GC线程做一下”。C#编译器处理基类Finalize的finally链，不能直接手写base.Finalize。

原专用MySafeHandle例，仍按Windows句柄片段阅读：

```csharp
using Microsoft.Win32.SafeHandles;
using System.Runtime.ConstrainedExecution;

class MySafeHandle : SafeHandleZeroOrMinusOneIsInvalid
{
    public MySafeHandle(IntPtr handle) : base(true)
    {
        SetHandle(handle);
    }

    // 这是唯一需要你重写的方法
    // CLR 会在安全的环境下调用它
    [ReliabilityContract(Consistency.WillNotCorruptState, Cer.Success)]
    protected override bool ReleaseHandle()
    {
        // 这里是释放非托管资源的唯一入口
        return NativeMethods.CloseHandle(handle);
    }
}
```

资源类型决定ReleaseHandle里的释放函数。原注释“唯一需要重写的方法”也以所继承的SafeHandleZeroOrMinusOneIsInvalid已实现IsInvalid为前提；直接继承SafeHandle还需实现相应抽象成员。`ReliabilityContract(WillNotCorruptState, Cer.Success)`表达历史可靠性契约，不能替自己证明任意CloseHandle结果、Console日志、分配或同步异常都不失败。SafeHandle有关键终结保障，但现代.NET不支持旧CER；本机.NET10编译此特性真实SYSLIB0004。[现代CER支持说明](https://learn.microsoft.com/en-us/dotnet/fundamentals/syslib-diagnostics/syslib0004)

原“组合拳”“临终清理交出去”“防弹保险箱”“保命符”类比有助于记住业务层与资源层的分工，保险箱仍需正确放入属于它的资源，ReleaseHandle仍需正确实现。不能据类比推出所有OOM、Thread.Abort、进程终止都必执行完、所有调用者并发使用自动安全或事务原子性。

保留原Q11的四个比较维度，改正绝对承诺：

| 场景 | 直接持有IntPtr并手写终结器 | 使用适合资源的SafeHandle |
| --- | --- | --- |
| 释放逻辑 | 自己在明确释放/终结路径调用匹配函数 | 自己在ReleaseHandle中实现匹配释放 |
| 终结器 | 自己实现，需按C#生成规则及实际合同处理 | 包装资源利用SafeHandle的后备终结机制；业务壳通常不再需要自己的终结器 |
| 线程安全 | 自己处理所有权及使用/释放竞争 | SafeHandle维护内部寿命状态；业务使用裸句柄仍需保护，不能包办所有线程安全 |
| 原子性 | 任意多步清理不自动原子 | 不保证任意ReleaseHandle或业务多步一定执行完/要么全成全不成 |

<a id="c20-safehandle-use-window"></a>
### IsInvalid检查和DangerousGetHandle不是使用期间的持有协议

原MyResource业务壳保留为**有寿命缺口的示例**，NativeMethods仍未提供：

```csharp
class MyResource : IDisposable
{
    // 关键变化：不再直接持有 IntPtr，而是持有 SafeHandle
    private readonly MySafeHandle _safeHandle;

    public MyResource()
    {
        IntPtr ptr = NativeMethods.CreateHandle();
        _safeHandle = new MySafeHandle(ptr);
    }

    public void DoSomething()
    {
        if (_safeHandle.IsInvalid)
            throw new ObjectDisposedException(nameof(MyResource));
        
        // 使用 _safeHandle.DangerousGetHandle() 获取原生指针进行调用
        NativeMethods.UseHandle(_safeHandle.DangerousGetHandle());
    }

    // 实现 IDisposable
    public void Dispose()
    {
        // 告诉 SafeHandle：现在就释放，不要等到析构器了
        _safeHandle.Dispose();
        
        // 告诉 GC：别再调用我的析构器了（因为我已经清理完了）
        GC.SuppressFinalize(this);
    }

    // ❌ 注意：这里不再需要手写析构器 ~MyResource()
}
```

IsInvalid按具体资源的无效值规则判断，不等于IsClosed。关闭后的包装可能仍保存一个数值上有效的旧句柄；DangerousGetHandle只返回该值，不自动增加引用。即使先检查IsClosed/IsInvalid，检查和native使用之间另一线程仍可能Dispose，释放或重用该句柄。[DangerousGetHandle的限制](https://learn.microsoft.com/en-us/dotnet/api/system.runtime.interopservices.safehandle.dangerousgethandle?view=net-10.0)

补充的解决形状之一是让正确声明的P/Invoke直接接收相应SafeHandle，使互操作封送按合同持有它；必须手取裸值时，使用成功的DangerousAddRef与finally中的DangerousRelease配对。下面是替换原DoSomething的**补充片段**，NativeMethods仍需真实声明，不当完整native程序：

```csharp
public void DoSomething()
{
    bool added = false;
    try
    {
        _safeHandle.DangerousAddRef(ref added);
        if (_safeHandle.IsInvalid)
            throw new InvalidOperationException("Invalid native handle.");
        NativeMethods.UseHandle(_safeHandle.DangerousGetHandle());
    }
    finally
    {
        if (added) _safeHandle.DangerousRelease();
    }
}
```

这里保护的是该引用协议下的资源寿命，不保证native操作、业务状态或其他API不会失败。危险引用若没归还，还可能延后真正释放。[DangerousAddRef的合同](https://learn.microsoft.com/en-us/dotnet/api/system.runtime.interopservices.safehandle.dangerousaddref?view=net-10.0)

受控补充自分配1024字节的SafeHandle，两环境实际输出均为：

```text
ADDED=True
DISPOSE_HELD=False/False/0
RAW_SAME_HELD=True
AFTER_RELEASE=True/False/1
STALE_VALUE_SAME=True
ADD_CLOSED=ObjectDisposedException
REPEATED=1
```

三项状态依次为IsClosed/IsInvalid/实际Release计数。持有时Dispose还没真正Release，最后DangerousRelease后才Closed；此时IsInvalid仍false、裸数值未清空，关闭后AddRef抛ObjectDisposedException。实验只比较旧数值，没有读取已释放内存；这是一个顺序协议观察，不是所有并发或极端故障的压力保证。[实际源码/命令/输出](整理记录/验证工作区/第20章/SafeHandle文件与GC/结果.json)

另一个原例缺口在CreateHandle成功与new MySafeHandle(ptr)之间：如果包装分配/构造失败，尚未转交的裸资源仍需原拥有者保护、匹配释放；直接返回适当SafeHandle的互操作声明或明确的转移失败保护可减小这类窗口。不能把“立即交给”两个连续语句当作已经证明无泄漏的原子交接。

这个MyResource没有自己的终结器，SuppressFinalize(this)既不消除它不存在的终结队列负担，也不取消字段SafeHandle自身的后备终结。SafeHandle.Dispose可触发释放，但有未归还的危险引用时释放可以延后。

## 保留1024字节手工Dispose模式的完整原例

用户要求更直接的新旧代码对照。下面是原MyResource_OldSchool完整类型，1024、所有原输出和Dispose(bool)分支均保留：

```csharp
using System;
using System.Runtime.InteropServices;

public class MyResource_OldSchool : IDisposable
{
    // 1. 直接持有非托管资源的指针
    private IntPtr _nativeHandle;

    public MyResource_OldSchool()
    {
        // 模拟调用 Win32 API 创建非托管资源（如文件句柄、内存块）
        _nativeHandle = Marshal.AllocHGlobal(1024); 
        Console.WriteLine("资源已分配");
    }

    // 2. 手动编写析构器（Finalizer）
    //    编译器会把它编译成 protected override void Finalize()
    ~MyResource_OldSchool()
    {
        Console.WriteLine("析构器被调用（GC调用的）");
        Dispose(false); // CLR的后备终结路径只释放本对象拥有的非托管资源，不依赖其他普通终结对象
    }

    // 3. 公开 Dispose 方法
    public void Dispose()
    {
        Console.WriteLine("Dispose被调用（用户调用的）");
        Dispose(true); // 重点：用户调用时，释放所有资源
        GC.SuppressFinalize(this); // 告诉GC：别再调用我的析构器了
    }

    // 4. 核心清理逻辑
    protected virtual void Dispose(bool disposing)
    {
        if (disposing)
        {
            // 这里释放托管资源（比如其他的IDisposable对象）
            Console.WriteLine("释放托管资源...");
        }

        // 无论如何，都要释放非托管资源
        if (_nativeHandle != IntPtr.Zero)
        {
            Marshal.FreeHGlobal(_nativeHandle); // 释放非托管内存
            _nativeHandle = IntPtr.Zero;
            Console.WriteLine("非托管资源已释放");
        }
    }
}
```

这段原类型正常顺序清理可以工作；不要因为同轮“旧写法危险”的评价就把合法Dispose模式本身判错。Dispose(true)负责此对象拥有的可处置托管资源及native资源，终结路径一般避免依赖其他普通终结对象的有效性。原注释/字符串“GC调用”只是通俗表示CLR后备终结，不是GC线程直接执行的证据。重复调用时ptr归零避免本例顺序doubleFree，但managed日志仍会重复；原类型没有给并发Dispose同步协议，不能用顺序成功保证并发安全。构造中AllocHGlobal成功后的Console也可能失败，终结日志本身亦可能失败，应按真实清理合同减少这类故障点。

实际只补using/Main、反射观察已归零及NoInlining创建，原类型算法/字符串不改。两环境正常两次Dispose都只打印一次“非托管资源已释放”，ZERO=True；受控Collect/Wait/Collect后，另一个未Dispose的原对象打印原析构与native释放日志，WEAK=False。没有触发OOM、中止、日志异常或并发doubleFree，不能因此证明各种退出方式都执行终结。

### 原SafeHandle类型与业务壳存在构造不匹配

原类型只有无参构造：

```csharp
using Microsoft.Win32.SafeHandles;
using System.Runtime.ConstrainedExecution;

public class MySafeHandle : SafeHandleZeroOrMinusOneIsInvalid
{
    public MySafeHandle() : base(true) { }

    // 这个方法是释放资源的唯一入口
    // 原答声称CER使它绝对跑完；实际须满足历史可靠性合同，现代.NET不支持CER
    [ReliabilityContract(Consistency.WillNotCorruptState, Cer.Success)]
    protected override bool ReleaseHandle()
    {
        Console.WriteLine("SafeHandle: ReleaseHandle 被调用（CLR保证执行）");
        Marshal.FreeHGlobal(handle); // 释放非托管内存
        return true;
    }
}
```

原业务壳却调用new MySafeHandle(ptr)：

```csharp
public class MyResource_Modern : IDisposable
{
    // 1. 不再直接持有 IntPtr，而是持有 SafeHandle
    private readonly MySafeHandle _safeHandle;

    public MyResource_Modern()
    {
        // 创建非托管资源，并立即交给 SafeHandle 保管
        IntPtr ptr = Marshal.AllocHGlobal(1024);
        _safeHandle = new MySafeHandle(ptr);
        Console.WriteLine("资源已分配（由SafeHandle保管）");
    }

    public void DoWork()
    {
        if (_safeHandle.IsClosed || _safeHandle.IsInvalid)
            throw new ObjectDisposedException(nameof(MyResource_Modern));
        
        Console.WriteLine("工作中...");
    }

    // 2. 只有 Dispose 方法，没有析构器 (~MyResource_Modern)
    public void Dispose()
    {
        Console.WriteLine("Dispose被调用，释放 SafeHandle");
        _safeHandle.Dispose(); // 告诉 SafeHandle：现在就释放
        // 注意：这里不需要 GC.SuppressFinalize，因为 MyResource_Modern 没有析构器！
    }
}
```

两者合起来都真实CS1729，不能把它当已完整可运行的标准答案。保持原1024与MyResource_Modern形状，补充如下构造到MySafeHandle即可解决这个成员缺失：

```csharp
public MySafeHandle(IntPtr ptr) : base(true)
{
    SetHandle(ptr);
}
```

补齐后的两环境普通DoWork打印“工作中...”，两次Dispose只有一次Release日志；之后DoWork抛ObjectDisposedException，业务壳DeclaredOnly终结器为false。Release日志中保留的“CLR保证执行”是**原打印文字**，不代表实验核实了该绝对主张。现代编译SYSLIB0004已实际保存；ReleaseHandle里的Console仍可能抛，而属性不会替它消除错误。AllocHGlobal成功→包装构造与后续日志的失败/所有权窗口也仍需处理，补构造并未补全所有故障保障。

Q12原五个对照维度不同于Q11四维表，分别保留：

| 特性 | IntPtr + 自己的终结器/Dispose模式 | SafeHandle包装 |
| --- | --- | --- |
| 非托管资源 | 手工记录裸值与所有权 | 交给正确的专用SafeHandle，仍需正确转移 |
| 析构器 | 此设计自己声明后备终结 | 普通业务壳不必重复写；专用SafeHandle继承已有后备机制 |
| 可靠性 | 依赖实现、线程/故障/所有权合同，不能只称GC线程中断 | 复用SafeHandle机制；不能声称现代CER仍支持或释放必成功 |
| 代码量 | 本例包含Dispose(bool)/Suppress/终结分支 | 本例业务壳较少，完整interop及转移保护仍有代码 |
| 心智负担 | 直接负责底层寿命细节 | 降低重复工作，仍要理解资源协议和拥有/借用关系 |

原“手榴弹+遗书”与“防弹保险箱+开关”“走钢丝/走天桥”“专业保镖”类比保留为分工说明，不能推出壳外任何错误由CLR包办。原“发动机/自动驾驶”“引擎盖/日常开车”“冰山分层”表达学习底层原理与使用封装的不同视角；封装把责任下移，并不等于资源消失，也不直接证明某种依赖倒置设计优于所有其他方案。

### 使用using、异步清理和DI时先判断谁拥有资源

普通List<int>、string、Dictionary、Person的托管内存由GC按可达性管理，既不需要C++式delete，也不能仅为了回收该内存加一个终结器。FileStream、HttpClient、Bitmap则有各自资源/连接/池/本机对象与生命周期合同；不能一概说这些类的底层都相同、都只有SafeHandle，也不能要求任何借到它们的调用者立刻Dispose。HttpClient按适当寿命复用，避免每个请求新建后立即丢掉的简单套法。[HttpClient寿命指南](https://learn.microsoft.com/en-us/dotnet/fundamentals/networking/http/httpclient-guidelines)

原a.txt读取的using语句：

```csharp
// 你看到的代码
using (var fs = new FileStream("a.txt", FileMode.Open))
{
    // 读文件
}
// 你看不到 FileStream 内部的析构器和 SafeHandle，但它们确实存在
```

这是调用方新建并拥有该流的片段，a.txt需已经存在。它与原C#8 using声明Process是不同语法目的，分别保留：

```csharp
public void Process()
{
    using var fs = new FileStream("a.txt", FileMode.Open); // 简洁！
    // 业务逻辑...
} // 自动调用 fs.Dispose()
```

using语句在离开相应语句体时清理；using声明在其所在作用域退出时清理。它们调用清理而不是删除托管对象；清理本身仍可失败。IAsyncDisposable可提供异步清理，`await using`按对应合同等待，不是GC自动调用DisposeAsync。

内建DI容器会按所创建对象的注册寿命清理可处置对象，Scoped/Transient的解析作用域、Singleton的容器寿命须区分。容器外创建再以实例注册的对象，例如AddSingleton(new ExampleService())，框架不会自动替拥有者Dispose；解析者也不能随意关闭由容器管理、其他使用者还需要的服务。原“Scoped结束自动Dispose”在正确的创建/解析/拥有条件下保留。[DI清理与外部实例条件](https://learn.microsoft.com/en-us/dotnet/core/extensions/dependency-injection/guidelines)

<a id="c20-dispose-finalizer-table"></a>
## Dispose与终结器的五项区别

用户问二者关系及微软怎样帮封装类清理。主动清理与后备终结不是两个独立的“必成功保险”。原“医生主动急救/自动除颤机器”“锅自己洗/等家政”“主动关门/自动落锁”类比说明调用时机，不能推延迟最多一周、永不疲倦、没关门锁就必落下等保证。

| 特性 | Dispose方法 | 终结方法（C# ~ClassName） |
| --- | --- | --- |
| 调用者 | 调用方、using降低或具有清理责任的框架 | CLR的终结机制，通常由专门终结线程执行 |
| 时机 | 明确执行到清理调用，调用仍可能阻塞/失败 | 依GC发现不可达及终结调度等条件，不是固定时刻 |
| 目的 | 按拥有合同释放/归还资源、结束生命周期 | 适合native资源的后备清理，不能代替确定性清理 |
| 速度 | 直接发起，不等于实际工作必快 | 可能延后且有额外GC寿命成本，不是固定性能排名 |
| 代码位置 | 常见public void Dispose，可含Dispose(bool)等模式 | C#终结器语法，编译器生成相应Finalize链 |

### FileStream本身有终结器，不能把简化伪码当源码

原使用端完整保留：

```csharp
// 你的代码
using (var fs = new FileStream("test.txt", FileMode.Create))
{
    fs.WriteByte(1);
} // 问：这里到底发生了什么？为什么文件没被锁死？
```

在正常using退出路径，Dispose进行按合同的关闭/清理；文件是否还允许别人删除或写入还取决于FileShare等条件，不是只要存在流就必锁死。

原“Framework内部简化源码”是下面这个**带错误结论的伪代码**，含CreateFile(...)省略，不是可直接编译的真实实现：

```csharp
public class FileStream : Stream, IDisposable
{
    // 1. 内部有一个 SafeHandle（这就是那个“保险箱”）
    private SafeFileHandle _handle;

    public FileStream(string path, FileMode mode)
    {
        // 调用 Win32 API CreateFile 拿到文件句柄
        IntPtr nativeHandle = CreateFile(path, ...);
        
        // 把原生句柄装进 SafeHandle 里
        _handle = new SafeFileHandle(nativeHandle, ownsHandle: true);
    }

    // 2. 实现 IDisposable
    public void Dispose()
    {
        // 关闭 SafeHandle
        _handle.Dispose(); 
        
        // 告诉 GC：别管我了，我已经把自己收拾干净了
        GC.SuppressFinalize(this); 
    }

    // 3. 注意：FileStream 类本身【没有】析构方法 (~FileStream)
    //    因为它把“善后工作”全权交给了 SafeFileHandle
}
```

它末尾说FileStream没有终结器，与Framework真实源码及.NET10固定版本都不符。Framework有~FileStream；.NET10仍保留它以兼容已有派生类对Dispose(false)调用的依赖，真实自身形状为：

```csharp
~FileStream()
{
    Dispose(false);
}
```

本机两环境DeclaredOnly反射也均确认FileStream自己的Finalize存在，不是仅继承Object。真实FileStream还涉及流缓冲、异步及平台策略，不能以原十几行壳替代完整实现。[Framework FileStream源码](https://raw.githubusercontent.com/microsoft/referencesource/main/mscorlib/system/io/filestream.cs)、[.NET10 FileStream源码](https://raw.githubusercontent.com/dotnet/runtime/v10.0.0/src/libraries/System.Private.CoreLib/src/System/IO/FileStream.cs)

原Windows SafeFileHandle的ReleaseHandle核心片段保留：

```csharp
protected override bool ReleaseHandle()
{
    // 这里是唯一的出口：调用 Win32 API 关闭文件句柄
    return CloseHandle(handle);
}
```

它表达正确资源函数配对，不是跨平台所有句柄统一用CloseHandle。现代OSFileStreamStrategy中，Dispose(bool)只有disposing=true时主动Dispose其SafeFileHandle；后备资源寿命仍结合SafeHandle终结与真实策略理解，不能从FileStream~直接推每条路径都在该方法立即Close。[.NET10 OS文件策略](https://raw.githubusercontent.com/dotnet/runtime/v10.0.0/src/libraries/System.Private.CoreLib/src/System/IO/Strategies/OSFileStreamStrategy.cs)

### 原using与忘记using的两种场景分别说明

原省略构造实参的通用using形状仍作为片段：

```csharp
using (var fs = new FileStream(...))
{
    // 使用文件
} // <-- 执行到这里
```

通常流程是离开语句体→调用fs.Dispose→进入实际流/策略清理→处理所拥有句柄及缓冲→按实现抑制相应终结。具体Release是否已经完成，还受额外SafeHandle危险引用及异步操作的协议限制；Dispose不保证所有native关闭都无条件立即完成，亦不证明GC已回收fs占的托管内存。

原忘记Dispose的Test：

```csharp
void Test()
{
    var fs = new FileStream("test.txt", FileMode.Create);
    fs.WriteByte(1);
    // 糟糕！我忘了 using，也没调用 Dispose()
} // <-- 方法结束，fs 变成垃圾
```

方法作用域结束不等于JIT精确根寿命结束，也不能保证对象从未保存到其他根。若确已不可达，GC/终结机制才进行后备处理。具有终结器的对象在创建时已被登记；发现不可达、成为待终结对象、执行终结、之后符合回收条件是不同阶段，不是“发现垃圾才首次放入全部终结队列/下一次GC必回收”。若复活或仍有其他持有关系，寿命可继续。

受控实验在每个独立验证目录用原test.txt/Create/WriteByte1新建文件，拒绝原本存在的文件。using体内独占重开IOException/False，体外能重开/长度1/首字节1；两个环境相同。另Test以NoInlining/WeakReference补观察，人工Collect/Wait/Collect后weakFalse、可独占打开，本次长度1/首字节1；四个文件外层确切清理后均不存在。此后备结果不保证正常生产时刻、退出必执行或任意未Dispose的缓冲写入可靠，不能用它替代using。[文件生命周期实证](整理记录/验证工作区/第20章/SafeHandle文件与GC/结果.json)

Framework退出终结与现代.NET退出不执行同一套终结保证；不可恢复的进程终止也可能没有机会清理。SafeHandle提供后备机制，不是所有情形资源永不泄漏的绝对保证。第21章另保完整终结、复活、弱句柄场景；这里不凭一个FileStream观察推全局调度。[终结器运行与版本说明](https://learn.microsoft.com/en-us/dotnet/csharp/programming-guide/classes-and-structs/finalizers)

<a id="c20-managed-native-types"></a>
## 托管内存与资源生命周期是两个问题

用户再问两种资源分类。原“办公室公司桌/自己的私物”“房东/租客/保洁员”“自动还盘子的机器人”“饭盒外壳/里面剩饭”类比保留，用来表达内存管理与资源协议可以分层；不能推出GC自动结束任何业务对象寿命、native全是Windows向OS申请或不用管持有引用。

托管内存由CLR的GC管理，List、string、Person、数组是常见例子；`new`的值类型并不都代表一个独立托管堆对象，实际存储/优化也要分条件。native资源可能是OS句柄、本机库对象或指定分配器得到的内存，不限Windows。IntPtr只是能够承载地址/句柄令牌的值，其存在不证明已取得资源；释放应匹配取得API及拥有责任，AllocHGlobal对应FreeHGlobal，文件句柄另有CloseHandle。

原List示例（只补using/类上下文即可）：

```csharp
public void DoWork()
{
    List<int> numbers = new List<int> { 1, 2, 3 }; // 托管资源
    numbers.Add(4);
    
    // 方法结束
}
```

List存储内存无需手工free。达到不可达条件后可被GC回收，不以方法结束这一个语法事件判定它此刻立即消失；若字段、事件、静态集合等还强持有，仍可能存活。原“只要全是C#自己类就永远不需担心释放”过强，托管对象也可能拥有其他IDisposable、订阅、池借用或应显式结束的业务寿命。

原忘记CloseHandle的Win32场景是**显式注明模拟API的伪代码**：

```csharp
public void ReadFile_Bad()
{
    // 注意：这是一个模拟的 Win32 API 调用
    // 它向操作系统申请了一个“文件句柄”（非托管资源）
    IntPtr fileHandle = CreateFile("test.txt", ...); 

    // 读取文件内容...
    ReadFile(fileHandle, buffer, ...);

    // 糟糕！我忘了关闭文件句柄！
    // CloseHandle(fileHandle); // <-- 漏了这一句

} // 方法结束
```

裸值变量离开作用域不会自动为这种取得合同调用关闭函数；句柄泄漏可造成占用或耗尽。原“任何其他程序都无法删除或修改”的结论要加文件共享条件；并非任何IntPtr都是内存地址，Windows句柄常是令牌。这里没实现CreateFile/ReadFile，不执行假native调用。

### FileStream混合资源示意与真实类型区分

原4096缓冲/IntPtr的教学壳：

```csharp

{
```

它声称IDisposable却未给Dispose，仅是类型片段，不是System.IO.FileStream源码。托管byte[]与native句柄可分开管理；byte[]若另有可达引用，不能说包装对象一回收它就在同次GC必回收。

原SafeFileHandle交接壳另例，保留并标注其末尾“没有析构方法”为错误：

```csharp
public class FileStream : IDisposable
{
    // 把非托管资源交给 SafeHandle 保管
    private SafeFileHandle _safeHandle; 

    public void Dispose()
    {
        // 1. 释放非托管资源（通过 SafeHandle）
        _safeHandle.Dispose(); 

        // 2. 告诉 GC：不用调用我的析构方法了
        GC.SuppressFinalize(this); 
    }

}
```

真实FileStream及SafeHandle机制见前节。自己新建且拥有的混合对象一般用using/Dispose结束资源协议，GC之后管理对象占的内存；不把对象内存回收与native资源关闭合成一次动作。

原三类资源的五列比较按条件保留：

| 资源类型 | 例子 | 谁来分配 | 谁来释放/结束 | 需要写什么代码 |
| --- | --- | --- | --- | --- |
| 普通托管内存 | List<T>、string、Person | CLR相应内存机制 | GC按根可达性回收 | 无需手工free/delete；仍须避免无意长持有，若另有业务清理协议则按协议 |
| native资源 | Win32返回的句柄、AllocHGlobal内存；IntPtr是其载体 | 对应OS/本机库/分配器 | 拥有者调用匹配释放，或交给正确SafeHandle | 按取得、转移、借用合同，不因任何IntPtr都调用CloseHandle |
| 混合包装 | FileStream、Bitmap | 托管壳及相应native API | GC管内存，拥有者/封装管资源 | 拥有且需关闭时Dispose/using；借用者不能任意关闭他人资源 |

<a id="c20-collect-contract"></a>
## 无参GC.Collect强制即时全代收集，却不是delete某个对象

用户问能否硬要手动释放托管资源。C#没有对普通托管对象执行C++式delete的关键字，Dispose也不把它占的托管内存立刻清零、返OS。C/C++的malloc/free、new/delete同样按其分配器和对象寿命合同工作，不等每次都直接向OS申请/立即返还一个页面。

原1,000,000字节例保留：

```csharp
var obj = new byte[1000000]; // 分配一个大对象
obj = null;                  // 解除引用
GC.Collect();                // <-- 试图强制回收
```

其中无参Collect的合同是**强制即时对所有代进行阻塞垃圾收集**，原“只是请求、GC不一定立刻执行”错误。它仍不是只回收obj、强制销毁仍可达对象、安全擦除或保证OS立即还页；也不等所有终结已经执行完。带GCCollectionMode.Optimized等参数、nonblocking重载应按各自合同解释，不能冒充这个无参调用。[GC.Collect各重载合同](https://learn.microsoft.com/en-us/dotnet/api/system.gc.collect?view=net-10.0)

原“餐厅碗不能自己冲进厨房砸/只能按铃叫服务员”类比用于区分任意破坏对象内存与调用受支持GC API；“服务员可以不来/觉得不划算就无限延期”不适用于该无参Collect。诱导全代收集可能增加暂停/CPU成本、扰动自然调度，不能无基准说一定造成多少损失或只有测试/profiling法律式允许。通常按证据评估需求，而非每次业务结束就强行全代收集。

<a id="c20-cycle-roots"></a>
### A/B互相引用可否回收，要看从根是否可达

原字段循环形状完整保留；其注释里的“根变量可达”应当有真实活根，而不是单凭变量词法作用域：

```csharp
public class A {
    public B b;
}
public class B {
    public A a;
}

A a = new A();
B b = new B();
a.b = b;
b.a = a;

// 即使你在这里 GC.Collect();
// a 和 b 都不会被回收，因为它们互相引用（形成了环），
// 但在 GC 的“可达性分析”中，它们都从根引用（a, b 变量）可达。
```

GC按可达性工作，环本身不阻止回收。补充受控程序保留这两个字段和赋值：检查后调用KeepAlive(a)/KeepAlive(b)，检查时两个weak均true；NoInlining方法构造同样循环后仅返回两个weak，受控Collect后两个均false。真实输出ROOTED=True/True、UNROOTED=False/False；这支持根与环的区别，不保证任何局部变量在整段作用域内都活着。

普通托管引用不能在对象仍被当前代码合法持有时被GC随意删除。没有在本章反射调用假内部删除API、提前free托管对象或触发AV。终结登记、待终结、复活及后续回收分阶段，不能说任何对象只要发现终结器就必于下一次GC回收；共享受控终结/短长weak协议确有复活后仍存活的不同观察，但不代表所有调度。[共享GC句柄与终结器真实证据](整理记录/核验与验收/共享-GC句柄与终结器核验.md)

<a id="c20-dispose-not-delete"></a>
### Dispose不删除对象，也不只用于native资源

原a.txt流例仍保留，GC与Dispose两责任的正确区别可用：

```csharp
using (var fs = new FileStream("a.txt", FileMode.Open))
{
    // 使用 fs
} // 这里调用的是 Dispose()，它关闭了文件句柄（非托管），
  // 但 fs 这个对象本身占用的内存（托管），并没有被释放！
  // fs 对象的内存要等到 GC 下次运行才会回收。
```

调用Dispose后，若代码还有真实可达引用，包装对象占的内存仍活着；它可能已经拒绝业务操作。何时随后回收由根与GC决定，而不是“下次GC无条件回收”。Dispose用于结束拥有的可处置资源生命周期，也可清理托管订阅、归还池中的对象等，不能说它唯一目的是非托管资源。清理若解除某些强引用，可能间接改变可达图，但不是直接free托管对象。

源另作一个假想：若强行释放仍有终结器的对象，可能漏清理资源、在错误时机清理，或使仍访问它的其他线程受损。这里保留该假设的风险意图；受支持的C#没有delete普通托管对象的API，不能把这些假想后果说成某个合法API的固定行为，也不能把Dispose当作此种强行释放。

原ClearCache片段：

```csharp
public void ClearCache()
{
    this._largeList = null; // 告诉 GC：这个大对象我不用了
    this._connection = null;
}
```

置空字段解除该持有关系，不意味着只有这个引用或立即回收。若_connection是本对象拥有的IDisposable连接，应按合同先适当清理/归还再丢引用，不能用null代替清理；若是借用者则按拥有者合同处理。

原字段缓存与局部缓存是**两个替代方案**，不能把两个Process直接放在同一类里当一个可编译程序：

```csharp
// 不好的写法：对象存活时间长
private List<int> _cache = new List<int>();

public void Process()
{
    _cache.Add(1);
    // ... 只用一次，但 _cache 因为是字段，会一直存活
}

// 好的写法：对象存活时间短
public void Process()
{
    List<int> cache = new List<int>(); // 局部变量
    cache.Add(1);
} // 方法结束，cache 立刻变成垃圾，GC 很容易回收（通常在 Gen 0）
```

字段_cache在其拥有者仍可达且字段未清时会继续持有List。局部的最后使用、JIT根寿命和是否逃逸影响可达性，词法作用域短不保证“方法结束立刻成垃圾”；减少不必要分配或长持有是设计选择，不自动让GC工作量降低固定比例。

### 保留1,000,000字节WeakReference缓存的原模式变量例

```csharp

else
```

| 想法 | 实际条件 | 对应做法 |
| --- | --- | --- |

| 手动调用GC | 无参Collect强制即时阻塞全代收集；可能有性能成本，不是所有场景必有害 | 有实证需求时按重载合同评估，避免无依据高频调用 |

| 帮助GC | 解除不必要长持有/减少分配可改变可达图；作用域不是精确根保证 | 正确字段/引用设计并实测，不以置null承诺立即回收或代替资源清理 |

原“黑盒/白盒”“脏衣服”“翻译官/传声筒”类比保留：公开路径使文件成为协定的一部分，翻译不能把可理解的文件失败改成误导的姓名失败；它并不让整个PhoneBook内部算法都变成完全公开白盒，也不把所有错误转换都叫欺骗。

## 同一个Worker通过默认反射和dynamic调用

原public Worker、具体InvalidOperationException和“数据库连接超时！”保留；这里是主动抛出的演示，没有实际数据库连接：

```csharp
public class Worker
{
    public void ThrowSpecificException()
    {
        // 注意：这是一个非常具体的异常类型
        throw new InvalidOperationException("数据库连接超时！");
    }

```

<a id="c20-reflection-original"></a>
### 原ReflectionTest完整Main

```csharp
using System.Reflection;

public class ReflectionTest
{
    public static void Main()
    {
        Worker worker = new Worker();
        MethodInfo method = typeof(Worker).GetMethod("ThrowSpecificException");

        try
        {
            // 使用反射调用
            method.Invoke(worker, null);
        }
        catch (Exception ex)
        {
            Console.WriteLine($"捕获到的异常类型: {ex.GetType().FullName}");
            Console.WriteLine($"异常消息: {ex.Message}");
            
            // 我们需要挖地三尺才能找到真正的异常
            if (ex.InnerException != null)
            {
                Console.WriteLine($"内部异常类型: {ex.InnerException.GetType().FullName}");
                Console.WriteLine($"内部异常消息: {ex.InnerException.Message}");
            }
        }
    }
}
```

它需要前面的Worker及System上下文，GetMethod拿到本例公开无参方法，默认Invoke把**目标方法执行时抛出的异常**包进TargetInvocationException。原输出示意保留：

```text
捕获到的异常类型: System.Reflection.TargetInvocationException
异常消息: Exception has been thrown by the target of an invocation.
内部异常类型: System.InvalidOperationException
内部异常消息: 数据库连接超时！
```

本机Framework实际第二行是“异常消息: 调用的目标发生了异常。”，.NET10为原示意英文；类型、内层类型及原中文业务消息均一致。异常Message会随资源语言/实现变化，不能强求所有运行环境英文逐字一样。

“为了隔离执行环境所以必须插层”“反射伪造堆栈”不是该API的完整规范解释；外层和内层本来代表不同抛出对象的轨迹。Inner对象保存了目标失败，默认ToString可显示它，不是全信息损毁。[MethodBase.Invoke合同及各异常条件](https://learn.microsoft.com/en-us/dotnet/api/system.reflection.methodbase.invoke?view=net-10.0)

<a id="c20-invocation-flow"></a>
### 两个调用流程图的原结构分别保留

默认反射目标执行异常的流程：

```text
你的代码
  ↓ 调用
MethodInfo.Invoke()
  ↓ 默认Invoke处理目标方法抛出的异常（不是所有调用失败）
TargetInvocationException (新异常)
  └── InnerException: InvalidOperationException (原始异常)
  ↓ 抛出
你的 Catch 块
```

本例普通Worker的动态成员调用流程：

```text
你的代码
  ↓ 调用
Dynamic 调用站点 (运行时绑定)
  ↓ 绑定到本例普通public Worker成员
Worker.ThrowSpecificException()
  ↓ 抛出
InvalidOperationException (原始异常)
  ↓ 直通
你的 Catch 块
```

动态调用有编译器生成的调用站点和运行时绑定/缓存机制，不能只叫MethodInfo.Invoke的语法糖，也不从这张示意图推所有JIT步骤或固定性能优势。需要程序集元数据、非公开成员扫描等功能时仍有反射的不同用途；动态调用运行时才判相应绑定，不能当作全面消除类型检查错误的方案。

<a id="c20-invoke-failure-kinds"></a>
### 参数错误、目标错误和运行时绑定错误是不同失败

受控补充保原Worker后分别改变调用条件，真实输出均有：

```text
BAD_PARAMS=TargetParameterCountException/TIE=False
BAD_TARGET=TargetException/TIE=False
BAD_BINDER=RuntimeBinderException/TIE=False
```

默认Invoke并非把任何参数、对象、绑定错误都包装。现代.NET10还能按适用的DoNotWrapExceptions调用选项直接得到原InvalidOperationException；本机Framework4.8枚举没有该选项，不能倒填进第四版4.5场景。新选项是补充，两个原Main仍完整保留。[原两程序及边界实际输出](整理记录/验证工作区/第20章/包装反射与宿主边界/结果.json)

原“解包”文字中给出的片段也保留为会重置内层轨迹的反例：

```csharp
catch (TargetInvocationException tex)
{
    throw tex.InnerException;
}
```

它是对那个内层对象进行新的throw，不能声称只去一层壳便自然保全原抛出信息。需要跨捕获边界重发时，可按已核EDI合同使用Capture(...).Throw；如果只在当前catch继续同一正在传播的外层异常，用裸throw才是另一目的。Inner是否存在、要传播哪一层也须按自己的合同检查。

原“雇翻译去吵架/问到底骂了什么”与“自己直接去吵架”类比表达默认包装与目标异常直接传播的区别，不等于反射不可能提供完整原信息或dynamic不会有其他失败。原CER预告的20.8编号和“绝对执行异常抛出”说法仍按20.12及真实历史准备/契约纠正。

<a id="c20-host-exception-models"></a>
## 未处理异常需放在具体应用模型中理解

用户给出八段应用模型入口，不能因为源最后补了现代对照就丢掉第四版历史入口。原“总闸/分闸”“CLR统一地基/框架自建楼层”“泼冷水”类比表达框架可能先处理其调度/请求范围的异常，不是必由整个AppDomain物理边界拦截，也不代表同一个异常会依次经过所有模型钩子。

原已处理片段：

```csharp
try {
    Dangerous();
}
catch (Exception e) {
    Log(e);  // 抓到了 → 已处理
}
```

若Dangerous的异常到达此catch且Log正常返回，当前异常被处理；Log自身失败是另一个传播问题。Task把异常储存等待观察与线程上真正未处理不是同一状态，框架可能捕获请求/调度异常后再发事件。

保留原四层表及其范围：

| 层级 | 观察范围 | 原例入口 |
| --- | --- | --- |
| CLR/AppDomain通知 | 未找到适用处理器的线程异常；常涉及进程终止政策 | AppDomain.UnhandledException，不是Handled恢复按钮 |
| UI框架 | 框架拥有的UI线程/相应Dispatcher调度 | WPF DispatcherUnhandledException等，不是所有后台线程异常 |
| Web框架 | 相应请求处理错误 | 旧ASP.NET HttpApplication.Error等，不等任何进程故障都请求隔离 |
| 服务框架 | 通道/调用及fault处理合同 | WCF IErrorHandler及ChannelDispatcher.ErrorHandlers |

<a id="c20-appdomain-hook"></a>
### AppDomain.UnhandledException是通知，不是一般catch

原crash.log注册片段保留：

```csharp
AppDomain.CurrentDomain.UnhandledException += (s, e) =>
{
    var ex = (Exception)e.ExceptionObject;
    File.WriteAllText("crash.log", ex.ToString());
};
```

这是需要合适System.IO上下文和日志路径/权限的片段，本章没有制造真正未处理异常或写crash.log。该事件没有一个“Handled=true”让通常终止路径转成恢复的合同；IsTerminating、版本、宿主与事件是否有机会触发要分条件，不能宣称所有模型/所有严重错误都必产生一次最后日志。处理时可能仍持有抛出处锁，记录也可失败，不能把任意保存业务状态视作自动安全恢复。[AppDomain通知合同](https://learn.microsoft.com/en-us/dotnet/api/system.appdomain.unhandledexception?view=netframework-4.8.1)

<a id="c20-winforms-hook"></a>
### WinForms的NativeWindow虚方法、Application静态方法与事件不同

原U列NativeWindow.OnThreadException与Application.OnThreadException都是“虚方法”。真实NativeWindow前者是protected virtual；后者是**public static void OnThreadException(Exception)**，它用于引发ThreadException，不能重写成实例虚方法。Framework4.8和本机桌面.NET10均真实反射确认：Application是sealed类（非abstract）、OnThreadException为public/static/nonvirtual。不能把它误写成类型声明C#static，也不能说这个方法不存在或仅internal。[NativeWindow方法](https://learn.microsoft.com/en-us/dotnet/api/system.windows.forms.nativewindow.onthreadexception?view=windowsdesktop-10.0)、[Application方法](https://learn.microsoft.com/en-us/dotnet/api/system.windows.forms.application.onthreadexception?view=windowsdesktop-10.0)

原WinForms事件注册及模式设置：

```csharp
Application.ThreadException += (s, e) =>
{
    MessageBox.Show($"出错了：{e.Exception.Message}");
    // 这里可以"吞掉"，进程不崩！
};

// 还要配合这个（否则 UI 线程外的未处理异常还是会走 AppDomain）
Application.SetUnhandledExceptionMode(UnhandledExceptionMode.CatchException);
```

它属于WinForms项目的Application，不是WPF同名类。SetUnhandledExceptionMode控制相应WinForms线程异常的处理模式，需按初始化时机/配置使用，不让所有后台线程也被ThreadException兜住。此事件参数是ThreadExceptionEventArgs，**没有Handled属性**；原后文把WPF的e.Handled套过来错误，真实静态反例CS1061。框架处理后继续不等共享状态已安全恢复。[WinForms线程异常适用范围](https://learn.microsoft.com/en-us/dotnet/api/system.windows.forms.application.threadexception?view=windowsdesktop-10.0)

<a id="c20-wpf-hook"></a>
### WPF的Handled与Filter.RequestCatch不能混用

原Application.Current事件片段：

```csharp
Application.Current.DispatcherUnhandledException += (s, e) =>
{
    Log(e.Exception);
    e.Handled = true;  // 设为 true 可以阻止进程崩
};
```

这里是System.Windows.Application的DispatcherUnhandledException；它对适用的UI调度异常可通过e.Handled标记处理，不会自动捕获所有其他Dispatcher/后台线程或任意崩溃。

原U另外列System.Windows.Threading.Dispatcher.UnhandledException和UnhandledExceptionFilter也保留。Filter是**返回void的事件处理器**，通过DispatcherUnhandledExceptionFilterEventArgs.RequestCatch影响后续：RequestCatch=false才使Dispatcher.UnhandledException不被引发，不是“返回true短路后处理”。元数据双环境均Void/Boolean可写；旧csc把return true放进该处理器真实CS0127及CS1662，初次预猜CS8030的记录保留，没修改真实输出或重跑。[WPF Filter合同](https://learn.microsoft.com/en-us/dotnet/api/system.windows.threading.dispatcher.unhandledexceptionfilter?view=windowsdesktop-10.0)

这些核验只查API形状与静态反例，没有开窗口、消息循环或实际Dispatcher事件顺序实验；事件流合同来自所引用一手文档。[两环境UI形状与原预设留痕](整理记录/验证工作区/第20章/包装反射与宿主边界/UI精确结果.json)

<a id="c20-web-wcf-hooks"></a>
### 旧Web Forms与WCF的原片段

原两个Web Forms方法分别保留，前者需Page/Server上下文，后者需Global.asax/HttpApplication上下文，不能把两个受保护方法随意合进一个空类：

```csharp
// Page 级别
protected void Page_Error(object sender, EventArgs e)
{
    var ex = Server.GetLastError();
    Server.ClearError(); // 可以"消掉"异常
}

// Application 级别（Global.asax）
```

用户列TemplateControl.Error、其Page和UserControl派生背景、HttpApplication.Error仍保留。Server.GetLastError取得相应错误，ClearError按请求错误处理合同清除该错误状态，不是修复底层业务、消灭对象或承诺任何请求故障永不影响进程。

原WCF类型是**省略ProvideFault签名/方法体的伪代码**：

```csharp
// 实现 IErrorHandler 挂到 ChannelDispatcher.ErrorHandlers
public class MyErrorHandler : IErrorHandler
{
    public bool HandleError(Exception error) => true; // 返回 true = 标记为"已处理"

}
```

它需实现IErrorHandler并添加到ChannelDispatcher.ErrorHandlers；真实ProvideFault签名接受Exception、MessageVersion与ref Message，HandleError返回Boolean按dispatcher session/instance context等相应条件解释，不能仅由true推所有错误完全恢复。ProvideFault决定返回fault，错误记录/其他收尾是相应职责，框架回调线程也有条件。[WCF IErrorHandler合同](https://learn.microsoft.com/en-us/dotnet/api/system.servicemodel.dispatcher.ierrorhandler?view=netframework-4.8.1)

<a id="c20-unobserved-task-hook"></a>
### Task未观察异常是另一条保存/升级路径

原注册片段保留，Log需调用方实现：

```csharp
// .NET Core/5+ 里，后台 Task 未观察异常
TaskScheduler.UnobservedTaskException += (s, e) =>
{
    Log(e.Exception);
    e.SetObserved(); // 标记为已观察，防止进程崩（.NET 5+ 默认也不会崩了，但会触发这事件）

```

其注释“5+默认也不会崩”所述默认不终止不是从5才开始；Framework4.5已改变默认Task未观察异常政策，事件仍可被引发，相应旧配置还能选择严格升级。已观察的失败Task不会仅因为它失败就必触发这个事件，事件也不是立即/每个Task一份统一crash通知；await/Wait等传播与观察的具体差别另见后续Task章。

这里没有运行会升级成真正未处理崩溃的Task实验；本机Framework元数据已存在事件，年代及政策由.NET4.5官方说明核证。异常“消失”时先查实际调用路径/线程/请求与是否被观察，而不是断言必由某个e.Handled吞掉。[.NET4到4.5的Task异常政策](https://devblogs.microsoft.com/dotnet/task-exception-handling-in-net-4-5/)

<a id="c20-cse-history"></a>
## 损坏状态异常的历史默认策略与边界

用户引用“本机某些异常被CLR认为是CSE，默认不交付托管catch/finally”的段落。这讨论的是严重native/runtime事件及版本/宿主政策，不能仅凭一个Exception类名或任何native throw判断进程已损坏。原“硬性熔断/放弃治疗”“普通异常软忽略”比喻说明不能把严重故障当普通业务失败吞掉，不是每次故障都已证明所有托管对象的每个字段损坏。

保留源表四个状态与原未展开的省略行，不补造省略成来源中的完整清单：

| 原Win32/NT状态 | 含义 | 原典型背景及限制 |
| --- | --- | --- |
| STATUS_ACCESS_VIOLATION | 不能完成相应内存访问 | 无效/无访问权指针可能表明严重错误，不能由此证明所有内存均已被践踏 |
| STATUS_STACK_OVERFLOW | 栈不能再按需要增长 | 无限递归可能导致，真实栈溢出与主动new同名异常对象不同 |
| STATUS_GUARD_PAGE_VIOLATION | 访问带PAGE_GUARD的页面触发一次性警报 | 保护页也用于合法监测/栈增长，不等保护机制必被破坏；需看是否被底层正确处理及实际运行时政策 |
| STATUS_IN_PAGE_ERROR | 页所需数据因底层I/O错误不能置入内存 | 原硬盘坏道/网络断开是可能背景，不把每个普通文件IOException都当CSE |
| ... | 原回答没有展开 | 不宣称此四行已完整列出CLR所有版本特殊状态 |

## 性能先分正常路径与失败路径，再比较具体设计

<a id="c20-error-return-original"></a>

用户引用20.11比较异常、HRESULT和特殊返回码的段落。少写逐层传递失败码、减少遗漏和保留成功返回值的表达力，是原书支持异常机制的工程理由；不能把“很难看出差异”改成仅凭99.9%成功就证明所有程序中异常必更快。

原Main→MethodA→MethodB返回码例完整保留，error状态未在片段声明：

```csharp
public int MethodB() {
    // 做一些事
    if (error) return -1; // HRESULT 错误码
    return 0; // S_OK
}

public int MethodA() {
    int hr = MethodB();
    if (hr != 0) return hr; // 必须检查！否则错误就丢了
    
    // 继续做其他事
    return 0;
}

public void Main() {
    int hr = MethodA();
    if (hr != 0) {
        // 处理错误
    }
}
```

这里-1/0可以是**自定义特殊返回码**，但不能把任何HRESULT都当hr!=0即失败。HRESULT按高位严重性判断，S_OK=0，而S_FALSE=1等正非零状态仍表示成功；以有符号Int32读取，通常FAILED对应hr<0，SUCCEEDED对应hr>=0。[HRESULT成功/失败判定](https://learn.microsoft.com/en-us/windows/win32/com/using-macros-for-error-handling)

受控补充用0/1/-1，两个环境都实际观察：1的NONZERO=True但FAILED=False、GetExceptionForHR结果none；-1的FAILED=True并得到COMException。这里只验证码判定/托管映射，没有实际COM组件调用。原重复传播短片段另保留：

```csharp
int hr = MethodB();
if (hr != 0) return hr; // 把错误码“漏回去
```

它表达检查失败后继续把结果传回更外层，不是安全信息“泄漏”。有失败返回值就须按接口正确消费，不能以“异常优选”为由忽略API已有状态码。返回码设计还能结合out业务数据、专门Result类型等补充方案，不是所有API必只能返回int、永远无法提供User或Order。

```csharp
} // 离开作用域，没有任何析构函数被自动调用！
```

离开作用域不会像上述C++自动局部对象那样立即调这几个对象的C#终结器，也不会仅因为类型实现IDisposable就自动Dispose。GC管对象内存不等取得的其他资源自动在正确时刻结束；是否有finally/using清理是源必须明确的另一个程序条件。

补仅日志/IDisposable的四托管夹具，第三ctor普通失败后原方法Disposed=0。另写**补充**嵌套using取得同样四对象的形状，第三ctor失败时已经取得的Crane/Excavator各Dispose一次，总2；没有native资源或终结器时机实验。[C#原形状与补充using实证](整理记录/验证工作区/第20章/性能例与CER普通路径/结果.json)

保留原五项对比维度并删除性能绝对排序：

| 特性 | 原C++自动对象/RAII例 | 原C#GC/IDisposable思路 |
| --- | --- | --- |
| 核心机制 | 按已完成构造及存储期调用析构，资源实际效果依实现 | GC管理托管内存；拥有的可处置资源按明确Dispose/using合同 |

| 簿记成本 | 需表示有效清理状态，具体表示/优化依ABI与实现 | 没有同样的自动局部析构要求，但using/finally仍有有效资源与清理结构 |
| 性能影响 | 有EH/清理代码与相关成本，不保证固定大或慢 | GC/EH/资源清理与JIT优化各有成本，不保证固定小或快 |

<a id="c20-appdomain-history"></a>
## AppDomain的历史逻辑隔离不是每域一个OS进程或私有GC堆

用户问AppDomain是什么。Framework中应用域是进程内的加载、类型/静态状态、配置、信任与卸载等逻辑边界；跨域对象通常经复制或MarshalByRef代理，线程可以跨域执行，不是每域一个独立线程或OS地址空间。域的loader heaps与承载对象的GC堆也不是同一个概念。[Framework应用域隔离/加载说明](https://learn.microsoft.com/en-us/dotnet/framework/app-domains/application-domains)

保留原进程/应用域五项对比：

| 概念 | OS进程 | Framework AppDomain |
| --- | --- | --- |
| 隔离单位 | 独立进程地址空间等OS边界 | 同一进程中的CLR逻辑隔离/加载/卸载边界 |
| 内存隔离 | 进程相对的虚拟地址空间；仍可显式共享内存/外部资源 | 不能普通直接跨域对象引用，依类型安全/复制/代理等；不是每域独立物理GC对象堆或可靠防native破坏的OS边界 |
| 通信成本 | IPC/网络等按方案 | 跨域代理/复制成本，不同于同域普通调用；不固定永远低 |
| 创建成本 | 依平台、载入内容/实际测量 | 常避免另启OS进程的一些成本，原“必MB对KB”无通用数值合同 |
| 崩溃影响 | 独立地址空间减少直接内存互害，外部依赖仍可相互影响 | 可按可信宿主政策隔离某些失败；进程级CSE/默认真正未处理等仍可能终止整个进程 |

原三自有项中，类型静态数据通常按域隔离、程序集加载/配置/上下文保留；“每域自己的托管堆”改为该域关联对象及可达关系由进程GC体系管理，不能与loader heaps混同。[历史CLR的loader heaps与GC heaps区别](https://learn.microsoft.com/en-us/archive/msdn-magazine/2005/may/net-framework-internals-how-the-clr-creates-runtime-objects)

原ASP.NET每应用域的历史、主程序+插件域隔离场景保留，插件严重破坏不保证主进程永不死。SQL Server不是每个存储过程/程序集各一域；官方CLR集成按database+owner组织，同域可有多个程序集，域缓存复用。[SQL CLR域分组](https://learn.microsoft.com/en-us/sql/relational-databases/system-dynamic-management-objects/sys-dm-clr-appdomains-transact-sql)

原“进程里的子房间”类比解释逻辑隔离；房间共处一栋楼时不能据此隔绝进程整体损坏，创建成本也不能由房间大小比喻算出来。

### 原Unload两个片段，现代已不支持，ALC不发Abort

原短调用：

```csharp
AppDomain.Unload(domain);
```

原主域调用插件域片段：

```csharp
// 主域
AppDomain.Unload(pluginDomain); // CLR 对 pluginDomain 里所有线程 Inject ThreadAbort
```

这都是需要真实domain变量、正确历史宿主政策的片段。Framework卸域涉及使在域中执行的线程离开/中止，普通与宿主升级的rude策略、native代码/受保护区域及卸载失败不同；不能说任何线程任意IL处立即被掐断或回收一个域专有的物理GC堆。现代.NET只有默认域，不支持新建/卸载这种AppDomain，不能说“仍在只是没那么常用”。本机现代CreateDomain实际PlatformNotSupportedException，Unload实际CannotUnloadAppDomainException，编译SYSLIB0024；没有运行真实Framework卸域或Abort。[Unload的版本合同](https://learn.microsoft.com/en-us/dotnet/api/system.appdomain.unload?view=net-10.0)

现代collectible AssemblyLoadContext供加载/协作卸载一组程序集，不提供AppDomain同等的权限隔离，也不发起Thread.Abort。卸载完成需要没有相关方法仍在活动线程栈上、没有规定之外的强引用/GCHandle等；Unload只是发起。[ALC协作卸载条件](https://learn.microsoft.com/en-us/dotnet/standard/assembly/unloadability)

明确补充仅自身新ALC加载自己的小DLL、后台线程已经进入被载方法：Unload通知True，请求后thread仍Alive=True、Done=False；随后自己的stop信号正常结束、Done=True/Join=True。所有等待有5/10秒界限与finallyStop；没有卸载用户程序集/线程中止，也没在还留强metadata局部引用时声称GC卸载已完成。[自有ALC合作实证](整理记录/验证工作区/第20章/ALC合作卸载/结果.json)

<a id="c20-cer-hidden-operations"></a>
## CER对准备和用户代码都施加条件

原把空try/finally称“穷人版CER”、Prepare机制称“官方版”，类比用于联系清理保护目的；普通Abort延期并不等已成为CER，准备仍要契约/受限清理配合。

原再次Account两步finally片段保留，依然不是原子转账：

```csharp
public static void Transfer(Account from, Account to, decimal amount)
{
    try { }
    finally
    {
        from -= amount;
        // CER 要保的就是这行：哪怕 Thread.Abort / AppDomain.Unload，
        // 这行也必须跑完，不能只跑一半
        to += amount;
    }
}
```

普通abort延期不消除to+=自身同步失败、运算符/参数语义或外部状态；前文已实际检验90/100与局部重绑定。原“finally一开始就绝对完成”的说法不能扩展到所有同步失败和宿主强制终止。

原ReleaseCriticalResource第一次调用的不同风险片段：

```csharp
try
{
    // 干点事
}
finally
{
    // 这一行代码还没 JIT 过！
    ReleaseCriticalResource(); // 释放非托管锁
}
```

finally属于所在方法的EH区域，不应画成每次进入块才给这个块独立JIT。被调ReleaseCriticalResource及其依赖的代码/类型准备、加载等可能有首次使用成本或失败；其发生阶段按调用与实现区分，不把JIT本身、类型初始化、程序集解析全叫同一个异步事件。

原SomeType.StaticField另一失败点：

```csharp
try
{
    // 第一次调用这个方法
}
finally
{
    // 静态构造器还没跑！
    SomeType.StaticField = 0; // 访问静态字段会触发 SomeType 的 .cctor
}
```

访问需初始化的类型可触发.cctor，失败后针对该已加载类型身份通常再次触发TypeInitializationException，元数据等操作仍可，不是所有操作“永久消失”。失败会打断后面的清理工作，但finally已经执行到哪与类型初始化失败在哪要分清。

原“没JIT/没cctor/没加载三宗罪”是准备相关的风险清单，不是只补这三项就证明任意用户清理成功；已准备方法还能主动throw、取得锁/分配、同步I/O失败或违反所有权。

### 原标准模板先修拼写，再满足实际历史合同

原R-reliabilityContract模板保留为**编译反例**：

```csharp
using System.Runtime.CompilerServices;

[R-reliabilityContract(Consistency.WillNotCorruptState, Cer.Success)]
void CriticalCleanup()
{
    // 这个方法承诺：不会破坏状态，且一定能成功
    ReleaseLock();
}

void Transfer()
{
    // 关键：PrepareConstrainedRegions 必须在 try 之前调用
    RuntimeHelpers.PrepareConstrainedRegions();
    
    try
    {
        // 业务逻辑
    }
    finally
    {
        CriticalCleanup(); // 这个 finally 现在是 CER
    }
}
```

真实两环境CS1003，不能用有“-”的这个名字直接写C#。正确历史双参特性是`ReliabilityContract(Consistency.WillNotCorruptState, Cer.Success)`，并需System.Runtime.ConstrainedExecution上下文。PrepareConstrainedRegions在IL上紧接try，允许NOP而不能插任意操作；其关联catch/finally/fault被标为CER，try业务体不因此受同一准备/约束。[PrepareConstrainedRegions合同](https://learn.microsoft.com/en-us/dotnet/api/system.runtime.compilerservices.runtimehelpers.prepareconstrainedregions?view=net-10.0)

原预JIT说明注释形状仍保留，不是可运行完整程序：

```csharp
// 还没进 try，CLR 就已经把：
// CriticalCleanup() 的 IL → 本地代码 编译好了
// finally 块本身的 IL → 本地代码 编译好了
```

Framework机制提前准备顶层及可静态发现、满足可靠性契约的调用图，目标不明的虚调用/接口/反射/委托不能一概自动找齐，必要显式准备也有自己的合同。强可靠性契约是实现承诺而不是让CLR把错误代码改对；CER内分配、装箱、取锁、调用未准备/弱契约代码都需按约束避免或明确处理失败。不能说自动扫描所有用到的字段类型/基类并执行一切cctor，加载全部未来程序集，更不能“因此以后不再有任何OOM”。[CER机制与约束](https://learn.microsoft.com/en-us/dotnet/framework/performance/constrained-execution-regions)

补充简单可静态发现的强契约Cleanup，以整数记cctor/try/finally/cleanup先后不在区域内打印/分配：Framework实际1/2/3/4，.NET10实际3/1/2/4；现代SYSLIB0004且Prepare方法是空实现。这个局部图不证明任何未来动态目标都已准备。[.NET10 RuntimeHelpers实现](https://raw.githubusercontent.com/dotnet/runtime/v10.0.0/src/libraries/System.Private.CoreLib/src/System/Runtime/CompilerServices/RuntimeHelpers.cs)

另故意给会主动throw的清理方法贴Cer.Success作为**违反承诺的补充反例**，两个环境都真实抛controlled cleanup failure并取代原对象传播。不是符合强可靠性合同的代码自己被CLR莫名破坏；它说明属性本身不能修复同步错误，前面原SafeHandle Release日志也不能因属性字样便绝对安全。

<a id="c20-plugin-lock-original"></a>
### 原Plugin先取得native锁，再准备/进入try，存在保护窗口

原被称为完整的Plugin形状，实际仍缺取得_globalLock、NativeMethods和ProcessData实现，保为**类型片段**：

```csharp
// 跑在插件 AppDomain 里
public class Plugin : MarshalByRefObject
{
    private IntPtr _globalLock; // 全局非托管锁

    [ReliabilityContract(Consistency.WillNotCorruptState, Cer.Success)]
    private void ReleaseLock()
    {
        NativeMethods.ReleaseMutex(_globalLock);
    }

    public void DoWork()
    {
        // 获取锁
        NativeMethods.WaitForSingleObject(_globalLock);

        RuntimeHelpers.PrepareConstrainedRegions();
        try
        {
            // 业务代码，可能抛异常，也可能域被卸载
            ProcessData();
        }
        finally
        {
            // CER 保证：这行一定能跑，锁一定释放
            ReleaseLock();
        }
    }
}
```

WaitForSingleObject真实取得锁后，保护try尚未覆盖随后的prepare/进入区域步骤；该时段的失败/中止可能没有到达关联finally。不能仅看随后存在Prepare便断言所有取得/准备失败都一定Release。实际CLR可能把部分准备尽早完成，不能谎称本章已实测该锁下的特定JIT/OOM失败；这里依据代码保护边界及准备适用合同指出缺口。可靠实现需明确取得成功、所有权与保护覆盖，不能调用未初始化的IntPtr或假native方法来“验证”锁必泄漏。

原“域卸载→finally→CERRelease必成功”“不用CER便永久锁/主程序必死锁”是特定历史风险说明，不是每次发生的事实；ReleaseMutex返回结果/真实锁协议和准备本身都仍需合同。没有运行本例假native锁、ThreadAbort或真实域卸载。

<a id="c20-guaranteed-cleanup-original"></a>
### ExecuteCodeWithGuaranteedCleanup的另一个原形状

```csharp
RuntimeHelpers.ExecuteCodeWithGuaranteedCleanup(
    // 主代码（可能抛/被中止）
    (state) => { ProcessData(); },
    // 清理代码（CER 保证执行）
    (state, exception) => { ReleaseLock(); },
    null);
```

它有TryCode、CleanupCode与用户状态三参数，cleanup的第二参数是是否有异常导致退出的Boolean，**不是Exception对象**。历史机制为特定回退/栈情形提供另一执行方式，主业务代码不自动成为更强CER；清理目标仍需适当可靠性/提前准备与栈需求约束，不能把两个未标记匿名lambda当所有stackoverflow都100%成功的范本。[历史可靠性与栈条件说明](https://learn.microsoft.com/en-us/archive/msdn-magazine/2007/december/clr-inside-out-writing-reliable-net-code)

本机两个环境普通成功TryCode/BackoutFlag=False、普通抛出TryCode/BackoutFlag=True，原异常同身份向外；现代实现只是普通try/finally兼容形状、仍有SYSLIB0004，不支持旧CER保证。没有真实栈溢出/中止实验，不用这两次普通结果证明最恶劣情况下必执行。[CER普通路径实证](整理记录/验证工作区/第20章/性能例与CER普通路径/结果.json)

SafeHandle关键终结/所有权机制在现代仍有意义，不能说“我们每天消费的FileStream/Mutex/Semaphore全部底层都在现代CER里”。历史源码出现ReliabilityContract、Prepare调用不等API在现代有同一功能；单参Cer.Success同样是前文已真负编的错误形式。

## 代码协定把前置、后置与不变式声明出来，工具支持须按历史条件

用户继续问20.13。代码协定把“id不能为空”“返回数组长度至少1”“对象结束某生命周期时连接须关闭”等假设写明，便于文档、工具分析/验证；并不自动将所有假设归为同一种不变式或把所有程序错误证明消失。

前置条件是调用者应满足的进入条件，例如除数不零、用户名非空；后置条件描述正常返回时的结果，例如返回值非null/数组长度大于0。对象不变式表达对外可见、按规定检查边界的有效状态，例如Range.Start<=End，不要求每条内部赋值后都已恢复。数据库连接是否处于Opening/Connecting等中间状态要看实际API，不能凭“要么开要么关”禁止其定义的状态。

原“销毁时连接必须关闭”需要生命周期/Dispose等相应协议，Code Contracts的不变式不会自动检查对象finalizer和IDisposable.Dispose；不能指望这句示例便令GC保证先关闭连接。[历史协定机制、检查边界、构建符号](https://learn.microsoft.com/en-us/dotnet/framework/debug-trace-profile/code-contracts)

现代.NET不支持该旧Code Contracts工具机制；部分System.Diagnostics.Contracts API仍在且本机Contract类型未带Obsolete，不等重写器/检查器受到现代工具链支持。NRT、Roslyn分析器及业务验证库能覆盖一些不同问题，不是替代所有前后条件/不变式证明；Rust Result、Swift guard、Kotlin require只是原对比中不同错误/条件表达方式，不能称所有现代语言同一DbC机制。

原“CER最后关头保镖/协定入职前背景调查”“治未病/治已病急救”类比保留，前者历史受约束执行，后者同时包括静态分析、构建文档和**运行时检查/重写**，不是全在代码运行前强制证明成功。

<a id="c20-sqrt-contract-original"></a>
### 原无协定Sqrt与Requires Sqrt是两个不同例子

原普通Sqrt：

```csharp
public double Sqrt(double value)
{
    // 脑子里假设：value >= 0
    // value < 0时Math.Sqrt规定返回NaN；原注释“或者抛异常”不成立
    return Math.Sqrt(value);
}
```

原注释“NaN或者抛异常”已修正：Math.Sqrt负值的规定结果是NaN，不是随机选择抛异常。自己的Sqrt包装若想禁止负数，可明确验证并抛符合接口的异常；文档、分析与运行时行为不是一回事。[Math.Sqrt返回合同](https://learn.microsoft.com/en-us/dotnet/api/system.math.sqrt?view=net-10.0)

原Requires版本：

```csharp
using System.Diagnostics.Contracts;

public double Sqrt(double value)
{
    // 明确声明：调用者必须保证 value >= 0
    Contract.Requires(value >= 0);
    
    return Math.Sqrt(value);
}
```

普通C#编译器认识语法/类型不等自己进行完整协定静态证明；旧额外工具、分析级别、构建/重写配置须正确，分析可能有警告或无法证明的情况，不是一装工具任何Sqrt(-1)都必红线硬拒绝。

多数Contract方法有Conditional("CONTRACTS_FULL")。未定义符号时调用及参数表达式可被编译器消除，不能说“没有静态检查器或关闭它，默认运行时就抛ContractException”。符号、静态检查与运行时重写是不同开关；定义FULL却未经适当重写也不能当已经获得有效检查，直接运行相应stub可能产生要求重写的失败/进程终止路径。[Requires的条件编译及工具要求](https://learn.microsoft.com/en-us/dotnet/api/system.diagnostics.contracts.contract.requires?view=net-10.0)

真实两环境无FULL调用原函数Sqrt(-1)为NaN，没有前置条件异常。本章未安装/运行旧重写器，PATH探测CCRewrite/CCCheck未解析；这不证明机器任何地方绝无旧工具。定义FULL的原库只编译并查看IL，未调用这些未经重写的协定方法或触发Contract FailFast。

<a id="c20-divide-contract-original"></a>
### 原Divide的Ensures应放在方法开头声明段

```csharp
public double Divide(double numerator, double denominator)
{
    Contract.Requires(denominator != 0); // 前置条件

    double result = numerator / denominator;

    // 明确声明：方法结束后，结果必须满足的条件
    Contract.Ensures(Contract.Result<double>() >= 0); 
    // 假设我们只关心非负结果（当然这个例子逻辑上不成立，仅为演示）
    
    return result;
}
```

源自己已说非负结果的业务逻辑仅为演示、并不成立，不能把它重新包装成真实任意Divide都应非负的保证。另一个工具协议问题是Ensures写在result计算之后；历史协定声明须在开头合同段，Requires之后、实际计算前。Contract.Result<double>()是协定用的返回值表达式，不是C#语言关键字；普通未经重写直接调用只不是返回实际结果的魔法。

保持原条件和演示意图，仅修声明位置的历史片段：

```csharp
public double Divide(double numerator, double denominator)
{
    Contract.Requires(denominator != 0);
    Contract.Ensures(Contract.Result<double>() >= 0); // 仍是原演示的强条件
    double result = numerator / denominator;
    return result;
}
```

它还不满足对任意合法参数的非负保证，若业务真要求该结果，必须另设计参数/算法/失败语义；移动声明不是自动证明正确。无FULL原方法实际Divide(-1,1)=-1、Divide(1,0)为正Infinity，浮点除零也不是这里语言自动抛DivideByZeroException。FULL普通编库成功只说明C#语法可接受，不等旧重写器已接受其原错误声明位置。

<a id="c20-range-contract-original"></a>
### 原Range的Invariant要集中在专用标记方法

```csharp
public class Range
{
    private int _start;
    private int _end;

    public Range(int start, int end)
    {
        Contract.Requires(start <= end);
        _start = start;
        _end = end;
        Contract.Invariant(_start <= _end); // 构造函数结束时必须为真
    }

    public void SetStart(int newStart)
    {
        // 方法内部可以改变状态，破坏不变式
        _start = newStart;
        // 但方法结束时，不变式必须恢复
        Contract.Invariant(_start <= _end);
    }

    // 告诉工具：这个对象有一个不变式
    [ContractInvariantMethod]
    private void ObjectInvariant()
    {
        Contract.Invariant(_start <= _end);
    }
}
```

ObjectInvariant的标记及单独Invariant调用意图正确，但ctor/SetStart里直接Contract.Invariant不是该声明协议；应集中在ContractInvariantMethod标记方法，由工具在适用边界插入检查。原SetStart先赋值到非法状态，末尾诊断失败不会自动回滚已修改字段，更不能保证对象生命中的每个瞬间都永不非法。

保持原字段/ctor/SetStart，另给**修正历史片段**，End公开供公共前置条件合法引用；不是声称本机已CCRewrite/静态证明成功：

```csharp
public class Range
{
    private int _start;
    private int _end;
    public int End { get { return _end; } }

    public Range(int start, int end)
    {
        Contract.Requires(start <= end);
        _start = start;
        _end = end;
    }

    public void SetStart(int newStart)
    {
        Contract.Requires(newStart <= End);
        _start = newStart;
    }

    [ContractInvariantMethod]
    private void ObjectInvariant()
    {
        Contract.Invariant(_start <= _end);
    }
}
```

历史工具规则还要求合同表达式纯、前置条件引用的成员至少与方法同样可见；不能在合同表达式里随意更改已有状态。不变式检查有重入等边界规则，并非任何任意时刻/Dispose/终结器全部保证。无FULL原Range(1,5).SetStart(10)实际保持非法字段关系，证实仅写这些API不会默认保护状态。[协定声明顺序、纯度及不变式边界](https://learn.microsoft.com/en-us/dotnet/framework/debug-trace-profile/code-contracts)

<a id="c20-contract-rewriter-original"></a>
### 原Add和重写的逻辑伪代码

原Add契约片段：

```csharp
public int Add(int x, int y)
{
    Contract.Ensures(Contract.Result<int>() == x + y);
    return x + y;
}
```

原重写解释是**逻辑伪代码**，someCondition/ContractException(...)及其类型未给，不当真实可直接编译的重写产物：

```csharp
public int Add(int x, int y)
{
    // 1. 前置条件检查（如果需要运行时检查）
    if (someCondition) throw new ContractException(...);

    int result = x + y;

    // 2. 后置条件检查（这是关键！）
    //    重写器把 Ensures 的检查代码插入到 return 语句之前
    if (result != x + y) 
        throw new ContractException("Ensures failed!");
    
    return result;
}
```

旧运行时重写器处理契约声明、返回值临时量及适用出口检查等，不能说只是给一个return前拼一行if或所有状态破坏被预防。源“C#不支持在return之后执行代码”过强：从try里return，finally可以在该返回路径完成之前运行。本机补充返回7的try/finally实际先打印FINALLY_ON_RETURN=True后RETURN_VALUE=7，支持明确的正常返回清理路径；并非任意return后面的顺序语句可达。

两环境原无FULL的Sqrt/Divide/Add/Range ctor/SetStart/ObjectInvariant六类方法中Contract调用计数都0；FULL库只反射IL分别1/3/2/2/1/1，包含原位置不正确的声明，**未执行**库中的FULL方法，也没证明旧重写/静态检查完成。APIRequires/Ensures/Invariant的真实Conditional均CONTRACTS_FULL，Contract类型Obsolete=False；语法可编译、字面API存在与工具有效是三个不同结论。[原代码及条件/IL/输出实证](整理记录/验证工作区/第20章/代码协定条件与NRT/结果.json)

此夹具初次反射Requires同bool签名未排泛型发生两次普通AmbiguousMatch未处理退出，发生源Math/Contract执行前；原源码/驱动/结果完整保留，随后仅修元数据筛选重编两项。不能把这些失败当协定运行时抛错或nativeCSE，亦没有把旧失败覆盖成成功。

### 原User?的正确guard保留，NRT默认是警告

```csharp
// 现代 C#：启用可空引用类型
public string GetName(User? user) // ? 表示允许 null
{
    // 启用nullable分析后未证明非null通常给警告；显式warnaserror才提升为错误
    if (user == null) throw new ArgumentNullException(nameof(user));
    return user.Name; // 这里编译器知道 user 不为 null
}
```

原代码主动检查null的行为正确，User类需另给，Name的可空/业务合同仍需定义。“编译器强制检查，否则报错”不是默认NRT行为：启用nullable分析后通常是诊断警告，运行时类型和行为不因?本身变成另一个强制非null类型；显式把相关警告视作错误才硬失败。NRT解决特定空状态分析，不承诺任意End>=Start或浮点正结果等业务前后条件。

补User.Name="John"与最小类上下文后原GetName的guard版本编库成功；明确补充去掉guard的反例默认CS8602警告仍编成功，另配置warnaserror:CS8602才编译失败。没有运行可能null访问的版本。[NRT当前合同](https://learn.microsoft.com/en-us/dotnet/csharp/nullable-references)

原Roslyn/分析器无需修改IL即可提供一些静态分析、运行时合同重写增加构建工作及运行检查有成本的取舍保留；不能无官方依据断言所有弃用动机就是某三项，或NRT/FluentValidation与完整DbC完全同等。
