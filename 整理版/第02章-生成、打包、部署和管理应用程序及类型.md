<a id="c02-overview"></a>
## 本章要解决的问题

第1章解释了CLR怎样加载和执行程序。本章进一步问：源码中的类型怎样成为可交付文件，交付包应该带哪些内容，程序怎样知道自己需要谁，以及多个应用使用组件时怎样减少相互影响。

原前三章总览把目标概括为让软件更稳定、更容易部署和管理。元数据、程序集标识、私有副本和配置可以帮助实现这些目标，但不是“换成.NET后所有版本冲突和部署错误都消失”的保证。第三章的强名称与GAC会进一步讨论共享情形，不能把它们当作私有部署的必需前提。

<a id="c02-build-package"></a>
## 从类型到模块和程序集

C#编译器处理源文件里的类型和成员，将结构信息生成到元数据中，将需要执行的实现逻辑生成到IL等相应表示中。原后续总览中“将类型生成到模块中”说的就是这一步。程序集的详细元数据/IL区别，以及`Employee`、`Program`和`Console`的例子，已在[第1章](第01章-CLR的执行模型.md#c01-metadata-il)展开。

模块与程序集并不是两个互斥的文件后缀分类。常见C#输出是带清单的单文件托管模块，它同时组成一个程序集；多文件程序集则由清单组织多个模块及资源。这里的“生成”和“打包”可以在常见构建中由工具连续完成，不表示开发者每次必须先造裸模块，再手工逐个合并。

原书把程序集称作重用、安全性及版本控制的基本单元。这里的安全性表述需要放回旧Framework的相关元数据、权限和身份处理背景；它不表示每个程序集都是独立进程或安全沙箱，也不意味着有一个程序集身份就能认证发布者可信。

| 项目 | 在生成/打包中的作用 | 容易混淆的地方 |
| --- | --- | --- |
| 源码类型和成员 | 编译器处理的输入 | 它们不按命名空间自动各生成一个DLL |
| 托管模块 | 含相应头、元数据和IL等内容的物理模块 | 不能仅凭dll/exe后缀判为托管 |
| 程序集清单 | 描述程序集标识、组成文件、资源和引用 | 它不是所有对象运行状态的快照 |
| 程序集 | 清单组织的逻辑部署、引用和版本单元 | 多文件程序集不等于引用多个独立程序集 |

例如，前章的`MyApp.exe`、`Logic.netmodule`、`Graphic.netmodule`及图片资源可以组成一个多文件程序集；也可能一个程序集引用另一个独立的`.dll`。前者是包内部组成关系，后者是程序集间依赖关系。完整原例保留在[模块与程序集的对照](第01章-CLR的执行模型.md#c01-assembly-module)，本章据此区分交付范围。

部署目标还包括程序所需Framework版本、处理器/进程平台及原生依赖。IL提供中间表示，不意味着所有应用都无需目标环境；平台位数的原问题见[第1章](第01章-CLR的执行模型.md#c01-platform)。

<a id="c02-manifest"></a>
## 清单、自描述、版本与文化

程序集内部保存自身结构及引用信息，工具和运行时可以读取它们，而不必另找一份C/C++式头文件说明这些托管类型。这就是原答强调的“自带说明书”。自描述可以简化类型使用、部署和版本管理，但不能替代文件实际存在、依赖兼容和配置正确等条件。

后续六章总览特别列出“程序集版本资源和语言文化设置”，需要和文件名字分开理解。

| 信息 | 表达的内容 | 与运行/部署的关系 |
| --- | --- | --- |
| 程序集标识 | 简单名称、版本、文化以及适用时的公钥等身份信息 | 用来描述程序集引用和身份 |
| 组成文件及资源 | 程序集包含哪些模块和资源 | 多文件交付时不能漏掉相关组成文件 |
| 引用信息 | 使用哪些外部程序集、类型或成员 | 帮助编译/加载解析依赖，不等于已经把依赖复制过去 |
| 版本资源与文件版本 | 文件及产品展示所用的版本资料 | 不应把文件版本数字直接当作程序集绑定身份的全部内容 |
| 文化信息 | 与程序集身份、特定语言/文化资源相关的资料 | 不能用命名空间名称或随意的文件夹名代替 |

这里对版本和文化的解释保留了原总览的主题范围。程序集标识、文件版本、资源文化各有用途，并非一个“版本号”或“语言设置”能同时决定所有行为。[程序集清单说明](https://learn.microsoft.com/en-us/dotnet/standard/assembly/manifest)列出了清单中的身份和组成信息。

原答还说“元数据记录精确版本，CLR严格按购物清单加载”。需要把两个层次分开：引用中**可以记录版本等身份信息**，并不等于运行时**无条件只能加载该数字对应的文件**。Framework的强名称绑定、配置策略、统一或重定向会参与决定；弱命名程序集也不能直接套用完全相同的版本检查规则。具体共享与绑定背景见[第3章](README.md#chapter-03)。

<a id="c02-dll-hell"></a>
## DLL Hell：Cool.dll的三个应用

原例有三个应用和两个组件版本，关键在于共享文件被替换后，已有应用面对的组件行为改变。

1. 应用A和B原本都使用第三方`Cool.dll`的1.0版，各自按这一版的接口和行为工作。
2. 后来安装应用C，它带来`Cool.dll`的2.0版，并把原共享位置中的1.0文件覆盖掉。
3. A和B再运行时遇到2.0版。若接口或行为不兼容，它们可能报错；C本身能工作，并不能证明A和B也兼容新版本。

```text
原来：A ─┐
         ├── 共享位置的 Cool.dll 1.0
      B ─┘

安装C并替换共享文件后：
      A ─┐
      B ─┼── 共享位置的 Cool.dll 2.0
      C ─┘
      A/B可能不兼容2.0
```

这就是原回答用来解释的“DLL地狱”：多个应用依赖同一共享组件，其中一个应用的安装或升级改变了其他应用的运行条件。问题不在`.dll`这个后缀本身，而在共享、覆盖和兼容关系。并非每次升级一定失败，也不能推断所有原生应用都只能采用这一种共享部署方式。

<a id="c02-private-deploy"></a>
## 私有部署：每个厨师自己的厨房

私有部署让一个应用携带并使用它自己的依赖副本，常见简单Framework场景是把应用和相应托管程序集放在应用目录或约定的私有探测路径下。A的副本不因C安装自己的文件而被直接替换，从而减少前例那类共享覆盖冲突。

```text
A目录：A.exe + Cool.dll 1.0
B目录：B.exe + Cool.dll 1.0
C目录：C.exe + Cool.dll 2.0
```

这个例子改变了**副本和部署边界**，没有证明1.0和2.0的代码本来兼容。每个应用仍要携带与自己匹配的文件，并保证实际加载的是预期副本。

原回答用了厨房和调味料的类比。共享组件的历史痛点像是所有厨师都去一个大厨房，使用同一套调味瓶；一个新厨师换掉盐的品牌，其他厨师按旧配方做的菜可能变味。私有部署像为每个厨师安排独立厨房，里面保留他所需版本的调味料。原例提到`System32`作为历史共享位置的直观说明，这只是某类旧部署情形，不能说所有共享组件或所有DLL都必须放在那里。

“复制一个文件夹即可部署”在这个语境下说明简单的XCopy部署思路，程序集通常不需要按传统组件机制注册其托管类型。它仍有前提：需要的运行时已经具备，托管/原生依赖和资源已交付，配置和路径匹配，应用需要的其他系统设置也已满足。如果应用还有原生组件、安装步骤或外部资源，就不能只凭这句话删去这些要求。[Framework部署说明](https://learn.microsoft.com/en-us/dotnet/framework/deployment/)区分应用私有部署及共享部署的范围。

私有部署是常见办法之一；需要本机多应用共享程序集时，身份及版本管理继续由[第3章](README.md#chapter-03)讨论。

<a id="c02-configuration"></a>
## 依赖和配置仍需要管理

原后续总览还列了“基本管理控制（配置）”。它提醒我们：生成文件之后，实际加载位置和绑定行为还会受到运行环境与配置影响，不能把元数据清单当作唯一输入。

编译阶段需要相应参考程序集，以检查源码使用的类型和成员；构建和交付阶段需要处理实际依赖文件；运行阶段按运行时的探测、身份与配置规则解析依赖。`using`只是源码名字解析的便利，既不自动下载依赖，也不代表已经把某DLL部署给应用。具体编译引用问题在[第4章](README.md#chapter-04)结合`MyApp`与工具库的实际追问展开。

在Framework背景中，配置可能影响版本策略和私有探测位置等。原第三章还提及`codeBase`这样的指定位置机制；网络地址加载不等于互联网有一个“公共GAC”。本章保留配置的这一作用范围，详细区别见[第3章](README.md#chapter-03)。[Framework程序集查找流程](https://learn.microsoft.com/en-us/dotnet/framework/deployment/how-the-runtime-locates-assemblies)说明了配置和探测参与加载的过程。

<a id="c02-corrections"></a>
## 现代差异与重要纠错

现代.NET应用有自己的宿主、发布包、依赖解析和部署方式；不能把本章简单Framework XCopy场景自动推广到所有现代应用，也不应把Framework的GAC或绑定配置元素当作通用新项目部署要求。

| 编号 | 原笔记的过度概括或容易产生的误读 | 原因与整理后的结论 | 一手依据 |
| --- | --- | --- | --- |
| C02-F04 | 元数据记录引用，就已经把所有依赖交付了 | 结构/引用记录、实际文件交付和运行时加载是不同阶段 | [清单内容](https://learn.microsoft.com/en-us/dotnet/standard/assembly/manifest) |
| C02-F01 | 引用记录有精确版本，就永远只按这个数字加载 | Framework还要考虑强/弱名称、版本策略和配置；身份记录不是无条件绑定保证 | [Framework绑定流程](https://learn.microsoft.com/en-us/dotnet/framework/deployment/how-the-runtime-locates-assemblies) |
| C02-F02 | 把所有dll复制到同一目录就能部署任何应用 | 这是简单私有部署思路，仍需运行时、原生依赖、资源及其他环境条件 | [Framework部署模型](https://learn.microsoft.com/en-us/dotnet/framework/deployment/) |
| C02-F03 | 私有部署从根本上消除了所有DLL冲突 | 它避免了原`Cool.dll`例中的共享覆盖问题，其他依赖或加载冲突仍可能发生 | [Framework部署与依赖条件](https://learn.microsoft.com/en-us/dotnet/framework/deployment/) |
| C02-F05 | 将文件版本、程序集版本和文化设置混作一个东西 | 它们表达的身份、展示和资源选择资料不同，需要区分 | [程序集清单身份](https://learn.microsoft.com/en-us/dotnet/standard/assembly/manifest) |

`Cool.dll`三个应用的例子和厨房类比说明的是副本边界；清单说明的是身份与组成。共享、副本、身份和配置结合起来，才形成可解释的部署模型。
