## 属性的主线与七个差异

原问题先问“属性相当于方法的语法糖吗”，又在后面困惑为什么程序集还记录一个属性定义。二者相容：C#给属性提供特殊的声明与调用语法；编译器生成或关联访问器方法，同时记录属性元数据；普通读写在执行时调用访问器。属性是类型系统与元数据中的成员，不能因此说CLR完全不知道属性。

原书对属性的警惕是API设计立场：字段式的轻量语法容易让调用者期待廉价、简单的状态访问，实际访问器却可以执行任意合法逻辑。下面保留原回顾的七个差异，并明确它们的范围。

| 原回顾的项目 | 可以怎样理解 | 需要补充的边界 |
| --- | --- | --- |
| 只读或只写 | 属性可以选择只提供getter或setter | 字段也有const、readonly等限制；普通readonly字段与只写属性并非同一机制 |
| 异常 | 访问器可能主动抛异常或因业务逻辑失败 | 字段访问也可能空引用，静态字段访问可能触发失败的类型初始化；不能说字段读取永不异常 |
| `ref/out` | 普通返回值属性不是可直接传引用的变量位置 | 现代C#的可写ref返回属性是另一种形式，不能套用这个绝对限制 |
| 耗时 | 属性可以计算、阻塞、加锁或跨边界调用 | 普通字段读取也不是固定纳秒保证；性能取决于执行路径 |
| 重复读值 | 连续读可能得到不同值，例如时间 | 时钟分辨率可能使两次相同；原作者对DateTime.Now的命名是设计意见，不是该API违法 |
| 副作用 | getter可以改变状态，调试器求值也可能触发它 | 是否自动求值取决于调试器设置，属性语法不保证无副作用 |
| 副本 | getter可以返回值副本或新建引用对象 | 要分别判断值语义、引用是否共享、是否ref返回以及是否防御性复制 |

原回顾还包括对象/集合初始化器、匿名类型、`Tuple`、索引器、访问器可访问性、性能和泛型属性限制，以下都保留理解所需的内容。

<a id="c10-initializers-accessibility"></a>
### 初始化器、访问器可访问性与泛型属性

类型与语句片段E10-01保留原`Employee`的Jeff、45：

```csharp
class Employee
{
    public string Name { get; set; }
    public int Age { get; set; }
}

// 调用方方法体内：
Employee value = new Employee { Name = "Jeff", Age = 45 };
```

这先建立实例，再完成相应成员赋值；它不是把对象分配与赋值变成一个对其他线程可见的原子操作。集合初始化器类似地组织构造与`Add`调用，各自要满足语言规则。

属性声明决定访问入口的可访问性；在允许的形式中，某一个访问器可以更受限制，例如`public string Name { get; protected set; }`，getter对外可读，setter供允许的派生类型等使用。不能把它写成两个独立的属性，也不能随意给两个访问器都加不相容的访问修饰符。

属性自己不能声明新的泛型类型参数。例如设想`public T Value<T> { get; }`不是C#属性声明；可以把它做成泛型方法，或者让属性属于泛型类型并使用该类型的`T`。这与CLR支持泛型方法并不冲突。

## 访问器方法、元数据与托管程序集

<a id="c10-property-lowering"></a>
### `Name`属性对应什么

类型片段E10-02，保留原`Person.Name`自动属性：

```csharp
public class Person
{
    public string Name { get; set; }
}
```

典型C#编译器为这个自动属性生成一个私有支持字段，例如`<Name>k__BackingField`，以及`get_Name()`与`set_Name(string value)`。该字段名称是编译器实现细节，不能在普通C#源代码里照写这个非法标识符；属性访问器的权限则由属性声明决定，不能因是生成代码就说它们都为private。

下面是元数据关系示意E10-03，**不是可编译的C#替代实现**：

```text
Person
├── 私有字段 <Name>k__BackingField : String
├── get_Name() : String
├── set_Name(String value) : Void
└── Name属性记录
    ├── 名称、标志、属性签名
    └── 通过MethodSemantics等关联访问器方法
```

赋值`p.Name = "Jeff"`对应setter调用；读`p.Name`对应getter调用。执行这个普通调用不必重新按属性名查询属性表；反射查询则会使用元数据。这里“普通调用执行方法”与“运行时可以通过反射理解属性”是不同工作路径。[属性语言规范](https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/language-specification/classes#157-properties)。

<a id="c10-property-design"></a>
### 为什么保留属性这个成员抽象

原回答提出三个理由：`person.Age`便于表达一个特征，`person.GetAge()`更像请求操作；许多UI绑定约定围绕属性建立；字段式的读写语法便于将直接存储改成受控入口。具体框架有自己的绑定规则，不能推广为所有框架只认识属性、绝不支持其他数据来源。

字段改成同名属性，许多普通读写源码仍能按原形式重新编译，但这不等于二进制兼容：旧客户端IL引用字段，新库只剩访问器时，旧字段引用不能自动改成方法调用。即使源码兼容也有范围，例如原来传`ref/out`的普通字段不能直接改成普通属性后继续同样调用。因此应区分调用外观、重新编译后的兼容性和旧二进制的兼容性。

<a id="c10-assembly-metadata"></a>
### “托管程序集”里有什么

原追问在属性元数据段落里遇到“托管程序集”。通常由C#等.NET工具编译的托管程序集包含代码、元数据、清单与资源等；常见物理格式是PE中的CLI程序集。`.dll`/`.exe`扩展名本身不能证明文件托管；传统Windows的`kernel32.dll`、`user32.dll`是原回答用来对照的本机库。

保留原表的五部分与书本类比，修正入口和正式表名：

| 组成 | 作用 | 原类比 |
| --- | --- | --- |
| PE头及相关目录 | 描述文件的本机装载结构，CLI头位置由相应目录指示 | 封面 |
| CLI/CLR头 | 描述CLI模块相关信息，包括元数据位置和适用的入口信息 | 目录页 |
| 元数据 | 描述类型、字段、方法、属性、程序集和它们的关系 | 目录与索引 |
| 通常的IL代码 | 由运行时编译或其他适用执行方式处理的代码 | 正文 |
| 清单与资源 | 程序集身份、依赖及附带数据等 | 附录 |

原表把逻辑性的“属性定义项”称为`PropertyDef`表。按CLI正式表名应区分`Property`、`PropertyMap`、`MethodSemantics`等；`AssemblyDef`、`FieldDef`也不能一律当作相应正式表名。`Property`记录名称、标志与签名；声明类型和访问器关联由相关表表达，并不是在一行里直接藏着一个任意的`Semantic`字段。[CLI元数据资料入口](https://learn.microsoft.com/en-us/dotnet/standard/metadata-and-self-describing-components)、[CLI表索引API](https://learn.microsoft.com/en-us/dotnet/api/system.reflection.metadata.ecma335.tableindex?view=net-10.0)。

通常C#产物的IL在JIT后成为机器码并在CPU上执行。托管的含义是受到相应运行时的管理，不能说托管程序“不直接在CPU上运行”。原表“入口在clr.dll”也不是所有程序集的PE契约：库可以没有程序入口，宿主与运行时实现有版本差异，还存在预编译或混合代码等情况。

思考区另用“早餐店菜单”类比：菜单上的名称像属性元数据，实际出餐的流程像访问器方法。目录或菜单告诉查询者怎样找到动作，却不能把它说成永远无用的“死数据”。这与前面的书本结构类比是不同用途，分别保留。

<a id="c10-init-metadata"></a>
### 现代`init`访问器的正确边界

类型片段E10-04（C#9+）：

```csharp
public class Person
{
    public string Name { get; init; }
}
```

原回答把它称作CLR在初始化后锁定对象的特殊支持，还说setter带`IsInitOnly`标记。这混淆了只读字段与初始化访问器。`init`会以setter方法表示，其返回签名带`IsExternalInit`必需修饰符，普通C#源码据规则限制何时可以赋值。它不是在每次运行时调用中检查对象是否过了初始化阶段的通用写锁。

本机反射确认存在`IsExternalInit`修饰符，并可经该setter把已构建对象的Name改成另一值。相关编译器、反射、动态绑定和序列化契约各有边界，不能由`init`自动推论对象图深层不可变。[init功能规范](https://github.com/dotnet/csharplang/blob/main/proposals/csharp-9.0/init.md)。

## 支持字段不是属性的必要条件

<a id="c10-explicit-backing-field"></a>
### 最常见的字段包装

类型片段E10-05：

```csharp
public class Person
{
    private string _name;
    public string Name
    {
        get { return _name; }
        set { _name = value; }
    }
}
```

`_name`是支持字段，访问器读写它；自动属性则让编译器处理类似存储。但访问器可以完全不引用一个专门对应的字段，它可以从系统、其他对象或计算取得结果。

<a id="c10-thread-priority"></a>
### `Thread.Priority`：涉及运行时与OS，却不能说完全没有字段

原答的假想类型片段E10-06仅为对照，改名以避免与真正的`System.Threading.Thread`混淆：

```csharp
class ThreadSketch
{
    private int _priority;            // 假想的手写字段
    public int Priority { get; set; } // 自动属性另有编译器生成的支持字段
}
```

它不是真实Thread实现；也不是自动属性一定使用 `_priority` 的示例。原回答据此断言Thread对象没有优先级字段，getter每次去Windows内核问值，这不成立：微软的.NET Framework参考源已有`m_Priority`，getter调用运行时本机辅助`GetPriorityNative`；现代.NET10的CoreCLR源码有`_priority`，getter直接读该字段，setter另有更新运行时/OS的路径。仅看到内部本机调用不能证明每次读取都调用OS。[Framework参考源](https://github.com/microsoft/referencesource/blob/main/mscorlib/system/threading/thread.cs)、[.NET10 CoreCLR源码](https://github.com/dotnet/runtime/blob/v10.0.0/src/coreclr/System.Private.CoreLib/src/System/Threading/Thread.CoreCLR.cs)。

保留原设置与读取的两个语句场景E10-07（API片段，仅核验编译与官方实现，不在核验中改变当前线程优先级）：

```csharp
using System.Threading;
// 调用方方法体内：
Thread.CurrentThread.Priority = ThreadPriority.Highest;
ThreadPriority p = Thread.CurrentThread.Priority;
```

原代码的`ThreadPriority.High`不是该枚举成员，修正为`Highest`；也可以按业务选择`AboveNormal`等。线程调度优先级有平台与运行状态限制，OS也不必按所设优先级给予某个固定执行结果。这一例的教学价值是属性可能触及运行时及外部系统，不是“任何属性必须没有缓存字段”。[Thread.Priority API](https://learn.microsoft.com/en-us/dotnet/api/system.threading.thread.priority)。

<a id="c10-array-zero-terminated"></a>
### CLR数组长度与以零结束的缓冲区长度不是同一例

原正式答的CLR数组片段E10-08：

```csharp
int[] arr = new int[10];
int len = arr.Length;
System.Console.WriteLine(len); // 10
```

数组长度由数组对象的运行时表示记录，不是每次从头扫描到整数0；新数组的10个零元素也不会使Length成为0。公开入口是只读属性或相应运行时操作，不是一个可由调用方普通赋值的公有长度字段。不能由此虚构“反射能随意修改数组长度”的正常API。

用户引文还提到以0结束的数组，表示另一种可能通过扫描取得长度的缓冲区约定。完整程序E10-09保留该不同场景：

```csharp
using System;

class ZeroTerminatedBuffer
{
    private readonly byte[] bytes;
    public ZeroTerminatedBuffer(byte[] bytes) { this.bytes = bytes; }
    public int Length
    {
        get
        {
            for (int index = 0; index < bytes.Length; index++)
                if (bytes[index] == 0) return index;
            throw new FormatException("缓冲区没有结束标记");
        }
    }
}

class Program
{
    static void Main()
    {
        byte[] data = { 65, 66, 0, 67 };
        Console.WriteLine(data.Length);                         // 4：数组存储长度
        Console.WriteLine(new ZeroTerminatedBuffer(data).Length);// 2：首个0之前的长度
    }
}
```

前提是明确采用结束标记约定。扫描边界以实际数组长度为限，不越界寻找不存在的0；这里没有结束标记时抛异常。属性能计算结果，不等于它计算的值必然是CLR数组本身的Length。

<a id="c10-rectangle-area"></a>
### 矩形面积不需要独立`_area`字段

类型与语句片段E10-10保留原Width/Height/Area：

```csharp
public class Rectangle
{
    public double Width { get; set; }
    public double Height { get; set; }
    public double Area { get { return Width * Height; } }
}

// 调用方方法体内：
Rectangle r = new Rectangle { Width = 3, Height = 4 };
System.Console.WriteLine(r.Area); // 12
r.Width = 5;
System.Console.WriteLine(r.Area); // 20
```

单线程或有适当同步的状态下，每次计算能反映相应的宽高，避免额外缓存字段失去同步。若两个维度并发变化，两个读取不自动形成同一时刻的快照，不能称“绝对一致”。计算与缓存谁更快也不能仅靠这个小片段保证。

保留原多个类比：字段像仓库负责存储，属性负责给出值；Thread属性可以像代理去执行运行时/系统操作；矩形Area像拿尺子量到宽高后现场加工。类比说明取得结果的不同方式，不证明任何具体BCL实现一定没有私有存储。

<a id="c10-aip-version"></a>
## 自动实现属性的历史与现代规则

<a id="c10-aip-historical"></a>
### 原书的“全有或全无”规则

原问题两次引用“如果使用AIP，属性必然可读可写，不能手写一个访问器而自动实现另一个”。在原书C#5语境中，具体非抽象自动属性需要getter和setter，访问器可有不同可访问性；`private set`仍是一个真实setter，不能说它取消了setter。

早期普通源码不能直接引用编译器生成支持字段的名字，因此若要自定义访问器逻辑，传统方式是声明自己的字段并实现访问器。这是语言设计与表示方式，不能把不合法源码解释成编译器“崩溃”或它技术上永远不可能支持半自动。

假想类型片段E10-11保留原User的“手写get、自动set”形式。此例在C#5不合法，而且下面的非void getter还缺返回值；它不是可以直接执行的程序：

```csharp
public class User
{
    public string Name
    {
        get { /* 我手写逻辑；这里尚没有返回值 */ }
        set; // C#5不接受具体类上的这种混合实现
    }
}
```

明确的C#5反例E10-12，保留原Test的getter固定10：

```csharp
public class Test
{
    public int MyProp
    {
        get { return 10; }
        set;
    }
}
```

旧编译器报相应方法/自动属性诊断，不会因为这个源程序“运行时崩溃”。

两个正确传统类型片段E10-13a/b：

```csharp
public class Test
{
    public int MyProp { get; set; }
}
```

```csharp
public class Test
{
    private int _myProp;
    public int MyProp
    {
        get { return 10; }
        set { _myProp = value; }
    }
}
```

第二个例的getter有意固定返回10，setter则写字段；不能把它解释成通常的“写多少就读回多少”。给MyProp赋7后，读属性仍为10，说明访问器逻辑由实现决定。

<a id="c10-aip-uppercase"></a>
### 另一追问的`Name.ToUpper`例不能省掉

原后续问题换成了手写getter返回大写姓名，场景不同。C#5反例E10-14：

```csharp
public class Person
{
    public string Name
    {
        get { return _name.ToUpper(); } // 此例还没有声明_name
        set;
    }
}
```

它既有未知字段问题，也有历史混合访问器限制。补齐传统实现E10-15（类型与语句片段）：

```csharp
public class Person
{
    private string _name;
    public string Name
    {
        get { return _name.ToUpper(); }
        set { _name = value; }
    }
}

// 调用方方法体内：
Person p = new Person { Name = "Jeff" };
System.Console.WriteLine(p.Name); // JEFF
```

这里未设置Name就读会因为`_name`为null而空引用，是否应接受这种输入需要业务契约处理。原讨论还有另一方向“手写setter、自动getter”，历史规则同样不允许该具体类混合形式，不因为换了方向就解决支持字段访问问题。

思考区的“全自动洗衣机”类比描述旧规则：通常选择机器完成全过程，或自己接管全过程。这个类比只帮助理解当时的规则；后来提供`field`后，机器和手写逻辑可以合作，不能用类比证明新语法不可能。

<a id="c10-aip-modern"></a>
### C#6的只读属性与C#14的`field`

以下不同类型片段E10-16分别保留原get-only与private-set，并增加版本标注：

```csharp
// C#6+：只读自动属性，可在声明初始化器或相应构造器内赋值。
public class ReadOnlyExample
{
    public int MyProp { get; }
    public ReadOnlyExample(int value) { MyProp = value; }
}

// AIP已有这种访问限制形式；不是C#6才允许。
public class PrivateSetterExample
{
    public int MyProp { get; private set; }
    public void SetInternally(int value) { MyProp = value; }
}
```

后续原例的`Person.Name { get; }`与`Person.Age { get; private set; }`同样按这两种规则理解；它们不依赖“必须是.NET Core/.NET5”这个运行时范围，语言版本和目标运行时要分开。

现代C#14完整程序E10-17，保留固定10场景，并展示有意义的半自动写入：

```csharp
using System;

class Test
{
    public int MyProp { get { return 10; } set; }
    public string Name
    {
        get { return field.ToUpper(); }
        set;
    }
    public int CheckedValue
    {
        get;
        set { field = value >= 0 ? value : throw new ArgumentOutOfRangeException(); }
    }
    static void Main()
    {
        Test p = new Test { MyProp = 7, Name = "Jeff", CheckedValue = 8 };
        Console.WriteLine(p.MyProp);      // 10
        Console.WriteLine(p.Name);        // JEFF
        Console.WriteLine(p.CheckedValue);// 8
    }
}
```

`field`在属性访问器中代表编译器生成的支持字段，可以让一个访问器有主体，另一个自动实现。名字仍不是任意可写的`<Name>k__BackingField`；`Name`为null时大写getter的业务问题也没有凭新语法消失。[C#14 field参考](https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/keywords/field)。

| 保留原五种模式 | 历史/现代含义 |
| --- | --- |
| 纯AIP `get; set;` | 编译器提供字段与两个访问器 |
| 纯显式访问器 | 作者决定使用字段或其他逻辑 |
| 手写get、自动set | C#5具体类不支持；C#14按相应规则可支持，不称编译器崩溃 |
| 只读AIP `get;` | C#6+；没有setter，允许规定的初始化赋值 |
| AIP `get; private set;` | 有两个访问器，只是setter受限；不属于手写实现 |

原导读还说AIP不能在声明处初始化和不便给getter/setter主体下断点。前者是历史限制，C#6+可用属性初始化器；后者是缺少手写主体所带来的调试操作差别，不是所有调试工具永远无法观察访问器或给其机器码设置断点。[自动实现属性说明](https://learn.microsoft.com/en-us/dotnet/csharp/programming-guide/classes-and-structs/auto-implemented-properties)。

<a id="c10-aip-serialization"></a>
## 自动属性与历史字段序列化

<a id="c10-serialization-fields"></a>
### 先看自动属性实际保存了什么

原问题引用“包含AIP就没办法反序列化”，要求结合例子。应把警惕**隐式字段契约的版本风险**与“当前对象不能序列化/反序列化”分开。

历史类型片段E10-18（.NET Framework）：

```csharp
[System.Serializable]
public class Person
{
    private int _age = 30;
    public int Age { get; set; }
}
```

正常建立该实例而未给Age赋值，手写字段`_age`为30，自动属性的支持字段则为0，它们不是同一个存储。源流结构示意中的`???`应明确为0；另给Age赋30又是后面的另一个场景。

字段序列化逻辑示意E10-19：

```text
Person（按默认字段契约处理）
├── 字段 _age                     值 30
└── 字段 <Age>k__BackingField      值 0
```

`BinaryFormatter`的这种默认场景处理可序列化字段及对象图，不是把对象的本机内存布局整块原样复制到文件。自定义`ISerializable`等路径又可改变所记录的数据契约。

<a id="c10-aip-roundtrip"></a>
### 同一版本的自动属性可以正常往返

历史完整程序E10-20仅处理程序自己创建的对象、使用MemoryStream：

```csharp
using System;
using System.IO;
using System.Runtime.Serialization.Formatters.Binary;

[Serializable]
public class Person
{
    private int _age = 30;
    public int Age { get; set; }
    public int OriginalField { get { return _age; } }
}

class Program
{
    static void Main()
    {
        Person original = new Person();
        using (MemoryStream stream = new MemoryStream())
        {
            BinaryFormatter formatter = new BinaryFormatter();
            formatter.Serialize(stream, original);
            stream.Position = 0;
            Person restored = (Person)formatter.Deserialize(stream);
            Console.WriteLine(restored.Age);          // 0
            Console.WriteLine(restored.OriginalField);// 30
        }
    }
}
```

这个正常往返反驳“一旦有AIP就绝不可能反序列化”。它没有消除长久持久化依赖编译器字段名称的版本风险，也没有把旧序列化器替换成现代API来掩盖原场景。

<a id="c10-backing-name-version"></a>
### 保留周一V1到周三V1.1的版本场景

原版本故事E10-21采用张三Age30：周一V1构建`new Person { Age = 30 }`并保存；周二换编译器/重新编译；周三V1.1尝试读取旧流。此例**假定**编译器将支持字段从`<Age>k__BackingField`改为`<Age>z__BackingField`。这是解释不稳定字段契约的条件，不是已经证实某版Visual Studio或Mono实际做过这种变更。

```text
周一V1：Age = 30
    → 假定流中记录 <Age>k__BackingField = 30
周二重新编译：假定实现字段名变成 <Age>z__BackingField
周三V1.1读旧流：需要处理旧字段契约与新类型成员不匹配
```

类型、字段和版本匹配规则可能导致错误或需要兼容措施；不能仅凭这个假定就保证所有版本都同一种异常、程序必定崩溃、持久文件中的数据必定丢失。真正的约束是编译器字段名不是开发者承诺的稳定持久化契约。

保留手写支持字段对照E10-22：

```csharp
[System.Serializable]
public class Person
{
    private int _age;
    public int Age
    {
        get { return _age; }
        set { _age = value; }
    }
}
```

开发者掌握`_age`名称，但开发者自己重命名、改变字段类型、改变契约或混淆工具处理也可能影响旧数据，不能把它叫“终身有效、永远不会改变”的身份证。原身份证类比保留为：隐式支持字段名称像实现者签发的证件，显式字段名称由类型作者掌控；两者都必须通过约定管理版本。

<a id="c10-custom-serialization"></a>
### 独有思考里的合同选择与排除字段

原思考区另提到`DataContractSerializer`与`[field: NonSerialized]`，不能当生成过程丢掉。数据合同序列化可以通过明确的DataContract/DataMember选择字段或属性；它也能处理声明为数据成员的私有字段，并非所有现代序列化器都永远只看公共属性。[数据合同类型](https://learn.microsoft.com/en-us/dotnet/framework/wcf/feature-details/types-supported-by-the-data-contract-serializer)。

现代语言补充E10-23（**C#7.3+**，可以编译为.NET Framework目标）：

```csharp
[System.Serializable]
public class Person
{
    [field: System.NonSerialized]
    public int Age { get; set; }
}
```

从C#7.3起，`field:`可以把这里的特性应用到自动属性支持字段；相关字段序列化路径忽略该字段，却不会另存Age或自动恢复其业务值。**旧C#5编译器会报CS0657警告并忽略这个特性，即使编译退出码为0也没有达到排除字段的目的。**本机旧编译器对应支持字段的IsNotSerialized/NonSerialized特性均为False，Age30往返后仍30；用现有Roslyn按C#7.3编译相同程序并在Framework4.8运行，两项元数据均为True，Age30往返后为0。[C#7.3版本说明](https://learn.microsoft.com/en-us/dotnet/csharp/whats-new/csharp-version-history#c-version-73)。

`ISerializable`可自行选择名称与值，重点是显式定义数据契约，而不是所有类型一律禁止使用AIP。忽略后的业务数据不会仅凭属性还存在就从流里还原。

现代差异：BinaryFormatter在.NET5开始出现相应弃用诊断，.NET9起内置实现已不能按历史方式工作；不能把它写成“.NET5起类型就被彻底移除”。这里的BinaryFormatter实验采用Framework运行时，E10-23的编译语法则是C#7.3+补充，语言版本与运行时目标不能混为一谈。[BinaryFormatter迁移官方说明](https://learn.microsoft.com/en-us/dotnet/standard/serialization/binaryformatter-migration-guide/)。

<a id="c10-json-contract"></a>
## JSON的契约与只读属性

<a id="c10-json-aip"></a>
### 默认属性契约不依赖支持字段的隐式名称

原追问现代序列化器怎样解决字段名问题。以System.Text.Json的通常公共属性契约为例：读取属性值，把契约名称写成JSON键；反序列化再按合同构建对象和设置成员。它不要求把`<Name>k__BackingField`这个私有实现名写进JSON。

现代完整程序E10-24：

```csharp
using System;
using System.Text.Json;

public class Person
{
    public string Name { get; set; }
    public int Age { get; set; }
}

class Program
{
    static void Main()
    {
        Person person = new Person { Name = "Jeff", Age = 30 };
        string json = JsonSerializer.Serialize(person);
        Console.WriteLine(json); // {"Name":"Jeff","Age":30}
        Person restored = JsonSerializer.Deserialize<Person>(json);
        Console.WriteLine("{0}, {1}", restored.Name, restored.Age); // Jeff, 30
    }
}
```

步骤是发现所选择成员的契约 → 取得Name/Age值 → 生成对应键值 → 按目标合同读取JSON → 创建对象并使其得到Jeff、30。这里的setter内部怎样储存不影响JSON键；编译器若改变隐藏字段名而公共合同保持一致，也不需要因此修改旧JSON。

不能把具体实现一律描述为“每次用反射搜索并调用get/set”：元数据解析可以缓存，也有源生成、构造器、字段合同及自定义converter等路径。Source-generated API仍受各自访问能力限制，不代表`JsonInclude`在所有生成上下文都能访问任意私有成员。新旧序列化路线的性能也不能仅由“字段/属性”区别统一判断；思考区“现代方案通常更快”的说法没有在本章提供相应基准，不能当作这些例子的实测结论。

原“私房钱与公开内容”类比表达选择契约的区别：旧默认字段路径看存储成员，常见JSON属性合同看公开成员。但契约可以选择字段，BinaryFormatter也不只看私有字段，两者都不能按人格类比概括成绝对行为。

<a id="c10-json-rename"></a>
### `Name`改成`FullName`时固定JSON名称

原例重构了公共属性名，仍要读旧`"Name"`键。现代完整程序E10-25保留这个不同场景：

```csharp
using System;
using System.Text.Json;
using System.Text.Json.Serialization;

public class Person
{
    [JsonPropertyName("Name")]
    public string FullName { get; set; }
}

class Program
{
    static void Main()
    {
        Person value = JsonSerializer.Deserialize<Person>("{\"Name\":\"Jeff\"}");
        Console.WriteLine(value.FullName);             // Jeff
        Console.WriteLine(JsonSerializer.Serialize(value));// {"Name":"Jeff"}
    }
}
```

成员名可继续改成其他名称而JSON合同保持Name，但仍须维护值类型、成员选择、转换器和版本行为。属性方法有异常或副作用时，也不能仅因是AIP/JSON就说整个序列化永远安全。[JsonPropertyName API](https://learn.microsoft.com/en-us/dotnet/api/system.text.json.serialization.jsonpropertynameattribute)。

| 原新旧对照项目 | 历史默认字段场景 | 通常JSON属性合同 |
| --- | --- | --- |
| 数据来源 | 可序列化字段，含相应私有支持字段 | 选入合同的公共属性；选项/特性/转换器可以改变范围 |
| 名称依赖 | 隐式字段名可造成版本耦合 | JSON合同名可与C#成员名分开管理 |
| AIP风险 | 需要考虑实现字段契约的稳定性 | 无需因隐藏字段名改变而变更该默认合同，不等于所有风险为零 |
| 格式互通 | 与相应.NET序列化规则联系紧密 | JSON是通用格式，双方仍须约定合同 |
| 实现原理 | 按字段/对象图或定制合同处理，不是原生内存布局深拷贝 | 取得成员值、创建对象、调用适用入口，也可使用字段/构造器/源生成等 |

<a id="c10-json-readonly"></a>
### 纯getter与`init`要分开

原后续追问“想了解一下”承接没有公开setter的属性如何赋值。下面两个类型是不同例子E10-26（现代类型片段）：

```csharp
public class GetterOnlyPerson
{
    public string Name { get; }
    public int Age { get; }
}

public class InitPerson
{
    public string Name { get; init; }
    public int Age { get; init; }
}
```

对JSON`{"Name":"Jeff","Age":30}`，默认无参构建`GetterOnlyPerson`且没有其他构造合同、Populate或自定义处理时，其Name保持null、Age保持0。`InitPerson`却有初始化setter，System.Text.Json可正常让它取得Jeff、30；原“get或init都丢数据”的概括错误。

<a id="c10-json-include"></a>
### 解法一：`private set`与`JsonInclude`

现代类型片段E10-27保留原两个字段及显式无参构造器：

```csharp
using System.Text.Json.Serialization;

public class Person
{
    [JsonInclude]
    public string Name { get; private set; }
    [JsonInclude]
    public int Age { get; private set; }
    public Person() { }
}
```

此例按相关JSON合同纳入非公开setter，反序列化上述JSON得到Jeff、30；对普通调用方，setter仍不可直接调用。它不意味着所有类型都必须提供public无参构造器，也不是序列化器“无视属性元数据”的证明；成员合同正是由类型、成员信息和相关特性建立。

<a id="c10-json-populate"></a>
### 解法二：填充已有可变引用对象

完整程序E10-28（.NET8+，保留原默认Tags及随机Guid的Id）：

```csharp
using System;
using System.Collections.Generic;
using System.Text.Json;
using System.Text.Json.Serialization;

[JsonObjectCreationHandling(JsonObjectCreationHandling.Populate)]
public class Order
{
    public List<string> Tags { get; } = new List<string> { "default" };
    public string Id { get; } = Guid.NewGuid().ToString();
}

class Program
{
    static void Main()
    {
        string json = "{\"Tags\":[\"a\",\"b\"],\"Id\":\"xxx\"}";
        Order order = JsonSerializer.Deserialize<Order>(json);
        Console.WriteLine(string.Join(",", order.Tags)); // default,a,b
        Console.WriteLine(order.Id != "xxx");           // True
    }
}
```

构造时已有的列表被复用，JSON的a、b追加进去，既没有清掉default，也没有给只读Tags换引用。Id的字符串没有可变内容供这样填充，且没有setter或构造参数来接收xxx，所以它保持这次构造产生的Guid文本。

这不是“反射强行给readonly字段赋值”的新功能。可变引用成员可以被填充，并不意味着任意不可变对象、整数或结构体都能沿同一路径处理。结构体属性需要适用setter来写回修改后的副本；对不满足Populate规则的合同可能有诊断或运行时错误，不能统称所有不支持的值都悄悄丢弃。官方还列出了参数化构造等相关限制。[Populate官方说明](https://learn.microsoft.com/en-us/dotnet/standard/serialization/system-text-json/populate-properties)。

<a id="c10-json-constructor"></a>
### 解法三：通过构造器建立只读状态

原record例E10-29（现代完整程序，record为C#9+；此处使用普通字符串而不额外要求原片段的C#11原始字符串语法）：

```csharp
using System;
using System.Text.Json;

public record Person(string Name, int Age);

class Program
{
    static void Main()
    {
        string json = "{\"Name\":\"Jeff\",\"Age\":30}";
        Person person = JsonSerializer.Deserialize<Person>(json);
        Console.WriteLine("{0}, {1}", person.Name, person.Age); // Jeff, 30
    }
}
```

这个类型有适用的构造合同，可以获得相应参数；它不是所有record任意有多个构造器时都永远自动选同一个入口的规则。

保留非record的`JsonConstructor`例E10-30（类型片段）：

```csharp
using System.Text.Json.Serialization;

public class Person
{
    public string Name { get; }
    public int Age { get; }
    [JsonConstructor]
    public Person(string name, int age) { Name = name; Age = age; }
}
```

Name/Age不靠setter赋值，而由构造器建立。构造器参数须按相应规则匹配**目标CLR成员名与类型**，名称匹配忽略大小写；不直接以JSON键名代替CLR成员名。这个区别在重命名场景尤为明显，补充类型片段E10-31：

```csharp
using System.Text.Json.Serialization;

public class Person
{
    [JsonPropertyName("Name")]
    public string FullName { get; }
    public int Age { get; }
    [JsonConstructor]
    public Person(string fullName, int age) { FullName = fullName; Age = age; }
}
```

JSON仍用Name，但构造参数是fullName，与CLR属性FullName匹配。错误地把它只命名为name而没有相应CLR成员，可能触发合同绑定错误。原说“给参数加JsonPropertyName即可映射”也不合法：该特性不能应用在这个构造参数上，编译器会报CS0592。

```csharp
// 反例片段：JsonPropertyName不允许在这里标构造参数。
// public Person([JsonPropertyName("Name")] string fullName) { }
```

现代.NET还支持版本规定的其他构造器选择形式，.NET8+的JsonConstructor可涉及非公开构造器；所以“必须public无参ctor”的断言不能作为三条路线的总规则。反射模式与源生成模式仍各有适用能力。[JSON不可变类型官方说明](https://learn.microsoft.com/en-us/dotnet/standard/serialization/system-text-json/immutability)。

| 保留的三种场景 | 适用方式 | 关键边界 |
| --- | --- | --- |
| 可变DTO，对外不公开setter | JsonInclude与private setter | 有setter且合同允许该访问；不是任意私有成员都无条件纳入 |
| 希望保留已有列表默认项并追加JSON输入 | .NET8+的Populate | 复用可变引用实例；不清空default；结构体等须满足另一组规则 |
| 需要由构造器建立只读数据 | 适用record构造器或JsonConstructor | 参数绑定CLR成员名/类型；record本身也不自动意味着深层不可变 |

这三种方式使用不同的成员/构造合同。它们说明序列化器可以选择怎样建立对象状态，却不能证明运行时和序列化器完全忽略属性元数据。

<a id="c10-property-cost"></a>
## 耗时、同步和远程访问

<a id="c10-property-inlining"></a>
### 简单getter可能内联，复杂getter可以执行任意逻辑

原解释用字段读取`obj._count`和属性`obj.Count`对照。前者取得存储值，后者执行访问器；如果访问器只取同一字段，JIT可能内联使调用成本很低。它不是“Release必内联、Debug永不内联、两者性能永远相等”的语言或运行时契约。[MethodImplOptions API](https://learn.microsoft.com/en-us/dotnet/api/system.runtime.compilerservices.methodimploptions)。

原场景E10-32的getter里包含`Thread.Sleep(5000)`，访问会要求当前线程等待；这能说明慢属性的可能性，不是一个需要实际让核验等待5秒的基准。访问器还可能包含I/O、锁或分配，不能只凭属性外观估计耗时。

原答给出了字段约1纳秒、本地方法约10纳秒、远程毫秒或秒的比较数字，没有对应的机器/测量条件，不能作为固定结果。JIT、CPU、缓存、调用逻辑、宿主与通信路径都会影响实际成本。本章不把这些示意数字升级为性能保证。

原七差异的另外两个点也与调用语义相连：`DateTime.Now`两次读取可能不同，getter也可能有副作用。调试器监视窗口若自动求值，可能执行getter，不能假定它只窥看字段。原作者据此建议把昂贵或显著改变状态的操作表达为方法，是设计指引而非禁止所有动态值属性的语法规则。

<a id="c10-property-locks"></a>
### 保留锁属性例，但补出真正的锁环条件

类型片段E10-33，保留原`_lock`、`_counter`和两个加锁访问器：

```csharp
public class CounterModel
{
    private readonly object _lock = new object();
    private int _counter;
    public int Counter
    {
        get { lock (_lock) { return _counter; } }
        set { lock (_lock) { _counter = value; } }
    }
}
```

原调用方语句片段E10-34需要已经建立`obj`与`someOtherLock`：

```csharp
lock (someOtherLock)
{
    int temp = obj.Counter;
    // 调用方继续处理其他工作
}
```

这表明读取属性可能等待内部锁，调用者在外部锁内执行它时要考虑锁顺序。它本身没有证明死锁：如果同一线程再次进入自己已持有的同一个Monitor锁，锁是可重入的，不会仅因重复进入就形成死锁。

真正的两线程反序获取场景E10-35（调度图，不作为必须卡住的程序运行）：

```text
线程A：已持有 someOtherLock(A)
        → 读取Counter，等待内部 _lock(B)
线程B：已持有 _lock(B)
        → 另一操作路径需要 someOtherLock(A)
结果：A等待B释放B，B等待A释放A，形成循环等待
```

两个锁、两个线程、相反顺序和实际交错是这个例的条件。若只是正常短临界区，也可能只是短暂阻塞；不能把所有锁属性称作必然死锁。

在上述类型内增加的相应方法片段E10-36：

```csharp
public int GetCounter()
{
    lock (_lock) { return _counter; }
}
```

`GetCounter()`让调用者更容易注意它是一段操作，却不会自动消除同样的锁环。线程同步仍须通过正确的锁设计解决。原引文中的“线程永远终止”应理解相关警告为长久等待/阻塞风险，而不是访问一个属性就保证线程退出。[Monitor.Enter的重入与同步契约](https://learn.microsoft.com/en-us/dotnet/api/system.threading.monitor.enter)。

<a id="c10-property-remoting"></a>
### `MarshalByRefObject`：须存在跨边界代理这个条件

原例讨论.NET Framework Remoting、跨AppDomain或跨进程访问。对象继承`MarshalByRefObject`使它可以参与相关代理机制，却不意味着每个本地实例调用都发生网络RPC。真正跨域/远程代理调用时，访问器可能经过消息构造、通信、远端执行与返回；跨域不一定经过网络，调用线程等待也不意味着整个进程全体线程停止。

保留原循环场景E10-37a（语句片段，假定`obj`是相应服务代理）：

```csharp
for (int i = 0; i < 1000; i++)
{
    System.Console.WriteLine(obj.Counter);
}
```

它会反复调用getter。如果通过远程代理执行，1000次成员取得会重复付出相应边界调用成本；具体耗时无法仅由数字1000确定。

保留“先取得一次再用缓存”的另一场景E10-37b：

```csharp
int counter = obj.GetCounter();
for (int i = 0; i < 1000; i++)
{
    System.Console.WriteLine(counter);
}
```

现在服务只被读取一次，循环使用同一个本地值。缓存成立的业务条件是允许这1000次输出表示同一取得时刻的值，不能要求每次都观察服务最新状态；仅仅把属性改名成方法，并不会自行减少调用次数。

原答把这种问题联系到Web API、gRPC、Service/Repository，以及`GetUserCountAsync()`与`UserCount`的命名选择：远程、数据库或其他耗时操作通常应清楚表达为操作，常见本地DTO则可以采用简单属性。这是让调用者形成准确成本预期的API设计思路，不是所有getter一律不得包含任何逻辑。

现代.NET不支持.NET Framework那套Remoting和多AppDomain调用机制，`MarshalByRefObject`类型仍可出现，不能把“这种旧远程机制不受支持”写成“该基类已不存在”。[现代.NET不支持的Framework技术](https://learn.microsoft.com/en-us/dotnet/core/porting/net-framework-tech-unavailable)。原“披着羊皮的狼”类比保留其目的：轻量的属性外观可能隐藏复杂操作；它不提供线程安全或远程调用的判定方法。

<a id="c10-ref-return-property"></a>
### 现代可写ref返回属性的例外

现代完整程序E10-38（C#7+），用来标明原“属性不能作ref参数”的范围：

```csharp
using System;

class Counter
{
    private int value = 1;
    public ref int Value { get { return ref value; } }
}

class Program
{
    static void Increment(ref int value) { value++; }
    static void Main()
    {
        Counter c = new Counter();
        Increment(ref c.Value);
        Console.WriteLine(c.Value); // 2
    }
}
```

这里返回的是可写变量的引用，普通按值返回属性没有这个条件。只读ref返回又有其他限制，不能因这里合法就把任意属性传入`ref/out`。[ref返回参考](https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/keywords/ref)。

## 属性返回副本

<a id="c10-datetime-copy"></a>
### `DateTime.AddYears`不会原地修改字段或属性

原例用1990年生日比较字段与属性，却把“不接AddYears返回值”的问题只归咎于属性。完整程序E10-39保留两种访问与两种调用形式：

```csharp
using System;

class Person
{
    public DateTime BirthField;
    private DateTime _birth;
    public DateTime Birth
    {
        get { return _birth; }
        set { _birth = value; }
    }
}

class Program
{
    static void Main()
    {
        Person p = new Person
        {
            BirthField = new DateTime(1990, 1, 1),
            Birth = new DateTime(1990, 1, 1)
        };
        p.BirthField.AddYears(1);
        p.Birth.AddYears(1);
        Console.WriteLine("{0}, {1}", p.BirthField.Year, p.Birth.Year); // 1990, 1990

        p.BirthField = p.BirthField.AddYears(1);
        p.Birth = p.Birth.AddYears(1);
        Console.WriteLine("{0}, {1}", p.BirthField.Year, p.Birth.Year); // 1991, 1991
    }
}
```

`DateTime`不可变，AddYears返回新值，既没有修改原字段值，也没有修改原属性值。正确保存结果需要赋回。普通按值返回结构体属性取得的是值，不提供原支持字段的可写变量位置；但字段在很多表达式中同样可以被按值读取，不能统一说“字段返回的任何值永远就是原内存”。值语义也不规定副本一定在物理栈上形成。[DateTime.AddYears API](https://learn.microsoft.com/en-us/dotnet/api/system.datetime.addyears)。

可变结构体的字段、按值属性、可写ref属性还可能表现不同，例如给普通结构体属性结果的字段赋值会遇到CS1612等规则。原例的关键在于区分访问形式和所调用方法是否修改对象，不能拿不可变DateTime误证“对字段调用就会改、对属性调用就不会改”。

<a id="c10-new-reference-copy"></a>
### 每次getter建立新列表

完整程序E10-40保留原Order的vip、新tag以及副本行为：

```csharp
using System;
using System.Collections.Generic;

public class Order
{
    private List<string> _tags = new List<string> { "vip" };
    public List<string> Tags { get { return new List<string>(_tags); } }
}

class Program
{
    static void Main()
    {
        Order order = new Order();
        order.Tags.Add("new");
        Console.WriteLine(string.Join(",", order.Tags)); // vip
    }
}
```

第一次访问拿到的列表被加了new；第二次又得到基于`_tags`建立的另一个列表，内部仍只有vip。这里确实建立了新列表容器；列表内的引用元素是否深层复制要另行判断，不能把创建容器称作整张对象图的深拷贝。

如果某个字段或属性直接返回原列表引用，调用方可修改那个同一列表。能否改变内部状态取决于是否共享对象，不由“字段/属性”两个词独立决定。

<a id="c10-defensive-array-copy"></a>
### 防御性数组复制

完整程序E10-41保留User/User→Admin的原场景：

```csharp
using System;

public class User
{
    private string[] _roles = { "User" };
    public string[] Roles { get { return (string[])_roles.Clone(); } }
}

class Program
{
    static void Main()
    {
        User u = new User();
        u.Roles[0] = "Admin";
        Console.WriteLine(u.Roles[0]); // User：重新取得的副本反映原内部状态
    }
}
```

这是设计者可能主动选择的边界。调用方修改了取得的数组副本，不是原数组。原例用字符串元素，字符串值本身不可变；换成可变引用对象的数组，Clone只复制元素引用，还须分析对象内容是否共享。这样的getter应写清合同与成本，也可用`GetRoles()`等方法名提示“取得一个副本”。

<a id="c10-span-copy"></a>
### 独有思考中的span与Bitmap要分别判断

思考区把ReadOnlySpan与普通结构体数据副本一并列为“改了白改”，这不成立。现代完整程序E10-42：

```csharp
using System;

class Program
{
    static void Main()
    {
        int[] data = { 1, 2 };
        Span<int> first = data;
        Span<int> second = first;
        second[0] = 7;
        ReadOnlySpan<int> readOnly = first;
        Console.WriteLine("{0}, {1}, {2}", data[0], first[0], readOnly[0]); // 7, 7, 7
    }
}
```

span值的复制可以只是复制引用某存储范围的描述信息，而没有复制其底层数据。ReadOnlySpan限制经这个视图写入，不意味着底层数组不能由其他路径改变。

思考区还提到getter返回新Bitmap的概念例：若访问器刻意创建一个独立图像对象返回，调用方操作的是所返回的新对象；若返回原图像引用，条件就不同。这保留了“引用类型也可能返回新对象”的教学场景，不需要在本章加载图片或虚构未提供的图像API实现。

这些分配与复制问题和前章params展开的成本有联系，但params并非每次调用都分配，属性也并非每次读取都new对象。原“字段式外观让人忽略成本”的设计目的保留，统一的零成本/必分配结论改为检查实际实现。

<a id="c10-anonymous-boundary"></a>
## 匿名类型与元组

<a id="c10-anonymous-definition"></a>
### 编译器为临时数据生成类型

原导读例E10-43a（语句片段）保留Jeff与Year1964：

```csharp
var value = new { Name = "Jeff", Year = 1964 };
System.Console.WriteLine(value.Name); // Jeff
```

后续姓名/年龄例E10-43b则是不同数据结构：

```csharp
var person = new { Name = "Jeff", Age = 30 };
System.Console.WriteLine(person.Age); // 30
```

匿名类型自C#3成为LINQ等临时投影常用的语言功能。它是编译器生成的引用类型，有可读属性，并具有相应的Equals、GetHashCode、ToString实现。典型元数据名称类似`<>f__AnonymousType0`，通常以内部密封类型表示；这是实现命名，不是在源码中可以直接书写的公开类型名，更不应说每次随意随机造一个新名字。

保留原生成类的表示目的，元数据概念示意E10-44：

```text
[CompilerGenerated]
internal sealed class <>f__AnonymousType0<TName, TAge>
    Name : TName（只读属性）
    Age  : TAge（只读属性）
    相应支持字段、构造器
    Equals / GetHashCode / ToString
```

这是示意，不是合法C#类型声明；编译器实际的泛型参数和字段名称以具体输出为准。只读属性也不意味着其中引用的对象自动深层不可变。

同一程序集内，属性名称、顺序和对应类型相同的匿名对象初始化通常形成相同的匿名类型；顺序不同不能仅因“看起来同样两项”就视为同一类型。类型存活也按正常可达性等规则管理，不因离开创建它的方法就立刻销毁。[匿名类型官方说明](https://learn.microsoft.com/en-us/dotnet/csharp/fundamentals/types/anonymous-types)。

<a id="c10-anonymous-object"></a>
### `object`参数、返回值与不能写出的显式类型名

完整程序E10-45保留原`Process(object)`、Jeff30和返回场景：

```csharp
using System;

class Program
{
    static void Process(object o)
    {
        // Console.WriteLine(o.Name); // 反例：静态object没有Name成员
        Console.WriteLine(o.ToString());
    }
    static object GetPerson() { return new { Name = "Jeff", Age = 30 }; }
    static void Main()
    {
        var person = new { Name = "Jeff", Age = 30 };
        Process(person);
        object o = person;
        // var p2 = (???)o; // 表达限制：没有可在源码中直接写出的匿名类型名
        Process(GetPerson());
    }
}
```

从匿名类型到object是引用转换，不是装箱。对象可以传出和返回，只是object静态类型不直接提供Name/Age成员。ToString、反射等仍可使用，所以“拿到object后什么都不能做”过强。方法返回类型位置不能写一个`new { ... }`匿名类型字面声明，也不能写问号占位符；这些表达的是静态API命名限制，不是对象禁止跨方法的运行时边界。

保留原返回签名反例的完整表示E10-45b（非法声明示意，不能编译）：

```text
public ??? GetPerson() {
    return new { Name = "Jeff", Age = 30 };
}
```

保留普通命名类型转回的对照E10-46（类型与语句片段）：

```csharp
class Person
{
    public string Name;
    public Person(string name) { Name = name; }
}

// 调用方方法体内：
object o = new Person("Jeff");
Person p = (Person)o;
System.Console.WriteLine(p.Name); // Jeff
```

这里可以直接在强制转换语法中写Person。对匿名类型，也有其他获得或使用静态类型的办法，不能把“无法直接写它的生成名称”推成“任何方式都无法转回”。

<a id="c10-anonymous-generic"></a>
### 保留限制并补出泛型、反射与dynamic的真实边界

完整程序E10-47（普通匿名类型与泛型为原书语境可用；dynamic场景在同一程序集执行）：

```csharp
using System;

class Program
{
    static object GetPerson() { return new { Name = "Jeff", Age = 30 }; }
    static T CastByExample<T>(object value, T prototype) { return (T)value; }
    static void Process<T>(T value) { Console.WriteLine(value.GetType().Name); }
    static void Main()
    {
        object o = GetPerson();
        var p = CastByExample(o, new { Name = "", Age = 0 });
        Console.WriteLine("{0}, {1}", p.Name, p.Age); // Jeff, 30
        Process(p);
        Console.WriteLine(o.GetType().GetProperty("Name").GetValue(o, null)); // Jeff
        dynamic d = o;
        Console.WriteLine(d.Name); // Jeff：本例的类型与使用代码同一程序集
        Console.WriteLine(p.GetType() == new { Name = "Alice", Age = 31 }.GetType()); // True
        Console.WriteLine(p.GetType() == new { Age = 31, Name = "Alice" }.GetType()); // False
    }
}
```

泛型类型推断得到`T`，转换仍需实际类型相符；不是把任意有Name/Age成员的对象都结构性转成这个类型。dynamic涉及绑定和可访问性，匿名生成类的内部可访问性会影响跨程序集使用；此例成功不保证在任意外部程序集都能直接`d.Name`。

原钥匙/锁与办公室便签的两个类比保留其目标：命名类型像有正式名称的标准表格，匿名类型便于临时组织姓名/年龄，无法在普通签名里直接填入其名字。便签本身可以被交给别的方法，只是接收者要采用适用的读取或类型推断办法；不能把类比说成物理上禁止传纸、禁止对象存活。

<a id="c10-anonymous-linq"></a>
### LINQ投影是典型用途，却不限在一个语句内部

完整程序E10-48保留原Age大于25的筛选与两种投影形式：

```csharp
using System;
using System.Linq;

class Person
{
    public string Name;
    public int Age;
}

class Program
{
    static void Main()
    {
        Person[] people = {
            new Person { Name = "Jeff", Age = 30 },
            new Person { Name = "Alice", Age = 20 }
        };
        var query = from p in people
                    where p.Age > 25
                    select new { p.Name, p.Age };
        foreach (var item in query)
            Console.WriteLine("{0}: {1}", item.Name, item.Age); // Jeff: 30

        var q = people.Select(p => new { p.Name, p.Age });
        foreach (var item in q)
            Console.WriteLine("{0}: {1}", item.Name, item.Age); // Jeff: 30；Alice: 20
    }
}
```

编译器在变量与foreach中保留了相应静态类型信息；序列可以在初始化语句外消费。原片段没有真正从方法返回query，不能把“得到一个序列值”说成已经演示了某个不存在的公开返回签名。

### 命名类、匿名类型与`System.Tuple`

原姓名/年龄需求首先使用命名类型E10-49（类型与方法片段）：

```csharp
public class NameAge
{
    public string Name;
    public int Age;
}

// 放在一个类型内部：
static NameAge GetPerson()
{
    return new NameAge { Name = "Jeff", Age = 30 };
}
```

如果只是临时装两个值，作者可能希望免去声明这个类。匿名类型与Tuple是不同选择，不是同一个机制重复讲两遍。

完整程序E10-50保留原Tuple返回、Jeff30与Item1读取：

```csharp
using System;

class Program
{
    static Tuple<string, int> GetPerson() { return Tuple.Create("Jeff", 30); }
    static void Main()
    {
        var data = GetPerson();
        Console.WriteLine(data.Item1); // Jeff
        Console.WriteLine(data.Item2); // 30
    }
}
```

System.Tuple在.NET4.0出现；原书C#5语境中已可使用。`System.Tuple<T1,T2>`是命名的泛型引用类型，Item1/Item2为只读属性，不是原示意所写的公有可写字段。它可以用于参数、返回值或字段的公开类型位置。泛型参数数量最大为8的形式把第8个位置用于Rest嵌套；这不是最多只能容纳8个数据元素，也不是所有参数都暴露为Item1到Item8。

先保留原“匿名类型与Tuple/ValueTuple”四维比较表，回应跨方法使用问题：

| 维度 | 匿名类型 | `Tuple` / `ValueTuple` |
| --- | --- | --- |
| 类型名称 | 生成名不能在普通C#类型位置直接书写 | 泛型类型名称可书写 |
| 成员名称 | Name/Age等语义名称 | Tuple用Item1/Item2等；现代值元组有元素名称语法 |
| 跨方法传递 | 可用object、泛型、dynamic等，但公开的强类型签名有命名限制 | 可直接给参数/返回类型命名 |
| 常见用途 | LINQ及临时组合 | 返回多个相关值、暂时数据容器；长期API也可选专门命名类型 |

原下一问另用“匿名类型与旧System.Tuple”五维表解释两节的衔接，比较范围与教学目的不同，分别保留：

| 维度 | 匿名类型（10.1.4） | `System.Tuple`（10.1.5） |
| --- | --- | --- |
| 提出动机 | LINQ等投影中省去额外类型声明 | 提供名称可写的数据组合API，不必为每一组合建专用类 |
| 类型名 | 生成名不能在普通C#类型位置直接书写 | `Tuple<T1,T2>`等名称公开可写 |
| 属性名 | Name/Age等语义化名称 | Item1/Item2等固定通用名称 |
| 能否跨方法 | 对象可跨方法；直接命名强类型签名受限，可使用泛型等路径 | 可直接声明为参数或返回类型 |
| 本质 | 编译器在当前程序集生成的类型 | BCL提供的命名泛型类 |

<a id="c10-value-tuples"></a>
### C#7的值元组与解构

现代完整程序E10-51保留原`(string Name,int Age)`、Jeff30、Name读取和解构：

```csharp
using System;

class Program
{
    static (string Name, int Age) GetPerson() { return ("Jeff", 30); }
    static void Main()
    {
        var p = GetPerson();
        Console.WriteLine(p.Name); // Jeff
        var (name, age) = GetPerson();
        Console.WriteLine("{0}, {1}", name, age); // Jeff, 30
    }
}
```

值元组的底层是ValueTuple结构体；元素名称主要是编译期表达，并通过相应元数据保留到需要的签名位置，不把运行时底层字段真正重命名为Name/Age。它有值复制语义，但装箱或嵌套在其他对象中仍可涉及堆存储，不能保证“因为struct永远省一次堆分配”。

匿名类型、Tuple、ValueTuple各有用途；原“老Tuple完全淘汰”是过强的当前状态结论。阅读原书时保留System.Tuple这一真实API，不把它静默替换成现代圆括号语法。[Tuple API](https://learn.microsoft.com/en-us/dotnet/api/system.tuple-2)、[值元组参考](https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/builtin-types/value-tuples)。

<a id="c10-indexer-names"></a>
## 索引器名称、默认成员及访问器调用

<a id="c10-vb-parameterized"></a>
### 有参属性可以有名称，C#索引器用`this[...]`

原问题两次引用“选择主要的有参属性”，关心为什么类型要指定默认成员。CLI元数据可以描述有参数的属性，C#主要以索引器语法表达这种实例成员；VB则允许声明具有不同名字的有参属性。

VB完整类型E10-52，保留原MyCollection的Item整数参数与Foo字符串参数，getter都返回空字符串、setter无操作。这只是展示签名和访问规则，没有虚构它保存了实际集合数据：

```vbnet
Public Class MyCollection
    Default Public Property Item(index As Integer) As String
        Get
            Return ""
        End Get
        Set(value As String)
        End Set
    End Property

    Public Property Foo(key As String) As String
        Get
            Return ""
        End Get
        Set(value As String)
        End Set
    End Property
End Class
```

VB调用语句片段E10-53：

```vbnet
Dim obj As New MyCollection()
Dim first As String = obj(1)
Dim second As String = obj.Foo("key")
```

Item被选为默认成员，省略属性名的`obj(1)`使用它；Foo要按相应VB语法明确写名称。两者的元数据都描述有参属性，默认标记并不把它们变成不同的CLR基础类型。

原另一轮的`MyClass`只给Item/Foo声明，是这个模式的简写；对于可执行的具体VB类，不能照抄没有访问器实现的参数化自动属性来声称已经提供完整实现。这里与前例的签名/参数/返回行为相同，合并到补齐后的E10-52，并明确简写的限制。

<a id="c10-default-member"></a>
### 默认`Item`和`DefaultMemberAttribute`

C#类型片段E10-54，保留原MyCollection空字符串getter和空setter：

```csharp
public class MyCollection
{
    public string this[int index]
    {
        get { return ""; }
        set { }
    }
}
```

编译器生成相应`get_Item(int index)`、`set_Item(int index,string value)`访问器，记录Item属性，并在类型上标记相应的`DefaultMemberAttribute("Item")`。DefaultMember保存的是**默认成员名称Item**，不是一个名为Item的普通方法，也不是字符串`get_Item`本身。

元数据示意E10-55保留原“编译后”例，使用文本表示以免和手写普通C#方法混淆：

```text
[DefaultMember("Item")]
MyCollection
    Item(Int32 index) : String（有参属性）
        getter → get_Item(Int32) : String
        setter → set_Item(Int32, String) : Void
```

具体C#代码中声明索引器时，相关默认成员特性由编译器处理，不能把这段示意再当作必须手写的重复特性。DefaultMember可以应用到适用的类、结构或接口，相关语言或反射通过它选择默认成员；普通访问器调用的每次执行不需要重新查这个名称。[DefaultMemberAttribute API](https://learn.microsoft.com/en-us/dotnet/api/system.reflection.defaultmemberattribute)。

<a id="c10-indexer-rename"></a>
### `IndexerName("Bit")`放在索引器上

原类型片段E10-56保留bool索引器返回false、setter空操作的签名场景：

```csharp
using System.Runtime.CompilerServices;

public class BitArray
{
    [IndexerName("Bit")]
    public bool this[int index]
    {
        get { return false; }
        set { }
    }
}
```

特性作用在索引器上，不是类上。原回答把`[IndexerName("Bit")]`放在BitArray类之前，那份代码不能用来证明正常的命名过程。

元数据示意E10-57：

```text
[DefaultMember("Bit")]
BitArray
    Bit(Int32 index) : Boolean
        getter → get_Bit(Int32) : Boolean
        setter → set_Bit(Int32, Boolean) : Void
```

对C#调用方仍写`bits[0]`；元数据中的属性名称与访问器名称变为Bit/get_Bit/set_Bit，并不增加一个可以按`bits.Bit(0)`调用的普通方法。[IndexerNameAttribute API](https://learn.microsoft.com/en-us/dotnet/api/system.runtime.compilerservices.indexernameattribute)。

<a id="c10-indexer-storage"></a>
### 自动索引器的原片段必须补实现

原后续问答给出具体类`MyList`的`this[int index] { get; set; }`。这不是自动实现属性的合法索引器写法：编译器无法仅由一个声明决定每个索引的数据放在哪里。保留其字符串索引器场景并补实际访问器E10-58：

```csharp
public class MyList
{
    private readonly string[] items = { "first" };
    public string this[int index]
    {
        get { return items[index]; }
        set { items[index] = value; }
    }
}
```

读取`new MyList()[0]`得到first，设置索引0为changed再读得到changed。这个有存储的例子与上一例只返回空字符串的签名示例条件不同，不合并。

原BitArray后续片段也使用自动get/set；补齐这个不同的可读写存储场景E10-59（类型与语句片段）：

```csharp
using System.Runtime.CompilerServices;

public class BitArray
{
    private readonly bool[] bits = new bool[8];
    [IndexerName("Bit")]
    public bool this[int index]
    {
        get { return bits[index]; }
        set { bits[index] = value; }
    }
}

// 调用方方法体内：
BitArray bitArray = new BitArray();
// bool b = bitArray.get_Bit(0); // 原C#静态直接访问器反例，应报CS0571
bool b = bitArray[0];
bool reflected = (bool)typeof(BitArray).GetMethod("get_Bit")
    .Invoke(bitArray, new object[] { 0 }); // 反射取得False
System.Console.WriteLine(b);             // False
bitArray[0] = true;
System.Console.WriteLine(bitArray[0]);    // True
```

索引0初值false，赋true后再读是true；数组索引超出范围按数组访问规则失败。类型在元数据仍对应默认Bit成员。它没有因为支持字段由自己声明就脱离有参属性规则。

原VB调用Bit的独立片段也保留（引用上面编译的类型）：

```vbnet
Dim bits As New BitArray()
Dim b As Boolean = bits(0) ' 默认有参Bit成员，此时为False
```

<a id="c10-string-chars"></a>
### `String.Chars`与反射访问

原String定义是简化示意，实际`System.String`不能在这里重新实现；正确的特性位置与元数据关系概念示意E10-60：

```text
System.String
    默认成员名称：Chars
    Chars(Int32 index) : Char（只读有参属性）
        getter：get_Chars(Int32) : Char
        对应索引器上的命名：IndexerName("Chars")
```

只读索引器没有setter，因此“每个属性一定生成两个方法”不是通用规则。元数据的名称是Chars，不是Item或源码关键字this。

完整程序E10-61保留原PropertyInfo/abc/索引0场景，同时对照无参Length：

```csharp
using System;
using System.Reflection;

class Program
{
    static void Main()
    {
        PropertyInfo charsProp = typeof(string).GetProperty("Chars");
        char c = (char)charsProp.GetValue("abc", new object[] { 0 });
        Console.WriteLine(c);                                // a
        Console.WriteLine(charsProp.GetIndexParameters().Length); // 1
        PropertyInfo lengthProp = typeof(string).GetProperty("Length");
        Console.WriteLine(lengthProp.GetIndexParameters().Length); // 0
    }
}
```

两者都能以PropertyInfo表示；可通过签名参数识别有参/无参。原`str="abc"; char c=str.get_Chars(0);`在普通C#静态代码中是访问器调用反例，不能当作成功代码；本节的反射路径正确取得a。不能说CLR“无法区分”有参/无参，只能说它们使用同一种属性元数据模型，而不是互不相关的两套成员机制。

思考区还独立声称VB可以调用`"abc".get_Chars(0)`。这个BCL字符场景也不能拿MyArray的整数结果替代；本机VB该直接调用报BC30456，正常路径如下：

```vbnet
Dim text As String = "abc"
' Dim c As Char = text.get_Chars(0) ' 原直接访问器反例：BC30456
Dim c As Char = text(0)            ' 默认Chars索引，c为"a"c
```

<a id="c10-indexer-overloads"></a>
### 同一个名称可按参数重载，不是一个类型只能有一个索引器声明

类型片段E10-62：

```csharp
public class Lookup
{
    public string this[int index] { get { return "index:" + index; } }
    public string this[string key] { get { return "key:" + key; } }
}
```

C#可以通过`lookup[1]`、`lookup["key"]`选择不同签名。原“只能有一个索引器”的说法应按同一个默认成员命名规则来理解，不是禁止重载。普通C#索引器声明没有`Foo[...]`这个命名语法位置；尝试写`public string Foo[int index]`不是合法声明。给同一类型的普通索引器重载选择不同IndexerName，也要遵循一致命名规则，不能凭特性任意创造多个默认名字。

原讨论还提到静态有参属性：CLI可以描述静态访问器与相关参数化属性，普通C#不提供静态索引器声明。只是“this表示实例”的助记解释，并非证明其他语言或CLI不能表达该签名。另有支持属性的语言，例如VB、C++/CLI，不应被列作“不理解有参属性”的例子。

<a id="c10-indexer-translation"></a>
### 三个角色与两次翻译

保留原“CLR裁判、C#球员、编译器翻译官”的类比，但修正实际分工：C#或VB编译器根据规则绑定成员并生成调用；CLR执行最终方法；反射在执行时可以查询成员描述。不能把VB的默认属性调用说成每次由CLR从DefaultMember开始逐项查表。

原`string s="Hello"; char c=s[0]`流程E10-63：

```text
C#调用处 s[0]
    → 编译/绑定阶段识别String相应的Chars索引器
    → 生成取得索引0字符的调用/适用IL
    → 运行时执行相应方法/优化后的操作，得到'H'
VB调用处 s(0)
    → VB按其默认成员规则绑定
    → 同样表达取得索引0字符的操作
```

原书Framework语境的调用签名示意如下，**不是本机程序集逐字IL导出**：

```il
call instance char [mscorlib]System.String::get_Chars(int32)
```

实际`call`/`callvirt`选择、核心库引用与后续优化要看编译产物；不能从这一示意说所有属性都固定采用该一条指令。

原“门牌贴纸、正门与其他门”类比表达默认成员选择：一个类型可以有若干入口，默认成员标签指出默认名称；重载还会看参数。糖纸/说明书类比说明源码外观与元数据名称相连，不意味着任何命名字符串都会自动变成可调用成员。

<a id="c10-accessor-calls"></a>
### 直接调用`get_`/`set_`到底会不会编译失败

这是用户最后的具体追问。需要分别判断：源码里正常支持的属性/索引器、元数据方法、反射、dynamic、其他语言，以及自己写的普通同名方法。

完整类型片段E10-64保留原MyArray、Element、Get/Set日志及返回索引值：

```csharp
using System;
using System.Runtime.CompilerServices;

public class MyArray
{
    [IndexerName("Element")]
    public int this[int index]
    {
        get { Console.WriteLine("Get Element called"); return index; }
        set { Console.WriteLine("Set Element called"); }
    }
}
```

调用方法中的片段E10-65：

```csharp
MyArray arr = new MyArray();
// arr.Element(1);     // 反例：不是名为Element的普通方法
// arr.get_Element(1); // 反例：C#静态调用正常索引器访问器，CS0571
int value = arr[1];   // Get Element called，value为1
arr[1] = 9;          // Set Element called；本例setter只打印，不存9
```

原单独写`arr[1];`也不是合法C#表达式语句；要像这里读取到变量或放入适用表达式中。访问器在元数据可以public，C#的调用语法限制并不使它变成private或不存在。直接以方法名调用同一访问器也不会跳过getter/setter里的逻辑，所以“为了防止绕过逻辑而禁止”不是准确解释。

保留手写普通属性对照E10-66：

```csharp
public class MyClass
{
    public int X
    {
        get { return 1; }
        set { }
    }
}
// 调用方方法体内：
// int x = new MyClass().get_X(); // 同样的普通C#访问器调用反例
```

是否自动实现不决定这个限制。与之不同，思考区独有的普通方法E10-67合法：

```csharp
public class OrdinaryMethod
{
    public int get_X() { return 1; } // 自己声明的普通方法，没有X属性
}
// 调用方方法体内：
int x = new OrdinaryMethod().get_X(); // 1
```

前缀get_不是一张自动赋予或禁止调用的通行证，要看它是不是相应属性的访问器。

<a id="c10-reflection-dynamic"></a>
### 反射与dynamic：保留原成功路径

在E10-64类型已经编译的条件下，反射调用片段E10-68：

```csharp
MyArray arr = new MyArray();
var getMethod = typeof(MyArray).GetMethod("get_Element");
object result = getMethod.Invoke(arr, new object[] { 1 }); // Get Element called，result为1
var setMethod = typeof(MyArray).GetMethod("set_Element");
setMethod.Invoke(arr, new object[] { 1, 9 });              // Set Element called
```

这里找到了public访问器，提供正确目标与参数，实际执行仍包括相应逻辑和可能异常。不是反射忽略任何可访问性或参数限制的普遍证明。

dynamic调用片段E10-69：

```csharp
dynamic arr = new MyArray();
int result = arr.get_Element(1); // 本机Framework动态绑定成功，打印Get Element called
```

这条源答的成功声称经本机验证确实成立，不能因为静态形式失败就把dynamic也改成失败。它把成员绑定交给运行时机制，并不把所有语法和运行时限制一概取消；具体对象、成员可访问性、参数与绑定器仍影响结果。

<a id="c10-thinking-myprop"></a>
### 思考区另一个`MyProp`命名例

完整程序E10-70保留MyIndexer、MyProp、不同Get/Set日志及索引1，不能只留正式答的Element例：

```csharp
using System;
using System.Runtime.CompilerServices;

public class MyIndexer
{
    [IndexerName("MyProp")]
    public int this[int i]
    {
        get { Console.WriteLine("Get called"); return i; }
        set { Console.WriteLine("Set called"); }
    }
}

class Program
{
    static void Main()
    {
        MyIndexer m = new MyIndexer();
        // m.MyProp(1);     // 反例：没有这个普通方法
        // m.get_MyProp(1); // 反例：普通C#静态访问器调用
        int value = m[1];  // Get called，value为1
        var method = typeof(MyIndexer).GetMethod("get_MyProp");
        method.Invoke(m, new object[] { 1 }); // Get called
        dynamic d = m;
        int dynamicValue = d.get_MyProp(1);   // Get called，dynamicValue为1
    }
}
```

思考区还用了getter返回空字符串的MyList/get_Item反例；它与前面默认Item的空字符串类型例属于同一签名/返回行为，合并其类型实现，但保留调用限制：静态`l.get_Item(1)`失败，正常`string text=l[1]`才是读取方式。对`"abc".get_Chars(0)`的静态直接调用同样不能当作成功的C#代码；E10-61保留了正确反射路径。

<a id="c10-vb-csharp-boundary"></a>
### VB与导入的非默认有参属性：不是所有语言都能直接调用所有访问器

原VB片段E10-71声称能直接调用MyArray的访问器，应作为纠正后的编译反例保留：

```vbnet
' 引用E10-64的C#类库
Dim arr As New MyArray()
' Dim x As Integer = arr.get_Element(1) ' 反例：本机VB编译报BC30456
Dim x As Integer = arr(1)               ' 合法默认索引：Get Element called，x为1
```

VB支持相应属性语法，却也会按本身规则处理访问器；不能写“VB完全没有屏蔽，所以直接get_都没问题”。C++/CLI等语言也要按各自规则判断，CLR层可执行一个public方法不等于每种语言都提供同一种源码调用入口。

另外，C#对导入的**非默认命名有参属性**可能暴露其访问器调用，这是原“C#永远不能get_”遗漏的不同场景。把E10-52 VB库编译后，C#调用方完整程序E10-72：

```csharp
using System;

class Program
{
    static void Main()
    {
        MyCollection obj = new MyCollection(); // 来自VB类库
        string a = obj[1];                    // 默认Item
        string b = obj.get_Foo("key");        // 非默认有参Foo的导入访问器路径
        Console.WriteLine(a == "" && b == "");// True：本例两个getter均返回空字符串
        // obj.get_Item(1);                    // 普通默认索引器的静态直接调用仍失败
    }
}
```

本机Framework C#编译、运行确认这个区分。C#通常的`obj[...]`语法按默认成员及其重载处理，不直接提供普通`obj.Foo[...]`声明/调用语法；能以其他入口执行非默认访问器，不推翻索引器语法的选择规则。[属性/访问器诊断说明](https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/compiler-messages/property-declaration-errors)。

| 原调用对照表的场景 | 本章核验后结论 |
| --- | --- |
| C#静态调用正常支持属性/默认索引器的get_ | 编译失败，使用属性或索引器语法 |
| public访问器的反射Invoke | 本例目标/参数正确时成功，执行相同访问器逻辑 |
| 本例dynamic的get_Element/get_MyProp | 本机成功；仍受实际绑定条件约束 |
| VB静态get_Element | 本机失败，默认索引`arr(1)`成功 |
| C#导入VB的非默认Foo有参属性get_Foo | 本机成功，与正常默认索引访问器限制区分 |
| 自己声明的普通get_X方法 | 可以普通调用；不是同名X属性的访问器 |

原“绕过属性，调用方法”强调语言外观最后映射到可执行方法；它不授权把一个语言中的合法调用照抄到另一个语言。属性关联、命名约定、可访问性与语言绑定规则一起决定实际入口。
