<a id="c14-char-model"></a>
## Char是UTF-16码元，静态与实例是另一分类

C#的char对应System.Char，属于struct，值宽度为16位。它表示UTF-16码元，不保证一个char就等于一个完整Unicode码点或一个用户看到的字符。普通非代理BMP例子中，码元数值恰好等于相应码点；代理对和组合序列要另外处理。

超过127只说明不在ASCII范围内，不自动需要代理对：例如¼的U+00BC仍是一个非代理BMP码元。非BMP码点在UTF-16中才要用相应代理对表达，不能把127当作UTF-16单双码元的分界。

类型是struct，不能推出来“它不允许实例方法”“它全部是静态工具成员”或“调用实例方法先要给每个值加对象头”。静态/实例由相应成员声明决定；一个值的存储、编译后的方法定义和调用方式分别是不同层次。

<a id="c14-char-static-call"></a>
### MinValue、IsDigit为什么不能从c访问

原问题的成员名分别是MinValue和IsDigit；`minval`/`isdigital`不是这两个区分大小写的API名称。Char.MinValue是**const字段**，按类型成员使用；IsDigit、IsLetter、IsWhiteSpace等分类方法为静态方法，接受要判断的输入字符。不能因为它们属于Char，就把它们当成一个c实例的无参方法。

MinValue为\0/U+0000，MaxValue为U+FFFF/65535；两者描述码元范围，不是所有Unicode码点都可以用一个char表示的承诺。

方法片段E14-01，保留原c='9'及正确/错误调用：

```csharp
char c = '9';
bool isDigit = char.IsDigit(c);
// 同样可写System.Char.IsDigit(c)。

// 反例，取消注释不能编译：
// bool wrong1 = c.IsDigit();  // 本机Framework csc：CS1501，无零参数重载
// bool wrong2 = c.IsDigit(c); // CS0176，不能通过实例访问该静态成员
// char wrong3 = c.MinValue;  // CS0176，const成员按类型访问
```

原注释把`c.IsDigit()`的诊断写成CS0117，实际核验为CS1501；缺参数的错误与静态成员访问方式的错误应分开。类似地，`int i = 5`不能使`i.MaxValue`成为合法调用，类型边界应从int.MaxValue取得。这是成员声明的规则，不是char或int“太小所以没资格有方法”。

原对照还举了String.Length和myStr.ToUpper：前者是实例属性，后者是针对当前字符串的实例方法。它们依赖相应实例，String是class也不意味着其中所有成员都是实例成员。

<a id="c14-char-extension-pattern"></a>
### 扩展语法与ASCII范围判断各自表示什么

类型片段E14-02，保留原CharExtensions的目的，用C#5可用的方法体：

```csharp
public static class CharExtensions
{
    public static bool IsDigit(this char c)
    {
        return char.IsDigit(c);
    }
}
// 在导入该扩展方法的适当范围和方法中：c.IsDigit()。
```

这增加的是扩展方法调用语法，不会重写System.Char的定义或将它的静态成员变成实例成员。原表达式方法体`=>`写法属于后来C#6语法；扩展方法本身早于它。

普通扩展方法从C#3即可使用，不能把这种形式一概说成只有最新语言才有。

原把下列范围比较说成现代替代，又把关系/逻辑模式标为C#7。要分别纠正：普通范围比较早已有；`>=`/`and`关系与逻辑模式是C#9的相应语法。两者下面都仅接受ASCII数字0—9，并不等于char.IsDigit所有Unicode十进制数字的语义。

方法片段E14-03a，各传统版本可表达的范围判断：

```csharp
char c = '9';
if (char.IsDigit(c))
{
    // 接受该API所判断的Unicode十进制数字。
}
if (c >= '0' && c <= '9')
{
    // 仅ASCII 0—9。
}
```

现代方法片段E14-03b，C#9关系/逻辑模式：

```csharp
switch (c)
{
    case >= '0' and <= '9':
        System.Console.WriteLine("Digit");
        break;
}
```

原9、全角３和圈数字①的实测对照，按“ASCII范围/Char.IsDigit”输出分别为True/True、False/True、False/False。选哪个判断必须先确定输入协议，不能把一个较窄集合一律称为更推荐、更快或语义相同的写法。

<a id="c14-struct-instance"></a>
## struct可以定义实例方法，设计动机不等于机制证明

原追问问“在struct里定义实例方法，再通过实例调用可行吗？”完全可行。方法片段E14-04保留int10的两个原调用：

```csharp
int i = 10;
string s = i.ToString();
int result = i.CompareTo(5);
```

ToString和CompareTo都可依据这个int的值完成操作；实例方法不必改变实例状态。“静态适合对输入操作，实例适合相应对象行为”是理解API的一个设计角度，不是规定所有只读判断必须静态的语法定律。原list.Add(item)、Math.Sqrt(d)和Char.IsDigit(c)也可用来比较这种表达目的。

原说明还把C标准库的isdigit(c)/isalpha(c)作为工具函数风格的类比。这个比较可以保留，不能据此声称微软早期选型的唯一历史主因已得到证实；C字符分类的输入/区域设置语义也不自动等于Unicode分类。C/C++的wchar_t宽度具有平台/实现背景，不能将所有wchar_t一概等同.NET的16位Char。

实例方法的值类型this通常以指向相应数据的托管指针/byref形式处理，不是每次必复制整个struct到一个新的物理栈对象。对临时值、属性结果或只读接收者等路径可能另有复制，须看具体代码；静态按值参数与实例byref的调用也不能保证固定的速度排序。IL计算栈是抽象执行模型，不能直接推出来参数机器级一定在物理栈而不可能在寄存器。

### DateTime和Guid两个原例

DateTime方法片段E14-05，把原无参实例IsLeapYear错误改为正确静态调用，保留同一用途：

```csharp
System.DateTime now = System.DateTime.Now;
System.DateTime tomorrow = now.AddDays(1);
bool isLeap = System.DateTime.IsLeapYear(now.Year);
// 原now.IsLeapYear()没有相应零参数调用；本机编译报CS1501。
```

Now是静态属性；AddDays及思考区提到的Add是相应实例操作，返回DateTime结果，不改变原now。这再次说明同一个struct可以同时有静态和实例API。

Guid方法片段E14-06：

```csharp
System.Guid g = System.Guid.NewGuid();
string s = g.ToString();
bool empty = g.Equals(System.Guid.Empty);
```

NewGuid与Empty、相应实例的ToString/Equals有不同声明和目的。不能把“struct主要是数据”解释成不能有自己的行为。

<a id="c14-nullable-char"></a>
### char?为null并不能证明静态API更安全

原Nullable<char>片段E14-07：

```csharp
char? c = null;
// c.IsDigit(); // Nullable<char>没有因为装着char就自动拥有其全部成员。
```

直接改成Char.IsDigit(c.Value)仍会在c没有值时抛InvalidOperationException。需要的条件是检查是否有值，而不是静态形式自动消除了null问题。

方法片段E14-08，在此场景给出明确缺值结果：

```csharp
bool isDigit = c.HasValue && char.IsDigit(c.Value);
```

当c为null输出False。其他业务可选择缺值时抛错/返回其他结果；它是Nullable契约的处理，不是对Char.IsDigit设计历史的证明。

<a id="c14-char-boxing"></a>
## 直接实例调用、装箱和方法内部行为要分开

原用户猜测“是否因为实例方法会装箱，所以Char才采用静态？”不能用这种一般规则解释。值类型直接调用相应实例实现，不必为了接收者先装成object；转object/某些接口路径、继承方法和方法内部操作又需分别判断。

类型片段E14-09a与独立方法片段E14-09b，保留原MyStruct例：

```csharp
struct MyStruct
{
    public void InstanceMethod() { }
}
```

```csharp
MyStruct s = new MyStruct();
s.InstanceMethod();
```

相应IL说明片段（省略其他初始化指令，非完整可汇编程序）：

```il
.locals init ([0] valuetype MyStruct s)
ldloca.s s
call instance void MyStruct::InstanceMethod()
```

这里取相应值的地址，没有为此调用要求一个box。作者另外给InstanceMethod加Count++作为可观察探针，调用后原s.Count为1，也否定“实例调用每次先复制整个this，所以只能修改副本”的泛化。实际方法可能还有别的分配或box，不能从这一条调用形式推断全部方法零分配。

<a id="c14-char-boxing-paths"></a>
### 原A字符的三个装箱场景

方法片段E14-10，转换object：

```csharp
char c = 'A';
object o = c;
```

常见生成IL包含box Char。另一个独立方法片段E14-11，对照原ToString和GetType：

```csharp
char c = 'A';
string s1 = c.ToString();
System.Type t = c.GetType();
```

Char提供自己的ToString实现，直接调用可用相应值地址；本机Framework生成GetType路径有box Char。GetType是Object的非虚实例方法，不属于“继承的虚方法未重写”的一个准确例子；现代JIT知道具体类型时可消除真实分配，见[第5章的IL与优化对照](第05章-基元类型、引用类型和值类型.md#c05-gettype)。ToString避免接收者装箱，也不表示生成字符串的操作绝无分配。

方法片段E14-12，保留非泛型IComparable的A/B例：

```csharp
char c = 'A';
System.IComparable comp = c;
int result = comp.CompareTo('B');
```

comp引用已装箱的A；这个接口的CompareTo参数是object，所以传入B还需要相应object转换。本机IL有两个box Char，不应只提接收者而漏参数。已装箱的接收者不因“接口调用”再装一次；相应泛型约束/constrained路径又可能不同，参见[第12章](README.md#chapter-12)。

<a id="c14-mychar-counterexample"></a>
### MyChar.IsDigit里面的Equals才是原反例的关键

原MyChar并未保存一个char字段，它的IsDigit写成this.Equals('0')，两个不同值类型之间的Equals不会把它变成Unicode数字分类。下面保留完整原场景，并明确它是错误的分类实现。

类型片段E14-13a：

```csharp
struct MyChar
{
    public bool IsDigit()
    {
        return this.Equals('0'); // 反例：MyChar与Char不是同一个值类型。
    }
}
```

独立方法片段E14-13b：

```csharp
MyChar c = new MyChar();
bool first = c.IsDigit();
bool second = ((object)c).Equals('0');
```

两结果均False。直接外层c.IsDigit的IL用值地址调用，但内部的Equals(object)已经包含Char参数的box，再通过constrained MyChar调用继承的Equals；未重写的相应继承实现还需按表示路径处理。第二条显式转换object又有明确接收者装箱路径。因此，“外层直接实例调用没有box”不等于“这个方法内部完全不会装箱”。

更具体地说，'0'转为Equals的object实参是一个装箱位置；constrained针对未由MyChar重写的Object/ValueType继承实现时，相应调用表示还可将接收者装箱，这是另一个位置，不能漏掉。前者在本机IL中明确box Char，后者不是同一条显式box MyChar，而在constrained继承调用的语义中判断；最终JIT可优化哪些真实分配再另看。

原解释给了“纯函数/按值输入减少别名修改风险”“静态便于内联”的设计角度，可以作为讨论：值参数的普通赋值不会修改调用方char变量。它不能保证极端unsafe/并发下所有共享数据都绝无改变，也不能替没有一手证明的设计动机作历史结论。实例只读判断同样可设计无副作用；JIT对静态和实例目标都可能优化。原将.NET1.0和泛型/AggressiveInlining混为同期条件也需纠正，后者不是原1.0已有机制。

读者可用ILSpy、ILDasm或SharpLab检查具体生成结果，分清外层调用、参数转换和方法体；这些工具显示的IL还不是最终优化机器码/真实分配的全部证明。

| --- | --- | --- |

<a id="c14-const-static"></a>
## Char.MinValue的const与IsDigit的static不是互斥选择

const表示相应编译期常量规则；类型中的const成员隐含静态性质，不能再写static。static说明成员属于类型，既可用于字段，也可用于方法等适用成员；它本身不意味着只读，更不把一个方法变成“运行时常量”。

Char.MinValue是固定的码元下界0；源码访问可按常量替换处理。IsDigit是执行判断的方法，不能给它加const修饰以代替方法逻辑；const也可声明局部常量，并非只修饰类型字段。它们回答的是不同问题：一个保存/表达固定值，一个提供类型关联的分类行为。

<a id="c14-const-static-table"></a>
### 原六维const/static对照表

| 特性 | const常量 | static成员的准确范围 |
| --- | --- | --- |
| 原赋值时机维度 | 声明时须合法常量表达式，值在编译期可知 | 静态字段按相应运行时初始化/赋值规则；普通static字段以后还可写，static方法不是被赋值的数值字段 |
| 原存储位置维度 | 常量资料与使用点的相应值/代码；普通整数无专用可变字段槽，代码/string等仍有成本 | 字段有相应类型关联存储，方法有代码/调用机制；不能统一说所有static成员都放一个Loader Heap数值槽 |
| 类型限制 | C#允许的常量类型/表达式；包括enum、decimal、string和相应引用null等 | 适用成员按语言规则声明，字段可以用更多类型，方法也有自己的签名和逻辑 |
| 原灵活性/版本维度 | 使用者已替换旧const值，采用新值通常需重编 | 字段读取或方法调用用实际加载的实现；需要正确部署和绑定，不是任意更新DLL只要重启必成功 |
| 原性能维度 | 替换可减少相应字段读取，但不能一概保证任何路径绝对最快或零成本 | JIT、调用路径及字段值处理影响成本，不能声称固定慢一档或纳秒差异 |
| 作用 | 表达需要按编译期常量契约使用的值，例如Math.PI、Char范围 | 提供类型关联的数据或行为，例如计数器、工具方法；本身不要求永不变化 |

“烧录进使用代码”的原比喻有助于理解const的版本问题，不意味着元数据/代码都不占内存。static readonly则约束相应字段重赋位置；对象内容是否可变是另一问题。详细语言规则和实际库更新50/50→50/60实验见[第7章](第07章-常量和字段.md#c07-versioning)。

原口诀“const给编译器看，static给CLR看”只能提醒替换和类型成员的不同用途；两者都经过语言编译与运行时执行/处理，不能划给彼此完全不知情的两个系统。

Q005末尾点名readonly/static readonly、线程安全及反射修改的学习方向也保留：只读字段的正常赋值限制不等整个对象/程序线程安全，反射写入的具体限制还取决字段及目标，详见[第7章](README.md#chapter-07)。不能把一个const/static分类直接当这些结论的证明。

<a id="c14-numeric-value"></a>
## GetNumericValue取得数学数值，整数强转取得码元值

原完整程序E14-18，保留3、¼和A三个输入：

```csharp
using System;
public static class Program
{
    public static void Main()
    {
        Double d;
        d = Char.GetNumericValue('\u0033');
        Console.WriteLine(d.ToString());
        d = Char.GetNumericValue('\u00bc');
        Console.WriteLine(d.ToString());
        d = Char.GetNumericValue('A');
        Console.WriteLine(d.ToString());
    }
}
```

原环境对应输出3、0.25、-1（数值格式受相应文化设置影响）。U+0033是字符3，其数学数值为3；U+00BC是预定义¼，数值为1/4；A没有该API可返回的数值，-1是无数值的契约标记。这里不是ASCII代码51/188/65，也不是从字符图形去做OCR识别。

原另外举了½、¾和⅓：对应0.5、0.75和近似1/3；1/5的十进制表示0.2是有限小数，不能将它也称作无限循环十进制。Double是这个API选择的返回类型，可表达分数/较大范围的近似值，但不是“任何有理数的唯一合理表示”，也不保证精确保存任意数值。源声称古代字符值一定超Int64而未提供具体数据，本章不据此编造一个字符或精度保证。

在本机Framework4.8和.NET10探针中，字符三(U+4E09)的GetNumericValue都返回-1；不能从“中文数学文本里三代表3”推定这两个API实现覆盖所有汉字数值语义。Unicode数据中的数值属性与一个库实际提供的读取范围仍要区别。

<a id="c14-digit-number-table"></a>
### 原IsDigit/GetNumericValue两行比较表

| 方法 | 关注点 | 返回值 | 典型用途 |
| --- | --- | --- | --- |
| Char.IsDigit(c) | Unicode十进制数字类别DecimalDigitNumber（Nd） | true/false | 判断相应十进制数字；不包括所有圈数字、罗马数字或分数字符 |
| Char.GetNumericValue(c) | 相应字符的数值信息 | double，或无数值时-1 | 获取API支持的数值含义；不是仅检查ASCII按键，也不直接返回码元编号 |

原将①和Ⅷ的IsDigit写成True，将²说成字母，均需要纠正。①为OtherNumber，Ⅷ为LetterNumber，²为OtherNumber；三者IsDigit均False，而IsNumber均True，GetNumericValue分别为1、8、2。IsNumber的类别范围与IsDigit不同，不要把两API名字混用。

十进制数字类别的相应数值为0—9，原“并非所有Digit有Numeric Value”的反向断言也错误；有数值的字符却不一定是Digit。API结果需以准确类别和数值规则判断。[IsDigit](https://learn.microsoft.com/en-us/dotnet/api/system.char.isdigit)与[GetNumericValue](https://learn.microsoft.com/en-us/dotnet/api/system.char.getnumericvalue)定义不同契约。

### 三种输入验证目的不能互相替代

原方法片段E14-19，作为“仅允许普通十进制按键”的错误策略保留：


原对应方法片段E14-20：

第三种目的可能是明确处理分数、罗马数字等数学文本，此时GetNumericValue有用，不能一律禁止将它的结果用于相应算术。是否接受哪些字符、如何解析多字符数及怎样处理近似结果，仍须由业务规则确定。“国际化程序”也可能有仅ASCII的协议字段；窄范围不是天然错误。

<a id="c14-code-numeric-map"></a>
## ASCII/Unicode编号与数学值是两层映射

原ASCII疑问问“一个int对应某个字符，不就是同一个东西吗？”编号与数值不是同一问题。ASCII定义0—127相应字符的编码映射；Unicode为更多字符分配码点，并提供相关属性。C# `(int)c`取得UTF-16码元整数值，当前这些非代理BMP例子才恰好等于相应Unicode码点。

方法片段E14-21，保留原3与¼的编号/数值输入。原变量名unicode_¼含不合法C#标识符字符（本机CS1056），改名不改变这个例子：

```csharp
int ascii3 = (int)'3';
int unicodeQuarter = (int)'¼';
double value3 = char.GetNumericValue('3');
double valueQuarter = char.GetNumericValue('¼');
```

分别为51、188、3和0.25。¼没有ASCII编码，不能把188说成其ASCII代码。原车牌类比完整保留：车牌沪A·0033与车里坐3个人是不同资料，看到号码0033不表示车里33人；同样，字符的编号51不意味着它代表数学51。

| 字符 | 当前BMP例的Unicode码点/码元整数 | GetNumericValue | 说明 |

<a id="c14-char-conversions"></a>
## Char强转、Convert和IConvertible：同输入的三种路径

原完整程序E14-25保留65、65536+65、70000及全部三种互转：

```csharp
using System;
public static class Program
{
    public static void Main()
    {
        Char c;
        Int32 n;
        c = (Char)65;
        Console.WriteLine(c);
        n = (Int32)c;
        Console.WriteLine(n);
        c = unchecked((Char)(65536 + 65));
        Console.WriteLine(c);

        c = Convert.ToChar(65);
        Console.WriteLine(c);
        n = Convert.ToInt32(c);
        Console.WriteLine(n);
        try
        {
            c = Convert.ToChar(70000);
            Console.WriteLine(c);
        }
        catch (OverflowException)
        {
            Console.WriteLine("Can't convert 70000 to a Char.");
        }
        c = ((IConvertible)65).ToChar(null);
        Console.WriteLine(c);
        n = ((IConvertible)c).ToInt32(null);
        Console.WriteLine(n);
    }
}
```

实际输出：

```text
A
65
A
A
65
Can't convert 70000 to a Char.
A
65
```

这些转换处理的是码元整数，不是GetNumericValue的数学数值属性。char是独立的C#类型，具有16位取值范围；不是把它与ushort认成同一种类型，就能解释所有重载和转换规则。

<a id="c14-char-truncation"></a>
### 65536+65为什么还得到A

原二进制过程保留，按32位整数表示：

```text
65         = 00000000 00000000 00000000 01000001
65536      = 00000000 00000001 00000000 00000000
65536 + 65 = 00000000 00000001 00000000 01000001

unchecked缩窄到Char：
原始值 [00000000 00000001] [00000000 01000001]
丢弃高16位                 保留低16位
得到65，当前BMP码元U+0041，显示为A。
```

65536为2¹⁶，第17位为1；unchecked缩窄保留低16位。原70000也可用来对比：32位是`00000000 00000001 00010001 01110000`，低16位`00010001 01110000`为4464。Convert.ToChar(70000)不采用这个截断结果，而抛OverflowException。

这里示意数值位运算，不保证真的将65601放进某个32位物理寄存器再截内存。本机C#编译原常量unchecked表达式直接得到ldc 65；变量路径才可见conv.u2，checked变量路径可见conv.ovf.u2。

<a id="c14-char-checked"></a>
### 常量编译错误和运行时检查要分开

原反例E14-26，放在适当方法中，不能编译：

```csharp
char c = (char)(65536 + 65); // 常量越界：CS0221
```

即便使用/checked-，相应常量表达式仍报CS0221；不是因为编译器默认把全部运行时转换检查打开。非恒定整数运算/转换通常默认unchecked，也可由编译选项或显式checked/unchecked改变。

方法片段E14-27，输入改为变量后观察运行时契约：

```csharp
int n = 65536 + 65;
char truncated = unchecked((char)n); // 65/A
// char rejected = checked((char)n); // 运行时OverflowException
```

checked相应整数/Char转换检查范围；unchecked允许按规定截断。这是选择语义，不是“checked仅给普通人，unchecked必然最快给专家”的人物分类或通用性能保证。Convert的Int32→Char重载按其契约检查0—65535；这个范围检查还不保证一个任意码元就是完整有效Unicode标量，例如代理码元仍可能落在该范围内。

<a id="c14-char-conversion-table"></a>
### 原三种转换比较表

| 转换方式 | 行为特点的准确范围 | 原代码 |
| --- | --- | --- |
| C#强转(Char) | checked/unchecked及常量规则决定是否拒绝越界或截断；不是永远不检查，也不必是内存复制 | c = (Char)65; |
| Convert.ToChar(Int32) | 检查该数值范围，越界如70000抛OverflowException；其他参数重载有其自身规则 | c = Convert.ToChar(65); |

原16升桶/32升壶与管家类比也保留：unchecked像只保留桶能容纳的部分；Convert的管家先拒绝不合范围的输入。但“16位”不是实际16升容量，水壶只有物理流量概念，不能从比喻算出程序速度或完整的数值语义。

<a id="c14-encoding-versus-numeric"></a>
## 编码整数与数值属性：门牌号和数值不是同一个问题

原确认问“这些转换是存储编码数字，不是意义上的数值，对吗？”在当前例子里，(Char)65给出码元U+0041，(int)c取得码元整数；GetNumericValue('3')给出数学值3。仍要保留“码元不总是完整码点”的范围，也不要说强转完全不进行数值运算。

<a id="c14-encoding-numeric-table"></a>
### 原两行操作对象表

| 原代码 | 操作的内容 | 准确名称/范围 |
| --- | --- | --- |
| (Char)65 | 取得16位值65，当前BMP例为U+0041/A | Char码元数值；本例恰等Unicode码点编号 |
| Char.GetNumericValue('3') | 取得字符3的相关数学数值3 | API的Numeric Value数值信息 |

原门牌号类比可以理解“65标识A”，与数学中的六十五、能做何种算术分开。源码转换本身按数值转换规则完成，不是在Unicode字形表里查图；将Char显示成A还涉及输出/字体。GetNumericValue同样不从图像认字，是根据输入编码取得相关数值信息。

原独立方法片段E14-28，保留半/全角编号与数学值的对照，统一错误十进制注释：

```csharp
int code1 = (int)'3';   // 51
int code2 = (int)'３';  // 65299
double val1 = char.GetNumericValue('3');  // 3
double val2 = char.GetNumericValue('３'); // 3
```

身份证号不同、职业同为数字3，仍是有用的比喻；但不能说这个API任意改变字符的存储编号，或直接转换根本不关心任何数值位规则。

## 字符串字面量：源码、元数据和运行时对象

原“语言将String视为基元类型”讲的是C#预定义类型和字面量等特殊语言待遇，不能只凭不用new的写法定义所有基元类型，也不能从class身份推出来所有对象只能显式new。

方法片段E14-31，保留原三个声明：

```csharp

```

string是System.String的语言别名，String为引用类型。本机反射String.IsPrimitive为False，Char为True；语言的预定义/字面量规则与这个CLR反射分类不是同一张清单。

<a id="c14-user-string-heap"></a>
### Hello在#US里，ldstr带相应token

方法片段E14-32：

```csharp
string s = "Hello";
System.Console.WriteLine("Hello");
```

普通托管编译结果可在元数据用户字符串堆#US记录相应字面量；IL的ldstr操作数是相应用户字符串token，不把整段文字直接作为ldstr指令中的可变长度文本。元数据表流#~与#US等堆流是并列的部分，原图把#US画在#~下面要纠正。

原MyProgram.exe结构图和0x70000001示意保留，调整层级：

```text
MyProgram.exe（概念结构，非固定文件偏移）
├── PE Header
├── CLR Header
├── Metadata根及相应流
│   ├── #~：TypeDef / TypeRef / MethodDef等表
│   ├── #Strings：名称等字符串资料
│   └── #US：用户字符串，例如"Hello"
│       └── 示意token 0x70000001 → 对应的用户字符串资料
└── IL Code
    └── ldstr 0x70000001
```

0x70表示用户字符串token的相应类别，低位在这里表示该堆的偏移；不是托管对象的内存地址，也不是普通元数据表的行号。具体token由实际编译结果决定，不能要求任何Hello都固定为000001偏移。

原整数/字符串对照方法片段E14-33：

```csharp
int x = 5;       // 典型IL可直接ldc.i4.5。
string s = "Hi"; // 典型IL用ldstr及相应#US token。
```

长度不定的字符串可能只有a，也可能像原例说的整本《红楼梦》，所以固定指令操作数引用字符串资料是容易理解的表示选择。它是CLI规定/编译模型，不是数学上“任何语言绝无另一种编码指令的可能”。运行时解析相应字面量并提供String引用；JIT、缓存或预编译实现可优化这条路径，不保证每次执行ldstr都新建一个对象或扫描一张全局表。

<a id="c14-literal-sharing"></a>
### 两个Hello同一实例与全局Intern池收录是两个范围

方法片段E14-34，同程序集普通string字面量正例：

```csharp

string b = "Hello";
System.Console.WriteLine(object.ReferenceEquals(a, b)); // True
```

C#规范对同程序集、按相应字符串相等规则等值的普通string字面量规定同一实例；不能把这个范围内的True全部说成无保证的巧合。[字面量规范](https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/language-specification/lexical-structure)明确这个范围。

全局Intern池是否收录、跨程序集/运行时生成字符串的引用、历史NGen和NoStringInterning、现代预编译环境等还需另判。NoStringInterning不要求字面量进入相应全局池，不能由此否定前述同程序集语言规则；String.Intern返回的canonical引用也不保证在所有运行模型中等于某个字面量引用。[Intern API说明](https://learn.microsoft.com/en-us/dotnet/api/system.string.intern)区分这些情况。

原new Hello的表达式写成`new string('H','e','l','l','o')`没有这样的五Char构造器；需按同目的改为char[]或其他适用构造。`new string('a',3)`则是合法的重复字符构造，与aaa字面量的内容相同不等于引用必须相同。这些例在下文分别保留。

<a id="c14-immutability-reason"></a>
### 不可变性不是PE页保护物理倒逼

元数据字面量资料与运行时String对象的表示要区别。对象可由字面量、托管数组或指针等产生；String不可变的公开契约有利于共享、留用、比较和其他运行时假设，不是因为“PE映射页只读/COW，所以数学上不可能实现可变对象”。构造器可把数据复制进独立的托管对象，字面量元数据并非它的可写对象字段。

“不能通过普通C#索引赋值改变String内容”与“把变量s换成另一个String引用”也要区别；后者是合法变量赋值，不会修改原对象。后面的实例操作可返回其他String，也可在适用情况下返回已有实例，不能说不可变便强制每次都新分配。

<a id="c14-string-construction"></a>
## 数组、指针和Span构造：复制数据，不能偷换来源和所有权

原问题问Char*或Sbyte*构造器为什么要unsafe。先看API参数：指针构造器的签名需要相应C#指针上下文；一般数组/重复字符构造不要求调用者写指针。内部实现可能使用本机帮助或unsafe操作，调用点安全范围与库内部实现不是同一层。

<a id="c14-constructor-kind-table"></a>
### 原两类构造器参数表

| 类型 | 参数的准确示例 | C#调用条件 |
| --- | --- | --- |
| 不要求调用点指针的构造器 | char[]；char[], startIndex, length；char, count等 | 满足正常参数/语言/API条件的托管调用；原char,int,int签名不存在 |
| 指针构造器 | char*、sbyte*及相应起始/长度/Encoding重载 | 指针声明/使用须在适用unsafe上下文，并启用相应编译支持；这不是一个CLR权限开关 |

原char[]Hello方法片段E14-35：

```csharp
char[] chars = new char[] { 'H', 'e', 'l', 'l', 'o' };
string s = new string(chars);
System.Console.WriteLine(s); // Hello
```

数组有托管类型/长度资料，相应库实现按契约处理。构造后的String内容不会因为随后将chars[0]改成X而变成Xello；作者实际验证原s仍Hello、用改后的数组再构造才Xello。正常API可有边界和参数检查，但不能将它泛称“运行时在JIT阶段证明任何业务都没有错误”。

<a id="c14-char-pointer-construction"></a>
### C#5式逐项填写栈缓冲区，再按明确长度复制

方法片段E14-36保留原5个char和Hello输出，需要/unsafe及相应上下文：

```csharp
unsafe
{
    char* p = stackalloc char[5];
    p[0] = 'H';
    p[1] = 'e';
    p[2] = 'l';
    p[3] = 'l';
    p[4] = 'o';
    string s = new string(p, 0, 5);
    System.Console.WriteLine(s); // Hello
}
```

这个buffer不是托管char[]，不用GC替它管理数组寿命；String构造器在有效范围内取得5个码元并形成相应String，不能在方法退出后继续使用逃出的栈指针。构造器不接管p的存储所有权，构造完成后的内容不依赖继续保持这个输入buffer。

源说“这里完全没有任何边界检查”过宽：指针重载仍会检查部分参数，如负长度/负起点；但它无法像托管数组那样从p本身证明实际分配大小、是否可读、是否已经释放。作者以有效p和-1长度得到ArgumentOutOfRangeException，没有为了试验而读取失效或越界地址。[构造器API](https://learn.microsoft.com/en-us/dotnet/api/system.string.-ctor)及[.NET10构造实现](https://github.com/dotnet/runtime/blob/v10.0.0/src/libraries/System.Private.CoreLib/src/System/String.cs)可反查这种区别。

<a id="c14-constructor-safety-table"></a>
### 原四维数组/指针对照表

| 场景 | 原数组构造器的范围 | 原指针构造器的范围 |
| --- | --- | --- |
| 参数来源 | 托管数组及已知相应类型/长度资料 | 原始指针可能来自栈、固定托管对象、本机模块或其他有效存储；指针不自带allocation长度证明 |
| 边界检查 | 相应API可以利用数组长度检查范围 | 仍有参数检查，但输入可读性、实际分配边界和寿命要有调用方条件 |
| 可验证性 | 适用托管调用可以构成可验证IL；不等任何业务永不出错 | 使用裸指针的具体IL通常不能获得相同的类型/内存验证保证 |
| 能否从非unsafe上下文直接使用指针参数 | 数组签名不要求调用者声明裸指针 | C#不能在普通安全范围使用char*/sbyte*参数；其他封装API的签名另判 |

<a id="c14-sbyte-pointer"></a>
### sbyte*不是将一个托管字符串直接当ANSI指针

原代码`(sbyte*)"Hello\0"`不能编译，本机CS0030；unsafe不会自动把托管String转换成有效8位字节地址。保留同一Hello/NUL场景的纠正方法片段E14-37，实际给字节buffer赋值：

```csharp
unsafe
{
    sbyte* p = stackalloc sbyte[6];
    p[0] = 72;  // H
    p[1] = 101; // e
    p[2] = 108; // l
    p[3] = 108; // l
    p[4] = 111; // o
    p[5] = 0;
    string s = new string(p);
    System.Console.WriteLine(s); // Hello
}
```

单指针形式按相应NUL终止规则读取；带起点/长度的重载有不同范围条件。8位字节不自带Windows-1252等特定编码身份，必须知道实际编码和平台约定。Windows上默认sbyte*重载按系统ANSI代码页的相应规则处理；非Windows适用实现的UTF-8规则不能直接套到所有Windows实例。

本机Windows ACP为936：Framework Encoding.Default为936，而.NET10 Default为65001；两环境将C3 A9交给默认sbyte*构造都得到U+8305，明确指定Encoding.UTF8的长度重载都得到U+00E9。说明“现代Encoding.Default是UTF-8”不能推出“Windows此指针重载也按UTF-8”。使用带Encoding的重载或相应Encoding API时，应明确实际字节协议。

原指出Encoding让编码意图更明确、错误编码易乱码，这项建议仍保留；不能把“多用托管API”说成它们会自动知道任意旧C字节数据的编码。

<a id="c14-modern-span-construction"></a>
### 现代Span例减少中间buffer堆分配，最终String仍复制

现代方法片段E14-38，C#7.3支持相应stackalloc初始化语法，需有String(ReadOnlySpan<char>)的目标API（例如.NET Core2.1+）：

```csharp
System.ReadOnlySpan<char> span = stackalloc char[5] { 'H', 'e', 'l', 'l', 'o' };
string s = new string(span);
System.Console.WriteLine(s); // Hello
```

不需要在源码中声明裸指针或unsafe；中间栈buffer/Span本身无需一个独立托管char[]。但构造最终String仍要按相应实现复制和通常分配对象，原“整个过程零堆分配”的结论错误。空结果等可能复用已有String.Empty；不能泛称所有构造都一定产生独立新对象。

使用指针可避免先创建额外托管数组，适用于明确的本机互操作、解析、序列化或网络缓冲区场景；它不免掉把内容形成String这一步，也不自动优于所有安全API。原思考里的“避免数组拷贝”应理解成避免不必要中间步骤，而非最终零复制。

<a id="c14-native-message"></a>
## GetMessage：保留本机库原例，明确ABI和内存寿命

原另一个完整Hello栈buffer程序E14-39保留初始化器形式，属于C#7.3语法而非旧C#5：

```csharp
using System;
public class Program
{
    public static void Main()
    {
        unsafe
        {
            char* p = stackalloc char[5] { 'H', 'e', 'l', 'l', 'o' };
```

栈来源只是这个例的分配方式，不是所有指针都unsafe、而所有栈访问都只能unsafe的充分推理；现代Span也可安全表示相应栈数据。裸指针的类型与访问规则才是C#上下文条件。

原C++动态库例E14-40a，Windows目标，字符串字面量用const wchar_t*返回以符合相应C++规则：

```cpp

{

```

对应C#完整程序E14-40b，实际库名MyCppLib.dll，显式指定此C++函数的cdecl约定与入口名称：

```csharp
// char* p = GetSomePointerFromSomewhere();

```

p单独不能证明它来自栈、堆、已释放区、另一个进程、内核或设备，也不能证明是5个还是500万个可读字符。一个用户进程里的整数地址并不授予跨进程/内核访问权限；非法读取常是进程访问违规等结果，不能泛称一读便让整个系统蓝屏。

### 原五维使用场景表

| 项目 | new string(char[])的范围 | new string(char*)的范围 |
| --- | --- | --- |

<a id="c14-string-copy-constructor"></a>
## new String("Hi there.")：旧书缺少相应重载，现代API范围变化

原提问担心“特殊构造器/unsafe，还是没有定义？”旧Framework中不存在String(string value)这一签名，所以上述string参数没有适用的相应构造调用；与unsafe上下文是两件事。本机Framework csc报CS1503（不能将相应参数转成适用的char[]等），原CS1729“完全不存在一参数构造器”注释不准确，char[]/char*等本就有一参数重载。

旧目标方法片段E14-41，故意保留反例：

```csharp
System.String s = new System.String("Hi there."); // Framework目标：不能编译。
```

原Java对照也保留（是Java程序中的语句，不是C#）：

```java
String s = new String("Hi there.");
```

不能由C#旧库没有某个签名推定“用字符串构造字符串属于循环定义”“字符串不可变便逻辑禁止副本”，也不能虚构微软有唯一已证实的反Java设计动机。不可变内容允许共享通常使复制不必要，但这是讨论用途和成本，不是类型系统禁止另一种构造的证明。

<a id="c14-modern-string-span-conversion"></a>
### 现代相同源码可能通过Span构造器成功

具有String(ReadOnlySpan<char>)的现代目标，例如.NET Core2.1+，可利用相应string→ReadOnlySpan<char>转换。作者在.NET10、语言版本7.3实测E14-41可以编译，输出Hi there.；反射GetConstructor(string)仍为null，结果与字面量是不同引用。这没有创造一个隐藏的String(string)签名，而是实际可用构造器集合和转换发生变化。

原两对变量情景因此分别说明：

```csharp
string s1 = "Hi there.";
string s2 = new string("Hi there."); // 旧Framework反例；有相应Span API的现代目标可成立。
```

独立方法片段，原abc同目的例：

```csharp
string a = "abc";
string b = new string(a); // 同样按目标API及转换规则判断。
```

若本意只是以后将b赋成另一段文本而不影响a，直接保存原引用也不会使不可变String内容随变量重赋变化。若确有复制/缓冲区等目的，再选择适用API；不能说任何副本一律无意义，也不能说共享只读字符数据必然“破坏封装”。

<a id="c14-copy-alternatives"></a>
### Copy、char[]和常量拼接三个原方式

历史Framework方法片段E14-42，保留Hi there.和ReferenceEquals输出：

```csharp
string s1 = "Hi there.";
string s2 = System.String.Copy(s1);
System.Console.WriteLine(object.ReferenceEquals(s1, s2)); // 本机Framework：False
```

这是.NET的API，其他适用.NET语言也能调用，并非C#语言独占。现代差异：从.NET Core3.0起String.Copy标为过时，官方也提示某些实现/情况不保证得到新引用；不能把它当作所有版本可靠的“强制新对象”接口，更不应为修改不可变String而依赖它。[Copy API](https://learn.microsoft.com/en-us/dotnet/api/system.string.copy)说明替代目的和限制。

原完整char[]内容的构造方法片段E14-43：

```csharp
string s = new string(new char[] { 'H', 'i', ' ', 't', 'h', 'e', 'r', 'e', '.' });
```

这直接说明并非只有String.Copy能形成同内容String。相应Span构造或其他合适API也有自己的用途，是否新引用和具体分配仍按契约/目标看。

原拼接例E14-44：

```csharp
string s = "Hi " + "there.";
```

它是常量字符串表达式，编译器可折叠成Hi there.字面量；本机与同程序集Hi there.字面量ReferenceEquals为True。不能把任何加号/插值形式都说成隐式运行时新对象。运行时拼接的输入和实现需要另看。

<a id="c14-copy-object-count"></a>
### Copy("Hello")究竟创建几个对象

原方法片段E14-45：

```csharp
string s = System.String.Copy("Hello");
```

元数据中保存Hello资料，不等于编译期已经存在一个运行时String对象。历史Framework例中，如果字面量对象已可用，Copy可再产生一个同内容对象；此时看到两个String引用对象，不等于这条表达式恰好新分配了两个。如果还要解析/物化字面量或运行时允许复用，额外分配次数又不同。现代Copy限制更不能忽略。

所以原“一定1个、因为literal编译期早就存在对象”的理由要纠正：分开**已有对象数、此操作新增对象/分配数、元数据字符串资料数**，给定运行时和先前状态才有可判断的具体答案。不可变对象的复制用途、字面量加载和普通构造的输入形式也不是“成品绝不能当另一个构造的原料”的硬规则。

<a id="c14-unsafe-mechanism"></a>
## unsafe：C#指针上下文、IL验证与运行策略是三层

原问“加unsafe才可使用构造器，这个机制怎样实现？”指针类型char*/sbyte*的声明、参数和使用要在相应C# unsafe上下文内；这个范围可以来自方法、类型或块等适用声明，不要求每个方法自己单独写同一关键字。编译还需允许unsafe的选项/项目支持。

原调用片段E14-46：

```csharp
// p为char*时，其声明/使用须在适用unsafe上下文：
// string s = new string(p);
```

指针出现在普通安全范围，本机报CS0214；标unsafe却未允许相关编译，本机报CS0227。源T将两个诊断混为“出现指针就CS0227”需纠正。编译器检查上下文与类型，不是C#把一个字符串关键字传给CLR，要求从此关闭所有安全检查。[unsafe规范](https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/language-specification/unsafe-code)定义语言范围。

<a id="c14-constructor-signatures"></a>
### 原指针构造签名清单

签名说明E14-47，保留两个数组与五个指针重载；这是API签名摘示，不是可自行编译的无主体String类。指针声明处也要有相应unsafe范围，原先说“定义不带unsafe”、后又说“带unsafe”的矛盾不能当两种机制。

```text

String(char[] value, int startIndex, int length)
String(char* value)
String(char* value, int startIndex, int length)
String(sbyte* value)

```

Encoding参数的可空标注与具体源码/语言版本另判，不能将C#8的Encoding?表面语法倒写成旧C#5完整声明。CoreCLR源码有相应构造与运行时帮助，不应把未核实的FString::NewString、CLSID_STRING等名字当所有版本必用的入口。

如果一个unsafe方法的**公开可见签名没有裸指针**，普通C#调用点仍可按相应规则调用。例如作者的unsafe int F(){return 1;}可被safe Main调用，输出1；它的IL还被PEVerify接受。不是unsafe关键字在调用链里无限“传染”，指针类型如何暴露和实际方法体要分别看。

<a id="c14-verification-instructions"></a>
### Verifier不只看某条指令名字是否“危险”

原列出的ldind/stind、cpblk/initblk、localloc和native int涉及不同类型/地址条件。不能说任意ldind/stind或native int一出现都验证失败：使用合法managed byref的读写可以是可验证代码，native int也是CLI可表达的数值/平台类型，不能一概等同非法裸地址操作。

作者安全ref读写/IntPtr探针输出7、9、17，PEVerify为0；Read(ref int)的真实IL含ldind.i4。空的unsafe方法也被接受。这与真正包含localloc/裸指针构造调用的例验证失败形成具体对照，不能用关键词替代验证规则。

原栈分配/构造路径的IL说明E14-48（省略其他初始化和方法结构，非完整程序）：

```il
.locals init ([0] char* p)
ldc.i4.s 10
localloc
stloc.0
// 实际代码先填入5个char，不能把未初始化buffer当Hello输入。
ldloc.0
ldc.i4.0
ldc.i4.5
newobj instance void [mscorlib]System.String::.ctor(char*, int32, int32)
```

这个具体指针样本在Framework PEVerify报告不可验证，而在本机Framework运行正常。**符合可移植验证规则、具体工具接受、宿主是否允许执行**不同；源码unsafe不是一项CLR“跳过验证”方法标志。旧Framework宿主/信任策略可能限制不可验证程序集，手写IL/ILGenerator绕开C#检查也不能当作已经满足这些策略；现代AOT并非凡unsafe都拒绝。

原SQL Server CLR Host的例子应按其实际宿主规则、程序集/信任设置与版本理解，不能拿来证明所有unsafe代码在每个SQL或AOT环境都必拒加载。本章未提供可用于任意当前服务器的统一配置结论。

<a id="c14-fixed-string"></a>
### fixed是固定地址的语法方式，不是safe代码绝无pin能力

原方法片段E14-49，保留hello与固定String来源：

```csharp
unsafe
{
    string s = "hello";
    fixed (char* p = s)
    {
        // 在相应固定范围内可将有效p交给需要的指针读取API。
    }
}
```

fixed可在这一范围维持对应地址条件；编译产物中的pinned局部与指针访问要按实际IL理解，不是一条“GC从此不敢动任何对象”的全局指令。它不证明传给别的函数的任意长度正确，也不允许把p逃出应有寿命。

GCHandle等托管API也可以提供适用固定能力，所以原“只有unsafe有pin权力，因为pin影响GC所以safe绝不可以”的因果错误。safe语言形式减少某类裸内存错误，不保证任何业务没有异常或任何进程绝不会终止；P/Invoke也可以通过IntPtr和适用封装使用，不是所有互操作都要求用户写指针。

原两层“门禁”和免责声明比喻应理解为：语言检查、CLI验证与宿主执行政策各有工作，程序员仍需明确来源条件。它不承诺默认模式所有程序绝不崩溃，也不承诺unsafe必定“零复制且极限性能”。

<a id="c14-interning"></a>
## 留用、字符串共享与String的特殊实现

原译注中的“拘留/拘留池”和本书采用的“留用”都在对应interning/Intern Pool，不是三个不同API。教学上可将相应池理解成按内容取得canonical String引用的共享仓库；但不能说所有同内容String对象都自动只有一个实例。

原仓库映射图保留，表示概念关系而非某个版本必须采用的全部物理结构：

```text
相应字符串内容 → 池中的canonical String引用
```

<a id="c14-intern-original-examples"></a>
### Hello的字面量、新数组构造和手动Intern

方法片段E14-50，将原s1/s2/s3/s4三段连接起来，保留输入和本机正常CLR结果：

```csharp
string s1 = "Hello";
string s2 = "Hello";
System.Console.WriteLine(object.ReferenceEquals(s1, s2)); // True：同程序集字面量。

string s3 = new string(new char[] { 'H', 'e', 'l', 'l', 'o' });
System.Console.WriteLine(object.ReferenceEquals(s1, s3)); // 本例False。

string s4 = string.Intern(s3);
System.Console.WriteLine(object.ReferenceEquals(s1, s4)); // 本机正常CLR例True。
```

最后一个True还利用了本例Hello已在相应池里的环境条件；Intern对于同值取得其canonical引用，不把s3变量自己改成那个引用，也不保证所有运行模型中的池引用必等于某字面量。要使用返回值s4，不能把一次调用当原对象被原地改造。[Intern](https://learn.microsoft.com/en-us/dotnet/api/system.string.intern)与前述同程序集规范分别提供保证。

思考区独有的重复字符例E14-51也保留：

```csharp
string generated = new string('a', 3);
bool sameReference = object.ReferenceEquals(generated, "aaa"); // 本机False。
```

内容相同与引用相同不同。动态创建、StringBuilder.ToString结果通常不自动改用某canonical引用，不能由此推出池中一定没有相同内容。

<a id="c14-isinterned-content"></a>
### IsInterned查内容条目，不是“这个实例是否就是池中对象”

原StringBuilder.He+llo示例E14-52，纠正其第一条输出：

```csharp
string dyn = new System.Text.StringBuilder().Append("He").Append("llo").ToString();
string found = string.IsInterned(dyn);
System.Console.WriteLine(found == null); // 本例Hello条目已存在：False。
System.Console.WriteLine(object.ReferenceEquals(dyn, found)); // False。

string interned = string.Intern(dyn);
System.Console.WriteLine(string.IsInterned(interned) != null); // True。
System.Console.WriteLine(object.ReferenceEquals("Hello", interned)); // 本机例True。
```

IsInterned返回的是按输入**内容**找到的相应池引用，未找到才null；输入可以是一个未作为canonical对象使用的新实例。原“dyn是动态生成，所以IsInterned(dyn)==null一定True”的推理错误。当前方法若含Hello字面量，解析/JIT等路径也可能在实际执行该查询之前已经使相应内容可查。

源声称现代每个AssemblyLoadContext有各自独立Intern池，思考区又犹豫改为每个CLR实例，不能采用这个猜测。作者在.NET10将同一个普通库分别加载到两个collectible ALC，库类型身份确实不同；两边对同一动态生成内容调用String.Intern得到同一个引用，也与默认调用得到的canonical引用相同。这足以否定本例中“每ALC相互隔绝的池”，不扩为任意多个CLR实例/历史AppDomain都必有同一完整生命周期。

<a id="c14-intern-immutability"></a>
### 共享的前提、1000处Hello和比较成本

原非法方法片段E14-53，假设内容可变时会影响别的共享使用者，但普通C#不能这样写：

```csharp
// 反例：String索引器不能赋值，本机CS0200。
// s1[0] = 'h';
// System.Console.WriteLine(s2);
```

不可变的公开契约使共享内容不会被正常String操作偷偷改变，也支持许多优化/使用假设；sealed与不可变是不同概念，不能从任意class sealed就推出来它全部字段/状态都不变。

原1000处Hello的内存例应保留并限定：如果原来保留1000个独立生成的同内容String，改保留相应canonical引用可以减少长期保留的重复内容；但同程序集的1000个相同字面量已有前述语言共享，不能声称没有全局留用便必创建1000个对象。对已经生成的对象再逐个Intern也不会撤销之前的临时分配/计算，还可能增加相应池的保留成本。

两个**已知在同一canonical机制下**的引用可用ReferenceEquals作相应常量时间身份判断。它不替任意两个非canonical字符串完成值相等；建立/查找canonical条目可能要处理内容，不能拿最终一次引用比较O(1)说整个留用过程毫无成本。

<a id="c14-string-layout"></a>
## CLR认识String的特殊布局，但不能伪造一般继承会移动基类字段

String是sealed，其变长内容和运行时识别的类型/字段帮助CLR实现字面量、长度、索引和GC等相应行为。普通字段访问也可能由JIT解析后直接按offset读取，不是每次都先遍历元数据TypeDef再找Field，因而不能用这个虚假的对照制造String“全部独有的极快优势”。

原布局图保留为概念图（不是固定32/64位字节偏移承诺）：

```text
String托管对象的概念布局
├── 运行时对象/类型信息
├── 字符串长度（UTF-16码元个数）
├── 第一个Char及其后续内联码元序列
└── 相应实现需要的结束/对齐等细节
```

这里不是另有一个独立托管char[]字段对象被每个String引用。Framework参考源使用m_stringLength/m_firstChar，现代相应源用_stringLength/_firstChar等；实际布局要与运行时定义一致。它的长度属性有get_Length API/相应实现，JIT可将适用路径内联或按已知字段作intrinsic优化，不能说C# IL里根本不存在getter调用。[Framework参考源](https://github.com/microsoft/referencesource/blob/main/mscorlib/system/string.cs)与[.NET10 String源](https://github.com/dotnet/runtime/blob/v10.0.0/src/libraries/System.Private.CoreLib/src/System/String.cs)显示这些具体实现关系。

<a id="c14-string-sealed-counterexamples"></a>
### 三个不同目的的继承反例

原加字段的类型反例E14-54a，不能编译：

```csharp
public class MyString : System.String // CS0509：String密封。
{
    public int ExtraField;
}
```

原企图修改底层内容的独立反例E14-54b：

```csharp
public class MutableString : System.String // 同样不能编译。
{
    public void Modify(int index, char c)
    {
        // 原假设：能直接修改底层内容；实际类型不能从String派生。
    }
}
```

原仅验证sealed的空类型反例E14-54c，与前两类目的不同：

```csharp
public class MyString : System.String // 独立片段；不能编译。
{
}
```

源说“普通派生类只加一个ExtraField，就一定把基类length的offset从4挤到8、CLR必越界”不是一般继承规律。基类字段的布局/访问可以由类型模型维持，增加派生字段不必移动原基类字段。String的特殊变长表示与精确类型/不可变契约受运行时特别处理，sealed约束有相应设计用途，不能用一个并不存在的MyString内存布局当实证或逻辑证明。

同样，源假设“只重写ToString就能改掉原String底层内容”也混淆返回值和对象修改。String已有密封契约，反例用来说明禁止派生；不模拟unsafe破坏留用内容来伪造支持。

<a id="c14-string-runtime-assumptions"></a>
### 哈希、跨域与GC假设需要具体版本

原列出的不可变与运行时关系保留，但不能照抄实现细节：相应GC知道String的非引用码元表示，可以按类型信息处理，而不把每个char当托管引用扫描；历史Framework跨AppDomain/相关共享要按对应运行时加载规则理解，不等所有现代上下文一概一份或无限相同寿命。

源还说String.GetHashCode首次后在每个String对象里缓存，后续只读缓存。不能把这个写成普遍事实：所核Framework参考实现和.NET10相应哈希实现从内容计算，没有这个通用的每对象哈希缓存契约。集合/留用表可保存其条目的hash，那与String.GetHashCode对象缓存不是一件事。[现代相应比较/哈希源](https://github.com/dotnet/runtime/blob/v10.0.0/src/libraries/System.Private.CoreLib/src/System/String.Comparison.cs)可反查具体路径；不得把hash持久化成跨进程/版本不变身份。

原逻辑链图保留为有范围的设计联系：

```text
需要高效文本处理/共享
→ 运行时认识String的特殊表示与相应契约
→ 不可变内容可安全共享，sealed限制相应派生/类型行为
→ 可以实施适用的字面量/留用/长度/GC等优化
```

这不证明一般不可变类型必须sealed，也不要求所有运行时布局永远不变、每个String操作都new或全部优化都固定为一种实现。

思考区独有的公司文具柜类比完整保留：大家从柜里取同一支“不能被偷偷涂改”的笔，像取得共享的不可变内容；柜子按规定规格管理，不能随意塞一支未经对应设计支持的加长笔再假定原操作都适用。它帮助理解共享内容与特殊类型契约，不能真的证明“任何继承都会挤走原字段”。

StringBuilder是可变构造工具，其ToString形成相应不可变String；并不因此自动保证生成结果已经作为池中canonical对象使用，也不免除所有复制/编码/比较成本。后续分别讨论它的容量和文本操作。

| 按语言习惯排序 | 语言学比较Linguistic | 通讯录姓名、OrderBy显示列表；要选定相应文化/比较选项 |
| 判断同一个程序key | 序号比较Ordinal等相应身份规则 | 协议/字典key/enum名等常需明确序号模式；文件名、路径、注册表/环境变量还要满足实际OS/协议大小写等约定 |

CurrentCulture通常是当前线程/异步执行环境的文化，可由程序和环境选择；不保证等于“这台机器用户所有语言偏好”，也不等同专供资源显示的CurrentUICulture。zh-CN、en-US、de-DE是原文化名示例。

InvariantCulture提供相应不依赖当前用户文化的设置，适合需要明确可重复格式的保存/交换等用途；它不是“任何排序数据永不变化的en-US别名”，也不自动是配置key/网络协议相等的最佳比较器。格式化/解析数值时选Invariant与比较程序身份时选Ordinal，是不同的选择。[比较最佳实践](https://learn.microsoft.com/en-us/dotnet/standard/base-types/best-practices-strings)说明相应场景和排序数据变化。

Ordinal比较按UTF-16码元序号语义处理，不是逐个完整Unicode码点的排序，也不是必须先把字符串编码成字节来比较。OrdinalIgnoreCase提供相应不依赖当前文化的忽略大小写规则；它不是任意字体/宽度/语言学等价的全部规范化。实现可能优化比较，不能保证任何字符串/平台上总有一种固定最快方法。

<a id="c14-comparison-apis"></a>
### 原CompareTo、Compare、==/Equals和StringComparer

方法片段E14-55，保留apple/Banana与显式Ordinal例：

```csharp
int linguistic = "apple".CompareTo("Banana");
int ordinal = string.Compare("apple", "Banana", System.StringComparison.Ordinal);
```

String.CompareTo的默认相应比较仍基于CurrentCulture；String.Compare无指定比较方式的相应重载也有自己的文化默认。原“Core变成另一套单词+文化混合规则”的说法不准确：文化、比较选项和NLS/ICU等排序引擎/数据版本是要分开的层次。[文化比较说明](https://learn.microsoft.com/en-us/dotnet/core/extensions/performing-culture-insensitive-string-comparisons)可核对这些默认值。

相应字符串的==与默认String.Equals是区分大小写的序号值相等，例如abc与ABC为False。不能一般用默认CompareTo==0替代这个Equals，因为语言学关系可能不同。Compare支持ignoreCase/CultureInfo等重载，使用时按具体契约显式选择条件，不能只见方法名就认定所有重载同一种语义。

原四种比较器入口保留：StringComparer.Ordinal、OrdinalIgnoreCase、CurrentCulture、InvariantCultureIgnoreCase。比较器对象可用于排序或相等/hash协议，创建/使用时要理解相应文化和大小写范围。

方法片段E14-56，原File/FILE字典：

```csharp
var dict = new System.Collections.Generic.Dictionary<string, int>(
    System.StringComparer.OrdinalIgnoreCase);
dict["File"] = 1;
System.Console.WriteLine(dict["FILE"]); // 1
```

默认Dictionary<string,T>的相应key判断区分大小写；同样只添加File，默认字典并没有FILE这个键。是否忽略大小写应由key契约决定，不能一律推荐OrdinalIgnoreCase。

### straße/STRASSE不能写成任何德语比较都0

原两个输入和操作关系E14-57，完整保留：

```csharp

string b = "STRASSE";
var previous = System.Threading.Thread.CurrentThread.CurrentCulture;
try
{
    System.Threading.Thread.CurrentThread.CurrentCulture =
        System.Globalization.CultureInfo.GetCultureInfo("de-DE");
    System.Console.WriteLine(string.Compare(a, b, System.StringComparison.CurrentCulture));
    System.Console.WriteLine(string.Compare(a, b, System.StringComparison.CurrentCultureIgnoreCase));
    System.Console.WriteLine(string.Compare(a, b, System.StringComparison.Ordinal));
    System.Console.WriteLine(a == b);
}
finally
{

}
```

比较结果通常应看负/零/正，不依赖具体非零数值。当前Framework环境的敏感比较符号为负、忽略大小写为0；当前.NET10环境分别为正、正。Ordinal符号为正，==为False。原对区分大小写CurrentCulture注释0不符合这两个实际环境；Ordinal整串还有s/S等差别，不只一处ß/S。

原还说straße.ToUpper(de-DE)会得到STRASSE，两个环境实际均得到STRAßE，未把ß展开成两个S。文化比较与大小写映射本就不是同一个算法；不能用某次ToUpper的结果证明所有语言学等价。NLS与ICU以及其数据更新会影响相应排序/查找行为；[全球化与ICU](https://learn.microsoft.com/en-us/dotnet/core/extensions/globalization-icu)说明平台/配置范围，不把本机结果扩成永久文化定律。

思考区独有的西班牙语ll例也保留：特定传统西班牙语排序可能对这种序列有特殊处理，不能泛称所有现代西班牙语文化/排序版本都把ll同样对待。CompareInfo/SortKey提供相关比较/排序资料入口；若用缓存排序键，还要考虑所选文化、选项和版本，不能自动把它当Ordinal身份。

<a id="c14-intern-performance"></a>
### 100万次比较：循环内Intern并没有免费O(1)

原两种列表遍历E14-61，保留100万/大量重复的场景和Hello条件；GetManyStrings是原未提供实现的来源函数，以下是方法/算法片段：

```csharp
// 原规模情景：约100万条，有许多重复；来源方法需由应用实现。
System.Collections.Generic.List<string> list = GetManyStrings();
foreach (string s in list)
{
    if (s == "Hello") { /* 原相应工作 */ }
}

string hello = string.Intern("Hello");
foreach (string s in list)
{
    if (object.ReferenceEquals(string.Intern(s), hello)) { /* 同一匹配目的 */ }
}
```

第一种相等实现可以先检查引用、null、长度等，不是每次必遍历所有字符。第二种最终ReferenceEquals为身份比较，但循环内String.Intern仍要按内容查找/登记，可能涉及hash、比较和保留；不能把整条表达式算成只有一次O(1)指针比较。

如果应用先取得并长期保留同机制的canonical引用，再重复作相应身份比较，可能获益；收益要抵扣准备/查找/分配与保留成本。长字符串、重复率、次数和生命周期都有影响，原“越长就必巨大提升”不是无需测量的保证。

原另列的三个实际用途场景都保留：Web请求中反复出现的URL，日志模块名Database/Network，配置文件key。若它们来自高基数/短寿命输入，自动全部Intern未必适合；用户上传文件名、GUID等大量不同内容会改变保留成本。1000个独立同内容对象改用canonical引用可以减少相应保留内存，但不能撤销此前1000个输入对象的分配，也不能将同程序集1000处字面量当必有1000对象。

### 原10万长串压力例说明保留，不能作所有实现寿命证明

<a id="c14-pooling-versus-interning"></a>
## 编译期相同字面量资料去重，与运行时留用不同

本书该上下文的字符串池化谈编译结果中的重复字面量资料；runtime interning谈相应canonical引用。一般资料说“字符串池/Intern Pool”时，那个“池”也可能直接指运行时池，原T关于词义依上下文的提醒保留；不要看到pool一个词就固定翻译成磁盘。

方法片段E14-63，保留原Hello/Hello/World：

```csharp
string s1 = "Hello";
string s2 = "Hello";
string s3 = "World";
```

同模块编译可让两个Hello的ldstr使用相同#US条目，World使用另一条目。原ILDASM示意把World当token70000002，误当顺序行号；#US token低位是字节偏移，Hello资料不只一个字节，不能这样推数值。

纠正后的IL说明E14-64（token数值由实际编译决定，非完整可汇编程序）：

```text
#US条目：Hello，World，各按实际堆偏移定位
ldstr <Hello token>
stloc.0
ldstr <同一个Hello token>
stloc.1
ldstr <World token>
stloc.2
```

编译资料去重有助于减少相应文件表示；它不是编译期创建托管对象。运行时可解析/缓存字面量，也可通过Intern处理运行时内容，但不能概括成每个程序启动都把整个#US全部新建对象并全量塞进一张池，再让每条ldstr重复查那张表。

<a id="c14-no-string-interning"></a>
## NoStringInterning是允许选择的标记，不是永久忽略或强制禁用

原问题的关键字是“可能”：CompilationRelaxationsAttribute与CompilationRelaxations.NoStringInterning提供对应放松/不要求相应字面量留用的标记。C#常见编译器会输出这个标记，不等生成结果非法，也不等运行时必须立即关闭留用；源说默认加“相反标志允许Intern”不正确。

原属性示意E14-66，放在合法程序集特性位置：

```csharp
[assembly: System.Runtime.CompilerServices.CompilationRelaxations(
    System.Runtime.CompilerServices.CompilationRelaxations.NoStringInterning)]
```

本机Framework编译的探针无需手工添加也看到值8（相应标志）。同程序集两个Hello仍ReferenceEquals为True。原许可证类比可理解成“允许实现按该条件选择”，而不是“我命令你绝不留用”，也不是“所有Microsoft实现铁律永远无视”。历史NGen及不同运行模型的相应行为有实际适用条件，不能仅把这件事归给非微软嵌入式CLR。

原提出小内存嵌入式运行时、追求启动速度的实现两种假设场景仍保留：它们说明实现可能考虑不同成本，不是已验证某个产品拒绝建立全部池；也不能说C#加标记仅为了满足规范而有唯一已证实的史因。[该标志API](https://learn.microsoft.com/en-us/dotnet/api/system.runtime.compilerservices.compilationrelaxations)和[Intern API](https://learn.microsoft.com/en-us/dotnet/api/system.string.intern)给出对应意义/实现范围。

<a id="c14-string-switch-value"></a>
### 字符串switch不以全局留用身份作为匹配前提

原把switch(string)的优化归结为“所有字面量必Intern”，要纠正。C#字符串case按相应值匹配；编译器可以选择不同lowering，未必每个switch都使用同一哈希表或总比if-else快。

作者验证片段E14-67，动态aaa和字面量引用不同仍能命中：

```csharp
string s = new string('a', 3);
System.Console.WriteLine(object.ReferenceEquals(s, "aaa")); // 本机False
switch (s)
{
    case "aaa":
        System.Console.WriteLine("matched");
        break;
}
```

输出False/matched。它说明内容匹配不能偷换成只有canonical对象才匹配；具体优化和成本应看相应编译器生成代码/运行环境。

<a id="c14-text-units"></a>
## 码元、Unicode标量和文本元素：Length并没有“数错”

String.Length按UTF-16码元计数；它不是用户感知字符数的API，因此看到代理对长度2并不说明Length“骗人”或实现不准。先确定需要遍历的是码元、完整标量还是相应文本元素。

原Deseret方法片段E14-68，保留字符𐐷及值U+10437：

```csharp
string s = "𐐷"; // U+10437：DESERET SMALL LETTER YEE。
System.Console.WriteLine(s.Length); // 2
```

原“大写长I”标签错误，[Unicode16数据](https://www.unicode.org/Public/16.0.0/ucd/UnicodeData.txt)定义此名为小写YEE；大写长I是另一编码。当前字符的UTF-16代理对D801 DC37正确，两码元表示一个非BMP标量。

<a id="c14-surrogate-pairs"></a>
### 😀、代理对和相应API

U+10000—U+10FFFF范围的Unicode标量在UTF-16中用代理对表示：高代理D800—DBFF、低代理DC00—DFFF。不是所有emoji都在非BMP范围，一些BMP符号及相应序列也可具有emoji显示用途。

方法片段E14-69，保留😀/h/l与输出，并用C#5格式写法：

```csharp
string s = "😀";
char h = s[0]; // D83D
char l = s[1]; // DE00
System.Console.WriteLine(char.IsHighSurrogate(h)); // True
System.Console.WriteLine(char.IsLowSurrogate(l));  // True
System.Console.WriteLine(char.IsSurrogatePair(h, l)); // True
int codePoint = char.ConvertToUtf32(h, l);
System.Console.WriteLine("U+" + codePoint.ToString("X")); // U+1F600
```

IsHighSurrogate/IsLowSurrogate识别相应半个码元；IsSurrogatePair检查有效的高/低组合，ConvertToUtf32转换为相应标量值。思考区另提的ConvertFromUtf32提供相应反向String表示入口。单独取某一半不等取得完整字符，显示为替代图形等也不证明存储值“没有意义”。

UTF-16并不是C#/String在1999年建立后才从定长变长；Unicode2.0在1996年已加入相应代理/UTF-16模型。[Unicode编码FAQ](https://www.unicode.org/faq/utf_bom.html)说明UCS-2旧术语与UTF-16的历史区别。

<a id="c14-combining-characters"></a>
### a+重音与思考区的ă

原方法片段E14-70：

```csharp

System.Console.WriteLine(s.Length); // 2
System.Console.WriteLine(s);        // 常见字体可显示为带acute的a。
```

U+0061与组合acute U+0301是两个码点/码元，可形成一个相应文本元素；直接写预组字符á(U+00E1)与这一序列的原始值不相同，规范化或相应语言比较是另外的操作。显示是否一个字形、占多少列还受渲染/字体影响。

原T独有的ă也保留并纠正组合标记：ă(U+0103)可对应a+combining breve U+0306；不是把a与独立符号ˇ拼起来就得到它，也不是combining caron U+030C的ǎ。

<a id="c14-stringinfo-version"></a>
### StringInfo的版本边界不能只说“人眼最准”

.NET5起StringInfo/TextElementEnumerator按UAX29扩展字素簇处理，旧Framework/旧Core在某些序列上的分段不同。[官方兼容性记录](https://learn.microsoft.com/en-us/dotnet/core/compatibility/globalization/5.0/uax29-compliant-grapheme-enumeration)明确该变化。

作者补充验证的woman-astronaut ZWJ序列、US旗帜区域指示符对、挥手+肤色序列，码元数分别5、4、4；Framework文本元素数3、2、2，当前.NET10均1。源仅凭“StringInfo最准”推荐给所有UI编辑，遗漏了这些历史版本条件。

字素分段也不是词、音节、显示列数或任何用户心中字符单位的全部定义。协议解析、UI光标/删除等场景应该选定相应单位及版本，不能把char方案一律“最快”或StringInfo方案一律“永远最准”当不用检查的保证。

<a id="c14-rune-modern"></a>
### 现代Rune是标量入口，不是任意码点盒子

现代方法片段E14-72，需要相应.NET Core3.0+等API，保留原四个值：

```csharp
string s = "A😀a\u0301";
foreach (System.Text.Rune r in s.EnumerateRunes())
{
    System.Console.WriteLine("U+" + r.Value.ToString("X"));
}
```

输出U+41、U+1F600、U+61、U+301。Rune表示Unicode标量，排除孤立代理码点；原string.GetRuneAt名称不准确，相应静态入口为Rune.GetRuneAt等。仍要处理非法UTF-16输入和目标API的替换/异常契约，不能从一个Rune的出现推定任意String本就有效。

书的主要语境是相应旧Framework/C#版本，不能将后来Rune或.NET5分段行为倒写进旧例。String可以说是char/UTF-16码元的序列，原末句“不是char的串，是码元的串”其实将同一含义硬分成两种东西，应理解为“不能把每个char自动当文本元素”。

<a id="c14-string-operations"></a>
## 其他String操作：内容不改，不代表每次必分配新对象

下面保留原正式答和思考区的各组输入/用途。String操作不能通过正常API改掉原内容；有些需要产生相应新结果，有些在全范围、空结果或无变化等条件下可以复用对象。不能从“不可变”推出来每动一刀都必有一项新String分配。

### 变量加号、常量加号、明确Concat与集合Join

方法片段E14-75a，保留原两个变量：

```csharp

```

<a id="c14-format-operation-examples"></a>
### Alice30、price12.5和思考区宽度10的独有格式例

方法片段E14-77a：

```csharp
string name = "Alice";
int age = 30;
string info = string.Format("Name: {0}, Age: {1}", name, age);
System.Console.WriteLine(info); // Name: Alice, Age: 30
```

原货币格式E14-77b，固定en-US只为让展示结果明确：

```csharp
decimal price = 12.5m;
string s = string.Format(System.Globalization.CultureInfo.GetCultureInfo("en-US"),
    "Price: {0:C}", price);
System.Console.WriteLine(s); // Price: $12.50
```

不提供provider时，当前文化可使货币符号、分组和小数等不同，不能普遍注释成$。IFormattable是数值等参数按格式/文化输出的一项契约；定制formatter和不实现该接口的对象还会有相应处理/回退，Format不是无条件只调用一个接口。

思考区独有E14-77c保留右对齐宽度10：

```csharp
decimal price = 12.5m;
string s = string.Format(System.Globalization.CultureInfo.GetCultureInfo("en-US"),
    "Price: {0,10:C}", price);
System.Console.WriteLine(s); // Price: 后面的字段前导4空格，再$12.50。
```

货币字段$12.50长度6，宽度10补4空格；模板Price:后本身还有一个空格，不能与字段padding混数。原3空格注释错误。对齐是对应文本宽度单位，不保证字体/非BMP/组合序列恰同显示列数。

现代方法片段E14-78，原C#6插值目的保留：

```csharp
string info = $"Name: {name}, Age: {age}";
```

它可以表达同一结果，但不是所有编译器/目标都固定降成String.Format。现代handler/拼接等不同lowering还影响中间处理、boxing和分配；不能把源码语法糖永远等同某个旧实现。格式化/自定义provider在后续专题再完整展开。

### Hello大小写与FileName规范化目的

```csharp
string s1 = "Hello";
string s2 = "Hello".ToUpper();
```

| Concat(+) | 常量可折叠、适用空/单片段可复用、其他结果有相应构建 | 循环反复累积可有重复长复制；不一律极差 |
| Replace | 改变结果要形成内容；无匹配等可返回原引用 | 数据量/匹配次数/重载决定，不固定“中等” |
| ToUpper | 依输入/文化/实现取得相应结果，可能复用 | casing与分配/文化成本另看，不预设固定级别 |
| Insert | 按原值与插入内容形成相应结果；空操作等另判 | 位置/长度/次数决定，不一律“差” |

### 思考区独有的String/StringBuilder四维表

原思考区三列四行比较表单独保留，不与正式答的操作成本表合并。

| 操作/维度 | String | StringBuilder |
| --- | --- | --- |
| 修改 | 普通API不改原内容；可新结果，也可在条件下复用 | 修改相应可变内容；仍可能扩容/产生中间分配 |

<a id="c14-clone-copy"></a>
## Clone、Copy和Array.Clone：接口名字不保证深拷贝

String.Clone的API返回当前实例引用；ICloneable本身不统一承诺深拷贝，所以不能把这个契约称为一个无效的“假方法”，也不能因字符串共享就推所有Clone同样实现。方法片段E14-90保留原Hello：

```csharp
string s1 = "Hello";
string s2 = (string)s1.Clone();
System.Console.WriteLine(object.ReferenceEquals(s1, s2)); // True
```

原“钥匙多配了一把，房子仍是那一套”的类比帮助理解两个变量都可引用同一不可变String。它是引用获取，不必先重建同内容对象；通过ICloneable处理异类对象时仍要看相应实现合同。

<a id="c14-clone-copy-operation-table"></a>
### 原补全五行操作表

| 操作 | 适用示例 | 行为范围 | 原备注的修正 |
| --- | --- | --- | --- |
| Clone | s.Clone() | String返回this，类型为object需相应转换 | 不可变共享有用，不将ICloneable泛成深拷贝 |
| Copy | String.Copy(s) | 旧Framework可复制；现代过时/引用保证有限 | 不移除/改变原Intern条目，也不一律可靠“打破池” |
| Substring | s.Substring(0,3)等合法参数 | 取得相应子串；全范围等可复用 | 原无参Substring不是适用调用 |
| Concat | String.Concat相应输入 | 形成相应合并结果，空/单片段/常量等另判 | 加号lowering和库重载决定步骤 |
| Replace | s.Replace(oldValue,newValue) | 替换相应匹配内容；无匹配等可返回原引用 | 不能既写无匹配复用又总结必new |

历史方法片段E14-91，保留Hello.Copy身份与值两种比较：

```csharp
string s1 = "Hello";
string s2 = System.String.Copy(s1);
System.Console.WriteLine(object.ReferenceEquals(s1, s2)); // 本机Framework False
System.Console.WriteLine(s1 == s2); // True
```

现代Copy限制与现代new string(s)的Span适用情况见[前文](#c14-string-copy-constructor)。原“只有Copy能复制”“唯一用途是打破Intern”的绝对说法不成立；char[]/Span等输入可形成适用的新String，Copy也不从池里删除原值。

<a id="c14-copy-pinning-scenario"></a>
### Test与独立寿命/Pin场景

方法片段E14-92保留Test四引用关系：

```csharp

string c = System.String.Copy(a); // 历史Framework复制例。
```

源另给底层性能测试、希望独立生命周期、Pin非托管交互且不影响池对象的场景，这些用途都保留。它们应选择能满足具体身份/可变buffer/寿命需求的API，不能依赖现代Copy总新引用；固定一段需要可控内容的char[]等也有自身协议。拥有另一个同内容String不表示全局池里的值已被删除或不再保留，也不自动保证任何固定操作不影响其他共享者。

“99%/99.9%业务不需Copy”没有本章统计；可按公开API现状和实际需求解释为什么普通不可变内容操作通常不需先复制。所谓逻辑复制/物理复制是帮助理解引用和内容处理的说法，不必升级为所有库都统一定义的两类复制协议。

### 数组A/B的Clone是另一个原例

方法片段E14-93：

### 原四行引用/新实例/留用关系表

| 方法/操作 | 行为 | 是否产生新String | 相应Intern关系 |
| --- | --- | --- | --- |
| 赋值= | 对已有String引用作赋值 | 该引用赋值本身不产生新String | 不自行更改任何池条目 |

<a id="c14-builder-members"></a>
## StringBuilder成员：可变构造与快照，各原输入分别保留

StringBuilder可修改其相应字符内容，适合某些重复构造/编辑场景；“String不可变性的补丁”是原教学说法，不表示String本来有一个必须修复的语言错误。操作Builder、形成String快照、保留/留用结果是不同动作。

原便签纸类比完整保留：容量像可写格子，有效长度像已经写下的格子；Append/Insert/Remove/Replace像涂改，ToString像复印成正式文件，便签纸仍可继续修改或Clear再用。实际实现可分块/分配新buffer，不承诺所有文字物理上在同一张不增长的纸。

<a id="c14-builder-capacity"></a>
### Capacity、Length与默认16

方法片段E14-94，原20容量/Hello输入：

```csharp
var sb = new System.Text.StringBuilder(20);
System.Console.WriteLine(sb.Capacity); // 20
System.Console.WriteLine(sb.Length);   // 0
sb.Append("Hello");
System.Console.WriteLine(sb.Length);   // 5
System.Console.WriteLine(sb.Capacity); // 本例20
```

Length是当前有效码元数，Capacity是相应容量数值，不是用户感知字数/显示列数；默认构造通常容量16。Framework4及现代相应实现采用分块等设计，Capacity不能不加条件直接定义成“唯一内部char[]的长度”，也不等所有物理分配数组空间之和。

原16→32→64增长方向和List类比可以说明部分小规模增长，但StringBuilder不是所有操作都严格单数组翻倍、每次把全部旧字符复制走。分块/当前块重新分配、请求的最小大小和实现限制会影响路径；应按所选版本源码/实际操作核对，而不是用List的一个实现替它证明全部行为。

思考区另用水杯类比：容量是可装多少、Length是现有水量、MaxCapacity是相应上限属性。杯子不是这个API所有超限行为的规范，下面保留实际边界。

<a id="c14-builder-maxcapacity"></a>
### 原Max100例成立，但MaxCapacity不是任何Append的硬日志限额

方法片段E14-95，保留原10/100/100个a/下一个b：

```csharp

sb.Append('a', 100);
// sb.Append('b'); // 作者两环境该给定例抛ArgumentOutOfRangeException。
```

默认MaxCapacity可为Int32.MaxValue，不表示实际能分配约21亿码元，也不保证设一个上限就不会有内存不足。官方明确指出Framework4+等实现的部分小字符串Append/AppendFormat可使Length/Capacity超过MaxCapacity；不能把它当可靠的安全/业务硬上限。[MaxCapacity API](https://learn.microsoft.com/en-us/dotnet/api/system.text.stringbuilder.maxcapacity)记录该边界。

作者补充的最小反例用capacity4/max5，7次Append("a")后两环境Length7、Capacity8、MaxCapacity5。它不推翻原给定Max100最后一步的真实异常，只说明不能将那个单例扩为所有调用绝不超过Max。

原T独有“日志最多1024码元”的场景保留：若合同要求这个硬限，要明确检查/截断/拒绝策略，不只构造MaxCapacity=1024便认为任何日志输入都被限制。真实总字节/文本元素数若是另一合同，还要按对应单位处理。

<a id="c14-builder-ensure"></a>
### Ensure1000及T中预计10000

方法片段E14-97：


<a id="c14-builder-append-numbers"></a>
### 0—9两个完整循环，结果相同不代表固定对象数

方法片段E14-98，保留两个独立累积路径：


<a id="c14-builder-complete-example"></a>
### Capacity100、Today日期与Prefix/C#的综合原例

完整程序E14-104保留初始化、追加、格式、插入、替换、删除、ToString、Clear复用全流程，改正“删除15个码元就总删完日期”的原错误。

```csharp
using System;
using System.Globalization;
using System.Text;
class Program
{
    static void Main()
    {
        StringBuilder sb = new StringBuilder(100);
        Console.WriteLine("初始：Capacity={0}, Length={1}", sb.Capacity, sb.Length);
        sb.Append("Hello");
        sb.AppendLine(" World!");
        DateTime now = DateTime.Now;
        int dateStartBeforeInsert = sb.Length;
        sb.AppendFormat(CultureInfo.CurrentCulture, "Today is {0:D}", now);
        int dateLength = sb.Length - dateStartBeforeInsert;
        Console.WriteLine("追加后：Length={0}", sb.Length);
        sb.Insert(0, "Prefix: ");
        sb.Replace("World", "C#");

        int dateStart = sb.ToString().IndexOf("Today", StringComparison.Ordinal);
        if (dateStart >= 0) sb.Remove(dateStart, dateLength);
        string result = sb.ToString();
        Console.WriteLine("\n最终结果：");
        Console.WriteLine(result);

        sb.Clear();
        sb.Append("Reused StringBuilder");
        Console.WriteLine("\n复用后：");
        Console.WriteLine(sb.ToString());
    }
}
```

原用AppendFormat("Today is {0:D}",DateTime.Now)构造日期；这里保留真实AppendFormat动作，用追加前后的Length差得到dateLength，避免重复读取日期或猜15。保留原格式/Now语义、Prefix和World→C#输入，删除后内容为Prefix: Hello C#!及相应换行，复用后为Reused StringBuilder。初始容量/长度100/0，追加后长度随文化/当天日期/换行而变，不伪造固定所有输出。

作者可复跑探针固定2026-10-05和Invariant：原Remove15还留下“, 05 October 2026”，按datePart.Length才去掉完整日期。这个受控日期只是验证原范围bug，没有用它替代原代码的DateTime.Now用途。

<a id="c14-builder-usage-boundaries"></a>
### 使用场景、线程与现代GetChunks

原建议的未知次数循环拼接、较大HTML/JSON/SQL构造、反复Insert/Replace等场景都保留；少量2—3个已知片段或很短字符串也可能直接Concat等更合适。不能只靠次数把性能固定排序，亦不能说“需要Intern所以不能用Builder”：Builder结果仍可按实际内容和寿命决定是否登记/保存canonical引用。

多线程并发修改同一Builder通常需要明确同步/设计；ConcurrentBag不是一个让这个实例的Append原子化的替代。不可变String的正常内容不变有助共享，但不替任意变量发布、复合操作或应用协议保证全部线程安全。

思考区独有的现代GetChunks入口也保留：支持该API的目标可枚举相应ReadOnlyMemory<char>块，可能避免先整体ToString只为读取内容。它不是原猜测的GetStringBuilder方法名，也不允许在枚举/借用期间随意修改Builder并假定所见内容稳定；目标版本与相应API条件另看。

本轮源答后半87块与前半逐字相同，正文合并完全重复内容；这里仍保留每个不同正式/T输入和操作，以及两个来源位置的追溯。不能将这么多方法仅缩成一句“StringBuilder比较快”。

### 导读点名的Jeffrey/Marc/Richter原书过程

<a id="c14-builder-chars"></a>
## StringBuilder.Chars：读写某个码元

Chars在C#中表现为索引器`sb[index]`。String的索引器只读；Builder可改有效范围中的一个char，长度不会因此改变，也不借赋值自动扩容。来源：Q025。

E14-105，Hello首字母的读写及原String的Remove/Insert对照：

```csharp
StringBuilder sb = new StringBuilder("Hello");
Console.WriteLine(sb[0]);              // H
sb[0] = 'h';
Console.WriteLine(sb.ToString());      // hello
string s = "Hello";
// s[0] = 'h';                        // 编译不允许
s = s.Remove(0, 1).Insert(0, "h");   // hello
```

Builder这次赋值不需要生成一份新String作为中间结果。已知位置直接改一个码元通常比先查找或删再插更直接；它仍不等于任意长度、布局、算法下都“最快”。索引使用UTF-16码元单位，不能把一个代理项或组合标记误当可独立修改的完整文本元素。

<a id="c14-builder-chars-bounds"></a>
### 读与写的异常不同，Release也检查边界

源码需要先在块链里找到包含相应索引的块，再访问块内数组。不能把`sb[i]`解释成无条件`m_ChunkChars[i]`，也不能从数组下标推出任意Builder索引都O(1)。原伪代码的意图是“先检查有效长度，再读写”；其正确示意应保留两个异常路径：

```text
get(index)：找包含index的有效块；找不到有效位置 → IndexOutOfRangeException
set(index, value)：找包含index的有效块；找不到 → ArgumentOutOfRangeException
                  找到 → 仅改该块的对应char
```

这两项异常在旧Framework和现代源码/本机Release验证中一致。原思考区声称“只Debug检查、错误索引未定义行为”错误；普通索引器会检查。它不把Capacity中尚未使用的预留空间变成有效字符。[Chars API](https://learn.microsoft.com/en-us/dotnet/api/system.text.stringbuilder.chars?view=net-10.0)

<a id="c14-builder-chars-length-table"></a>
原Q025-A-B030五行边界表，补足负索引及get/set区别：

| 操作 | 是否允许 | 结果 |
| --- | --- | --- |
| `sb[i]`，`0 <= i < Length` | 允许 | 正常读写一个有效码元 |
| `sb[i]`，`i < 0`或`i >= Length` | 不允许 | 读抛IndexOutOfRangeException；写抛ArgumentOutOfRangeException |
| `sb.Length = 10; sb[9] = 'a';` | 允许 | 索引9已成为有效范围 |
| `sb.Length = 5; sb[5] = 'a';` | 不允许 | 等于Length，写越界 |
| `sb.Capacity = 100; sb[50] = 'a';`，原Length不足51 | 不允许 | 增加Capacity不会自动增加Length |

## “常规格式、调用线程文化”要落实到具体类型

来源Q026—027。原表的意思是：数值、日期等类型有默认文本表示，许多会使用当前文化；`Append(Object)`本身仅在非null时调用对象无参ToString，再追加结果。这个概念伪代码可保留：

```csharp
// 说明Append(object)这一条路径，不代表每个Append重载都先box到object。
public StringBuilder Append(object value)
{
    if (value == null) return this;
    return Append(value.ToString());
}
```

`Object`只声明无参虚ToString，没有`ToString(IFormatProvider)`重载。某些数值/日期类型另外提供provider重载，或实现IFormattable；任意自定义对象的无参ToString不必遵循G格式和CurrentCulture。`Append(int)`、`Append(decimal)`等又有专用重载，不应把`Append(42)`等全说成Append(object)装箱。[Object.ToString](https://learn.microsoft.com/en-us/dotnet/api/system.object.tostring)、[Append重载](https://learn.microsoft.com/en-us/dotnet/api/system.text.stringbuilder.append)

数值123无参常见输出123；DateTime无参通常按当前文化的G日期时间格式。但`DateTime.Now.ToString()`的日期时间来自实际Now，原2026/1/15或12/15示意不是固定输出：

原Q026还分别列出三种格式的示意：`d` → `2026/1/15`，`D` → `2026年1月15日`，`G` → `2026/1/15 10:30:00`。它们可作为相应旧zh-CN文化规则下该日期/时间的教学示意，不是DateTime.Now的固定值，也不伪称本次作者执行所得。现代同一文化数据的D格式可能另含星期，实际显示按目标及文化配置判断。

```csharp
int num = 123;
Console.WriteLine(num.ToString());
DateTime now = DateTime.Now;
Console.WriteLine(now.ToString());
```

<a id="c14-format-and-culture"></a>
## format与provider：同一模具可用不同材料

来源Q027、Q030、Q031。IFormattable定义相应`ToString(string format, IFormatProvider formatProvider)`；在原C#5语境可用非nullable注解签名，现代注解为string?/IFormatProvider?。类型解释format，provider通过GetFormat提供所需信息；CultureInfo是provider的一种实现，NumberFormatInfo和DateTimeFormatInfo也可直接提供相应规则。接口不是“任意对象都有这个重载”。

<a id="c14-format-specifiers"></a>
### 标准说明符和自定义字符串

原G/C/D/N/d/T及yyyy-MM-dd、##,###.00、yyyy-MM-dd HH:mm:ss.fff等说明保留。说明符含义按类型、大小写、标准/自定义上下文解释：整数D是十进制整数格式，DateTime的D是长日期、d是短日期；decimal不支持整数D。C、N等标准格式可带精度如C2/N2，因此“标准一定只有一个字符”错误。某些单字符也有转义/自定义用法；不能说用户传任何字符串任何类型都必须支持。[标准数字格式](https://learn.microsoft.com/en-us/dotnet/standard/base-types/standard-numeric-format-strings)、[标准日期格式](https://learn.microsoft.com/en-us/dotnet/standard/base-types/standard-date-and-time-format-strings)

format可描述输出形状，provider供应文化符号；原“模具/材料供应商/工人”“形状说明书/工具仓库”的类比保留。实际自定义provider也可提供执行逻辑，并非纯静态材料；格式处理也包含算法、可能使用日历等，不能把ToString判成“static简单拼接”、Compare判成“dynamic才能复杂”。这里没有代言CLR团队的唯一历史动机。

### Format/AppendFormat的原金额、日期和订单导出

## 比较的culture/options与格式化的format/provider

### format解析不是两个Replace就能模拟货币规则

Q031原伪代码先取NumberFormatInfo，再把`value.ToString()`的小数点/逗号互相Replace后前缀货币符号。这既没有可靠分组，也受当前文化干扰，第二次Replace可能再次改掉刚生成的分隔符；德国货币符号也常在数值后。该伪代码不可作为实际Decimal算法。

```text
具体类型按format选择所支持的格式；取得适用NumberFormatInfo。
按该格式的分组大小、小数位、正负样式、符号位置等规则处理数值。
使用对应符号/分隔符生成文本；不能靠已有文化文本的两个Replace代替。
实际代码直接调用：price.ToString("C", CultureInfo.GetCultureInfo("de-DE"))。
```

format用字符串可表达原yyyy-MM-dd HH:mm:ss.fff等开放模板，不仅是有限枚举名；每个消费者仍有自己的语法和错误处理，不能声称任意字符串都自动有效。“价格是___元/词典元→$”填空题与“足球规则书/VAR/裁判判罚”原类比也保留：模板选呈现，规则/选项选比较；format处理实际数值不只是把元字替换美元字符。

<a id="c14-encoding-model"></a>
## 编码：从码元序列到文件、网络和串口字节

Q032开始把内存中的String接到IO。字符身份/码点、UTF-16码元、文本元素和编码后字节须分层：C# char固定16位；把String编码成UTF-8、UTF-16或其他字节序列时，长度由所选编码、输入及回退决定。CultureInfo负责此前数字/日期等文本生成或比较规则，Encoding负责相应码元到字节及反向转换。

Unicode提供字符与码点及相关属性/规范，不等于UTF-16；“Unicode”在.NET API名字中有时指特定UTF-16小端Encoding，不能用这个名字证明整个Unicode标准只有一种编码。GB2312/GBK是历史编码/代码页体系，不是完整Unicode的另一种等价表示；只能表达其支持的字符或采用回退。

原T独有“想法→中文写下的想法→摩斯密码→翻回中文”的完整类比保留：String表示已有想法的文本，编码像选定密码规则，解码像按同一规则恢复；开头标识可提示规则。UTF-16不等中文语言，BOM也不识别任意自定义密码/所有编码。原Web接口GBK而前端按UTF-8读、文件写读默认不同的场景仍是必须按协议匹配的例子；IO也可能直接存二进制，不必所有编码操作最终都创建String。

<a id="c14-encoding-byte-examples"></a>
### 😀并不能用“一字符等于两字节”概括

E14-123，保留原代码的两种编码及.Length对照：

```csharp
string s = "😀";
Console.WriteLine(s.Length); // 2 UTF-16码元
byte[] utf8Bytes = Encoding.UTF8.GetBytes(s);
Console.WriteLine(utf8Bytes.Length); // 4
Console.WriteLine(BitConverter.ToString(utf8Bytes)); // F0-9F-98-80
byte[] utf16Bytes = Encoding.Unicode.GetBytes(s);
Console.WriteLine(utf16Bytes.Length); // 4
Console.WriteLine(BitConverter.ToString(utf16Bytes)); // 3D-D8-00-DE，小端
```

这里两种编码恰好都是4字节；区别在表示和其他输入的大小分布，不应沿用原“看这个例就知两种字节数完全不同”的注释。UTF-8的4字节scalar在String里占2个码元，故它也不是突破`s.Length * 3`的反例：按默认替换、无状态完整String的通常UTF-8范围，每码元三倍可覆盖此emoji（6≥4）。但这可能浪费、有整数溢出/大分配风险，自定义fallback可能输出更多字符，流式状态也有额外边界；实际用GetByteCount/GetMaxByteCount等适用API，不能把一个粗界套所有编码配置。

### Encoder/Decoder记住跨块的未完成序列

原1GB文件、网络流分块处理场景保留：无需一次装下全部数据。Encoder收到的是完整char码元，可能记住一个高代理待下一块低代理，不是“半个UTF-16码元”。Decoder可记住UTF-8等不完整字节序列。原E4 BD其实是**2字节**，是你的UTF-8 E4 BD A0前两字节；下一块A0才完成一个码元你。

E14-128，保留原FileStream test.txt、1024字节块、GetChars(false)和最后flush(true)流程，修正缓冲区界及处理末尾输出；C#5使用using块：

```csharp
Encoding utf8 = Encoding.UTF8;
Decoder decoder = utf8.GetDecoder();
byte[] byteBuffer = new byte[1024];
char[] charBuffer = new char[utf8.GetMaxCharCount(byteBuffer.Length)];
StringBuilder text = new StringBuilder(); // 示例处理目标；大文件可增量交下游
using (FileStream fs = File.OpenRead("test.txt"))
{
    int bytesRead;
    while ((bytesRead = fs.Read(byteBuffer, 0, byteBuffer.Length)) > 0)
    {
        int charsDecoded = decoder.GetChars(
            byteBuffer, 0, bytesRead, charBuffer, 0, false);
        text.Append(charBuffer, 0, charsDecoded);
    }
    int tail = decoder.GetChars(byteBuffer, 0, 0, charBuffer, 0, true);
    text.Append(charBuffer, 0, tail);
}
```

GetMaxCharCount按所选编码/fallback给保守范围，不把字节块1024直接等同任何配置所需char1024。GetChars缓冲不足可抛；固定缓冲容量时也可用Decoder.Convert和bytesUsed/charsUsed/completed循环消费。flush false告诉编码器/解码器还有后续，true要求处理最后残留并按回退处理无法完成的尾部；其作用不是保证任何坏输入都能无损“刷出半字符”。[GetMaxCharCount](https://learn.microsoft.com/en-us/dotnet/api/system.text.encoding.getmaxcharcount?view=net-10.0)

作者小文件探针将边界安排在1023个a后的你/😀，再1024个z，原1024读取流程两库完整恢复2050码元、2054UTF-8字节；未真实读写1GB。另直接分两块E4BD/A0，先输出0char再1char你；编码分D83D/DE00高低代理，先0byte再F0 9F 98 80。后续流式例仍按各实际输入保留，不只引用这一验证概括全部编码。

## 代码页的覆盖范围和不可逆回退

Q033的原书问题是在警告：将16位码元表示的文本交给覆盖有限的编码时，不能保证所有字符都能表示；除非兼容遗留资料/应用，否则宜选适合协议的Unicode编码。代码页是具体编码的标识/映射，不是微软把128—255这128个数字一一塞成几千个汉字。CP936含多字节字符，CP950又是不同映射；ASCII是公开标准，GBK也不是程序私有的秘密表。旧字符编码的历史不能全归于微软一个方案，亦不能把GBK本身说成一定在Unicode出现前发明。

原方言/普通话、局部圈子/全球身份证两个类比保留：选定规则的参与者可交换，换规则而不声明可能误读；覆盖之外要失败或回退。Unicode为已定义字符分配码点，UTF编码可表示有效Unicode scalar；这不意味着任意破损字节、未配对代理项或任意协议转换都保证不丢信息。

### 码点身份与码元容器

Q036的小区邮编比喻另保留：Unicode小区给😀门牌1F600、中门牌4E2D；UTF32用一个4byte大箱，UTF16用16位标准箱、😀两个箱D83D/DE00，UTF8用8位小单位组成1—4个byte。这里“2字节”不是“两位十进制邮编”，Unicode约110万个码点位置也不是全都有已分配字符的百万房间。

Q038用户问“二声a是否可直接有一个编号”，答案先用实际反例说明：á确有U+00E1；a+0301是规范等价的分解形式。不是一切元素缺单独编号，也不是Unicode只为每个显示成品建唯一码点。原乐高类比保留：基础砖和组合标记可构成很多形态，不必每种造型单独开模；显示/文字语义和规范分割仍约束组合，不能保证任意拼法都是有意义字符。

### 越南语与临时标记场景

原越南语a、ă、â及声调/附加元音符号场景保留，修正错误量化：Unicode16说明有12个元音字母和5个书写声调标记；无声调标记的平调另计，不是只有5个声调，也不是近200个基字符要用几万/几十万码点。大量元音+调号已有预组合形式，NFC可组合，NFD可拆；不能用原臆造“占Unicode5%”证明组合必要性。[Unicode16拉丁文字/越南语](https://www.unicode.org/versions/Unicode16.0.0/core-spec/chapter-7/)

原语言学研究给a加小箭头表示发音、数学带标记字母、少数民族特殊变体、新造网络符号等动态/临时组合需求均保留。现有定义过的标记可组成新序列；新增字符/标记仍需相应定义，字形呈现也靠字体/渲染，不能说任何新符号都无需Unicode变化。原中文注音、韩文、班巴拉语及原住民文字的多样性提示保留为需按各文字规则处理，不编造统一组合数量。

数学例ā、ǎ、ȧ、ạ恰好都有预组合：U+0101/U+01CE/U+0227/U+1EA1；本机NFD分别a+0304、a+030C、a+0307、a+0323，不能沿用原“这些只有组合序列”的反例。T提苏格兰盖尔语/夏威夷语的组合需求也需逐个字符核对，不能仅按语言名字宣称没有预组合。变体选择器是另一类按已定义变体选择显示形式的机制，不是任意在同码点下切换简繁字、全部glyph的通用开关。

原T完整“预制菜/现炒/后厨/旧系统赶时间”比喻另保留：预组合像某种现成菜，分解序列像用基础原料组合，后厨需按规则处理；两者可表示规范等价内容，不能据类比判一种始终次要、另一种可以不限制搭配。有限码点空间与大量潜在组合是扩展性背景，不采用源“去掉保留/私用后80万可用”的无依据数量，也不代言Unicode唯一设计动机。

<a id="c14-normalization"></a>
### 规范化与比较、分割、文件系统各自的边界

NFC/FormC执行规范分解/重排并在适用条件下组合；NFD/FormD为规范分解；NFKC/FormKC和NFKD/FormKD还涉及兼容分解。NFC不是“把任何组合都变一scalar”，兼容规范化也可能损失应用想区分的全角/上标等形式。[Unicode规范化UAX15](https://www.unicode.org/reports/tr15/)

E14-138保留原两个表示、InvariantCompare与两种Normalize操作，并补原值等价的不同条件：

```csharp
string precomposed = "\u00E1";
string combining = "\u0061\u0301";
Console.WriteLine(string.Compare(precomposed, combining,
                                StringComparison.InvariantCulture)); // 本机两库0
Console.WriteLine(precomposed == combining); // False，默认Ordinal值不同
string normalized1 = precomposed.Normalize(NormalizationForm.FormD);
string normalized2 = combining.Normalize(NormalizationForm.FormC);
Console.WriteLine(normalized1 == combining); // True
Console.WriteLine(normalized2 == precomposed); // True
```

两种表示规范等价不要求所有比较自动返回0。Ordinal直接比较码元，其他文化模式的具体行为按规则/选项/版本判断；StringInfo是元素分割，不自动把内容NFC/NFD改写。原欧洲常用字、越南语/非洲文字、数学/语音标记的观察场景仍保留，不能说大多数程序默认NFC或只有冷门语言才有组合。

Windows文件IO将路径看成WCHAR序列，不自动将组合文件名变NFC；原“Windows/NTFS都是NFC、Linux都是NFD”不成立。具体macOS文件系统也要按实现/接口判断，不把历史某种行为套全平台。[Windows文件名规则](https://learn.microsoft.com/en-us/windows/win32/fileio/maximum-file-path-limitation)

## Encoding静态属性的具体规则

Q039原引用列UTF8、Unicode、BigEndianUnicode、UTF32、UTF7、ASCII、Default，并指Win32 GetACP和控制面板“非Unicode程序当前语言”解释Framework活动代码页；Q040再问GetEncoding。原工具箱、正规军/历史遗留/墙头草分类比喻保留其“先辨每个工具用途”的目的，但BigEndianUnicode是确定大端规则，不能归为随系统乱变的危险工具；ASCII在明确ASCII协议中也完全合理。

Unicode属性是UTF16 LE，BigEndianUnicode是UTF16 BE；中分别2D 4E和4E 2D，原A/T把两者交换了。UTF32属性通常LE，按scalar4byte，不能据此保证对文本元素随机访问总最快或ICU内部一律如此。UTF16.GetBytes也会处理未配对代理/fallback等，不是任意字符串都无条件直接复制内存即可。

ASCII覆盖字母、数字、符号、控制等128个码位，不仅英文字母；GetByteCount("你好")默认本机为2，问题是内容已替换，不是调用必失败。UTF7是原书时期可见API，现代.NET5起其属性/构造器obsolete，并默认从GetEncoding等入口移除；说明变化不能倒写成Richter当时已知道后续弃用。[UTF7的.NET5变化](https://learn.microsoft.com/en-us/dotnet/core/compatibility/core-libraries/5.0/utf-7-code-paths-obsolete)

<a id="c14-streaming-encoder-convert"></a>
### 原4096输出缓冲的Encoder.Convert流程

E14-149保留hugeString、4096byteBuffer、charIndex、charsUsed/bytesUsed/completed及末尾flush，去掉每轮复制整个ToCharArray、明确fileStream由调用者提供：

```csharp
static void WriteEncoded(Stream fileStream, string hugeString)
{
    Encoder encoder = Encoding.UTF8.GetEncoder();
    char[] source = hugeString.ToCharArray(); // 原数组重载需要；只转换一次
    byte[] byteBuffer = new byte[4096];
    int charIndex = 0, charsUsed, bytesUsed;
    bool completed;
    do
    {
        encoder.Convert(source, charIndex, source.Length - charIndex,
            byteBuffer, 0, byteBuffer.Length, false,
            out charsUsed, out bytesUsed, out completed);
        fileStream.Write(byteBuffer, 0, bytesUsed);
        charIndex += charsUsed;
        if (!completed && charsUsed == 0 && bytesUsed == 0)
            throw new InvalidOperationException("输出缓冲不足以推进转换");
    } while (!completed);

    do
    {
        encoder.Convert(source, charIndex, source.Length - charIndex,
            byteBuffer, 0, byteBuffer.Length, true,
            out charsUsed, out bytesUsed, out completed);
        fileStream.Write(byteBuffer, 0, bytesUsed);
        charIndex += charsUsed;
        if (!completed && charsUsed == 0 && bytesUsed == 0)
            throw new InvalidOperationException("输出缓冲不足以完成末尾回退");
    } while (!completed);
}
// 原占位输入保持：实际数据由调用者获得。
// string hugeString = "超大的字符串...😀...";
// using (FileStream fileStream = File.Create("encoded-output.bin"))
//     WriteEncoded(fileStream, hugeString);
```

charsUsed是本次消费的输入char数量，bytesUsed是本次写入输出byte数量，completed依本次输入/flush要求判断，不能简单解读“缓存必空”。共享验证使用4097个a+😀+孤立高代理：false第一轮4096/4096/false，第二轮4/5/true，此时末高代理仍待处理；最后空输入flush true产生0/3/true，输出与一次性默认编码逐byte一致。补充压力仅几千单位，未跑10G/网络；末尾自定义回退很大或缓冲不足时需继续处理，不假定一次flush对所有配置足够。

该数组版本仍一次分配整char[]；若目标是真正增量输入且不想持有完整hugeString，可从上游连续给小char块或选目标支持的Span重载。原高/低代理分块的目的另保留：strictUTF8 Encoder收D83D/false先0byte，再DE00/true得到F0 9F 98 80；不是缓存半个char码元。

<a id="c14-two-byte-context"></a>
## 关键疑问：原书“每个字符2字节”究竟在说什么

Q044不能只靠聊天推测第一版年份、作者只懂BMP或emoji未流行就替原书定性。本地第4版已实际核原页：印刷313/PDF物理330的14.6.1用UTF16 NetworkStream先读5byte再7byte，按16位单元解释每次未完成一个单元的尾部；同页译注又区分抽象codepoint可能需多个byte。这里把character理解为C# char/码元时，2byte成立；若理解为有效Unicode scalar，则可1—2个16位单元，即2或4byte；若指文本元素，还可能更多。

<a id="c14-base64"></a>
## Base64：把已有二进制包装成文本

Q047—048的UTF编码与Base64分工应明确：前者将文本表示转换为字节，后者把任意byte序列包装成规定字母表的文本。图片、证书、密文、GUID原始bytes等可能不是有效UTF8文本；若文本接口要求这种包装，可编码后传输再还原。Base64普通结果是.NET String，内部仍用UTF16码元保存，但内容只含相应ASCII符号。

<a id="c14-base64-vs-encoding-table"></a>
Q047-A-B011三行4列表：

| 方案 | 输入 | 输出 | 用途 |
| --- | --- | --- | --- |
| UTF8 | 相应Unicode文本/UTF16码元 | 按scalar规则生成byte序列 | 字符文本的字节表示，长度依输入 |
| 原GBK/CP936场景 | 需要其支持字符/回退策略的文本 | 单/多byte映射 | 明确要求此编码的旧资料/协议 |
| Base64 | 任意二进制bytes | 规定ASCII数据符号与必要padding | byte数据的文本包装，不为它定义自然语言字符身份 |

每24bit（3byte）分四组6bit，用64个**数据**符号A—Z/a—z/0—9/+/查表；`=`另为填充，不算这64个数据符号。标准带padding、无换行输出的长度为`4 × ceil(n/3)`，n=0时0；短输入1byte变4字符，不是所有输入都固定1.33倍。大组整体通常约4/3。Base64不加密、认证或压缩数据。[RFC4648](https://www.rfc-editor.org/rfc/rfc4648)

<a id="c14-base64-byte-example"></a>
E14-153保留原四byte往返：

```csharp

string base64 = Convert.ToBase64String(binary);
Console.WriteLine(base64); // EjRWeA==
byte[] decoded = Convert.FromBase64String(base64);
// decoded仍12 34 56 78
```

E14-154保留原3个zero与文本bytes计数，以及错误方法所求目标的区别：

```csharp

string s = Convert.ToBase64String(b);
Console.WriteLine(s.Length);                        // 4，AAAA
Console.WriteLine(Encoding.UTF8.GetByteCount(s));    // 4

// 45 6A 52 57 65 41 3D 3D：Base64这段文本的UTF8，不是原binary

```

为传输Base64文本而再UTF8编码，第一种操作可以正确；若目标是恢复原binary，则用FromBase64。反向链条文本→UTF8 bytes→Base64→传输→FromBase64→UTF8解码也保留，不把二者说成不得组合。Base64文本排序不等binary按数值排序，需要的比较语义依应用，不用自然语言CompareTo猜原byte意义。

<a id="c14-securestring"></a>
## SecureString的历史设计与实际保护范围

Q001提到这一主题，之后多轮结尾又把它描述成“唯一绕过String、字节层、安全终极、阅后即焚/彻底防泄露”。这些混合技术断言不能因为带邀请语气就整段丢弃，也不能原样当结论。

原书Framework/Windows历史目的应保留：普通String不可变，修改/构造可能留下多个明文版本；赋null或等待GC不承诺立刻擦除。SecureString可以维护自己控制的缓冲，允许字符逐项修改、标只读并Dispose；适用实现可在不使用时保护内部内容，避免始终以普通String保存全部敏感值。原书本地印刷315—317/PDF332—334明确讨论非托管缓冲、修改时短暂解密、再保护以及清理，属于该实现和时代的解释。

原书列的CSP、X.509证书、特定用户进程启动、EventLogSession、WPF PasswordBox等Framework支持方向说明它依赖少数接受相应对象的API，并非把任意应用字符串替换后所有接口就自动更安全。使用者需要明文时可能导出临时缓冲，须缩短寿命并按分配方法配对释放；这仍存在明文窗口，不是彻底绕开UTF16码元、Encoding或所有可能副本的安全边界。

### 字符修改、只读及Dispose的机制示意

E14-160使用作者非秘密ad数据，只演示历史API，不收集用户密码：

```csharp
using (SecureString ss = new SecureString())
{
    ss.AppendChar('a');
    ss.AppendChar('b');
    ss.InsertAt(1, 'c');
    ss.RemoveAt(1);
    ss.SetAt(1, 'd');
    ss.MakeReadOnly();
    Console.WriteLine("{0}/{1}", ss.Length, ss.IsReadOnly()); // 2/True

    IntPtr p = IntPtr.Zero;
    try
    {
        p = Marshal.SecureStringToCoTaskMemUnicode(ss);
        // 只在这里交给需要此明文表示的受控操作；不保留普通String副本。
    }
    finally
    {
        if (p != IntPtr.Zero) Marshal.ZeroFreeCoTaskMemUnicode(p);
    }
}
```

这里IntPtr入口不必在C#方法签名写unsafe；若像原书示范改用char*访问，才需相应unsafe上下文/选项。Marshal分配/释放必须按配对方法，例如SecureStringToBSTR配ZeroFreeBSTR，CoTaskMemUnicode配ZeroFreeCoTaskMemUnicode。Dispose只对所管理缓冲承担其契约，不能证明历史拷贝、日志、其他String或外部组件中的所有明文都已清掉。

<a id="c14-securestring-modern"></a>
### 现代变化：只读Span并不能自动清零或替代安全存储

官方不建议在现代.NET新开发/迁移时采用SecureString；不同平台保护机制不同，非Windows平台不为内部存储执行同样加密，Windows使用时也有解密/明文交互窗口。现代建议不能反过来抹掉原书历史设计价值，也不能据“.NET API少数接受”推论其在所有目标都已删除。[SecureString官方说明](https://learn.microsoft.com/en-us/dotnet/api/system.security.securestring?view=net-10.0)

Q001提出ReadOnlySpan<char>+尽快清零：只读Span是访问视图，自己不能写内容或调用一个相应Clear保证；作者直接赋s[0]的现代编译反例为CS8331。拥有可写缓冲的调用者可按设计清自己拥有的范围，但不能借这个视图倒推已清所有复制/编码输出或得到加密保护。Writable Span<char>.Clear可改它借用的范围；是否存了其他副本、是否被发布/记录、生命周期如何，仍需应用管理。

原ProtectedMemory方向也保留并限定：它是特定平台/API支持的内存保护机制，接受相应byte缓冲及scope，长度等有规则（常要求16倍数），解保护后仍有明文。它不是所有现代目标都有的自动替代，也不与只读Span或及时清理逻辑等同。[ProtectedMemory API](https://learn.microsoft.com/en-us/dotnet/api/system.security.cryptography.protectedmemory?view=netframework-4.8.1)

作者两库生命周期探针实际核Append/Insert/Remove/Set、MakeReadOnly后追加异常、非秘密a/d的临时Marshal读取/配对释放、Dispose后访问异常。没有扫描真实秘密、验证非Windows环境或证明所有内存副本擦除；不可把API调用成功当成全进程保密性证明。

## 原书语境与现代变化

原书以Framework/C#5为主，本章正例通常按对应API理解；“实现观察”只指作者记录的Windows Framework4.8或.NET10.0.12，不代表跨平台固定结果。以下各项在前文已有完整原输入、程序和原因，这里给版本阅读入口：

| 主题 | 原书/旧目标范围 | 现代阅读边界 |
| --- | --- | --- |
| Char扩展调用和语法 | 静态分类成员仍按声明使用；旧C#5可用适用扩展方法 | 表达式体、关系模式等按语言版本；ASCII范围不是Unicode IsDigit的替代 |
| String构造/复制 | Framework new String(string)不适用；Copy历史语义 | 支持Span构造器/隐式转换的现代目标可绑定new String(string表达式)；Copy现代obsolete且不保证新引用 |
| 留用与普通literal | #US、对象共享与global intern分别；历史NGen模式有边界 | 同assembly普通stringliteral语言保证不因“全局池不保证”而一并删除；跨程序集/动态new/NativeAOT等另判 |
| 文化比较/显示 | Framework本机排序/显示为该数据环境观察 | NLS/ICU、数据版本和模式可能变；不把straße/长日期输出写固定全球规则 |
| 文本元素 | 旧StringInfo支持相应分割规则 | .NET5起UAX29扩展grapheme影响ZWJ/旗帜/肤色；Rune为scalar，API目标而非要求C#9 |
| Builder/格式化 | Framework4时代已使用块结构，Max小Append可超配置并非仅modern | GetChunks/Span/插值handler按目标；Clear容量变化及Format内部路径不是语言固定保证 |
| 编码 | Framework Default活动代码页、旧编码较广泛可用 | modern DefaultUTF8；注册provider可影响GetEncoding(0)，不改Default；UTF7限制和BOM读取层需分别看 |
| Base64/SecureString | Convert旧API/Framework历史安全类型 | 手工URL早版本可用、现代专用API另标；SecureString不建议现代新用，平台保护并不一致 |
